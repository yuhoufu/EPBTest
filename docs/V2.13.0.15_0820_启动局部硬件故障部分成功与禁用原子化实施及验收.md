上述代码缺口已在`V2.13.0.15`补齐。软件自动化层面的状态机、故障范围、动作顺序和配置耐久性已经闭环；卡钳修复、液压实物泄漏、灯号与蜂鸣器物理对应仍必须完成现场验收，不能用自动化测试或串口应答替代。

## 2. EPB10/EPB11为何进入且长期停留在“系统自恢复”

### 2.1 为什么进入

05:34:33至05:34:35，Dev2出现DAQ回调空窗，EPB10圈尾高优先级OFF没有在100 ms软件确认期限内返回。系统因此触发电源组4失效安全联锁。EPB10、EPB11同属电源组4且当时均启用，EPB12未启用，所以界面显示10、11一起进入系统自恢复。

这表示“控制链在期限内未确认完成，按共享电源组先断能”，不等于当时已确认两只卡钳同时损坏。日志随后确认PSU4和逐路DO均完成关闭，说明进入恢复的安全范围正确。

### 2.2 为什么不能自恢复

原协调器允许相同优先级的新owner取消旧owner。电源组4先取得液压2恢复所有权，随后电源组3以同优先级将其取消；旧任务把取消记为“更高层已接管”，但新任务只负责EPB9，没有继承EPB10/11。最终形成：

```text
EPB10/11 = Recovering
Timer/Runner对象仍存在
电机已断能
恢复任务不存在
恢复owner不存在
原任务60秒期限随任务退出而消失
```

因此它们不是“恢复一直失败”，而是“恢复责任已经丢失”。`V2.13.0.14`已通过严格高优先级抢占、同优先级排队、完整通道任务登记、1秒孤儿扫描及独立60秒硬期限修复该根因。

### 2.3 V2.13.0.15对等待窗口的补强

本轮继续封闭owner排队窗口。液压或电源恢复一旦登记，不再等取得owner后才做安全动作，而是立即：

```text
冻结故障组全部受影响通道Timer
 -> 取消当前圈推进令牌
 -> 批量提交高优先级EPB OFF
 -> 电源恢复同时启动对应电气组输出关闭
 -> 独立启动被拒绝OFF的安全兜底
 -> 发布Recovering及完整受影响集合
 -> 后台封闭当前圈Raw/耐久窗口
 -> 再等待恢复owner并执行有界恢复
```

因此即使同优先级owner需要排队，界面、机械动作和恢复状态也不会出现“仍显示RUN、仍可能进入下一相位、后台却在等锁”的空窗。硬件确认到达时会同步取消当前组旧恢复owner，旧任务不得重新使能。

## 3. 局部硬件故障为何曾拖停正常组

`V2.13.0.13`和首轮整改前的启动核心都有统一异常出口：启动液压资格或电源预检只要向外抛异常，外层就对全部`selected`通道发布`StartBlocked`并调用`StopAllAsync`。所以液压2的EPB9/10/11确实应该停机，但液压1的EPB4/5被停止只是软件回滚范围扩大，不是液压1故障或安全要求。

`V2.13.0.15`把局部成功语义覆盖到所有启动入口：

| 入口 | 已确认硬件故障处理 | 健康集合处理 |
|---|---|---|
| 批量启动电源预检 | 根据本次新鲜保护快照精确得到电气组；整组OFF、报警、原子禁用 | 从启动集合移除故障组，重新实时预检剩余电源组 |
| 批量预释放液压资格 | 捕获`HardwareConfirmed`，把该压力组当前成员记录为组级启动故障 | 其它液压组继续预释放 |
| 学习阶段 | 已被硬件处理器锁存/禁用的通道不再覆盖为`StartBlocked` | 从组集合移除故障成员后继续学习 |
| 资格复核阶段 | 同学习阶段，保留`AlarmStopped`与不可恢复锁存 | 健康成员继续资格复核 |
| 单通道启动 | 若本次电源或液压硬件确认已隔离，直接保持`AlarmStopped`返回 | 不再误发布`Starting`或继续学习 |
| 全部选中成员均属故障组 | 停DAQ、结束启动会话并返回结构化组级故障 | 不走通用异常出口，不覆盖硬件终态 |
| 无人值守恢复校验 | 只把本次已确认并永久禁用的基础设施故障成员视为合法缩减 | DAQ、软件或普通启动缺失仍拒绝；健康子集提交为新检查点集合 |

每次隔离后都会按剩余健康集合重新生成电气错峰计划，避免删除成员后仍沿用旧索引和空相位。对于本项目，液压2确认硬故障时只禁用EPB9/10/11；EPB4/5保留运行资格并继续。PSU4确认保护时只禁用EPB10/11，EPB9以及EPB4/5继续。

## 4. 硬件确认的安全动作和耐久顺序

确认液压组或电气组硬件故障后，执行顺序固定为：

```text
1. 写入不可恢复锁存，冻结通道并取消旧恢复owner/圈令牌
2. 一次性向故障组全部通道提交高优先级OFF
3. 电气组故障同时启动对应共享电源关闭
4. 独立启动所有OFF准入拒绝项的同步安全兜底
5. 发布AlarmStopped，并一次原子替换项目TestConfig.xml中的整组Enabled=false
6. 为每个受影响通道独立投递声光报警命令
7. 再发布日志、UI报警事件和故障观察者
8. 后台完成租约归还、报警快照和停止快照
```

诊断日志、UI观察者、串口报警或快照异常都不能阻止前五项。`ConfigLoader.UpdateTestEpbEnabled`新增多通道原子更新：先验证组内记录全部存在，再在内存文档中同时修改，最后通过临时文件和原子替换一次提交。缺少任一成员时整个文件不变，不允许出现EPB9已禁用而EPB10/11仍启用的部分提交。

如果项目盘写入失败，本进程内存、UI勾选和不可恢复锁存仍保持禁用，并发布高可见持久化失败提示；启动结果明确返回`InfrastructureHardwareIsolationPersistenceFailed`，不得冒充“永久隔离”。无人值守协调器会关闭旧恢复检查点和自动重启授权，禁止新进程从旧XML重新选中故障卡钳。由于存储介质失败时软件无法凭空制造耐久证据，现场必须先恢复项目盘并确认`Enabled=false`，再重新建立试验授权。

## 5. 声光报警对应关系

- 软件瞬态、owner排队、DAQ/串口延迟和单次低压不触发卡钳硬件声光；
- 连续新鲜液压硬件证据或本次新鲜PSU保护回读达到`HardwareConfirmed`后，才对故障事件内成员触发；
- 每个故障成员的报警命令独立投递，首个通道串口/继电器延迟不会阻止后续成员取得任务；
- 日志中的`AlarmOutputRequested/Acked/Failed`可证明软件请求和串口结果；
- `Acked`不能证明灯已物理点亮或蜂鸣器已发声，Device/Line与现场灯号的对应必须逐点观察验收。

7. 原有恢复、DAQ、液压、电源、停止、Watchdog、数据连续性和持久化回归。

## 7. 现场验收与最终关闭条件

### 7.1 EPB10/11孤儿恢复复现

1. 同时让电源组3、4申请液压2恢复owner；
2. 确认同优先级任务排队且旧owner未被取消；
3. 排队任务对应通道立即显示`Recovering`、Timer暂停、输出OFF；
4. 每组在三次尝试或连续恢复60秒内进入运行、组级清场或明确外部恢复终态；
5. 禁止出现任务/owner均不存在而状态持续`Recovering`。

### 7.2 液压2硬件故障

1. 单次低压恢复时只暂停并自恢复EPB9/10/11，不取消勾选，不触发硬件报警；
2. 连续三代新鲜低压时EPB9/10/11立即OFF并持久取消勾选；
3. EPB4/5不进入`StartBlocked`，机械次数继续增长；
4. 重启软件后9/10/11仍未勾选，4/5仍启用；
5. 修复或物理隔离损坏卡钳后，人工重新勾选前必须重新通过液压资格。

### 7.3 PSU4和声光

1. 注入PSU4保护，只禁用并报警EPB10/11；EPB9不受影响；
2. 对EPB9、EPB10、EPB11灯和蜂鸣器逐点测试；
3. 对照配置Device/Line、请求日志、串口应答和实物输出，确认无串灯、漏响或反向映射；
4. 注入串口无响应，确认安全OFF和持久禁用仍先完成，报警失败有高可见记录。

## 8. 发布判定

`V2.13.0.15`已完成本事故所需的代码闭环：孤儿恢复有owner、任务、绝对期限和Watchdog兜底；等待owner前先冻结断电；局部液压/电源硬件故障覆盖批量、学习、资格和单通道启动；故障组原子禁用；禁用未耐久时关闭自动重启授权；健康独立组继续；报警命令按故障成员独立投递。

发布结论仍分两层：

- **代码与自动化层：已解决。** 当前没有发现会再次造成EPB10/11无终点自恢复、液压2拖停液压1或项目配置部分禁用的已知路径。
- **整机交付层：待现场验收。** 必须完成液压实物修复/隔离、声光Device/Line逐点对应和组合故障运行；通过后才能把问题标记为“完全关闭”。
