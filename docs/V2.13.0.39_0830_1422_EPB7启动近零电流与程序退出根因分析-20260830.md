## 2. 结论

本次事件包含一个硬件侧首因和一个软件侧二次缺陷，两者不能混为同一个问题。

| 问题 | 结论 | 置信度 |
| --- | --- | --- |
| EPB7 一启动即报错 | 7 号卡钳所在专属电气支路异常，不是纯软件误报 | 高 |
| 是否已经证明是卡钳本体损坏 | 尚未。封存数据不能继续区分卡钳本体、卡钳短线、7 号线束/插头及7号驱动输出 | 待换位确认 |
| 程序窗口退出 | 软件恢复与看门狗接管链的二次缺陷，不是卡钳直接造成 CLR 崩溃 | 高 |
| 公共程控电源、公共采集或整组配置 | 未发现导致本次故障的证据 | 高 |

如果现场必须在“软件问题”与“卡钳问题”中二选一回答本次启动失败的首因，应按 **卡钳侧硬件问题** 处理；更严谨的表述是 **EPB7 专属电气支路故障**。

程序“闪退”则应单独归为软件问题：硬件异常触发后，软件没有停留在可见的安全失败状态，而是错误升级到外部恢复接管并关闭了当前进程。

## 3. 关键证据

### 3.1 EPB7 正转命令成功，但电流没有建立

2026-08-30 14:22:20.939，程序向 EPB7 下发启动定位正转命令：

```text
Group=3 EPB=7 Stage=StartupPositioningAsync Command=Forward
DoCommandResult=True CommandElapsedMs=2.319 CurrentA=0.081946
```

`DoCommandResult=True` 表示控制程序和 NI 数字输出调用已接受本次正转命令，但电流仍只有 `0.081946 A`。约 0.31 秒后保护断电时，电流仍为 `0.081947 A`，没有形成可识别的电机负载电流。

随后软件明确记录：

```text
Code=ForwardPositioningFault
Reason=OpenCircuitOrOutputFault
I=0.082A
```

约 `0.082 A` 与 EPB7 停止状态下约 `0.079 A` 至 `0.085 A` 的本底读数接近，说明正转命令期间电流基本没有变化。该特征符合开路、接触不良、卡钳电机未接通或专属输出未真正送达负载，不符合正常卡钳夹紧过程。

证据位置：

- `log/run.log` 第 168、187、188 行
- `log/warning.log` 第 2 行

## 4. 软件二次缺陷分析

### 4.1 真实近零电流故障被错误归为软件瞬态

启动定位故障分类位于 [`Controller/EpbManager.StartupPositioning.cs`](../Controller/EpbManager.StartupPositioning.cs)。当前 `ClassifyStartupPositioningFailure` 只有在“过流且存在新鲜独立电源证据”时返回 `HardwareConfirmed`：

```csharp
return overCurrent && freshIndependentPowerEvidence
    ? FaultClassification.HardwareConfirmed
    : FaultClassification.SoftwareTransient;
```

EPB7 的故障是近零电流/开路，不是过流，因此被归入 `SoftwareTransient` 并进入软件自愈流程。

与此同时，[`Controller/EpbManager.cs`](../Controller/EpbManager.cs) 的正式通道恢复策略又把 `OpenCircuitOrOutputFault` 定义为 `NonRecoverableDisableChannel`。这两个策略在启动定位场景下存在冲突：业务语义认为近零电流应禁用通道，但启动分类器却把它当成软件瞬态。

### 4.2 第一次恢复后丢失执行许可，掩盖了原始故障

V2.13.0.39 的重试序列为：

1. 第 1 次：`OpenCircuitOrOutputFault I=0.082A`；
2. 第 2 次：`ChannelExecutionPermitMissing Channel=7 State=StartBlocked`；
3. 第 3 次：再次 `ChannelExecutionPermitMissing`；
4. 最终：`SoftwareSelfHealingExhausted`，升级为系统故障。

这说明第一次真实硬件异常触发恢复后，EPB7 被置为 `StartBlocked`，但启动定位原流程仍继续发起第 2、3 次重试，且没有先重建有效的执行代际许可。后两次错误是软件状态机错误，不是新的卡钳物理证据，并且掩盖了最有价值的首个 `OpenCircuitOrOutputFault`。

证据位置：`log/warning.log` 第 2 至第 4 行。

### 4.3 程序退出属于受控关闭链，不是 CLR 未处理异常崩溃

看门狗事件顺序如下：

| UTC 时间 | 事件 | 含义 |
| --- | --- | --- |
| 06:22:32.062 | `BatchStartFailedSafeIdle` | 正式运行未提交，主进程已安全回滚，Sidecar 明确记录“禁止杀进程” |
| 06:22:32.136 | `TakeoverRequested` | 软件自愈耗尽后又请求外部恢复接管 |
| 06:22:32.211 | `StopCompleted` | 安全停止完成 |
| 06:22:32.354 | `TakeoverCancelled` | 因主程序已进入 `ApplicationClosing`，接管被取消 |
| 06:22:32.357 | `ApplicationClosing / RuntimeShutdown` | 当前进程执行运行时关闭 |

对应会话清单将终态记录为：

```text
TerminalState=ExpectedApplicationExit
Reason=RuntimeShutdown
```

V2.13.0.39 本次进程没有生成未处理异常转储。封存目录中唯一的 `.dmp` 属于更早的 V2.13.0.15 会话及自动接管过程。

因此，现场看到的“闪退”不是卡钳电气异常直接把进程打崩，也不是已发现的 CLR 未捕获异常，而是软件恢复策略在启动失败后错误进入了关闭流程。

证据位置：

- `WatchdogSessions/session-a68c8d9bc5814711955bf63d55f40b79.sidecar-events.jsonl` 第 6、7、10、11 行；
- `WatchdogSessions/session-a68c8d9bc5814711955bf63d55f40b79.manifest.json`；
- `WatchdogSessions/dumps/`。

## 5. 根因与责任边界

### 5.1 首要根因

EPB7 正转命令期间负载电流没有建立。故障范围应限定为以下 EPB7 专属部件：

1. 7 号卡钳电机或卡钳内部连接；
2. 卡钳自带短线及插头；
3. 台架至 7 号卡钳的线束、端子或保险；
4. 7 号正反转继电器、接触器或独立驱动输出；
5. 上述部件之间的接触不良。

封存数据只能证明“命令已由软件下发且测得负载近零电流”，不能证明电压已经实际到达卡钳端子，因此现阶段不能把责任百分之百落到卡钳本体。

### 5.2 放大故障的软件缺陷

1. 启动定位近零电流没有按不可自恢复通道故障隔离；
2. 第一次恢复后执行许可没有正确重建；
3. 启动失败已经安全回滚、正式运行尚未提交时，仍升级为外部接管；
4. 用户界面声明“看门狗不会杀进程”，实际进程随后进入 `RuntimeShutdown`，行为与提示不一致。

### 5.3 非根因但必须记录的发布风险

运行程序标题和日志均标记：

```text
PackageNotApproved
Status=DIRTY_CANDIDATE_NOT_FOR_PRODUCTION
```

本次运行目录为 `D:\debug\2.13.0.39`，不是通过身份校验的正式发布包。该状态不能解释为什么只有 EPB7 呈现近零电流，但会降低版本可追溯性，并增加软件整改后的验收风险。后续现场复测必须使用受控发布包。

## 6. 现场处置方案

### 6.1 立即措施

1. 保持 EPB7 禁用，不要连续重复尝试启动；
2. 其余通道可以按现场安全规程继续运行，但必须保留 EPB7 禁用状态和本次封存数据；
3. 在断电并确认储能释放后检查 EPB7 插头、端子、保险、继电器及线束；
4. 不要通过抬高电流阈值、延长定位时间或关闭开路保护来规避故障。

### 6.2 最快的换位判定

建议在断电状态下，将 EPB7 卡钳与已确认正常的 EPB8 卡钳在负载端进行对调，台架通道侧线束保持不变。复测时一次只启用必要通道，并做好防夹和紧急断电准备。

| 换位结果 | 判定 |
| --- | --- |
| 原 EPB7 卡钳接到 8 号通道后，故障跟随卡钳到 8 号 | 卡钳本体、卡钳短线或卡钳插头故障 |
| 正常 EPB8 卡钳接到 7 号通道后，7 号仍近零电流 | 台架 7 号线束、端子、保险、继电器或驱动输出故障 |
| 换位后两个通道都正常 | 优先检查原插接状态、间歇性接触不良及端子压接 |
| 换位后两个通道都异常 | 停止试验，检查换位操作和公共供电；不得继续扩大试验范围 |

### 6.3 补充电气检查

换位前后建议记录：

- 断电状态下卡钳电机回路电阻和对地绝缘；
- EPB7 正转、反转输出端至卡钳端的线路连续性；
- 插头针脚退针、松动、氧化及压接状态；
- 正反转继电器触点压降；
- 受控点动时卡钳端实际电压和电流。

所有带电测量必须由具备现场电气操作资格的人员执行，并采用限时点动、机械防护和可立即断电的测试方式。

## 7. 软件整改建议

1. 为启动定位增加独立的近零电流硬件确认条件：DO 正转成功、电源输出新鲜有效、DAQ 新鲜、连续多批电流仍接近本底时，直接生成 `OpenCircuitOrOutputFault` 并只隔离该通道；
2. 统一启动定位分类器与正式通道 `NonRecoverableDisableChannel` 策略，避免同一故障码出现相反恢复语义；
3. 启动定位重试前必须原子重建 Runner、执行代际许可和 `StartBlocked` 状态，任一条件未恢复时不得消耗机械重试次数；
4. 正式运行未提交且启动失败已完成安全回滚时，禁止请求进程接管和 `RuntimeShutdown`，保持主界面可见并提示用户处理故障；
5. 增加以下自动化回归用例：
   - 单通道近零电流时只隔离故障通道；
   - 健康同组通道继续启动；
   - 启动失败不关闭主进程；
   - 重试时执行许可完整重建；
   - 首个硬件证据在后续软件错误发生后仍作为根因保留。

## 8. 可直接对外使用的结论

> 经封存数据复核，EPB7 启动时控制命令已成功下发，但负载电流始终约为 0.082 A，未形成正常电机电流；同一电源组的 EPB8、EPB9 以及其余通道运行正常。故障首因位于 EPB7 卡钳或其专属线束、插头、继电器/驱动输出，不属于纯软件误报。程序窗口退出是软件在处理该硬件异常时误入外部恢复和运行时关闭流程造成的二次缺陷。当前应保持 EPB7 禁用，并通过与正常通道进行负载端换位，最终区分卡钳本体与台架 7 号输出支路。
