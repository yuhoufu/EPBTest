# V4.1 独立机械目标快照与完成识别

承接 `a30f539`。本轮解决正常运行阶段“目标已经完成却仍留在停滞监控集合”的路径；恢复验证中途达到目标的处理尚未闭环。

## 依据和修改

主程序 `EpbDiskWriter.GetMechanicalCycleCompletedCount` 按数据库中 `mechanical_completed=1` 的记录数判断机械完成圈数，学习/资格动作也可能消耗剩余目标。独立监督此前只有选中通道，没有持久目标次数，无法独立区分正常完成和停滞。

人工建立批次时，新增各通道 MechanicalTargets：优先使用通道 TotalCount，否则使用项目 TestTarget。它与运行意图一起持久保存；目标次数本身仍受配置摘要校验。非法、重复或不能覆盖选中通道的目标快照被拒绝。空快照仅保留旧协议对象兼容，不作为目标完成证据；当前人工新批次总会生成快照。

独立执行器在无活动恢复事务时，每五秒用原有有界数据库子进程读取机械计数及最近正式记录。在同一只读快照上计算达到目标的通道，按状态修订号 CAS 写入 CompletedChannels；未完成通道继续监控，全部选中通道完成时解除 Armed。即使主程序已退出，也先尝试检查完成事实，避免把正常完成退出立即判作重启需求。数据库不可读且精确主进程已退出时仍可以根据进程退出证据接管，不伪造完成或数据库停滞。

完成写入核验数据库路径、创建时间、目标快照和当前阶段；活动安全清理/恢复事务期间拒绝此普通完成写入。该路径报告 `MechanicalTargetCompleted:...;NotRecoveryVerification`，不生成 Verified。

正式恢复验收的“机械计数推进且至少三个正式周期落盘”未放宽。正常学习达到最终机械目标不能冒充已恢复三个正式周期。

## 本地验证

所有命令均取得实际退出码 0，日志在主仓库根 `Codex`。

| 项目 | 结果 | 日志 |
|---|---|---|
| Debug x86 解决方案 | 通过 | v41-completion-build.log |
| 有界工作进程 / 持久状态 | 17/17、137/137 | v41-completion-process.log |
| Fallback 专项 | 75/75 | v41-completion-fallback.log |
| EpbDiskWriter | 58/58 | v41-completion-disk.log |
| PowerSupplyDebugger | 19/19 | v41-completion-power.log |

新增状态测试核验数据库身份不匹配拒绝、只排除完成通道而保留未完成同伴、旧状态修订拒绝、全部完成解除授权且不伪造恢复事务。SQLite 证据测试另外验证达到机械目标不等同三正式周期恢复证据。
