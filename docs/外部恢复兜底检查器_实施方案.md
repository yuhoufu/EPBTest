## 1. 目标与实施顺序

建设独立部署的 `MTTFTest.RecoveryGuard.exe`，在主程序或既有恢复链失效时，识别业务与恢复停滞，取得唯一接管权，通过安全恢复入口重建必要的软件组件，并以实际业务提交确认恢复结果。

采用“独立检查器＋稳定状态契约＋统一接管协议”。检查器正常时只观察，不参与采样、控制或数据库写入。独立部署用于隔离组件故障；自动续测仍需最小接口协作，不能做到所有启动者互不协调。

按用户要求，工作顺序为：

1. **第一步：外部恢复兜底方案及后续实现。** 本次先落地方案文档；后续实现按第 10 节分阶段推进。
2. **第二步：I0050 液压恢复状态发布一致性修复。** 单独处理恢复计数、恢复契约与生命周期发布之间的潜在中间态窗口，不作为本次文档工作的前置阻塞，不混入第一步实现范围。

第一步的验收目标是发现并处理恢复长期无进展，不是消除采样空窗或消除全部退出。第二步未完成前，相关故障仍可能重复触发，必须保留故障归因，不能把外部重启成功算作根因修复。

## 3. 组件职责与独立部署

| 组件 | 职责 |
| --- | --- |
| 主程序内部恢复 | 正常控制与局部自愈；发布权威业务证据和用户意图 |
| Supervisor / sidecar | 常规监督、安全交接与进程替换，优先完成已有恢复 |
| RecoveryGuard | 独立检查业务与恢复期限；登记接管、协调组件重建、核实结果 |
| SafetyAgent | 执行既有受支持的独立安全处置，不由 Guard 伪造安全凭证 |
| SessionAgent | 在指定交互会话中启动唯一合法实例 |
| 现有 RecoveryHealth 任务 | 保留组件健康职责，并遵守接管事务及维护约束 |

建议独立程序根目录为 `%ProgramFiles%\MTTFTestRecoveryGuard`，独立运行状态根目录为 `%ProgramData%\MTTFTestRecoveryGuard`；路径为拟议布局，最终由部署设计确定。安装级共享契约建议放在 `%ProgramData%\MTTFTest\RecoveryControl`，不随业务 Current 切换，也不随项目备份回滚。

要求：

- Guard 不加载业务目录 DLL，不引用主界面、Controller 或 NI 运行组件；自身运行依赖纳入独立交付和校验。
- Guard 单独安装、升级、卸载；停用 Guard 不打断正常试验。主程序升级不能覆盖其程序和监督记录。
- 系统接口调用和子进程查询均有期限；失败时记录具体原因，不能猜测 PID 或设备状态。
- 不以长时间扫描日志、查询活动数据库作为正常检查方法。仅在异常时有界取证。
- 共享契约有格式版本和兼容范围；不兼容时进入只观察或阻塞状态，不猜测字段含义。
- 配置与共享记录采用明确 ACL，区分主程序意图写入、Guard 事务写入和只读观察权限；检查器不能把可随意修改的文件视为恢复授权。

Guard 不依赖无响应 Supervisor 批准接管，但仍依赖可信安全处置与用户会话启动能力。安全组件失效时，可以先重建其可用性；无法确认断能或设备控制权时，保持阻塞，不能直接启动试验绕过它。

## 4. 三类稳定状态契约

字段名均为拟议，不表示现有字段或已定稿 API。复用已有业务证据，通过窄接口导出，不把整个内部状态机变成外部协议。

### 4.1 运行授权与停止记录

| 字段 | 语义 |
| --- | --- |
| SchemaVersion、InstallationId、BenchId | 契约版本、安装及台架身份；不能只按项目名识别 |
| AuthorizationId、RootRunId | 一次人工开始形成的授权及其运行链身份；自动恢复不创建新的人工授权 |
| IntentVersion | 本授权内用户意图的单调版本；不能以墙上时钟代替顺序 |
| DesiredState | Run、Paused、Stopped、Completed 等明确状态 |
| IssuedUtc、RecoveryAdmissionUntilUtc | 授权签发及由可信运行证据续期的首次接管截止时间；后者不是普通文件更新时间，也不是从试验开始后固定倒计时 |
| ConfigurationIdentity | 项目与设备配置身份，复用既有合法性校验 |
| Revocation / TerminalRecord | 暂停、停止、完成等决定及原因，持续生效 |

授权是续测前置条件，不代替安全证明。停止/完成记录不能被普通进度刷新覆盖，也不能因时间过去而失效。再次人工开始应产生新授权身份；自动恢复可改变子 RunId、PID，但不能因此重置授权限制。

人工暂停后的人工继续保留原业务进度，但必须产生更高的意图版本并重新建立监督有效期；旧暂停前启动许可不能复用。新的人工开始、人工继续与自动恢复应使用不同事件类型，禁止自动恢复伪装成人工操作刷新授权。

### 4.2 只读观察快照

至少包含：

- 授权身份、IntentVersion、当前 RunId/RunEpoch、SessionId。
- 当前进程 PID、启动时间、完整路径和系统启动身份。
- PublishedUtc、Sequence、聚合快照版本及来源时间。
- 当前参与通道/压力组、逐通道采样位置、控制步骤与完成序号、正式圈提交位置、持久化提交位置。
- 当前阶段、进入时间、允许期限、最后实质进展及证据质量。
- 恢复事务、阶段、最后实际完成的动作；明确区分尝试计数与进展。

主程序通过有界后台发布，使用不可变快照和原子替换，Guard 短暂共享读取后关闭。普通快照可合并更新；人工停止决定不得使用可丢弃的普通发布队列。异步磁盘发布不能把不同代次的数据拼成同一权威状态。

### 4.3 接管事务与 Guard 观察记录

持久保存：TransactionId、授权身份及版本、TakeoverEpoch、Owner 身份、所有者租约、当前阶段、实质进展、阶段期限、Guard 最后有效观察、启动预留与消费记录、冷却状态、结果及原因。

事务不能通过“文件过期就删除”解锁。Guard 意外退出后，下一轮重新核实实际状态，再继续同一事务；不能从头重复强杀。

权威写入采用短事务、预期版本校验和原子提交；主程序与 Guard 不能同时各自按“读版本加一”覆盖同一个文件。普通快照不拥有授权写权限。首次部署建立的安装代次与 Guard 注册代次参与验证，卸载重装不能自动继承备份中的活跃恢复许可。

## 5. 时效性与旧试验禁止误恢复

### 5.1 首次接管和已接管分别判断

首次接管必须同时满足：

1. 授权、台架、项目、当前运行链身份匹配，最新意图仍允许续测。
2. Guard 已与本次合法运行建立监督关系，存在近期有效观察，而非首次启动时只读到一份旧文件。
3. 在首次接管有效期内，Guard 自身监督未发生不可接受的中断。
4. 已确认原恢复机制超期且无实质进展；无维护、急停或其他阻断条件。
5. 不存在另一已合法运行的新会话；旧会话失败不能作为重建当前新试验的理由。

主程序崩溃后快照自然过期；快照过期是失联候选，不是永久禁止恢复的理由，也不是独立的强杀授权。

**长期试验的续期规则：** 同一人工授权下，Guard 持续观测到身份一致、满足当前阶段要求的真实进展，才推进首次接管有效期；不改变 IntentVersion，也不重置重启预算。正常长保压等步骤依据明确的合法阶段期限保持资格，不要求圈数不断增加。首次发现停滞时保留最后可信运行依据；发布序号、重复失败及无新完成结果的恢复声明均不得延长有效期。

**恢复循环的期限规则：** 单次步骤完成可以推进本次接管阶段，但反复出现同样的“退出→启动→学习失败”不能刷新业务未恢复的观察起点。分别保存本次尝试阶段预算与跨尝试 LastVerifiedBusinessCommit。用户已确认冷却后继续尝试：阶段期限用于结束卡住的本次动作、升级接管和告警，不因累计失败次数或累计业务停滞时长而永久取消恢复。对已在有效期内接管且持续受到 Guard 监督的事务，不再用首次接管截止时间中止冷却重试；人工停止、无可续测通道、监督中断过期或安全条件不满足仍阻止续测。Guard 自身心跳仅证明监督连续性，不证明业务已恢复，也不延长尚未取得的首次接管资格。

已经登记的接管事务可以跨分钟和短暂进程中断续接，但必须重新核实授权、停止记录、所有者、监督连续性和实际阶段。Guard 长期失联后不能靠残留“接管中”记录无限续测。

### 5.2 必须明确的特殊情形

| 情形 | 行为 |
| --- | --- |
| 新安装、重装或观察历史丢失 | 默认未建立监督信任；先与当前合法运行建立关系 |
| 台架闲置很久，残留 Armed=true | 不首次自动续测 |
| 昨天人工停止/完成，备份写着运行中 | 停止/完成持续有效，禁止恢复旧授权 |
| 权威提交状态无法确认、同版本内容冲突或已知版本倒退 | 信息不足，禁止自动续测；不得回退旧 Run 授权 |
| 只有状态发布线程还活着 | 快照更新不能延长业务无进展期限 |
| 原恢复反复初始化、失败、重试 | 重试不刷新总无进展起点 |
| Guard 在冷却期间正常持续监督 | 保留同一事务，冷却结束继续尝试可恢复的软件故障；不因累计次数或累计业务停滞时长而永久放弃 |
| 系统重启/断电恢复 | 从最后可信监督记录起，中断不足 60 分钟时按跨系统启动入口重新核实；达到 60 分钟即过期，不自动处理旧试验 |
| 单个卡钳确认永久故障 | 沿用现有逻辑隔离该通道，其余未完成通道在共享设备安全条件满足后继续 |
| 全部卡钳完成目标或已无可续测通道 | 不自动续测；分别记录完成或无可续测通道，不能将永久故障记成完成 |
| 时钟显著跳变 | 不直接凭墙上时间重建信任；结合启动身份和持久证据核实，无法判定时阻塞并告警 |

运行中的等待时长优先用单调时间计算；跨进程用 UTC、系统启动身份与 Guard 持久观察交叉检查。未来时间、序号倒退、身份变化、观察间隔异常不能解释为新鲜运行。

跨系统启动恢复是单独的准入入口：旧 PID/启动时间、会话号、租约和一次性启动许可均不继承，只继承经核实仍有效的人工授权及业务检查点。建立新系统启动代次、重新做安全和数据检查，再签发新启动许可。桌面程序需等待受支持的交互用户会话；没有会话时为 WaitingForSession，不计恢复成功。本方案不自动更改 Windows 登录设置。

**用户确认的过期阈值：60 分钟。** 以最后一份可信且持久化的监督记录为起点，当前核验时间与该记录相差达到 60 分钟（`>= 60 min`）即过期；不足 60 分钟只表示可以继续核验，不代表可直接启动。记录缺失、时间异常或不能证明身份连续性时，不能按“刚开机”重新计时。该间隔是监督中断的保守估计，并非声称精确测到了市电断电时长；记录发布延迟会计入其中。

跨系统启动使用上述 60 分钟准入窗口，不机械套用普通进程故障的候选“15 分钟首次接管”参数，避免把用户允许的短时断电恢复提前拒绝。它仍须持有断电前已建立的有效运行授权及监督关系，且没有停止、完成、维护或安全阻断。跨系统启动后必须在这一窗口内完成准入登记；等待交互会话不能自行无限续期。已经合法登记的事务进入持续监督后，再按同一事务的阶段预算和冷却规则执行。

长时间断电过期后的“不予处理”指不自动启动、不自动终止进程、不清理数据、不重置圈数；只记录一次过期结果，保留项目供人工选择继续。该规则同样适用于 Guard 自身长时间停用后重启，包括断电前已经接管的事务。过期后不能靠重新运行 Guard 或刷新旧状态文件恢复资格；只有受支持的人工开始/继续才能形成新的有效意图。过期约束禁止恢复旧授权，不得干扰后来已经合法启动的新试验。

共享授权权威与项目检查点分离。业务数据可以从主备恢复，但自动恢复授权不能仅从旧项目备份重建。共享状态整体丢失或回滚时，应重新建立信任，不能把“有效 JSON”视为最新授权。

原子替换后主文件与备份正常相差一个版本，不直接判为冲突；应依据提交记录和已观察版本判断。若最新权威主记录损坏，较旧备份可以供诊断和恢复业务数据，不直接提供自动续测权。不能声称仅凭同一磁盘上的版本与摘要能够检测该磁盘所有记录被一致回滚；已知备份恢复/重装需要重新注册，无法检测的整体回滚属于能力边界。

### 5.3 已确认阈值与待验证参数

| 参数 | 确定依据 |
| --- | --- |
| Guard 扫描周期 | 分钟级为目标，结合调度延迟与现场负载 |
| 快照发布周期和失联确认时间 | 正常发布抖动、磁盘延迟和短暂重连 |
| 通道/步骤进展期限 | 当前试验配置，区分保压、学习、正式圈和等待 |
| 原恢复阶段/总无进展期限 | 已有恢复预算与实际最长合法进展间隔 |
| 首次接管有效期 | 应覆盖正常恢复预算、确认次数和调度延迟，避免等待结束后已无法接管 |
| Guard 监督中断容忍时间 | 与下行共用已确认的 60 分钟过期阈值；短期调度异常告警可以另设，但不得刷新最后可信记录或另开过期窗口 |
| 断电及长期监督中断过期阈值 | 用户已确认 60 分钟；达到阈值禁止自动续接旧授权或旧事务，不是软件持续重试总时长上限 |
| 所有者租约、接管阶段期限 | 可恢复性及最坏合法执行时长 |
| 重启预算和冷却 | 与现有安装级预算统一核算，不另起独立次数池 |

讨论中的“10 秒发布、2 分钟失联候选、15 分钟首次接管”仅作为候选示例，不因出现在讨论中就成为生产默认值或已验收指标；实施阶段可以使用明确标注的可配置试验初值。60 分钟过期阈值是本轮用户确认的设计要求，实际实现与验证范围见实现进度记录，不以本方案代替验收。其他时间参数仍须测量后确定；参数校验应确保正常恢复等待、连续确认及调度延迟能够落在适用的首次接管窗口内。现有十分钟三次限频是当前代码事实，也不意味着所有新动作均应机械使用同一预算。

## 6. 人工停止优先

推荐流程：

1. 用户停止/暂停立即触发本地撤权和相应安全停止动作，不等待 Guard 的扫描周期。
2. 持久化更高 IntentVersion 的用户决定，撤销本授权下后续启动和续测许可。
3. 继续正常停止、保存和资源释放；异步恢复请求不能覆盖新决定。
4. Supervisor、SessionAgent、新主程序及输出使能入口均核对最新授权版本。

停止决定落盘失败时，仍执行本地安全停止，明确记录持久撤权未确认；对已经观察到该故障或撤销请求的恢复组件，禁止退回旧备份继续自动续测。应通过独立撤销通知让恢复组件尽早进入禁止状态，并重试持久化；该通知接收者可以存活于原主程序之外，但不能把没有确认的发送当成成功。

**保证边界：** 若停止点击后主程序在任何外部通知或持久记录产生前立即死亡，纯软件观察者无法区分这次死亡和运行中的异常退出；磁盘与通知同时失败也不能保证停止意图被传达。文档中的“人工停止优先”指已被权威提交或被独立接收者确认的停止决定，以及主程序仍存活时的本地即时撤权。未确认时不得向用户显示外部续测已可靠取消。要求覆盖此联合故障下的绝对禁止输出，需要可独立保持的硬件停机/禁止使能信号。用户已确认现场按钮只能人工按下；其保持、反馈和断能范围仍须现场核实，不能推定具备上述保障，按第 13 节确定的能力边界实施。

暂停只允许后续受支持的人工继续；完成与停止禁止自动续测。维护禁止、急停及未解除硬件故障具有阻断效力，Guard 无权清除。

永久故障按现有通道/压力组作用范围处理，不将单通道故障擅自升级为全台禁止恢复。共享电源、液压或采样资源故障影响其他通道安全时，仍执行既有共享资源约束。已隔离通道不纳入“必须恢复推进”的参与集合，Guard 不自动解除其永久故障。

并发语义以已提交的意图版本及启动预留事务排序。若停止发生在创建进程之后，允许进程留在安全空闲做收尾，但不得继续试验。启动进程与允许设备输出必须是分开的门槛。

原 UI 不存在时，仍需可用的人工取消恢复入口；可由独立管理命令写入同一撤权协议。不能要求用户必须等待主程序恢复后才能取消自动续测。该入口不承担替代物理急停的职责。

用户已确认“面板按钮”是**只能人工按下的停机按钮**。它不能作为无人值守强杀前的自动断能手段；松开/复位按钮也不得自动恢复试验授权。人工触发方式不等于已证明按钮的接线、断能范围、保持特性或独立反馈能力；这些作为现场验收事实核实，不再作为方案定稿的前置问题。在独立反馈及持久撤权能力未验证前，不承诺主程序完全失联时仍能自动感知面板停止。无法取得既有安全链的有效断能证明时，停滞重建停在 Blocked，保留告警与后续检查，不盲目强杀或使能。

“冷却后继续尝试”允许再次检查安全条件及尝试受支持的恢复入口，不允许用冷却结束替代断能证明。主程序已退出时仍须完成适用的安全、身份和检查点核验，不能把进程退出等同于设备已断能。本期不新增自动按压按钮或硬件改造要求；若后续需要覆盖既有安全链完全失效且主程序占用硬件的无人值守恢复，应另行设计并验证独立断能路径。

## 7. 与既有看门狗的接管互斥

### 7.1 短事务锁与持久代次共同约束

短事务锁用于登记接管、更新意图、预留启动名额；不得持锁等待硬件、网络或整个恢复过程。持久 TakeoverEpoch 隔离旧请求和迟到回调。

租约到期只允许重新竞争接管权，不证明旧进程已经失去硬件控制能力。接管者仍需确认旧实例退出、在途启动状态和设备安全。

所有可能创建实例的入口必须遵守该协议，包括 Supervisor、sidecar、SessionAgent、健康任务涉及的组件重建、自动启动任务和主程序自身恢复入口。具体入口清单在实施阶段逐项检索并形成覆盖表，不允许只在 Guard 中创建锁文件。

现有安装维护标志保留独立语义，维护禁止优先；不得自动清除 `maintenance-inhibit.json` 来促使恢复。维护互斥和接管记录的锁顺序统一，避免互相等待。

Guard 接管 Supervisor 失联时，应先持久化接管代次，阻止旧代次主程序启动，再由短事务核对精确 Supervisor 身份并恢复该组件。现有健康任务在有效接管期间不能另行替换 Guard 当前使用的监督组件；只有接管执行者失效且事务允许重新竞争时才参与有界救援。不能把“接管中”设计为健康任务永久不工作的标志。

Guard 自身执行者使用短租约与精确进程身份恢复；不得终止持有通用互斥锁的任意进程来强行解锁。遇到无法安全恢复的持锁者时记录阻塞。新协议不得在跨进程启动交换期间持有全局授权锁，现有 `_mainLaunchGate` 等内部锁需单独梳理，不能简单套一层大锁。

### 7.2 在途启动与旧会话

启动预留必须绑定授权版本、接管代次和唯一操作标识。SessionAgent 消费前重新核对；创建完成后记录 PID/启动时间。请求响应丢失时先查消费结果，不直接重发创建。

进程创建与记录写回之间可能中断，因此新实例启动时也要绑定合法身份并参与唯一实例核对，在获准前保持输出禁用。不能用单个文件存在性检查宣称已经解决创建竞态。

若旧会话仍失败重试、新会话已合法运行，Guard 应记录旧会话残留，避免影响新运行。只有持久协议明确撤销旧启动权后，才能安全整理旧恢复组件；不得按进程名批量结束所有 Watchdog。

### 7.3 接管阶段

| 阶段 | 动作与完成条件 |
| --- | --- |
| Observe | 获取有效快照，建立监督关系 |
| Suspect | 按当前阶段连续确认无实质进展，排除正常等待 |
| Claim | 登记新代次、启动禁入、预留接管；再核对意图与新会话 |
| SafeStop | 优先原安全入口，必要时恢复安全组件；得到适用的断能与保存证据 |
| Retire | 有界等待退出；必要时结束准确归属实例，确认其不再控制设备 |
| Launch | 通过交互会话入口创建唯一实例，绑定代次和授权 |
| Verify | 验证必要初始化/学习及参与通道的实际业务、持久化进展 |
| Complete | 持久记录结果后交还正常恢复职责 |
| Cooldown / Blocked / Cancelled | 保留原因和事务，按授权及期限等待或终止；不伪报完成 |

不得同时结束正在负责安全处置的组件。若必须结束占用硬件的失联进程才能接管，必须先明确独立断能保障和后续设备重新确认流程；没有这条已验证路径时保持阻塞。

## 8. 进展、成功与失败的判定

以下都不能单独算恢复成功：进程存在、窗口出现、日志增长、健康响应、许可 Approved、重试次数增加或“正在恢复”的状态刷新。

实质进展应是可验证的完成结果，例如安全阶段完成、准确旧实例退出、新实例绑定成功、必要学习完成、当前参与通道控制步骤完成及持久化提交推进。不同阶段采用各自证据，不强求保压阶段持续增加圈数。

恢复成功至少满足：

- 授权仍有效，无新的停止、维护或安全阻断。
- 只有一个有效运行实例，旧许可与旧代次不能重新启动。
- 当前参与通道及压力组取得符合其阶段的采样、控制和保存进展。
- 从可靠检查点续接，解释在途作废圈与成功圈口径，不清零圈数或伪造保存完成。
- 取得连续有效业务提交证据，观察窗口覆盖合法步骤推进。

总无实质进展期限不能被失败重试刷新。预算记录必须跨 Guard、Supervisor 和主程序重启保留。Guard 不应重复创建另一套主程序重启计数，使合计重启数突破安装级限制。

摘要损坏、身份冲突、授权撤销等确定性阻断须报告具体原因，不能用反复重建代替修复。对 I0050，第一步应在包含已知摘要比较修复的匹配组件基础上实施；这不包含第二步液压状态一致性整改。

## 10. 第一阶段工作的分步实施

此处是“第一步外部兜底建设”的内部阶段，不与第 1 节“第二步 I0050 根因修复”混淆。

| 阶段 | 交付内容 | 开放能力 / 进入下一阶段条件 |
| --- | --- | --- |
| A 契约与只观察 | 独立 Guard、快照、授权及观测记录、拟接管审计 | 不发送恢复或终止命令；验证合法长步骤、空闲、暂停、停滞识别 |
| B 统一授权与启动隔离 | 停止凭据、版本、接管代次、在途启动约束 | 所有入口通过并发与旧授权拒绝测试，再允许自动执行 |
| C 已退出后的恢复 | 主程序已死亡且授权有效时协调恢复 | 不强杀活动主程序；真实安装态验证唯一实例和业务提交 |
| D 停滞后的重建 | 原恢复超期后的安全接管与准确实例终止 | 安全处置、持久化、事务中断续接全部通过后启用 |
| E 现场观察及参数确定 | 原项目对账、误判统计、恢复时长、失败记录 | 确定生产参数；独立记录硬件验收限制 |

运行模式建议为 ObserveOnly、RecoverExited、RecoverStalled，逐阶段开放；默认 ObserveOnly。单次检查有界、IgnoreNew；跨次恢复依赖持久事务，不能要求所有恢复在一分钟内结束。

**检查与动作分离：** 分钟任务只判定、登记并监督动作；需要连续执行的安全停止/设备接管由受监督执行者完成，不能每到分钟任务期限就中断安全操作。可使用同一独立 EXE 的执行模式，通过单独受控任务承载，配置独立总预算和子进程归属。持久事务保证执行者中断后的对账，不等于让每个硬件步骤之间空等一分钟。原有健康任务的 45 秒不是新增整套恢复流程的默认期限。

## 11. 必须通过的验收场景

| 类别 | 场景与判据 |
| --- | --- |
| 独立性 | 主程序 Current 缺失/损坏时 Guard 仍可启动并准确报告；结束 Guard 不影响正常试验 |
| 旧状态 | 昨天完成/停止、旧项目备份仍 Armed=true、Guard 隔天启用，均不得自动启动旧试验 |
| 主备冲突 | 正常主备版本差可接受；权威主记录损坏、同版本冲突、已知回滚，不回退旧 Run 授权 |
| 状态时效 | 发布线程持续报活但业务停滞，仍能识别；合法保压和学习不误判 |
| 人工优先 | 停止发生于 Claim、SafeStop、Launch、创建后及输出前，后续续测均被撤销 |
| 持久失败 | 已知停止写盘失败时继续安全停止并禁止自动续测；独立撤销通知及其失败分别验证；未对外留下任何停止证据的联合故障按第 6 节界定能力边界 |
| 双重启动 | Supervisor 与 Guard 同时请求、旧凭证迟到、响应丢失重试，只有一个合法实例 |
| 旧新会话 | 旧会话持续失败、新会话正常，不能误杀新实例或恢复旧项目 |
| 长期重试 | 数百次相同失败不刷新总无进展起点；不能只靠日志更新躲过接管 |
| 冷却与过期 | 持续监督下恢复累计超过 60 分钟仍可冷却重试；Guard 中断监督达到 60 分钟后旧事务不得继续 |
| 断电边界 | 59 分 59 秒恢复监督可以进入身份与安全核验；60 分钟及以上拒绝旧授权；缺失/未来时间拒绝；较短普通首次接管参数不误拦截跨系统启动准入 |
| 面板停止 | 按实际接线分别验证断能、保持、反馈及撤权；复位不自动续测；无法读取按钮状态时明确记录能力边界，不将人工按钮当作自动安全凭证 |
| 事务中断 | Guard 在每个阶段退出，下一轮先核实再续接；不重复强杀或启动 |
| 原协调者失联 | Supervisor 卡死不导致 Guard 永久等待；安全条件无法确认时明确阻塞 |
| 维护和时钟 | 安装维护并发、系统重启、时钟跳变和序号倒退，符合第 5 节规则 |
| 预算 | 重启所有软件后限频仍有效；重复同一启动操作不重复消费/创建 |
| 数据 | 最后成功圈、在途作废圈、检查点与最终提交对账；不能伪报零丢失 |
| 成功判定 | 进程存在但没有正式业务提交不能判通过；各参与通道按阶段验证 |

涉及 Controller、持久化、看门狗或电源的后续代码改动，按仓库要求构建并运行 AdaptiveControlTests、EpbDiskWriterTests、PowerSupplyDebugger.Tests；另补 Guard 契约和端到端测试。故障注入先在隔离环境完成；真实 NI、电源和液压验收单独记录，不以组件模拟替代。当前程序不包含 CAN 硬件，CAN 不属于检查或验收范围。

## 12. 部署、回退与当前完成状态

先验证匹配版本与契约，再注册只观察任务；自动恢复模式仅在对应阶段验收后启用。现场切换遵循既有部署章程，不因本方案存在而认为已取得停机或故障注入授权。

停用/卸载 Guard 不删除停止记录、接管事务或恢复预算。若接管正在进行，先核实事务终态及所有权再退出自动执行模式，不能直接删文件释放旧启动者。回退到不认识新接管协议的业务版本前，需要进入维护并完成事务收口；不能让旧组件与新接管权威同时运行。

方案复核完成项：方案文档。后续实现阶段的代码、测试、安装包与验收状态，以[实现与交付进度](02_Issues/2026-09-07_RecoveryGuard_实现与交付进度.md)为准；本方案中列出接口不等于已接入所有执行者。I0050 液压恢复状态一致性修复按用户指定顺序留到第二步处理。

## 13. 本轮复核与最终决策

已修正的技术问题：首次接管窗口需随可信正常运行续期；区分单次阶段进展与跨重试业务无进展；正常主备版本差不能一律阻断；授权多写入者采用提交协议；停止意图完全未传达的联合故障不能作纯软件绝对保证；分钟检查与连续安全动作分离；接管禁入不能永久关闭健康组件救援。

本轮用户决策已收敛如下；现场硬件事实和实验参数仍按验收要求核实，不将其写成已经实现或验证：

| 决策 | 推荐/候选 | 当前状态 |
| --- | --- | --- |
| 电脑重启/断电后的自动续测 | 用户确认“长时间断电，认定过期，不予处理即可”，随后明确“60 分钟” | 已确认；达到 60 分钟过期；不足 60 分钟仍须身份、停止和安全核验 |
| 持续监督下同一软件故障反复失败 | 用户确认“冷却后继续尝试” | 已确认；受统一限频、安全条件及人工意图约束 |
| 主程序卡死且 NI 被占用时的独立断能条件 | 用户确认“只能人工按下的停机按钮” | 已确认按钮触发方式；不作为自动断能保障，无法取得既有安全链有效断能证明时保持 Blocked，不强杀占用硬件的主程序 |
| 单个卡钳永久故障的影响范围 | 用户确认“隔离通道，按之前的逻辑处理即可” | 已确认；复用既有隔离与共享设备安全约束 |

参数应先形成实验默认值和可配置范围，再由软件与现场验证确定生产值。最终设计可以明确这些参数的推导与验收方法，不需要把未经试验的数字称为已验证上限。

本轮答复收敛结果：从最后可信且持久化的监督记录起计算，间隔达到 **60 分钟**即禁止自动处理旧试验；停止、暂停、完成及维护阻断不受这 60 分钟宽限。持续监督的冷却重试不受累计 60 分钟限制，单通道永久故障继续沿用原隔离逻辑。软件方案据此确定；面板按钮只能人工操作，不能补足无人值守断能证明，缺少有效安全证据的强杀接管保持阻塞。I0050 液压恢复状态发布一致性仍在第二步处理。

### 13.1 人工面板按钮确认后的恢复边界

本表为最终方案的行为要求，不代表当前分支已经完成相应链路或现场验证。

| 情况 | 方案要求 |
| --- | --- |
| 异常退出，监督间隔不足 60 分钟 | 仅允许进入恢复核验；授权、通道范围、安全交接和唯一接管权全部有效后才能续测 |
| 主程序卡死并占用硬件，无法取得有效独立安全证明 | 保持 Blocked，记录原因并告警；人工面板按钮不能为无人值守强杀提供证明 |
| 冷却结束，但安全阻断仍在 | 可再次核验或调用受支持的安全入口；不得直接强杀、启动输出或把阻断判为成功 |
| 已确认人工停止，随后按钮复位或程序重启 | 停止继续有效；必须由明确的人工开始操作重新授权 |
| 按钮已按下，但软件没有可信反馈或停止记录 | 不能声称软件已可靠获知停止；现场须验证保持与反馈能力，未验证前不承诺覆盖该情形 |

因此，第一步可以补充具备安全恢复条件时的异常退出与恢复停滞兜底；对于原安全链失效、活动主程序仍占用硬件的情况，本期方案接受等待人工处理的边界。按钮接线与反馈、其余时间参数通过后续验收确定，无需据此扩大本次方案为硬件改造。
