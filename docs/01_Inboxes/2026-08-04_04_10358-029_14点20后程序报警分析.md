# 10358-029 项目 14:20 后程序启动及报警分析

## 结论摘要

分析范围为北京时间 `2026-08-04 14:20:00` 之后，现场数据目录为 `\\wj-epb\EPB_Data\10358-029`。

本次不是单一故障，而是三类问题叠加：

1. **14:27 EPB5 报警包含真实的断电后电流续升。** 软件在 `14:27:18.738` 发出断电命令时，快速峰值为 `15.009 A`；原始 2 kHz 数据在约 `1.7 ms` 后继续超过该值，并在断电命令后约 `33.7 ms` 达到 `16.138 A`，约 `55.7 ms` 后才首次降到 `0.1 A` 以下。该圈与此前 EPB5 约 `14.858～15.240 A` 的完整峰值相比属于突发异常。现有记录只能证明软件 DO 方法返回成功，`PhysicalOffStatus=NotMeasured`，不能证明继电器触点在命令时刻已经物理断开。应优先检查 EPB5 继电器/接插件/线束和实际断电延迟，同时把该事件从笼统的 `PeakEvidenceMismatch` 拆分为“断电后续升/过冲”诊断。
2. **14:44、14:48、14:50 暴露了确定的软件数据链路问题：快速控制链与后台全数据链不同步，后台处理曾积压超过安全新鲜度窗口。** EPB8 在快速电流已经达到 `14.770 A` 时，后台全速峰值仍停在 `13.132 A`；原始数据表明后台证据约落后 `0.17～0.20 s`。压力新鲜度也由同一个后台 `ProcessLoop` 更新，项目配置要求样本年龄不超过 `100 ms`，连续 `100 ms` 无有效新样本即触发故障，所以后台短时积压会被误报成 `HydraulicPressureLost`。
3. **液压报警文本具有误导性，现有证据不支持真实掉压。** `14:44:48` 的液压 2 报警记录 `Actual=74.939 bar`，`14:50:01` 两个液压组分别记录 `70.475 bar`、`75.321 bar`，均高于 `65 bar` 保压下限。源码中的有效性判定还包含 `AgeMs <= 100`；异常文本却没有输出 `AgeMs` 和失效类型。结合 14:50 两台 DAQ 对应的两个液压组几乎同时触发，主因是后台样本陈旧，而不是两个液压系统同时掉压。

另有一条独立的 UI 配置保存异常：`14:22:09.693` 的 `File.Replace` 因目标文件被占用而抛出 `Application.ThreadException`。它没有中断随后持续约 22 分钟的试验，也与 14:27/14:44 的控制报警没有时间或调用链因果关系，但仍需修复并发写入。

### 目标报警策略

按本次确认，建议落实为：

| 场景 | 目标策略 | 前序提示 | 复位规则 |
|---|---|---|---|
| 普通峰值证据偏差 | 同一 EPB 通道连续 `3` 个有效圈均超过 `1.0 A`，第 `3/3` 次才硬报警 | 第 `1/3`、`2/3` 次只发中文软预警，本圈继续完成安全反向释放和证据封存 | 任一有效圈回到 `≤1.0 A` 立即清零 |
| 普通单圈过冲 | 峰值连续 `5` 圈超过目标 `0.8 A`，第 `5/5` 次才硬报警 | 第 `1/5`～`4/5` 次发中文软预警，模型继续提前修正下一圈断电点 | 任一圈回到 `≤+0.8 A` 平衡带立即清零 |
| 严重正向过冲 | 峰值超过目标 `3.0 A` | 不容错 | 立即硬报警并断电 |
| 过流、断电命令失败、物理断电未确认、DAQ 硬故障、真实液压低压 | 不纳入上述次数容错 | 不等待累计 | 立即执行原有失效安全停机 |

这里的“3 次”和“5 次”均应理解为**按通道独立统计的连续有效圈数**，不能在 EPB5 与 EPB8 之间合并计数，也不能把捕获无效、捕获身份不匹配或后台证据过期当成一次有效的物理偏差。

### `PeakEvidenceMismatch` 连续 3 次的实现要求

当前代码在 `Controller/EpbCycleRunner.Adaptive.cs::RunOneAdaptiveAsync` 中发现一次偏差后直接调用 `AlarmRaised` 并返回 `HardFault`。目标实现需要增加每通道状态，例如：

```text
ConsecutivePeakEvidenceMismatchCount
PeakEvidenceMismatchConfirmCycles = 3
```

处理顺序建议为：

1. 先确认快速证据和最终证据属于同一 Run、同一通道、同一圈，并检查后台证据的 `ProcessedThroughUtc/LagMs`；
2. 后台证据超龄时报告“峰值证据处理延迟”，不计入物理偏差连续次数；
3. 两个证据窗口一致且差值 `>1.0 A` 时，本通道计数 `+1`；
4. 第 `1/3`、`2/3` 次：正向已断电，本圈继续完成反向释放，保存 WarningSnapshot，不隔离通道；
5. 第 `3/3` 次：硬报警、隔离该通道并导出 AlarmSnapshot；
6. 任一有效匹配圈差值 `≤1.0 A` 时立即清零；
7. 计数应写入 `EpbAdaptiveProfile` 并持久化，程序重启后不应无提示地丢失；人工清模型或更换硬件时允许显式清零，并写审计日志。

EPB5 Cycle 13 的最终峰值达到 `16.138 A`，同时具有断电后真实续升。连续 3 次机制可以避免单圈偶发值立刻隔离，但**不能替代严重过冲和物理断电保护**：如果最终峰值已经跨过独立的立即过流/严重过冲阈值，仍应立即报警。

代码在 `Controller/EpbCycleRunner.Adaptive.cs::RunOneAdaptiveAsync` 中做了以下比较：

## 液压误报警的直接代码原因

`Controller/HydraulicGroupCoordinator.cs::MonitorQualifiedPressureAsync` 的保持判定调用：

```text
IsPressureSampleQualified(sample, minimumBar, PressureSampleMaxAgeMs)
```

项目当前参数为：

```text
PressureThresholdBar = 70
HoldDropToleranceBar = 5
MinimumBar = 65
PressureSampleMaxAgeMs = 100
HoldDropConfirmMs = 100
```

有效性实际要求：

```text
finite(value)
and 0 <= AgeMs <= 100
and ValueBar >= 65
```

但 `HydraulicPressureLostException` 只保存并打印 `ActualBar` 和 `MinimumBar`，不保存 `AgeMs`，也不区分 `BelowMinimum`、`SampleStale`、`SampleInvalid`。因此旧值即使为 `74.939 bar`，只要超过 100 ms 未刷新并持续约 100 ms，仍会输出：

```text
HydraulicPressureLost ... Actual=74.939bar Minimum=65.000bar
```

这正是现场看起来“压力高于下限却报压力不足”的原因。

更关键的是，`PressureSample` 并非在 NI DAQ 回调收到新批次时更新，而是在 `IO.NI/TwoDeviceAiAcquirer.cs::ProcessLoop` 处理完工程量转换和因果中值滤波后才更新。该 `ProcessLoop`：

1. 用一个全局 `ConcurrentQueue` 同时串行处理 Dev1 和 Dev2；
2. 转换和滤波整批数据；
3. 更新压力样本；
4. 为每个激活通道逐点扫描全数据峰值；
5. 同步调用 `OnDiskBatch`，为各 EPB 分配数组并进入记录器；
6. 同步调用 `OnEngBatch` 更新 UI。

只要任一环节出现短时阻塞或 GC/写盘/UI 回调抖动，队列中的两个设备都会落后。快速电流控制仍在 NI 回调线程运行，所以会出现“控制电流仍实时、后台峰值和压力年龄已经陈旧”的分裂状态。

现场证据与该链路吻合：

- 14:44 快照中的 EPB8 原始文件共有 `6,920` 点，2 kHz 时间戳从 `14:44:45.9338303` 连续到 `14:44:49.3933303`，点间隔完整为 `0.5 ms`；这说明 DAQ 缓冲数据仍完整，问题发生在数据到达后的后台处理时效，而非已证实的硬件断流。
- 14:48 EPB8 快速值与后台峰值约相差 `0.17～0.20 s`。

## 整改建议

### P0：保持安全停机，但修正故障分类和证据语义

1. `HydraulicPressureLostException` 增加 `Reason`、`AgeMs`、`SampleUtc/MonotonicTicks`：
   - `BelowMinimum`：压力真实低于下限；
   - `SampleStale`：压力值正常但样本超龄；
   - `SampleInvalid`：NaN/Infinity/无样本。
2. `PeakEvidenceMismatch` 改为至少三类：
   - `PeakEvidenceLag`：决策时全数据处理进度明显落后；
   - `PostOffPeakOvershoot`：同一全数据窗口中，断电后峰值继续上升超过限制；
   - `CaptureIdentityMismatch/Invalid`：捕获身份或窗口无效。
3. 不建议只把 `1 A` 峰值容差或 `100 ms` 压力新鲜度直接放宽；这会同时掩盖真实继电器延迟和真实采集故障。

### P0：拆开实时安全数据链与后台写盘/UI 链

1. 压力“新样本到达时间”应在 DAQ 回调或独立的轻量实时路径更新，不能依赖包含写盘和 UI 的单线程 `ProcessLoop`；压力值可以继续使用经过验证的批内代表值/轻量滤波。
2. Dev1、Dev2 至少使用独立消费队列，或使用有界通道和明确背压策略，避免一个设备/订阅者拖慢另一个设备。
3. 把 `OnDiskBatch` 和 `OnEngBatch` 从压力新鲜度及峰值安全证据路径中解耦；写盘、快照和 UI 不得同步阻塞安全样本更新。
4. 峰值证据在进入安全比较前必须带 `ProcessedThroughUtc`/`LagMs`；过期证据不得与当前快速值直接做“同一时刻”的差值判定。

### P0：现场检查 EPB5 实际断电链

1. 示波记录 EPB5 的 DO 指令、继电器线圈、负载端电压和电流；
2. 验证命令后约 `34 ms` 达峰、约 `56 ms` 清零是否为正常硬件特性；
3. 与 EPB4 同电源组、同批次波形对比，确认 EPB5 是否存在独有的继电器或线束延迟；
4. 若硬件延迟正常，则控制模型必须显式学习/限制“命令到物理断电”的延迟，而不是把软件返回时刻当成能量切断时刻。

### P1：增加可观测性与保护

1. 每秒或异常时记录 `ProcessLoopQueueDepth`、最老批次年龄、单批处理耗时、GC 暂停、写盘耗时和 UI 回调耗时；
2. 现有 `DaqCallbackTimingLog` 建议先设置为 `anomaly`，同时新增后台处理延迟日志；仅有回调节拍不足以发现本次问题；
3. 当后台延迟超过阈值时，产生独立的 `DaqProcessingLag` 安全事件，先断电，但不要误导为液压泄漏；
4. 为两台设备分别记录最新回调年龄和最新处理年龄，明确区分“采集没到”和“到了但没处理”。

### P1：修复 UI 配置保存

1. 对同一配置路径串行化保存；
2. 使用唯一临时文件并保证 finally 清理；
3. 原子替换失败时保留旧文件，禁止先删旧文件再移动；
4. 合并短时间内重复的复选框保存事件，并将最终失败显示为可恢复提示，不让异常冒泡到 `Application.ThreadException`。
