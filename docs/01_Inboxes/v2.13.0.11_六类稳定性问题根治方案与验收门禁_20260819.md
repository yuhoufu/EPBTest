> 主要依据：`v2.13.0.11_运行健康与试验历程分析_20260819.md`、本数据包日志/Watchdog journal/DMP 清单，以及当前仓库中后续整改实现

## 1. 结论先行

这六类现象不是六个彼此独立的小问题，而是三个故障域在不同层面的表现：

| 故障域 | 现场表现 | 根治目标 |
|---|---|---|
| 恢复状态与资源契约不一致 | 4 次自动接管，其中 3 次 `OrphanPausedTimeout`，另 1 次通道 60.1 s 无进展 | 一个通道只有一个生命周期真相；一个根事件只有一个恢复 owner；所有恢复必须成功结束或进入持久 `RecoveryBlocked` |
| 异步回调/通信的长尾与公共调度停顿 | DAQ 1.0～1.4 s 长尾；末段双 DAQ 约 3.315 s 空窗；PSU 13.37 s/3.31 s 超时；末段 Watchdog ACK 3.131 s 超时 | DAQ、PSU、安全监控不依赖同一个容易饥饿的异步调度面；超时必须成为真正的硬截止时间；故障时先安全、再恢复 |
| 事故身份和证据生命周期不完整 | 约 21 组根事件被展开为 122 条 error；两次 `HeartbeatProvider` 空引用只有消息没有堆栈；第一次接管 DMP 最终缺失 | 每个事故有唯一身份和闭环状态；遥测明确标记有效/无效；每次接管的证据事务化生成、校验、归档和保护 |

总体判断：

1. v2.13.0.11 的安全关断和自动恢复链能够兜底，但频率和证据质量不满足长期无人值守要求。
2. 当前 v2.13.0.13 候选代码已经对“孤儿暂停、恢复 cohort 漂移、恢复计数误判、阶段资源契约、接管前刷新”等核心状态机问题做了结构修复，并通过仓库内自动化回归；这只能标记为“代码已整改，待实机验证”，不能据此宣告现场根因关闭。
3. DAQ 底层长尾、PSU 硬超时、看门狗快照原子性和 DMP 留存策略仍有需要补齐的闭环。尤其是 DMP 缺失已经能定位到明确的软件策略，不再只是“可能复制漏文件”。
4. 根治不能靠加大超时、增加无限重试、降低安全门限、关闭告警或减少证据采集。这些做法只会延后发现时间或掩盖问题。

## 2. 新增关键发现

### 2.1 第一次接管 DMP 不是单纯“没有生成”，而是后来被保留策略删除

第一次接管的 Watchdog journal 给出了完整顺序：

| 本地时间 | 事件 | 结果 |
|---|---|---|
| 08-18 01:08:37 | `TakeoverRequested` | `ChannelProgressStalled`，EPB9 约 60.1 s 无进展 |
| 08-18 01:08:52 | 第一次 `MiniDumpRequested` | 原因 `AutomaticTakeover` |
| 08-18 01:08:52 | 第二次 `MiniDumpRequested` | 原因 `StopCompletedButProcessAlive`，与前一次并发/重叠 |
| 08-18 01:08:53 | `MiniDump Captured` | 记录生成 `MTTFTest_21228_20260817_170852_467.dmp` |
| 08-18 01:08:53 | 第二次 `MiniDump` | `MiniDumpWriteDump failed`，Win32Error `-2147024597` |

当前 `MiniDumpCapture.Prune()` 的逻辑是：同一 session 只保留按创建时间排序的最近 3 个 `.dmp`，并同时受 256 MiB 上限约束。该 session 共发生 4 次接管，当前数据包恰好只剩后 3 份、每份约 17～18 MiB；第一次成功 DMP 会在后续接管触发的 `Prune()` 中成为超出数量上限的旧文件并被删除。并发失败的第二个转储文件还可能让清理更早发生。原运行目录中的成功 DMP 精确路径也已经不存在。

因此，第一次 DMP 缺失的直接根因是：

1. 转储请求没有按 `SessionId + PID + TakeoverId` 去重，第一次接管发生双重捕获；
2. 留存按“最近 3 个文件”而不是按“每个未关闭事故至少 1 份证据”管理；
3. 日志中的 `Captured=` 只证明当时写文件调用完成，不证明文件已经登记、校验、归档并受保护。

这是一条可以直接整改和自动化验证的软件根因。

### 2.2 08-19 11:46 更像一次公共异步调度停顿，不像三套硬件同时独立故障

同一时段出现：

- Dev1 `LastCallbackGapMs=3315.455`；
- Dev2 `LastCallbackGapMs=3315.424`；
- Watchdog ACK age `3131 ms`；
- PSU4 `SOUR:VOLT?` 总耗时 `3308.263 ms`；
- PSU2、PSU3 的分钟聚合最大耗时也接近 `3.3 s`；
- DAQ 恢复后队列深度仍为 0，`EndRead`、`Rearm` 通常接近 0～0.01 ms，磁盘队列和 CPU 也没有持续饱和证据。

这些时间高度对齐。最合理的当前假设是：线程池/异步 continuation、系统调度、驱动/DPC、GC 或其他主机级瞬时停顿共同延迟了多个回调。它不是最终定论，因为现有数据没有 ETW、GC pause、ThreadPool、DPC/ISR 和 NI 驱动 trace；但它要求 DAQ、PSU、Watchdog 的设计不能把所有安全期限都押在同一类 `Task.Delay/Task.WhenAny` 和异步回调调度上。

同时，运行中还存在多次主要落在 Dev1 的约 1.16～1.18 s 空窗。这提示至少要并行验证两个假设：

- 单设备/端口/驱动链问题：更偏向 Dev1；
- 主机公共调度停顿：双 DAQ、多个 PSU、Watchdog 同时受影响。

不能用一个“线程池卡顿”标签把所有 DAQ 长尾都提前结案。

## 3. 根治后的统一故障模型

根治后的运行链应固定为：

```text
原始异常证据
  → 创建/命中唯一 RootIncident
  → 立即撤销执行权并执行物理安全动作
  → 冻结故障 cohort、RunEpoch、RecoveryEpoch 和资源快照
  → 由唯一 RecoveryOwner 执行有限恢复
  → 恢复成功并关闭事故，或进入持久 RecoveryBlocked
  → 固化日志、快照、DMP、哈希和最终结果
```

统一身份至少包含：

```text
SessionId, RunId, RunEpoch, RootIncidentId, RecoveryEpoch,
Device/Group, AffectedChannels, PrimaryCauseCode,
FirstSeenMonotonic, EvidenceRevision, RecoveryOwnerId
```

统一终态只能是：

- `Recovered`：安全、资源和业务进度均重新满足阶段契约；
- `RecoveryBlocked`：已安全停机，自动恢复预算耗尽或遇到确定性故障，禁止隐式重拉；
- `OperatorClosed`：操作员在确认证据和安全状态后关闭。

不存在无限 `Recovering`、无 owner 的 `Paused`、只有布尔值没有事务身份的“假恢复”，也不存在同一根故障由 DAQ、Timer、PSU 和 Watchdog 各自启动一条恢复链。

## 4. 问题一：4 次自动接管

### 4.1 证据与根因分层

| 层次 | 判断 | 依据 |
|---|---|---|
| 现象 | 已确认 | 47.96 h 内 4 次接管；1 次 `ChannelProgressStalled`，3 次 `OrphanPausedTimeout` |
| 安全结果 | 已确认 | 四次均完成安全停机、旧进程终止、恢复进程启动和批次恢复 |
| 3 次孤儿暂停的软件机制 | 高置信并已在后续整改中定位 | 迟到 Timer 状态可覆盖新恢复状态；恢复 cohort 可漂移；正常活动周期被计入 `SoftwareRecoveryCount`；失败恢复缺少可靠终态 |
| 第一次 EPB9 60.1 s 无进展的最底层触发 | 未完全确认 | 第一次 DMP 已被清理，接管前又有 DAQ/落盘突发；只能确认“进度真实停滞”，不能仅凭现有日志锁定具体线程栈 |

### 4.2 必须保留并发布验证的后续结构修复

当前 v2.13.0.12/.13 候选实现中，下列机制是根治自动接管误判/循环的必要基础，不能回退：

1. Timer 状态带单调 `TimerGeneration`，迟到事件必须同时匹配 `RunId + RunEpoch + TimerGeneration` 才能改变通道状态。
2. 一次恢复开始时冻结 cohort；后续通道退出、完成或报警只更新事务结果，不能悄悄改变本次恢复参与者。
3. 活动周期数与恢复 owner 数分离，健康运行不能把 `RecoveryActive` 置为真。
4. 阶段化资源契约：例如 Learning 阶段合法形态不能按 Running 阶段的 Timer/Runner 要求误判。
5. Sidecar 首次发现资源矛盾时先请求同源结构化快照刷新；只有相同运行身份、相同故障签名持续到硬截止时间，才允许接管。
6. 确定性失败立即进入 `RecoveryBlocked`；瞬态和未知故障分别只有有限预算；阻断后 sidecar 重启也不能绕过。
7. 重启前必须同时验证 `MotorOff`、`PowerOff`、`PressureSafe`、持久化边界和逻辑资源清场。

### 4.3 仍需补齐的根治项

1. **建立唯一生命周期状态机。** 通道的 `Learning/Running/PausePending/Paused/Recovering/Completed/Alarmed` 只能由一个中心 transition gate 更新。Timer、Runner、DAQ、UI、恢复任务只能提交带 epoch 的事件，不能直接写状态。
2. **把接管判断改成证据协议。** Watchdog 必须收到 `TelemetryValid=true` 的原子快照，并核对进程身份、阶段契约、状态版本和刷新结果；空对象、旧快照和 provider 异常不得解释成“Timer/Runner 缺失”。
3. **先按故障作用域隔离。** 单 DAQ/单液压组事故优先只冻结受影响 cohort；只有共享资源失效、物理安全无法证明或主进程失去响应时，才升级为全局 StopAll/进程接管。
4. **把接管作为最后一级动作。** 顺序固定为：发现异常 → 安全关断 → 结构化刷新 → 有界本地恢复 → 明确失败后才进程接管。任何层级不得反向并发发起第二条恢复链。
5. **每次接管绑定唯一 `TakeoverId`。** DMP、StopAll、进程终止、恢复进程和最终结果均引用同一个身份，以便去重和审计。

### 4.4 自动化与故障注入

- 连续注入 10,000 次旧 Timer 的迟到 `Paused`，状态不得被旧 generation 覆盖；
- Learning 合法资源形态持续 30 min，不得触发缺 Timer 接管；
- 人工暂停、自动恢复、通道完成、永久报警并发交错，不得产生无 owner `Paused`；
- 单设备 DAQ 停顿、双设备公共停顿、恢复中再次停顿，各自只能产生一个 RootIncident 和一个 RecoveryOwner；
- 注入确定性配置错误，必须直接进入持久 `RecoveryBlocked`，重启 sidecar 后仍不得启动主程序；
- 注入瞬态故障直到预算耗尽，必须进入同一终态，禁止无限 `CircuitProbe`。

### 4.5 验收门禁

- 正常长稳：`OrphanPausedTimeout=0`、`ChannelProgressStalled=0`、非预期自动接管 `=0`；
- 故障注入：每个故障最多一个 `TakeoverRequested`，停止链和恢复链身份完整；
- 每次接管都必须在一个确定终态结束，不允许会话无限 `Recovering`；
- 自动恢复成功后无遗留 Timer、Runner、CTS、液压 lease 或恢复 owner；
- 达到第 10 节的实机长稳门禁后，才能把 v2.13.0.11 的 4 次接管问题标记为“现场关闭”。

## 5. 问题二：约 21 组错误事件与 122 条 error

### 5.1 根因

日志中的主要链条通常是：

```text
DAQ callback/sample stale
  → 压力/电流新鲜度不可证明
  → 执行权撤销、FailSafe、PSU 关断
  → Timer/周期中止
  → 自动隔离与恢复
```

这是一个根事件在 AI、liquid、EPB、Timer、PSU、Watchdog 多个模块中的派生记录。问题不只是“日志太多”，而是如果每个模块都把自己当恢复发起者，就会放大成并行 StopAll、重复快照、重复蜂鸣和恢复状态竞争。

当前 `Controller/DaqIncidentLatch.cs` 已经能按运行和设备锁存 DAQ incident，并在两设备 100 ms 内同时发现异常时尝试复用关联号；这是正确方向，但还不是跨 DAQ、PSU、Timer、Watchdog 的全局根事件协调器。

### 5.2 根治设计

新增/强化统一 `RootIncidentCoordinator`：

1. 所有模块只上报 `IncidentObservation`，由协调器决定创建新事故或附加到已有事故。
2. 根因优先级按证据质量而不是模块先后决定。例如 `DaqCallbackGap` 可成为主因，`PressureStale`、`OffCurrentUnverifiable`、`CycleAborted` 作为 `DerivedFrom`。
3. 根事件状态固定为 `Detected → SafeContained → Diagnosing → Recovering → Recovered/Blocked`。
4. 每个状态跃迁只写一条结构化 ERROR；同状态下的重复/派生明细进入聚合字段、环形证据或 DEBUG，不再重复触发动作。
5. 同一 RootIncident 只允许一个安全动作 owner、一个快照 owner、一个恢复 owner。其他模块只能追加证据。
6. 事故结束时写一条闭环摘要：首因、派生码、受影响设备/通道、最大 age、关断结果、恢复结果、耗时、证据路径。
7. 统计口径分离：`RootIncidentCount` 代表真实事故数，`DerivedObservationCount` 代表诊断丰富度，不能再用 error 行数衡量可靠性。

跨设备合并不能只靠固定 100 ms 窗口。还应同时核对：

- 相同 `RunId/RunEpoch`；
- 单调时间窗口重叠；
- 是否同时出现 Host/Watchdog 调度迟滞；
- 是否共享液压组、PSU 或安全动作；
- DAQ generation 和恢复 epoch 是否一致。

### 5.3 验收门禁

- 注入一次 1.2 s DAQ 空窗，最终只能有 1 个 RootIncident、1 次主报警、1 份主快照、1 个恢复 owner；
- AI、压力、关断电流、Timer 和 PSU 派生症状全部带同一 `RootIncidentId`；
- 重复 observation 不得延长恢复预算或重置硬截止时间；
- 根事件闭环摘要必须能从日志一条记录定位全部证据；
- 日志降噪不得删除原始取证：详细 DAQ/DO 进入事件前后环形缓冲，事故发生时固化。

## 6. 问题三：DAQ 1.0～1.4 s 长尾

### 6.1 已确认与未确认

已确认：

- 当前安全新鲜度上限是 100 ms，现场最大 callback/control age 约 1,435.6 ms，超限一个数量级；
- 多次 Dev1 空窗约 1.16～1.18 s；
- 08-19 11:46 双设备同时约 3.315 s；
- 长空窗后的 `EndRead`、`Rearm` 和队列深度不高，说明至少部分延迟发生在回调进入之前，不是下游处理队列长期积压；
- 当前 `OnAiBatch()` 在 `EndRead` 后仍完成时钟模型、快速代表值、质量扫描、控制队列复制和后台发布，最后才再次 `BeginReadMultiSample()`。这会扩大回调执行时间的敏感面，虽然它不能单独解释已经发生在回调进入前的 1～3 s 空窗。

尚未确认：

- NI 驱动/固件、设备端缓冲、总线/端口、DPC/ISR、GC pause、ThreadPool starvation 中哪一个是主要物理根因；
- Dev1 单设备长尾和 08-19 双设备公共停顿是否属于同一原因。

### 6.2 根治分为“设计去敏感”和“现场定根因”两条线

#### A. 设计去敏感

1. **回调最小化并尽早续采。** `EndRead` 和 generation 校验后，优先完成下一批采集的安全 rearm；时钟估计、工程量转换、日志、质量统计和派生发布转移到预分配的专用 worker。若 NI API 的 buffer 所有权不允许先 rearm，则改为明确的双缓冲/连续采样模式，而不是在同一回调里扩大临界区。
2. **不让安全期限依赖通用线程池。** DAQ freshness monitor、关键控制消费和 FailSafe 触发使用独立、长期存活、可观测的专用线程/调度器；不建议使用 Windows `Realtime` 优先级，以免反向饿死系统和驱动。
3. **全链路零/低分配。** callback 内不得逐批创建大对象、做无界字符串格式化或同步磁盘 I/O；数组、控制尾窗和事件对象预分配/池化。
4. **独立的单调时钟监督。** 同时记录硬件样本时间、回调入口、`EndRead` 完成、rearm 完成、控制消费和物理关断时间。回调停顿时由独立 freshness monitor 撤销执行权，而不是等待下一次回调自己发现已经陈旧。
5. **按作用域分类。** 仅 Dev1 停顿归类为 `DeviceDeliveryStall`；双设备并伴随 Watchdog/PSU 延迟归类为 `HostAsyncSchedulingStall`；两类事故走不同诊断和恢复路径。
6. **先安全、后重建。** 超过 100 ms 时立即使样本无效并撤销相关执行权；DAQ task 重建、设备复位和试验恢复不得阻塞物理安全动作。

#### B. 现场定根因

常驻低开销环形诊断，越界时固化前后至少 60 s：

- ETW：线程调度、ThreadPool queue/worker、GC pause、异常、磁盘 I/O；
- Windows Performance Recorder：CPU sampling、DPC/ISR、context switch；
- NI：驱动版本、设备/任务状态、buffer overrun、USB/PCIe/网络链路事件；
- 每个 DAQ 设备独立的 callback entry、hardware sample age、generation、rearm duration；
- Watchdog ACK、PSU phase 和主机资源使用同一单调时间基准。

按以下矩阵做 A/B，单次只改变一个变量：

| A/B 项 | 判定目的 |
|---|---|
| Dev1/Dev2 交换物理端口、线缆、设备角色 | 问题跟设备走还是跟端口/主机通道走 |
| 更新/回退已验证的 NI 驱动与固件 | 是否为特定驱动组合 |
| 关闭非必要第三方服务、杀毒实时扫描的测试目录监控 | 是否存在系统级 pause/扫描干扰 |
| 压低普通日志量但保留环形取证 | 验证日志 I/O 是否放大调度长尾 |
| 独立采集进程或独立主机对照 | 区分应用内调度与硬件/驱动问题 |

### 6.3 故障注入与验收

必须注入：单设备回调暂停 120 ms/1.2 s/3.5 s、双设备同时暂停、ThreadPool 饥饿、长 GC、处理队列满、磁盘延迟、设备断开/重连。

验收标准：

- 正常发布长稳中，DAQ callback/sample age 不得越过现有 100 ms 安全门限；
- 每个越界事件 100% 具有分类和时间证据，不允许只留下 `sample stale` 文本；
- 故障注入时不得继续使用旧样本做安全判定；执行权撤销和物理安全动作必须通过既有安全时限用例，不能把“100 ms 新鲜度”错误等同于未经评审的机械动作时限；
- 单次 DAQ 根事件只有一个恢复 owner，成功恢复或进入 `RecoveryBlocked`，不得产生孤儿暂停；
- 正常状态的处理/原始/持久化队列没有永久 gap、溢出或未结清 in-flight；
- ETW/NI 证据能够把下一次长尾归入设备、驱动、主机调度或应用临界区之一，否则问题仍标记“未定根因”。

## 7. 问题四：两次 Watchdog `HeartbeatProvider` 空引用

### 7.1 当前风险

现场两次事件分别发生于 08-17 23:59:40 和 08-18 11:21:55。现有 v2.13.0.11 日志只有“未将对象引用设置到对象的实例”，没有堆栈和具体字段，不能定位是哪一个集合、对象或释放竞态。

当前 v2.13.0.13 代码在 provider 抛异常后会：

1. 创建一个空 `WatchdogHeartbeat`；
2. 写入 `RecoveryCode=HeartbeatProviderFault`；
3. 只记录 base exception message；
4. 仍把这个心跳发送给 sidecar。

这比完全中断心跳好，但空对象仍可能与“正常但没有资源”的业务状态混淆。v2.13.0.13 的刷新前置能降低误接管概率，却没有从数据模型上消除“无效遥测被当成有效快照”的歧义。

### 7.2 根治设计

1. **控制器只发布不可变快照。** 主流程在自己持有一致性锁/版本门时构造 `ImmutableWatchdogSnapshot`，通过原子引用发布；provider 只读取该引用并序列化，不再现场遍历多个可变 Dictionary、Timer、Runner 和正在释放的对象。
2. **明确快照有效性。** 新增 `TelemetryValid`、`SnapshotGeneration`、`CapturedMonotonicTicks`、`DataAgeMs`、`ProviderState`、`ProviderErrorFingerprint`。异常时发送 `TelemetryValid=false`，绝不能伪装成空的正常心跳。
3. **生命周期门禁。** 所有必要控制器完成初始化后才注册 provider；停止/Dispose 前先撤销 provider 并发布 `ShuttingDown` 终态快照；启动、恢复、窗体关闭并发时也要满足这一顺序。
4. **Sidecar 的无效遥测策略。** 短暂无效时保留 last-known-good 只用于对比，不得用它继续证明当前安全；立即请求结构化刷新。持续超过固定硬期限后进入专门的 `TelemetryUnavailable` 安全流程，不能误报成 `OrphanPaused` 或 `ExpectedRuntimeMissing`。
5. **记录完整异常证据。** 记录异常类型、完整 stack、inner exception、snapshot generation、生命周期阶段和逐段采集 breadcrumb；对同一 fingerprint 限频，但第一条必须完整。
6. **传输与内容解耦。** provider 内容异常不能让 pipe 心跳线程退出；pipe 正常不等于遥测有效，两者分别统计。

### 7.3 验收门禁

- 正常长稳 `HeartbeatProviderFault=0`；
- 并发执行启动、恢复、StopAll、Dispose 各 10,000 次，不出现空引用或集合并发异常；
- 注入 provider 抛异常：sidecar 收到 `TelemetryValid=false`，先刷新，且 0 次误分类为资源缺失/孤儿暂停；
- 持续 provider 故障按设计进入一次 `TelemetryUnavailable` 安全终态，不能无限重连或反复接管；
- 每个异常都有可定位到方法和字段阶段的完整证据。

## 8. 问题五：两次明显 PSU 超时

### 8.1 现场证据

| 时间 | 设备/命令 | 配置超时 | 实际完成 | 已收字节 | 关键含义 |
|---|---|---:|---:|---:|---|
| 08-18 00:54 | PSU3 `SOUR:VOLT?` | 2,000 ms | 13,374.674 ms | 6 | 首字节约 10 ms 已到，但完整行/终止符未按期完成，且软件超时本身晚触发约 11.4 s |
| 08-19 11:46 | PSU4 `SOUR:VOLT?` | 2,000 ms | 3,308.263 ms | 5 | 与双 DAQ 3.315 s 空窗和 Watchdog ACK 3.131 s 超时同窗 |

因此要分开处理两个问题：

1. 仪器/TCP 响应只到了一部分或缺少行终止符；
2. 依赖 `Task.Delay + Task.WhenAny` 的 2 s 超时没有形成真正硬截止时间。

简单把超时从 2 s 调到 15 s 会掩盖第二个问题，并延长安全动作的不确定时间。

### 8.2 根治设计

1. **每台 PSU 一个有界 session worker。** 查询、设置、关断按优先级进入同一串行 worker；普通遥测不得占住安全关断队列。
2. **硬截止时间由独立监督器执行。** 监督器不与普通异步 continuation 共用易饥饿的调度面。到达 deadline 后主动关闭 socket/transport，使在途读立即失败；调用必须在 `2,000 ms + 允许调度裕量` 内返回。
3. **缓冲式 SCPI frame parser。** 一次读取可用缓冲而不是每字节创建数组和异步读取；识别 `\r/\n`，限制最大行长，保存 bounded partial bytes/hex 和终止符状态。
4. **超时后废弃整条连接。** 未完成读取不得留在后台吞掉下一条命令响应；重连后必须执行会话清理/身份检查，再恢复遥测。
5. **安全命令优先。** 一旦 FailSafe 触发，取消/中断低优先级查询，优先执行 OFF；如果 PSU 链路本身不可用，必须由上游安全链/硬件断电路径兜底，不能等待遥测查询恢复。
6. **协议与网络取证。** 对 PSU3/4 开启短期 packet capture 或交换机端口镜像，核对设备是否实际发送完整 `SOUR:VOLT?` 响应、是否缺少 LF、是否存在重传/RST/窗口阻塞。
7. **共同停顿归并。** 08-19 11:46 这类双 DAQ、Watchdog、多个 PSU 同时迟滞的事件，应归为主机级根事件；PSU partial frame 仍作为派生证据保留，不重复启动恢复。

### 8.3 故障注入与验收

模拟服务端必须覆盖：正常行、只有部分字节无 LF、慢速逐字节、半开连接、远端 FIN/RST、超时 continuation 被延迟、调用方取消和关断命令抢占。

验收标准：

- 配置 2,000 ms 时，任何查询在建议门禁 `≤2,250 ms` 内成功或失败返回；若平台测量证明需要不同裕量，必须经评审固化，不能按事故临时放宽；
- partial line 超时后下一条命令不被旧读取吞响应；
- 安全关断从入队到开始执行不受普通遥测查询阻塞，并通过整机物理关断验收；
- 正常长稳 `PSU query >2,000 ms=0`；故障注入时进入一次通信降级/恢复或明确阻断，不产生重复 error 风暴；
- packet capture 能判断两次事件是设备缺终止符、网络传输还是主机调度延迟；未完成该判断前，PSU 物理根因状态仍为“开放”。

## 9. 问题六：第一次接管 DMP 缺失

### 9.1 确定根因

源码 `MTTFTest.Watchdog/MiniDumpCapture.cs` 当前仍采用以下规则：

```text
按 CreationTimeUtc 倒序
仅保留 index < 3
且累计大小不超过 256 MiB
```

同一 session 的 4 次自动接管对应 4 个转储，后 3 个现存；第一次已成功记录但因“最近 3 个”规则被第四次捕获后的 `Prune()` 删除。四份合计约 70 MiB，本来远未达到 256 MiB 大小上限。

另有一个并发问题：第一次接管同时从 `AutomaticTakeover` 和 `StopCompletedButProcessAlive` 两条路径发起转储；一个成功、一个失败。DMP 捕获没有以 PID/接管身份串行化。

### 9.2 根治设计

1. **捕获去重。** 使用 `SessionId + ProcessId + ProcessStartUtcTicks + TakeoverId` 作为幂等键；同一进程同一次接管只允许一个在途捕获，其他请求复用同一 Task/结果。
2. **事务化写入。** 在同一卷写 `.tmp`，`MiniDumpWriteDump` 完成后 Flush，验证文件非零、可重新打开，计算 SHA-256，最后原子 rename 为 `.dmp`。
3. **收据后置。** 只有最终文件存在、长度和哈希已写入 `dump-manifest.jsonl` 后，才能记录 `DumpCommitted`；`Captured=` 不再作为最终成功语义。
4. **按事故留存。** 每个未关闭 RootIncident/Takeover 至少保护 1 份 DMP；当前 session 的未归档事故不得按固定 3 份删除。空间不足时先清理已关闭、已归档、已校验且低优先级的旧 session。
5. **归档握手。** 数据采集/打包工具读取 manifest，复制后重新计算哈希并回写 `ArchiveVerified`。只有该状态成立，源端才允许按策略清理。
6. **失败降级。** 完整 dump 失败时记录 Win32 error 和 stack，尝试更小的 dump type 一次；仍失败则保存线程清单、模块清单、Watchdog/RootIncident 快照，不能只留一句失败文本。
7. **超时可收敛。** 3 s 到期时必须取消/终止捕获或等待明确结果；不能一边记录 timeout、一边让后台捕获继续与进程终止竞争。

建议 manifest 字段：

```text
TakeoverId, SessionId, PID, ProcessStartUtcTicks, Reason,
RequestedUtc, CommittedUtc, Path, Bytes, Sha256, DumpType,
CaptureResult, Win32Error, ArchivePath, ArchiveSha256, ArchiveVerifiedUtc
```

### 9.3 验收门禁

- 每次符合捕获条件的接管必须有且只有一个 `DumpCommitted`；
- journal、manifest 和实际文件三方一致率 100%，SHA-256 校验通过率 100%；
- 同一 session 连续模拟 10 次接管，前 10 个未关闭事故的 DMP 都不得因固定数量策略提前删除；
- 模拟磁盘满、拒绝访问、DbgHelp 失败、超时、进程提前退出和并发双请求，均得到明确终态和可用降级证据；
- 归档工具完成哈希握手前，源文件不得清理；
- 第一次已经被删除的 PID21228 DMP 无法由现有数据重建；除非存在外部备份，否则只能把该次线程栈证据标记为永久缺口。
