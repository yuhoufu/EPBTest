## 1. 结论先行

### 1.1 总体判定

**总体健康度：有条件健康，黄灯。**

更准确地说：

- **安全保护链健康**：发现采样陈旧、液压状态不可验证或通道停滞时，程序能够撤销执行权、关断输出、执行隔离恢复；4 次看门狗接管均完成安全停机，重启前检查均显示 `MotorOff=True`、`PowerOff=True`、`PressureSafe=True`、`Logical=True`，且 `AbortedOrphanCycles=0`。
- **数据完整性健康**：SQLite `PRAGMA quick_check=ok`；本版本窗口内 57,299 条周期记录没有重复 `(epb_id, cycle_number)`，没有负持续时间，也没有缺失结束时间。
- **资源与基本实时性健康**：未出现 CPU、内存、磁盘空间或队列持续耗尽；正式启动偏差 p95 约 14.94 ms，DO 命令耗时 p95 约 1.55 ms。
- **运行稳定性仍不达“完全健康”**：近 48 小时内发生 **4 次看门狗自动接管**，其中 3 次是 `OrphanPausedTimeout`，1 次是 EPB9 连续约 60 s 无进展；另有约 21 组错误事件，主因是 DAQ 回调/样本偶发陈旧到约 1.0～1.4 s，明显超过 100 ms 安全新鲜度要求。
- **报警本身不严重，但告警噪声很大**：本版本窗口没有永久报警、没有新增 `AlarmSnapshots`；4,355 条 warning 中 3,888 条（89.28%）是峰值软告警，峰值没有达到 `+2 A` 永久报警门槛。大量软告警会造成“报警疲劳”。
- **`run` 日志对日常健康监控确实过于冗余**：约 47.96 小时产生 1,989,581 行、512.72 MiB，平均 11.52 行/s；约每个正式完成周期写 34.94 行、9.44 KB。它对事故取证有价值，但不适合作为日常运维主视图。

因此，这个版本可以继续在**有人监控、保留自动保护、设置验收门槛**的条件下运行；但不能只凭“运行时间最长”就宣布稳定性问题已经解决。

### 1.2 “最长正常运行”的准确含义

本次是**试验服务层面**连续运行约 47.96 小时，但中间由看门狗执行了 4 次自动接管和进程拉起。最长单个进程观测时长约 16.57 小时，而不是 47.96 小时。

以每次 `TakeoverRequested` 到 `RecoveryBatchCommitted` 的全局恢复区间计，4 次恢复合计约 576.57 s（9 分 36.6 秒），试验服务连续性约为 **99.666%**。这是服务可用性指标，不等同于单进程无故障稳定性。

- `AlarmEvidenceRecovery` 当前窗口新增文件数：0；

### 6.3 Error：122 行约对应 21 组事件，不是 122 个独立根故障

122 条 error 的类别为：EPB 51、PSU 25、Timer 22、AI 16、liquid 6、watchdog 2。按相近时间和共同上下文合并后，大约是 21 组事件簇。

主传播链通常为：

`DAQ callback/sample stale`  
→ 液压样本超过 100 ms、状态不可验证  
→ off-current 或动作结果不可确认  
→ PSU FailSafe/通道执行权撤销  
→ 周期中止或隔离恢复  
→ 同一根事件在 EPB、AI、liquid、Timer、PSU 多处各记一条 error。

因此，error 行数会放大根事件数量；但 **1.0～1.4 s 的 DAQ 偶发停顿是真实存在的**，不能因为自动恢复成功就忽略。

两个明显 PSU 超时为：

- 08-18 00:54：PSU3 `SOUR:VOLT?` 用时 13,374.7 ms；
- 08-19 11:46：PSU4 `SOUR:VOLT?` 用时 3,308.3 ms。

它们都超过 2,000 ms 配置上限。后者与看门狗 ACK 超时/transport lost 几乎同时发生，值得从仪器网络、串口/网口驱动、线程池阻塞、系统瞬时调度停顿几个方向联合排查。

### 6.4 “Unhandled” 并不等于未处理进程崩溃

日志中字符串 `Unhandled` 共命中 5 行，但实际只有 2 个独立异常事件：08-17 19:28 和 08-19 11:38，均为 EPB4 的 `UnhandledSoftwareException: HydraulicPressureLostException`，另外 3 行是后续说明。

从完整上下文看，这两次异常均被**正式周期外层异常边界捕获**，随后撤销通道执行权、执行 FailSafe 和隔离恢复。当前窗口没有发现 `Fatal`、OOM、`StackOverflow`、`AccessViolation` 或未捕获异常导致的直接进程退出。

因此它们是“业务层将该异常标成 UnhandledSoftwareException”，不是 CLR/操作系统意义上的未处理崩溃。命名容易让运维误解，建议后续在日志语义上区分“被周期边界捕获的业务异常”和“进程级未处理异常”。

## 8. `run` 日志是否过于冗余

### 8.1 量化结果

答案是：**对日常运维和健康判定而言过于冗余；对事故取证而言仍有价值。**

- 12 个 run 轮转文件；
- 1,989,581 行；
- 512.72 MiB；
- 平均 11.52 行/s、约 256.6 MiB/天；
- 平均每个正式完成周期约 34.94 行、9.44 KB；
- run 中都是 INFO，未发现与 warning/error 文件逐行完全重复，因此问题主要是 run 内部的高频轨迹，而不是三个等级文件互相复制。

主要占用如下：

| 类别 | 行数 | 行占比 | 字节数 | 字节占比 |
|---|---:|---:|---:|---:|
| EPB | 609,429 | 30.63% | 143.47 MB | 26.69% |
| FIELD | 365,690 | 18.38% | 216.91 MB | 40.35% |
| DO 操作 | 275,819 | 13.86% | 19.81 MB | 3.69% |
| AI | 206,664 | 10.39% | 32.46 MB | 6.04% |
| HOST | 170,981 | 8.59% | 50.98 MB | 9.48% |
| EPB-DO | 114,887 | 5.77% | 43.33 MB | 8.06% |

FIELD 中最占空间的是 DAQ：167,762 行、173.56 MB。HOST 资源状态约每秒 1 条，共 170,981 行、50.98 MB。多个固定模板几乎每个通道周期都会重复写入，例如峰值捕获开始、正向/反向 DO、关断确认、历史快照写入等。

### 8.2 建议的日志分层

以下仅为后续整改建议，本次没有修改程序：

1. **运维 INFO**：每个通道周期保留一条结构化摘要，包含周期号、耗时、峰值、液压、终态、是否恢复；保留启动、停止、报警、接管和恢复结果。
2. **详细 TRACE/DEBUG**：正反向 DO、AI 峰值捕获过程、FIELD DAQ 周期性状态等保留到可开关的详细日志，不作为默认 INFO。
3. **事件前后环形证据**：平时采样，发生 warning/error/接管时固化前后 30～120 s 的完整 DO/DAQ 轨迹，兼顾低噪声和取证能力。
4. **HOST 降采样**：从约 1 s 改为 10～30 s，状态变化或阈值越界时立即写；仅此项预计可在本窗口减少约 49 MB。
5. **FIELD DAQ 降采样/事件化**：稳定状态每 10～30 s 写摘要，队列、age、连续性指标越界时恢复高频。
6. **软告警聚合**：同通道、同类型、同区间的峰值偏差按 1～5 分钟汇总数量、最大值、p95，而不是逐周期 warning；首次、恶化、恢复时单独记录。
7. **保留策略**：按天数和总容量双限制；永久报警、接管和未恢复异常的证据包单独长期保留。

从类别占比估算，默认日志量有机会降低 **70%～90%**，同时保留事故级完整轨迹。该比例是基于当前模板占比的估算，需在实施后用相同 24～48 小时工况复测确认。

## 9. 建议的处理顺序与继续运行门槛

### 9.1 立即执行的非代码措施

1. 将当前状态定义为“黄灯受控运行”，不要以“最长运行”替代稳定性验收。
2. 重点监控以下关键字/指标：`TakeoverRequested`、`OrphanPausedTimeout`、`ChannelProgressStalled`、`DaqSampleStale`、`HeartbeatProvider`、`TransportLost`、PSU 查询 elapsed。
3. 保全现有 3 个当前窗口 DMP、看门狗 session JSON/JSONL、`index.db` 与 WAL；第一次接管缺失的 PID21228 DMP如在源主机其他目录可找到，应补入事故档案。
4. 对 08-18 00:54 和 08-19 11:46 的 PSU/系统通信时段做设备侧日志、网络交换机/串口服务器日志和 Windows 事件日志的时间对齐。

### 9.2 建议的下一阶段验收门槛

建议至少再观察一个连续 24～48 小时窗口，并同时满足：

- 自动看门狗接管：0 次；
- `OrphanPausedTimeout` / `ChannelProgressStalled`：0 次；
- DAQ 样本超过 100 ms 并触发 FailSafe 的事件簇：0 组；
- `HeartbeatProvider` 空引用及看门狗 transport lost：0 次；
- PSU 查询超过 2,000 ms：0 次；
- 永久报警：0；

- 软件恢复中止率不高于当前 0.0733%，并优先要求达到 0。

在这些条件满足前，版本可以继续试验，但应定位为“安全自愈有效、稳定性待收敛”，不宜定位为“完全稳定、可长期无人值守”。

## 10. 最终判断

v2.13.0.11 相比“直接报警停机或无法自动恢复”的状态，已经表现出明显改进：安全链闭环、自动接管可恢复、周期数据完整、资源和实时性主体健康，且本窗口没有永久报警。

真正需要警惕的不是 4,355 条 warning 的表面数量，而是其背后的少数高价值信号：**4 次自动接管、约 21 组错误事件、DAQ 1.0～1.4 s 长尾、两次看门狗空引用、两次明显 PSU 超时，以及第一次接管 DMP 缺失。**这些问题都被安全机制成功兜住了，但“被兜住”不等于“根因已经消失”。

综合结论：**程序当前可受控继续运行，安全性表现合格；长期无人值守稳定性尚未通过，应优先解决接管频率、DAQ 长尾、看门狗自身异常和 PSU 通信超时，再用单进程连续 24～48 小时无接管作为下一阶段健康证明。**
