# 10364-009 V2.5.0.5_1 与当前版本 DAQ 数据过时对比分析

> 分析时间：2026-08-05（Asia/Shanghai）  
> 旧版数据：`\\wj-epb\EPB_Data\10364-009_V2.5.0.5_1`  
> 旧版发布提交：`4fd1e6122f1ccbe21a8e99d1ca52805b02a08d66`（V2.5.0.5）  
> 当前工作区版本：`2.10.2.2`  
> 对比事件：`10358-029` 的 Dev1 `DaqSampleStale>100ms` / 约 1.160 s 留存数据空洞  
> 结论状态：**源码整改和自动测试已通过；真实 NI 硬件长跑尚未验收**

当前 `2.10.2.2` 仍包含未提交的源码改动；本文对“当前版本”的判断指本次实际编译、测试的工作区，不代表现场已经部署了同一二进制。现场结论必须以部署包SHA-256为准。

## 1. 技术结论

### 1.1 当前版本能否解决“数据过时”

答案需要分成三层：

1. **对已经确认的软件链路问题，当前工作区已经进行了针对性整改。** Dev1/Dev2 的控制、后台处理和持久化不再共用一条同步消费链；控制样本、UI发布和磁盘写入被拆开；队列满不再静默覆盖；安全新鲜度使用“有效控制样本已提交”而不是仅使用“回调进入”。本次自动测试全部通过。
2. **对真实发生的采集或控制断流，当前版本仍会在 100 ms 时安全停机。** 这不是“问题未解决”，而是必须保留的失效安全行为。新版本会进一步区分 `DaqCallbackStale`、`ControlEnqueueStale` 和 `ControlProcessingStale`，锁存受影响设备的通道，并保留诊断证据；DAQ恢复后也不会自动重新上电。
3. **目前不能宣称从根源上保证永不再出现数据过时。** NI板卡、DAQmx驱动、Windows调度、GC或硬件链路仍可能造成真实停顿。当前代码尚未经过六路真实NI硬件的长时间验证，因此结论应写成：**软件已具备消除已知拥塞源并安全处理真实断流的能力，但现场根除仍待验证。**

### 1.2 为什么 V2.5.0.5_1 的早期数据看起来没有出现

“V2.5.0.5 以前没有这个问题”不是完整结论，原因如下：

- V2.5.0.5 源码本身已经包含 `DaqSampleStale>100ms` 看门狗，不是后续版本新增检测后才“多出报警”。
- 用户提供的 `V2.5.0.5_1` 数据只覆盖约 25 分钟、397 个正式圈记录，其中 396 圈完成、1圈因 EPB10 电流爬升停滞报警；这个样本量不足以证明长时间不会出现偶发过时。
- 该早期试验的正式运行通道为 EPB8、9、10、11，带电和圈数据写入负载集中在 Dev2；Dev1采集任务虽然启动，但没有 EPB1～6 正式圈。当前 `10358-029` 的六路运行同时覆盖 Dev1和Dev2，且首发事件发生在 Dev1 的 EPB4/5，负载形态并不相同。
- 旧版早期保留CSV中已经能看到一次 Dev2 同步抖动：EPB8、EPB9、EPB11 在 `2026-07-31 14:47:01.8842237` 到 `14:47:01.8972495` 同时出现 `13.0258 ms` 相邻样本间隔。它没有超过100 ms，所以不会触发停机，但说明旧版并非完全没有采集/调度抖动。
- 更长的同项目现场备份 `D:\EPB_Data\10364-009_0731_20260803_backup` 在 `2026-08-02 01:28:09` 明确记录 EPB11 第8036圈 `DaqSampleStale>100ms`。该长跑数据累计约 42,668 个完成正式圈，证明早期“未见”主要是观察窗口较短，不等于旧版免疫。
- V2.5.0.5 的 `DaqCallbackTimingLog=off`。没有触发硬故障时，回调间隔、`EndRead`耗时、线程池和GC等亚阈值证据不会留下完整记录，也容易形成“以前一直正常”的印象。

需要注意：长跑备份没有保存部署EXE哈希，不能仅凭目录名对二进制做密码学同一性证明；但其运行时间处于 V2.5.0.5 发布之后、V2.5.0.6 发布之前，并且日志明确存在同类报警，足以否定“旧软件体系从未出现数据过时”的绝对说法。

三次 `13.0258 ms` 间隔同时出现在 Dev2 的 EPB8、EPB9、EPB11 第100圈，时间完全一致，说明这是设备级批次/调度抖动，不是三只卡钳各自的机械现象。它仍低于100 ms安全阈值。

### 2.3 同项目长跑中的反例

本机保留的长跑备份中存在下列原始日志：

```text
2026-08-02 01:28:09.273 ERROR 报警 EPB[11] 硬故障，立即停止该通道并导出报警快照。
原因=AdaptiveHardFault DaqSampleStale>100ms
```

对应信息：

- 通道：EPB11（Dev2）；
- 正式圈：8036；
- 结果：通道安全停机，之后人工停止并重启；
- 长跑累计完成正式圈：EPB8 15,049、EPB9 11,390、EPB10 1,197、EPB11 15,032，合计42,668圈。

报警圈留存CSV的样本时间仍基本连续，EPB11第8036圈最大相邻时间间隔约 `7.4461 ms`。这并不否定100 ms实时过时：NI缓冲区中的样本可在控制线程恢复后补交，最终CSV保持连续，但控制看门狗在当时已经超过100 ms没有收到可用更新。它进一步说明要区分：

- 硬件是否丢样；
- 回调是否准时进入；
- 控制样本是否准时提交；
- 数据是否最终补写到CSV。

旧版只有单一 `DaqSampleStale`，无法把这四层拆开定位。

## 3. 旧版未早发、后续版本暴露的主要原因

### 3.1 不是阈值新增，而是曝光量和负载变化

V2.5.0.5 发布提交中的 `Controller/Adaptive/EpbAdaptiveControl.cs` 已在带电阶段检查：

```text
最后控制样本超过100 ms未更新 -> DaqSampleStale>100ms
```

因此不能用“新版增加100 ms检测”解释现象。更合理的解释是：

1. 早期397圈观察窗口短；
2. 带电及落盘集中在Dev2四路，当前六路跨两设备并行；
3. 后续版本增加了更多自适应判断、诊断、快照、UI和持续持久化工作，实时裕量下降；
4. 旧架构使用一个 Dev1/Dev2 共享的后台队列和单个 `ProcessLoop`，任一设备或订阅者变慢会积压整条链路；
5. 诊断日志默认关闭，使亚阈值抖动和偶发停顿缺少证据。

### 3.2 已确认的直接事件与尚未确认的底层原因

`10358-029` 的 Dev1 事件已经确认：

- EPB4和EPB5在同一时间因 Dev1 控制样本超过100 ms而停机；
- 当时样本年龄约157 ms；
- EPB5留存CSV存在约 `1,159.667 ms` 空洞；
- Dev1重建后约 `1,195 ms` 取得连续新鲜回调；
- 事件前出现过后台积压，最大可见证据达到 `QueueDepth=21 / OldestBatchAge=208.7 ms`。

但旧日志没有保存事发瞬间的 `EndReadMultiSample` 耗时、重新挂读耗时、GC暂停和线程池探针，因此不能把该次事件唯一归因于 NI板卡、DAQmx驱动、Windows调度、GC或某个订阅者。当前整改的价值之一，就是下次可以把故障定位到具体层级，而不再只有一个笼统的“数据过时”。

## 4. 当前 2.10.2.2 的针对性整改

| 整改项 | 当前实现 | 对数据过时的作用 |
|---|---|---|
| 设备隔离 | Dev1/Dev2独立控制环、后台队列、信号和工作线程 | 一台设备的慢处理不拖住另一台 |
| 控制与持久化拆分 | 控制样本先进入独立快速环；原始批次再交给后台处理和独立持久化协调器 | 磁盘/SQLite/UI变慢不应阻塞安全控制样本 |
| 有界队列 | 每设备控制/处理队列容量64；队列满发布设备级硬故障 | 不允许无限积压或静默丢弃 |
| 心跳拆分 | 分别记录回调进入、控制入队、控制处理和有效样本提交 | 100 ms安全判断不再被“只有回调、没有有效样本”伪装通过 |
| 根因分类 | `DaqCallbackStale`、`ControlEnqueueStale`、`ControlProcessingStale` | 区分NI/调度、回调生产区和控制消费区 |
| UI限频 | 普通工程值/UI发布限为25 Hz，动作和故障不降采样 | 降低界面刷新对2 kHz采样链的压力 |
| 代次隔离 | 每次DAQ任务有唯一 generation；旧回调和旧数据被拒绝 | 避免恢复后旧批次倒灌 |
| 故障锁存 | 按设备生成一次关联事故，受影响通道断电并保持停机状态 | DAQ恢复不等于自动恢复电机运行 |
| 诊断证据 | 默认 `anomaly`，保存回调、EndRead、re-arm、队列、处理、GC、内存、线程池和恢复过程 | 下次可确定停顿发生在哪一层 |
| 安全阈值 | 继续保持100 ms | 不用放宽阈值掩盖问题 |

当前工作区还进一步做了：

- 快速控制批携带单调序号、代次、生产线程、样本时钟和质量标志；
- 拒绝回调生产区重入、重复/倒序批次和未来样本时间；
- UI只发布最新趋势，原始落盘和控制仍按2 kHz保留；
- 持久化按设备批量写入，减少逐样本数据库更新和持续分配；
- 对控制、后台和持久化积压分别记录真实队列年龄和容量。

## 6. 现场验收标准

建议把“已解决”定义为以下条件全部满足，而不是只看界面没有弹出报警：

1. 使用实际六路配置（Dev1：EPB4/5；Dev2：EPB8/9/10/11），保持 `2000 Hz / 20点每批 / 100 ms阈值`；
2. 最少连续运行500个正式圈；建议发布放行前提高到1000圈或2小时；
3. `DaqCallbackStale=0`、`ControlEnqueueStale=0`、`ControlProcessingStale=0`、`BackgroundQueueFull=0`；
4. 两设备控制队列年龄 P99 `<50 ms`，最大值 `<100 ms`；
5. 保留圈CSV不存在 `>100 ms` 相邻时间空洞；
6. 警报快照能导出最近60秒 `daq_timing.csv` 和运行时诊断；
7. 人工注入一次 Dev1断流时，EPB4/5在100 ms阈值后安全停机，Dev2四路不受影响，DAQ恢复后不得自动重新上电；
8. 部署记录 EXE、`IO.NI.dll`、`Controller.dll`、`DataOperation.dll` 的 SHA-256，避免目录名与实际二进制版本不一致。

## 8. 数据与方法

本次分析使用以下证据：

- `\\wj-epb\EPB_Data\10364-009_V2.5.0.5_1\log`；
- `\\wj-epb\EPB_Data\10364-009_V2.5.0.5_1\index.db`；

- `\\wj-epb\EPB_Data\10364-009_V2.5.0.5_1\AlarmSnapshots`；

- Git发布提交 `4fd1e61` 与当前工作区源码；
- `docs/01_Inboxes/2026-08-04_06_10358-029_17点29运行错峰失效与日志检查.md`。

计算口径：

- SQLite按 `cycle_number > 0` 定义正式圈；
- 保留CSV先按文件SHA-256去重，再以 `RelativeTimeSeconds[i] - RelativeTimeSeconds[i-1]` 计算相邻样本间隔；
- 正常采样间隔为 `1 / 2000 Hz = 0.5 ms`；
- `>100 ms` 是实时安全阈值，不等同于最终文件一定丢失100 ms数据；NI缓冲样本可能在控制恢复后补交。
