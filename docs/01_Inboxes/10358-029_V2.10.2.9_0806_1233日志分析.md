# 10358-029 V2.10.2.9 日志分析

> 数据包：`\\wj-epb\EPB_Data\10358-029_V2.10.2.9_0806_1233`  
> 重点运行窗口：2026-08-06 11:47:24 ～ 12:28:54；12:28:58 ～ 12:32:28 为人工重新开始后的验证窗口  
> 分析对象：EPB4 报警、EPB5 停止且未自愈、全程其他异常  
> 结论置信度：EPB5 未自愈根因“高”；EPB4 报警触发有效性“高”；造成首次 DAQ 回调延迟的更底层原因“中低”

## 技术结论

1. **EPB4 报警不是无依据的误报，但也不能解释为 EPB4 卡钳硬件故障。** 12:24:01，EPB4 正向上电期间 Dev1 控制样本年龄达到 112.7 ms（事故快照中的回调年龄为 114.5 ms），超过 100 ms 安全阈值。此时电源组 2 仍为 ON，独立电源遥测测得输出电流 0.506 A；控制系统无法用新鲜 DAQ 样本确认断电电流，因此按失效安全策略报警并切断电源是合理的。准确分类应为“DAQ/控制数据链瞬态异常触发的有效安全报警”，不是“EPB4 机械或电气本体已证实损坏”。

2. **EPB5 停止是同电源组联锁的连带动作，不是 EPB5 自身故障。** EPB4、EPB5 属于 Dev1 / 电源组 2。EPB4 触发失效安全后，程序在 5 ms 内暂停并移除 EPB5 的定时器和 Runner，并关闭组 2 电源；EPB5 当时电流仅约 0.016 A，没有 EPB5 硬故障证据。

3. **EPB5 未能自动恢复的直接根因是恢复状态机与电源安全状态矛盾。** DAQ 在约 1.2 s 内已完成重建并通过 10 个新鲜批次、队列深度和持久化新鲜度验证；但恢复流程随后调用 `RevalidateEnabledAsync()`，强制要求组 2 电源必须为 ON。组 2 又刚被安全联锁明确关闭，因此每次都以“电源2恢复复核时输出为 OFF”失败。流程没有在复核前安全重启电源，也没有把“因本次联锁而 OFF”视为可接受的预期状态，形成稳定的自愈死循环。

4. **人工“停止 → 重新开始”可以恢复，进一步排除了持续硬件故障。** 12:28:58 重新开始后，Dev1/Dev2 启动健康检查一次通过；EPB4 和 EPB5 分别在 12:29:16、12:29:17 完成第一学习圈，之后继续成功运行。说明 DAQ、组 2 电源和两个卡钳均具备继续工作的能力。

5. **还存在三类值得修复的问题：** 自愈失败期间产生 593 次相同电源复核告警和 626 个事故快照子目录；12:24 硬报警对应的 `AlarmSnapshots` 文件夹缺失；另有 EPB5 峰值波动/控流观测无效、短时持久化延迟以及预期取消被记为 ERROR 等次要问题。

- 若“异常报警”指 **没有真实触发条件的误报**：结论为 **否**。日志和独立电源遥测都支持触发条件真实存在，安全动作合理。

### 自愈失败的代码级因果链

1. `TryCompleteDaqAutoRecoveryAsync()` 已确认队列、新鲜批次和 DAQ generation 正常。
2. 随后调用 `PowerSupplyCoordinator.RevalidateEnabledAsync(affectedChannels)`。
3. `RevalidateEnabledAsync()` 对组 2 使用 `expectedOutputAfter: true`，并在 `OutputEnabled == false` 时直接抛出异常。
4. 但同一故障链前面刚通过组级失效安全把组 2 电源关闭；事故快照也明确记录 `expectedOn=false / telemetryOn=false`。
5. 异常被捕获后只记录“恢复检查失败”，恢复上下文没有完成；终端 watchdog 再次重建 DAQ，之后重复同一电源复核。

因此，**DAQ 重建不是失败点；恢复提交前的电源状态契约错误才是失败点。**

### 修复建议

1. 在恢复状态机中区分两种进入条件：
   - 故障前电源应保持 ON、且没有执行组级切断：可以使用现有 `RevalidateEnabledAsync()`；
   - 电源已被本次失效安全联锁主动关闭：先在所有 DO 关闭、机械释放、DAQ 新鲜度通过后执行受控电源组重新启用/预检，再复核 ON；或者将 OFF 作为该阶段的正确预期，待重入流程统一启用。
2. 把“expected power state”放入恢复上下文，并在每个阶段使用同一状态契约，禁止一处记录 `expectedOn=false`，下一处无条件要求 ON。
3. 增加集成测试：`DaqSampleStale → group cutoff → DAQ rebuild succeeds → PSU initially OFF → safe re-enable/rejoin`，要求 EPB4/5 能回到公共节律槽。
4. 对相同 `correlationId + failure reason` 做日志和快照节流；重建不能改变的条件（例如电源 OFF）不应反复重建 DAQ。

## 分析范围、方法与限制

### 使用证据

- `log/run.log`：控制命令、DAQ 回调、周期、联锁、电源、重启时间线。
- `log/warning.log`、`log/error.log`、`log/ui-info.log`：用户可见报警、恢复失败、异常栈。
- `IncidentSnapshots/20260806_122401_191-Dev1-efcd5b431f554a1f97cba0e6a0af47a5`：触发、重建、验证及自维护快照。
- `PowerSupplyTelemetry/20260806_114724_5c52ad9a457b4f37b7eb8a3e1e50b85b.csv`：组 2 独立电源输出状态与电流。
- 当前源码中的 `Controller/EpbManager.cs`、`Controller/PowerSupplyCoordinator.cs`：恢复阶段调用顺序与电源复核条件。

### 判定边界

- 本报告可以确认“样本陈旧条件真实存在”“联锁动作合理”“DAQ 重建成功”“电源复核逻辑导致自愈卡死”。
- 仅凭本数据包不能确认 114.5 ms 回调陈旧的最底层外因；需要进程级 CPU/GC/线程、NI-DAQ 驱动和操作系统事件数据。
- 重新开始后的验证窗口只有约 3.5 分钟，足以证明设备可恢复工作，但不足以证明长期不会再次出现 DAQ 调度抖动。

## 建议处理优先级

1. **立即修复自愈电源状态契约**，并补组级联锁后自动重入集成测试。
2. **修复硬报警快照提前返回无记录/证据缺失**，保证报警圈可审计。
3. **对恢复失败日志与事故快照去重、节流**，避免单一事件产生数百份重复证据。
4. **增加 DAQ >100 ms 延迟的系统级诊断指标**，定位首次回调陈旧的底层原因。
5. **继续优化 EPB5 与 EPB10 的控流观测有效率和峰值一致性**，但不要把它与本次 EPB5 停止混为同一根因。

## 待验证问题

- 在组级切断后，设计期望究竟是“自动重新启用电源并让 EPB4/5 重入”，还是“保持 OFF 等待人工确认”？当前 UI 和恢复代码表现为想自动恢复，但电源策略表现为必须保持 OFF，产品行为需要统一。
- 114.5 ms DAQ 回调中断是否与同一时刻的线程调度、GC 或磁盘/快照工作有关，需要下一版增加对应运行时遥测后才能回答。
- 硬报警快照缺失是否稳定复现于“DAQ 自愈先作废当前圈”的竞态路径，需要自动化回归测试确认。

## 代码修复落地（2026-08-06）

本报告发现的问题已在当前代码分支完成修复，落地行为如下：

1. 电流硬故障（连续三采样过流、异常高电流平台、峰值超过硬阈值以及电源独立保护证据）保持首次发生即安全停机报警；其它控制故障按“作用域 + 故障码 + 尝试圈”连续确认，单圈重复回调只计一次，通用门槛最小为 3。
2. 普通故障前两次立即断电、机械释放并作废当前尝试圈，只发布警告；警告快照保存该作废圈的 CSV/BIN、连续次数、确认门槛、故障码、作用域、关联号及尝试号。有效完整圈会清除连续计数。
3. 达到确认门槛后保留正式报警历史，随后自动执行完整恢复预检和资格复核；恢复验证通过后自动清除活动报警并重入。输出关闭失败、电源保护或恢复验证失败仍保持锁存停机。
4. DAQ 安全联锁不再删除受影响通道的 Timer/Runner；恢复上下文冻结故障前运行通道。DAQ 与持久化恢复后改为执行 `PrepareAndEnableAsync()` 完整安全上电，不再用 `RevalidateEnabledAsync()` 错误要求已被联锁关闭的电源预先为 ON。
5. 报警快照在故障发生时冻结圈号。当前圈已被软件自愈作废时，从冻结圈导出证据；活动圈和冻结圈均缺失时写入明确错误，不再静默返回。
6. DAQ 事故快照按恢复关联和阶段幂等保存；相同恢复验证错误 30 秒内去重。Timer 自身停止导致的取消降级为正常控制日志；无效控流观测改为 30 秒限频诊断，不更新模型且不作为停机故障。

验证结果：`AdaptiveControlTests` Debug 全量 **216/216 通过**；Visual Studio MSBuild Release 全解决方案构建通过。原有过冲 5 圈、控流停滞 5 圈、峰值证据偏差 3 圈门槛保持不变，新增通用配置 `GenericFaultConfirmCycles="3"`。
