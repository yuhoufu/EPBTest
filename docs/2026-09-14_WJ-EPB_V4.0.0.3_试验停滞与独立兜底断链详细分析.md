# WJ-EPB V4.0.0.3：2026-09-14 早间试验停滞及独立兜底未续测分析

日期：2026-09-14。分析对象：项目 `D:\EPB_Data\10243-028`，08:02 前后发生、08:24 人工强制重启处置的事故。

## 1. 结论先行

此次不是“监督程序没启动”这么简单，而是**试验动作停滞以后，主程序内部恢复、原看门狗修复、独立兜底重启三条链路同时未能完成闭环**。

已确认的关键链条是：

1. 六个目标通道的机械动作和数据库记录在 08:02:25—40 停止推进。界面仍有通道显示运行，主程序仍发心跳，但实际已不能继续试验。
2. 主程序的液压组恢复停在 `HydraulicSelfHealingQueued`；4、5 在恢复状态，7、8、9 在槽位屏障等待，12 在 `PausePending`。这不是正常持续试验状态。
3. FallbackGuard 正确检测到了 `DatabaseStalled:4,5,7,8,9,12`，也确实发起了独立恢复请求。但它不是完全独立的执行器：重启仍依赖主程序完成停止、落盘、硬件释放和生成安全/续测回执。
4. 第二次请求于 08:04:10.348 发出。主程序独立状态最后更新在 08:04:10.680，随后停止更新；封存证据未见相应回执。08:05:40.660，兜底报告 `RequestExpired;NotRecovered`，没有执行替换进程启动。
5. 更严重的是：兜底在请求发出阶段就持久封锁了原看门狗启动权限；请求超时后仅清理自身内存中的请求和互斥租约，没有解除持久封锁，也没有完成替代接管。形成“原链路被禁止，新链路没走通”的恢复断链。
6. 原看门狗仍尝试修复。08:13:33 主程序明确拒绝其停止请求：`SameSourceIdentityConflict`；08:13:38 看门狗报修复期限超时，`StopTransactionObserved=false`。心跳和重连并未转换成有效停止事务或重启。

**最高权限不能解决上述逻辑依赖。此次没有证据表明是 Windows 权限不足阻止了 Kill/Start；从实际状态和代码看，程序根本没有满足执行 Kill/Start 的前置分支。**

必须分别看待两个问题：采集/控制异常为何发生，以及发生以后为何无法恢复。后一个问题已有直接证据与代码缺陷；前一个问题只能定位到回调中断、液压恢复及屏障等待，尚不能把 NI 驱动、USB、线程调度或具体锁死位置写成已证实的最终根因。

## 4. 为什么部分界面显示运行，但实际全部卡住

08:04:10 的主程序快照给出了比界面文字更具体的状态：

| 通道 | 实际运行契约状态 | 机械计数 | 恢复所有者 |
|---|---|---:|---|
| 4 | Recovering | 74248 | HydraulicGroupRecovery |
| 5 | Recovering | 74230 | HydraulicGroupRecovery |
| 7 | WaitingForSlotBarrier | 74241 | None |
| 8 | WaitingForSlotBarrier | 74285 | None |
| 9 | WaitingForSlotBarrier | 74228 | None |
| 12 | PausePending | 74240 | None |

聚合状态同时记录 `HydraulicSelfHealingQueued`、`Timers=6`、`Runners=6`、`SoftwareRecovery=2`；液压组1 `Gate=Busy`，但 `Operations=0`、`Leases=0`。这些计数不是6条线程都在有效运行的证据，也不能只凭 Gate=Busy 断言物理液压硬件损坏。

源码 `Controller/EpbManager.cs:10375` 在液压软件自愈排队阶段发布 Recovering，随后冻结受影响通道、提交断电并退出液压参与者。这说明报警后停止输出是程序的安全行为；真正的问题是后续工作没有完成重新加入或升级重启，状态长期停在排队/等待。

恢复工作包含硬期限及所有权等待（同文件约10105—10119），所以不能说源码完全没有超时。但 CancellationToken 只是协作式取消，不能中断未响应取消的同步锁等待或同步硬件调用；工作体启动前、同步前缀以及异常收尾都需要单独确认是否被期限覆盖。

**强证据推断：**液压组恢复与槽位屏障形成了持续无进展状态，其他通道受同步关系影响一起停下。**尚待验证：**具体哪个任务/锁/设备调用最先不返回，以及屏障参与者是否存在遗漏释放。故障时未取得线程转储，不应将“死锁”作为已证实结论。

Dev1CallbackGapCount=25、Dev2CallbackGapCount=27 是当前快照中的累计计数，不是此次中断持续25秒、27秒，也不能据此证明本次恰好1.175秒触发。需要故障前后的原始回调时间、队列和任务调度证据才能解释频发机制。

## 5. 原看门狗为何没有修复成功

### 5.1 停止请求确实被拒绝

`MTTfTest/WatchdogRuntime.CallbackPipeline.cs:450—471` 对同一入口已记录的来源再次提交不同 reason/correlation/request 身份时，设置 `_failClosed=true` 并返回 `SameSourceIdentityConflict`。后续请求还会被 `_failClosed` 分支直接拒绝。

现场客户端明确记录了这一错误；看门狗随后确认没有观察到停止事务。因此这是实证阻断，不是仅从代码猜测。

需要修复的是“不同恢复事务”和“同一事务的重复/冲突消息”的生命周期区分。不能直接删除身份校验：否则旧进程、旧批次的请求可能控制新试验。当前尾部材料未保留首次 canonical 请求，故还不能断言本次冲突一定源于哪一个旧请求；需要补齐规范身份的创建、完成和释放记录。

### 5.2 心跳重连并不代表恢复事务成功

侧车记录 `AttachedReconnectValidated`，又记录管道超时和重新连接；这说明部分线程仍能运行。`UiResponsive=true` 只是窗口响应性，`OriginalResponsive=true` 是来源快照新鲜度，均不能覆盖数据库停滞事实。

原 journal 的 `RelaunchState=Committed`、`RecoveryBlocked=false`、`RecoveryAttempt=3` 是持久恢复状态。其旧 `UnhandledSoftwareStartup`、`RelaunchAlreadyPending` 和此前 PID 3812 的退出意图身份不匹配不能直接作为本次08:02的根因。尤其不能把旧Committed当成本次已续测。

## 6. 独立FallbackGuard为何检测到却不能重启

### 6.1 只独立了检测，没有独立完成恢复执行

`FallbackGuard/IndependentRecovery.cs:45—120`：检测数据库停滞后先读主程序 `fallback-main-status.json`，要求 Armed 且更新时间不超过5秒，再发请求并等待主程序回执。

`MTTfTest/FrmEpbMainMonitor.IndependentFallback.cs:75—112`：回执依赖主程序依次完成：

1. `RevokeExecutionForExternalRecovery`；
2. `StopAllAsync`，要求本次事务的新鲜安全结果；
3. `QuiesceAndFlushForUnattendedRestartAsync`；
4. `ShutdownPersistenceAsync(10000)`；
5. `ReleaseHardwareForRestart`；
6. 注册续测检查点和Nonce，最后写出Ready回执。

只有回执有效、检查点匹配，Guard才进入 `Restart` 的 `main.Kill()` 和 `Process.Start(... --epb-recover ...)`。因此主程序控制链卡住时，独立Guard也会等不到重启许可。这不满足“主程序无法配合时仍能兜底”的目标。

### 6.2 状态发布循环也可能被准备阶段一起阻塞

桥接循环在约60行直接调用 `PrepareIndependentFallbackAsync`，并非将完整工作隔离到另一个执行进程。C# async 方法会同步执行至首次未完成的 await；`RevokeExecutionForExternalRecovery` 位于首次 await 之前，而且在25秒CancellationTokenSource创建之前。

`Controller/EpbManager.StopSafetyHardening.cs:253` 中撤销方法会获取 `_recoveryAdmissionGate`，随后逐通道提交高优先级OFF。这里没有独立硬超时。若同步部分卡住，调用方的每秒状态写入也会停下；25秒令牌尚未建立，无法救援这段等待。

现场第二次请求与独立状态停止更新时间只差约0.33秒，且没取得回执，与此类同步阻塞非常吻合。但仍有其他可能：心跳构造、文件写入、StopAll同步入口或后续准备任务不完成。因此本文把“桥接/准备链卡住”列为强证据推断，把具体阻塞栈列为待验证。

### 6.3 90秒超时之后没有有效升级路径

`IndependentRecovery.cs:58—64` 请求超时仅执行 Report、清空 `_request`、释放互斥、设置1分钟后重试。随后又在状态超过5秒时直接return。因此旧状态一直停在08:04:10后，第三次请求无法发起。

Attempts=2并不是“配置只允许两次”；代码上限是3。现场尚未触及3次上限，而是新鲜状态前置条件使重试失去进展条件。增加重试次数或提高Windows权限都不能解决这种等待。

### 6.4 提前封锁原恢复者，却没有保证新恢复者接管

`Watchdog.Protocol/FallbackCoordination.cs:66—79` 的 `RetireForIndependentRecovery` 写入 `IndependentRecoveryRequestId`。调用顺序位于发出请求之前，尚未取得主程序安全回执。

现场 ledger 已是 `Owner=Original, Phase=Idle`，但同时保留该独立请求ID及“Original launch authority fenced...”说明。`MTTFTest.Watchdog/WatchdogHost.Fallback.cs:41` 遇到该字段直接禁止原恢复启动；约56行连旧协议命令也会以 `IndependentFallbackOwnsReplacement` 拒绝。

请求超时分支没有与持久ledger协调清除或转移此字段。于是内存租约已释放并不等于旧启动权恢复。这是本次最明确、最需要优先修复的恢复权限交接缺陷。

不能简单超时清空字段：晚到的回执和旧执行器可能产生双启动。必须以带代际的单一恢复事务完成取消确认、旧执行器失效确认或继续由独立执行器接管，保证任何时刻只有一个有效启动者。

## 7. 人工重启后的旧绑定问题

08:27 监控状态仍显示“原快照暂不可用，保留已绑定数据库观察”，而新主程序已经使用新会话 `631f0d4946cf4041a9365b714b7eadc4`。

`Tools/Resolve-FallbackBinding.ps1:26—44` 依赖唯一当前侧车及新鲜侧车快照；解析失败时不能得到新绑定。`Tools/Watch-ActiveFallback.ps1:24—40` 只有得到明确不同的新绑定，才进入旧绑定排空；拿不到新绑定时继续保留旧观察者，并将详细解析错误覆盖为概括提示。

这解释了代码如何进入“进程还在但没有绑定新试验”的状态。现场存在两个新增Watchdog进程，但封存进程列表不含命令行，不能据此断言两者都是session-host，也不能认定解析失败必然是多侧车。唯一侧车数量、快照过期、身份不匹配均需进一步区分。

它是人工恢复后的监督连续性问题，不是08:02停机的先因。新试验动作已恢复与独立监督尚未完成重新绑定，应分别报告。

自动回归应至少覆盖：主状态停止更新；撤销函数同步卡住；StopAll不响应取消；落盘超过90秒；第一次请求超时第二次到达；晚到回执；Guard在写入封锁后崩溃；原看门狗同时接管；连续两个合法停止修复事务；重复消息；人工停止与接管并发；新进程已运行但侧车快照暂不可用；仅部分通道停滞；全部通道停滞。

验收不能只断言重启函数被调用：必须看到旧PID退出、新PID身份正确、每个目标通道恢复真实动作、机械计数增加、正式数据库跨至少三个周期推进、旧授权失效、新监督绑定正确。写盘失败/设备不可用则明确未恢复。相关控制、写盘、Watchdog及电源测试通过后再做隔离环境/jxcq演练；真实电流压力仍需台架验证。
