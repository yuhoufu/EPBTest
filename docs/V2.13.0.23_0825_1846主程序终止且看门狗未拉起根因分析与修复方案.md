# V2.13.0.23 主程序终止且看门狗未拉起——根因分析与修复方案

## 1. 结论摘要

分析日期：2026-08-26

程序版本：V2.13.0.23

试验：10358-029a

实际数据封存目录：`D:\EPB_Data\10358-029a_V2.13.0.23_0825_1846`

看门狗 Session：`2bdfa2c489964cedb2e75ce4e401a53a`

本次主程序 PID：`13564`

本次现象不是“主程序自行崩溃后看门狗没有发现”，而是下面这条故障链：

1. 18:46:01 起，两块 DAQ 先后出现约 1.1～1.2 秒的回调空窗，触发带电状态下的 100 ms 安全切断和软件自愈。
2. 电源组 2 已多次执行 OFF，但液压组恢复随后又按 Stop→Start 等价清场流程重新接通电源并进行启动定位。此时恢复聚合状态仍把电源组 2 判为 `PowerDisablePending/PowerOffUnconfirmed`，并沿用了前一轮断电开始时间。
3. 18:46:17.368，看门狗据此触发 `PowerOffUnconfirmedTimeout` 接管。主程序仍然存活、仍有心跳和运行日志，并非已经退出。
4. 主程序收到 StopAll 后，首个 `FreezeActiveWork` 阶段在 2 秒硬截止内没有完成；恢复 owner、Timer/Runner 与液压 Gate 同时存在，安全清场转为超时接管。
5. 看门狗等待 15 秒后抓取转储，并于 18:46:32.982 主动终止 PID 13564。
6. 看门狗没有重新拉起主程序，因为上一次 16:21 的恢复进程虽然在会话日志中被记录成“恢复批次已提交”，严格耐久重启许可却一直停在 `Attached`，没有进入 `Committed`。第二次接管把这个旧 `Attached` 当成“已有重启许可”，但真正消费许可时只接受 `Approved`，于是直接返回，形成“主程序被杀、看门狗仍在、没有新主程序”的最终状态。

因此：

- **直接造成“主程序消失、看门狗仍在”的主根因**：看门狗的耐久重启状态出现分裂提交，加上“先杀进程、后申请重启许可”的顺序缺陷。
- **触发本次接管的主根因**：恢复重新上电期间，`PowerDisablePending/PowerOffUnconfirmed` 的代次和阶段语义没有正确收口，导致看门狗把有意的恢复上电判成断电确认超时。
- **使 StopAll 无法正常退出的并发缺陷**：StopAll 的冻结阶段没有完全抢占正在运行的液压/Timer 自愈，2 秒内没有清完活动对象。
- **伴生缺陷**：恢复 Timer 捕获了稍后被释放的 `CancellationTokenSource`，产生 `ObjectDisposedException`；它会恶化恢复，但不是 PID 13564 被终止的直接原因。
- **DAQ 空窗是最早触发事件，不足以单独解释最终现象**。现有证据不能确认空窗来自 NI 驱动、设备链路、系统调度或应用重入；不能把它直接定性为硬件故障。

## 4. 为什么不是普通崩溃或资源耗尽

### 4.1 看门狗明确记录了主动终止

`session-...sidecar-events.jsonl` 的关键事件序列为：

```text

200  18:46:32.908  MiniDump               Captured=...

```

所以，封存证据能够确定：**PID 13564 的最终退出是看门狗执行 `Process.Kill()` 的结果**。操作员之后在任务管理器中的强杀可能针对遗留看门狗或其他仍在进程；它不是 PID 13564 消失的首个原因。

### 4.2 终止前主程序仍在工作

- Sidecar 在 18:46:17 接管时收到并确认到心跳 8550；18:46:31 重连后又收到心跳 8564。
- `run.log` 一直写到 18:46:32.087。
- 18:46:00～18:46:32，进程 CPU 大多为 1%～6%，最高短时 8.6%；Working Set 约 208～216 MiB；可用内存约 11.9 GiB；磁盘队列为 0；线程数约 57～59。
- 未见 OOM、磁盘满、句柄耗尽或未处理异常导致进程退出的证据。

### 4.3 转储结论

18:46:32 的 x86/.NET Framework 4.8 转储显示：

- UI 主线程仍在 `MtEmbTest.Program.Main` 下，没有应用层未处理异常，也没有落在业务锁或同步 I/O 堆栈上。仅凭一次转储不能证明窗口一定可交互，但可以排除“UI 线程已因某个明确业务调用永久卡死”的现成证据。
- 两个 NI 异步采集线程位于 `DaqTask.ReadAnalog2DF64 → AnalogMultiChannelReaderImpl.ReadMultiSample`。这与持续等待采集数据相符，也与此前 DAQ 空窗相关，但单次栈不能证明 NI 驱动永久挂死。
- DAQ 控制、处理、持久化、看门狗客户端、DO 高优先级 Worker 等线程仍存在。
- 两个异步 Timer/恢复状态机正处于取消/退出路径，其中可见 `WaitForDaqRecoveryAsync`、`EnsureMotorReleasedBeforeFormalRejoinAsync`、`PreReleaseBatchWithPlanAsync` 和液压协调调用链。

综合判断：主程序处于“复杂恢复和停止竞争，逻辑上无法正常收口”的状态，而不是已经崩溃或完全失去执行能力。

## 5. 根因分析

### 根因 A：恢复重新上电与“断电待确认”使用了冲突的状态语义

可信度：高；导致第二次看门狗接管。

现场事实：

1. 18:46:02.602、18:46:02.756、18:46:04.596 均记录电源组 2 已关闭。
2. 18:46:13.127 再次关闭电源组 2，随后恢复流程在 18:46:13.707 确认 `OUTP ON`，18:46:14.222 接管成功。
3. 18:46:15.461～18:46:17.175，EPB 4/5 正在执行恢复启动定位。
4. 但 18:46:17.368 的看门狗事件投影仍是 `RecoveryStage=HydraulicSelfHealingQueued`、`PowerDisablePending=True`，于是触发 `PowerOffUnconfirmedTimeout`。

当前聚合逻辑在 `Controller/EpbManager.BatchStart.cs:1163-1182` 中，只要恢复上下文未到 `CutoffCompleted`，且某电源组满足以下任一条件，就把它放入 `powerGroups`：

- 旧的 `PowerDisableTasksByGroup` 任务还没有完成；
- `ExpectedOutputEnabled` 为真；
- `TelemetryOutputEnabled` 为真。

随后 `Controller/EpbManager.BatchStart.cs:1301-1310` 直接把 `powerGroups.Length > 0` 同时投影为：

```text
PowerDisablePending = true
PowerOffUnconfirmed = true
```

这对“正在执行断电”成立，但对“已完成断电、现在按恢复流程有意重新上电”不成立。恢复上电后，`ExpectedOutputEnabled/TelemetryOutputEnabled` 正常为真，却仍被解释成“OFF 没确认”；同时 `PowerDisableSinceUtcTicks` 来自原恢复上下文的旧断电开始时间，没有形成新的阶段/代次边界。看门狗因此在恢复正进行到启动定位时发起了错误的超时接管。

封存日志没有记录 `taskPending`、`ExpectedOutputEnabled`、`TelemetryOutputEnabled` 三项的逐项值，因此不能断言究竟是哪一项单独保持了 pending；但“有意重新上电”和“断电待确认”被同时表达为同一布尔状态，已经由日志、事件投影和代码共同证实。

### 根因 B：上一次恢复的“会话提交”与“严格重启许可提交”发生分裂

可信度：高；直接导致第二次接管后无法重新拉起。

上一次恢复的现场状态如下：

```text
16:21:15  RecoveryProcessLaunched PID=13564 Permit=1
16:23:57  RecoveryBatchCommitted Generation=167824
```

marker 内容为：

```text
167824|2026-08-25T08:23:57.4596698Z|RunId=e3beda1612e74a48801a9b2021eeba38;RunEpoch=3;Channels=[4,5,11,12]
```

但事发后的严格 relaunch 文件仍是：

```text
State=4                         # Attached
Generation=1
ProcessId=13564
RunId=2a423ecc6ee8417093750477ef9868d9   # 仍是旧 RunId
RunEpoch=1
RecoveryCommitGeneration=0
LaunchConsumed=True
LastFailureDisposition=RelaunchAlreadyPending
```

`State=4` 在 `Watchdog.Protocol/DurableRelaunchPermit.cs:15-25` 中明确对应 `Attached`，而不是 `Committed`。

代码缺陷位于 `MTTFTest.Watchdog/WatchdogHost.cs`：

- 心跳路径 `684-695`：调用 `TryCommitRecoveryBatch(...)` 后不检查返回值，紧接着无条件调用 `ObserveRecoveryBatchCommit(...)`。
- 管道消息路径 `759-774`：同样忽略 `TryCommitRecoveryBatch(...)` 的 `bool` 结果，再无条件执行会话层提交。
- marker 轮询路径 `1009-1018`：甚至没有先提交严格 authority，直接调用 `ObserveRecoveryBatchCommit(...)`。
- `TryCommitRecoveryBatch` 自身在 `2111-2145` 会因为状态不是 `Attached`、authority Busy、提交失败或 blocked 返回 `false`。

于是产生了两个互相矛盾的事实：

- 会话日志、marker、`LastRecoveryBatchCommitGeneration` 认为恢复已经成功；
- 真正控制下次进程拉起的严格 authority 仍认为 PID 13564 只是 `Attached`，尚未提交。

由于失败返回没有被上层处理，而且除 Busy 分支外缺少足够的失败审计，现有封存不能继续判定当时严格提交失败的最底层原因是文件提交、上下文不一致还是竞态；但“失败仍被观察成成功”是确定的代码错误。

### 根因 C：看门狗先终止旧进程，后申请新的可消费许可

可信度：高；与根因 B 共同形成最终故障。

`MTTFTest.Watchdog/WatchdogHost.cs:1467-1546` 的自动接管顺序是：

1. 等待主程序自行退出，最长 15 秒；
2. 抓取 DMP；
3. `process.Kill()`；
4. 之后才调用 `ApproveRelaunchPermit(reason)`；
5. 再进入 `RelaunchLoopAsync`。

第二次接管时严格 authority 仍是旧 `Attached`。`Watchdog.Protocol/DurableRelaunchAuthorityV4.cs:467-475` 把 `Approved/LaunchIntent/Started/Attached` 全部视为“已有 pending”，返回 `RelaunchAlreadyPending` 和旧 Generation 1。

`ApproveRelaunchPermit` 在 `WatchdogHost.cs:1896-1904` 接受 `RelaunchPermitAlreadyPending` 并返回 Generation 1；但 `TryConsumeRelaunchPermit` 在 `1907-1916` 又严格要求状态必须是 `Approved`。实际状态是 `Attached`，因此消费失败并直接退出，没有启动新进程。

这解释了最终现象的每一部分：

```text
旧主程序被看门狗 Kill
        ↓
看门狗进程仍在
        ↓
旧 Attached 被误当成已有 permit
        ↓
消费时又因不是 Approved 而拒绝
        ↓
没有 RecoveryProcessLaunched
```

### 根因 D：StopAll 没有抢占正在进行的恢复，FreezeActiveWork 超时

可信度：中高；导致主程序没有在看门狗 15 秒宽限期内正常退出。

StopAll 从 18:46:17.401 开始，首阶段截止时间约为 18:46:19.401。最终心跳为：

```text

StopTerminalReason=StageDeadlineExceeded:FreezeActiveWork
StopTakeoverRequired=True
StopTimedOut=True
StopPhysicalSafe=False
TimerCount=8
RunnerCount=8
CyclePauseCtsCount=2
SoftwareRecoveryCount=2
RecoveryOwnerCount=1
EnergizedChannelCount=0
```

同时：

- 18:46:19.412 报告液压组 2 `Gate=Busy Pending=[12]`，逻辑清场失败。
- 通道 4/5 的恢复启动定位刚刚在运行；通道 11/12 又进入 Timer 自愈。
- `FreezeStopRuntimeObjects` 在 `Controller/EpbManager.StopSafetyOperations.cs:306-360` 同步暂停所有 Timer，再取消 CTS、移除 Timer/Runner 和液压参与者。
- 该阶段硬截止仅 2 秒，见 `Controller/EpbManager.StopSafetyHardening.cs:47-52`、`238-259`。

这说明 StopAll 与多套恢复 owner 同时操作相同运行对象，且 StopAll 没有先建立一个能拒绝所有晚到恢复/重新上电动作的代次栅栏。物理电源最终在 18:46:19.497～18:46:19.513 全部关闭，但逻辑对象没有在首阶段及时收口。

### 伴生缺陷：恢复 Timer 使用了已释放的 CancellationTokenSource

可信度：高；不是进程被杀的直接原因。

`error.log:34-35` 的异常对应 `Controller/EpbManager.PauseResume.cs:1857-1868`：

```csharp
var stopCts = RenewStopCts(channel);
...
timer.StartAsync(... async (...) =>
{
    ...
    using var linked = CancellationTokenSource.CreateLinkedTokenSource(
        timerToken,
        stopCts.Token,
        cyclePauseCts.Token);
```

异步回调捕获的是可被其他清场路径释放的 `stopCts` 对象；回调晚到时再访问 `stopCts.Token`，就会抛出 `ObjectDisposedException`。这与 StopAll/恢复同时发生的现场顺序一致。

## 6. DAQ 空窗的判断边界

可以确认：

- Dev1/Dev2 确实发生过约 1.1～1.2 秒回调空窗；不是日志误报。
- 带电时触发 100 ms 安全 OFF 是正确的失效安全方向，不能简单放宽阈值来掩盖问题。
- 空窗后 DAQ 回调恢复，队列没有积压，采集和持久化计数继续增长。
- 同时段进程 CPU、内存和磁盘正常，Windows System/Application 日志没有对应错误。
- 转储时两个 NI 异步读取线程位于 `ReadAnalog2DF64/ReadMultiSample`。

仍不能确认：

- 是否为 NI-DAQmx 驱动/USB 或总线瞬态；
- 是否为设备时钟、Windows 调度/GC 暂停；
- 是否为应用在恢复期间对 DAQ Task 的并发重配或 Read 重新挂载产生空窗。

因此应把 DAQ 空窗列为“首发触发事件、待进一步定位”，而不是本次“看门狗留存、主程序消失”的直接根因。

## 7. 修复方案

### P0-1：把恢复批次提交改成一个不可分裂的耐久事务

目标：任何地方只有在严格 authority 已经从 `Attached` 成功转为 `Committed` 后，才能发布/记录 `RecoveryBatchCommitted`。

建议修改：

1. 管道消息和心跳路径必须检查 `TryCommitRecoveryBatch` 返回值。
2. 返回 `false` 时：
   - 不调用 `ObserveRecoveryBatchCommit`；
   - 不推进 `LastRecoveryBatchCommitGeneration`；
   - 不关闭恢复转场 UI；
   - 保留待提交 generation，并进行有界重试；
   - 记录结构化失败：authority state、generation、RunId、progress token、transition status、reason。
3. marker 轮询必须走同一严格提交入口，不能只凭 marker 直接观察为成功。
4. `ObserveRecoveryBatchCommit` 增加最终防线：只有严格快照满足 `State=Committed` 且 `RecoveryCommitGeneration >= incomingGeneration` 才允许执行。
5. 对现场已经存在的 `marker=167824 + authority=Attached` 增加启动时 reconcile：若 marker、PID/启动时间、RunId/RunEpoch 和能力身份均可证明同一恢复批次，则补交 `Committed`；不能证明时进入明确的 `Blocked`/人工处理，不能静默当作成功。

### P0-2：改变自动接管顺序，禁止“无可消费许可先 Kill”

目标：凡是期望自动重启的接管，在终止旧进程前必须已经拥有一个新鲜、耐久、可消费的 `Approved` 许可。

建议顺序：

```text
建立接管事务与代次
→ 独立安全断能/确认物理安全
→ reconcile 上一代 authority
→ 耐久生成新的 Approved permit
→ 校验 permit 与当前 Session/旧 PID/新 Generation 完整绑定
→ 抓取 DMP
→ Kill 旧进程
→ 原子消费 Approved → LaunchIntent → Started → Attached
```

若无法取得新鲜 `Approved`：

- 不得把旧 `Attached` 返回给消费者当作可启动许可；
- 如果物理安全已确认，保留当前进程于安全空闲态并明确报警；
- 如果物理安全未确认，优先执行独立断能并进入 fail-closed/人工处置；
- 必须记录一个终态事件，例如 `TakeoverAbortedNoConsumablePermit`，不能以无事件的 `return` 结束。

同时把 `RelaunchAlreadyPending` 细分：

- `Approved`：可以继续消费；
- `LaunchIntent/Started`：先按进程身份 reconcile；
- `Attached`：代表已有进程，不是下一次启动许可；必须先提交、失败关闭或阻断，绝不能直接返回其 generation 给新的 relaunch loop。

### P0-3：修正恢复上电阶段的电源状态模型

不要再用“电源输出为 ON”直接推导“断电未确认”。建议为每个电源组引入带 generation 的显式阶段：

```text
DisableRequested
→ Disabling
→ OffConfirmed
→ ReEnergizeAuthorized
→ ReEnergizing
→ OnStable
```

规则：

1. `PowerDisablePending` 只在当前 generation 的 `DisableRequested/Disabling` 为真。
2. `PowerOffUnconfirmed` 只表示当前断电命令在其独立截止时间内没有得到 OFF 权威确认。
3. 进入 `ReEnergizeAuthorized` 前，必须完成/关闭旧 `PowerDisableTasksByGroup`，并结束旧 `PowerDisableSinceUtcTicks`。
4. 恢复流程有意上电时，`ExpectedOutputEnabled/TelemetryOutputEnabled=true` 应证明“重上电进行中/已稳定”，不能反向复用为“旧断电未完成”。
5. 每次心跳记录每组的 `Intent`、`Generation`、`TaskPending`、`ExpectedOutputEnabled`、`TelemetryOutputEnabled`、`DisableSince`，以后可以直接判断是哪一个条件未收口。

### P0-4：StopAll 必须以最高优先级抢占所有恢复和重新上电

建议：

1. StopAll 的第一步只做无等待动作：递增 stop generation、撤销所有 energization permit、安装“禁止晚到上电”的原子栅栏，并向 DO/电源高优先级通道提交 OFF。
2. 任何液压恢复、Timer 自愈、启动定位和 formal rejoin 在执行 DO ON/电源 ON 前，都必须校验相同 stop generation；发现已被 StopAll 抢占就立即退出。
3. `FreezeActiveWork` 不应同步等待可能被恢复线程持有的锁、Timer Pause 完成或 owner 释放。清理放到可观测的后续阶段，物理 OFF 不得被逻辑清场阻塞。
4. StopAll 开始后，禁止创建新的 Timer/Runner/CTS/恢复 owner；晚到回调只能执行幂等 OFF 和退出。
5. 将 `Gate=Busy Pending=[12]`、TimerCount、RunnerCount、RecoveryOwnerCount 的具体 owner 身份写入结构化事件。

### P0-5：修复 CTS 所有权和释放时序

最低限度先在创建异步回调前捕获 token，而不是在回调内访问可能已释放的 CTS：

```csharp
var stopCts = RenewStopCts(channel);
var stopToken = stopCts.Token;
```

回调只捕获 `stopToken`。更完整的修复是：

- CTS 与 Timer generation 绑定；
- 先取消，再等待该 generation 的回调退出；
- 最后 Dispose；
- 旧 generation 的回调不得释放或复用新 generation 的 CTS；
- `RenewStopCts`、`CancelStopCts`、`Release...` 统一通过一个 owner/lease API 管理。

仅捕获 token 可以消除现场的 `get_Token()` 异常，但不能替代完整的生命周期修复。

### P1：继续定位 DAQ 空窗，但保留 100 ms 带电安全切断

建议增加：

- 每次 BeginRead/EndRead/Rearm 的单调时钟、DAQ Task generation、线程 ID 和 NI 状态码。
- 大于 50/100/500 ms 空窗时，采集 GC pause、线程池饥饿、系统时钟跳变、设备/总线状态和 NI Task 状态。
- 区分“硬件没有返回样本”“回调已到但控制线程未处理”“应用主动重建 Task”。
- 在 DAQ 已恢复且所有物理输出确认 OFF 后，允许本地恢复继续，但必须从新的 recovery generation 开始，不能复用旧断电计时。
- 对两个设备同时约 1.2 秒空窗建立联合诊断，重点检查共同的线程调度、Task 重配和主机侧事件。

### P1：补齐发布治理

截图标题含 `[非受控包:PackageManifestMissing]`。本次二进制哈希能够通过耐久记录与仓库构建产物匹配，所以它不是本次终止的直接原因；但正式发布仍应包含 package manifest、版本、Git commit、EXE/PDB 哈希和配置快照，避免下一次无法确定现场代码。

## 8. 必须新增的测试

### 8.1 耐久提交测试

建议放在 `Tests/AdaptiveControlTests/DurableRelaunchCoordinatorTests.cs` 和 `WatchdogHostIntegrationTests.cs`：

1. `TryCommitRecoveryBatch` 返回 Busy/Invalid/Blocked 时，断言不会产生会话层 `RecoveryBatchCommitted`，不会推进 commit generation。
2. 首次失败、稍后重试成功时，只产生一次 `Committed`，authority 和 session generation 一致。
3. 只有 recovery marker、authority 仍为 `Attached` 时，不能直接清除失败预算或关闭转场。
4. 模拟现场状态：第一次恢复 PID attached → 批次提交 → 第二次故障；断言第二次必须产生 Generation 2 的 `Approved`，并且恰好拉起一次。

### 8.2 Kill 前许可测试

1. authority 为旧 `Attached` 时，自动接管不得先 Kill。
2. `ApproveRelaunchPermit` 返回旧 Attached generation 时，必须 reconcile/阻断，不能进入消费者。
3. Kill 发生前，断言严格快照已经是当前接管 generation 的 `Approved`。
4. 任何早退路径都必须有终态审计事件。

### 8.3 电源恢复状态测试

复现下面的完整顺序：

```text
DAQ stale
→ Power disable requested
→ OFF confirmed
→ 液压 Stop→Start 恢复
→ 电源重新 ON 并稳定
→ 启动定位
```

断言：

- 重新上电期间不发布旧 generation 的 `PowerOffUnconfirmed`；
- 旧 `PowerDisableSince` 不会跨阶段延续；
- 真正的新断电请求仍可在自己的 deadline 后触发接管。

### 8.4 StopAll 与恢复并发测试

- 在启动定位 Forward/Reverse、液压 Gate Busy、Timer self-heal 各关键点注入 StopAll。
- StopAll 后不得再出现任何 DO ON/电源 ON。
- Freeze 阶段必须在 2 秒内返回；清理未完成时也必须已经发出并完成物理 OFF。
- 最终 Timer/Runner/CTS/recovery owner 数量为 0，或者明确进入“物理安全、需进程重启”的可审计终态。

### 8.5 CTS 竞态测试

循环执行“rejoin → Timer 回调排队 → StopAll/Cancel/Dispose → 晚到回调”，断言：

- 无 `ObjectDisposedException`；
- 旧 generation 不会影响新 generation；
- 所有回调最终退出，无后台未观察异常。

## 9. 现场验收标准

修复版本至少满足：

1. 注入 120 ms、600 ms、1.2 秒 DAQ 空窗时，带电通道仍在 100 ms 策略下执行 OFF。
2. 物理 OFF 已确认且 DAQ 恢复时，恢复可重新上电，不被旧 `PowerDisableSince` 误杀。
3. 若确需进程级接管：只发生一次旧进程终止，只拉起一个新 PID，且新进程在限定时间内进入 `Attached → Committed`。
4. 不允许出现“看门狗在、主程序不在、relaunch state=Attached、没有终态告警”的状态。
5. 连续执行至少两次进程级恢复，第二次必须使用新 generation，不能复用第一次的 permit。
6. StopAll 后所有上电动作被 generation fence 拒绝；物理输出与电源组均有 OFF 权威回执。
7. SQLite `PRAGMA quick_check` 为 `ok`，未完成圈统一记录为软件恢复作废，不增加机械完成数。

## 11. 修复版本发布前的临时处置

在 P0 修复完成前，不建议让 V2.13.0.23 在无人值守条件下继续长时间运行。若再次出现“只剩看门狗”：

1. 先从设备和电源面板确认所有电机 DO、电源输出和液压压力处于安全状态。
2. 完整复制数据目录、`WatchdogSessions`、DMP 和日志，不要手工编辑 `.relaunch.json` 或 recovery marker。
3. 在确认物理安全后，结束遗留看门狗并从完整程序入口建立一个全新 Session；不要只单独启动主 EXE 去复用旧 Session。
4. 记录主程序 PID、看门狗 PID、现场时间和电源状态。

不要通过放宽 DAQ 100 ms 安全阈值、删除耐久状态文件或禁用看门狗来规避本问题。

## 12. 最终根因分级

| 级别 | 项目 | 结论 |
|---|---|---|
| 直接根因 | 上一轮恢复批次提交未原子落到严格 authority | 确定，严格状态最终仍为 `Attached`。 |
| 直接根因 | 自动接管先 Kill、后申请 permit；旧 Attached 被返回后又无法消费 | 确定，完整解释未重新拉起。 |
| 接管触发根因 | 恢复重新上电仍投影为 `PowerDisablePending/PowerOffUnconfirmed` | 确定存在语义冲突；具体是 pending task、expected 或 telemetry 哪一项未收口，封存未逐项记录。 |
| 正常退出失败原因 | StopAll 与多套恢复并发，FreezeActiveWork 超过 2 秒 | 确定超时；具体阻塞点需增加分步骤耗时日志。 |
| 伴生缺陷 | 回调访问已释放的 `stopCts.Token` | 确定。 |
| 首发触发事件 | DAQ 回调空窗约 1.1～1.2 秒 | 确定发生；底层来源未定。 |
| 已排除 | CPU/内存/磁盘资源耗尽、主程序先自行崩溃 | 当前证据不支持。 |
