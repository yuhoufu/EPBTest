# V3.0.0.0 通用自恢复内核实施与验证

- 文档日期：2026-09-03
- 实施分支：`codex/feat-v3-recovery-kernel`
- 基线提交：`84a1b94`
- 产品、程序集、文件版本：`3.0.0.0`
- Recovery Protocol：schema 7
- Package Slot：schema 6
- 架构代际：`EPB-RecoveryKernel-V3`
- 当前判定：**开发集成候选；禁止作为现场正式无人值守包安装**

## 1. 本轮结论

本轮不是继续给某个错误码增加分支，而是建立了 V3 恢复控制面：硬件运行体迁入独立 `MTTFTest.EngineHost.exe`，WinForms 变为客户端，LocalSystem Supervisor 内的 `RecoveryKernelService` 成为唯一进程级恢复所有者，SafetyAgent 独立形成物理安全证明。

系统约束变为：

> 任意模块只能提交事实；Recovery Kernel 必须先耐久提交 Incident、唯一 Owner 和 RecoveryIntent，才可断能、重建、换进程或切换 LKG。系统最终只能收敛到 `Running`、`RunningDegraded`、`SafeIdleAlarmed` 或 `StoppedByOperator`。

本轮已经接通以下端到端软件路径：

1. 操作员 Start 先进入 Supervisor 的期望状态门；
2. Kernel 先提交 Owner/Intent，再要求断能；
3. SafetyAgent 独立执行并证明数字量、模拟量、电源和压力安全；
4. EngineHost 执行无源预检、两圈资格复核和正式 Resume；
5. 检查点在上电前写入，跨 EngineHost 替换保留正式完成圈、剩余圈、隔离域和代次；
6. EngineHost 消失时跳过无意义的进程内重建，按两次 Current、一次兼容 LKG 的有界阶梯替换；
7. UI 异常退出只重启 UI，不再连带结束硬件运行体。

但“版本号已升级”和“软件路径已接通”不等于现场放行。旧 `Controller` 内部仍保留部分私有恢复决策源码，资源重建目前采用全硬件组合根安全重建而不是严格最小域重建，完整配置/标定/维护 UI 尚未全部客户端化，而且本机无法完成真实 NI、CAN、电源、液压和 168 小时验证。因此本轮不生成正式发布包，不宣称无人值守闭环已经通过。

## 2. V2.15 I0026 无法启动复盘

### 2.1 证据范围

封存目录：

`D:\EPB_Data\Backups\10243-028_V2.15.0.0_I0026_0903_1739`

主要证据来自 `log`、`Recovery`、`LearningCycles` 和 `WatchdogSessions`。现场截图显示：软件完成自学习并准备启动 4、5、7、8、9、12 号卡钳，随后全部进入“启动受阻”；重新开始又提示物理安全/软件逻辑不变量未通过。

### 2.2 已确认故障链

1. 17:38:42 起，EPB4、5、7、8、9、12 的启动定位首先出现 `DaqSampleStale`。
2. 后续尝试转为：

   `StartupPositioningException / ChannelExecutionPermitMissing / State=StartBlocked`

3. 进程内清场后活动 Timer、Runner、输出参与者和恢复对象均为 0，但仍残留 `RegistryLeases=1`。这个易失租约同时被当作恢复授权和阻断条件，导致重新开始无法形成闭环。
4. 电源组 4 的 `SOUR:CURR?` 在 1500 ms 内无响应，冷启动基线无法证明电源已 OFF；安全策略正确地阻止重新上电。
5. SafetyAgent 最终完成了物理安全阶段，Watchdog 也确实启动了新 PID；故障并非“进程完全未拉起”。
6. 替换进程把首个正式圈之前的启动工作解释为没有可恢复工作，产生 `RecoveryCheckpointRejectedNoWork`。
7. NoWork 证据提交又因语义不一致失败，两次同指纹后进入 `SafeIdleRecoveryBlocked`。

### 2.3 根因

| 层次 | V2.15 架构缺陷 | 现场后果 |
|---|---|---|
| 启动事务身份 | 正式首圈前没有稳定、跨进程的 Run/Incident 身份 | 替换进程把真实失败判断成 `NoWork` |
| 恢复授权 | `RegistryLeases` 既表示活动事实，又参与恢复准入 | 工作对象清零后，残留租约仍能永久阻断 |
| 安全证明 | 单次电源查询超时无法区分瞬时通信慢和确实未断能 | 正确禁止上电，但缺少后续有界重试与升级 |
| 决策所有权 | 启动定位、同进程恢复、Watchdog 和检查点各自决定终态 | 前一层已安全收口，后一层仍按另一套语义开熔断 |

DAQ 陈旧和电源查询超时是触发条件；使其演变成“永久无法启动”的根因是：**预正式工作身份、恢复 Owner、资源租约和跨进程检查点语义没有统一。**

## 3. V3 防止 I0026 再现的实现

| I0026 失败点 | V3 实现 | 失败时行为 |
|---|---|---|
| 预正式工作被判 `NoWork` | Supervisor 在第一次上电前创建 `SessionId + RunId + RunEpoch`；Start 本身就是耐久 RecoveryIntent | 替换进程继续同一未完成 Run，不以正式圈是否为零判断有无工作 |
| 活动圈跨进程重复计数 | 检查点保存活动圈作废状态；上次状态为 Running/QualifiedFormalStarted 时，预检前先作废中断圈 | 中断圈正式计数增量为零 |
| `RegistryLeases=1` 成为恢复授权 | 旧进程 lease、permit、nonce 和 Owner 一律不迁移；V3 只接受 Journal 中的 Incident/Owner/generation/revision | 新进程不会被旧内存租约永久阻断 |
| 单次 PSU 查询超时 | SafetyAgent 对 OFF 和回读执行有界的两轮重试，每次查询仍有 3000 ms 上限 | 瞬时慢响应可恢复；仍无法证明 OFF 时保持断能并进入 `SafeIdleAlarmed` |
| 多套恢复逻辑争权 | EngineHost 只发布 FaultObservation；Supervisor Kernel 决定作用域和阶梯 | 不允许第二 Owner，不允许模块自行换进程或切包 |
| EngineHost 已退出却仍尝试局部重建 | Supervisor 结合 pulse 超时和精确 PID/StartTicks 形成 EngineHost 事实 | 直接进入 Current 进程替换，不向不存在的进程发局部命令 |
| 新进程被重复拉起 | SessionAgent capability 区分 EngineHost/UI；替换前证明旧实例不存在或精确终止旧 PID | 同一角色最多一个有效实例 |
| 恢复风暴 | 预算固定为 2 次局部、2 次 Current、1 次 LKG；仅在 2 个资格圈、5 个正式圈、连续稳定 10 分钟后重置 | 预算耗尽后断能并报警，不重启 Windows |

边界说明：以上软件语义和模拟执行器回归已经通过；真实电源组 4、DAQ 陈旧和现场六通道启动仍必须做硬件复现，不能仅凭自动化测试宣称问题已现场解决。

## 4. 已落地实现

### 4.1 分支、版本与组件

- 从 `84a1b94` 创建 `codex/feat-v3-recovery-kernel`；
- 保留并纳入 I0024 事故复盘和通用自恢复蓝图；
- `Build/UnattendedVersion.props` 统一为 `3.0.0.0`；
- 新增 AnyCPU `Recovery.Kernel`；
- 新增 x86 `MTTFTest.EngineHost`；
- 新增 `RecoveryKernelTests` 和 `EngineHostIntegrationTests`；
- 四个项目均加入 `TfTest.sln`；
- 发布身份从 8 个扩展为 10 个正式组件。

### 4.2 schema 7 与耐久 Journal

已增加 `FaultObservation`、`RecoveryIntent`、`RecoveryCommand`、`SafetyProof`、`QualificationReceipt`、`SystemDesiredState`、`ResourceHealthLease`、`EngineStateSnapshot`、`OperatorCommand` 和 `ProcessRole`。

每个恢复事务绑定：

`SessionId + RunId + RunEpoch + IncidentId + ResourceScope + Generation + Revision`

Journal 固定位于 `%ProgramData%\MTTFTest\RecoveryKernel`，由 Supervisor 单写，使用 DPAPI LocalMachine、原子替换、单调 revision 和耐久 CAS。重复命令以 idempotency key 返回同一回执；并发异域故障会扩大为 System 作用域，不会覆盖原命令或生成第二 Owner。

### 4.3 Recovery Kernel

- Start/Stop 都是先提交 Owner/Intent 的持久事务；
- 合法终态只有 `Running`、`RunningDegraded`、`SafeIdleAlarmed`、`StoppedByOperator`；
- 未知故障按资源属性和拓扑计算作用域，不依赖新增错误码；
- 每个阶段都有 deadline，丢回执会升级阶梯或安全收口；
- 恢复阶梯为两次局部重建、两次 Current EngineHost、一次同代 LKG；
- 确认硬件故障在完整断能和无源预检后最多主动资格尝试一次；
- 不完整安全证明、压力不安全、旧进程未隔离、数据边界不完整和安全链故障均禁止复跑；
- 连续稳定条件满足前不重置预算，避免间歇故障形成重启风暴。

### 4.4 EngineHost 与检查点

- EngineHost 独占 Controller、NI、CAN、电源、液压、数据写入和运行检查点；
- 启动后先全域断能，只以 `SafeIdleAlarmed` 接受 Supervisor admission；
- 发布独立 pulse、状态快照、资源 lease、latest-only 遥测和 FaultObservation；
- 遥测丢旧帧且不反压控制线程；故障队列溢出时发布 System 级 `FaultObservationOverflow`；
- `EngineRunCheckpointStore` 在 `%ProgramData%\MTTFTest\RecoveryKernel\engine-checkpoints` 保存正式计数、剩余目标、活动圈作废、配置哈希、资源 generation、隔离状态、资格/正式进度和稳定时间；
- V2 检查点只保守迁移正式完成圈和剩余目标，不迁移 permit、nonce、Owner 或中间恢复状态；
- 实现无源预检、资格圈、正式 Resume、全硬件安全重建和故障域隔离；
- 隔离域失败时持久化禁用/报警状态，健康剩余通道重新完成两圈资格后进入 `RunningDegraded`；
- Recovery receipt 跨进程保存，替换后重复命令不会重复上电；
- EngineHost 不含进程替换或包切换权，OperatorCommand 直连永久拒绝。

当前限制：`RebuildResource` 已可执行，但现阶段采用全硬件 composition root 释放并重建，安全性优先，尚未达到严格“只重建最小资源域且健康通道完全无扰”的目标。

### 4.5 独立 SafetyAgent

- Supervisor 为每个 Incident 生成不可变安全配置和安全 authority；
- `V3SafetyProofExecutor` 以隐藏窗口启动 `MTTFTest.SafetyAgent.exe`；
- EngineHost 只贡献进程/数据边界事实，SafetyAgent 独立执行 DO、AO、电源 OFF/回读、液压释压和压力证明；
- authority 终态转换成 schema 7 `SafetyProof`，证明不完整时永不继续上电；
- 大单调时间浮点值在持久 JSON 中先规范化再计算 SHA-256，避免写入后立即因数值格式变化变成 `AuthorityInvalid`；
- 电源 OFF 查询采用有限重试，解决 I0026 单次 1500 ms 超时即永久阻断的问题，同时保持 fail-closed。

### 4.6 EngineHost 替换与 LKG

- 使用精确 PID + StartTicks 证明并终止旧 EngineHost；
- 旧实例已经崩溃时，只接受经签名、已启动且同身份的 SessionAgent capability 作为前一代证据；
- Current 和 LKG 均要求 schema 6、schema 7、`EPB-RecoveryKernel-V3` 和十组件同版本身份；
- Current 最多替换两次，之后只允许一次兼容 LKG；
- 新进程使用新的 generation capability，并在 30 秒内等待 `SafeIdle` admission；
- 首次 V3 安装不能把 V2.15 作为自动回滚槽；
- 不提供软件主动重启 Windows 的路径。

### 4.7 WinForms 客户端与 Supervisor

- 活动入口改为 `V3EngineClientForm`，不构造旧 `Main_Frm`、`FrmEpbMainMonitor` 或运行中的硬件控制器；
- Start/Stop 均经 Supervisor 期望状态门提交；
- UI 读取状态、日志和 latest-only 遥测；
- Running、RunningDegraded 或有活动 Incident 时拒绝正常关闭；
- 正常安全关闭写 typed exit；无 typed exit 的消失只重启 UI；
- EngineHost 与 UI capability 分离；快捷入口语义变成“确保运行环境并显示 UI”；
- V2 `--session-host` 生产入口返回拒绝，旧会话只审计、不参与 V3 决策；
- 旧协议进程回归入口仅在仓库 `Tests/bin` 且同目录存在 `AdaptiveControlTests.exe` 时可达，正式包无法启用。

当前限制：配置 base revision + hash 提交、完整曲线/报警页、非运行态标定和全部维护命令尚未完成客户端化。

## 7. 尚未完成的 P0 项

### 7.1 删除双恢复策略

活动 V3 UI 和 Supervisor 已不运行旧 Sidecar 决策链，但旧 `Controller`、旧 UI 和旧 Watchdog 的部分私有恢复源码仍编译在程序集内。正式生产切换前必须：

- 把 V2 只读迁移器和回归适配器拆到明确的 migration/test 边界；
- 将 Timer、DAQ、电源、液压私有恢复循环降级为事实发布器或命令执行器；
- 删除进程内换进程、模块私有预算、字符串状态推断和 UI 直接全局 StopAll；
- 将源码门禁扩大到整个生产编译图，保证不存在第二 Owner。

这一项未完成前，即使活动入口没有调用旧逻辑，也不能声称“最终生产包不存在双恢复策略”。

### 7.2 最小域真实重建

当前局部恢复命令能按资源图选择作用域，但物理实现为了安全采用全 composition root 重建。需要把 DAQ、液压组、电源组和单卡钳分别做成 generation-aware 执行器，并用真实硬件证明健康独立通道没有非必要停机。

### 7.3 完整客户端 UI

还需实现配置 base revision + hash 事务、项目/通道选择、完整曲线和报警、标定及维护命令。所有配置修改必须在非运行状态提交，EngineHost 校验后原子生效。

### 7.4 安装态和现场验证

尚未执行：

- 安装态 LocalSystem 在 Intent、安全请求、安全证明、旧进程退出、capability、检查点、资格圈和首个正式圈前后的强杀矩阵；
- UI、EngineHost、Supervisor、SessionAgent、SafetyAgent 的完整 crash matrix；
- 250 ms 断能命令、30 秒独立安全证明、180 秒恢复的真实时限；
- 单/双 DAQ、共享电源、液压组、健康独立通道和 I0026 六通道启动复现；

- 24/72/168 小时长稳；
- 正式发布包递归校验和现场安装。

## 8. 放行判定

当前判定：

> **不放行。当前是开发集成候选，不是 V3 现场候选，更不是正式无人值守闭环。**

达到“现场候选”至少需要：

1. 删除生产编译图内的旧恢复决策权；
2. 完成最小资源域 generation-aware 重建；
3. 完成配置、标定和维护 UI 客户端化；
4. 通过安装态 LocalSystem 全事务强杀矩阵；
5. 在 I0026 原现场硬件上完成“DAQ 陈旧 + PSU 查询超时 + EngineHost 替换”组合回归；
6. 记录十组件文件哈希、配置哈希、Current/LKG 身份和安装回滚结果。

达到“正式无人值守闭环”还必须完成 24/72/168 小时长稳，并证明任何已知或未知故障都在有界时间内进入四种合法终态之一。物理设备损坏、操作系统失效或安全状态无法证明时，正确终态只能是断能、报警可见的 `SafeIdleAlarmed`，不能强制继续试验。
