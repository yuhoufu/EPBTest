# V3.0.0.0 后台附着超时与报警会话重开修复

## 结论与本机证据

界面报“后台未连接：Supervisor 未批准后台重新附着：操作已超时”。本机此次直接原因是后台 EngineHost 没有启动，旧的安全空闲报警会话被误认为仍由恢复内核接管。

- `C:\ProgramData\MTTFTest\DeploymentLogs\last-deployment-result.json`：2026-09-05 07:38:47 安装完成，版本 3.0.0.0，安装提交 `d87fa2a15bf199500057783dee44370b6905ef73`，保留 ProgramData。
- 进程查询有 Watchdog、SessionAgent、MTTFTest，没有 EngineHost。
- `C:\ProgramData\MTTFTest\Supervisor\supervisor-audit.log`：北京时间 07:39:12 记录 `DisplayDurableSessionWhileKernelOwnsRecovery`；随后只记录界面拉起。
- 只读解密本机 `RecoveryKernel\recovery-journal.v7.json`：Revision=14，DesiredState=`SafeIdleAlarmed`，Reason=`SafetyProofIncomplete`，ActiveIntents 为空，PendingCommand=null。SessionId=`eca8be6604ef421e88ce9bd28cceb40b`，RunId=`66072a41d843426db0a7ad405238f4ac`，RunEpoch=1。

`EngineEnvironmentSession.Resolve` 原来仅允许 `StoppedByOperator` 的旧会话重开后台。与此同时，后台缺失检测仅对 Running/RunningDegraded 创建恢复任务。因此，无恢复任务的 SafeIdleAlarmed 会话既不重开后台，也不触发恢复，界面连接持续超时。

此外发现一处独立缺陷：Supervisor 的附着审批仍从控制管道读取快照，该管道被占用时也会造成超时。这不是本机此次后台缺席的原因。

## 修改

1. 无活动恢复任务、无待执行命令、无已观测后台且取得原生进程互斥权时，允许 SafeIdleAlarmed 会话重开同一 Session/Run/Epoch 的后台。既有启动路径仍须证明无存活 EngineHost，并通过 SessionAgent 启动能力授权。
2. 保留持久化报警原因、恢复预算和资源隔离信息，不修改期望状态，不创建自动开始试验命令。存在恢复任务、待执行命令、后台实例或外部原生进程持有者时仍不允许重复拉起。
3. 附着审批复用 `ReadBoundSnapshot`，通过独立 SupervisorRead 管道读取状态，保留实际管道服务端 PID、启动时间、角色、会话和响应绑定校验。

## 安装态验收

源码修复不等于本机已安装程序更新。本次未修改 ProgramData 状态、未重启已安装服务、未启动现场试验，也未执行 NI/CAN/液压硬件验收。

部署包含本修复的完整程序包后，以保留上述报警会话的方式重新打开界面，验证日志出现 `ReopenAlarmedDurableSession`、EngineHost 启动和附着成功。连接恢复后仍应展示原安全失败；开始试验必须经过原有操作员命令及安全证明、预检、资格验证流程。不能以清空恢复日志或修改期望状态作为解决办法。
