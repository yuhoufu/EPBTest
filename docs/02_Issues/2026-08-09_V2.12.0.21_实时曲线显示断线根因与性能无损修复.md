# V2.12.0.21 实时曲线显示断线根因与性能无损修复

> 后续完成性审计发现 UI 日志仍存在每批全量重写，可造成最高约 5.9 秒停顿；V2.12.0.21 已由 [V2.12.0.22 UI 日志全量重写卡顿根因与彻底整改](./2026-08-09_V2.12.0.22_UI日志全量重写卡顿根因与彻底整改.md)取代，不应再作为最新部署候选。

## 1. 结论

V2.12.0.20 截图中压力平台和电流曲线的短暂断线是**显示层误判**，不是已证实的 DAQ 丢数、控制链中断或落盘缺失。

根因是两项原本用于防止 UI 卡死的策略叠加：

1. 采集器按频率门限只向 UI 发布部分批次，采集器和窗体又分别只保留 Dev1、Dev2 的最新待显示批次；UI 忙时中间显示批次允许被覆盖。
2. 绘图代码原先用“下一批首点与上一次实际绘出点之间的 X 间隔”判断采集断点。只要 UI 超过 300 ms 没画到中间批次，就插入 `Y=NaN` 让 ZedGraph 断笔。

因此，V2.12.0.20 把“UI 为降载主动跳过显示批次”错误画成了“DAQ 数据断点”。V2.12.0.21 改为只使用当前批次自带的 `current/last` 相邻 DAQ 批次时间判断真实采集断点。显示邮箱被覆盖时继续连接相邻可见点；只有 DAQ 时间轴本身发生异常空窗或回退才断笔。

## 3. 代码整改

### 3.1 断线依据改为 DAQ 相邻批次时间

新增 `Controller/UiCurveContinuityPolicy.cs`，规则如下：

- `currentBatchEnd - previousAcquisitionBatchEnd` 接近期望批次跨度：连续绘制；
- UI 限频、邮箱覆盖、窗体消息泵延迟：不参与断线判定；
- 相邻 DAQ 批次时间出现超过容差的空窗或回退：插入 `NaN`，明确表示真实时间轴异常；
- 首批或时间信息无效时不凭空制造断线。

`FrmEpbMainMonitor.ApplyEngBatchToCurves` 每批只计算一次判定，15 条曲线复用结果。

### 3.2 保留所有既有 UI 降载措施

本次没有恢复历史显示队列，也没有提高绘图帧率或绘图点数：

- Dev1/Dev2 最新值邮箱仍固定为两个槽；
- UI 唤醒仍为二值合并，不积累历史消息；
- UI 重绘仍为 10 FPS；
- 曲线显示仍最多 10 Hz 抽稀；
- 旧点仍按时间窗口批量裁剪；
- 2 kHz 控制、峰值判定、Raw/SQLite 落盘完全不经过本次策略。

所以修复不会把“视觉连续”换成新的 UI 追赶、内存增长或 CPU 风险。

## 5. 部署与验收

当前运行中的 V2.12.0.20 不应被在线覆盖。应先正常停止试验并确认退出耐久门禁完成，再部署 `MTTfTest/bin/Release` 中经 `Tools/Verify-Release.ps1 -RequireDeploymentApproved` 验证的 V2.12.0.21 干净候选。

现场至少连续观察 2 小时，并同时满足：

1. 曲线平台、上升沿和下降沿不再出现由 UI 忙造成的空白断段；
2. 双设备 `Discontinuities=0`、`OverCapacityDropped=0`；
3. `ControlDepth` 和 `PersistenceDepth` 可回落到 0；
4. UI `Pending=0`、`Dropped=0`、`FileDropped=0`；
5. 主程序 CPU、工作集和句柄无持续上升；
6. 人工制造真实 DAQ 空窗时，曲线仍能断笔且系统按既有安全恢复策略处理。

正式候选的 Git SHA、构建时间、EXE/config SHA 和 `deploymentApproved` 状态，以候选目录内 `build-identity.json`、`release-manifest.json` 与 `SHA256SUMS.txt` 为唯一依据。

## 6. 风险边界

V2.12.0.21 解决的是“显示层把 UI 跳帧误画成断线”。它不修改实际采集数据，也不会用插值数据参与报警、控制或落盘。两次可见点之间的连线仅用于屏幕趋势显示；需要审计某一圈的真实 2 kHz 波形时，仍以 SQLite/BIN 和报警证据导出为准。
