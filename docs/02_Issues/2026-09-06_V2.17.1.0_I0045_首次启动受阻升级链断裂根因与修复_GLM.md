## 1. 结论先行

第一次运行"启动受阻、手动重开才恢复"不是 V2.17.1.0 已修复链路失效，而是**恢复升级链的最后一步静默断裂**：同进程恢复失败后，升级请求 `RequestExternalRecovery` 在消息发送层被静默丢弃，独立看门狗从未收到接管请求，替代进程自然无人拉起。已修复为"可验证送达 + 未送达即降级自重启"，并顺带修复两个伴生缺陷。

## 2. 根因逐层分析

### 2.1 触发层：首次启动磁盘写风暴（环境性）

首次启动后 13:30:17—20 出现 ~91 MiB/s 的持续磁盘写（配合 DiskQueue 2—3），持久化写盘被压制，双设备队列在 3 秒内打满 256 批硬上限。该现象与 I0043 的"首次运行拥塞"同类（彼时是 CPU 竞争，这次是磁盘写风暴），均发生在当天/安装后第一次启动，第二次启动即不复现——属于首启环境扰动（冷缓存/杀软扫描/首次建库写放大等），不是 V2.17.1.0 的代码回归。B5 归因遥测已就位，后续同类事件可量化归因。

### 2.2 判定层：物理确认"待定"被判定为恢复失败（诊断空白的来源）

同进程恢复的 `PrepareForFreshRestartAsync` 中，StopAll 返回时压力新鲜度与持久化边界确认**仍处于等待**（StopSafetyPending：`Pressure=WaitingForActivation; Dev1=NoCommittedBatch`）——这些是"未确认"而非"确认失败"，因此四个诊断 Error 字段全空，但 `CanRestartInProcess=false` 仍判失败。逻辑侧实际已全部通过（ActiveCycles=0，V2.17.1.0 的 B3 清扫在现场真实生效）。判定为失败后升级是安全设计（看门狗做整批恢复），问题不在判定本身，而在升级链断裂与诊断空白：

- 修复：失败异常现在附加 `Flags=Physical/Motor/Power/Pressure/Persistence/Logical/RequiresRestart/TimedOut` 转储，"待定"与"真错误"可区分。

### 2.3 根因层：升级请求被静默丢弃（本次修复的核心）

- `WatchdogRuntime.RequestExternalRecovery → SendSimple` 返回 `void`：`CaptureContext()` 为 null（会话上下文已分离）或 `TrySendForSession` 失败时**直接丢弃、无日志、无返回值**。
- 现场：13:30:36.372 `RestartAsync` 已判 `IsAttached=true` 并发出请求，但 sidecar 全程未收到 `TakeoverRequested`——请求在发送层消失。
- 结果：升级链最后一步断裂。旧进程未退出、替代进程未拉起、上电授权未撤销，界面呈现"启动受阻"，用户只能手动关闭重开。
- 修复（双保险）：
  1. `SendSimple/RequestExternalRecovery` 返回 `bool`，丢弃/失败不再不可见；
  2. `RestartAsync` 附着分支与恢复监控边界分支都校验送达结果，**未送达即记录 ERROR 并降级为进程自重启序列**——即使接管通道不可用，也保证"退出后必有人接手"。

### 2.4 伴生缺陷：未开圈的幂等终止报错

人工停止清场对 EPB7 的圈 -605 调 `AbortCycle`，写盘器该通道当前圈登记为 null（该圈从未开圈或已被清空），`EnsureCurrentCycleIdentity` 按身份不符抛错。已改为：当前圈为 null 时幂等返回（无可作废终态），身份确实错配（Current 非空且不同）仍拒绝。
