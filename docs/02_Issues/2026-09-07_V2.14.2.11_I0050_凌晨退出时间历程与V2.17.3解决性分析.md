# V2.14.2.11 I0050：凌晨退出时间历程与 V2.17.3.0 解决性分析

分析日期：2026-09-07。项目：10243-028。事故：I0050。本文依据今晨封存包、当日下午现场只读核查及版本源码对照编写。所有时间表统一为北京时间（UTC+08:00）；JSON 中 `Z` 时间需加八小时，不能把 JSON 的 09-06 17:10 当成北京时间昨天下午。

## 1. 结论

**这次是 Dev1 采样回调空窗触发电流/液压样本过期，液压局部自愈启动后，看门狗以 `InconsistentRecovery` 要求全局停止并替换主进程；旧程序确实退出，但安全代理启动被身份校验持续拒绝，自动恢复没有完成。** 不是仅凭“窗口消失”推断崩溃，也没有证据把它归为用户正常退出或内存耗尽。

**V2.17.3.0 修复了本次退出后起不来的摘要大小写缺陷，并改进关闭、监督及重连链；但不能认定它已彻底解决 I0050 整条故障链，更不能承诺以后不退出。** 本次最初是约 1.17 秒 DAQ 回调空窗，而非 I0048/I0049 的持久化积压。新版仍有液压恢复登记与心跳投影之间的潜在中间态窗口，仍保留 `InconsistentRecovery` 的停止修复判断，需要补充针对本次路径的确定性验证。

截至本次约 15:04–15:12 的分次核查，现场主程序是 06:11:04 启动的另一 PID 14084，版本仍为 2.14.2.11；当前有业务日志推进。**这不能计为凌晨旧恢复许可成功续测**：旧会话仍在失败重试，新会话身份不同。新进程是谁启动的，现有证据未唯一确定。

## 4. 原因分层

### 4.1 初始触发：Dev1 回调没有及时提供新数据

电流保护记录 `Root=DaqCallbackStale`，CallbackAge、ControlEnqueueAge、ControlProcessedAge 基本相等；液压随后记录 StaleSample。01:10:17.295 双卡 PersistenceDepth=0，01:10:18.094 主进程 CPU 7.1%、系统 CPU 14.6%、可用内存约 11 GB、磁盘队列 0。这些观测不支持把本次直接归因于内存耗尽、全机 CPU 饱和或持久化高水位。

**不能由压力 70.835 bar 推断硬件一直安全，也不能把压力过期误写为实际掉压。** 系统不应依赖过期读数继续上电，断电保护有必要。样本时间戳与宿主回调年龄口径不同，不能简单用日志时间减 `ProcessedSampleUtc` 替代 CallbackAge。

约 1.17 秒的底层原因仍未唯一定位：NI 驱动/读取回调、线程调度、同步等待或其他系统延迟均需事故时段线程栈、ETW/驱动与逐阶段时延证据。间隔形态相似不足以证明某个固定超时。此次没有取得匹配时刻的 dump；Windows Application 的 00:30–06:20 Level=Error 查询未返回记录，也不能据此证明没有任何系统异常。

### 4.2 放大：局部恢复被恢复状态不一致判据升级为全局停止

日志直接证实 `InconsistentRecovery` 是看门狗的请求原因，接着同一事务 `4242528738cc489f9c5ed0d96fcddb7d` 进入 StopAll。源码判据为：非人工暂停，`RecoveryActive=false`，但 `DaqRecoveryCount`、`SoftwareRecoveryCount` 或 `RecoveryOwnerCount` 任一大于零。

进一步源码复核发现一个**有依据但尚未完成确定性复现的竞态解释**：

1. `BeginHydraulicSoftwareRecovery` 先 `_hydraulicSoftwareRecoveryGroups.TryAdd`，再冻结、断电、撤销参与者，之后才 `TryBeginRecoveryIncident` 发布恢复身份与通道状态。
2. 逻辑快照把 `_hydraulicSoftwareRecoveryGroups.Count` 计入 `SoftwareRecoveryCount`。
3. 心跳生产端 `ShouldPublishRecoveryActive` 不允许“只有软件恢复计数，没有恢复身份/状态/owner”宣称恢复中；因此上述中间态可能为计数大于零而 RecoveryActive=false。
4. 看门狗会对此请求停止修复。S169 中 RecoveryIncident、RecoveryContext、RecoveryStage 均为空，与这一解释相符。

本次 S169 未保留触发心跳全部计数与聚合快照，故不能断言已锁定到某条指令或具体字段读取时刻。已确认的是**恢复遥测矛盾触发了全局停止**；“登记中间态被快照采到”是高相关实现线索。不能把仅约百毫秒的局部恢复过程描述成恢复长时间卡死。

### 4.3 无法拉起：同一个 SHA-256 被当作两个不同字符串

I0050 安全交接里的 SafetyAgent 摘要为：

```text
9bd0a6a872072f1b74ecf003bc9e1beb543e48431e161ad4f6d340d3e37a3b0a
```

下午实际读取现场 SafetyAgent EXE，摘要与之相同。旧版 `SupervisorSafetyAgentLaunchClient` 通过 `SupervisorProtocol.ComputeSha256` 产生大写文本，旧版 Supervisor 却用 `StringComparison.Ordinal` 与交接里的小写文本比较。**同一摘要仅大小写不同，就足以进入本次 `SupervisorSafetyHandoffIdentityMismatch` 拒绝分支。** 这是明确的软件缺陷，不需要假设 EXE 损坏。

旧版错误分支还合并了 Schema、HandoffId、nonce、许可与路径等检查；现场完整请求未导出，故不能宣称绝无其他不匹配项。但即使其他项都正确，这个摘要比较也必然失败。旧标签 Supervisor schema=5，封存 receipt schema=5，不能用新版 schema=7 反推旧现场本来就是 schema 错误。

I0050 交接为 Accepted / SafetyAgentLaunchIntent、WorkerProcessId=0、IsSafetyCompleted=false、AttemptCount=600。恢复许可 Approved、CircuitOpen=false、LaunchConsumed=false、ProcessId=0、最大主程序拉起数 8。由此可排除“已经耗尽八次主程序重启”和“没有保留恢复意图”作为本次长期起不来的解释。

### 4.4 退出并非凭空崩溃，后续收尾也存在重复监督

退出意图明确为 TakeoverReplacementExit，保留已批准许可，最终记录未请求强杀。23.881 的 CanClose=True 与退出记录 LogicalQuiescent=false、Leases=3，以及 29.053 再次监督逻辑静默的现象，表明不同收尾层仍有状态差异。之后重新采样确认低压、再次保存边界，最终旧程序退出；本次并非永远卡在关闭。

无需以“禁用看门狗”“放宽所有阈值”处理。这样的改动会掩盖采样过期与真实孤儿恢复，应修正恢复发布的一致性，并保留真正失联时的有界升级。
