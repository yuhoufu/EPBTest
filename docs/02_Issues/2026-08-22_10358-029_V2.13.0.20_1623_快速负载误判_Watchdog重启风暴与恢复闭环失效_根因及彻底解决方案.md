## 1. 结论先行

V2.13.0.20 仍未解决稳定运行问题，当前包不能放行生产长稳试验。

本次不是一个孤立故障，而是四个缺陷串联成的故障链：

1. **V2.13.0.20 新增的“无本圈空载基线时快速进入 LoadRise”逻辑，把正常电机启动涌流尾部误认为机械负载上升。**
2. 该分支表面只报“软预警”，实际同时把自适应状态机改成 `LoadRise`；随后正常涌流回落满足既有 `AbnormalLoadRiseDrop` 条件，形成硬故障、连续圈计数和永久报警。
3. 正式圈发生可恢复硬故障后，EPB5 被留在 `Paused`，但没有有效恢复 owner；Watchdog 在 5 秒后按安全设计接管、杀进程并拉起恢复进程。
4. 第二次恢复时又发生 DAQ 压力/电流样本陈旧，恢复生命周期失去 owner/task 覆盖；随后 StopAll 的液压释放阶段耗时 10.441 秒，而 Watchdog 以“阶段 5 秒无进展”为条件继续请求接管。恢复子进程的 Sidecar 进程句柄管理还有确定性缺陷，最终形成 49 次约 250 ms 间隔的重连风暴。

因此，当前现象不能通过“放宽 Watchdog”“把报警隐藏掉”或“把电流阈值调大”解决。必须同时修复：

- 快速负载判定的证据语义；
- 可恢复暂停/恢复 owner 的原子生命周期；
- DAQ 陈旧时的有界安全恢复与 StopAll 阶段进展协议；
- Watchdog Sidecar 的唯一实例和重连进程句柄；
- 相同故障指纹的恢复预算与熔断。

## 4. “本圈尚未取得空载电流基线”报警详解

现场提示：

> 警告：检测到负载快速上升，但本圈尚未取得空载电流基线：当前电流=1.398A；这是软预警，不会单独触发卡钳永久停机。

### 4.1 这条报警为什么每圈都会出现

当前自适应正向流程每圈都会：

1. `ResetDirection` 把 `_observedForwardEmptyA` 清零；
2. 忽略至少前 100 ms 的启动涌流；
3. 本圈空载窗口又要求至少 100 ms 的稳定覆盖；
4. 恰好在 100 ms 忽略期结束的第一批代表样本上，电流仍处于涌流尾部，已经高于历史空载基线加 0.5 A；
5. 新逻辑没有继续等待涌流衰减和本圈稳定谷值，而是只凭“超过历史阈值 + 正斜率”立即进入 `LoadRise`。

对本场三个通道的统计如下：

| 通道 | 报警次数 | 当前电流最小/平均/最大 | 历史阈值 |
|---|---:|---:|---:|
| EPB4 | 33 | 1.398 / 1.670 / 2.223 A | 1.048 A |
| EPB5 | 34 | 1.628 / 2.020 / 2.465 A | 1.131 A |
| EPB10 | 31 | 1.587 / 2.080 / 2.547 A | 1.176 A |

98 次报警几乎覆盖了所有启动尝试，不是偶发机械故障。报警中“尚未取得本圈空载基线”是算法窗口设计的必然结果，而不是卡钳本身突然失去空载段。

### 4.2 V2.13.0.15 是否有同样报警

没有。

在 V15 的 `run*.log`、`warning.log`、`error.log` 和 `ui-info.log` 中：

- `RapidLoadRiseWithoutObservedEmpty`：0；
- 中文快速负载提示：0；
- `AbnormalLoadRiseDrop`：0。

当前工作区的快速分支位于 `Controller/Adaptive/EpbAdaptiveControl.cs` 633～648 行。`git log -S` 和 `git blame` 显示它由提交 `0770d7a`（2026-08-21 23:17）引入，晚于 V15 的封存运行。V20 运行包没有发布清单，无法从包内审计 Git commit；但现场日志中的唯一字符串、阈值和后续状态行为与该分支完全一致，代码对应关系可信度高。

### 4.3 这条报警是否合理

结论分两层：

- **监测意图合理**：如果机械负载真的在未取得空载基线前快速建立，程序需要快速断电保护。
- **当前实现和文案不合理**：单个 10 ms 代表样本和历史阈值不足以证明机械负载建立；更严重的是，代码在报软预警的同时执行 `SetStage(LoadRise)`。

之后既有逻辑只要看到：

```text
LoadRise 阶段
&& 峰值 - 当前值 >= 2.0 A
&& 当前值 < 正向目标
&& 持续 >= 100 ms
```

就产生 `AbnormalLoadRiseDrop` 硬故障。正常启动涌流本来就是先冲高再回落，因此新分支把正常波形送进了一个必然容易满足的硬故障条件。

所以“这是软预警，不会单独触发永久停机”只在字面上成立，现场语义具有误导性：

```text
快速软预警
  -> 修改状态为 LoadRise
  -> 正常涌流回落
  -> AbnormalLoadRiseDrop 硬故障
  -> 连续三圈 Streak=3/3
  -> 永久报警/暂停/Watchdog 接管
```

它已经不是无副作用的软预警。

## 6. Watchdog 为什么会多次恢复

### 6.1 前两次接管：Watchdog 判断本身正确，错误在上游状态

两次事件完全同构：

```text
正常涌流误判为 AbnormalLoadRiseDrop
  -> 本圈断电
  -> Timer 进入 Paused
  -> 恢复路由发现 State=Paused，但 Owner=None / Target=None
  -> 代码选择“交给生命周期 owner”后直接返回
  -> 实际没有 owner 接手
  -> 5 秒后 Watchdog 发现 ChannelPausedWithoutManualOwner
  -> StopAll、转储、终止、拉起恢复进程
```

Watchdog 不应该对一个无人负责的暂停无限等待，因此这两次接管不是简单的“Watchdog 太敏感”。应该修复的是：任何可恢复暂停在对外可见前，必须先原子登记有效 owner 和活跃任务；或者不进入 `Paused`。

### 6.2 第三次接管：DAQ 陈旧和恢复 owner 生命周期再次断裂

PID 11296 恢复后的冷启动安全预检已经通过，说明 14:17 场次发现的启动残余负载问题在这里不是直接失败点。

真正的新事故是 Dev1 DAQ 回调出现约 1.164 秒空窗：

- 安全新鲜度门槛：100 ms；
- 压力值：69.378 bar，本身高于 60 bar 最低要求；
- 样本年龄：1118.1 ms，因此不能作为当前安全证据；
- EPB4/5 断电电流样本年龄：1118.2 / 1134.5 ms；
- 程序按失效安全关闭电源组 2，这个断电动作是合理的。

不合理的是后续恢复状态：EPB4/5 被发布为 `Recovering / PowerSupplySelfHealingQueued`，约 1 秒后监督器却看到 `Owner=`、`TaskCovered=False`，于是将两通道转为 `StartBlocked`。这说明运行包中的恢复 owner 字段、任务注册或清理顺序至少有一项不是原子闭环。

由于 V20 包缺少 manifest，不能从现场二进制准确反推具体源提交；整改时必须以运行契约验证，而不能只看某一行代码“看起来已经传了 owner”。

### 6.3 StopAll 的 5 秒监督与 10.441 秒物理阶段冲突

第三次接管的 StopAll 最终结果是安全成功：

- MotorDO、Power、Pressure、RawStorage、Persistence、DataContinuity、Logical 全部 `Confirmed`；
- 最终 `Timer=0, Runner=0, Energized=0, RecoveryOwners=0`；
- 但 `ReleaseHydraulics` 阶段耗时 10.441 秒。

Watchdog 从阶段 5 秒无进展起，每约 250 ms 记录一次 `StopStageNoProgress5s`，共 20 次。当前 `WatchdogHost.cs` 的统一 5 秒阈值短于真实可接受的释压/DAQ 恢复阶段时长，且阶段内部没有把“DAQ 重启、收到新压力样本、DO/AO 已确认关闭”等子进展发布给 Watchdog。

不能简单把所有 Watchdog 超时改为 15 秒。正确方式是区分：

- 立即安全动作：DO OFF、AO=0、PSU OFF，应有短硬期限；
- 物理证明动作：压力降到阈值、DAQ 恢复和落盘闭合，可有更长但有上限的阶段期限；
- 每个有效子进展必须递增 `StopProgressVersion`，只有“无进展且超过本阶段硬期限”才允许终止主进程。

## 7. 49 次 Sidecar 重连风暴的确定性代码原因

该风暴不是 49 次主程序恢复，而是 Watchdog 客户端错误跟踪 Sidecar 进程造成的传输重连循环。

当前逻辑组合如下：

1. 恢复子进程通过 `AttachRecoverySessionAsync` 连接原会话，不持有原 Sidecar 的 `Process` 句柄；
2. 16:19:36 第一次管道写超时后进入重连；
3. 重连代码看到没有存活的 `_watchdogProcess`，于是启动一个新的 `MTTFTest.Watchdog.exe`，并把新进程句柄保存为 `_watchdogProcess`；
4. Sidecar 使用 `Local\MTTFTest.Watchdog.<SessionId>` 互斥量。原 Sidecar 仍存活并持有互斥量，新启动的重复 Sidecar 立即 `return 0`；
5. 客户端随后仍能连接原 Sidecar 的命名管道，Heartbeat Ack 也继续增长；
6. 250 ms 后 TransportMonitor 看到“被跟踪的新重复进程已经退出”，即使 Ack 只有约 250 ms 也再次判 `WatchdogProcessExited`；
7. 再启动一个重复 Sidecar，循环往复。

现场日志与该代码路径完全一致：

- 第一次：`HeartbeatSendFailed`；
- 此后：`WatchdogProcessExited; AckAgeMs≈247～259`；
- 49 次 `SidecarRelaunched`；
- 49 次成功连接原 Session；
- 49 次 `WatchdogReconnected`。

因此必须改为“先连接、握手获得权威 Sidecar PID，再决定是否启动”，不能把一个因单例互斥量正常退出的重复进程当成会话权威进程。

## 8. 根因分层

### P0-A：已证实的首要回归

V20 新增快速分支仅凭历史基线、单批代表电流和正斜率，把正常启动涌流尾部升级为 `LoadRise`。该状态变化激活 `AbnormalLoadRiseDrop` 硬故障规则。

### P0-B：已证实的生命周期缺口

可恢复故障能够发布 `Paused` 或 `Recovering`，但没有持续有效的 owner/task 覆盖。Watchdog 只能把它识别为孤儿状态并接管。

### P0-C：已证实的恢复监督协议冲突

DAQ 样本陈旧触发安全断电本身正确，但恢复和 StopAll 没有与真实物理阶段匹配的结构化进展及阶段硬期限，导致安全收口尚在推进时被判“无进展”。

### P0-D：已证实的 Sidecar 进程身份缺陷

恢复子进程不掌握权威 Sidecar PID；重连后跟踪的是因单例互斥量立即退出的重复进程，于是形成 250 ms 重连风暴。

### P1：发布包不可审计

现场 V20 包：

- `ExecutablePath=D:\debug\2.13.0.20_1\MTTFTest.exe`；
- `ExeSha256=bb2bc8d6c892d1553e20b6686281c02a92ab6a466473086486e22aaf844a169a`；
- `PackageVerified=False`；
- `PackageManifestMissing`；
- `GitCommit/BuildUtc=unknown`。

它不直接制造电流误判，但使“现场运行的到底是哪一份源码”无法完整审计，必须纳入发布门禁。

## 9. 彻底解决方案

### P0-1：取消“历史基线直接进入 LoadRise”的有副作用捷径

修改范围：`Controller/Adaptive/EpbAdaptiveControl.cs`、`Controller/EpbCycleRunner.Adaptive.cs` 及对应测试。

要求：

1. `RapidLoadRiseWithoutObservedEmpty` 不得调用 `SetStage(LoadRise)`；
2. 历史基线只能用于诊断阈值和超时兜底，不能冒充本圈机械负载证据；
3. 只有满足以下任一证据链才允许进入 `LoadRise`：
   - 本圈已经形成满足覆盖时长、离散度和样本数要求的空载基线，之后持续上升；
   - 2 kHz 全速证据证明“启动涌流峰 → 明确谷值/稳定空行程 → 持续二次上升”，并且二次上升持续时间、斜率和幅值都达标；
4. `AbnormalLoadRiseDrop` 只能在 `LoadRiseEvidenceQualified=true` 后启用，禁止对“历史基线快速候选”启用；
5. 正常波形若尚无本圈基线，应继续处于 `EmptyTravel/AcquireBaseline`，直到形成谷值/基线或达到有界进展期限；
6. 15 A 目标、绝对过流、最长通电时间等真正安全保护继续保留，不得因本修复放宽。

不建议只把 0.5 A 提高到 1 A 或 2 A。现场原始启动涌流可达约 10 A，固定调大阈值仍会随电机、温度和继电器时序反复失效。

### P0-2：把快速提示真正降为无副作用诊断

1. 诊断事件不得修改自适应 Stage、生命周期、连续硬故障计数或通道暂停状态；
2. 对正常重复事件按 `RunId + Channel + Reason` 限频：首次记录详细波形，之后仅累加计数，禁止每圈刷 UI；
3. 文案改为可验证语义，例如：

   > 诊断：本圈空载基线尚未形成，当前样本高于历史空载范围；状态机仍在采集本圈证据，本事件不改变控制阶段、不计入故障连续次数。

4. 如果后续取得合格机械负载证据，再发布独立的 `LoadRiseQualified`；如果到进展期限仍无法取得证据，则按“负载未建立/电流证据不完整”分类，而不是复用涌流回落故障。

### P0-3：恢复 owner 与生命周期状态必须原子提交

修改范围：`Controller/EpbManager.cs`、`Controller/EpbManager.TimerRuntimeHealth.cs`、`Controller/EpbManager.RecoveryCoordination.cs`。

建立唯一事务：

```text
创建 RecoveryIncident
  -> 在 Registry 登记 active task/owner/RunEpoch/TargetPhase/HardDeadline
  -> owner 登记持久可见
  -> 才允许发布 Paused 或 Recovering
  -> 执行 OFF、释放、数据截止和恢复
  -> 成功时原子恢复 Running；失败时原子进入 SafeIdle/AlarmStopped
  -> 最后撤销 owner
```

硬性不变量：

- 对外可见的 `Paused` 必须是人工 owner 或结构化恢复 owner；
- `Recovering` 必须有 `OwnerKind + OwnerId + OwnerGeneration + TargetPhase + active task`；
- owner/task 不得在状态退出 `Recovering` 之前清理；
- 恢复任务创建失败时，不得留下 `Paused/Recovering`，而应保持输出关闭并直接进入单一安全终态；
- Watchdog 心跳从同一原子快照读取状态与 owner，禁止跨字典拼接出瞬时矛盾。

Watchdog 的孤儿暂停门禁应保留。可给原子发布提供不超过一个心跳周期的 revision grace，但不能用简单延长到几十秒掩盖 owner 缺失。

### P0-4：DAQ 陈旧恢复必须有单一 owner 和阶段化进展

1. DAQ 新鲜度超过 100 ms 时立即禁止继续用陈旧电流/压力做安全判定，当前断电策略保留；
2. `DaqLivenessSupervisor` 成为该事故的唯一根 owner，电源自愈、液压自愈和通道恢复作为子阶段，不再各自创建竞争 owner；
3. 每个阶段发布 `RecoveryProgressVersion`：发现陈旧、DO OFF、PSU OFF 确认、DAQ restart 开始、首个新鲜批次、压力重新确认、数据边界闭合、通道重入；
4. 新鲜样本在有界时间内恢复，则从同一 owner 完成一次安全定位/资格验证并回到原阶段；
5. 超过硬期限仍无新鲜样本，只执行一次 SafeIdle，禁止继续主进程重启；
6. 日志同时记录原压力值和样本年龄，明确区分“压力不足”和“压力证据陈旧”。

### P0-5：StopAll 使用阶段专属期限，不再统一 5 秒

建议协议至少区分：

| 阶段 | 安全目标 | 监督原则 |
|---|---|---|
| MotorOff / PowerOff | 立即去能量 | 短期限，失败可立即外部接管 |
| AO/PressureDO Off | 立即撤销压力命令 | 短期限，写入/回读必须有结果 |
| ReleaseHydraulics | 等待压力证明或 DAQ 恢复 | 允许大于 5 秒，但必须有子进展和明确硬期限 |
| ClosePersistenceBoundary | 闭合 Raw/SQLite/最近圈 | 按队列深度和序列进展监督 |
| VerifyLogicalQuiescence | Timer/Runner/owner 全清 | 短期限、无残留 |

具体秒数应根据台架实测 P99/P99.9 加安全裕量确定，不能拍脑袋。根据本场 10.441 秒的有效完成样本，`ReleaseHydraulics` 的硬期限至少必须覆盖真实最大物理时长；推荐先在故障注入中验证 15 秒候选值。

### P0-6：修复 Sidecar 唯一实例和权威 PID 握手

修改范围：`MTTfTest/WatchdogRuntime.cs`、`MTTFTest.Watchdog/WatchdogHost.cs`、`Watchdog.Protocol`。

推荐协议：

1. 恢复子进程先连接既有 Pipe；
2. AttachAck 必须返回权威 `SidecarPid + SidecarProcessStartTicks + SessionId`；
3. 客户端用该 PID 打开只读进程句柄并作为 liveness 事实；
4. 只有 Pipe 不存在、权威 PID 不存活且会话未撤权时才允许启动新 Sidecar；
5. 新 Sidecar 因单例互斥量退出 0 时，不得覆盖权威句柄；
6. TransportMonitor 在 Ack 新鲜时不得仅因非权威辅助进程退出而重连；
7. 同一时刻只允许一个 reconnect worker，采用指数退避和次数上限；
8. 重连成功后必须停止旧 monitor，不能反复把 `_transportMonitorStarted` 重置为 0 产生并行监督。

### P0-7：相同故障指纹只允许一次有意义恢复

当前最终 `CheckpointDisarmed` 已经能打开熔断，这一点应保留并前移：

- 故障指纹至少包含 `RootCode + Device/ChannelGroup + RunId + RecoveryStage`；
- 同一指纹只有在硬件状态或恢复阶段发生真实变化时才消耗下一次恢复；
- 连续相同指纹达到预算后进入 `SafeIdleRecoveryBlocked`，保持全部输出关闭；
- 不得重复完整定位和 10 圈学习来证明同一个确定性错误；
- 恢复成功后才清零该指纹预算；
- UI 必须明确显示“已安全阻断，等待人工确认”，而不是继续显示正在自动恢复。

### P1：发布包身份必须成为现场准入门禁

候选包必须带：

- Git commit、dirty 状态和构建 UTC；
- 主程序、Sidecar、Controller、配置的 SHA-256；
- 文件集合清单；
- `deploymentApproved` 和自动/台架测试记录；
- 启动时 `PackageVerified=True`。

从 `D:\debug` 直接复制、缺少 manifest 的包只能用于开发验证，不能继续作为生产候选。

## 10. 禁止采用的“假修复”

- 不得只把快速报警文本隐藏或降日志级别；状态迁移仍会触发硬故障。
- 不得只提高历史负载阈值；10 A 涌流会使阈值调参失去稳定边界。
- 不得删除 `AbnormalLoadRiseDrop`；真实机械负载突然丢失仍需要保护，应修正它的前置证据资格。
- 不得关闭 Watchdog 或简单把孤儿暂停超时调大；V15 的 Watchdog 心跳实际不完整，复制其“看起来稳定”会失去外部安全保护。
- 不得只把 StopAll 的统一 5 秒改成统一 15 秒；立即断电和物理释压需要不同期限。
- 不得在每次恢复时再启动一个 Sidecar；必须复用同一 Session 的权威进程。
- 不得以自动化单元测试全绿代替原始 2 kHz 波形回放和真实台架长稳。

## 11. 必须新增的回归和现场验收门禁

### 11.1 波形级自动回归

1. 回放 V20 `EPB10_Cycle_-002094.csv`：不得进入合格 `LoadRise`，不得产生 `AbnormalLoadRiseDrop`；
2. 回放 V15 `EPB10_Cycle_084529.csv`：应通过启动涌流、等待真实负载建立并正常完成；

4. 构造无空载段但 2 kHz 波形存在明确“涌流谷值后第二次上升”的快速卡钳：允许快速夹紧，但必须有完整证据；
5. 正常波形连续回放 10000 圈：快速诊断不得改变 Stage、生命周期或故障 Streak。

### 11.2 生命周期/恢复并发回归

- 在 EPB5 正式圈注入一次可恢复异常，任何心跳都不得出现 `Paused/Recovering + Owner=None`；
- owner/task 建立失败时只允许一个 SafeIdle 终态；
- 恢复 task 结束和 owner 清理必须晚于状态退出 Recovering；
- 预正式、学习、资格和正式阶段分别验证恢复目标，不得跨阶段进入正式节拍；
- 同一故障多线程同时上报时只产生一个 RecoveryIncident。

### 11.3 DAQ/StopAll 故障注入

- 注入 Dev1 1.2 秒回调空窗：立即断电，但新鲜样本恢复后能由同一 owner 收口，不触发外部接管；
- 注入 DAQ 永久失联：一次安全停机并熔断，不循环拉起；
- 注入 12 秒液压释压但 DO/AO/PSU 均已确认 OFF：Watchdog 识别阶段进展，不得在第 5 秒杀进程；
- 注入真正 DO/PSU OFF 无确认：仍必须在短期限内外部接管。

### 11.4 Sidecar/Watchdog 回归

- 恢复子进程连接现存 Sidecar：`SidecarRelaunched=0`；
- 真正杀死 Sidecar：最多拉起 1 个新权威 Sidecar；
- 启动重复 Sidecar且互斥量拒绝：不得覆盖权威 PID；
- Ack 新鲜但辅助进程退出：不得 TransportLost；
- 同一 Session 10 分钟压力测试：只允许一个 transport monitor 和一个 reconnect worker；
- 相同恢复失败指纹达到预算：只进入一次 SafeIdle，不再拉起主程序。

### 11.5 真实台架放行标准

建议按以下顺序，任一失败均不得替换 V15：

1. 受控 Release 包，`PackageVerified=True`；
2. 10358-029 的 4、5、10 号卡钳完整完成启动、定位、学习、资格和正式运行；
3. 不少于 1000 圈初步长稳：
   - 正常波形 `RapidLoadRiseWithoutObservedEmpty` 状态迁移为 0；
   - `AbnormalLoadRiseDrop` 误报为 0；
   - `Owner=None` 孤儿暂停/恢复为 0；
   - 主进程 Watchdog 恢复为 0；
   - Sidecar 重连风暴为 0；
4. 完成上述全部故障注入；
5. 不少于 24 小时或 5000 圈（取更严格者）无人值守长稳：
   - 主进程 PID 不变；
   - Heartbeat/Ack 持续增长；
   - DAQ、压力、电源、落盘无未闭合事故；
   - Stop/Start 可重复且没有资源残留；
6. 保存日志、原始波形、Watchdog Session、转储、包 manifest 和 SHA-256，形成放行证据包。

## 14. 最终判定

1. **当前 V2.13.0.20 未解决问题，不可放行。**
2. 频发快速报警的主要对象是正常启动涌流尾部，V15 没有该分支和该报警。
3. 该报警的安全意图合理，但当前实现会改状态并间接触发硬故障，属于严重设计错误；文案也具有误导性。
4. 前两次 Watchdog 接管由错误硬故障和孤儿暂停触发；第三次由 DAQ 陈旧恢复、owner/task 缺口及 StopAll 监督冲突触发。
5. 49 次重连是独立的 Sidecar 权威进程句柄缺陷，必须单独修复。
6. 临时继续使用 V15 可以维持主试验，但必须认识到其 Watchdog 监控证据并不完整；最终版本应保留外部安全能力，同时修复上述四项 P0 根因。
