# V2.11.0.15 EPB 状态污染、系统自恢复卡死与“启动受阻但仍运行”根因及彻底整改方案

## 1. 文档结论

**数据来源**：`\\wj-epb\EPB_Data\10358-029_V2.11.0.15_0808_1103`<br>
**软件版本**：V2.11.0.15<br>
**分析日期**：2026-08-08<br>
**现场对象**：10358-029

本次不是四个互不相关的显示问题，而是两条确定的故障链叠加：

1. **安全控制线程被同步日志写盘拖住**：EPB5 的 NI 数字量全关实际仅耗时 `1.058 ms` 且最终成功，但安全调用方在 `100 ms` 内没有收到返回，将一次“迟到的成功”判成“断电失败”，继而扩大成 EPB4/5/6 电源组联锁。随后 Dev1 控制链持续积压并出现 NI `-200279`，自恢复又依赖已经失新的 Dev1 压力证据，形成无法闭合的循环。
2. **同一卡钳存在两个生命周期拥有者**：新批次仍在学习时，EPB8 的报警自动恢复任务绕过批次阶段，单独创建正式运行 Timer；批次启动流程随后又将 EPB8/9/10/11 判为隔离并发布“启动受阻”。于是 EPB8 的 UI 终态是“启动受阻”，但另一个拥有者留下的 Timer 仍在继续发 DO 命令和计圈。

四个现场现象的直接解释如下：

| 现场现象 | 直接原因 | 性质 |
| --- | --- | --- |
| EPB4、EPB5 已不运行，却显示“系统自恢复” | EPB5 全关调用被误判超时，触发 4/5/6 电源组联锁；Dev1 DAQ 又失去新鲜压力证据，自恢复卡在清场阶段 | 控制链阻塞 + 循环恢复依赖 |
| EPB6 本应“未启动”，却显示“系统自恢复” | 电源组故障影响集按物理组扩展到 4/5/6，运行状态发布没有过滤 `Enabled=false` 的 EPB6 | 状态污染 |
| 重启后 EPB8/9/10/11 显示“启动受阻” | EPB8 在学习期间被自动恢复任务提前拉入正式 Slot，导致液压屏障等待 9/10/11 超时；学习任务被隔离，批量启动只提交了 4/5 | 生命周期竞态 |
| EPB8 显示“启动受阻”但实际仍运行 | 批量结果写入 `StartBlocked` 时没有原子撤销 EPB8 的独立 Timer、Runner 和输出许可；UI 显示的是最后一次终态事件，不代表执行资源真实状态 | 双拥有者 + 状态/资源不一致 |

**结论强度**：以上结论同时得到截图、现场日志、最终配置、DO 分段计时和 V2.11.0.15 代码路径支持，不是根据单一 UI 现象推测。

## 3. 代码级根因

### 3.1 根因 A：DO 安全工作线程把日志写盘计入 100 ms 硬件超时

相关代码：

- `IO.NI/DoController.cs`
  - `HighPriorityOffTimeoutMs = 100`
  - 高优先级工作线程执行 `SetEpbOffCore`
  - `SetEpbOffCore` 在 `_doTaskLock` 内完成 NI 写入后，继续调用 `LogInfo("EPB...全关")`，之后才返回
- `MTTfTest/FormLoggerAdapter.cs`
  - `Info` 同步调用 `ProjectLogHub.Write`
  - `Warn/Error` 同步写入后还调用 `ProjectLogHub.Flush(true)`
- `Config/ProjectLogStore.cs`
  - 所有日志共用 `_gate`
  - `StreamWriter.AutoFlush=true`
  - 每条普通 Info 都可能同步落盘；警告和错误还会执行持久化刷新

DO 计时器在 NI 写入后记录了 `niWriteCompletedTicks`。现场数据证明锁等待为 `0 ms`、NI 写入为 `1.058 ms`，而 Worker 为 `169.245 ms`。写入后的有效代码只剩状态赋值、日志和返回；状态赋值不足以解释约 168 ms，实际阻塞点位于同步日志链路。

更严重的是，终端判定发生在 DAQ 控制消费链中。该链同步等待高优先级 OFF 最多 100 ms，因而日志写盘抖动会反向阻塞 AI 数据消费；这与后续控制链延迟、70 秒积压和 NI `-200279` 完全一致。

这不是把超时从 100 ms 调大就能解决的问题。调到 200 ms 只会把“假失败”阈值推后，同时允许控制线程被磁盘 I/O 阻塞更久。

### 3.2 根因 B：把“调用方超时”错误地等同于“硬件断电失败”

现场命令已经给出互相矛盾但语义清晰的结果：

- `CallerTimedOut=True`
- `FinalResult=True`
- `NIWrite=1.058ms`

当前流程只消费了第一个事实，把它升级为 `TerminalOffCommandFailed`；没有用命令 ID 接收迟到完成，也没有以程控电源输出状态、新鲜电流或 DO 回读进行最终裁决。

正确模型必须至少区分：

1. `HardwareWriteFailed`：NI 写入抛异常或最终返回 false；
2. `CallerTimedOutPending`：调用方未及时得到结果，硬件结果暂未知；
3. `LateHardwareSuccess`：超时后收到同一 CommandId 的成功完成；
4. `PhysicalOffVerified`：由新鲜电流/电源输出/回读确认实际断电；
5. `PhysicalOffUnverified`：没有证据，继续保持电源组失效安全，但不能伪造为硬件写失败。

### 3.3 根因 C：禁用通道仍被组级运行状态污染

物理安全动作和业务运行状态被混为一谈：

- 出于安全目的，电源组故障时对物理成员 4/5/6 全部发 OFF 是合理的；
- 但将同一 `AffectedChannels=[4,5,6]` 直接发布成运行状态，导致 `Enabled=false` 的 EPB6 也进入 Recovering；
- UI 将 Recovering 映射并持久化，最终 EPB6 变成 Paused，而不是 NotStarted/NotEnabled。

必须拆分两个集合：

- `PhysicalSafetyTargets`：可以包含组内全部物理通道，只用于去能量化；
- `RuntimeAffectedChannels`：故障发生瞬间的已启用、已参与本 RunEpoch 的通道快照，只允许它们改变运行状态。

### 3.4 根因 D：自恢复依赖发生故障的同一个 Dev1，形成闭环死锁

Dev1 采集不再提供新鲜压力后，恢复流程仍要求“先由 Dev1 新鲜压力证明液压已释放，再完成 Dev1/液压代次重建”。这在逻辑上无法完成：

```text
要重建 Dev1 → 先要求 Dev1 的新鲜压力证明释放
要得到新鲜压力 → 必须先重建 Dev1
```

因此“系统自恢复”长期不退出并不意味着系统在有效地恢复，它只是反复等待不可能由当前故障源提供的证据。

### 3.5 根因 E：批量启动与报警自恢复都能创建正式 Timer

V2.11.0.15 的关键竞态为：

```text
批量启动拥有 EPB8：Starting → Learning
            │
            ├─ EPB8 报警
            │
报警恢复又拥有 EPB8：Qualification → RejoinFormal → 创建 Timer
            │
            └─ 原批量学习继续结算：EPB8/9/10/11 → StartBlocked
```

`BeginRecoverableChannelRestartLoop` 可在批次学习阶段直接调用 `ResumeAlarmStoppedChannelAsync`；后者完成两圈资格复核后调用 `RejoinFormalChannelsAtSharedFutureSlot(new[]{8})`。它没有检查：

- 当前批次是否仍处于 Positioning/Learning；
- 当前恢复任务是否拥有本 RunEpoch；
- EPB8 是否允许先于同液压组其他参与者进入 Formal；
- 批次协调器是否已经提交正式阶段。

所以 Formal 屏障等待 9/10/11 是必然超时，不是偶发时序抖动。

### 3.6 根因 F：状态终态与执行资源没有原子不变量

`ChannelRuntimeStateStore` 会锁存 `AlarmStopped / InterlockStopped / SystemFault / StartBlocked`，UI 则按最后一次状态事件显示颜色和文字。但 Timer、Runner、液压参与权和 DO 发命令许可是另一套独立资源。

当前没有强制以下不变量：

```text
StartBlocked / AlarmStopped / ManualStopped / Disabled
    ⇒ 无 Timer
    ⇒ 无有效 Runner owner
    ⇒ 无液压屏障参与租约
    ⇒ 无可发出的电机加电命令
    ⇒ 已完成 OFF 或进入可审计的 OffUnverified 失效安全态
```

因此批量流程能写入 StartBlocked，旧恢复流程创建的 Timer 却不受影响，直接产生“红色启动受阻但 RUN”。

## 4. 为什么现有 V2.11.0.16 仍不能宣称彻底解决

V2.11.0.16 已经增加了若干有价值的修正，包括恢复阶段门、参与者版本、恢复租约精确移除、部分原子重入、人工停止覆盖旧 StartBlocked，以及峰值证据同窗比较。它也在部分组级状态发布路径中过滤了禁用通道。

但针对本次现场链路，仍存在发布阻断缺口：

1. `DoController → FormLoggerAdapter → ProjectLogStore` 的同步日志路径没有消除，1 ms 硬件动作仍可能被日志拖成 100 ms 调用超时；
2. `BeginRecoverableChannelRestartLoop` 仍可在活动批次的学习阶段调用独立的 `ResumeAlarmStoppedChannelAsync`；
3. 单通道恢复仍可通过 `RejoinFormalChannelsAtSharedFutureSlot(new[]{channel})` 创建正式 Timer；
4. `StartBlocked` 写入与 Timer/Runner/输出许可撤销仍不是一个原子事务；
5. UI/持久化层仍没有全局强制 `Enabled=false ⇒ NotEnabled/NotStarted`；
6. 现有 `--incident-10358-029` 的 9/9 测试没有注入本次三个核心组合场景。

所以 V2.11.0.16 可以定义为“部分缓解版本”，不能作为这次问题的最终闭环版本。

## 5. 彻底整改方案

### P0-1：把日志和所有观察者彻底移出实时/安全控制路径

#### 必须修改

1. `SetEpbOffCore` 只允许做：准备 DO 状态、NI 写入、更新内存状态、释放 `_doTaskLock`、返回硬件结果；不得在锁内或返回前写日志、刷新文件、调用 UI/事件观察者。
2. DO Worker 的完成时间定义为“NI 写入和内存状态提交完成”，不能包含日志时间。
3. `ProjectLogStore` 改为有界、单写者异步队列：
   - 普通日志批量写入，建议 100～250 ms 或 4～64 KB 刷盘；
   - 告警审计日志可进入高优先级队列，但 durable flush 只能由后台写线程完成；
   - 队列满时先合并/丢弃重复 Info，保留计数摘要，不得反压控制线程；
   - Writer 卡顿时保留内存环形缓冲并产生独立健康指标。
4. DAQ callback、FastControlSample 消费、DO/AO Worker、持有硬件锁的代码统一禁止同步文件 I/O、同步 UI、同步网络 I/O。

#### 结果语义

高优先级 OFF 返回结构化结果，而不是单一 bool：

```text
CommandId, IssuedUtc, HardwareCompletedUtc,
CallerTimedOut, FinalHardwareResult, LateCompletion,
PhysicalOffVerification, VerificationAgeMs
```

调用方超时后仍立即执行电源组失效安全是正确的，但收到同 CommandId 的迟到成功后必须进行物理证据对账，不能永久保留伪造的 `TerminalOffCommandFailed`。

### P0-2：建立“单通道单拥有者”的显式生命周期状态机

每个通道改为串行 Actor/命令队列，最少携带：

- `RunEpoch`
- `BatchId`
- `LifecyclePhase`：Disabled、Starting、Positioning、Learning、Qualification、Formal、Recovering、Paused、Stopping、Terminal
- `OwnerTransactionId`
- `TimerGeneration`
- `EnergyPermitGeneration`

所有异步任务在创建时捕获 Epoch/Owner；在创建 Timer、发布状态、发加电 DO、计圈前都必须二次校验。旧 Epoch 的回调只能清理自身资源，不能改变新运行。

#### 阶段规则

1. 新 Start 先递增 RunEpoch，取消并等待旧恢复任务、旧 Timer、旧 Runner 完成清退，再进入 Starting。
2. 报警发生在 Positioning/Learning/Qualification 时，只能回到**同一个批次协调器**：作废本逻辑圈、安全 OFF、释放、重做该逻辑圈；禁止调用独立正式恢复入口。
3. 只有批次协调器完成所有学习结算并原子提交 Formal 后，报警恢复才允许重新加入正式节律。
4. 正式期单通道恢复也必须使用同液压组当前参与者集合和未来完整 Slot，不能让一个通道越过组阶段。
5. Stop/Pause/StartBlocked/Disabled 都会撤销 EnergyPermit；无有效 Permit 的任何 Forward/Reverse 命令必须被硬拒绝并记录不变量违规。

### P0-3：终态提交与执行资源撤销必须是同一事务

提供唯一入口，例如：

```text
TransitionToNonRunningState(channel, targetState, epoch, reason)
```

其事务顺序为：

1. 校验 Epoch/Owner；
2. 撤销加电许可；
3. 取消并等待 Timer/Runner；
4. 退出液压参与租约和屏障；
5. 发 OFF 并获得硬件结果或进入 `OffUnverified`；
6. 原子提交 RuntimeState 和资源快照；
7. 异步发布 UI/日志。

如果 Timer 仍活动，禁止直接提交 `StartBlocked`。可以选择“先停止资源再提交”，或让事务失败并进入明确的 `Stopping/OffUnverified`，但绝不能显示已经停止而后台继续运行。

另增加 200～500 ms 的轻量不变量审计，发现以下任一组合立即撤销加电许可并报警：

- 终态 + 活动 Timer；
- Disabled + 非 NotEnabled 状态；
- 无 Owner + 活动 Runner；
- 非 Formal/Recovering + Forward/Reverse DO；
- UI/持久化状态版本落后于当前 RunEpoch。

### P0-4：分离物理安全目标与运行状态影响集

1. 组级 OFF 可继续覆盖物理成员 4/5/6；
2. RuntimeState 只发布给“故障发生时 Enabled 且属于当前 RunEpoch 的参与者”；
3. 中央状态发布函数强制：`Enabled=false` 时除 NotEnabled 外一律拒绝；
4. UI 和配置持久化从 EpbManager 的权威快照派生，不再把任意迟到事件直接写入 `EpbTestRecord.Status`；
5. 配置切换为 Disabled 时，先完成安全退出，再提交 `NotEnabled + NotStarted + RunCount不变`。

### P0-5：打破 DAQ 恢复的循环证据依赖

当 Dev1 压力样本失新时，恢复顺序应为：

1. 立即电机 OFF、程控电源 OFF；
2. 压力 DO OFF、AO=0，并记录命令级证据；
3. 若压力不可观测，状态标记为 `PressureUnobservable`，等待硬件规定的最大机械释放时间，而不是伪装成已确认压力安全；
4. 清理并重建 Dev1 DAQ；
5. 要求新 Generation 的连续新鲜控制样本；
6. 再用新鲜压力确认释放；
7. 重建液压代次和参与者；
8. 在当前 Epoch/Owner 下原子重新加入。

即：先通过电气去能量化和有界机械等待获得可重建条件，再用重建后的传感证据完成最终确认。若风险评估不允许仅靠时间窗口，需增加独立压力开关/泄压回读作为恢复证据，不能让单一 DAQ 同时成为故障点和恢复前置条件。

### P0-6：修正学习期的故障与取消作用域

1. 液压屏障异常应只作废同组同一逻辑学习 Slot，组内按策略重试；不能由一个通道进入 Formal 后把仍在 Learning 的兄弟通道判为 Pending。
2. 区分三种取消：用户/新 Epoch 取消、通道自身故障、同组同步故障；不能把共享 CTS 的取消统一写成 `ChannelCanceled` 并污染隔离结果。
3. `BatchStartResult.StartedChannels/Faults` 必须在提交锁内根据真实 Owner、Timer、Permit 和终态计算，不使用过期 `quarantined` 标记单独裁决。
4. 部分启动返回前，对所有 Fault 通道执行 P0-3 的非运行事务并验证；对 Started 通道验证唯一 Timer 和唯一 Owner。

### P1：补齐可观测性

每次状态转换输出一条结构化记录：

```text
RunId, RunEpoch, Channel, Enabled,
FromState, ToState, LifecyclePhase,
OwnerTransactionId, TimerGeneration, EnergyPermitGeneration,
ReasonCode, CorrelationId, ResourceInventory
```

DO 日志额外记录 NI 完成时刻、日志入队时刻和后台落盘时刻。故障快照记录当时 Timer/Runner/液压租约/Permit 清单。这样以后可以直接判断是硬件未执行、控制线程迟到，还是 UI 事件迟到。

2. 真实台架至少完成 30 轮“运行→报警注入→自恢复→暂停→停止→启动”；

## 9. 修复发布前的临时处置

在上述 P0 项完成前，不建议将“系统自恢复”当成可无人值守能力。现场临时规则：

1. 出现控制链延迟或 NI `-200279` 后，停止当前批次并确认所有电机、电源和压力输出已去能量化；
2. 如果 UI 显示 StartBlocked 但 RUN 开关、计数、电流或动作任一仍在变化，按“仍在运行”处理，不可信任红色状态文字；
3. 禁止在旧自恢复任务仍活动时反复 Pause/Stop/Start；安全停机后重启程序/DAQ，避免旧异步任务残留；
4. EPB6 这类禁用通道以配置 `Enabled=false` 和实际输出为准，旧 Paused/Recovering 文案不作为运行依据；
5. 保留完整现场包和退出前快照，避免仅截取 error.log 而丢失 DO 分段计时与状态转换上下文。

这些只是降低风险的操作措施，不是最终修复。

## 10. 最终判定

本次现场问题已经定位到可执行的代码机制，不需要再以“偶发 NI 问题”“液压可能不稳定”或“UI 刷新不及时”笼统处理：

- EPB5 的 NI 全关写入实际上成功，错误升级来自实时路径同步日志造成的迟到返回；
- EPB6 的异常状态来自物理组影响集直接污染禁用通道运行态；
- EPB8～11 的启动受阻来自学习阶段和正式恢复阶段同时存在；
- EPB8 的“启动受阻但仍运行”来自终态与执行资源没有原子一致性。

只有完成 P0-1～P0-6，并通过 T1～T10 及真实台架验收，才能认为该类问题被彻底解决。
