**V2.13.0.7 已修复 1017 数据暴露的主要根因，但不能判定为完全解决。** 1350 数据证明又存在一个 P0 状态机缺口：操作员执行正常“暂停”时，客户端仍把 `PausePending/Paused` 包装成外部恢复阶段，Sidecar 将健康人工暂停误判为 `ExternalRecoveryStageStalled`，随后安全停机、杀进程、退避 60 秒、启动恢复进程并自动续测。第二次暂停再次触发同样链路，因此现场看到卡钳停止、状态故障、程序被 Watchdog 重启并继续试验。

1. 假运行监督主要依赖全局圈数，15 秒周期按 90 秒接管，无法证明是哪一个通道停滞；
2. 学习圈、资格圈及“机械动作完成但正式证据作废”的圈没有统一消耗耐久目标；
3. 恢复检查点在主程序侧拒绝时可能没有把失败送达 Sidecar；
4. 多个硬截止后的原始 Task 没有全部纳入迟到观察；
5. Watchdog 退避期间没有独立可见界面，主程序被杀后会短时露出桌面；
6. 墙钟跳变与程控电源通信超时缺少可直接定位阶段的结构化日志。

上述缺口已统一落到 **V2.13.0.8**。本轮代码状态为：

## 4. V2.13.0.8 人工暂停状态机修复

Heartbeat 新增：

- `ManualPauseActive`
- `ManualPausePending`
- `Phase=ManualPausePending/ManualPaused`
- `RecoveryStage=ManualPausePending/ManualPaused`

同时执行以下语义隔离：

```text
人工 PausePending/Paused
  != Recovering/ResumeChecking
  != 外部恢复停滞
  != 允许自动续测的事故接管
```

Sidecar 在健康人工暂停期间抑制：

- 恢复阶段停滞推断；
- 全局/逐通道圈进展停滞推断；
- 孤儿暂停和残留恢复计数推断；
- Timer/Runner 仍存在但已安全暂停的误接管。

安全兜底没有被取消。若人工暂停期间发生以下任一情况，Sidecar 仍会接管：

- 主进程退出或心跳真正丢失；
- 暂停后通道仍带电超过 5 秒；
- Stop 明确卡住；
- 已确认物理安全条件不成立。

但该接管走 `ManualPauseSafetyTakeover -> LaunchIdleRestart`：只执行安全 StopAll、必要时杀进程、重新打开到**空闲界面**，绝不自动恢复试验。这样同时满足“暂停意图优先”和“进程死掉仍能确保断能”。

## 5. 真正独立的逐通道假运行监督

每个通道 Heartbeat 独立携带：

- 最后机械完成 UTC；
- 机械完成累计数；
- 连续软件作废次数；
- DO 命令序列；
- 峰值截止 generation 与 accepted-sequence 水位；
- Runtime state、revision、进入状态时间；
- Timer/Runner/上电事实。

Sidecar 不再用“其他通道还在加圈”掩盖单通道停滞。触发条件包括：

1. `ConsecutiveSoftwareAbortCount >= 2`；
2. Running/Warning/Learning/Qualification，以及仍带 Timer/Runner/上电资源的 Recovering/ResumeChecking 通道，机械完成数和最后完成时间 60 秒不再变化；
3. Recovering/ResumeChecking 中 Timer、Runner、状态不变量超过 30 秒不收敛。

这里必须特别说明：**DO、曲线峰值截止水位、Runtime revision 即使持续变化，也不能重置机械无进展期限。** 1017 现场故障本来就是“曲线仍刷新、控制外观看似动作，但圈数不增”；若把 DO 或曲线刷新计入进展签名，假运行会被永久掩盖。本版 `WatchdogChannelProgressTracker` 只接受机械完成数/最后完成 UTC 的变化作为重置条件，DO、峰值和状态仅写入接管原因用于定位。

峰值截止也不再用 DO 序号代填。`TwoDeviceAiAcquirer` 在真实全速率峰值窗冻结时保存 `Generation + CutoffAcceptedSequence`，Heartbeat 直接读取该采集水位；因此日志可以区分“DO 在发但峰值管线未封口”和“峰值管线在推进但机械圈未完成”。

正式进展门限统一为：

```text
timeout = min(3600s, max(60s, 3 × ExpectedCyclePeriod))
```

| 配置周期 | V2.13.0.7 | V2.13.0.8 |
|---:|---:|---:|
| 15 秒 | 90 秒 | **60 秒** |
| 60 秒 | 270 秒 | **180 秒** |

60 秒是正常 15 秒周期的 4 倍，保留调度和证据排空余量，同时满足现场要求“不等 90 秒”。

## 6. 机械圈成为耐久目标的权威口径

V2.13.0.8 明确区分两个指标：

| 指标 | 含义 | 用途 |
|---|---|---|
| `RunCount` | 正式控制成功且证据事务提交的质量圈 | 数据质量、正式证据统计 |
| `MechanicalCycleCount` | 实际完成夹紧+释放的全部机械圈 | 耐久磨损、剩余目标、Watchdog 进展 |

机械圈包括：

- 自学习圈；
- 暂停恢复资格圈；
- 正式成功圈；
- 已完成释放，但峰值/DAQ/持久化证据随后被软件恢复作废的正式圈。

只有 Runner 到达 `Released` 才计机械圈；取消在夹紧中途、硬故障未释放等半圈不会误计。

`index.db` 原位迁移增加：

```text
mechanical_completed INTEGER NOT NULL DEFAULT 0
mechanical_completed_at TEXT
```

升级旧库时，对确定完整的 `completed`、`learning_completed`、`qualification_completed` 自动回填机械事实；含义不确定的历史 canceled/alarm/软件作废圈不猜测。新版本运行后，机械完成会在圈最终证据状态提交之前独立置位，因此软件作废也不会丢失物理事实。

所有启动和恢复路径改为：

```text
Remaining = TotalCount - max(XML机械圈, SQLite机械圈, 进程内机械圈, RunCount)
```

达到机械目标后，即使最后一圈正式证据作废，也必须安全完成该通道，不能为了补证据再磨损一圈。UI 左侧、汇总面板、设置页、无人值守检查点和 Watchdog 统一使用这一口径。

另外补了两个目标边界：

- 学习/资格软件自愈每次重试前重新检查机械剩余数；若作废圈已经完成最后一次夹紧+释放，禁止重做同一逻辑圈；
- 若目标在启动前已完成，或在学习/资格阶段刚好耗尽，该通道进入 `CompletedDuringStartChannels`，不执行启动定位/额外学习/正式圈；无人值守恢复把它视为自然完成而不是“启动受阻”。

UI 不再依赖机械事件与正式成功事件的 `BeginInvoke` 到达顺序盲目 `+1`，而是用 Controller/SQLite 的绝对机械水位幂等对账，避免同一正式圈因回调乱序被双计数。

## 7. Watchdog 恢复过程持续可见

Sidecar 新增独立 STA WinForms 过渡窗，由 Watchdog 进程自身拥有，不依赖即将被杀的主程序：

- 屏幕中央、TopMost；
- 显示接管原因、安全停机、终止旧进程、退避倒计时、启动新进程、等待附着；
- 明确提示“系统正在执行安全恢复，请勿操作设备电源”；
- Sidecar 即使以 Hidden 方式启动，也通过原生窗口 API 显示该窗；
- 只有新主程序 Heartbeat 确认进入 Learning、Formal 或合法 ManualPaused 后才隐藏。

因此恢复退避 5/15/30/60 秒期间不会再只剩裸桌面，操作员能看到倒计时和当前阶段。

## 8. 其余恢复与诊断闭环

### 8.1 检查点拒绝必达 Sidecar

主程序验证 Watchdog 恢复检查点失败时，先连接现有 Sidecar session 并发送：

```text
RecoveryAttemptFailed:RecoveryCheckpointRejected:<reason>
```

短暂等待发送完成后才退出。Sidecar 将其作为可重试失败，而不是人工关闭或正常停止。

### 8.2 硬截止后迟到 Task 全观察

以下原始任务超过硬截止后仍进入 `TaskSupervisor`，并在最终完成、取消或异常时记录迟到毫秒数和异常：

- StopAll `coreTask`；
- 全部物理 OFF 聚合任务；
- `powerDisableTask`；
- 程控电源总组任务；
- 每个电源组 Disable owner 任务。

这既避免 `UnobservedTaskException`，也为“硬截止后到底晚了多久、最终是否异常”保留证据。

### 8.3 墙钟跳变事件

每个 DAQ device 独立比较 UTC 增量与 `Stopwatch` 增量，偏差超过 500 ms 输出：

```text
WallClockStepDetected
Direction=Forward/Backward
StepMs / WallElapsedMs / MonotonicElapsedMs
Device / Generation
Produced / Accepted / Processed / DiskPublished / RawTransferred
ActivePeakCapture / Cutoff / ProcessedWatermark
```

控制正确性继续只依赖单调时钟；该事件只用于诊断 Windows 校时来源和影响范围。

### 8.4 程控电源阶段耗时

每条 SCPI 命令记录：

```text
PowerCommPhase Phase=DnsResolve/TcpConnect/ScpiWrite/FirstByte/FullLine/Total
State=Started/Completed/TimedOut/Canceled/Failed
ElapsedMs / Endpoint / Command / Detail
```

下一次出现 `*IDN? 2000 ms` 时，可以直接区分 DNS、TCP 建连、命令写入、设备首字节不回或返回半行，不再只有一个总超时结论。

### 10.3 完整套件与压力用例确定性

完整套件第一次执行暴露了既有 `WatchdogJournalStorageTests.FailedStorageDoesNotBlockProducer` 的错误测试假设：项目盘不可写时，后台线程可能足够快地把事件写入 LocalAppData spool，因此内存队列并不一定溢出，原断言却强制要求 `DroppedEventCount > 0`。测试已改为接受并验证两种设计内合法结果：

- 有界队列确实溢出并记录 `DroppedEventCount`；或
- 生产者不阻塞，事件成功进入本机 spool 回退证据。

修正测试判据后，AdaptiveControlTests 完整套件 **435/435** 通过，不再保留已知红项。
