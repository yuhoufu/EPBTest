# 10358-029 / V2.13.0.5 启动异常、自动重启与恢复失败分析

> 分析对象：`D:\EPB_Data\10358-029_V2.13.0.5_0814_1422`  
> 分析时间：2026-08-14，Asia/Shanghai（UTC+8）  
> 对照背景：V2.13.0.4 于 12:44:55 发生 DAQ/电源确认链异常，12:50:36 人工结束；V2.13.0.5 控制与恢复逻辑与 V2.13.0.4 相同。  
> 分析方式：只读检查封存日志、SQLite/WAL、程控电源遥测、看门狗会话和相关源码；未修改程序、配置或原始封存数据。

## 1. 结论先行

本次事件不是单一故障，而是三层问题连续叠加：

1. **第一次试验停机的上游环境特征是主机共模资源压力。** 13:00:04～13:01:23 系统 CPU 大量时间处于 70%～100%，其中本程序自身一般仅约 5%～23%，主要负载来自其他进程；同时出现最高约 123.49 MiB/s 读、51.96 MiB/s 写和磁盘队列 34。随后控制相位偏差达到 7～8 s、DO 高优先级命令失败、程控电源遥测过期、两块 DAQ 同时出现 1～2.3 s 回调空窗。
2. **触发自动重启的直接原因是 Dev2 DAQ 时钟模型失效后，相关电源组无法在 5 s 内完成下电确认。** 13:01:18 Dev2 报 `DaqClockModelInvalid`；13:01:23 组 3、4 仍被判定为带电，形成 `DaqPowerDisableDeadlineExceeded` 和 `ExternalRecoveryRequired=true`。外部看门狗因此终止 PID 2892，并启动 PID 18852。
3. **自动重启进程实际上进入了恢复流程，并非只启动了 EXE。** 13:01:47 加载试验配置，13:01:49 完成恢复预检，13:01:50～13:01:51 重新连接并接管电源，随后进入启动定位。
4. **恢复失败的直接原因是在“启动定位”进行中，两块 DAQ 又触发活性故障，安全恢复把电源组 2、3、4 关闭。** 启动定位的通道级重试没有重新执行整批 DAQ/电源预检，也没有重新取得电源许可，只是断电、延时后原地重试；所以各通道连续看到 `ExpectedOutputDisabled`。EPB4 最先达到 3 次上限，整批启动失败。
5. **之所以没有继续自动恢复，是恢复进程在请求下一次外部接管后立即关闭了应用界面，导致原看门狗会话以 `ApplicationClosing` 终止。** Sidecar 收到 `WatchdogRecoveryStartupFailed`，但还没出现第二次 `OldProcessTerminated → RecoveryBackoff → RecoveryProcessLaunched`，会话就被撤销。因此自动恢复链只执行了一次进程重启。
6. **“没有进入试验界面”的现场感受基本准确，但技术上应表述为：恢复监视窗已创建并执行到启动定位，随后因启动失败被关闭，未形成稳定的学习/正式试验界面。** 自动恢复 RunId `ffdd...a15` 没有产生任何学习圈或正式圈。
7. 13:02:38 后在同一个 PID 18852 中重新加载配置，并以 `RecoveryMode=ManualAuthorization` 开启了新的根 RunId `72336...f97`。该次不是上一个恢复链的自动续测；它在 13:04:47 完成批量启动，并持续正式运行到封存时 14:22，5 个通道各形成 309 个正式控制结果。

综合定性：

> **首发停机：主机外部负载/IO 压力引发的共模调度延迟，表现为电源遥测陈旧和双 DAQ 回调异常；自动重启：由 Dev2 DAQ 恢复下电超时触发；恢复失败：启动定位与 DAQ 安全恢复并发冲突，电源许可被撤销后通道级重试没有回到整批预检；只重启一次：恢复失败路径主动关闭应用并终止了看门狗会话。**

## 4. 首次异常原因剖析

### 4.1 直接故障表现：电源遥测与控制时序同时陈旧

13:01:09 附近不是单个电源或单个卡钳先独立损坏，而是多条实时链同时迟滞：

- 组 2、3、4均出现 `PowerSupplyEnergizationPermitMissing ... TelemetryStale`。
- EPB4、9、10、11、5 的控制相位比计划时间晚约 7～8 s。
- 多条高优先级 DO OFF 命令执行约 103～111 ms 后返回 False。
- Dev1 和 Dev2 同时记录 1～2.3 s 的 DAQ 回调空窗。
- Dev2 持久化先出现 108.9 ms 延迟，随后时钟模型残差异常。

这些证据共同指向主机级共模延迟，而不是 5 个卡钳同时产生相同机械故障。

### 4.2 最强上游驱动：其他进程造成的 CPU/IO 压力

在 12:59～13:01:23 的 140 个 HostRuntime 秒级样本中：

- 系统 CPU ≥80%：46 个样本。
- 系统 CPU ≥70%：66 个样本。
- 系统 CPU 峰值 99.6%，当时本程序仅 14.6%，OtherCpu 85.1%。
- 本程序 CPU 峰值 22.9%，当时系统 CPU 84.4%。
- 磁盘读峰值 123.49 MiB/s，写峰值 51.96 MiB/s。
- 13:01:08.920 磁盘队列达到 34。

因此可以高置信判断：**本次实时链受到了本程序之外的主机负载干扰。** 封存日志只提供 `OtherCpu`，没有记录进程名，所以不能进一步断言究竟是杀毒扫描、文件复制、同步盘、备份、数据库工具还是其他程序。

### 4.3 为什么最终升级到进程重启

资源压力造成数据与遥测陈旧后，Dev2 进入 DAQ 自恢复。安全规则要求重建 DAQ 前先确认所属电源组关闭；但 5 s 截止时组 3、4仍在 Energized 集合中，因此当前进程被禁止继续重建 DAQ，升级到外部看门狗：

```text
外部 CPU/IO 压力
  → 控制线程、遥测、DAQ 回调共同延迟
  → TelemetryStale + 双 DAQ 大空窗
  → Dev2 时钟模型失效
  → DAQ 自恢复请求组 3/4 下电
  → 5 s 内未完成下电状态确认
  → ExternalRecoveryRequired
  → Sidecar 终止 PID 2892，启动 PID 18852
```

## 5. 自动重启为什么没有恢复试验

### 5.1 成功的部分

自动恢复进程完成了以下步骤：

- 正确启动同版本、同哈希的 PID 18852。
- 正确读取恢复授权和检查点。
- 正确识别项目、5 个待续通道和剩余正式圈数。
- 正确创建实时监视窗并进入恢复调用链。
- 正确执行安全接管、项目配置加载、DAQ 初检和程控电源预检。
- 组 2、3、4均完成“原本 OUTP ON → 先关断回读 → 重新上电稳定”的启动预检。

因此问题不在于“程序完全没有恢复功能”或“检查点丢失”。

### 5.2 失败的竞争窗口

关键竞争发生在 13:01:53：

1. 整批电源预检已通过，启动定位开始。
2. 启动定位过程中 Dev1、Dev2 同时越过 100 ms DAQ 活性阈值。
3. DAQ 安全恢复立即关闭组 2、3、4并撤销 `ExpectedOutputEnabled`。
4. 尚在运行的启动定位任务继续尝试通道动作。
5. `HasEnergizationPermit()` 首先检查 `ExpectedOutputEnabled`，因此返回 `ExpectedOutputDisabled`。
6. 启动定位的重试逻辑只执行本通道 OFF、延时 1 s/2 s、再次调用 `StartupPositioningAsync()`；没有等待整批 DAQ 恢复完成，也没有重新调用整批电源预检。
7. EPB4 最先累计到第 3 次，抛出 `SoftwareSelfHealingExhausted`；并行整批随即失败。

这是一种恢复层级不匹配：**故障发生在整批 DAQ/电源层，但重试停留在通道定位层。**

### 5.3 为什么没有第二次自动重启

恢复失败 catch 路径先执行：

```text
RequestExternalRecovery("WatchdogRecoveryStartupFailed:...")
```

随后立即：

```text
BeginInvoke(Close())
```

实际事件顺序为：

- 13:01:59.378：Sidecar 收到新的 `TakeoverRequested`。
- 13:02:09.839：应用关闭，并将会话终态写成 `ApplicationClosing`。
- 之后没有 `OldProcessTerminated`、第二次 `RecoveryBackoff` 或第二个 `RecoveryProcessLaunched`。

也就是说，“请求继续看门狗重试”和“关闭应用并撤销会话”发生了冲突，后者终止了恢复链。这是“只重启了一次”的直接原因。

### 5.4 为什么操作员看不到稳定试验界面

源码顺序是先 `OpenChildForm(monitor)`，再执行 `ResumeFromWatchdogCheckpointAsync()`。因此监视窗对象确实被创建；但恢复启动在约 15 s 内失败，异常路径随后关闭主界面/会话，同时无人值守模式还抑制了模态提示框。现场效果就是：

- 程序出现过或闪过；
- 没有稳定停留在正在学习/正式运行的试验界面；
- 也没有清晰弹出“恢复失败，等待下一次重试”的操作员提示。

## 6. 与 V2.13.0.4 异常的关系

两次事件不是完全相同的首发信号，但属于同一故障家族：

| 对比项 | V2.13.0.4 最终事件 | V2.13.0.5 本次事件 |
|---|---|---|
| 首发数据异常 | Dev2 `DaqCallbackStale` | 双 DAQ 回调空窗、Dev2 时钟模型失效 |
| 电源链 | 组 3、4下电状态不能确认 | 组 2、3、4遥测陈旧；组 3、4下电截止超时 |
| 主机证据 | 未见明显持续资源耗尽 | 明确出现外部 CPU/IO 高负载与磁盘队列 34 |
| 自动恢复结果 | 最终停在 Recovering/Paused，人工结束 | 外部重启一次；恢复启动竞争失败；会话被关闭 |

V2.13.0.5 在 V2.13.0.4 人工结束后约 4 分钟即重新开始，底层主机/DAQ/电源环境没有经过独立验证。由于控制和恢复逻辑相同，原有的“DAQ 恢复必须先确认电源下电”安全门继续生效；这是正确的安全原则，但启动与恢复之间的协调缺口也被完整继承。

## 7. 解决方案

### 7.1 P0：现场立即措施，不改程序即可执行

1. **先消除外部主机负载再启动试验。** 使用任务管理器、资源监视器或 Process Explorer 确认 13:00 附近的高 CPU/高磁盘进程；停止对 `D:\EPB_Data` 的复制、压缩、同步、备份、杀毒全盘扫描或其他大 IO 操作。
2. **重启前留出稳定观察窗。** 建议至少连续 30～60 s 观察两块 DAQ 无 >100 ms 回调间隙、系统 CPU 不持续高位、磁盘队列接近 0，再允许上电和启动定位。
3. **对电源组 2、3、4做完整冷态确认。** 先确认 OUTP OFF、输出电压降到安全范围、遥测时间戳连续更新，再由程序执行启动预检；不要只依据约 0 A 判断整组已关闭。
4. **自动恢复失败后采用受控人工重开。** 确认 `index.db` 中上一批有效 `completed` 圈已提交、活动圈已作废，再重新加载项目并开始完整学习。13:02:38 的实际操作证明该路径可以重新运行。
5. **避免在恢复窗口做封存复制。** 封存、压缩或同步应在试验安全暂停并确认数据收口后执行，避免把证据采集动作本身变成实时负载。

### 7.2 P1：程序恢复逻辑建议

1. **把 DAQ 故障升级为整批启动取消，而不是通道定位原地重试。** 启动定位期间一旦发生 DAQ recovery epoch 变化，应取消当前 `PreReleaseBatchWithPlanAsync`，等待 DAQ 恢复、全电源 OFF 和数据边界完成，再从 `EnsureDaqReadyBeforeStartAsync → EnsurePowerSupplyReadyBeforeStartAsync → StartupPositioning` 顶层重新开始。
2. **重试前重新获取整批电源许可。** `ExpectedOutputDisabled`、`PlannedTransition`、`TelemetryStale` 应视为整批基础设施瞬态；不能仅执行通道 OFF 后再次调用 `StartupPositioningAsync`。重新上电必须由集中式电源协调器完成，禁止通道并发各自上电。
3. **将 DAQ 恢复窗口从通道三次预算中剔除。** 如果失败原因是恢复线程主动撤销电源许可，通道重试次数不应累计；待恢复 epoch 完成并取得新鲜遥测后再重新计数。
4. **修正恢复进程退出与 Sidecar 会话的竞态。** `WatchdogRecoveryStartupFailed` 后应保留会话授权，等待 Sidecar 确认接管或通过专用“为重启而退出”路径结束当前进程；不能用普通 `ApplicationClosing` 撤销同一恢复会话。
5. **增加恢复启动的主机健康门。** 若 OtherCpu、磁盘队列、DAQ gap 或遥测年龄超过启动门槛，保持全断能并延迟重试，不进入启动定位。
6. **把恢复状态显式呈现给操作员。** 非模态显示“恢复预检、启动定位、DAQ 恢复、等待外部重启、恢复失败原因和下一次退避时间”，避免只看到程序闪退或回到初始页。

### 7.3 P2：诊断与监控增强

1. HostRuntime 增加 CPU 前几名进程名/PID、磁盘 IO 前几名进程，或在异常前后触发轻量 ETW/性能计数器快照。
2. 对电源遥测记录最后成功采集时间、轮询耗时、请求/应答错误和线程调度延迟，区分“设备通信失败”与“主机线程没获得调度”。
3. 对启动定位记录每次尝试对应的 DAQ generation/recovery epoch、电源 operation epoch 和 permit 原因，直接证明许可由谁撤销。
4. 将“已请求 Sidecar 重试”和“Sidecar 已确认接管”设为不同状态，只有后者成立后才允许当前恢复进程退出。

## 8. 建议验收用例

| 用例 | 注入条件 | 期望结果 |
|---|---|---|
| 启动定位中 DAQ gap | 定位阶段让 Dev1/Dev2 超过 100 ms | 取消整批定位，保持全断能；DAQ 恢复完成后从整批预检重新开始，不累计通道硬故障 |

## 9. 证据强度与未决项

### 9.1 已证实

- PID 2892 和 PID 18852 为同一 V2.13.0.5 二进制和配置。
- 首次试验期间主机存在明显的外部 CPU/IO 压力。
- 电源遥测过期、DO 延迟/失败和双 DAQ 回调大空窗发生在同一窗口。
- 外部重启原因是 `PowerDisablePendingTimeout`。
- 自动恢复读取检查点成功，失败在启动定位而非检查点/数据库加载。
- 启动定位与双 DAQ 安全恢复并发，电源许可被撤销后报 `ExpectedOutputDisabled`。
- 恢复失败后会话终态为 `ApplicationClosing`，未发生第二次自动进程启动。
- 13:02:43 的新运行是 `ManualAuthorization`，不是原恢复链继续。

### 9.2 高可信判断

- 首次异常的主要上游驱动是本程序之外的主机资源竞争。
- 自动恢复失败属于恢复层级和生命周期协调缺口，而不是 EPB4 单独硬件损坏。

### 9.3 仍未解决

- 封存日志没有记录高负载进程名，不能确认具体外部程序。
- 无独立物理接点，`PhysicalOffStatus=NotMeasured`；只能根据程序状态、程控电源回读和电流代理判断。
- V2.13.0.5 封存时仍在运行，存在 WAL 和 `running` 记录；14:22 之后的试验结果不在本报告范围。

## 10. 数据质量评估

总体评估：**可带 caveat 分享。**

- 版本、启动、Watchdog、错误、UI 和 SQLite 证据可以互相对齐。

- 主机负载证据足以判断存在共模资源压力，但不足以锁定具体外部进程。
