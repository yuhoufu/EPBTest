# V2.13.0.5 独立看门狗 StopAll 液压租约清场误判与自动续测代码分析

## 1. 结论摘要

2026-08-14 07:36:38 的这条错误并不表示电机、电源或液压没有执行安全停止。仅按当前代码还原，最符合日志的过程是：

1. 独立看门狗已经判定主进程需要进行进程级接管，向主程序发送 `RequestStopAll`，并在外部进程内同时启动 15 秒接管倒计时。
2. 主程序收到请求后执行了完整的 `StopAll` 安全动作，包括撤销当前批次、取消 Runner/Timer、提交全通道高优先级 OFF、关闭程控电源、强制释放液压、停止 DAQ，并尝试闭合 Raw/SQLite 持久化边界。
3. StopAll 强制释放液压时，液压协调器按设计用 `OperationCanceledException("HydraulicForceRelease Reason=StopAll:SystemFault")` 结束旧液压代次。
4. 随后的“最终逻辑清场”再次清理 EPB11 的旧液压租约。该租约已经属于刚才被强制结束的代次，因此等待旧代次终态时重新抛出了同一个预期取消异常。
5. EPB11 租约仍在 `finally` 中被成功移除。异常日志里的最终快照也证明：批次、Timer、Runner、CTS、液压参与者、液压租约、DAQ 恢复、软件恢复和恢复所有权均已归零，两个液压组也都处于可重新启动的健康状态。
6. 但是最终清场函数把这次“旧代次已被强制取消”的历史异常保留在 `errors` 列表中，并使用 `logical.IsQuiescent && errors.Count == 0` 判定是否通过。因此即使最终状态已经干净，仍得到 `LogicalQuiescenceConfirmed=false`，继而抛出本次 `InvalidOperationException`。
7. 主进程捕获异常后只记录错误，不发送 `StopCompleted`，也不主动退出。独立看门狗自己的 15 秒倒计时不会因此停止；如果 Session 没有被人工撤权，而且 PID 与进程启动时间仍匹配，它会终止旧主进程，经过首轮 5 秒退避后启动恢复进程。
8. 恢复进程重新执行全断能和物理安全确认，从检查点与 SQLite 成功正式圈计算剩余圈数，重新学习后继续试验。因此现场看到“程序后来仍在正常运转”与当前无人值守设计是一致的。

需要准确区分两件事：这不是“全过程完全没有停机”，而是“没有形成永久停机”。代码已经在异常抛出前执行过 StopAll，电机输出、程控电源、液压和 DAQ 都经历过安全收口；之后很可能由独立看门狗完成了换进程续测。因为目前没有 Watchdog Journal、PID、运行日志和持久化边界记录，不能仅凭这一条错误日志证明实际换进程时间，也不能证明本次停顿持续了多久。

## 2. 分析范围与证据限制

本报告只使用以下证据：

- 用户提供的 2026-08-14 07:36:38 错误日志；
- 当前工作区 V2.13.0.5 代码；
- 当前 Git 基线 `70ccbe5` 及工作区中与本链路无冲突的现有修改。

本次没有封存项目数据，因此缺少以下关键运行证据：

- `WatchdogSessions` 中的 Watchdog Journal；
- 主进程和恢复进程 PID、ProcessStartTicks；
- `TakeoverRequested`、`OldProcessTerminated`、`RecoveryProcessLaunched` 和 `Watchdog SafetyTakeover 已确认` 记录；
- StopAll 分项结果中的 Raw、Persistence、DataContinuity 完整字段；
- 故障前后的圈号、SQLite 状态和恢复检查点。

所以，本报告可以高置信解释“为什么产生该异常”和“代码设计上异常后会做什么”，但不能把首次触发看门狗的原因唯一确定为心跳丢失、孤儿暂停、电源关闭超时或恢复阶段停滞中的某一种。

另外，07:36 运行程序的精确二进制可能早于当前工作区当天后续构建；不过日志中的方法、行号、异常文本和当前代码链完整对应，因此以下控制流还原具有直接代码依据。

## 3. 原始日志逐字段解释

### 3.1 顶层日志来源

日志由 `MTTfTest/FrmEpbMainMonitor.UnattendedRecovery.cs` 的 `OnWatchdogStopAllRequested` 捕获分支写出：

```csharp
catch (Exception ex)
{
    ProjectLogHub.Write(ProjectLogLevel.Error,
        "独立看门狗请求 StopAll 未能收口，外部进程将在15秒期限后强制接管：" + ex.Message,
        "独立看门狗", ex);
}
```

因此这条日志说明的不是“看门狗线程崩溃”，而是：独立看门狗已经发出接管请求，主进程尝试自行完成 StopAll，但没有拿到允许原进程重新启动的完整许可。

### 3.2 `Motor=; Power=; Pressure=;`

这三个字段来自 `StopSafetyResult.MotorError`、`PowerError` 和 `PressureError`。它们为空说明本次抛出的异常没有携带对应错误文本。

从后续控制流和最终液压组快照看，没有出现明确的电机 OFF、程控电源关闭或压力释放失败证据。尤其两个液压组都显示：

```text
Admission=Open
Generations=0
Operations=0
Leases=0
Gate=Available
Pending=[]
```

这符合液压释放完成且协调器可接纳新代次的终态。

但应注意：空错误字符串不是单独的物理测量报告。严格确认仍应查看同一 CorrelationId 的 `StopAll分项结果`，核对：

- `MotorDO=Confirmed`
- `Power=Confirmed`
- `Pressure=Confirmed`
- `RawStorage=Confirmed`
- `Persistence=Confirmed`
- `DataContinuity=Confirmed`

当前异常文本没有包含 Persistence 和 DataContinuity，所以不能从这条日志单独证明它们也已闭合。

### 3.3 `Logical=EPB11Lease:HydraulicForceRelease Reason=StopAll:SystemFault`

这是本次异常最关键的字段，含义如下：

- `EPB11Lease`：最终逻辑清场处理 EPB11 的液压租约时捕获到异常；
- `HydraulicForceRelease`：旧液压代次由强制释压路径结束；
- `Reason=StopAll:SystemFault`：强制释放由 `SystemFault` 来源的 StopAll 发起；
- 它不是“EPB11 液压未释放”的直接表述，而是“EPB11 的旧租约观察到了所属代次被强制取消的终态”。

### 3.4 最终逻辑快照

日志中的快照为：

```text

Session=False
Batch=00000000000000000000000000000000

Runners=0
StopCts=0
```

逐项含义如下：

所以，快照所描述的“最终状态”本身是干净的。失败来自清场过程中的异常历史仍留在 `errors` 列表，而不是快照中仍残留活动对象。

## 4. 异常形成的完整代码链

### 4.1 独立看门狗先发起接管

独立看门狗每 250 ms 检查主程序状态。满足以下任一条件时可以发起接管：

1. 主进程已经退出；
2. 心跳年龄达到 5 秒；
3. 存在可恢复通道，并且孤儿暂停持续达到 5 秒；
4. 存在可恢复通道，并且程控电源 Disable Pending 持续达到 5 秒；
5. 存在可恢复通道，并且一般恢复阶段连续 60 秒没有有效进展。

接管开始后，`WatchdogHost.BeginTakeover` 同时做两件事：

```text
记录 TakeoverRequested
发送 RequestStopAll 给主进程
启动 TakeoverAsync 的 15 秒倒计时
```

因此“15 秒”是外部 Watchdog 进程自己的期限，不依赖主程序日志分支继续执行。

### 4.2 主进程把请求切回 UI 线程

`WatchdogRuntime.ReaderLoopAsync` 收到 `RequestStopAll` 后触发 `StopAllRequested` 事件。主窗体使用 `BeginInvoke` 把处理投递到 UI 线程，然后调用：

```csharp
await _epb.PrepareForFreshRestartAsync(
    new StopContext
    {
        Source = StopSource.SystemFault,
        Reason = "独立看门狗整批接管：" + reason,
        Initiator = "MTTFTest.Watchdog",
        ...
    });
```

### 4.3 `PrepareForFreshRestartAsync` 先完成 StopAll

该方法先调用 `StopAllAsync(context, CancellationToken.None)`。这里特意不用调用方取消令牌，目的是保证安全停止不会因 UI 或启动调用取消而半途退出。

`RunStopSafetyAsync` 的主要顺序是：

1. 冻结当前活动圈身份；
2. 结束批次 Session，递增 RunEpoch，撤销旧运行提交资格；
3. 暂停全部 Timer；
4. 取消通道 CTS，移除 Timer/Runner 运行对象；
5. 为所有涉及通道提交最高优先级电机 OFF；
6. 并行启动全部程控电源 Disable；
7. 发布各通道 `SystemFault` 终态并清理运行对象；
8. 取消 DAQ 恢复并等待恢复所有权退出；
9. 对账电机 OFF 的实际完成结果；
10. 强制释放液压并等待真实压力安全；
11. 停止 DAQ，冻结最终接纳边界；
12. 排空 Raw 和持久化队列，提交被中断圈终态，并导出最近圈证据；
13. 生成 `StopSafetyResult`。

这说明异常在 `PrepareForFreshRestartAsync` 第 533 行抛出时，主要安全动作早已执行，而不是刚进入 StopAll 就失败。

### 4.4 StopAll 强制结束旧液压代次

压力安全确认调用：

```csharp
_hydCoordinator.ForceReleaseAsync(id, $"StopAll:{context.Source}")
```

当液压组仍有活动代次时，`ForceReleaseAsync` 对每个代次调用：

```csharp
FailGenerationAsync(
    state,
    new OperationCanceledException(
        $"HydraulicForceRelease Reason={reason}"),
    publishFault: false)
```

随后继续执行输出回零和安全压力等待：

```csharp
await ExecuteReleaseOutputAsync(hydraulicId);
await WaitForSafePressureAsync(hydraulicId);
```

因此 `HydraulicForceRelease` 是 StopAll 主动终止旧液压代次的内部终态信号。`publishFault: false` 也表明代码原意是不把这次 StopAll 主动取消发布成新的液压故障。

### 4.5 EPB11 旧租约再次观察到已结束代次

StopAll 返回后，`PrepareForFreshRestartAsync` 还会调用 `FinalizeLogicalQuiescenceForRestartAsync`。它遍历 `_hydraulicLeaseByChannel`，对残留映射逐个执行：

```csharp
await AbortHydraulicLeaseForChannelAsync(
    channel,
    reason + ":LogicalQuiescence");
```

EPB11 的租约对应代次已经在前面的 `ForceReleaseAsync` 中被标记为失败并从活动代次表移除。租约关闭进入 `MarkVoltageReleaseAsync` 时发现代次已不在活动表，于是按设计等待 `lease.Completion`，以便旧租约仍能观察所属代次的真实终态。

该 `Completion` 保存的正是前面写入的：

```text
OperationCanceledException: HydraulicForceRelease Reason=StopAll:SystemFault
```

所以该异常被重新抛出，并在最终清场函数中记录为：

```text
EPB11Lease:HydraulicForceRelease Reason=StopAll:SystemFault
```

### 4.6 租约实际仍完成了清除

异常没有阻止租约清除，因为两层代码都有 `finally`：

- `HydraulicGroupCoordinator.CloseChannelScopeAsync` 的 `finally` 从 `_activeLeaseScopes` 移除 scope；
- `EpbManager.AbortHydraulicLeaseForChannelAsync` 的 `finally` 从 `_hydraulicLeaseByChannel` 移除 EPB11 映射。

这与最终日志中的以下结果完全一致：

```text
Participants=0
Leases=0
Hydraulic 1/2 Generations=0 Operations=0 Leases=0 Gate=Available
```

### 4.7 最终状态干净，但验收仍失败

最终清场的判定是：

```csharp
var logical = CaptureLogicalQuiescenceSnapshot();
result.LogicalQuiescenceConfirmed = logical.IsQuiescent && errors.Count == 0;
```

本次：

```text
logical.IsQuiescent = true
errors.Count = 1
errors[0] = EPB11Lease:HydraulicForceRelease Reason=StopAll:SystemFault
```

于是：

```text
LogicalQuiescenceConfirmed = false
CanRestartInProcess = false
```

`PrepareForFreshRestartAsync` 因自动 `SystemFault` 接管不允许抛弃历史检查，最终抛出：

```text
InvalidOperationException: 重新开始清场未通过物理安全与软件逻辑不变量
```

从代码语义看，这是一个“终态已经安全，但清场验收保留了预期取消异常”的假阴性。它会降低可用性并触发更重的进程级恢复，但没有把不安全状态误判成安全状态。

## 5. 报错以后主程序做了什么

### 5.1 当前主进程的处理

`OnWatchdogStopAllRequested` 的成功路径原本应该：

1. 发送 `StopCompleted` 给独立看门狗；
2. 设置 `_watchdogTakeoverExit=1`；
3. 强制刷新项目日志；
4. 调用 `Application.Exit()` 主动退出。

本次在 `PrepareForFreshRestartAsync` 内抛出异常，因此以上四步都没有执行。catch 只做一件事：记录当前错误。

catch 之后 UI 消息循环不会因为这个异常直接崩溃，主窗体可能暂时仍显示。但当前批次已经被 StopAll 撤销，代码也没有在该 catch 中重新启动批次，因此原进程本身不会沿此分支恢复为正常试验运行。

### 5.2 独立 Watchdog 的处理

独立看门狗在发送 `RequestStopAll` 时已经启动 15 秒倒计时。它不会等待这条错误日志，也不要求收到 `StopCompleted` 才能继续。

倒计时结束时，如果同时满足：

- Session 没有被人工停止或撤权；
- 旧进程仍存在；
- PID 和 ProcessStartTicks 仍与 Journal 中记录的旧进程一致；

则调用 `process.Kill()`，等待最多 5 秒确认旧进程退出，并记录 `OldProcessTerminated`。

如果旧进程已经自行退出，则跳过 Kill，直接进入恢复启动循环。

### 5.3 恢复进程的启动

首次恢复等待 5 秒；后续失败依次退避 15 秒、30 秒、60 秒。恢复进程通过以下参数启动：

```text
--watchdog-recover
--watchdog-pipe
--previous-pid
--recovery-attempt
--exclude-channels
```

排除集合包括：

- 人工禁用通道；
- 已达到正式目标圈数的通道；
- Controller 权威永久硬件报警锁存通道。

普通可恢复报警、联锁状态和健康通道不会仅因旧 UI 状态被永久排除。

### 5.4 新进程的 SafetyTakeover

恢复进程初始化控制对象后不会立即恢复上电，而是再次执行安全接管：

1. `_do.AllOff()`，明确写入全部 DO 关闭；
2. `_ao.ResetAll()`，模拟输出回零；
3. 再次执行 `StopAllAsync(Source=SystemFault)`；
4. 强制要求 MotorOff、PowerOff 和 PressureSafe 三项全部确认；
5. 将上个进程遗留的活动圈提交为软件恢复中止；
6. 应用排除通道；
7. 从 SQLite 已成功提交正式圈计算各通道剩余圈数；
8. 校验检查点进度不能比耐久事实更靠前；
9. 对仍需运行的通道重新执行学习；
10. 建立新的 RunId/RunEpoch，继续剩余正式圈。

如果新进程 SafetyTakeover 或批次启动失败，它不会冒险上电，而是保持本轮 Watchdog 授权，关闭当前恢复进程并请求独立 Watchdog 继续按退避策略重试。

## 6. 为什么现场看起来仍然正常运转

### 6.1 最符合代码的解释

最符合代码的解释是：旧进程在该错误后没有成功自行退出，独立 Watchdog 在 15 秒期限后接管，终止或确认旧进程退出，然后启动了新的恢复进程；新进程完成 SafetyTakeover、重新学习，并从 SQLite 成功圈之后继续运行。

这正是独立进程看门狗的设计目标：单次同进程自愈或清场验收失败，不应造成整轮试验永久停止。

### 6.2 “没有永久停机”不等于“没有发生停机动作”

从代码上可以确定，异常抛出前至少已经进入以下流程：

- 当前 Batch Session 被取消；
- 旧 RunEpoch 被撤权；
- Timer/Runner 被清除；
- 全通道 OFF 被提交；
- 程控电源 Disable 被启动并对账；
- 液压被强制释放；
- DAQ 被停止；
- 最终软件对象快照归零。

所以如果“没有停机”指电机动作和正式圈完全连续、没有重新学习、进程 PID 也没有变化，那么它与这条日志对应的代码路径不一致。更准确的现场现象应描述为：

> 试验发生了一次安全中断和自动进程接管，但系统没有永久停机，之后自动恢复并继续正式目标。

### 6.3 为什么视觉上可能不明显

恢复进程会：

- 打开同一个程序和实时监视界面；
- 加载同一个项目；
- 使用检查点恢复选中通道；
- 从 SQLite 已成功圈数计算剩余目标；
- 排除已完成、人工禁用和永久报警通道；
- 重新学习后继续运行。

因此操作者可能只看到短暂刷新、重新学习或圈间间隔，而不会看到软件长期停在错误状态。

## 7. 本次问题的性质与影响

### 7.1 直接问题

直接问题是最终逻辑清场对“预期取消终态”的分类不正确：

- StopAll 主动用 `OperationCanceledException(HydraulicForceRelease...)` 终止旧代次；
- 同一个旧租约稍后观察到该终态；
- 租约和协调器最终已经清空；
- 验收仍因为历史异常存在而失败。

这是逻辑清场的假阴性，不是液压硬件释放失败的直接证据。

### 7.2 安全性影响

当前行为偏向失效安全：

- 没有在状态可疑时继续沿用旧进程；
- StopAll 的电气、液压和 DAQ 停止在异常前执行；
- 最终许可失败后升级到独立进程接管；
- 新进程重新执行全断能和物理安全验证后才允许重新学习。

因此从代码结构看，该误判带来的主要问题是可用性代价和额外停顿，而不是绕过安全门禁。

### 7.3 可用性影响

原本最终状态已经干净，理论上可以让主进程主动完成交接；但该假阴性迫使系统等待外部 15 秒期限，再经历至少首轮 5 秒恢复退避和程序初始化/重新学习，增加一次不必要的进程级恢复。

### 7.4 数据影响

StopAll 在抛异常前会尝试：

- 停止 DAQ 并冻结最终接纳边界；
- 排空 Raw；
- 等待 SQLite/持久化边界；
- 提交被中断圈终态；
- 导出最近圈证据。

恢复进程又以 SQLite 成功正式圈数作为继续起点，因此设计上不会把内存计数直接当成耐久事实。

不过当前错误文本没有输出 `PersistenceError` 和 `DataContinuityError`，且本次没有封存数据，所以不能对本次 07:36 事件的最后一批 Raw、SQLite 边界和中断圈终态作现场级确认。

### 7.5 首次触发原因仍未知

`HydraulicForceRelease Reason=StopAll:SystemFault` 只说明 StopAll 的来源是系统故障接管，不说明独立看门狗最初为什么接管。

首次触发可能是：

- `HeartbeatUnresponsive`；
- `ProcessExitedUnexpectedly`；
- `PowerDisablePendingTimeout`；
- `OrphanPausedTimeout`；
- `ExternalRecoveryStageStalled`；
- 主程序主动发送 `ExternalRecoveryRequired`。

必须读取 Watchdog Journal 中紧邻本日志之前的 `TakeoverRequested` 才能确定。

## 8. 代码层面的改进建议

本报告未修改程序。后续若整改，建议遵循“只消除假阴性，不放松物理安全门禁”的原则。

### 8.1 精确识别 StopAll 主动取消终态

最终清场处理租约时，可把同时满足以下条件的异常识别为预期终态：

- 异常为 `OperationCanceledException`；
- 原因明确为当前 StopAll 的 `HydraulicForceRelease`；
- 对应租约已经从 EpbManager 和协调器活动表移除；
- 液压组最终 `IsHealthyForFreshStart=true`；
- 电机 OFF、程控电源关闭和压力安全仍由独立证据确认。

不能笼统吞掉所有 `OperationCanceledException`，更不能吞掉 `HydraulicReleaseTimeoutException`、压力证据不可用、DO OFF 未确认或代次门仍被占用等真正失败。

### 8.2 以最终状态重新归类过程错误

建议把 `errors` 分为：

- 最终仍未解决的阻断错误；
- 已由幂等清场消解的过程异常；
- 仅用于诊断的历史终态。

`LogicalQuiescenceConfirmed` 应只被“最终仍未解决的阻断错误”否决，同时把已消解异常保留为 WARN 诊断，避免丢失证据。

### 8.3 增加精确回归测试

当前测试检索未发现覆盖本次精确序列的用例。建议增加：

1. 创建包含 EPB11 scope 的活动液压代次；
2. 先执行 `ForceReleaseAsync(..., "StopAll:SystemFault")`；
3. 再执行租约 Abort；
4. 验证 scope 和 manager 映射最终归零；
5. 验证两个液压组健康；
6. 验证该预期取消不会单独导致 `LogicalQuiescenceConfirmed=false`；
7. 反例验证真实释放超时、OFF 未确认、活动租约残留和 Gate Busy 仍必须阻断重启。

### 8.4 完善接管日志

建议错误日志统一附带：

- SessionId、CorrelationId；
- 当前 PID、ProcessStartTicks；
- Watchdog 原始接管 Reason；
- StopAll 所有布尔项；
- PersistenceError、DataContinuityError；
- `logical.IsQuiescent` 与阻断错误数量分别输出；
- 明确标记 `OldProcessWillBeTerminatedAtUtc`。

这样即使事故数据没有完整封存，也能从单条错误附近判断是物理安全失败、持久化未闭合，还是最终状态已干净但过程异常误判。

## 9. 后续现场验证要点

下次出现同类日志，应优先封存项目下 `WatchdogSessions` 和同时间段项目日志，并核对以下事件顺序：

```text
TakeoverRequested
RequestStopAll
StopAll分项结果
重新开始逻辑清场失败
独立看门狗请求 StopAll 未能收口
OldProcessTerminated（或旧进程自行退出）
RecoveryBackoff Attempt=1 DelaySeconds=5
RecoveryProcessLaunched PID=...
Watchdog SafetyTakeover 已确认
系统恢复预检
无人值守进程交接启动已确认
```

同时核对：

- 旧 PID 与新 PID 是否不同；
- 从错误到旧进程退出是否约 15 秒；
- 首次恢复启动是否再等待约 5 秒；
- 是否重新执行学习；
- SQLite 成功正式圈数是否连续且没有重复计数；
- 中断圈是否标记为 canceled/软件恢复中止；
- 已完成、人工禁用、永久报警通道是否没有被重新上电。

若这些事件成立，就可以确认本次“程序仍正常运转”来自独立进程看门狗成功接管和续测，而不是原进程忽略错误后继续沿旧批次运行。

## 10. 最终判断

仅从当前代码和这条日志判断：

- **高置信**：EPB11 液压租约已实际清除，最终软件快照和液压协调器快照均已干净；
- **高置信**：异常由 StopAll 主动强制释放旧液压代次后，最终租约清场再次观察到预期取消终态所触发；
- **高置信**：当前判定把“已消解的过程异常”作为最终阻断条件，形成逻辑清场假阴性；
- **高置信**：异常前已经执行 StopAll，不能把现场现象描述为完全无停机动作；
- **中高置信**：现场后来正常运行是外部 Watchdog 终止/确认旧进程退出并启动恢复进程后自动续测；
- **无法确认**：最初触发接管的具体原因、实际 PID 切换时间、Raw/SQLite 最终边界和中断圈落盘结果，因为本次没有封存运行数据和 Watchdog Journal。

总体评价：这次表现说明独立进程看门狗的“防永久停机”路径发挥了作用，这是好的；同时也暴露出原进程最终清场验收存在一个可复现的误判点，导致本来已经干净的状态仍升级为一次成本更高的强制进程接管。
