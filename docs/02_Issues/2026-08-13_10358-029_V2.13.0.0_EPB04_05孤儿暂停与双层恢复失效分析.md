## 1. 结论

这次不是 EPB4、EPB5 自身报警，也不是写盘堵塞使两只卡钳停机。

直接触发原因是 **Dev1 新增了一次约 1.172 秒的 DAQ 回调空窗**。进程内 DAQ 存活监督在 22:47:52.981 检出历史空窗事件，立即执行了安全优先暂停，因此同属 Dev1 的 EPB4、EPB5 被置为 `PausePending/Paused`。

但是后续恢复链没有建立：没有创建可观察的 DAQ 恢复上下文，没有冻结持久化边界，没有安装 suppression，没有发布 `Recovering`，没有生成事故快照，也没有进入 DAQ 重建、重新学习或外部恢复升级。结果是两只卡钳形成了“**已被安全路径暂停，但没有任何恢复事务拥有它们**”的孤儿暂停。

独立 Watchdog 当轮已经成功启动并完成初始握手，不是未部署或启动失败；但封存包没有带回它的 Session Journal，因此不能证明 sidecar 在事故时仍然存活并持续收到心跳。未接管存在两条需要同时修复的路径：

1. 若 Watchdog 当时仍存活：主进程 PID 和心跳生产线程未失活，不满足 3 秒/5 秒门槛；主程序又没有发布 `ExternalRecoveryRequired`；同时“恢复进度”错误地包含持续增长的 Dev1/Dev2 `Persisted` 序号，导致 60 秒无进展计时不断被刷新；
2. 若 Watchdog 在事故前已经退出或管道断开：主程序没有 Watchdog 进程退出监测、心跳 ACK 和自动重连机制，发送失败还会被静默吞掉，因此 UI 上的“已握手”状态不会反映 sidecar 已失效。

无论 sidecar 当时属于哪一种状态，现有实现都不能覆盖本次“主进程整体存活，但 EPB4/5 进入无恢复所有者的局部孤儿暂停”。

本事故还暴露出一项高优先级安全缺陷：**电源组2的关闭任务从事故时一直悬挂到人工 StopAll**。遥测确认 22:47:52.998 之后电源组2仍为 `Output=True`、约 11.995 V，直到 23:12:23.054 才变为 `Output=False`。因此当时只有卡钳 DO 方向输出得到关闭，电源组失效安全并没有及时完成。

## 4. 进程内自恢复为何失效

### 4.1 当前调用顺序存在不可达窗口

`Controller/EpbManager.DaqLiveness.cs` 当前顺序为：

```text
RegisterDaqRecoveryBatchBarrier
  → OnDaqDeviceFaultSafetyDetected
      → Pause timers
      → submit high-priority DO OFF
      → StartElectricalGroupSafetyDisables
  → OnDaqDeviceFaultDetected
      → ObserveDaqIncident
      → BeginDaqAutoRecoveryAsync
      → InstallCutoff / FrozenBoundary / suppression / recovery watchdog
```

恢复上下文、FrozenBoundary 和硬期限均在第二段才创建。只要第一段的任一同步前置调用没有返回，程序就会停在“已暂停、未建立恢复所有权”的中间状态。当前源码虽然把电源 Disable 的主体设计为异步 Task，但 `FreezeAndCancelSafetyChannels`、状态发布、任务观察以及 async 方法第一次未完成 `await` 之前的代码仍在 liveness 调用线程同步执行，事务顺序本身仍然存在不可达风险。

本次实际证据与这一断点完全一致：

- safety pause 和 DO OFF 已发生；
- 第二段的所有恢复证据均不存在；
- 外层也没有记录 `DAQ独立存活监督异常已隔离`，更符合调用栈仍在等待，而不是抛异常后返回。

现场 Session 同时记录 `PackageVerified=False / PackageManifestMissing`，无法证明现场程序集与当前仓库源码逐文件一致；事故数据又没有线程 dump。因此本报告不能把缺失 publication 唯一归因到某一个当前源码调用点。可确认的是：现场执行只留下 safety pause，没有提交 recovery transaction。应按两种原因共同整改：既消除 safety-first 前置同步调用造成的不可达窗口，也保证全量发布目录中的程序集来自同一次构建。包身份只用于诊断和防止混装，不作为 Watchdog 拒绝恢复的硬门禁。

### 4.2 电源关闭链允许长期等待

`PowerSupplyCoordinator.DisableGroupCoreAsync` 在发送 `OUTP OFF` 前会：

1. 取消当前计划操作；
2. 无限等待 group operation gate；
3. `StopMonitorAsync` 取消并无限等待遥测任务退出；
4. 再进入 PSW client gate 发送 `OUTP OFF` 和回读。

PSW 单次命令有超时，但 operation gate、监控任务退出和调用方的同步前置执行没有统一的总硬期限，也没有在超时后主动打断旧 TCP transport、重建安全 OFF 通道的确定流程。本次 group 2 OFF owner 实际存活约 24 分钟，证明现有局部超时没有形成端到端硬期限。

### 4.3 Timer 健康监督把 DAQ 暂停当作永久合法状态

Timer 状态回调先发布 `PausePending`。之后 Timer 真正进入 `Paused` 时，通道已经不是 `Running/WarningRunning`，状态回调提前返回，因此通道状态长期停在 `PausePending`。

同时 `IsIntentionalOrOwnedTimerPauseReason` 把所有以 `Daq` 开头的暂停理由都视为“已有恢复所有者”。Timer 健康监督不会验证 `_daqAutoRecovery` 中是否确实存在匹配的 RunId、RunEpoch、Device 和 CorrelationId，也不会对孤儿暂停设置期限。

结果是：

```text
Timer 已暂停
AND 通道仍 Eligible
AND 没有 DAQ recovery context
AND Timer self-healing 也不接管
```

### 4.4 事故圈作废依赖后续恢复事务

事故圈的统一 `AbortedBySoftwareRecovery` 当前在恢复截止/Finalizer路径完成。由于恢复事务没有建立：

- EPB4只收到普通取消，保存为 `canceled`；
- EPB5自然完成当前圈，保存为 `completed`；
- 没有事故身份阻止晚到 Finalizer 提交成功状态。

这说明安全触发与数据终态仍不是同一个不可分割的事故提交。

## 5. 独立 Watchdog 为何失效

### 5.1 Watchdog 已启动

`ui-info.log` 明确记录：

```text
[2026-08-12 16:30:56.120] 本轮独立进程看门狗已启动并完成握手。
```

所以本次不能归因于用户未启动、sidecar未部署或初始握手失败。但这条日志只证明 16:30:56 的状态，不能证明 22:47:52 时 sidecar 仍存活。

### 5.2 进程失活门不成立

主进程从事故后一直输出 Host、DAQ、Timer和EPB9/10/11运行日志，PID 11060直到人工停止都存在。若 Watchdog仍连接，它收到的每秒心跳也可继续产生。因此：

- 3 秒 `Suspect` 不成立；
- 5 秒 `Unresponsive` 不成立；
- `ProcessExitedUnexpectedly` 不成立。

独立 Watchdog能兜底“进程死掉/心跳死掉”，但这次是主进程大部分功能正常、局部恢复链和两个通道失效。

### 5.3 60 秒无进展门被错误进度持续刷新

主程序的 `CreateWatchdogHeartbeat` 使用如下信息拼接 `progressSignature`：

```text
Paused/Recovering channel state
DaqRecoveryCount / SoftwareRecoveryCount / RecoveryOwnerCount
Dev1 Persisted / QueueDepth
Dev2 Persisted / QueueDepth
```

只要签名变化就递增 `RecoveryProgressVersion`。本次 Dev1、Dev2每秒仍约增加 100 个持久化批次，因此 `Persisted` 每秒变化，`RecoveryProgressVersion` 也每秒变化。

Watchdog端只检查该版本是否变化；变化即重置 `_lastProgressTimestamp`。所以即使 EPB4/5状态 24 分钟不变，60 秒 `ExternalRecoveryStageStalled` 也永远不成立。

这是把“后台采集仍活着”误当成“卡钳恢复状态机取得进展”。它是当前代码中足以导致本现象的确定性缺陷；由于缺少现场 Journal，无法再证明事故时 sidecar 实际收到了这些心跳。

### 5.4 缺少孤儿暂停独立判据

Watchdog协议已有 Enabled、Eligible、Paused/Recovering等集合，但接管条件仍要求：

```text
RecoveryActive == true
AND EligibleChannels.Length > 0
AND RecoveryProgressVersion 60秒不变
```

它没有单独检查：

```text
某个 Eligible 通道持续 PausePending/Paused
AND 不是人工暂停、人工停止、永久报警、已完成
AND 没有匹配的恢复上下文/阶段/所有者
```

因此这种“局部活着、局部孤儿暂停”的场景落在了两个看门狗的共同盲区。

### 5.5 主程序无法发现 Watchdog 自身失活

`WatchdogRuntime` 启动 sidecar 后没有保留并监控其 `Process`：

- 心跳没有 ACK 序号；
- `Send` 写管道异常被空 `catch` 静默吞掉；
- ReaderLoop 结束后不会把 UI 状态改为失效，也不会重启或重连 Watchdog；
- 初始“已握手”可能在 sidecar 后续退出后长期保持为用户认知。

因此，即使事故未接管的实际原因是 sidecar 自身提前退出，现有主程序也不会留下足够证据或自动恢复监督能力。

### 5.6 Watchdog Journal 未进入封存目录

独立 Watchdog Journal 当前写入 `%LOCALAPPDATA%\MTTFTest\Watchdog`，本次数据封存目录没有包含对应 session journal。虽然主程序日志足以确认握手，但无法从封存包复核每秒心跳内容、Watchdog最后状态和未接管判据。

这使本次无法在“sidecar存活但判据错误”和“sidecar已经失活”之间做最终取证，也属于事故可审计性缺口。

## 6. 整改方案

### P0-1：先提交恢复事故身份，再启动任何可能阻塞的安全 I/O

将 liveness trip 改为一个统一、不可分割的入口，禁止再用“先 safety，返回后才 recovery”的两段调用：

```text
TryBeginDaqRecoveryIncident
  1. CAS确认 RunId/RunEpoch/Device/Generation 尚未处理
  2. 创建 DaqAutoRecoveryContext 与硬期限
  3. 记录受影响通道、当前事故圈和 CorrelationId
  4. 原子安装 FrozenBoundary + SuppressAfter
  5. 发布 Recovering/RecoveryRegistered
  6. 非阻塞投递整组 Timer pause、DO OFF、电源 Disable、压力释放
  7. 进入受监督恢复任务
```

最低不变量：一旦任一通道因 `DaqDeviceFaultSafety` 被暂停，必须已经存在以下二者之一：

- 匹配的、带硬期限的 `DaqAutoRecoveryContext`；
- 已持久发布的 `ExternalRecoveryRequired`。

不允许再次出现第三种“只有 Pause，没有 owner/deadline”的状态。

### P0-2：电源安全关闭改为非阻塞准入和端到端硬期限

为每个电源组新增独立的高优先级安全 OFF worker/队列，DAQ liveness线程只做 `TryPostDisable`，不得执行可能延伸到监控退出、operation gate或SCPI读取的同步前置逻辑。

电源关闭链应有结构化阶段：

```text
DisableAccepted
MonitorCancelRequested
MonitorExited | MonitorExitTimeout
TransportAborted（超时才执行）
OutpOffSent
OutpOffReadbackConfirmed | OutpOffUnconfirmed
```

建议硬期限：

- 安全请求准入：不超过 20 ms；
- 原遥测任务退出：不超过一个 PSW 命令超时加 500 ms；
- group OFF 总期限：不超过 5 秒；
- 总期限失败：保持 DO OFF，立即 `ExternalRecoveryRequired=PowerDisableStalled`，不得无限等待。

超时后必须主动 dispose旧 transport以打断无法取消的 `ReadLineAsync`，确认旧连接退出后再由安全 owner重建连接发送 `OUTP OFF`。禁止两个连接并发读写同一设备。

### P0-3：增加进程内孤儿暂停检测

每 250 ms 检查：

```text
BatchActive
AND Channel Eligible
AND Channel in PausePending/Paused/Recovering
AND pause reason is not Manual/Alarm/Completed
AND no matching recovery context or recovery owner
```

满足超过 2 秒时：

1. 尝试补建同一 Device 的 DAQ 恢复上下文一次；
2. 若无法补建或已超过 5 秒，立即发布 `ExternalRecoveryRequired=OrphanRecoveryPause`；
3. 不等待 60 秒通用阶段期限。

该检测必须验证 RunId、RunEpoch、Device、CorrelationId，旧 Run 的暂停不能恢复新 Run。

### P0-4：修正 Watchdog 的恢复进度语义

从 `RecoveryProgressVersion` 的签名中删除：

- Dev1/Dev2 `Persisted`；
- 普通运行时 QueueDepth波动；
- 与恢复阶段无关的 DAQ数据面计数。

版本只能在以下真实状态机事件中递增：

- Recovery incident/context创建；
- FrozenBoundary安装完成；
- 安全关闭某一确认项完成；
- DAQ Stop/Close/Start阶段切换；
- generation变化并通过新鲜批次验证；
- 持久化前缀达到固定 FrozenBoundary；
- 通道从 Recovering进入 Learning/Formal；
- 明确失败终态/外部升级。

心跳新增：

- `RecoveryIncidentId`；
- `RecoveryContextPresent`；
- `RecoveryStageOrdinal`；
- `RecoveryAttempt`；
- `ExpectedRecoveryChannels`；
- `OrphanPausedChannels`；
- `PowerDisablePendingGroups`及持续时间；
- 每通道 PauseReason 和 PauseSinceMonotonic。

Watchdog新增两条独立接管规则：

```text
A. OrphanPausedChannels 非空持续 5 秒 → RequestStopAll
B. PowerDisablePendingGroups 非空持续 5 秒 → RequestStopAll
```

这两条不依赖 `RecoveryActive`、持久化序号或60秒通用进度计时。仍保留现有 3秒 Ping、5秒进程失活和60秒正常恢复阶段停滞规则。

### P0-5：让主程序监督 Watchdog 自身

初始握手成功不能等同于本轮 Watchdog 始终有效。主程序需增加：

- 每个 Heartbeat 对应 `HeartbeatAck(SessionId, Sequence, WatchdogMonotonic)`；
- 连续 3 秒无 ACK 时 UI 和主日志明确显示“独立看门狗失联”；
- 同一 Session 内仅允许一次受控重连/重启 sidecar，保持人工停止撤权优先级；
- 监控启动时保存的 Watchdog PID 与 StartTicks，进程退出必须结构化记录；
- 管道读循环退出或写失败不得静默吞掉，至少发布 `WatchdogTransportLost`；
- 重连不得生成新 RunId、不得重置事故身份或绕过人工停止。

这样即使本次真实情况是 sidecar 提前退出，现场也能自动补回监督能力并留下确定证据。

### P0-6：Timer 状态与恢复所有权联动

调整 Timer 状态观察：

- 即使当前通道已是 `PausePending`，Timer进入 `Paused` 时仍要发布最终 `Paused`；
- “Reason以 Daq 开头”不再自动视为永久合法；
- DAQ-owned pause必须能查询到匹配恢复 context；
- context不存在时由组级 DAQ恢复接管，不允许 Timer单通道自行 Resume；
- context存在但阶段超时则发布外部恢复要求。

### P0-7：事故触发时立即锁定事故圈终态

在 liveness incident提交时立即登记受影响通道的事故圈，不依赖后续恢复任务是否启动成功：

```text
IncidentCycles = current cycle for EPB4/5
TerminalIntent = AbortedBySoftwareRecovery
```

后续普通 Finalizer必须先检查该身份：

- 禁止把 EPB5这类晚到完成写成 `completed`；
- 将 `canceled/failed/completed pending commit`统一 CAS 为一个 `AbortedBySoftwareRecovery`；
- 只能提交一次；
- 不增加正式成功计数；
- 重启后从 SQLite提交成功圈重算剩余次数。

### P1-1：补齐恢复链审计日志

每次 DAQ事故必须至少形成以下成对日志：

```text
DAQ_INCIDENT_REGISTERED
DAQ_SAFETY_SUBMITTED
DAQ_CUTOFF_INSTALLED
DAQ_RECOVERY_STAGE
DAQ_RECOVERY_TERMINAL
```

每条带 RunId、RunEpoch、Device、Generation、CorrelationId、AffectedChannels、FrozenBoundary、StageStarted、Deadline。若五条中任何一条缺失，现场分析工具直接标记 `RecoveryProtocolIncomplete`。

Watchdog每 30 秒将摘要同步到主运行日志，并在人工停止、完成或接管时将 session journal复制到：

```text
<ProjectData>\WatchdogSessions\<SessionId>.json
```

### P1-2：增加 DAQ 空窗根因采样

当前只能确认约 1.172 秒空窗，不能唯一确定来源。下版需在 gap事件记录：

- callback开始/结束/重挂载耗时；
- NI task状态和 generation；
- GC暂停与线程池饥饿计数；
- liveness timer实际扫描间隔；
- 进程/系统 CPU、硬缺页、上下文切换；
- 每个同步 NI/PSW调用的 stage、线程ID和开始时间；
- 超过 500 ms 时自动捕获进程线程栈或轻量 dump。

注意：本次事故时 Host CPU约 5%～7%、DiskQueue约 0、磁盘写入很低，因此不能把空窗归因于磁盘压力。

## 7. 精确回归测试

### 7.1 事故复现测试

构造以下组合，不可只单测其中一项：

1. Dev1当前 callback已恢复，但 `CallbackGapEventCount` 新增，`LastCallbackGapMs=1172`；
2. EPB4正在圈内，EPB5同组并处于错峰相位；
3. 电源组2 `DisableGroupAsync` 在 monitor退出或operation gate处永久不完成；
4. Dev1/Dev2采集和 `Persisted` 序号继续增长；
5. 主进程心跳继续每秒发送。

必须验证：

- liveness扫描调用在有界时间内返回；
- context、FrozenBoundary、suppression和硬期限在电源 OFF等待前已建立；
- EPB4/5不产生新的正式成功圈；
- 两个事故圈各只有一个 `AbortedBySoftwareRecovery`；
- 电源关闭 5 秒未确认时发布 `ExternalRecoveryRequired`；
- Watchdog不会因 `Persisted` 增长刷新恢复进度；
- 最迟在孤儿暂停 5 秒或阶段硬期限到达时发出 `RequestStopAll`；
- 旧进程 15 秒不退出时执行既定强制接管，新进程先 `SafetyTakeover`。

### 7.2 Watchdog 单测

- `RecoveryProgressVersion`只随 stage ordinal变化，不随 Persisted变化；
- Eligible通道 `PausePending` 且 `RecoveryContextPresent=false` 5秒必接管；
-人工暂停、永久报警、人工禁用、已完成通道不得触发；
- ManualStop与自动接管竞态时 ManualStop胜出；
- 新 RunId/RunEpoch/SessionId使旧 heartbeat和旧接管消息失效；
- sidecar进程退出或管道断开后，主程序在3秒内记录失联并按同一Session受控重启；
- Heartbeat写失败不能被静默吞掉，ACK超时必须在主运行日志中可见；
- sidecar session journal可随封存数据一同回收。

### 7.3 电源关闭测试

- monitor处于正常轮询时请求 OFF；
- monitor卡在 `ReadLineAsync`；
- group operation gate被旧 ON/复核占用；
- transport超时后断开并重建；
- 重复 OFF请求加入同一 owner但不得无限延长硬期限；
- 达到硬期限时上报 `PowerDisableStalled`，不阻塞 DAQ恢复上下文创建；
- 最终不得出现“日志宣称安全暂停但连续遥测 Output仍为 True”的假闭环。

### 7.4 数据验收

- `PRAGMA integrity_check=ok`；
- 无 `running/open`；
- 每个事故圈恰好一个 `AbortedBySoftwareRecovery`；
- 无重复正式计数；
- FrozenBoundary只生成一次；
- suppression从 `FrozenBoundary+1`开始；
- StopAll最终 `DaqRecovery=0`、`SoftwareRecovery=0`、`RecoveryOwners=0`；
- EPB9/10/11等健康通道在整批重启后重新学习并续测，永久报警、人工禁用和已完成通道仍排除。

## 8. 现场临时处置

在上述 P0 全部完成并通过故障注入前，V2.13.0.0的独立 Watchdog不能被视为已经覆盖“局部孤儿暂停”。现场若出现以下组合：

```text
部分选中通道 PausePending/Paused 超过 1 分钟
AND 其他通道仍运行
AND DAQ/Persistence仍显示 Recovered
```

应人工执行“停止试验 → 再开始试验”。这与本次实际恢复方式一致，但只能作为临时操作，不是无人值守闭环。

同时应确认对应电源组 UI回读已为 OFF；若仍为 ON，保持卡钳 DO关闭并优先执行整批 StopAll，不要单独恢复该通道。

## 9. 与既有整改的关系

本次不是对既有 FrozenBoundary方案的否定。当前源码已经包含：

- 不可变 `DaqCutoffSnapshot`；
- `InstallCutoff`内 FrozenBoundary与suppression同锁提交；
- `RecoveryBoundaryContradiction`；
- `RecoveryTaskRegistry`；
- 独立 Watchdog进程和按试验生命周期启动。

问题在于现场故障入口只完成了 safety pause，没有留下 recovery transaction；当前事务顺序又允许在 recovery context 建立前执行同步前置工作。Watchdog侧既可能被数据面“伪进度”掩盖控制恢复停滞，也缺少自身失联的反向监督和封存证据。

因此本次修复重点不是再增加版本限制或发布身份门禁，而是：

1. 消除“Pause已发生但恢复上下文尚未提交”的中间窗口；
2. 让电源 OFF具有独立准入和端到端硬期限；
3. 让 Watchdog直接识别孤儿暂停和电源关闭停滞；
4. 让主程序确认 Watchdog 持续在线，失联可见且可受控重连；
5. 将事故圈作废绑定到事故触发，而不是绑定到后续恢复是否有机会运行。

## 10. 分析边界

封存 Session记录 `PackageVerified=False / PackageManifestMissing`，且 GitCommit、BuildUtc均未知，因此本报告不能用发布 manifest对现场 EXE与当前源码做逐文件同一性证明。现场行为与当前源码共同确认了事务顺序和 Watchdog 判据存在缺口，但不能据此唯一认定 recovery publication 缺失发生在当前源码的某一个具体等待点。

本报告不建议把包身份设为恢复硬门禁。按既定要求，现场仍采用全量目录更新；构建身份只用于确认没有混装程序集。下次封存必须同时带回 Watchdog Journal、ACK/进程退出记录和线程/阶段证据，才能把未接管路径与 recovery publication 的具体断点提升为确定结论。
