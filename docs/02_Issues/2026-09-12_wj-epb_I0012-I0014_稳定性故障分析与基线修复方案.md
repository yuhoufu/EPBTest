# wj-epb：I0012–I0014 稳定性故障分析与基线修复方案

分析日期：2026-09-12。项目：10243-028。时间统一为北京时间 UTC+08:00，原始 JSON 中 `Z` 时间加八小时。本文是证据分析与实施方案，不是修复完成或现场验收报告。

## 1. 直接回答：为什么反复故障，怎样解决

**目前不是一个“增加重启次数”就能解决的问题，而是三层问题叠加：采样/存储出现停顿；局部恢复和整批清理不能可靠收敛；退出后的许可、安全交接、启动回滚互相影响，导致窗口起来但试验没有恢复。** 旧版已经包含这些恢复模块，不能把它描述成“没有看门狗，再加一个即可”。

本次证据确认了以下事实：

1. **V3 的这次首发故障是学习期间的持久化积压。** 10:15:13 准备启动，10:17:21 Dev1、10:17:23 Dev2 先后超过约 1 秒积压门限，随后达到 256 批硬上限，并出现后台处理超过 500 ms。不是六个卡钳同时发生了六个独立机械故障，也不是本次所有报警都由 StartupPositioning 引起。
2. **同进程重建确实启动了，但没有完成。** 第一轮积压排空后重建学习，20 多秒后再次积压；又发生电源组断电确认失败、恢复登记失败，重建学习被取消。
3. **跨进程恢复被程序自己的启动回滚撤销。** 检查点审计证明：外部交接准备完成后，`StartupRollback` 把 `Armed` 从 true 改成 false。后续 `InProcessRecoveryFailed` 只覆盖原因，掩盖了真正撤权点。子进程因此拒绝续测；手动启动随后又被未关闭的接管事务拦截。
4. **旧版长时间后“消失”至少有一类是软件主动退出以便替换，不是已证明的随机崩溃。** 09-11 12:43 液压样本过期与周期收尾异常后，12:44 发起替换退出；旧进程退出，安全代理却连续遭身份校验拒绝，恢复链停在启动主程序之前。
5. **回退旧版也不是问题解决。** I0014 新增证据表明：10:55 旧版同样出现双卡采样/落盘停顿，停止边界卡住，随后走关闭限时终止；10:57 新会话启动，11:00 后再次有正式完成数据。这个新会话不能自动算作旧恢复事务成功。

实施方向：以 2.14.2.11 为稳定性比较基线，先修证据已经指向的恢复身份、取消语义和停止边界，再通过同负载测量解决停顿来源。不要整批搬回 V3 改动，也不要通过提高安全门限、隐藏报警、重置计数或无限重启来消除表面故障。

“不因软件故障长期停测”的可验收含义是：可恢复的软件故障有明确负责人和完成期限；需要安全断电时及时断电；故障解除后自动恢复动作、计数和正式数据。真实电源、压力、过流等安全条件不满足时，必须保留安全停机。

### 4.2 启动回滚撤权的代码解释

V3 `Controller/EpbManager.BatchStart.cs:1074` 的 `ResolveStartupCleanupSource`，只在熔断已打开，或“预期取消且 `_startupRecoveryCleanup` 精确匹配本启动Run/Epoch”时把回滚归为 `SystemFault`；否则归为 `StartupRollback`。该 owner 在清理调用的 finally 中释放，作用范围不能天然覆盖后续重建学习与外部接管的整个生命周期。

V3 `MTTfTest/UnattendedRecovery.cs:1745` 附近的 `OnRunAuthorizationRevoking`，只对 `SystemFault` 且 RestartPending/InProcessRecoveryPending 提供保留检查点的例外。审计中的 StartupRollback 不满足例外，于是撤销原本用于外部续测的 Armed。

**已证实：错误撤权的发生及上述分支行为。强证据推断：清理owner作用域与新批次生命周期不匹配，使重建学习取消落入普通回滚。待验证：通过确定性并发测试固定每个回调交错，确认当时 owner 已释放、缺失或不匹配的具体分支。**

旧标签同样有问题基础：`Controller/EpbManager.BatchStart.cs:2160` 按 circuitOpen 二选一，其他回滚均为 StartupRollback；`MTTfTest/UnattendedRecovery.cs:1713` 采用相同保留规则。不能仅回退就认为该链不存在。

正确修复是保留“用户希望继续的根试验意图”，同时撤销旧执行代的硬件权限；显式区分用户取消、内部重建取消、外部接管取消。不能全局禁止 Disarm，也不能凭异常类型 `OperationCanceledException` 就认为用户按了停止。

### 7.2 恢复必须满足的状态约束

1. 用户“运行意图”持续存在，直到明确停止/关闭策略、目标完成或确需人工介入的安全故障；每次临时软件恢复只撤销旧执行权限。
2. 同一资源集合同时只有一个恢复执行者。其他故障合并到该事务，不因为登记冲突重复全停或重复扣预算。
3. 每次恢复都有开始时间、当前阶段、实质进展、截止时间、下一负责人；没有永久 `Recovering` 或只有进程Healthy的无人接管状态。
4. 只有旧定时器/回调隔离、物理断能确认、数据冻结边界闭合，才能重建；新批次重新验证样本、压力和执行资格。
5. 跨进程启动后先接收合法许可与数据检查点，再重新学习/正式运行；必须证明动作和提交，不以Attach完成或窗口出现结束监督。
6. 熔断按同一根事故的实质失败计数；等待安全前置、重复通知、同一失败回执重放不能冒充新主程序失败。熔断保留明确原因和合法恢复入口；不默认放大次数。
7. 手动开始要先对合法已结束的接管进行幂等收敛；仍存在未释放硬件owner则说明阻塞及证据，不删除状态文件硬解锁。

### 7.3 停顿原因如何继续查到可修复层

首发物理停顿的唯一底层原因目前仍未证明。下一步本地/台架测量必须同时记录单调时钟和以下低开销指标：NI读取结束时间、回调入口、控制发布/消费水位、队列深度/最老年龄、写盘批量和flush时长、线程池/GC暂停、进程内存/句柄趋势、供电响应时长。

比较顺序是：纯采样与控制→加入正常落盘→加入快照/日志/备份→加入恢复故障注入，每次只改变一项。长耗时诊断和dump放在已安全停止之后；运行中只记录有界环形轻量证据。不能让观测代码本身引入新的秒级停顿。

若吞吐不足，应先减少重复序列化和同步flush次数、批量提交和隔离非关键写入；若是GC/线程阻塞，定位分配与锁等待；若是驱动停顿，再以NI错误码、调用栈和采样时钟证据确定处理方式。门限必须来自实际控制安全预算，不能为了通过测试随意从250ms扩大到数秒。

### 8.2 统一成功标准

每个应恢复通道同时满足：

- 正向夹紧、反向释放均有本代动作证据，定时器/执行体实际推进。
- 机械动作计数按真实动作增加；正式有效计数只随正式提交增加，不重置、不重复计数、不为补证据额外消耗已达目标的机械寿命。
- 新正式圈以completed落入SQLite，并可关联对应原始数据/波形；原事故圈有明确终态，已接受数据没有无说明缺口。
- 至少连续完成3个正式周期用于识别“刚恢复即复发”；这是单场景最低功能检查，不能替代耐久验收。
- 恢复事务、旧owner、未消费许可均闭合；没有部分通道永远停在Recovering/StartBlocked而全局显示Healthy。

恢复耗时从首个安全暂停计到最后一个应恢复通道的正式提交。方案阶段不编造统一“30秒必恢复”：此项目自学习10圈已有约2分多钟，必须把安全停止预算、重建预算和学习计划时长分开，再测出并冻结每阶段上限。
