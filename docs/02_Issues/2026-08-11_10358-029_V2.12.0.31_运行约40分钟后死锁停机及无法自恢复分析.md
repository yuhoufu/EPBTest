## 一、现象一句话总结

V2.12.0.31 运行约 40 分钟后，两块 DAQ 在同一时刻同时出现约 264ms 的回调空窗（双设备同时、同量级，指向公共调度/驱动/进程级短暂停顿）。独立存活监督在 100ms 门槛正确触发，并在约 1ms 内完成已带电通道的高优先级 OFF。

**导致不能自恢复的直接原因**不是 264ms 空窗本身（回调随后已自行恢复），而是恢复链存在**两层边界语义缺陷**：
1. **圈终态重新抓取动态边界**：当前圈作废通过通用圈收尾流程，该流程用 `GetLastDiskPublishedSequence`（当前实时发布序号）而非恢复事务冻结的 238368 作为耐久前缀目标。由于 DAQ 恢复采样后 Published 持续增长，该目标永远不可达。
2. **StopAll 门禁要求 `finalBoundary == boundary`**：为获取新鲜压力而只读重建的 DAQ 继续产生新批次，`FinalBoundary` 单调增长，该等式不可达。

同进程恢复抛异常、进程自重启 2 次交接全部失败，最终重启预算耗尽，系统永久停机。

## 三、停机根因分析

### 3.1 首发触发：双 DAQ 同时 264ms 回调空窗（真实硬件级停顿，非误报）

> **本节为更正版**。初版误判为"看门狗误报"，经核对 `daq_timing.csv` 硬件级数据后纠正。

**直接证据**：两份 `IncidentSnapshots/.../00-trigger-001-.../daq_timing.csv` 在同一 UTC 时刻精确记录了 Callback 行的回调间隔：

| 设备 | UTC 时刻 | 回调间隔 | EndRead | Rearm | 处理队列深度 | 时钟状态 |
|---|---|---:|---:|---:|---:|---|
| Dev1 | `2026-08-11T06:31:16.3113846Z` | **264.019ms** | 0.007ms | 0.025ms | 0 | Locked |
| Dev2 | `2026-08-11T06:31:16.3113846Z` | **264.179ms** | 0.002ms | 0.024ms | 0 | Locked |

关键判据：
- 两块设备在**完全相同的 UTC 时刻**同时跳到约 264ms，正常回调间隔仅 15–16ms
- `EndRead≈0ms`、`Rearm≈0ms`——不是 NI 读取或重新装填慢，而是回调本身未被调度
- 264ms 后回调自行恢复，积压的 27 个批次在 3ms 内连续交付
- 时钟仍为 `Locked`，采样率稳定在 2000.026Hz——不是硬件失锁

**结论**：两块 DAQ 硬件本身正常，但 NI 驱动回调线程或宿主进程在 14:31:16.047–14:31:16.311 期间经历了约 264ms 的调度停顿。双设备同时、同量级，指向**公共调度/驱动/进程级短暂停顿**（可能是 GC、Windows API 阻塞、NI 驱动内部锁或外部进程干扰）。

**为什么 incident.json 中的 `beforeCallbackAgeMs=11.216ms`？**

这是一个关键的**时序错位**：
- 264ms 空窗发生在 14:31:16.047–14:31:16.311（上次回调→本次回调）
- 周期内看门狗在空窗期间（约 14:31:15.795 上电后 100ms+）触发 `DaqSampleStale>100ms`
- 安全断电和高优先级 OFF 在 14:31:16.312 执行
- 恢复上下文（`incident.json`）在 14:31:16.302–14:31:16.368 期间建立快照
- 此时 264ms 空窗**已经结束**，回调已恢复，因此 `beforeCallbackAgeMs` 自然只有 11ms

初版分析将这个"恢复建立时"的新鲜度数据误读为"触发瞬间"的新鲜度，从而得出"误报"的错误结论。

**看门狗触发路径**：

周期内看门狗（`EpbAdaptiveControl.cs:556-577 CheckWatchdogReusable`）在 `WaitAdaptiveDecisionAsync`（`EpbCycleRunner.Adaptive.cs:1565-1601`）中每 20ms 轮询，检查 `_lastSampleTick`（控制路径上次更新时间）距今是否超过 100ms。在 264ms 空窗期间，控制路径无新样本到达，`_lastSampleTick` 停止更新，看门狗在 100ms 时正确触发。这是**正确的安全行为**。

**独立存活监督**（`EpbManager.DaqLiveness.cs`）同时在宿主定时器中检测到 `CallbackAge>100ms`，记录 `DAQ_LIVENESS Result=Trip`。这是第二道独立防线，同样正确触发。

**不能精确归因的事项**：GC ETW 因权限不足为 Access Denied，当前只能将首发来源定义为"双 DAQ 公共调度/驱动/进程级短暂停顿"，不能无证据精确归因到 CLR GC、Windows 某个 API、NI 驱动或外部进程。

### 3.2 不能自恢复的直接根因一：圈终态重新抓取动态边界

**代码位置**：`Controller/EpbManager.cs:758 TryWaitForCycleDurableCutoffAsync`

恢复事务在 `TryFinalizeDaqCutoffCyclesAfterPersistenceAsync`（`EpbManager.cs:3050`）中执行三个阶段：
1. 冻结后台/Raw 前缀闭合
2. SQLite 耐久前缀闭合
3. 受影响当前圈作废（`DiscardCurrentCycleForSoftwareRecovery`）

第 3 步通过 `DiscardCurrentCycleForSoftwareRecovery` → `AbortCycleAfterPersistence`（`EpbManager.WarningSnapshots.cs:718`）→ `FinalizeCyclePersistence`（`:692`）→ `TryWaitForCycleDurableCutoffAsync`（`EpbManager.cs:722`）。

**致命缺陷在第 758 行**：

```csharp
// TryWaitForCycleDurableCutoffAsync 内部
foreach (var device in devices)
{
    var boundary = _acq.GetLastDiskPublishedSequence(device);  // ← 重新抓取当前实时 Published！
    // ...
    if (!await _persistence.WaitForDurablePrefixAsync(
            device, boundary, remainingMs, token))  // ← 等待 Persisted 追上这个动态边界
    {
        return false;  // ← 永远 false
    }
}
```

恢复事务已经在第 1-2 步冻结了前缀边界 238368，但圈终态的通用流程在第 758 行**重新抓取**了当前实时的 `GetLastDiskPublishedSequence`。由于 DAQ 在恢复期间仍在产生新批次（这些批次被 `SuppressAfter=238368` 抑制，不物理写入，但 `Published` 序号仍在增长），这个动态 `boundary` 远大于冻结的 238368，`WaitForDurablePrefixAsync` 必然超时。

**日志精确佐证**（warning.log:102,106,110）：

```
14:31:26.480  软件恢复截止耐久前缀超时 Device=Dev1 Boundary=238380 Persisted=238368 ... Reason=CycleFinalize:30794
14:31:26.483  EPB[4] 正式圈落盘软件异常；保留圈事务并等待真实耐久收口。Cycle=30794 Error=圈收尾 Raw/耐久前缀未闭合。
14:31:30.749  软件恢复截止耐久前缀超时 Device=Dev2 Boundary=238796 Persisted=238357 ... Reason=CycleFinalize:31509
14:31:30.827  软件恢复截止耐久前缀超时 Device=Dev2 Boundary=238805 Persisted=238357 ... Reason=CycleFinalize:29906
```

- EPB4 圈 30794 的动态边界取到 238380（> SuppressAfter=238368），Persisted 固定在 238368
- EPB11 圈 31509 取到 238796（> SuppressAfter=238357），Persisted 固定在 238357
- EPB8 圈 29906 取到 238805，Persisted 固定在 238357

这些新边界都位于 `SuppressAfter` 之后，按当前数据语义不会物理写入。**恢复事务必须用已冻结前缀作废当前圈，不得在圈终态内部再抓取动态前缀。**

**复合 bool 掩盖了真实失败阶段**：

`TryFinalizeDaqCutoffCyclesAfterPersistenceAsync` 对三个阶段只返回一个 `bool`。上层对任何 `false` 都统一标记为 `DaqPersistenceBoundaryPending`（`EpbManager.cs:3430`），结构化 DAQ 水位虽已记录但未被用于区分失败阶段。因此日志文本"截止圈原始批次尚未真实落盘"与同一时刻的数值证据（`Persisted >= cutoff`、`Depth=0`、`State=Recovered`）矛盾——这实际上是圈终态失败，不是 SQLite 前缀未写入。

### 3.3 不能自恢复的直接根因二：StopAll 门禁要求动态最终边界等于冻结边界

这是第一节概述中提到的第二层缺陷，也是导致进程自重启交接全部失败的直接原因。

**冻结边界逻辑**（`EpbManager.cs:6800`）：

```csharp
// StopAll 继承 DAQ 恢复的冻结前缀
stopPersistenceBoundaries[device] = hasExistingSuppressedTail
    ? Math.Min(finalContinuousBoundary, existingSuppressionBoundary)  // = min(239001, 238368) = 238368
    : finalContinuousBoundary;
```

当 StopAll 接管一个尚未完成的 DAQ 恢复时，边界冻结在恢复登记时的 `existingSuppressionBoundary=238368`，而不是当前的 `LastAccepted=239001`。这是正确的设计意图——238368 之后的批次已被标记为非正式尾段，不应要求它们"重新出现"。

**闭合判定逻辑**（`EpbManager.FieldMetrics.cs:226-248`）：

```csharp
internal static bool IsFrozenStopPersistenceBoundaryClosed(
    long boundary, long finalBoundary, bool rawPipelineDrained,
    long published, long persisted, int queueDepth, ...)
    => rawPipelineDrained && finalBoundary == boundary &&  // ← 致命条件
       IsStopPersistenceBoundaryClosed(boundary, published, persisted, ...);
```

闭合要求 `finalBoundary == boundary`，即 `GetLastProcessRecycleBoundary(device) == 238368`。

**`GetLastProcessRecycleBoundary`**（`TwoDeviceAiAcquirer.cs:2208-2214`）返回**当前实时的 `LastAccepted`**。

**致命矛盾**：StopAll 为取得新鲜压力证据，在全输出已断能时会只读重建 DAQ 采集（warning.log:105,114,119,120,125,126,130,131）：

```
2026-08-11 14:31:27.998  液压协调  StopAll检测到液压组1压力证据陈旧；
  所有输出保持断能，已只恢复DAQ采样 Channels=[1,2,3,4,5,6]，现在重新确认新鲜压力。
```

DAQ 一旦恢复采样，`LastAccepted` 就会从 238368 持续增长到 239001→239537→240074→240611→241148…，而冻结边界 `boundary` 始终是 238368。`finalBoundary == boundary` 永远不可能为 true，闭合判定**确定性失败**。

**STOP_PERSISTENCE 数据佐证**：

|---|---|---:|---:|---:|---:|---:|---|
| 14:31:22 | Dev1 | 238368 | 239001 | 239001 | 238368 | 0 | **False** |
| 14:31:22 | Dev2 | 238357 | 238999 | 238999 | 238357 | 0 | **False** |
| 14:31:33 | Dev1 | 238368 | 239537 | 239537 | 238368 | 0 | **False** |
| 14:31:48 | Dev1 | 238368 | 240074 | 240074 | 238368 | 0 | **False** |
| 14:32:14 | Dev1 | 238368 | 240611 | 240611 | 238368 | 0 | **False** |

`Persisted=238368` 从 14:31:16 起到 14:32:24 **完全冻结不动**。注意：按 V2.12.0.31 自身定义的耐久前缀语义，上述状态其实已经满足闭合条件（`Persisted >= cutoff`、`Depth=0`、`State=Recovered`、`DurabilityBlocked=False`、截止后新批次已归入 `Suppressed/TerminallyHandled`）。**前缀已闭合，只是门禁不认。**

### 3.4 并发圈终态所有权竞争加速了升级

时序上，Attempt 1 在 14:31:17.312 已被立即判失败，但 EPB4 圈 30794 的动态耐久前缀直到 14:31:26.480 才超时（`CycleFinalize:30794` 耗时约 10s）。这表明至少有一个圈终态调用仍在后台等待，另一个恢复调用却已经将同一复合门禁判为失败并累加 Attempt。

`CutoffCyclesFinalized=1`（InProgress）时，后到调用会立即返回 `false`（`EpbManager.cs:3109-3110`），而不是等待同一个共享终态 Task。上层又把这个"别的所有者正在工作"解读为"耐久化失败"，因而在真实 10s 圈收尾等待结束前，仅用约 4.4s 就将 Attempt 推到 3 并打开整批熔断。

### 3.5 同进程恢复失败的直接代码路径

`PrepareForFreshRestartAsync`（`EpbManager.BatchStart.cs:187-235`）：

```csharp

// ...
if (!safety.CanRestartInProcess && !canDiscardHistoricalChecks)
{
    throw new InvalidOperationException(
        "重新开始清场未通过物理安全与软件逻辑不变量。");

```

`CanRestartInProcess`（`ChannelRuntimeState.cs:241`）：

```csharp

                                   !DataContinuityCompromised;
// FullyConfirmed = PhysicalSafetyConfirmed && PersistenceBoundaryConfirmed
```

`PersistenceBoundaryConfirmed=false`（因 3.2/3.3 节两层边界语义缺陷）→ `FullyConfirmed=false` → `CanRestartInProcess=false` → 抛异常 → 升级进程自重启。

`discardHistoricalStopChecks` 默认为 `false`，只有人工 UI 停止后显式传 `true` 才会跳过历史检查。无人值守恢复路径传入的是默认 `false`。

## 五、为何"运行没多久之后就停机"

本次运行 13:51:28 启动，14:31:16 停机，正式自主运行约 37 分 42 秒。

**首发原因是双 DAQ 同时出现约 264ms 的回调空窗**——两块设备在完全相同的时刻同时跳到约 264ms，正常回调间隔仅 15–16ms。`EndRead≈0ms`、`Rearm≈0ms`、时钟 `Locked`，排除了单块 DAQ 硬件损坏或硬件失锁的可能，指向公共调度/驱动/进程级短暂停顿。

GC ETW 因权限不足为 Access Denied，因此当前只能将首发来源定义为"双 DAQ 公共调度/驱动/进程级短暂停顿"，不能无证据精确归因到 CLR GC、Windows 某个 API、NI 驱动或外部进程。

这类停顿在长时间运行后概率增大（GC 堆碎片化、NI 驱动缓冲累积、Windows 线程调度随机性等），且回调随后自行恢复——**单次 264ms 空窗本身不应导致永久停机**。真正的问题是恢复链存在两层边界语义缺陷（第 3.2/3.3 节），使得任何一次此类停顿都会陷入确定性死锁并最终耗尽重启预算。

## 六、彻底解决方案

### 方案分为四层，按优先级实施

#### 第一层 P0：恢复事务必须统一使用冻结前缀（消除根因一，立即实施）

这是导致同进程恢复失败和 Attempt 快速耗尽的首要原因。

**修复 B0：圈终态作废必须使用恢复冻结边界，禁止重新抓取动态 Published**

`EpbManager.cs:758 TryWaitForCycleDurableCutoffAsync` 当前在第 758 行调用 `GetLastDiskPublishedSequence(device)` 获取动态实时边界。当本方法由 DAQ 恢复的"当前圈作废"路径调用时，必须改用恢复事务已冻结的边界：

```csharp
// 方案：为 TryWaitForCycleDurableCutoffAsync 增加可选的冻结边界参数
private async Task<bool> TryWaitForCycleDurableCutoffAsync(
    IReadOnlyDictionary<int, int> cycles,
    DateTime cutoffUtc,
    string reason,
    int timeoutMs,
    CancellationToken token,
    Func<bool> canMutate = null,
    IReadOnlyDictionary<string, long> frozenDeviceBoundaries = null)  // 新增
{
    // ...
    foreach (var device in devices)
    {
        // 优先使用恢复事务冻结的边界；没有冻结边界时才回退到动态 Published
        var boundary = frozenDeviceBoundaries != null &&
                       frozenDeviceBoundaries.TryGetValue(device, out var frozen)
            ? frozen
            : _acq.GetLastDiskPublishedSequence(device);
        // ...
    }
}
```

`DiscardCurrentCycleForSoftwareRecovery` → `AbortCycleAfterPersistence` → `FinalizeCyclePersistence` 整条调用链必须把恢复事务的 `context.CutoffPersistenceBoundary` 透传到 `TryWaitForCycleDurableCutoffAsync`，禁止在圈终态内部再抓取动态前缀。

**修复 B0b：复合阶段输出结构化结果**

`TryFinalizeDaqCutoffCyclesAfterPersistenceAsync` 应为每个阶段输出结构化结果（`BackgroundPrefix`、`PersistencePrefix`、`CycleTerminalization`、`OwnershipInProgress`），禁止全部写成 `DaqPersistenceBoundaryPending`。这样上层可以区分"前缀真的没落盘"和"圈终态所有权竞争"两种完全不同的情况。

**修复 B0c：圈终态并发调用必须共享结果**

`CutoffCyclesFinalized=InProgress` 时，后到调用必须等待同一个 Task/结果，不得立即返回 `false`（`EpbManager.cs:3109-3110`）。恢复 Attempt 只能在上一个终态事务真实失败或超时后增加，不得因"所有权已被同一事务占用"而增加。

#### 第二层 P0：StopAll 门禁必须认可有限/终态处理尾部（消除根因二，立即实施）

**修复 B1：闭合判定移除 `finalBoundary == boundary`**

`EpbManager.FieldMetrics.cs:226-248` 的 `IsFrozenStopPersistenceBoundaryClosed` 应改为证明冻结前缀已落盘 + 尾段已被抑制/终态处理：

```csharp
internal static bool IsFrozenStopPersistenceBoundaryClosed(
    long boundary, long finalBoundary, bool rawPipelineDrained,
    long published, long persisted, int queueDepth,
    DaqPersistenceState state = DaqPersistenceState.Recovered,
    bool requireRecoveredState = true,
    bool durabilityBlocked = false,
    long discardedGenerationBatchCount = 0,
    long overCapacityDroppedBatchCount = 0)
    => rawPipelineDrained &&
       // 关键修改：只要冻结前缀已真实落盘即可
       persisted >= boundary &&
       published >= boundary &&
       queueDepth == 0 &&
       !durabilityBlocked &&
       discardedGenerationBatchCount == 0 &&
       overCapacityDroppedBatchCount == 0 &&
       (!requireRecoveredState || state == DaqPersistenceState.Recovered);
```

理由：`finalBoundary > boundary` 是**正常的**——它代表恢复期间 DAQ 继续产生的被抑制尾段，这些尾段已被 `SuppressAfter` 明确排除，不应阻碍闭合。

**修复 B2：只读压力采集应切换到新 generation**

StopAll 为取得新鲜压力证据而只读重建 DAQ 采集时，新批次应切换到新 generation/新终态区间，**绝不得扩大旧 Run 的耐久前缀**。这样旧 Run 的 `LastAccepted` 不再增长，`finalBoundary` 对旧 Run 保持稳定。

#### 第三层 P0：双设备同时异常必须真正合并为单一批次恢复事务

**修复 D1：统一 BatchCorrelationId 去重**

两块 DAQ 的 264ms 记录来自完全相同的时刻，但事故快照显示 Dev1（CorrelationId=`d0e589a1...`，RecoveryEpoch=1）和 Dev2（CorrelationId=`1e02a94b...`，RecoveryEpoch=2）使用了不同的恢复上下文。应通过同一 `BatchCorrelationId` 去重，同一时窗的 Dev1/Dev2 异常只能有一个批次恢复所有者。

#### 第四层 P1：增强恢复韧性和减少触发频率

**修复 A1：减少 264ms 级调度停顿的发生概率**

虽然 264ms 停顿是真实事件而非误报，但它的来源（GC / Windows API / NI 驱动 / 外部进程）应进一步排查：
- 开启 GC ETW 监控（当前因权限不足为 Access Denied），确认是否为 Gen2 GC 导致的 STW
- 检查 NI 驱动版本和已知的回调延迟问题
- 排查是否有外部进程（杀毒软件、备份、索引服务）在故障时刻抢占 CPU
- 考虑将 NI 回调线程的优先级提升到 `ThreadPriority.AboveNormal` 或更高

**修复 A2：看门狗阈值的合理性评估**

当前周期内看门狗阈值为 100ms（`EpbAdaptiveControl.cs:576`），独立存活监督也为 100ms（`EpbManager.DaqLiveness.cs`）。对于 2kHz 采样（每 0.5ms 一个样本），100ms 意味着 200 个样本未到达即触发。这个阈值是否过于激进需要评估——如果 264ms 级停顿在生产环境中偶尔发生且回调总能自行恢复，可以考虑将阈值提高到 500ms 并增加确认次数，在安全性和可用性之间取得平衡。

**修复 C1：进程自重启交接在物理安全确认后即可放行**

当同进程恢复因边界语义缺陷失败时，进程自重启应**绕过持久化边界检查**，只要求物理安全（电机 DO + 程控电源已关闭）即可交接。进程重启本身就是"丢弃同进程状态、从检查点恢复"的手段：

```csharp
if (safety.CanReleaseAcquisition)  // 只要求 MotorOff + PowerOff
{
    await RestartAsync(reason, correlationId, fault?.RunId.ToString("N")).ConfigureAwait(false);
    return;
}
```

**修复 C2：增加重启预算并引入指数退避**

将 `UnattendedProcessRestartBudget` 从默认值提高到 5，重启间隔改为 5s/15s/30s/60s/120s 指数退避。配合 B0/B1 修复后，可以避免偶发抖动导致预算耗尽。

## 七、验证方法

1. **264ms 空窗恢复验证**：双 DAQ 在同一批次同时停顿 264ms，断能后回调自行恢复；必须只建立一个批次恢复事务，恢复前缀立即通过。

2. **圈终态冻结边界验证**：恢复当前圈作废时，后续 Published 持续增长；圈终态必须使用恢复冻结边界，不得从 Published 重新抓取新耐久边界（修复 B0）。

3. **StopAll 闭合验证**：StopAll 继承早期冻结边界，为新鲜压力只读重建 DAQ，FinalBoundary 持续增长；只要尾部全部终态处理，就必须允许安全进程交接（修复 B1）。

4. **并发终态共享验证**：恢复线程和圈 Finalizer 同时尝试结束同一圈；只能有一个终态所有者，其余调用等待同一结果，Attempt 不增加（修复 B0c）。

5. **端到端无人值守验证**：连续运行 24 小时以上，模拟周期性后台线程抖动（264ms 级），确认系统能自动恢复并继续运行，不出现重启预算耗尽。

## 十二、首发触发更正（初版误报结论的纠正）

### 12.1 初版结论（错误）

本文初版将首发触发判定为"自适应周期看门狗误报 `DaqSampleStale>100ms`"，依据是 `incident.json` 中的 `beforeCallbackAgeMs=11.216ms` 和 `reason` 字段中的 `CallbackAge=0.0ms`——所有真实新鲜度指标均远低于 100ms 阈值。

### 12.2 纠正依据

经核对 `IncidentSnapshots/.../00-trigger-001-.../daq_timing.csv` 中的硬件级 Callback 行数据：

| 设备 | UTC 时刻 | 回调间隔 | 时钟状态 |
|---|---|---:|---|
| Dev1 | `2026-08-11T06:31:16.3113846Z` | **264.019ms** | Locked |
| Dev2 | `2026-08-11T06:31:16.3113846Z` | **264.179ms** | Locked |

两块 DAQ 在**完全相同的 UTC 时刻**确实发生了约 264ms 的真实回调空窗。这是 NI 驱动回调线程级别的真实停顿，不是控制路径延迟误报。

### 12.3 初版误判原因

初版犯了**时序错位**的错误：
- 264ms 空窗发生在 14:31:16.047–14:31:16.311（上次回调→本次回调的实际间隔）
- 周期内看门狗在空窗期间触发 `DaqSampleStale>100ms`（14:31:15.795 上电后约 100ms+）
- 安全断电在 14:31:16.312 执行
- 恢复上下文 `incident.json` 在 14:31:16.302–14:31:16.368 建立快照
- **此时 264ms 空窗已经结束，回调已恢复**，因此 `beforeCallbackAgeMs` 自然只有 11ms

初版将"恢复建立时"的新鲜度数据误读为"触发瞬间"的新鲜度，从而得出"误报"的错误结论。

### 12.4 与 Codex 分析的对比

本事件有两份独立分析文档。经核对原始数据，**Codex 的分析在首发触发判定上是正确的**（264ms 真实空窗），本文初版的"误报"结论是错误的。两份分析在死锁根因（圈终态重新抓取动态边界 + StopAll 门禁要求 `finalBoundary == boundary`）上结论一致，但 Codex 额外识别出了：
1. `TryFinalizeDaqCutoffCyclesAfterPersistenceAsync` 返回单一 bool 掩盖了真实失败阶段（圈终态失败被误标为"前缀未落盘"）
2. 圈终态并发所有权竞争加速了 Attempt 耗尽
3. 双 DAQ 恢复未合并为单一批次事务

本文已根据 Codex 的分析纠正了首发触发结论并补充了上述深层根因。
