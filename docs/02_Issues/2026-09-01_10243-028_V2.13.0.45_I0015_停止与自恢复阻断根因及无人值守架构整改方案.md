## 1. 结论先行

本次不是单一“偶发报错”，而是三层故障串联：

1. **首发运行故障：Dev1 DAQ 回调停止更新。** 16:18:02.659，Dev1 回调年龄达到 264.7 ms，系统按安全策略切断 EPB4、5 当前圈；16:18:03.040 回调年龄继续扩大到 645.7 ms，而 Dev2 同时仍为 3.1 ms。现有封盘能够确认“Dev1 单设备采集停更”，但没有保存 NI 任务终态、驱动错误、线程栈或事故 Dump，不能进一步唯一判断是板卡/驱动、NI Task、回调链还是软件生命周期竞争。
2. **故障被放大为整批退出：当前圈安全边界未及时闭合。** EPB4 出现 `FormalSlotSafetyBoundaryFailed ... Persistence=False`，随后全局 StopAll。物理 DO OFF 实际成功，但回调停更又导致液压压力样本陈旧，组内恢复和全局停止并发叠加，产生大量重复 OFF、圈作废和 CTS 重复释放。
3. **最终不能自恢复的直接原因不是 DAQ，也不是硬件仍上电，而是恢复链存在两个确定性软件缺陷。** 独立 SafetyAgent 的程控电源 OFF 判定把“成功关闭后返回的 `false`”误判成失败；同时，主进程退出后没有把精确退出证据转化为 `LogicalQuiescent=true`。任一缺陷都足以阻止恢复，两者叠加使 V2.13.0.45 的这类进程级恢复事实上不可能成功。

因此，本次最终定性为：

> **Dev1 DAQ 单设备停更触发安全切断；正式槽/液压恢复/停止事务的耦合把局部故障升级为换进程；换进程恢复又被 SafetyAgent 布尔语义错误和逻辑静默证据缺口确定性阻断。**

设备安全侧总体有效：主程序完成了所有 EPB DO OFF、两路 AO/液压关闭、四组程控电源 OFF，最终压力和持久化也得到确认。Watchdog 在独立证据不足时拒绝重启，属于正确的 fail-closed；错误在于独立证明链自身永远无法成功。

“无人监控下一直稳健运行”不能定义为硬件损坏后仍强行续测。正确目标应是：

- 可恢复故障在有界时间内自动恢复并续测；
- 单通道/单设备故障尽量隔离，不拖垮无关通道；
- 不可恢复或安全证据不足时自动保持安全、远程报警，不进入无期限模糊状态；
- 任意进程崩溃、线程卡死、驱动停更或网络故障都不能绕过物理安全，也不能让恢复状态机把自己锁死。

## 4. 本次程序为什么停止

### 4.1 可以确定：Dev1 采集回调停更

事故前 16:18:01.031，Dev1 回调年龄只有 3.250 ms；事故后 16:18:03.040 已达到 645.689 ms。相同时间 Dev2 仍为 3.108 ms，说明不是整个进程、系统时钟或全局调度器同时停顿。

系统在 250 ms 新鲜度阈值处先切断正在动作的 EPB4、5，这是合理的安全动作。真正的问题是：切断之后没有立即形成一个由单一所有者管理的“Dev1 DAQ 隔离—重建—重新资格确认”事务，反而让以下流程同时继续：

- 当前圈 finalizer；
- 液压组恢复；
- 电源组失效安全联锁；
- 正式槽安全边界提交；
- 全局 StopAll；
- Timer/Runner/CTS 清理。

这使一个局部 DAQ 故障变成了全局状态竞争。

### 4.2 不能确定：Dev1 回调为何停更

封盘没有以下关键证据：

- Dev1 NI Task 的运行/停止/故障状态；
- `EveryNSamplesRead` 回调线程 ID、最后进入点和最后退出点；
- NI 缓冲区可读样本数、溢出计数和最后一次 DAQmx 错误；
- CLR GC pause、线程池饥饿和关键锁等待；
- 16:18:02 的进程 Dump；
- 板卡、总线、驱动或操作系统事件记录。

所以不能把首发停更唯一归因为“NI 硬件坏了”“驱动卡死”或某一把源码锁。现有证据只支持：Dev1 采集链停止推进，且通过 StopAll 中的重建能够恢复。

### 4.3 为什么局部故障升级为全局停止

EPB4 当前槽在断电、液压释放后仍未完成持久化边界，产生：

```text
FormalSlotSafetyBoundaryFailed Slot=1243 EPB=4
MotorOff=True HydraulicReleased=True Persistence=False
```

随后系统永久撤销当前进程上电授权，并把其他正式通道也升级为 `SystemFault`。这反映出 V2.13.0.45 仍把“一个正式槽成员未闭合”与“整批设备必须换进程”强耦合。

当前仓库在 V2.13.0.45 标签之后已经出现液压组隔离、作废圈封存和正式槽重入限制相关补丁，但这些提交晚于事故版本，而且仍未修复本报告第 5 节的两处恢复必败缺陷，不能据此宣布无人值守闭环已经完成。

## 5. 为什么最终不能自恢复

### 5.1 确定性缺陷一：OFF 成功返回值被反向解释

`PowerSupply.Core.PswTcpClient.SetOutputAsync(false)` 的契约是：

- 写入 `OUTP OFF`；
- 回读 `OUTP?`；
- 若实际状态与请求不一致则抛异常；
- 成功时返回实际输出状态，即 `false`。

测试代码也明确使用 `Assert.False(await client.SetOutputAsync(false))`，证明 `false` 是“输出已关闭”的成功值。

但独立安全代理的 `SafetyPowerOutputController.ConfirmAllOff` 使用了：

```csharp
if (!client.SetOutputAsync(false, timeout.Token).GetAwaiter().GetResult())
    return false;
```

当电源成功关闭时，`SetOutputAsync(false)` 返回 `false`，`!false` 为 `true`，函数立即返回失败。第一组电源成功关闭就会被判为 `SafetyPowerOffUnconfirmed`，后续电源甚至不再检查。

这不是偶发条件，而是确定性逻辑错误：**只要电源按协议正常返回 OFF，SafetyAgent 就必然报告失败。**

对应源码：

- `PowerSupply.Core/PswTcpClient.cs`：`SetOutputAsync`；
- `MTTFTest.SafetyHardware/SafetyHardware.cs`：`SafetyPowerOutputController.ConfirmAllOff`；
- `MTTFTest.SafetyAgent/SafetyAgentRunner.cs`：将 `false` 转为 `SafetyPowerOffUnconfirmed`。

这也解释了 V2.13.0.44 和本次 V2.13.0.45 都在 SafetyAgent 的同一阶段反复失败：不是两次现场电源同时出现相同偶发故障，而是相同代码路径每次都会失败。

### 5.2 确定性缺陷二：旧进程退出后，逻辑静默证据不会补齐

本次主程序安全结果为：

```text
MotorsOff=True
PowerOff=True
PressureSafe=True
PersistenceDrained=True
LogicalQuiescent=False
```

`LogicalQuiescent=False` 的直接运行证据是停止摘要仍显示 `Leases=1`。因此 Stop 结果正确选择 `SafeButRestartRequired`，要求由 Watchdog 换进程清场。

主程序随后创建 Safety Handoff，并把这个 `false` 原样写入回执。16:18:34.616，Watchdog 已精确证明旧 PID 22380 退出；此时旧进程的线程、回调和进程内租约实际上已经消失，但 Sidecar 没有用这一独立证据单调推进：

```text
OldProcessExitProven = true
LogicalQuiescent = true
CallbacksIsolated = true
HardwareResourcesReleased = true
```

恢复前置条件 `IsCompleteSafetyHandoffProof` 又明确要求 `LogicalQuiescent=true`。因此即使修正 5.1 的电源布尔错误，SafetyAgent 完成物理证明后仍会得到 `SafetyHandoffCompletedWithIncompleteSafetyEvidence`，恢复依然被拒绝。

这说明当前协议在语义上自相矛盾：

- 正因为主进程不能证明逻辑静默，才要求退出并换进程；
- 但退出后，独立监督者又不允许用“精确旧进程已死亡”补齐逻辑静默；
- 于是所有 `SafeButRestartRequired + GracefulHandoff` 场景都无法闭环。

### 5.3 “安全停止流程超时”是错误的界面翻译

截图显示恢复原因“安全停止流程超时”，但封盘记录为：

```text
StopTimedOut = false
StopStage = Completed
StopTerminalReason = Stop safety completed with restart required
```

源码 `DescribeRecoveryReason` 把所有以 `Stop` 开头的原因统一翻译成“安全停止流程超时”。本次实际含义是“物理安全完成，但逻辑未静默，需要更换进程”，不是 StopAll 硬超时。

错误文案会把排查方向引向“继续放大超时”，而真正应修的是逻辑静默交接和恢复证明链。

### 5.4 `UnhandledSoftwareStartup Count=2` 不是两次主程序启动失败

最终持久状态同时显示：

```text
RecoveryAttempt = 0
RelaunchGeneration = 1
RelaunchProcessId = 0
ConsecutiveStartupFailures = 2
```

即：没有新主程序被启动，计数却已经是 2。当前恢复授权把同一接管事务中的不同失败回执/阶段推进计入“连续启动失败”，导致名称、预算和实际动作不一致。

这不是本次 90 秒阻断的唯一原因，但会造成：

- 界面误称“启动失败”；
- 尚未真正尝试启动就提前消耗预算；
- 同一根故障被多个关联号重复计数；
- 现场无法区分“安全前置条件失败”和“新进程启动/附着失败”。

### 5.5 人工点击不是根因

操作员在 16:20:27 点击“停止自动恢复并退出软件”，发生在 16:20:04 自动恢复已经熔断之后。它只终止了一个已经失败的恢复会话，不导致 16:18:02 的 DAQ 停更，也不导致 SafetyAgent 的六次失败。

## 6. 为什么版本迭代很多次，仍然总会落到不能自恢复

问题不在“还少修一个 if”，而在研发和验证方法仍以事故补丁为中心，没有把无人值守当成一个可证明的系统属性。

### 6.1 恢复链新增很多，但没有完整端到端契约测试

SafetyAgent、持久许可、Closing Tombstone、Handoff Receipt、独立硬件证明分别都有单元测试，但缺少一条真实语义链：

```text
主程序故障
→ StopAll 返回 SafeButRestartRequired
→ 主程序退出
→ Sidecar 精确确认旧 PID 死亡
→ SafetyAgent 连接模拟电源并成功回读 OFF
→ 完整安全证明提交
→ 新主程序启动、附着、加载 checkpoint
→ 续测提交首个有效圈
```

如果存在这条测试，`SetOutputAsync(false)` 的布尔反转和 `LogicalQuiescent=false` 无法补齐都会立即暴露。

### 6.2 用弱类型 `bool` 表达方向命令，天然容易反转

`SetOutputAsync(false)` 同时包含“请求关闭”和“返回实际为关闭”两层 `false`，调用方很容易把它理解成失败。安全关键代码不应让一个裸 `bool` 同时承担命令参数、实际状态和操作结果三种语义。

### 6.3 状态很多，但所有权没有真正收敛

DAQ 安全切断、液压自愈、电源组联锁、正式槽终态、StopAll 和 Watchdog 都能升级状态、撤权和发起 OFF。每个局部模块单看都在“更安全”，组合后却产生重复清理、重复故障、重复预算消耗和互相否定的证据。

### 6.4 “失败安全”与“自动续测”没有分层验收

过去版本大量验证了“遇到异常会断电、不会冒险启动”，这保证了安全底线；但“断电后如何在证据完整时重新运行”是另一条独立功能链。把 fail-closed 通过等同于无人值守恢复通过，会得到“每次都能安全停住，但最终都需要人来”的系统。

### 6.5 发布不可追溯，现场问题无法和源码形成不可抵赖闭环

本次仍为 `PackageManifestMissing`。没有 Git commit、BuildUtc、全包文件哈希和配置哈希签名，自动化通过的源码与现场 EXE 之间缺少强身份绑定。只要发布流程不强制阻断这种包，任何“测试已经通过”都不能完整覆盖现场二进制。

### 6.6 放行标准仍以“回归用例通过”为主，而不是故障注入覆盖率

无人值守系统的核心不是正常路径用例数量，而是每个故障注入点最终都只能落入有限个、可审计的终态。若不在每个异步边界强杀、断网、停回调、延迟落盘，状态机缺口只会在现场逐个出现。

## 7. 完整解决方案

“完美方案”不是承诺永不出现新故障，而是通过架构和验证保证：新故障出现后，也不会变成无期限卡死、双进程、错误续测或无人可知的阻断。

### 7.1 P0：立即修复本次确定性阻断

#### P0-1 修复电源 OFF 契约，不保留裸布尔歧义

短期修复应删除错误的否定判断；`SetOutputAsync(false)` 成功返回后继续读取 snapshot，并以 `snapshot.OutputEnabled == false` 作为证明。

长期应改为结构化结果：

```csharp
PowerOutputCommandResult
{
    RequestedState,
    ObservedState,
    CommandAccepted,
    ReadbackVerified,
    SupplyId,
    Endpoint,
    FailureStage,
    ExceptionType,
    ElapsedMs
}
```

禁止安全代码继续使用 `if (!SetOutputAsync(false))` 这种双重否定。

#### P0-2 由 Sidecar 在旧进程精确退出后补齐独立逻辑静默证明

只有 Sidecar 有权推进这组字段，且必须满足精确 PID + StartUtcTicks 身份：

- `OldProcessExitProven=true`；
- `LogicalQuiescent=true`；
- `CallbacksIsolated=true`；
- `HardwareResourcesReleased=true`；
- 记录证据来源和单调 revision。

这不是绕过安全，而是用更强的进程外证据替代主进程无法完成的进程内证明。必须防止 PID 重用和回执回退。

#### P0-3 分开安全前置条件失败与主程序启动失败

至少拆为：

- `SafetyPrerequisiteFailure`；
- `MainProcessLaunchFailure`；
- `MainProcessAttachFailure`；
- `CheckpointResumeFailure`；
- `FirstCycleCommitFailure`。

只有真正启动过新进程并失败，才能增加 `ProcessRelaunchFailureCount`。同一 permit、operation、fingerprint 的重复回执必须幂等。

#### P0-4 修正 UI 根因链

过渡窗口同时显示三层原因：

```text
首发故障：Dev1DaqCallbackStale
停止结果：SafeButRestartRequired / LogicalQuiescent=False
恢复门禁：SafetyPowerOffUnconfirmed / SupplyId / FailureStage
```

不得再把所有 `Stop*` 原因翻译成“流程超时”。

#### P0-5 补齐 SafetyAgent 诊断

每次尝试必须持久化：电源组、IP/端口、连接、身份、写 OFF、第一次回读、二次回读、输出状态、异常类型、退出码、耗时。当前只有汇总码，无法区分协议错误、身份错误、网络不可达和程序逻辑错误。

#### P0-6 发布清单改为硬门禁

正式包缺少 package manifest、Git commit、BuildUtc 或文件哈希时，禁止标记为现场无人值守候选。诊断界面可以允许工程包运行，但必须永久显示“非受控包”，且不能签署长稳放行。

### 7.2 P1：把局部故障限制在最小故障域

按真实资源边界划分故障域：

- 单 EPB 通道；
- 单电源组；
- 单液压组；
- 单 DAQ 设备；
- 主进程；
- 整机/操作系统。

Dev1 DAQ 停更时，合理流程应为：

```text
冻结 Dev1 对应通道的新圈准入
→ 立即切断 Dev1 正在动作的 EPB
→ 把当前圈写为明确 aborted 终态
→ 保持 Dev2 无关组继续或进入短暂同步等待
→ 由唯一 DAQ Recovery Owner 重建 Dev1
→ 重新确认压力、零电流、回调连续性和配置身份
→ 只恢复受影响通道
→ 连续失败超过预算才升级进程级恢复
```

只有共享安全资源无法隔离、故障跨域或恢复证明失败时，才允许全局 StopAll。

### 7.3 P1：统一取消和资源生命周期

本次 4 个 `CyclePauseCts.CancelDispose` 重复释放说明清理所有权仍不唯一。建议：

- 每个 Timer/Runner/CTS 由一个生命周期对象独占；
- `Cancel`、`Dispose`、事件解绑、字典移除全部幂等；
- StopAll 只发布终止意图并等待 owner receipt，不直接跨模块重复 Dispose；
- 所有清理动作使用同一 transaction/operation id 去重；
- `ObjectDisposedException` 不应成为正常控制流，更不能污染故障定性。

### 7.4 P1：把圈终态与运行恢复解耦

当前圈无法形成完整数据边界时，不应无限等待，也不应阻止整个系统证明物理安全。应提供不可逆终态：

```text
Completed | Failed | AbortedByDaqLoss | AbortedBySafetyStop | DataIncomplete
```

每个终态必须包含最后完整 sequence、缺口范围、设备代次、原因和关联事务。物理安全、数据可审计、是否允许续测是三个独立结论，不能由一个 `Persistence=False` 同时代表。

### 7.5 P2：建立单一、持久、分层的无人值守状态机

建议系统级状态只允许以下迁移：

```text
Running
  → Degraded
  → Isolating
  → Safe
  → Recovering
  → Requalifying
  → Running

任意阶段失败
  → ProcessReplacement
  → Requalifying
  → Running

外部硬件持续不可用或证据损坏
  → SafeIdleAlarmed
```

每个状态必须具备：

- 唯一 owner；
- 单调 generation；
- 幂等 operation id；
- 进入时间、软期限和硬期限；
- 成功 receipt；
- 明确失败域；
- 下一合法状态；
- 远程报警策略。

不允许多个局部恢复器直接互相调用 StopAll 或修改全局状态，只能向系统恢复协调器提交事实和请求。

### 7.6 P2：独立安全监督应常驻，而不是故障后临时拼装

更稳健的结构是把 Sidecar/SafetyAgent 作为开机自启动的 Windows Service：

- 主程序只持有短租约；租约过期硬件进入断能；
- Service 长期持有唯一恢复授权和持久日志；
- 主程序崩溃后 Service 无需重新装载大量依赖即可执行最小安全闭包；
- 服务先确认 DO/AO/电源/压力，再决定是否拉起主程序；
- 主程序恢复后必须重新通过配置身份、硬件资格和 checkpoint 一致性检查。

对于真正安全关键的无人值守，还应使用独立硬件看门狗、失电释放继电器或安全 PLC。Windows 进程不能成为唯一物理安全层。

### 7.7 P2：建立远程可观测和人工接管通道

“无人值守”不等于“无人知晓”。进入 `SafeIdleAlarmed` 时必须：

- 本地持续声光报警；
- 远程发送 P0 告警；
- 自动封盘最近日志、状态机、配置、Dump 和硬件探针；
- 给出可执行的现场处置项；
- 禁止通过删除证据文件或手改计数恢复。

物理硬件持续故障时，系统应安全等待维修，而不是为了“持续运行”循环上电。

## 8. 必须新增的自动化和故障注入

### 8.1 一条不可拆分的端到端恢复测试

使用真实 Watchdog、真实 SafetyAgent 进程、模拟 NI 后端和模拟 SCPI 电源，验证：

1. 主程序进入 `SafeButRestartRequired`；
2. 精确旧进程退出；
3. 四组模拟电源 `OUTP OFF` 回读 `0`；
4. Sidecar 补齐逻辑静默；
5. 安全证明完整提交；
6. 新主程序只启动一次；
7. checkpoint 恢复；
8. 首个正式圈提交；
9. 重启预算只增加真实失败次数。

这条测试不通过，任何版本都不得宣称具备无人值守自恢复能力。

### 8.2 SafetyAgent 契约测试

至少覆盖：

- `OUTP OFF` 回读 `0`：成功；
- 回读 `1`：明确 `ObservedOn`；
- 连接超时：明确具体 Supply；
- 身份未验证：禁止写入；
- 第一组成功、第二组失败：保留逐组结果；
- 旧进程已退出但原 `LogicalQuiescent=false`：Sidecar 可用独立证据补齐；
- PID 被复用：拒绝补齐；
- 回执损坏/回退：fail-closed；
- SafetyAgent 在每个阶段被强杀：下一进程幂等继续。

### 8.3 DAQ 故障注入矩阵

对 Dev1、Dev2 分别注入：

- 回调停更 260 ms、1.5 s、5 s；
- 回调仍在但处理队列停滞；
- NI `-200279`；
- Task 意外停止；
- 回调内异常；
- 设备拔出/恢复；
- GC pause、线程池饥饿、磁盘慢写；
- 故障恰好发生在上电、峰值断电、反向释放、圈落盘和暂停边界。

每个注入必须验证故障域、DO OFF 时限、作废圈、重建次数、续测通道和最终状态。

### 8.4 进程级 Chaos 测试

在以下每个持久写入和等待点前后强杀主程序、Sidecar、SafetyAgent：

- permit 预留；
- closing tombstone；
- DO/AO/电源/压力阶段回执；
- 旧 PID 退出证明；
- main launch intent；
- attach；
- checkpoint commit；
- 恢复后首圈 commit。

期望终态只能是 `Running` 或 `SafeIdleAlarmed`，不得出现无限中间态、双主进程、双有效 permit 或无 owner 状态。

## 9. 无人值守放行指标

以下为建议的工程放行线，最终数值需由机械、电气和安全负责人确认：

| 指标 | 建议门槛 |
| --- | --- |
| 新鲜数据丢失后的活动 EPB 断电 | 绝对上限 500 ms，并记录实际 p99 |
| 健康硬件下独立安全证明 | 30 s 内完成 |
| 可恢复故障到恢复续测首圈 | 180 s 内完成 |
| 同一故障事务的新主进程数量 | 任一时刻最多 1 个 |
| 同一 operation 对预算的消耗 | 最多 1 次 |
| 恢复中间态最长停留 | 每个状态有硬期限，超时自动转 `SafeIdleAlarmed` |
| 远程 P0 告警 | 进入不可自动恢复终态后 30 s 内送达 |
| 数据完整性 | 无 completed 圈缺口；不完整圈必须显式 aborted/data-incomplete |
| 发布身份 | 100% manifest、commit、build time、文件哈希可验证 |
| 长稳 | 先 24 h，再 72 h，最终 168 h；期间持续注入可恢复故障且无需现场人工操作 |
| 不可恢复硬件故障 | 必须保持安全并报警，不以“继续运行”为验收目标 |

168 小时不能只跑正常路径。至少每小时自动注入一种可恢复故障，并核对恢复事务、预算、完成圈连续性和资源趋势。

## 10. 实施顺序与版本策略

### 阶段 A：阻断错误版本继续扩散

- V2.13.0.45：NO-GO，不可作为无人值守版本；
- 当前 V2.13.0.46：虽包含事故后的隔离/正式槽补丁，但上述两处恢复必败缺陷仍存在时，同样不能直接放行；
- 暂停用继续增加超时、扩大阈值或隐藏报警的方式迭代。

### 阶段 B：一个版本只闭合恢复协议

先完成 P0-1～P0-6 和完整进程级端到端测试。该版本只验证“任何 Stop/Crash 都能进入 Running 或 SafeIdleAlarmed”，不混入新的控制算法调整。

### 阶段 C：一个版本完成故障域隔离

完成 Dev1/Dev2、液压组、电源组和单通道的最小故障域恢复，并通过 DAQ 故障注入矩阵。

完成 Windows Service/硬件看门狗、远程告警、受控发布和 24/72/168 小时带故障注入长稳后，才能签署正式 GO。

任何阶段发现新问题都应增加对应故障模型和永久回归，不允许只补现场出现的那一条日志分支。

## 12. 最终回答

### 12.1 此次为什么停

Dev1 DAQ 回调在 EPB4、5 正式动作期间停止推进，系统正确切断电机；随后压力样本因同一采集停更而陈旧，当前正式槽数据边界又未及时闭合，局部故障被升级为全局安全停止和换进程。

### 12.2 此次为什么不能自恢复

不是现场电源一定没有关闭。主程序已经多次记录四组电源 OFF。真正的直接阻断是：

1. SafetyAgent 把 `SetOutputAsync(false)` 成功返回的 `false` 错当成失败，导致 `SafetyPowerOffUnconfirmed` 必然发生；
2. 换进程场景原本就是为了解决 `LogicalQuiescent=false`，但旧进程精确退出后 Sidecar 没有补齐逻辑静默证明；即使电源判断修好，恢复门禁仍然失败。

### 12.3 为什么总是修不完

因为过去主要是在补“上一次事故的分支”，而不是用端到端状态机、强类型契约、故障域隔离、进程级 Chaos 和受控发布去证明无人值守属性。单元模块越多，如果契约没有贯通，反而会产生更多互相否定的安全证据。

### 12.4 达到最终目的的方案

先修复两处确定性恢复缺陷并建立不可拆分的端到端恢复门禁；再把 DAQ、液压、电源和通道故障限制在最小故障域；最后以常驻独立监督服务、硬件失效安全、远程告警和 168 小时带故障注入长稳作为放行条件。

最终目标不是“永远不报错”，而是：

> **任何错误都能在有界时间内自动收敛到继续运行或安全告警；不会无限卡住，不会错误上电，不会丢失可审计数据，也不会需要等现场再次复现后才知道该修什么。**
