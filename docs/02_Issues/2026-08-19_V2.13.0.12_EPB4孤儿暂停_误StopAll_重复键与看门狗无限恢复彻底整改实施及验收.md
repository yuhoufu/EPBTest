## 1. 交付结论

V2.13.0.12 已对文档中的三类现场问题形成闭环，不再依赖延长超时或人工重启：

1. 旧 Timer 的迟到 `Paused` 事件不能再覆盖 `Recovering`，EPB4 不会再形成“界面暂停、但 Timer/Runner 均不存在”的孤儿状态。
2. 正常活动圈与软件恢复对象已经彻底分离。五个健康卡钳运行时为 `ActiveCycleCount=5、SoftwareRecoveryCount=0`，不会再假报 `RecoveryActive`，因此不会触发 `ExternalRecoveryStageStalled -> RequestStopAll`。
3. 看门狗会反向校验恢复遥测结构。即使主程序错误声称 `RecoveryActive=true`，只要没有 owner、stage、incident 等恢复身份且机械进度健康，也只会记录协议矛盾并请求刷新，不会直接全局停机。
4. 停机后的恢复失败按确定性、瞬态基础设施和未知软件异常分类。确定性失败立即进入持久 `RecoveryBlocked`；同一失败指纹达到有限预算后也进入终态。终态后 sidecar 重启仍保留阻断，且任何 `CircuitProbe` 都不能再启动主程序。
5. `EpbRecords` 已从公开可变 `List` 改为线程安全、按 Id 唯一的集合；启动使用原子 `StartPlan` 快照。并发或恶意重复插入也无法再制造重复键启动异常。
6. sidecar 新增跨层不变量：授权通道缺少 Timer/Runner，或 `Paused` 没有人工暂停 owner，持续 5 秒即识别并接管，不再因其他通道仍有心跳而漏掉单通道孤儿。

本次解决的是 DAQ 空窗之后的软件失控链。Dev1 回调为何在现场出现 1.172 秒空窗，仍需 NI/ETW/设备端口 A/B 证据才能判定为驱动、设备、总线或系统调度原因；现有数据不足以诚实地给出唯一硬件根因。无论底层诱因是什么，V2.13.0.12 都应做到安全断电、恢复对象不丢失、失败有界且不无限拉起进程。

## 2. 问题 2“所有卡钳停机”的触发原因及修复

### 2.1 触发链

V2.13.0.11 最后一份健康心跳中，五个通道均为 `Running`，恢复 owner/stage/incident 全为空，但同时出现：

```text
Active normal channels = 5
SoftwareRecoveryCount = 5
RecoveryActive = true
```

直接原因是 `_currentCycleNumberByChannel.Count` 被错误加入 `SoftwareRecoveryCount`。旧 sidecar 只观察“恢复对象数量”是否变化；五个通道持续运行时字典数量一直是 5，于是 15 秒后被误判为恢复停滞：

```text
健康正式运行
  -> 活动圈错误计入软件恢复数
  -> 假 RecoveryActive
  -> 恢复签名数量长期不变
  -> ExternalRecoveryStageStalled
  -> Watchdog RequestStopAll
  -> 所有卡钳安全断电
```

这就是问题 2 中所有卡钳一起停机的高置信软件触发，不是五个卡钳同时硬件损坏。封存数据截止于 11:50:46，缺少约 11:51 的原始 `TakeoverRequested` journal；因此现场事件原文仍需找回才能把证据等级从高置信提升为完全确认，但错误心跳、旧策略和全局停止路径已经形成闭合机制证据。

### 2.2 V2.13.0.12 的双层防线

主程序侧：

- `SoftwareRecoveryCount` 只统计具有恢复语义的 owner、协调任务和恢复上下文；
- `_currentCycleNumberByChannel.Count` 只进入新增的 `ActiveCycleCount`；
- `RecoveryActive=true` 必须有 owner 或结构化恢复生命周期/身份，单独一个原始计数不再成立；
- 逻辑静止判定同时检查 `ActiveCycleCount`，避免遗漏仍在执行的机械圈。

sidecar 侧：

- 检测 `RecoveryActive=true` 但 owner、stage、incident、context 全为空的非结构化声明；
- 记录 `RecoveryTelemetryInconsistent` 并发出一次状态刷新；
- 在机械进度正常时禁止把这种矛盾升级为 `ExternalRecoveryStageStalled` 和全局 `RequestStopAll`。

因此即使未来主程序某个新缺陷再次生成错误恢复布尔值，也不会重现本次误停全部卡钳。

## 3. EPB4 孤儿暂停整改

### 3.1 Timer 实例、代次和 RunEpoch 栅栏

[EpbManager.TimerRuntimeHealth.cs](../../Controller/EpbManager.TimerRuntimeHealth.cs) 现在为每次 Timer 激活登记：

- Timer 实例；
- 单调 `TimerGeneration`；
- 当前 `RunEpoch`；
- 可注销的实际事件 delegate。

移除 Timer 时先解除对应 delegate，再停止资源。任何迟到事件必须同时满足“仍是当前实例、观察登记一致、代次一致、RunEpoch 一致”，否则仅记录 `StaleTimerEventIgnored`，不允许改变通道状态。

### 3.2 中央状态转换门禁

[EpbManager.cs](../../Controller/EpbManager.cs) 在统一状态发布入口禁止：

```text
Recovering -> Paused/PausePending
且不存在有效人工暂停 owner
```

被拒绝的转换记录 `ChannelRuntimeTransitionRejected`。人工 `PauseChannel` 会建立 `_channelPausedUtc`，人工 `ResumeChannel` 会移除它；程序自愈不再冒充人工暂停。

### 3.3 冻结恢复 cohort

[EpbManager.RecoveryCoordination.cs](../../Controller/EpbManager.RecoveryCoordination.cs) 将故障发生时的通道集合视为冻结事务 cohort。后续迟到 UI 状态不再把成员剔除：

- `[EPB4, EPB5]` 冻结后，即使 EPB4 迟到显示 `Paused`、EPB5 仍为 `Running`，两者仍属于本次恢复事务；
- 只排除 `NotEnabled`、`AlarmStopped`、`InterlockStopped`、`ManualStopped`、`Completed`、`StartBlocked` 等耐久终态和明确人工暂停通道；
- 不再发生“只恢复 EPB5、永久丢失 EPB4”。

### 3.4 sidecar 兜底不变量

[WatchdogPolicy.cs](../../Watchdog.Protocol/WatchdogPolicy.cs) 对每通道持续跟踪：

- `Paused` 但没有人工暂停 owner：5 秒后触发 `ChannelPausedWithoutManualOwner`；
- 应运行通道没有当前 Timer/Runner：5 秒后触发 `ChannelExpectedRuntimeMissing`；
- 人工暂停命令明确存在时不误接管。

这使监督对象从“主进程有没有心跳”提升为“每个授权通道的业务状态和运行资源是否一致”。

## 4. 看门狗无限恢复整改

### 4.1 结构化失败与有限预算

协议新增：

```text
RecoveryFailureCode
RecoveryFailurePermanent
RecoveryFailureDetail
RecoveryFailureContextSha256
```

[WatchdogPolicy.cs](../../Watchdog.Protocol/WatchdogPolicy.cs) 的分类与预算为：

| 类型 | 典型错误 | 主程序自动重启上限 |
|---|---|---:|
| 确定性/永久性 | 重复/非法配置、checkpoint 不变量、包校验错误 | 0 |
| 瞬态基础设施 | 临时设备或通信不可用 | 同一指纹最多 5 次 |
| 未分类软件异常 | 启动异常、未知程序错误 | 同一指纹最多 2 次 |

恢复主程序会把完整异常、失败分类和项目 `TestConfig.xml` SHA-256 上报给 sidecar；checkpoint 拒绝明确标记为永久 `CheckpointInvariant`。

### 4.2 持久 RecoveryBlocked

[WatchdogHost.cs](../../MTTFTest.Watchdog/WatchdogHost.cs) 将以下字段写入 session journal：

- 是否 `RecoveryBlocked`；
- failure code、永久标志、detail、fingerprint；
- 首次/末次失败时间；
- 同指纹连续失败次数和最大预算。

sidecar 启动时会恢复同一 session 的既有阻断和预算，不再因 sidecar 自身重启而清零。进入阻断后：

1. 输出保持 OFF；
2. 界面明确显示恢复已阻断且“不会再启动主程序”；
3. `BeginTakeover`、退出后重拉、退避循环、退避结束和 `Process.Start` 锁内均再次检查阻断；
4. 不再存在 `ScheduleCircuitProbe`，也不存在 `RelaunchLoopAsync("CircuitProbe", ...)`；
5. `AllowsMainProcessCircuitProbe=false`，硬件低频探测不能通过启动整个 `MTTFTest.exe` 实现。

这不是“把间隔改长”，而是把永久故障从无限循环改成真正的终态。

## 5. 重复键启动失败整改

新增 [EpbTestRecordCollection.cs](../../Config/EpbTestRecordCollection.cs)，并将 `TestConfig.EpbRecords` 改为只读引用的线程安全唯一集合：

- Id 是唯一键，重复 `Add/Replace` 在集合内部合并，不产生第二项；
- `EpbTestRecord.Id` 的 setter 收紧为程序集内部，UI 不能随意改键；
- 枚举返回快照，避免 UI、保存和启动并发修改；
- 加载时保留原始节点用于重复/非法 Id 诊断，随后一次性替换为唯一集合；
- 保存仍执行唯一性归一化和原子文件边界；
- `CreateEpbStartPlan()` 在锁内验证精确的 Id 1..12，并返回新的字典快照；
- UI 批量刷新使用 `ReplaceAll`，监控器和 Controller 启动统一消费原子 StartPlan。

测试额外注入 128 路并发恶意重复记录，最终集合和启动计划仍保持 12 个唯一通道。因此现场的 `Dictionary.Add` 重复键失败不再有可达数据路径。

### 9.2 必做故障注入

EPB4/5 同组运行且处于正式圈时，分别注入 Dev1 回调空窗 120ms、1.2s、3.5s：

- 样本年龄超过 100ms 后，受影响通道高优先级 OFF 在 150ms 内提交；

- 30 秒内恢复成功，或进入明确 `RecoveryBlocked`；
- 进入阻断后观察至少 30 分钟，新增主程序 PID 必须为 0；
- 连续注入 100 次后 Timer/Runner/CTS/owner/lease/participant 回到基线。

另需注入：重复 EPB 配置、损坏 checkpoint、包哈希错误、主进程提前退出、瞬态设备不可用、人工暂停和人工停止。永久错误必须立即阻断，瞬态同指纹不超过 5 次，未知软件错误不超过 2 次。

- 72 小时或 100,000 机械圈取先到者，再连续运行 24 小时；
- `OrphanPaused=0`；
- `RecoveryTelemetryInconsistent` 若出现必须能解释并且不能伴随误 `RequestStopAll`；
- `RecoveryOwnerLeak=0`、`DuplicateEpbIdAtStart=0`；
- 同一永久 fingerprint 新增恢复 PID=0；
- 每次 StopAll 的 MotorDO、Power、Pressure、Persistence、Logical 均有明确终态；
- RunId/RunEpoch、机械圈和正式证据圈连续且事故圈只作废一次。

上述实机和长稳结果尚未在本次代码提交中执行。任何一项失败都不得只通过增加超时或重试次数放行。

## 10. 现场日志判据

V2.13.0.12 重点检索以下事件：

| 事件 | 含义 | 验收期望 |
|---|---|---|
| `StaleTimerEventIgnored` | 旧 Timer 迟到事件被拒绝 | 可出现；不得随后覆盖业务状态 |
| `ChannelRuntimeTransitionRejected` | 非法恢复到暂停被中央门禁拒绝 | 可出现；通道继续恢复或安全阻断 |
| `ChannelPausedWithoutManualOwner` | sidecar 发现孤儿暂停 | 故障注入可出现；正常长稳为 0 |
| `ChannelExpectedRuntimeMissing` | 授权通道缺少 Timer/Runner | 故障注入可出现；正常长稳为 0 |
| `RecoveryTelemetryInconsistent` | 恢复布尔值与结构化身份矛盾 | 正常长稳为 0；出现时不得误 StopAll |
| `RecoveryProcessLaunchSuppressed` | 阻断或会话撤权拒绝启动进程 | `RecoveryBlocked` 后必须出现或保持无启动 |
| `RecoveryBlocked`/失败 fingerprint | 自动恢复进入耐久终态 | 永久故障必须稳定保持 |
