# V2.16.0.0 I0037：运行故障、监控子窗口关闭返回、主程序 30 秒退出——根因与整改方案

日期：2026-09-05。阶段：封盘取证、源码分析与缺陷复现；尚未实施本轮生产代码修复。

## 1. 结论与问题边界

**I0037 已证明 V2.16.0.0 没有达到现场稳定运行要求。当前版本不能标记“彻底解决”，此前构建和自动化测试通过的结论，也不能代替这次失败的现场结果。**

本轮找到了可在本机复现的软件缺陷：活动圈收到不连续的 DAQ 批次后，写盘器正确拒绝不完整数据，但上层把这个确定性错误当成临时存储错误，不断重试同一批次。采样恢复正常也无法解除落盘阻塞，继而触发恢复竞争、正式圈收尾失败和全局停止。

按用户明确纠正，下面三个问题分别立项。B、C 有共用收尾代码，但不是同一个问题，不能用一个问题的修复或测试替代另一个。

### 3.2 序号缺口从哪里来：V2.15 改进与 V2.14 写盘契约没有配套

源码路径：

1. `Controller/EpbManager.cs:9296` 的 `IsDaqDeviceControlActive` 只检查 `_energizedChannelsMask`。**电机此刻未带电，不等于正式圈已结束，也不等于不需要保存本圈原始数据。**
2. `IO.NI/TwoDeviceAiAcquirer.cs:3435` 计算 `dropStaleBatch = !deviceControlActive && (staleSample || backlogPresent)`。
3. 回调已经分配批次序号；同文件 `3619` 又用 `!dropStaleBatch` 控制是否进入原始数据处理/落盘链。被判为“未带电时陈旧”的批次，从控制和原始持久化两条路径一起消失。
4. `DataOperation/EpbDiskWriter.cs:1602` 要求活动圈 `sequence == lastSequence + 1`，遇到跳号抛出 `InvalidDataException`。
5. `Controller/DaqPersistenceCoordinator.cs:854` 的 `WriteWithRetry` 没有把序号完整性错误独立分类，而是进入通用重试；10000 ms 后发布 Failed，却仍保留当前批次继续尝试。

与 `2.14.2.11` 比较：新增了采集端的 `dropStaleBatch` 及原始数据入队条件；`EpbDiskWriter.cs` 和 `DaqPersistenceCoordinator.cs` 与该基线没有差异。**这属于引入采集改进时未同步处理下游数据契约的兼容缺陷。** “控制不可用”可以拒绝参与上电判断，但不能据此无声删除仍属于正式圈的原始批次。

证据强度分开说明：序号跳变、写盘长期阻塞及源码中的上述缺陷已经确认；I0037 没有保存每一个被丢弃批次的完整决策记录，不能声称已经逐批证明 12 个缺失批次各自经过了哪一个分支。采集入口到正式圈提交的故障注入测试仍需补齐。129 ms 空窗本身的最底层触发因素也仍待取证。

### 3.4 EPB5 为什么显示“启动受阻”

`EpbManager.WarningSnapshots.cs:1159` 在正式圈落盘失败后启动 `ScheduleIsolatedInfrastructureRecovery`。后者在 `EpbManager.RecoveryCoordination.cs:1303` 再申请独立恢复事务。

此时 EPB5 已被 DAQ 恢复提交为系统故障终态。新的发布调用未显式授予从该终态重入的权限；`ChannelRuntimeStateStore.Publish` 保留锁存终态，而 `IsRecoveryContractPublished` 要求所有通道已经处于与新 owner 完全匹配的 Recovering。校验失败后，协调器补偿分支把通道发布为 `StartBlocked / RecoveryContractRegistrationFailed`。

这条时间线与代码条件一致，但注册异常没有逐字段输出 state/contract 差异；是否同时夹杂其他 owner 竞争，需要下面的交叉故障测试确认。不能通过删除校验或无条件开启 `allowTerminalReset` 修复。

整改要求：同一设备的 DAQ 完整性事件、正式圈收尾异常必须归并到同一恢复事务；新的故障信息追加为子原因。恢复 owner 的转交应由旧 owner 提交明确终态、CAS 校验与新 owner 接收完成。人工停止、永久报警和旧 epoch 均不可被借机重新授权。正式阶段的恢复失败应显示“数据恢复失败/等待恢复”，保留首因，而不是误称“启动受阻”。

### 3.5 为什么上次测试通过仍然漏了

现有测试覆盖了慢盘、瞬时异常、队列容量、边界等待、单项恢复契约等，但缺少本次组合：

`正式圈仍开放 → 电机暂时 OFF → 采集时间抖动 → 原始批次被跳过 → 真实序号写盘器拒绝 → DAQ 恢复与正式圈恢复并发 → 停止/关闭`。

例如 `DaqPersistenceCoordinatorTests.DiskPauseMatrixRemainsBoundedAndRecovers` 使用 BlockingRecorder 模拟耗时，不能检验真实 writer 的连续序列约束。之前报告中的测试数量应继续作为历史执行记录保留；本次必须补生产链路的组合测试，不能再用数量推断现场闭环已经成立。

## 4. 问题 B：监控子窗口关闭后返回（独立问题）

### 4.1 现场证据

| 时间 | 子窗口观察/日志 |
|---|---|
| 16:51:23.742 | 停止命令 `efd48034456448abb09e956e928acd6d` 已接收，随后开始收尾 |
| 16:51:35 | 截图 1：监控关闭遮罩，等待液压卸压和压力确认 |
| 16:51:49 | 截图 2：停止事务仍在收口，等待数据边界 |
| 16:51:53.304 | `ui-info.log:150`：数据耐久边界仍未确认 |
| 16:51:57 / 16:52:10 | 截图 5/6：原监控界面再次可见，通道显示人工停止 |

不能把 16:52:11 以后的主程序退出倒计时放进这次子窗口关闭耗时里。现有日志没有独立、完整的“点击子窗口 X”事件，因此不虚构该点击的毫秒级起点。

### 4.2 直接根因：关闭失败后主动恢复了界面

- `FrmEpbMainMonitor.cs:3039` 首次 FormClosing 设 `e.Cancel=true`，启动异步关闭准备。
- `PrepareAndFinalizeMonitorCloseAsync` 在 `CanCloseApplication=false` 时显示数据未保存信息并返回 false（约 `3223`）。
- `BeginMonitorCloseSequence` 随即执行 `HideCloseOverlay()`，清空 `_isClosing`、`_formClosedFlag`、`_closingReentry`，将生命周期恢复为 Running/Idle（`3054`）。
- 所以这不是 Windows 重新打开窗口，而是程序取消关闭后又恢复了原界面。
- `FrmEpbMainMonitor.CloseOverlay.cs:109` 将停止阶段结束映射到 100%；停止尝试结束并不等于窗口已关闭，也不等于所有等待项成功，因此进度表达也有误导。

### 4.3 正确方案

1. 引入明确的 **CloseMonitorView** 意图；子窗口生命周期只能从 Open → CloseRequested → Closing → Closed 单向前进。失败或等待状态不能隐式返回 Running/Idle。
2. 将试验运行时和收尾任务的所有权提升到主程序/运行时宿主，子窗口只持有显示订阅。子窗口关闭后，必要的断能、证据归档仍有确定的负责人；不能因 Form.Dispose 一并销毁仍在执行的 worker。
3. 用户关闭监控子窗口后，保持停止意图、不自动续试。主程序保留待机界面及明确的后台收尾状态；只有用户再次打开监控入口才能重新显示监控窗口。
4. 子窗口快速响应目标：点击后 100 ms 内反馈，**1 秒内完成关闭或转到主程序的明确收尾状态**。这是子窗口目标，不替代第 5 节对主进程 5 秒退出的要求。
5. 保留一个可以等待的关闭任务；重复点 X 加入同一任务。主程序退出可以等待/升级它的意图，但不再次独立启动收尾。
6. 进度条只展示实际阶段和等待项；未完成时不显示“100% 已完成”。若运行时所有权接收失败，应留在明确的“关闭受阻”状态，不恢复普通监控操作。

### 5.2 旧进程的关闭记录阻塞了本次人工关闭

当前会话仍有 `.closing.json`：

| 字段 | 留存记录 | 本次人工停止/关闭 |
|---|---|---|
| SessionId / Generation / Lease | `0ccbc... / 1 / 1` | 相同 |
| 意图 | `WatchdogCrashRecovery` | 人工停止、关闭监控、关闭主程序 |
| 进程 | OldProcessId=21412 | PID 21708 |
| StopSafetyTransactionId | `1a66431c475d4423aa8a17a5bde1c194` | 16:51 人工停止事务为 `966f6c7d98394a1c926767777b3fc181` |
| StopRunId / Epoch | `UnknownRun / 4` | 人工停止日志为 Guid.Empty / 7，后续重复关闭又推进 epoch |

`WatchdogRuntime.cs:3416` 不仅检查 session 身份，还通过 `IsCompatibleClosingTransaction`（`3737`）比较停止事务、运行 epoch 和安全边界。旧关闭记录未完成退休，恢复后的新进程沿用同一会话，新的停止事务因此被拒绝。

日志 `DurableCloseFenceIdentityChanged` 却只列出 session/generation/lease，省略真正冲突的事务字段，所以看起来“所有身份都一样还报错”。这与之前的 JSON 哈希规范化缺陷不是一回事，必须修复事务生命周期并补充逐字段诊断，不能取消身份校验。

主程序退出回执还绑定到了上述旧 StopSafetyTransactionId，说明除了诊断不清楚，退出证据的事务归属也需要校正。

### 5.3 其他已定位的耗时与重复工作

- `FrmEpbMainMonitor.cs:3127` 等人工停止任务 15 秒后仍继续无期限 await；该 15 秒仅改变显示，并不保证退出。
- `PrepareForMainApplicationExitAsync` 即使 `_closingReentry` 已经置位，也再次调用关闭准备；缺少共用任务的加入/升级机制。现场 16:52:11.543 与 .576 两轮停止接纳相隔约 33 ms，run epoch 随之多次推进。
- 16:51:26.787 起，`StopSafetyPending` 显示 DO 已无待完成项，Power task 已完成，但压力等待中且两设备都是 `NoCommittedBatch`。
- `EpbManager.cs:12736` 先尝试液压释放确认，等压力证据超时后，才按异常中一个液压组恢复 DAQ 只读采样，再重试所有组。现场先后在 16:51:30.965 和 16:51:36.131 才恢复两组取证，造成逐轮耗时。
- 不能据此声称正常停止流程一定“先停止采样再确认压力”：当前生产阶段顺序是 ReleaseHydraulics 在 StopAcquisition 前。此次故障退出时采样/代际证据已经不可用，缺陷是未在关闭开始时主动准备所有缺失的压力取证，而是等异常后一组组补救。
- 生产停止代码还在等待旧恢复 owner 退出；已经撤权的事务又因 epoch 不匹配不能提交终结。应允许旧事务对**自身**的安全终结证据落账，但不能让它改写新运行或重新上电。

### 5.4 主程序 5 秒退出的实施契约

**目标是主程序进程退出，不是把主窗口隐藏；后台安全服务是否继续工作单独记录。** 正常环境和下表中可接管的软件故障，均按 5 秒要求验收。

| 从点击主程序 X 开始 | 目标工作 | 约束 |
|---|---|---|
| 0～100 ms | UI 响应；冻结新的试验启动，持久登记 OperatorExit、禁止自动续试 | 意图只登记一次，单调时钟计时 |
| 0～1 s | 并行提交各电源安全 OFF、DO OFF；发现缺失压力证据时同时准备两设备只读采样 | 每个电源连接保持命令串行；跨设备可并行；禁止为取证重新开启电机电源 |
| 0～3 s | 等真实断能/压力证据；关闭当前数据段；准备数据和安全责任交接 | 不先等待普通任务退出才发安全 OFF；不做历史全量导出 |
| 最迟 4 s | 本地收尾完成，或独立后台拥有者完成耐久接管并返回匹配 ACK | ACK 必须匹配本次退出意图、进程启动身份、运行代际与停止事务 |
| 最迟 5 s | 主进程退出，产生完成回执 | 独立观察者确认该 PID/启动时间的进程已经结束 |

为实现这个时间预算，需要：

1. **保持同一停止事务。** 人工停止、子窗口关闭、主程序关闭按不同意图加入或升级同一收尾任务；不反复 StopAll、撤权、增长 epoch。
2. **正确退休旧恢复记录。** 恢复进程建立新的执行代际/进程实例身份，旧 tombstone 按旧事务保留审计且终结退休；当前人工退出生成当前事务回执。禁止粗暴删除历史记录、重用旧许可或把旧 ACK 当新 ACK。
3. **先准备并行取证，再等待。** 各液压组可以独立释放与验证，缺失的两路 DAQ 取证同时恢复；使用同一个绝对截止时间，避免每层再加 5/10/15 秒。
4. **建立可跨进程恢复的数据交接。** 运行中就将已接受数据/数据缺口决定写入有界的本地恢复日志或持久 spool；关闭时只封口和交接，不临时复制无限积压。后台收到的不能只是内存对象引用或“稍后再写”的承诺。
5. **建立明确的后台数据拥有者。** 不能默认现有 SafetyAgent 会保存主进程中的 Raw 队列。应复用可承载该工作的独立组件，补齐数据恢复、去重提交和 ACK；协议区分安全责任与数据责任。主进程退出前，未完成部分必须存在耐久内容和实际接收方。
6. **消除固定 30 秒产品路径。** 在上述收尾和交接验证通过后，收敛到 5 秒预算。仅将常量 30 改 5、加 Kill 或隐藏窗口，不满足此方案。

如果独立后台无法接管、所有可用存储都不可写，或硬件回执永久缺失，软件不能同时保证“绝不丢数据/责任不丢失”和“任何情况下无条件 5 秒退出”。应明确返回具体受阻项并留下证据，计为该场景验收失败，不伪报完成。这不是让正常关闭继续等待 30 秒的理由，而是必须由故障注入验证的异常边界。

## 8. 尚待取证的内容和已排除的误判

1. **129 ms 双设备停顿的底层因素尚未确定。** 需要采集 reader 开始/结束、dispatcher 等待、GC 暂停、线程调度、驱动缓冲与下游处理的同一单调时钟证据。不能直接断言硬件坏，也不能断言一定是 GC。现有 runtime CSV 的 GC ETW 为 unavailable，不能用该源证明暂停原因。
2. **当前故障不需要假设磁盘故障即可解释。** 写盘明确报的是 InvalidDataException，事件时 CPU/内存指标也未显示持续耗尽；但 `quick_check=ok` 仍不等于所有磁盘/网络路径永远无问题。
3. **I0037 内确有另一次旧进程终止。** Sidecar 在 16:25:09.7028991 记录 PID 21412 `OldProcessTerminated / PowerOffUnconfirmedTimeout`，随后新 PID 21708 运行。这是被软件看护链主动终止的证据，不应笼统写成系统随机闪退。08:18 UTC 的 `SemanticSnapshotStalled` 首次诊断及 minidump 已封存，主因与触发阈值还需单独检查。
4. **不能把此次缺陷追溯为全部 2.14.2.11 退出的唯一原因。** 本轮证实了新增采集逻辑与旧写盘契约之间的问题；历史 I0023～I0035 的每次进程退出仍需按各自包身份、异常栈和看护事务归类。此前退出问题尚不能承诺全面清零。
5. 现场多个独立问题可串联：数据卡死会延长 B/C 的收尾，但 B 的“恢复原界面”和 C 的“30 秒强杀/旧事务冲突”各自都有独立代码缺陷。修复 A 后仍必须执行 R10～R16。
