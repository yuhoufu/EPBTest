# 10358-029 V2.13.0.20 启动即失败：与 V2.13.0.15 对照根因及彻底解决方案

> 分析日期：2026-08-22  
> V2.13.0.20 封盘数据：`D:\EPB_Data\10358-029_V2.13.0.20_0822_1417`  
> V2.13.0.15 稳定样本：`D:\EPB_Data\10358-029_V2.13.0.15_0821_1750`  
> V2.13.0.15 对照基线：Git `05c7f51a91a1a3d852261ca27db07b1f5e31e87e`  
> 当前状态：**本次 V2.13.0.20 启动失败的系统根因已确定；本文只给出整改设计，尚未修改代码、尚未完成现场验证。**

## 1. 结论先行

V2.13.0.20 本次不是“刚启动随机报了一堆错误”，也不是 DAQ、程控电源通信或电源保护误报警。它是在正式运行前，被启动零电流安全门禁确定性拦住：

- 电源 2 上电后的电流长期约为 `2.23 A`，电源 4 长期约为 `1.56 A`；
- 两台电源均稳定在约 `12 V`，无保护、无恒流、无通信丢数；
- 当前规则要求上电后 `|Iout| <= 0.500 A` 连续 `300 ms`，因此三次尝试都必然失败。

安全门禁本身是正确的，**不能通过提高 0.5 A 阈值来“修好”启动**。真正的软件缺陷是启动顺序：

```text
现有顺序：DAQ健康检查 -> 电源上电并检查零电流 -> 失败三次 -> 首次初始化DO并全关

正确顺序：全部电源OFF并确认 -> 显式初始化DO -> 26路DO全部置零并确认
          -> 等待继电器释放 -> 选择组电源ON -> 零电流检查 -> 才允许定位/运行
```

也就是说，V2.13.0.20 在尚未把 12 路 EPB 正/反向继电器及 2 路压力 DO 建立为确定的全关状态时，就先给负载上了电。若上一进程异常退出后现场存在遗留输出状态，程序会给非零负载上电；门禁随后能发现危险，却没有在重试前清除危险来源，只把电源机械地 OFF/ON 三次，因此三次结果相同。

本次异常初态有完整证据链：

1. 上一段 V2.13.0.15 在 14:08:24 被 Watchdog 记录为 `ProcessExitedUnexpectedly`；
2. 它退出前最后一帧程控电源遥测中，电源 2、4 都仍为 `Output=True`；
3. 14:15:35 启动 V2.13.0.20，14:16:00 又明确读到电源 2、4 启动前已经 `OUTP ON`；
4. V2.13.0.20 到 14:16:19.883，也就是三轮上电预检全部失败、两台电源已回滚 OFF 之后，才首次记录 `DO 初始化完成`。

另有一个独立的二次故障：这是一次尚未进入正式运行、`RunId=000...000`、恢复检查点 `Armed=false` 的启动失败，但外部 Watchdog 仍无条件接管、终止原进程并重启。新进程随后必然因 `CheckpointDisarmed` 拒绝恢复。这个恢复策略把一个本可留在安全空闲态、允许诊断后重试的问题，升级成了“软件被杀、恢复又失败”。

## 4. 与 V2.13.0.15 究竟差在哪里

### 4.1 表面结果不同，关键启动逻辑并没有不同

V2.13.0.15 稳定样本在 2026-08-21 11:25 的启动过程：

| 时间 | V2.13.0.15 事实 |
|---|---|
| 11:25:24.215 | DAQ 健康检查通过 |
| 11:25:24.290 / .298 | PSU2、PSU4 连接成功 |
| 11:25:24.680 / .740 | 同样等待 `Vout>=6 V`、`|Iout|<=0.500 A` 连续 300 ms |
| 11:25:25.213 | PSU4 以 `11.992 V / -0.036 A` 通过 |
| 11:25:25.260 | PSU2 以 `11.995 V / 0.000 A` 通过 |
| 11:25:26.571 | 开始启动定位 |
| 11:25:26.690 | **到这里才首次初始化 DO** |

所以，V2.13.0.15 也采用了“先电源预检、后 DO 初始化”的顺序。它能运行，不是因为这段时序更完整，而是因为当时两组电源上电后的现场初态恰好接近零电流。

### 4.2 配置与核心电源代码对照

V2.13.0.15 与 V2.13.0.20 日志中的 `ConfigSha256` 相同，均为：

`18930035780a269f551123e34390a60ee0a951345dfe43c5208fe6a8f58ea3b9`

以 V2.13.0.15 基线提交 `05c7f51...` 对照当前工作区：

- `Controller/PowerSupplyCoordinator.cs`：无差异；
- `MTTfTest/Config/PowerSupplyConfig.xml`：无差异；
- `MTTfTest/Config/DOConfig.xml`：无差异；
- `StartupZeroCurrentA=0.50`、稳定时间 `300 ms` 没有在 V2.13.0.20 新增或收紧；
- DO XML 中 12 个 EPB 的默认方向均为“全关”，2 个压力默认值均为 0。

V2.13.0.15 基线 `EpbManager.BatchStart.cs` 的关键顺序是：

```text
EnsureDaqReadyBeforeStartAsync
BeginPowerSupplyTelemetryRecording
EnsurePowerSupplyReadyBeforeStartAsync
```

当前 V2.13.0.20 对应执行顺序仍然相同；在 `EnsurePowerSupplyReadyBeforeStartAsync` 前没有显式 `DoController.Initialize()` 或 `AllOff()`。

`DoController` 只有在第一次 DO 调用触发 `EnsureReady()` 时才懒初始化；初始化过程才创建 26 条线并下发 XML 默认值。V2.13.0.20 现场日志也精确印证：电源预检在 14:16:00 开始，DO 初始化直到 14:16:19.883 的失败收尾才发生。

### 4.3 真正差异是“进程接手时的硬件初态”

本次对启动结果有决定作用的差异如下：

| 条件 | V2.13.0.15 成功样本 | V2.13.0.20 失败样本 |
|---|---|---|
| 上电后 PSU2 电流 | 0.000 A | 平均 2.23 A |
| 上电后 PSU4 电流 | -0.036 A | 平均 1.56 A |
| 启动前电源是否已 ON | 成功样本未报遗留 ON | 两台均明确报“已经 OUTP ON” |
| 上一进程退出链 | 成功样本前置链未见本次异常证据 | V2.13.0.15 异常退出且恢复被取消 |
| DO 安全基线 | 仍然晚于电源预检，但当次没暴露 | 同样晚于电源预检，遗留负载使缺陷必现 |

因此，不能把结论写成“V2.13.0.20 新增的 0.5 A 判断导致不能启动”。准确结论是：

> V2.13.0.15 与 V2.13.0.20 都没有在上电前主动建立可验证的 DO 全关基线。V2.13.0.15 的稳定性依赖于干净的现场初态；V2.13.0.20 接手了异常退出后的非干净初态，终于把这个长期潜伏的启动时序缺陷暴露出来。

### 4.4 Watchdog 逻辑同样不是 V2.13.0.20 新增，但必须修

V2.13.0.15 基线和当前代码都存在：

```text
收到 BatchStartFailed -> 无条件 BeginTakeover
IsRetryableFailure(BatchStartFailed) -> true
```

本次消息却同时具备：

- `RunId=00000000000000000000000000000000`；
- 尚未进入正式运行；
- `StopCompleted CanRestart=True`；
- 检查点 `Armed=false`。

这类失败没有“续测”对象，进程重启后当然无法恢复。该逻辑是既有设计缺陷，不是本次直接上电失败的第一原因，却显著放大了现场影响。

## 5. 根因分层

### 5.1 已证实的直接原因

两台选中电气组的程控电源上电后存在稳定非零负载，无法满足启动零电流门禁，程序因此禁止启动卡钳。

### 5.2 已证实的软件设计根因

启动事务缺少“冷启动安全基线”阶段：电源 ON 和零电流检查发生在 DO 控制器初始化、默认全关写入和全通道 OFF 之前。失败重试只重复电源 OFF/ON，没有改变 DO/继电器负载状态，因此不具备自愈能力。

### 5.3 有强证据的触发条件

上一 V2.13.0.15 进程异常退出时，两台程控电源仍为 `Output=True`，随后自动恢复被操作者取消。V2.13.0.20 启动时再次确认两台电源已经 ON。这个交接过程形成了非干净初态。

需要严格说明：现有封盘数据没有 DO 物理回读，因此不能从日志点名“26 路中的哪一条继电器线处于 ON”。可以确定的是两组真实负载存在，也可以确定程序没有在上电前初始化和全关 DO。整改必须消除对具体遗留线路的依赖，而不是只针对猜测的某个通道。

### 5.4 已证实的二次恢复根因

Watchdog 把所有 `BatchStartFailed` 都当作进程级可恢复故障，没有先校验“正式运行已提交、检查点已 Armed、存在有效 RunId”。因此它终止了已经完成安全收尾的原进程，又用一个未 Armed 的旧检查点启动恢复，最终被 `CheckpointDisarmed` 永久拒绝。

## 6. 哪些不是本次根因

- **不是 DAQ 启动失败**：Dev1、Dev2 在 14:15:59.939 已通过健康检查。
- **不是程控电源连接失败**：PSU2、PSU4 均正常连接并持续产生无丢失遥测。
- **不是电源保护或限流**：186 行遥测中相关标志均未触发。
- **不是 0.5 A 阈值在 V2.13.0.20 被改严**：V2.13.0.15 使用完全相同的阈值并能通过。
- **不是 V2.13.0.19 曾出现的启动定位/执行授权问题**：本次连电源启动预检都没有通过，尚未进入 StartupPositioning。
- **不是 `PackageManifestMissing` 的直接运行故障**：V2.13.0.15 成功样本也有同类发布包身份警告。但缺失 manifest 会妨碍精确版本审计，仍需补齐。

## 7. 彻底解决方案

### P0-1：新增唯一的冷启动安全基线事务

在生命周期锁内、DAQ 健康检查之后或之前均可，但必须在任何程控电源 ON 之前执行唯一入口，例如：

`EstablishColdStartSafeBaselineAsync(selectedChannels, token)`

建议强制顺序：

1. 撤销全部运行、定位、DO 上电授权，确保 Timer、Runner 尚未创建；
2. 对全部四组程控电源发送 `OUTP OFF`，不能只处理本次选择组；
3. 逐台实时回读 `OutputEnabled=false`，任一台不能确认就阻止启动；
4. 显式调用 DO 初始化，禁止依赖第一次通道操作的懒初始化；
5. 初始化成功后，再按设备执行一次 26 路原子全零写入，覆盖 12 个 EPB 的正/反向线及 2 路压力线；
6. AO 压力指令同步归零，压力 DO 保持 OFF；
7. 等待继电器实际释放时间。延时应做成配置项，初值可用 300 ms，最终以继电器规格及现场测量确定；
8. 最低限度记录 NI 写入成功；推荐增加 DO 端口回读或继电器辅助触点回读，形成物理层确认；
9. 只对选择组设置电压/电流参数并 `OUTP ON`；
10. 保留现有 `Vout>=6 V`、`|Iout|<=0.5 A` 连续 300 ms 门禁；
11. 所有组通过后，才颁发电源/执行代际授权，进入 StartupPositioning。

这一步同时解决干净启动、崩溃后重启、版本切换、Watchdog 拉起和设备任务丢失后的不确定初态。

### P0-2：把“稳定非零负载”从软件瞬态中剥离

当前三次尝试完全重复同一动作，没有清理 DO，属于无效重试。应调整为：

- 电压正常、无保护、通信正常，但电流持续超 0.5 A：分类为 `ResidualLoadDetected` 或 `UnsafeStartupBaseline`；
- 第一次发现后，电源 OFF，重新执行一次完整 DO 全关安全基线；
- 只允许一次有状态变化的自动清理重试；
- 若仍超限，保持全部电源 OFF，直接阻止启动并报告具体电源组、最小/最大/平均电流；
- 同时收集 PSU2 和 PSU4 的结果，不能只保留第一个抛出的异常；
- 绝不能通过把 0.5 A 提高到 2 A、3 A 或关闭该门禁来绕过故障。

### P0-3：修改 BatchStartFailed 的 Watchdog 接管资格

外部接管前必须同时判断恢复资格：

```text
FormalRunCommitted == true
&& RunId != Guid.Empty
&& Checkpoint.Armed == true
&& Checkpoint.RunId == Message.RunId
```

建议策略：

- 新试验启动预检失败、StopAll 已证明安全、检查点未 Armed：主程序留在 `SafeIdle`，不终止进程，不拉起 Watchdog 恢复；
- UI 显示明确诊断及“重新执行安全基线后重试”操作；
- 只有正式运行已提交且检查点有效，或主进程失联/卡死、StopAll 无法证明安全时，才允许外部接管；
- Watchdog sidecar 在杀旧进程之前再次校验检查点资格，不能等新进程启动后才发现 `CheckpointDisarmed`。

### P0-4：修正停止、退出与版本切换的硬件交接

本次上一版本留下了 `ManualStopIntent`，但最后遥测仍为 `Output=True`，之后被记录为异常退出。停止协议应区分“意图”和“完成”：

1. `ManualStopIntent` 可先写，用于禁止新的动作；
2. 必须完成全部 DO OFF、全部 PSU OFF、液压释放、落盘清空；
3. 实时回读电源输出已 OFF；
4. 写入 `ManualStopCompleted / PhysicalSafeConfirmed`；
5. 之后才允许主窗体和进程退出，并通知 Watchdog `ShutdownExpected`。

若在物理安全确认前主进程意外退出，Watchdog 的第一职责应是执行或协调硬件安全收口，而不是立即重启试验。

### P1-1：清理检查点的新旧运行污染

- 手工开始新试验时创建“暂态启动上下文”，不要直接把旧正式运行检查点当成当前恢复对象；
- 只有 StartupPositioning 成功且正式批次提交后才 `Armed=true`；
- `WatchdogSessionAttached` 不能覆盖最后一次有业务意义的停止原因，也不能把未 Armed 检查点伪装成可恢复；
- 本次检查点仍残留 `BuildVersion=2.13.0.19` 和旧 `RunId`，应在新启动上下文中明确隔离；
- 恢复拒绝时不要再宣称“启动授权仍有效”或继续触发进程重启。

### P1-2：补齐可诊断性与发布身份

每次开始试验应输出一张结构化安全基线表：

| 阶段 | 必须记录的字段 |
|---|---|
| 接手初态 | 每台 PSU 的连接、OUTP、Vout、Iout、保护状态 |

## 12. 分析边界

本文已经能够确定本次 V2.13.0.20 失败的直接原因、启动时序根因及 Watchdog 二次故障，不再把“可能是某个授权竞态”当成本次结论。

仍保留两项边界：

1. 封盘 EXE 缺少发布 manifest 和 Git commit，不能做已发布二进制的逐字节源码归属；
2. 系统没有 DO 物理回读，不能从现有日志点名具体哪条继电器线造成 PSU2/PSU4 的稳定负载。

这两项不影响整改方向：无论遗留的是哪条 DO、哪只继电器或哪次异常退出，**任何版本都必须在电源上电前主动建立并验证统一的物理安全基线**。
