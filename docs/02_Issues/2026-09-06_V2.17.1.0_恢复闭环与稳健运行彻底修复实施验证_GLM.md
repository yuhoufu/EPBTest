## 2. 修复内容与代码锚点

### A1 统一关闭墓碑 schema（I0043/I0044 共同根因）

- [WatchdogClosingTombstone.cs](../../Watchdog.Protocol/WatchdogClosingTombstone.cs)：类默认 `SchemaVersion` 由硬编码 6 改为 `SupervisorProtocol.SchemaVersion`；`IsValidFor` 由硬编码接受 1—6 改为 `1..SupervisorProtocol.SchemaVersion`。校验上限从此跟随权威常量，两处常量不可能再脱节。
- 向后兼容：磁盘上的旧 schema 5/6 墓碑仍可读（历史版本在接受集合内）；`WatchdogHost` 的 `SchemaVersion < 5` 升级分支对 6 不触发，行为不变。

### A2 区分"墓碑写失败"与"会话撤销"（I0044 连重试都没有的原因）

- [WatchdogRuntime.cs](../../MTTfTest/WatchdogRuntime.cs)：新增 `WriteClosingTombstoneDurable`（生产路径有界重试 3 次、50/100ms 退避；测试经 `ClosingTombstoneWriteOverride` 内部 seam 注入失败）。写失败时**仅非接管路径**写 `.revoked`；`TakeoverReplacementExit + PreserveApprovedPermit` 路径禁止写撤销标记，保持管道/心跳，由 sidecar 经既有崩溃补证路径（`CreateCrashRecoveryClosingTombstone`）重建墓碑。`CompleteSessionCloseTombstone` 同步走持久化助手。
- [WatchdogJournalStorage.cs](../../Watchdog.Protocol/WatchdogJournalStorage.cs)：`WatchdogControlMarker` 新增 `TryReadReason`（读取撤销原因，供防御纵深判定）。

### A3 sidecar 防御纵深

- [WatchdogHost.cs](../../MTTFTest.Watchdog/WatchdogHost.cs)：监控循环 TerminateSession 分支新增守卫——legacy 撤销标记原因为 `ClosingTombstoneWriteFailed` 且许可为保留时，不终止会话，记录 `LegacyRevocationMarkerSuppressed` 后继续监护。A2 修复后正常不触发，仅防磁盘类瞬态故障。

### A4 同进程恢复完成优先于空边界（I0044 误升级直接根因）

- [UnattendedRecovery.cs](../../MTTfTest/UnattendedRecovery.cs)：监控循环退出后以 `recovery.IsCompleted` 为唯一事实源，升级判定提取为纯函数 `ShouldEscalateToExternalRecovery(completed, boundaryReason)` = `!completed && 非空白边界`。"恢复恰在 500ms 轮询窗内完成 + 空串边界"从此不可能升级。

### B1 准入窗覆盖计划错开跨度（I0044 触发根因）

- [EpbManager.BatchStart.cs](../../Controller/EpbManager.BatchStart.cs)：错峰相位是每通道固定偏移（`PhaseMs = batchOrdinal × staggerMs`），计划内通道的到达跨度按设计横跨整个相位带；固定 300ms 窗小于跨度时后到通道被确定性饿死。有效准入窗改为 `max(配置值, 相位跨度 + 250ms 余量)`，并一次性记录 effective/configured/phaseSpan 归因日志。**未在窗口到达的通道仍不准入**（可能未过 DAQ/电源预检），安全语义不放松。

### B2 CTS 安全取消（I0043 同进程恢复失败点之一）

- [EpbManager.BatchStart.cs](../../Controller/EpbManager.BatchStart.cs)：学习 deadline 分支对 `_stopCtsByChannel` 实例的裸 `Cancel()` 改为捕获 `ObjectDisposedException/InvalidOperationException`（该实例可被停止事务的清场工作项并发摘除并 Cancel+Dispose）。`RenewStopCts/CancelStopCts/RenewCyclePauseCts/CancelCyclePauseCts/ReleaseCyclePauseCts` 审计结论：均已有防护，未改。

### B3 圈号注册表清场收敛（I0043 `ActiveCycles=5` 残留）

- [EpbManager.cs](../../Controller/EpbManager.cs)：新增 `SweepCurrentCycleRegistryForRestartQuiescence()` 并接入 `FinalizeLogicalQuiescenceForRestartAsync`——按既有 `ClearCurrentCycleNumber` 守卫逐通道清理 `_currentCycleNumberByChannel`；仍等待耐久恢复的圈身份保留并告警（fail-closed），交由恢复路径收敛。停止事务摘除 Timer/Runner 后正常收尾不再运行，此显式清扫使重启不变量 `ActiveCycles=0` 可达成。

### B4 停止路径持久化终态收敛（I0043 `Depth=0 但 State=Failed/Closed=False`）

- [DaqPersistenceCoordinator.cs](../../Controller/DaqPersistenceCoordinator.cs)：新增 `TryConfirmDrainedTerminalForStop(device)`——无未解决写故障、无数据丢弃、队列排空（有界 2s 等待在途写入收口）时，确认停止期排空终态并复位拥塞锁存（含解除写恢复超时锁存），发布 `DaqPersistenceDrainedTerminalForStop`；存在未解决写故障或数据丢弃时拒绝（fail-closed）。
- [EpbManager.FieldMetrics.cs](../../Controller/EpbManager.FieldMetrics.cs)：`WaitForStopPersistenceBoundariesAsync` 在 `DrainAsync` 后、快照评估前调用该方法（仅 requireRecoveredState 场景），既有 `Closed` 判定自然通过，无判定逻辑改动。

### B5 DAQ 分发队列可归因 + 容量可配置（I0043 触发源观测）

- [DaqReadDispatcher.cs](../../IO.NI/DaqReadDispatcher.cs)：新增高水位 `HighWaterDepth`、消费停滞 `ConsumerStallMs`（消费线程心跳）；`TryPublish` 保持"满即 false、不阻塞、不抛"契约。
- [TwoDeviceAiAcquirer.cs](../../IO.NI/TwoDeviceAiAcquirer.cs)：容量经 AppSettings `DaqReadDispatchQueueCapacity`（钳位 16—4096，默认仍 64，行为不变）；溢出异常携带 `capacity/HighWater/Depth/ConsumerStallMs`，可区分"消费者被饿"与"生产突发"。
