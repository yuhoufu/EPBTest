# 10358-029a：V2.13.0.15 人工停止卡顿与 V2.13.0.21 Watchdog 误接管根因及彻底解决方案

> 分析日期：2026-08-25（Asia/Shanghai）
> 项目：10358-029a
> 结论性质：现场封盘数据 + Watchdog 会话日志 + 当前仓库源码/提交历史的联合诊断
> 处置结论：暂停部署 V2.13.0.21；V2.13.0.15 的连续运行稳定性成立，但其人工停止入口需要单独修复

## 1. 技术摘要

本次现场实际包含两条相互独立的故障链，不能混为“V2.13.0.15 运行不稳定”：

1. **V2.13.0.15 连续运行是稳定的。** 它从 2026-08-24 14:10 左右持续到 2026-08-25 09:54，约 **19 小时 44 分钟**。09:54 的停止是为了切换测试 V2.13.0.21 而人工发起，不是程序自行故障停机。
2. **V2.13.0.15 的人工停止路径存在卡顿缺陷。** 点击停止后，恢复检查点已在 13 ms 内解除武装，但后续 `StopAllAsync` 没有进入；控制循环仍继续约 82 秒，进程约 106 秒后退出。阻塞边界已定位在 UI 线程同步执行的 Watchdog 人工停止通知链，最可能是命名管道发送或日志强制刷新。
3. **V2.13.0.21 的主故障是 Watchdog 读取了陈旧的逻辑聚合快照。** 程序每 15 秒正常完成学习圈，但心跳里的 EPB4 机械计数和完成时间在整个监督窗口内不更新，Sidecar 连续两次在约 60 秒后误报 `ChannelProgressStalled`。
4. **V2.13.0.21 还存在独立的接管取消竞态。** 主程序已经报告 `BatchStartFailedSafeIdle`，Sidecar 也记录“正式运行未提交、禁止杀进程”，但此前启动的 `TakeoverAsync` 任务没有被取消，8.8 秒后仍抓取转储并杀死 PID 14012。
5. V2.13.0.21 的 EXE SHA-256 与仓库记录的目标构建一致，但运行目录缺少发布清单，窗口持续标记 `PackageManifestMissing`。这**不是本次误接管的直接根因**，但说明 DLL、配置和辅助程序的整包一致性没有发布级证明，必须作为发布阻断项修复。

因此，彻底解决不能只把 60 秒阈值调大，也不能只屏蔽 `ChannelProgressStalled`。必须同时修复：

- 心跳聚合数据的**生产、版本、新鲜度和消费门禁**；
- 在途接管任务的**可取消事务语义**；
- 人工停止的**物理断能优先与外部 I/O 隔离**；
- 发布包身份与端到端现场回放测试。

## 4. 根因分析

### 4.1 根因 A：V2.13.0.21 心跳中的 ChannelProgress 是陈旧聚合快照（已确认，P0）

V2.13.0.21 引入了“心跳只读取一个不可变聚合快照”的改造。设计目标正确：防止一个心跳混用不同时间点的恢复状态、通道状态和 Stop 状态。但生产者没有形成完整闭环。

当前数据流是：

```text
机械圈完成
  └─ OnMechanicalCycleCompleted
       ├─ 更新 _watchdogMechanicalCompletedCount
       └─ 更新 _watchdogLastMechanicalCompletedUtcTicks
            （没有发布新的 LogicalSource）

心跳线程
  └─ CaptureWatchdogRecoverySnapshot
       └─ _recoveryAggregateStore.Capture()
            └─ 只返回上一次已提交的 LogicalSource

Sidecar
  └─ 连续 60 秒看到相同 MechanicalCompletedCount / LastMechanicalCompletedUtcTicks
       └─ 误报 ChannelProgressStalled
```

源码证据：

- [`Controller/EpbManager.BatchStart.cs`](../../Controller/EpbManager.BatchStart.cs) 的 `OnMechanicalCycleCompleted` 只更新内存字典；
- [`Controller/EpbManager.cs`](../../Controller/EpbManager.cs) 的 `CaptureLogicalQuiescenceSnapshotLocked` 才把这些字段组装成 `ChannelProgress` 并调用 `PublishLogicalSource`；
- 但 [`Controller/EpbManager.BatchStart.cs`](../../Controller/EpbManager.BatchStart.cs) 的 `CaptureWatchdogRecoverySnapshotLocked` 在提交 `935b65d` 后只执行 `_recoveryAggregateStore.Capture()`，心跳读取时不再主动刷新逻辑源；
- `PublishLogicalSource` 的生产调用只出现在停止/清场等少数边界，没有随每个学习圈或周期性心跳刷新；
- [`Watchdog.Protocol/WatchdogPolicy.cs`](../../Watchdog.Protocol/WatchdogPolicy.cs) 的监督器将机械计数和最后完成时间组成签名，签名 60 秒不变即触发接管。

现场数据与该数据流完全一致：

| 进程 | 实际学习进度 | Sidecar 看到的 EPB4 进度 | 旧时间来自 |
|---|---|---|---|
| PID 14012 | 09:57:09、09:57:24、09:57:39 完成 3 圈 | `Mechanical=5013; LastMechanical=09:55:55.247` | V2.13.0.15/新版启动前 |
| PID 12004 | 09:58:54、09:59:09、09:59:24 完成 3 圈 | `Mechanical=5016; LastMechanical=09:57:39.765` | 上一个 PID 14012 |

这也解释了为什么把学习期合同设为 `TimerRequired=false, RunnerRequired=true` 仍然误报：**合同本身允许学习期没有 Timer，真正失效的是机械进度字段的新鲜度。**

现有自动化测试的盲点也与此一致：`PhaseAwareRuntimeContractPreventsLearningFalseTakeover` 在测试对象上直接递增 `MechanicalCompletedCount` 和时间戳，证明的是“监督器收到新进度后会重置期限”；聚合快照测试主要证明深拷贝、单版本和并发一致性。它们没有贯通“真实 `OnMechanicalCycleCompleted` → `PublishLogicalSource` → 心跳 → Sidecar”的生产链，因此无法发现“快照一致但长期不新鲜”的回归。

### 4.2 根因 B：安全空闲拒绝没有取消已启动的接管任务（已确认，P0）

[`MTTFTest.Watchdog/WatchdogHost.cs`](../../MTTFTest.Watchdog/WatchdogHost.cs) 的 `BeginTakeover` 会将 `_takeoverStarted` 置 1，然后后台启动 `TakeoverAsync`。`TakeoverAsync` 固定等待最长 15 秒，随后在进程仍存活时抓 dump、杀进程、申请重启许可。

收到 `BatchStartFailed` 且 `FormalRunNotCommitted` 时，现有代码只写一条：

```text
BatchStartFailedSafeIdle ... Sidecar保持附着但禁止杀进程
```

它没有：

- 取消 `TakeoverAsync`；
- 使当前 correlation/generation 失效；
- 在 dump、kill 和 relaunch 前重新检查“接管是否仍获授权”；
- 记录真正的 `TakeoverCancelled` 终态。

因此 09:58:00.029 的“禁止杀进程”只是日志描述，09:58:08.865 仍进入 dump，09:58:09.489 仍杀死进程。这是一个确定的状态机竞态，不是硬件问题。

### 4.3 根因 C：V2.13.0.15 人工停止在物理断能之前同步执行外部 I/O（边界已确认，具体内部调用高概率，P0）

V2.13.0.15 的 `BtnStop_Click` 顺序是：

1. 同步修改 UI 通道开关；
2. 写“已接收停止命令”；
3. `UnattendedRecoveryCoordinator.Disarm("ManualStopIntent")`；
4. `WatchdogRuntime.NotifyManualStop(...)`；
5. `ClearGracefulPauseCheckpoint(...)`；
6. 取消批次；
7. 最后才调用 `_epb.StopAllAsync(...)`。

现场审计证明第 3 步已经完成；但没有同一 CommandId 的 `StopAll` / StopStage 证据，Sidecar 也没有收到 `ManualStopIntent`，控制继续执行。因此阻塞发生在第 3 步之后、第 7 步之前。

V2.13.0.15 的 [`MTTFTest/WatchdogRuntime.cs`](../../MTTFTest/WatchdogRuntime.cs) 历史实现中，`NotifyManualStop` 会同步记录事件、同步 `writer.WriteLine(...)`、同步 `FlushClientJournal()`；管道写入还持有全局 `Gate`，没有 I/O 超时。长时间运行后，V2.13.0.15 会话的当前心跳/日志状态已经明显陈旧，命名管道或日志刷新阻塞与现场边界高度吻合。

提交 `02a0ac6` 已明确按同一问题类别进行过修正：将 `StopAllAsync` 提前为第一个可能阻塞的动作，把 Watchdog 通知、检查点清理和批次取消移到后台，并把管道发送串行锁与全局状态锁分开。现场运行的 V2.13.0.15 EXE SHA=`1bdf2491...a84953` 不包含该后续修复。

需要强调：这不否定 V2.13.0.15 的长时间运行稳定性；它说明**稳定运行路径和人工停止路径是两项不同的可靠性指标**。

### 4.4 灰色界面的性质（高置信度，P1）

09:59:37 Watchdog 误接管后，主程序执行系统故障 `StopAll`；09:59:40 运行时发布 `ApplicationClosing`。第二张截图的灰色区域是监视子窗体关闭后暴露的 MDI 背景。

因此灰屏主要是错误接管的 UI 后果，不是根因。但当前 UI 没有保留“Watchdog 已接管 / 正在安全停机 / 等待恢复”的持久状态，操作员只能看到空白灰屏，必须改善可解释性。

### 4.5 `PackageManifestMissing` 是发布完整性缺陷，不是本次直接根因（P1）

V2.13.0.21 两次启动均记录：

```text
PackageVerified=False PackageCode=PackageManifestMissing PackageFiles=0
```

EXE SHA=`66acc31c...6191bf4` 与仓库 V2.13.0.21 记录一致，且误接管可以由同一 EXE 的源码和日志直接解释，所以不能把本次故障归咎于“拿错 EXE”。但没有 manifest/checksums 时，无法证明 DLL、配置、Watchdog 辅助程序和 EXE 属于同一个发布包，后续版本必须禁止以此状态进入耐久测试。

### 4.6 次要/后果性异常

以下现象需要修，但不是本次第一根因：

- 09:56:42 初始 Watchdog 命名管道连接超时以 `UnobservedTaskException` 形式出现，说明启动连接任务没有被统一观察；
- 09:59:40 的 AO 写零失败、遥测清理窗口不足和 `OperationCanceledException` 发生在误接管后的关闭阶段；
- V2.13.0.15 长时间运行中出现过 DAQ 瞬态恢复，但均恢复成功，没有导致本次人工切换前的终止。

## 5. 彻底解决方案

### 5.1 P0-1：为 Watchdog 聚合快照建立“生产即提交、消费先验鲜”的完整契约

不要退回到心跳线程随意扫描多个实时字典，也不要只把 60 秒改成 120 秒。保留不可变聚合快照，但补齐生产与新鲜度协议。

#### 5.1.1 协议字段

在聚合/心跳中增加：

```text
AggregateVersion
LogicalSourceVersion
LogicalCapturedUtcTicks
ChannelProgressVersion[channel]
ChannelLastProgressUtcTicks[channel]
ChannelProgressKind[channel]   // Learning / Qualification / FormalMechanical
```

监督身份必须至少包含：

```text
SessionId + ProcessId + ProcessStartUtcTicks
+ RunId + RunEpoch
+ Channel
+ LifecyclePhase + RuntimeContractRevision
+ LogicalSourceVersion / ChannelProgressVersion
```

Run、进程、阶段或合同修订变化时，监督器必须重新建立基线，不能继承上一阶段已经累计的停滞时间。

#### 5.1.2 生产者发布

实现一个 Controller 所有的单一发布器：

- `OnMechanicalCycleCompleted` 更新计数后立即标记 dirty，并在不超过 1 秒内提交新的 `LogicalSource`；
- Runner/Timer 创建或移除、阶段变化、通道启停、Stop 进度变化必须立即提交；
- 增加 1 Hz 周期发布作为漏事件兜底；
- 发布时继续在恢复合同 gate 内一次性采样，提交深拷贝，不让心跳线程读取可变字典；
- 聚合存储分别保存每个 source 的版本与捕获时间，不能只用任意 source 更新都会递增的总 `AggregateVersion` 掩盖陈旧的 `LogicalSource`。

#### 5.1.3 Sidecar 新鲜度门禁

`ChannelProgressStalled` 只能在以下条件同时满足时评估：

1. 当前心跳与当前进程/Run/阶段身份一致；
2. `LogicalSource` 时间戳新鲜，例如不超过 3 个心跳周期；
3. 已观察到当前身份的初始基线；
4. 当前阶段确实要求机械/工作进度；
5. 从最后一个**新鲜进度版本**开始超过阶段截止时间。

如果逻辑源陈旧，应先报告 `WatchdogLogicalSourceStale` 并请求结构化刷新，不能谎报 `ChannelProgressStalled`。刷新仍失败时，应按“监督数据源失效”执行有界安全停机；是否杀进程必须依据 Stop 事务的物理安全回执，而不能依据陈旧的机械计数直接决定。

#### 5.1.4 分阶段进度语义

- Learning：学习机械圈完成版本；
- Qualification：资格圈/资格阶段完成版本；
- Running / WarningRunning：正式机械圈完成版本；
- Recovering：使用恢复阶段和 `RecoveryProgressVersion`；
- Stopping：使用 `StopProgressVersion`。

可以继续保留统一机械完成事实用于磨损计数，但 Watchdog 字段必须带 `ProgressKind`，避免旧正式圈时间被当作新学习阶段的起始进度。

### 5.2 P0-2：把接管改造成可取消、单所有者、带代次的事务

新增 `TakeoverTransaction`，包含：

```text
CorrelationId
Generation
ProcessIdentity
RunIdentity
CancellationTokenSource
State = Requested / StopRequested / Cancelled / Dumping / Killing / Relaunching / Completed
Reason
```

规则：

1. `BeginTakeover` 只能通过 CAS 创建一个当前事务；
2. `BatchStartFailedSafeIdle(FormalRunNotCommitted)` 必须原子调用 `CancelTakeover`，写入 `TakeoverCancelled`，并使该代次永久失效；
3. `TakeoverAsync` 的每次等待之后，以及 dump、kill、批准 relaunch permit 之前，都必须验证 token、代次、进程身份和授权状态；
4. 一旦 `Cancelled`，任何迟到 continuation 都不得 dump、kill 或重启；
5. 取消完成后允许未来新的、不同 correlation 的真实故障重新建立接管事务；
6. `BatchStartFailedSafeIdle` 的文字、内存状态和持久化会话状态必须一致，不能只写一条“禁止杀进程”的日志。

### 5.3 P0-3：彻底隔离人工停止路径中的外部 I/O

对 V2.13.0.15 稳定运行分支回移 `02a0ac6` 的停止修复，并进一步做到：

1. 点击停止后的第一个可能阻塞调用必须是幂等的 `_epb.StopAllAsync(ManualUi)`；
2. UI 开关同步、批次取消、checkpoint 解除武装、Watchdog 通知、journal flush 均在 Stop 事务启动后异步执行；
3. UI 线程只向有界队列投递 Watchdog 消息，不直接调用 `StreamWriter.WriteLine`；
4. 使用单独发送 worker、有限队列、每条消息的发送/ACK 截止时间；超时丢弃诊断消息也不能阻塞物理断能；
5. 管道 I/O 不持有全局运行状态锁；关闭管道必须能使阻塞 writer 退出；
6. journal flush 使用后台任务和硬截止；人工停止安全性不依赖日志落盘成功；
7. Stop 事务以 CommandId/Generation 保证 exactly-once；重复点击只复用同一事务；
8. UI 每秒显示真实 StopStage，但消息泵不能被停止核心或 I/O 阻塞。

建议验收目标：

- 点击后 200 ms 内可见 Stop 事务已进入首个物理断能阶段；
- 500 ms 内发出所有通道 DO OFF 请求；
- UI 消息泵持续响应；
- 即使命名管道不读、日志盘满/变慢、checkpoint flush 卡住，也不影响上述两项；
- 点击后不允许再出现新的正/反向上电圈。

具体物理确认上限仍以硬件回读预算为准，不能用 UI 响应时间替代安全回执。

### 5.4 P1：让 Watchdog 接管状态在 UI 上可解释

- 发生系统故障 StopAll 时，监视子窗体保留到安全终态或主进程实际退出；
- MDI 主窗体显示持久横幅：故障原因、CorrelationId、当前 StopStage、物理安全状态、是否等待重启；
- 不允许在未给出状态说明时只剩灰色空白区域；
- 如果恢复被阻断，明确显示“安全空闲、禁止自动续跑”，而不是自动重开监视窗。

### 5.5 P1：发布包完整性作为硬门禁

- 只能通过正式发布脚本生成包；
- 包内必须含 manifest、全文件 checksums、Git commit、构建时间和发布配置 hash；
- 启动必须满足 `PackageVerified=True`；
- `PackageManifestMissing`、DLL hash 不匹配、辅助 Watchdog 不匹配时，禁止进入耐久测试；
- 保存现场包，而不只保存 EXE。

## 6. 落地顺序

### 6.1 立即处置

1. **暂停 V2.13.0.21 继续耐久运行。** 两次约 60 秒确定性误接管证明它不具备现场稳定性。
2. **允许 V2.13.0.15 作为当前稳定运行基线继续使用，但不要把现有人工停止缺陷忽略为普通界面问题。** 先回移停止修复并重新打受控包；修复前的人工停止必须按现场设备安全规程确认实际断能，不能只依据按钮状态。
3. 保存 V2.13.0.21 原始运行包、session、dump 和封盘数据，禁止被下一次试验覆盖。

### 6.2 修复版本建议

发布一个新的受控修复版本（建议 V2.13.0.22），以 V2.13.0.21 功能为基础，但必须包含：

- LogicalSource 周期/事件发布和 source freshness；
- phase/run/process scoped 的进度监督；
- 可取消接管事务；
- 人工停止物理断能优先；
- 启动连接任务统一观察；
- 灰屏状态提示；
- 完整发布 manifest/checksums。

不建议只在 V2.13.0.21 上把 60 秒改大后重新命名发布，因为陈旧快照无论阈值多大最终都会误报。

## 7. 必须新增的自动化测试

### 7.1 现场一比一回放

1. 从机械计数 5013 恢复；进入 Learning，`Timer=false, Runner=true`；每 15 秒完成一圈；连续 10 圈不得出现 `ChannelProgressStalled`。
2. 进程重启后从 5016 恢复，同样连续学习；Sidecar 必须看到新进程的 `LogicalSourceVersion` 和 `ChannelProgressVersion` 递增。
3. 断言学习圈完成到 Sidecar 可见的传播延迟小于 2 秒。

### 7.2 真停滞与陈旧源必须区分

1. 冻结真实学习 runner，但心跳和 LogicalSource 仍新鲜：在阶段期限后只触发一次真实 `ChannelProgressStalled`。
2. 只冻结 LogicalSource 发布、控制仍运行：先触发 `WatchdogLogicalSourceStale`/refresh，不得伪造 `ChannelProgressStalled`。
3. source 长期不恢复：进入有界安全停机，并以 Stop 物理回执决定后续，不得直接依据旧计数杀进程。

### 7.3 接管取消竞态

对以下交错执行至少 1,000～10,000 次确定性调度测试：

- `TakeoverRequested`；
- 主程序完成启动回滚；
- `BatchStartFailedSafeIdle(FormalRunNotCommitted)`；
- 15 秒等待即将结束；
- dump/kill continuation 被释放。

验收：`TakeoverCancelled` 恰好一次；dump=0；kill=0；relaunch permit=0；随后新的真实故障仍能创建下一代接管事务。

### 7.4 人工停止故障注入

分别注入：

- Sidecar 不读命名管道；
- 发送锁长期占用；
- journal flush 10 秒不返回；
- checkpoint 写盘慢/失败；
- 批次取消回调阻塞；
- UI 控件事件异常。

所有场景均需满足：StopAll 首先启动、DO OFF 按预算发出、UI 不冻结、不再产生新上电圈、重复点击不创建第二个 Stop 核心。

### 7.5 端到端耐久验收

- 台架完成 24 小时，现场完成 72 小时；
- 覆盖不少于 20 次受控进程恢复、20 次人工停止/再启动；
- 学习、资格、正式、恢复、停止各阶段都观察 source version；
- `ChannelProgressStalled` 必须能回溯到新鲜 source 和真实无进展；
- `BatchStartFailedSafeIdle` 后 dump/kill 次数必须为 0；
- 整包每次启动均为 `PackageVerified=True`；
- 24/72 小时通过前，不得宣称“彻底解决”。

## 8. 发布验收门槛

| 门槛 | 必须满足 |
|---|---|
| 心跳新鲜度 | 运行态 `LogicalSource` 持续更新；机械完成到 Sidecar 可见 < 2 秒 |

## 9. 结论与根因置信度

| 结论 | 置信度 | 依据 |
|---|---|---|
| V2.13.0.15 在人工停止前连续运行稳定 | 高 | 约 19 h 44 min 连续控制/DAQ/落盘与现场描述一致 |
| V2.13.0.15 人工停止在 `Disarm` 后、`StopAllAsync` 前阻塞 | 高 | checkpoint audit 已完成；无 StopAll 证据；控制继续 82 秒 |
| 阻塞具体位于 `NotifyManualStop` 的管道写/日志刷新 | 中高 | Sidecar 未收到意图；历史代码同步 WriteLine/Flush 且无 I/O 截止；缺少线程栈不能绝对区分内部子调用 |
| V2.13.0.21 误接管由陈旧 LogicalSource 导致 | 高 | 两个 PID 重复；旧时间精确来自上一进程；学习圈实际持续完成；源码生产/消费断链闭环 |
| SafeIdle 后仍杀进程由在途接管未取消导致 | 高 | 日志顺序确定；源码 `TakeoverAsync` 无取消事务，kill 前不检查 SafeIdle 拒绝 |
| 灰屏是错误接管后的监视窗关闭表现 | 高 | 截图与 `StopAll`、`ApplicationClosing` 时间一致 |
| `PackageManifestMissing` 是本次直接根因 | 低/否定 | EXE hash 与目标构建一致，已有更直接、可复现的软件根因；但整包仍不可信 |

最终判断：**V2.13.0.15 是本次的稳定运行基线，人工停止是为了切换测试 V2.13.0.21；需要修的是其人工停止入口。V2.13.0.21 的不稳定来自 Watchdog 聚合快照新鲜度回归，并被接管取消竞态放大为错误杀进程和灰屏。只有同时关闭三项 P0，并通过现场一比一回放及 24/72 小时耐久，才可视为彻底解决。**
