## 2. 事故事实与本轮不变的安全判断

### 2.1 首发事件

事故目录的原始 `daq_timing.csv` 证明：

| 设备 | UTC 时间 | CallbackIntervalMs | EndReadMs | RearmMs | QueueDepth |
|---|---|---:|---:|---:|---:|
| Dev1 | 2026-08-11 06:31:16.311 | 264.019 | 0.007 | 0.025 | 0 |
| Dev2 | 2026-08-11 06:31:16.311 | 264.179 | 0.002 | 0.024 | 0 |

因此本次不是“DAQ 始终正常、100ms 看门狗纯误报”。两块设备确实同时发生约 264ms 回调空窗。恢复快照中的 `beforeCallbackAgeMs≈11ms` 是回调恢复后生成快照时的当前年龄，不能反向否定此前已经完成的 264ms 回调间隔。

### 2.2 安全动作

V2.12.0.31 的独立 DAQ 存活监督正确触发，电机高优先级 OFF 和程控电源关闭均成功。100ms 带电安全门槛在 V2.12.0.32 中保持不变，不采纳“提高到 500ms、连续三次才断能”的建议。

### 2.3 最终停机原因

导致永久停机的不是短空窗本身，而是恢复和 StopAll 对持久化边界的解释不一致：

1. 首次故障冻结前缀已经真实落盘；
2. 圈作废流程又重新抓取更大的动态发布边界；
3. StopAll 又要求不断增长的 `FinalBoundary` 必须等于早期冻结边界；
4. 同步写批次可能已从队列出队但仍处于 `InFlight`，旧停止门禁只看 `Depth=0`；
5. 自动进程交接反复得到 `Persistence=Unconfirmed`，最终耗尽三次预算。

这属于恢复状态机的逻辑活性失败，不是传统线程互斥锁死锁，也不是卡钳永久硬件故障。

## 3. V2.12.0.32 已落地整改

### 3.1 冻结耐久前缀成为唯一正式义务

涉及：

- `Controller/EpbManager.cs`
- `Controller/EpbManager.WarningSnapshots.cs`
- `Controller/DaqPersistenceCoordinator.cs`

改动：

1. DAQ 故障首次登记时冻结 `CutoffPersistenceBoundary`；后续重试只读取该值，不再扩大。
2. 新增结构化 `DaqDurablePrefixResult`，明确输出：
   - `Boundary`
   - `Persisted`
   - `PendingHeadSequence`
   - `InFlightSequence`
   - `DurabilityBlocked`
   - `PendingPredicate`
3. `Persisted == frozen cutoff`、截止范围内无队头/在途批次且无写故障时立即判定冻结前缀完成。
4. 冻结前缀完成后，作废事故中断圈直接提交 `AbortedBySoftwareRecovery`，不再进入会重新读取 `LastDiskPublishedSequence` 的通用圈收尾。
5. 故障中断圈不计入正式完成数，原圈身份不允许污染新 Run 或新圈。

修复后的数据语义为：

```text
正式耐久义务 = 首次故障时冻结的 LastAcceptedSequence
截止后尾段   = Suppressed / TerminallyHandled
恢复验证批次 = 不得反向扩大正式耐久义务
```

### 3.2 圈终态收尾改为共享任务

旧 `CutoffCyclesFinalized` 只有 0/1/2 状态。一个调用正在执行时，后到调用看到 1 会立即返回 `false`，上层将“另一个所有者正在工作”误判为 `DaqPersistenceBoundaryPending`，提前增加恢复次数。

现在每个恢复上下文保存一个共享 `TaskCompletionSource<bool>`：

- 首个调用取得收尾所有权；
- 后到调用等待同一个结果；
- 成功后终态永久复用；
- 失败后才允许下一次有界重试；
- 旧 Run 取消后不得修改新 Run 的圈身份。

这消除了现场中“真实 10 秒圈收尾尚未结束，恢复次数却已经提前推进到第 3 次”的并发误判。

### 3.3 StopAll 接受冻结前缀与有限终态尾段

涉及：

- `Controller/EpbManager.FieldMetrics.cs`
- `Controller/EpbManager.cs`
- `Tools/validate_epb_field_gate.py`

旧条件：

```text
FinalBoundary == FrozenBoundary
```

该条件在只读 DAQ 为获取新鲜压力而继续产生批次时不可达。

新条件分两种情况：

1. 没有截止后尾段：`FinalBoundary == FrozenBoundary`，按普通耐久前缀闭合；
2. 存在截止后尾段：必须同时证明：
   - `SuppressAfter == FrozenBoundary`；
   - `SuppressThrough` 覆盖 `FinalBoundary`；
   - `Published >= FinalBoundary`；
   - `TerminallyHandled >= FinalBoundary`；
   - 冻结前缀 `Persisted >= FrozenBoundary`；
   - 截止范围内没有队头和在途所有者；
   - Raw 后台管线与持久化队列均已真正 Drain；
   - 没有永久数据连续性空洞、写故障或容量丢弃。

这不是用 Suppressed 水位冒充物理落盘。正式前缀仍必须真实写入；只有冻结点之后明确排除的非正式尾段使用 `TerminallyHandled` 证明。

### 3.4 修复 `Depth=0` 但同步写仍在途的假闭合

第二轮审查发现：持久化 worker 取走队头后，队列 `Depth` 可以变成 0，但同步 SQLite 写调用仍处于 `InFlight`。旧 StopAll 可能只根据 `Depth=0` 和历史 `Persisted` 放行。

V2.12.0.32 增加：

- `PersistenceQueueDrained`；
- `PendingHeadSequence`；
- `InFlightSequence`；
- 停止门禁要求截止范围内三者全部闭合。

因此写调用即使已出队，只要尚未形成明确终态，就不能被当成可重启或可交接状态。

### 3.5 双 DAQ 同时异常改为批次级协调

涉及：

- `Controller/EpbManager.DaqLiveness.cs`
- `Controller/DaqIncidentLatch.cs`
- `Controller/EpbManager.RecoveryCoordination.cs`
- `Controller/RecoveryCoordination.cs`

同一扫描检测到 Dev1/Dev2 同时异常时：

1. 两台设备共享同一个批次 `CorrelationId`；
2. 仍分别保存设备终态，终态去重键改为 `Device + CorrelationId`，防止先完成设备吞掉另一台；
3. 相同批次对同一液压组使用同一 `DAQ_BATCH:{CorrelationId}` 所有者；
4. 所有权使用引用计数，同优先级的两台设备不再互相取消；
5. 增加 `DaqRecoveryBatchBarrier`：两台设备都完成新鲜样本、持久化、数据连续性和断电电流验证前，任一设备都不得重新上电或重入正式节拍；
6. 任一设备在共同验证前取消或失败，另一台保持断能，交给有界恢复/整批回收收口。

### 3.6 旧 Run 不得在 StopAll 后重新拉起 DAQ

涉及：`IO.NI/TwoDeviceAiAcquirer.cs`

第二轮审查发现一个生命周期缝隙：

```text
旧恢复 StopDevice
StopAll StopDevice
旧恢复 StartDevice
```

原 `taskGate` 只分别保护 Stop 和 Start，没有覆盖 Stop→Start 整体，旧 Run 可能在 StopAll 停止设备以后补做 Start，造成最终边界继续增长。

现在每台设备新增独立生命周期门：

- 普通 Start；
- 普通 Stop；
- 恢复 Stop→Start；

三条路径使用同一把设备级门。StopAll 取得门并返回后，旧恢复不能再补做 Start。RunEpoch、上下文引用和该物理生命周期门共同防止旧 Run 控制新 Run。

### 3.7 有界恢复与进程回收保持有效

V2.12.0.31 已修复 V2.12.0.29 的无限局部恢复，本轮保留并复核：

- 第 1、2 次允许同进程局部恢复；
- 第 3 次失败打开一次 `UnattendedBatchRecycle`；
- 60 秒硬期限同样进入整批回收；
- 10 分钟内最多 3 次进程交接；
- 预算耗尽后保持全断能，并判定当前十万圈验收失败；
- DAQ、Timer、持久化等软件/外部设备故障不得冒充卡钳永久硬件报警。

第三轮审查进一步发现，通用基础设施恢复在异常后重新登记任务时，原实现会重新计算 60 秒期限。现改为首次进入恢复时保存单调时钟起点，后续重试、重新登记和异常回退均传递同一个起点；达到第 3 次失败或首次起点后的 60 秒，任一条件先满足即只发布一次 `UnattendedBatchRecycle`。

### 3.8 自动重启链保留最初授权身份

进程重启后会创建新的执行 RunId，但它不能被当作一次新的人工授权运行。第三轮审查发现，旧检查点会用新 RunId 覆盖原 RunId，而且多个启用通道重复上报 `Starting` 时可能重复重置重启历史，导致证据链断裂并可能重新获得重启预算。

现将检查点提升为 Schema V5，并明确保存：

- `RootRunId`：首次人工启动形成的授权运行链根身份；
- `ParentRunId`：本次进程交接前的直接父执行；
- `CurrentRunId`：当前进程实际执行身份；
- `RestartGeneration`：从 0 开始单调增加的进程交接代次；
- `RecoveryChainPendingStart`：恢复票据已消费、等待新进程第一次 `Starting` 的一次性状态；
- `RestartHistoryUtc`：跨进程保留的 10 分钟重启预算；
- `RecoveryNonceSha256` 和故障关联号：用于验收关联，不在日志中暴露可重放的原始 Nonce。

同一个 CurrentRunId 的多通道 `Starting` 现在是幂等操作；只有明确的新人工授权才会创建新 RootRunId、清空旧重启历史并从 Generation 0 开始。受控恢复子进程则保留 RootRunId，将旧 CurrentRunId 记为 ParentRunId，并只增加一次 Generation。

### 3.9 重新上电或公共节律重入失败立即安全回滚

第三轮审查发现：DAQ 新代次验证完成后，系统进入“程控电源重新使能、机械释放、重新加入公共节律”阶段；若这一阶段抛出异常，旧路径只记录异常并等待下一轮恢复，可能让程控电源在最长 60 秒恢复窗口内保持使能，或者在验证循环中重复尝试使能。

现对 `PowerEnableThenMechanicalRelease` 和 `RejoinAndCommit` 两个阶段设置强制回滚：

1. 立即暂停并取消圈推进；
2. 对本次受影响通道提交最高优先级 OFF；
3. 启动对应电源组断能；
4. OFF 请求被拒绝时安排受控后备断能；
5. 若处于自维护验证循环，向外抛出并进入既有有界失败计数，禁止循环内再次上电；
6. 若是独立恢复回调，只登记一次有界自维护，不形成无界重入。

### 3.10 持久化现场证据补齐队头和在途序号

结构化排空结果虽然已定义 `PendingHeadSequence` 和 `InFlightSequence`，但第三轮审查发现普通 Publish 状态事件没有填充这两个字段，现场日志可能只看到深度变化，无法判断是队头阻塞还是同步 SQLite 写仍在途。

现已在状态快照和 `FieldMetric` 中持续输出：冻结边界、Published、RawTransferred、Persisted、PersistenceHead、PersistenceInFlight、有限抑制区间、TerminallyHandled、恢复阶段、恢复次数、硬期限、RunEpoch 和最终结果。容量故障测试同时要求至少报告真实队头或在途序号。

### 3.11 现场门禁接受可证明的自动重启链，拒绝人工拼接

旧 Python 门禁简单要求验收区间内只有一个 RunId，这与“允许受控自动进程重启计入同一授权运行链”的验收定义冲突。现改为验证一棵严格的线性执行链：

- Generation 必须从 0 连续递增，不能跳代、重复或分叉；
- 每个子执行的 ParentRunId 必须等于上一执行的 CurrentRunId；
- 所有执行的 RootRunId 必须一致；
- 每个执行分别且只能有一个 Start 和一个终态；
- 子执行必须携带有效故障关联号和 64 位十六进制 Nonce 哈希；
- 父执行终态到子执行 Start 的交接间隔不得超过检查点 5 分钟有效期；
- 每个执行区间内部独立检查心跳，合法进程交接间隔不冒充进程内心跳冻结；
- 任意外来 RunId、缺失票据、错误父子关系、缺失终态或人工会话拼接仍判失败。

### 3.12 独立存活监督补上“历史回调空窗”证据

第四轮审查发现，仅检查监督器执行当下的 `CallbackAgeMs` 仍有漏检：如果整个进程或宿主线程暂停约 120—264 ms，DAQ 回调先恢复、20 ms 监督器后恢复，则监督器看到的当前年龄可能只有数毫秒，会错过刚刚发生的超限空窗。这与 V2.12.0.31 封存中“`CallbackIntervalMs≈264ms`，但恢复快照 `CallbackAgeMs≈11ms`”完全一致。

现由 DAQ 回调层单调记录每个设备、每个采集代次的：

- `CallbackGapEventCount`；
- `LastCallbackGapIntervalMs`；
- `LastCallbackGapMonotonicTicks`。

监督器同时检查“当前年龄”和“自上次确认后新增的历史空窗事件”。只要带电期间出现超过 100 ms 的新历史空窗，即使回调已经恢复，也按 `DaqCallbackGap` 先断能、再进入唯一恢复事务。首次给设备上电前会建立事件计数基线，避免把启动前的正常无回调时段误判为带电事故；证据只有在恢复上下文登记成功后才确认消费，登记异常不会永久吞掉故障。

配置值也不再允许放宽安全默认值：运行时强制 `WatchdogIntervalMs<=20`、`StaleThresholdMs<=100`。每个实际 `(RunId, PID)` 都在 SESSION Start 后输出一条绑定记录；现场门禁拒绝只在构造阶段、尚无 RunId 的孤立配置日志。

### 3.13 同进程恢复与进程恢复使用同一授权链、不同证据规则

旧检查点只完整描述了进程重启。第四轮审查发现，同进程整批恢复会被误当作一次新的人工授权，导致 RootRunId、重启代次、故障关联和剩余正式圈证据断裂。

现明确区分：

- `RecoveryMode=InProcess`：保留 RootRunId 和故障关联号，增加恢复代次，不要求进程 Nonce；
- `RecoveryMode=ProcessRestart`：除上述身份外，必须包含 Nonce 哈希和结构化 `PROCESS_RESTART` 交接证据；
- `RecoveryMode=ManualAuthorization`：只有人工明确开始新批次时才允许清空旧链并建立新 RootRunId。

同进程和进程恢复均从 SQLite 已耐久提交的成功正式圈重算剩余目标：检查点不得比数据库更乐观，数据库已领先时按数据库收敛；已完成通道不再重新启动；学习圈、资格圈和故障中断圈仍不计数。多个通道的 `Starting` 必须全部形成同一新 RunId 后才原子确认恢复成功，禁止部分通道启动就提前消费恢复票据。

### 3.14 双 DAQ 事故即使从不同入口首发，也归并到同一规范事务

双设备异常不一定由同一轮 20 ms 扫描首先发现：圈等待器可能先为 Dev1 建立上下文，随后独立监督器才发现 Dev2。仅在扫描器里共用一个新关联号无法合并已存在的上下文。

现采用两层归并：

1. 同一 RunId 内，两个设备首次异常时间或历史空窗单调时间相差不超过 100 ms 时，事故锁存自动复用最早的关联号；
2. 若两个恢复上下文已经分别存在，建立关联号别名表，全部解析到最早、已取得所有权的规范批次；屏障在所有别名下可见，但只存在一个批次 owner 和一个最终提交。

因此圈等待器、DAQ 回调、独立监督器无论谁先到，都不会再形成两个互相竞争的“恢复所有者”。

### 3.15 恢复确认与人工停止撤权改为原子且可跨进程

第四轮审查发现两个授权竞态：

1. 恢复线程先读到 `Pending=true`，人工停止随后撤销检查点，恢复线程再执行 Arm，可能把已经撤销的运行重新授权；
2. 人工停止的检查点落盘观察者原为异步。如果停止恰好发生在恢复父进程最后一次校验与 `Process.Start` 之间，父进程可能先退出，异步撤权尚未来得及写盘，子进程会读取旧票据。

整改后：

- `Arm(requireRecoveryPending:true)` 在同一检查点锁内检查 Pending、内存撤权标记并提交新 Run，消除“先 Load、后 Arm”的 TOCTOU；
- 人工停止先同步写入只做内存操作的 Run 撤权屏障并取消恢复序列，不把文件 I/O 放到高优先级硬件断能之前；
- 进程交接增加两个按 Nonce 命名的内核事件。子进程必须先接管跨进程撤权门并回执，父进程才允许退出；人工停止即使发生在 `Process.Start` 之后也会置位同一个事件；
- 子进程等待父进程退出后、读取检查点和初始化硬件前再次检查撤权门。未接管、已撤权或 5 秒内无回执时保持全断能并拒绝续测。

### 3.16 恢复提交后的观察性失败不再回收健康新批次

恢复成功的原子边界是“全部授权通道已启动且检查点已确认新 Run”。该边界之后，日志、UI 状态或观察者异常不能再执行 StopAll、重新消费票据或再次启动进程回收。

现用 `recoveryBatchCommitted` 明确划界：提交前异常进入既有安全回滚和有界进程回收；提交后异常只记录隔离错误，新批次继续运行。恢复进程路径同时移除了必须由现场点击确认的模态框，未授权、票据过期、预检失败和恢复预算耗尽均写结构化终态并保持安全停机。

同样的提交边界也应用于父子进程交接：子进程完成撤权门接管回执后，交接立即标记为不可逆提交；`ChildCreated` 日志不再执行同步 Flush，也不能把已成功创建的子进程拖回重试路径。若 `Environment.Exit` 本身异常，父进程先置位跨进程撤权门，确保子进程拒绝续测，再进入安全停机。

## 5. 保持不变的安全不变量

任何同进程恢复、DAQ 重建或进程交接均不得绕过：

1. 已带电通道优先执行高优先级 OFF；
2. 对应程控电源确认关闭；
3. DAQ 陈旧时不得使用冻结电流证明断电电流已经清零；
4. 压力证据陈旧时，只能在电机和电源已确认关闭后重建只读采集；
5. 新进程取得新鲜压力、完成机械释放和启动预检前不得重新上电；
6. 已由独立证据确认的卡钳永久硬件报警继续锁存；
7. 自动恢复不得使用“人工明确停止后的新批次”旁路跳过历史安全复核；
8. 学习圈、资格复核圈和故障中断圈不计正式完成数。
