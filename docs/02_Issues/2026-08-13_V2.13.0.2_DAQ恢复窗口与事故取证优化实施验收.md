# V2.13.0.2 DAQ 恢复窗口与事故取证优化实施验收

> 文档状态：实施完成，等待现场发布门禁与硬件长稳验收
>
> 当前 HEAD：`V2.13.0.2`
>
> 本任务未修改程序版本号、未提交 Git commit、未生成发布包。

## 结论先行

V2.13.0.2 已完成本轮 DAQ 恢复窗口证据隔离、持久化边界保护、存活日志降噪和双设备事故取证目录修复。最关键的行为变化是：

1. `FirstSuppressedSequence`、`LastSuppressedSequence`、`SuppressedRangeCount` 现在只表示当前/最近一次恢复窗口；同一进程内第二个窗口不再复用第一个窗口的历史首序号。
2. 新增进程累计的首序号、末序号和范围计数，并在状态快照、状态事件、事故 JSON、`FieldMetric` 中同时保留窗口级和累计级证据。
3. 活动截止点重复安装保持幂等；`SuppressAfter` 只允许把活动边界收紧，不允许扩大；`InstallCutoff` 仍拒绝扩大 FrozenBoundary。
4. Dev1、Dev2 的双窗口恢复均有回归覆盖，第二窗口的首个抑制序号必须大于该窗口 FrozenBoundary。
5. `BatchMerged` 转换日志按 Run/RunEpoch/Correlation/参与设备集合进行有界去重；带电设备首次真实 gap 仍为 `Trip`，未带电设备新观察到的 gap 仅写 `INFO`，且不触发恢复或断电。
6. 双 DAQ 事故证据使用确定性的 `RunId + CorrelationId` 根目录，并将设备身份放入上下文键和 phase 目录名，避免 Dev1 终态过早清理后 Dev2 另起根目录。

代码级回归与构建结果达到本轮验收门槛；这不等价于完成 24/72 小时硬件长稳、现场故障注入、发布包清单或独立 Watchdog journal 验收。

### 1.2 实施方式

本轮采用 SOL 的“设计—审查—并行执行—集成验证”策略：主代理先固定边界和不变量，再由 Luna workers 分别执行持久化窗口、DAQ liveness、事故取证及对应测试；主代理完成共享工作树整合、冲突审查和最终测试核对。所有 worker 均在共享工作树中工作，未回退其他未提交修改。

### 1.3 不在本次范围内

- 不改变控制时序、断电动作、报警阈值或物理电源策略。
- 不把 `INFO` 观察日志解释为持久化或 DAQ 已恢复。
- 不把代码回归测试当作 24/72 小时硬件长稳或真实磁盘/DAQ 故障注入的替代品。
- 不在本任务中生成发布包、发布清单、签名或部署介质。

## 2. 已实施的代码变化

### 2.1 恢复窗口证据与进程累计证据拆分

`DaqPersistenceCoordinator.DeviceQueue` 和 `DaqPersistenceStateChanged` 现在分别维护两组字段：

| 证据层级 | 字段 | 语义 |
|---|---|---|
| 当前/最近窗口 | `SuppressedBatchCount` | 当前恢复窗口内被明确排除的批次数；窗口关闭后保留最近窗口值。 |
| 当前/最近窗口 | `FirstSuppressedSequence` | 当前/最近窗口第一个被排除的序号。 |
| 当前/最近窗口 | `LastSuppressedSequence` | 当前/最近窗口最后一个被排除的序号。 |
| 当前/最近窗口 | `SuppressedRangeCount` | 当前/最近窗口内的非连续排除范围数。 |
| 进程累计 | `CumulativeSuppressedBatchCount` | 设备在本进程内所有恢复窗口的排除批次总数。 |
| 进程累计 | `CumulativeFirstSuppressedSequence` | 本进程内该设备最早被排除的序号。 |
| 进程累计 | `CumulativeLastSuppressedSequence` | 本进程内该设备最晚被排除的序号。 |
| 进程累计 | `CumulativeSuppressedRangeCount` | 本进程内所有窗口的排除范围总数。 |

具体语义如下：

- 只有在前一个 suppression window 已经关闭、随后真正开始新窗口时，才同时清零 `SuppressedBatchCount` 和三项当前窗口 First/Last/Range 字段。
- `ResumeAdmission` 只是把有限迟到尾段封闭到 `SuppressThroughSequence`，不会提前清除最近窗口证据；首个严格超过该有限上界的批次才完成窗口关闭。
- 同一活动 cutoff 的 `InstallCutoff` 或 `SuppressAfter` 重装不会清除窗口证据；它可以更新调用方提供的运行身份，但不重复初始化窗口计数。
- `RecordSuppressedUnderGate` 同时更新窗口级和累计级计数。每个新窗口的第一个抑制批次都会增加累计范围，即使它在序号上恰好紧接上一个窗口；同一窗口内出现非连续序号时，窗口范围和累计范围都会增加。
- 所有 `long` 计数和序号继续使用 `Interlocked.Read/Exchange/Increment`，保留 32 位生产进程下的原子访问约束。

### 2.2 活动边界的幂等、收紧与不可扩大

- `InstallCutoff` 对活动 FrozenBoundary 保持原有不可变语义：重复安装相同边界可幂等返回；请求更大的边界发布 `RecoveryBoundaryContradiction` 并保持原边界不变。
- `SuppressAfter` 用于 StopAll/永久 gap 收尾时，允许把活动边界单调收紧到更早序号；收紧过程不重置当前窗口证据。对更晚边界不扩张，保留更严格的已有边界。
- 以上逻辑仍在 `SuppressionGate` 内与 Enqueue 最终提交线性化，不改变“已接收且不超过 FrozenBoundary 的批次必须真实写盘”的前缀证明。

### 2.3 Dev1/Dev2 第二窗口回归修复

新增 `SuppressionEvidenceResetsPerWindowAndAccumulates` 回归，分别覆盖 Dev1、Dev2，并交叉使用 `SuppressAfter` 与 `InstallCutoff` 路径。每个设备均验证：

- 第一个窗口产生首/末/范围和累计证据；
- 重装同一活动 cutoff 不擦除当前窗口证据；
- 活动 `SuppressAfter` 收紧边界后仍保留当前窗口证据；
- 通过有限迟到尾段关闭窗口后，第二窗口从干净的当前证据开始；
- 第二窗口满足 `FirstSuppressedSequence > SuppressAfterSequence`（即本窗口首个抑制序号位于 FrozenBoundary 之后）；
- 累计批次、累计首序号、累计末序号和累计范围跨两个窗口连续保留。

### 2.4 边界矛盾 first-wins 与原因发布

`EpbManager.TryCaptureFirstBoundaryContradiction` 为每个恢复上下文提供一次性提交门：并发到达的多个矛盾只允许第一个原因被锁存和发布，后续原因不会覆盖首个原因，也不会重复发布同类错误。安全终态仍是保持事故圈作废语义、禁止扩大边界或继续同类重试。

### 2.5 DAQ 存活日志和 gap 严重度

- `BatchMerged` 日志按 `RunId + RunEpoch + CorrelationId + 参与设备集合 + 结果` 去重；`Trip` 额外携带设备/代次 transition token。去重门最多保留 32 个键，按 Run/RunEpoch 切换自动清理，避免故障风暴造成无界内存或重复状态跃迁。
- 带电设备的首个真实回调 gap 仍走原有 `DaqCallbackGap`/`Trip` 保护路径；本轮没有把带电 gap 降级为 INFO，也没有减少断电或恢复动作。
- 未带电且不在恢复中的设备，首次观察只建立 gap baseline；只有之后出现新的、超过既有阈值的 gap 才记录 `ObservedUnenergizedGap` INFO。该 INFO 不触发恢复、不触发断电、不改变带电安全判定。

### 2.6 双设备事故证据身份和目录

- 事故上下文键由 `RunId:CorrelationId:Device` 组成，Dev1/Dev2 的逻辑证据上下文相互独立。
- 物理根目录由 `Run-{RunId:N}-Incident-{CorrelationId:N}` 确定性生成；同一 Run/关联号的两个设备共享同一根目录，不因终态到达顺序而分裂成两个时间戳目录。
- trigger、recovery、terminal 等 phase 目录名包含规范化设备 token（例如 `Dev1`/`Dev2`），便于人工和脚本按设备核对；Dev1 先终态不会把 Dev2 的迟到提交导向第二个根目录。
- 事故 JSON 新增：`cumulativeFirstSuppressedSequence`、`cumulativeLastSuppressedSequence`、`cumulativeSuppressedRangeCount`；原有窗口级 JSON 字段保持不变。
- `FieldMetric` 新增兼容性追加 token：`SuppressedCumulativeFirst`、`SuppressedCumulativeLast`、`SuppressedCumulativeRanges`；原有 `SuppressedFirst`、`SuppressedLast`、`SuppressedRanges` 保留。

## 3. 安全不变量与不可回归性质

以下不变量是本次验收的硬约束：

1. 不降低任何带电 DAQ 陈旧、回调 gap、过流、断电确认或恢复超时阈值；未带电 INFO 观察路径不能绕过原有带电 Trip 门。
2. 带电设备首次真实 gap 仍然是 `Trip`，不能被“首次观察 baseline”逻辑吞掉。
3. 未带电新 gap 只能产生低严重度观察信息，不得伪装成恢复成功，也不得触发恢复、断电或报警终态。
4. `Persisted`、`LastPersistedSequence` 和 DurablePrefix 不能因 suppression 计数增长而伪推进；明确排除的批次只能推进 `LastTerminallyHandledSequence`，不能推进物理写盘水位。
5. FrozenBoundary 不得扩大。`InstallCutoff` 对扩大请求 first-wins 地保留原边界；StopAll 只能通过 `SuppressAfter` 收紧边界。
6. 所有 `Sequence <= FrozenBoundary` 的已接纳批次必须真实写入；冻结边界之后的尾段必须留下明确 suppression 审计。
7. Dev1、Dev2 的事故证据身份和窗口证据不得互相污染；相同 Run/关联号的根目录必须确定性一致。
8. BatchMerged 去重状态必须有界并按运行代次隔离，不能把旧 Run 的日志状态带入新 Run。
9. 安全动作排序不变：暂停、撤销运行所有权、提交 OFF/Disable、等待和排空等既有动作不因日志降噪而跳过。

## 6. 风险 P1/P3 的前后映射

### P1：同进程第二次局部恢复被历史窗口证据阻断

**此前风险：** 第一次恢复留下的 `FirstSuppressedSequence` 被第二次恢复边界校验复用；新窗口的边界本身正确，却可能因为历史首序号而产生 `SuppressionMismatch`/`RecoveryBoundaryContradiction`，进而把可局部恢复事件升级成整批 StopAll。

**本轮代码修复：** 当前窗口 First/Last/Range 与进程累计 First/Last/Range 分离；仅在旧窗口关闭后初始化新窗口；第二窗口首个抑制序号独立于第一窗口；FrozenBoundary 仍不可扩大，StopAll 仍可收紧。这一 P1 的代码根因已由 Dev1、Dev2 双窗口回归覆盖。

### P3：取证身份和 liveness 观察被并发/重复状态污染

**此前风险：** Dev1/Dev2 的终态和 phase 可能争用或复用错误根目录；同一 Run 的 BatchMerged 重复刷屏；未带电设备缺少独立 gap 观察，首次看到的历史 gap 语义不清，可能被追溯性地当作当前需要记录的事件（不是升级为 Trip）。

**本轮代码修复：** 证据上下文加入设备，物理根目录固定为 RunId+CorrelationId，phase 显示设备；BatchMerged 去重按运行身份且有界；未带电 gap 建立 baseline 后只报告新 INFO；带电首 gap 继续 Trip。P3 的代码路径已由 50/50 incident 回归和 101/101 liveness 回归覆盖。

### 仍不能由本次代码验收闭合的事项

- **EPB5 物理趋势：** 高平台、负载上升停滞或机械/电源异常仍需现场物理证据，不能因日志降噪或恢复窗口修复而宣称消失。
- **发布清单与部署证据：** 现场 EXE、配置、依赖、哈希和版本清单仍需由发布流程生成并核对；本任务没有发布包。
- **24/72 小时硬件长稳：** 代码回归不能替代真实 DAQ、磁盘、CPU/GC、NI 驱动、电源和液压负载下的连续运行。
- **真实故障注入：** 仍需验证映射故障、写盘超时、队列满、DAQ gap、双设备同时终态和进程重启。
- **独立 Watchdog journal：** 主进程代码不能单独证明进程完全卡死时的外部监督、授权、日志落盘和默认断能；该项需要独立 Watchdog 构建、部署和现场演练。

## 8. 回滚指导

若现场出现新的边界扩大尝试、带电 gap 未 Trip、双设备证据串根、StopAll 安全排序异常或无法证明的物理故障：

1. 立即按现有安全流程停止试验并保留输出关闭、暂停和恢复状态证据；不要为了“清日志”删除事故目录、SQLite、Raw 或 Watchdog 文件。
2. 保存当前运行目录、`FieldMetric`、事故 JSON、完整日志和发布清单，标记 RunId、CorrelationId、Device 及时间。
3. 使用已验证的旧版程序和对应配置进行受控回滚；旧版与新版目录、数据卷和清单分离，禁止运行中覆盖文件。
4. 回滚后先做短时空载/受控样本验证，再决定是否恢复试验；任何物理趋势仍需单独排查。
5. 将触发回滚的最小复现输入加入后续故障注入，不以回滚后“暂时没有复现”作为代码验收结论。

本次任务只产生上述实施验收文档和工作树中的代码/测试变更记录；没有提交 commit，也没有生成 release package。
