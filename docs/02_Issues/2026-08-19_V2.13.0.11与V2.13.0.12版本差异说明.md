## 2. 版本差异总览

| 能力 | V2.13.0.11 | V2.13.0.12 | 结果 |
|---|---|---|---|
| Timer 事件身份 | 只携带通道和 Timer 引用，匿名订阅难以解绑 | 实例、TimerGeneration、RunEpoch、观察登记四项校验 | 旧 Timer 迟到事件不能覆盖新状态 |
| `Recovering -> Paused` | 可被 Timer 的迟到 `Paused` 覆盖 | 中央状态入口要求有效人工暂停 owner | 消除 EPB4 孤儿暂停 |
| 恢复 cohort | 执行时按易变 UI 状态再次过滤 | 故障发生时冻结事务成员，仅排除耐久终态/人工暂停 | 不再只恢复 EPB5 而丢失 EPB4 |
| 活动圈计数 | `_currentCycleNumberByChannel.Count` 被计入 `SoftwareRecoveryCount` | 新增 `ActiveCycleCount`，与恢复计数完全分离 | 健康运行不再假报恢复 |
| `RecoveryActive` | 只要任一恢复布尔/计数非零即可为 true | 必须具有 owner 或结构化恢复生命周期/身份 | 从生产端阻断假恢复遥测 |
| sidecar 假恢复处理 | 假恢复停滞后可能全局 `RequestStopAll` | 识别 `RecoveryTelemetryInconsistent`，健康进度下禁止全局接管 | 阻断所有卡钳误停链 |
| 单通道孤儿监督 | 其他通道有心跳时可能漏检 | 5 秒识别无人工 owner 的 Paused 或缺少 Timer/Runner | 独立看门狗可识别 EPB4 类异常 |
| 恢复失败分类 | 不区分永久错误和瞬态错误 | 永久 0 次、瞬态最多 5 次、未知软件最多 2 次 | 重试与故障性质匹配 |
| 失败预算 | 主要为进程内计数，sidecar 重启可能重置上下文 | 按失败 fingerprint 写入 session journal 并恢复 | 同会话预算耐久化 |
| 熔断后的行为 | 2/5/15 分钟 `CircuitProbe` 持续启动主程序 | `RecoveryBlocked` 为真正终态，不再启动主程序 | 消除无限恢复循环 |
| 恢复失败证据 | 主要上报原因字符串 | code、permanent、detail、配置 SHA-256 和完整异常 | sidecar 可机器判定错误类型 |
| EPB 记录容器 | 公开可变 `List<EpbTestRecord>` | 线程安全、按 Id 唯一的 `EpbTestRecordCollection` | 类型层阻止重复 Id |
| 启动计划 | 遍历集合并构造字典，重复 Id 可抛异常 | 锁内校验 1..12 并创建原子字典快照 | 消除重复键启动失败 |
| 版本信息 | 主程序/Watchdog 为 2.13.0.11 | 主程序/Watchdog/ApplicationVersion 均为 2.13.0.12 | 组件版本一致 |

## 3. EPB4 孤儿暂停差异

### 3.1 V2.13.0.11 行为

V2.13.0.11 的 Timer 事件采用匿名订阅：

```csharp
timer.StateChanged += update => OnTimerRuntimeStateChanged(channel, timer, update);
```

恢复路径移除 EPB4 的 Timer 和 Runner、发布 `Recovering` 后，旧 Timer 仍可能迟到发布 `Paused`。旧事件处理没有完整验证：

- 事件来源是否仍是 `_timers[channel]` 的当前实例；
- Timer 是否仍属于当前代次；
- Timer 是否属于当前 RunEpoch；
- 事件 delegate 是否已经解除；
- `Recovering` 是否允许转换为普通 `Paused`。

现场实际结果为：

```text
EPB4 Recovering
  -> 旧 Timer 迟到 Paused
  -> EPB4 显示 Paused
  -> Timer=False、Runner=False、Energized=False
  -> 恢复筛选排除 EPB4
  -> 人工 RUN 又因不存在人工暂停 checkpoint/Timer/Runner 而失败
```

因此 V2.13.0.11 界面的“暂停”不是人工暂停，而是业务状态与资源事实不一致。

### 3.2 V2.13.0.12 行为

[EpbManager.TimerRuntimeHealth.cs](../../Controller/EpbManager.TimerRuntimeHealth.cs) 新增每通道 Timer 观察登记：

```text
Timer instance
TimerGeneration
RunEpoch
StateChanged delegate
```

每次 Timer 激活都会递增 generation 并保存可注销 delegate；移除 Timer 时先解除实际 delegate，再停止 Timer。事件到达时依次校验：

1. 来源 Timer 仍是当前活动实例；
2. 来源和观察登记完全匹配；
3. 来源 generation 等于当前 generation；
4. 来源 RunEpoch 等于当前 RunEpoch；
5. 当前为 `Recovering` 时拒绝 `PausePending/Paused`。

任一条件失败只记录：

```text
StaleTimerEventIgnored
```

并附带原因码：

```text
TimerInstanceNotActive
TimerObserverRegistrationStale
TimerGenerationStale
TimerRunEpochStale
RecoveryOwnsChannelLifecycle
```

[EpbManager.cs](../../Controller/EpbManager.cs) 又在统一状态发布入口增加第二道门禁：没有有效人工暂停 owner 时，任何 `Recovering -> PausePending/Paused` 都被拒绝并记录 `ChannelRuntimeTransitionRejected`。

两层门禁的区别是：Timer 门禁阻止已知的旧资源事件，中央状态门禁阻止未来其他调用路径制造同类非法转换。

### 3.3 操作表现差异

| 场景 | V2.13.0.11 | V2.13.0.12 |
|---|---|---|
| 程序内部暂停 Timer | 可能直接显示普通“暂停” | 业务状态保持 `Recovering` |
| 旧 Timer 迟到事件 | 可能覆盖状态 | 记录并忽略 |
| 真正人工暂停 | 依赖 `_channelPausedUtc` | 仍建立人工 owner，允许恢复 |
| 无人工 owner 的 Paused | sidecar 可能视为合法 | 5 秒后触发 `ChannelPausedWithoutManualOwner` |
| 授权通道 Timer/Runner 缺失 | 可能因其他通道心跳而漏检 | 5 秒后触发 `ChannelExpectedRuntimeMissing` |

## 4. 恢复 cohort 差异

### 4.1 V2.13.0.11

恢复调度虽然最初能够获得 EPB4/5 同组集合，但执行前再次依据实时 UI 生命周期状态过滤，只接受 `Recovering/SystemFault`。EPB4 被迟到事件改为 `Paused` 后从事务中消失，最终只恢复 EPB5。

### 4.2 V2.13.0.12

[EpbManager.RecoveryCoordination.cs](../../Controller/EpbManager.RecoveryCoordination.cs) 把输入通道解释为故障发生时冻结的事务 cohort。执行过程中，`Running`、内部 `Paused`、`Recovering` 或状态迟到都不能删除成员。

只有以下耐久事实可以排除成员：

```text
NotEnabled
AlarmStopped
InterlockStopped
ManualStopped
Completed
StartBlocked
明确的人工暂停 owner
```

因此冻结 `[4,5]` 后，恢复结果只能覆盖完整事务成员，不会因为 EPB4 的易变显示状态而退化成 `[5]`。

## 5. 所有卡钳误停差异

### 5.1 V2.13.0.11 的触发原因

V2.13.0.11 将正常执行中的 `_currentCycleNumberByChannel.Count` 加入 `SoftwareRecoveryCount`。现场五个通道正常运行时形成：

```text
Active channels = 5
SoftwareRecoveryCount = 5
RecoveryActive = true
RecoveryOwnerCount = 0
DaqRecoveryCount = 0
RecoveryStage/Incident/Context = empty
```

旧 sidecar 的恢复进度签名只看到“软件恢复对象数量=5”，并不包含正常机械圈号。数量持续不变达到旧判据后，被判定为 `ExternalRecoveryStageStalled`，随后 `BeginTakeover` 发送一次全局 `RequestStopAll`，导致全部卡钳安全断电。

### 5.2 V2.13.0.12 主程序侧修复

[ChannelRuntimeState.cs](../../Controller/ChannelRuntimeState.cs) 和 [EpbManager.cs](../../Controller/EpbManager.cs) 新增 `ActiveCycleCount`：

```text
ActiveCycleCount = 正常执行中的机械圈数量
SoftwareRecoveryCount = 真实的软件恢复对象数量
```

两者不再相加。正常五通道运行必须得到：

```text
ActiveCycleCount=5
SoftwareRecoveryCount=0
RecoveryActive=false
```

逻辑静止判定仍检查 `ActiveCycleCount=0`，所以拆分字段不会让正在执行的圈被误判为已经完全清场。

[FrmEpbMainMonitor.UnattendedRecovery.cs](../../MTTfTest/FrmEpbMainMonitor.UnattendedRecovery.cs) 使用结构化策略生成 `RecoveryActive`：

- 人工暂停时为 false；
- DAQ recovery 或 recovery owner 存在时可以为 true；
- 仅有软件计数时，还必须存在恢复生命周期或事故身份；
- 单独一个非零原始计数不能证明正在恢复。

### 5.3 V2.13.0.12 sidecar 侧修复

[WatchdogPolicy.cs](../../Watchdog.Protocol/WatchdogPolicy.cs) 检查下列结构证据：

- `DaqRecoveryCount` 或 `RecoveryOwnerCount`；
- `RecoveryCode/Stage/Incident/Context`；
- 通道是否处于 `Recovering/ResumeChecking/SystemFault`。

如果心跳声称 `RecoveryActive=true`，但上述证据全部不存在，则判为非结构化声明。sidecar 记录：

```text
RecoveryTelemetryInconsistent
```

并请求一次状态刷新；在普通机械进度健康时不允许由此触发全局 StopAll。

这是双重防御：即使以后主程序又错误生成恢复布尔值，sidecar 也不会重演 V2.13.0.11 的全部卡钳误停。

## 6. 看门狗无限恢复差异

### 6.1 V2.13.0.11

V2.13.0.11 对恢复失败主要使用统一重试。连续失败达到阈值后虽然显示熔断，却仍调用 `ScheduleCircuitProbe()`：

```text
第 1 次 CircuitProbe：等待 2 分钟
第 2 次 CircuitProbe：等待 5 分钟
第 3 次及以后：等待 15 分钟
每次都重新启动完整 MTTFTest.exe
失败后再次排程
```

重复 EPB Id 属于确定性错误，相同二进制和相同配置反复启动不会自行成功。因此旧策略只降低了重试频率，没有形成终态。

### 6.2 V2.13.0.12 失败分类

V2.13.0.12 新增三类策略：

| 分类 | 识别示例 | 同一 fingerprint 主程序自动重启上限 |
|---|---|---:|
| 永久/确定性 | `ConfigDuplicateEpbId`、`ConfigEpbRecordInvariant`、checkpoint 不变量、包/程序集校验错误 | 0 |
| 瞬态基础设施 | `HardwareUnavailable`、`DaqUnavailable`、电源通信、Timeout、PortInUse、临时 attach 失败 | 5 |
| 未分类软件异常 | 未识别的启动异常或程序错误 | 2 |

允许重试的错误使用 5/15/30/60 秒进程重启退避。达到同一 fingerprint 的预算后进入持久 `RecoveryBlocked`。

### 6.3 V2.13.0.12 持久终态

[WatchdogHost.cs](../../MTTFTest.Watchdog/WatchdogHost.cs) 在 session journal 中新增：

```text
RecoveryBlocked
RecoveryFailureCode
RecoveryFailurePermanent
RecoveryFailureFingerprint
RecoveryFailureMaxProcessRelaunches
RecoveryFirstFailureUtcTicks
RecoveryLastFailureUtcTicks
RecoveryBlockedUtcTicks
```

sidecar 重启时读取同一 session 的既有 journal，恢复阻断状态和失败预算。阻断后：

1. 所有输出继续保持 OFF；
2. 过渡窗口显示“自动恢复已阻断，设备保持安全”；
3. 明确提示“不会再启动主程序”；
4. `BeginTakeover`、退出后重拉、重启循环、退避结束和 `Process.Start` 锁内均检查 `RecoveryBlocked`；
5. 已移除 `ScheduleCircuitProbe` 和通过 `CircuitProbe` 调用重启循环的路径；
6. `AllowsMainProcessCircuitProbe=false`。

保留的 `SelectCircuitProbeDelayMinutes()` 仅是协议兼容辅助方法，生产 WatchdogHost 已无调度调用，不能据此启动主程序。

### 6.4 UI 和运维差异

| 场景 | V2.13.0.11 | V2.13.0.12 |
|---|---|---|
| 永久配置错误 | 重复显示主程序加载/恢复次数 | 立即进入明确阻断 |
| 超过重试预算 | 仍显示若干分钟后继续 | 显示不会再启动主程序 |
| sidecar 重启 | 可能重新开始恢复序列 | 同 session 恢复既有阻断和预算 |
| 解除方式 | 等待下一次探测 | 处理原因后由操作员创建新会话 |

## 7. EPB 重复键和启动计划差异

### 7.1 V2.13.0.11

V2.13.0.11 的 `EpbRecords` 是公开可变 `List<EpbTestRecord>`。加载、UI 回写、保存或并发补齐后，其他调用者仍可再次插入相同 Id。启动路径构造 `Dictionary<int,int>` 时，重复键会抛出：

```text
已添加了具有相同键的项。
```

即使在若干边界做归一化，也无法从类型上保证归一化之后不会再次被污染。

### 7.2 V2.13.0.12

新增 [EpbTestRecordCollection.cs](../../Config/EpbTestRecordCollection.cs)：

- 所有写操作在集合锁内执行；
- 相同 Id 的 `Add/AddRange/ReplaceAll/索引赋值` 执行单调证据合并，不保留第二项；
- 枚举基于快照，避免 UI、保存、启动并发时出现“集合已修改”；
- `EpbTestRecord.Id` setter 收紧为 `internal`；
- `TestConfig.EpbRecords` 只暴露只读集合引用，不允许替换为任意 List；
- 加载器先保留原始行做重复/非法 Id 诊断，再原子替换运行时集合；
- UI 回写使用一次 `ReplaceAll`，读者只看到替换前或替换后的完整快照。

新增 `CreateEpbStartPlan(fallbackTotalCount, expectedCount=12)`：

1. 在同一锁边界内补齐和归一化；
2. 校验记录数恰好为 12；
3. 校验 Id 精确等于 1..12；
4. 创建新的 `Dictionary<int,int>` 快照；
5. UI 或保存线程之后的修改不能改变本次启动计划。

Controller 初始计划和界面启动路径统一使用该方法，不再各自遍历可变集合。

## 8. Watchdog 协议差异

协议版本号仍为 `2`，最低兼容版本仍为 `1`。V2.13.0.12 采用 JSON 可选字段扩展，没有删除旧字段。

### 8.1 心跳新增字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `ActiveCycleCount` | `int` | 正常活动机械圈，仅用于运行/残留诊断，不参与 `RecoveryActive` |

### 8.2 恢复失败消息新增字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `RecoveryFailureCode` | `string` | sidecar 可判定的错误码 |
| `RecoveryFailurePermanent` | `bool` | 是否属于不能通过相同进程重启修复的永久错误 |
| `RecoveryFailureDetail` | `string` | 完整错误详情或堆栈 |
| `RecoveryFailureContextSha256` | `string` | 与失败相关的项目配置 SHA-256 |

旧消息缺少这些字段时，V2.13.0.12 sidecar 会按原因字符串兼容分类；协议往返测试覆盖 V1/V2 兼容。但是部署时仍必须同时替换：

```text
MTTFTest.exe
MTTFTest.Watchdog.exe
MTTFTest.Watchdog.Protocol.dll
全部同包依赖
```

“能够反序列化旧消息”不等于允许混用版本。V2.13.0.11 主程序配 V2.13.0.12 sidecar 会缺少完整恢复身份；V2.13.0.12 主程序配旧 sidecar 又会失去假恢复抑制和持久阻断能力。

## 9. 结构化错误证据差异

V2.13.0.12 的无人值守恢复入口捕获异常后：

1. 使用 `GetBaseException()` 获取根异常；
2. 按恢复失败策略分类；
3. 保存完整 `ex.ToString()`，不再只有 message；
4. 计算项目 `TestConfig.xml` 的 SHA-256；
5. 向 sidecar 发送结构化 `RecoveryAttemptFailed`；
6. checkpoint 拒绝明确上报永久 `CheckpointInvariant`。

[RuntimeBuildIdentity.cs](../../Controller/RuntimeBuildIdentity.cs) 的文件 SHA-256 计算方法改为公开复用，使恢复入口与构建身份使用同一算法。

## 10. 配置、数据和兼容性影响

### 10.1 项目 XML

- 没有引入新的 EPB XML 节点；
- V2.13.0.11 项目配置可由 V2.13.0.12 加载；
- 重复容器、重复 Id 和非法 Id 会在加载边界诊断并归一化；
- 保存时仍写回单一、按通道排序的唯一记录集合；
- 升级前仍必须备份 `TestConfig.xml` 和数据库。

### 10.2 二进制/API 兼容性

`TestConfig.EpbRecords` 从 `List<EpbTestRecord>` 改为 `EpbTestRecordCollection`，setter 被移除；`EpbTestRecord.Id` 的 setter 从 public 改为 internal。仓库内所有项目已同步重编译并通过测试，但任何仓库外插件若直接：

- 替换 `EpbRecords` 整个 List；
- 调用仅属于 `List<T>` 的 API；
- 从外部程序集修改 `record.Id`；

都需要按新 API 调整和重新编译。这是为了建立唯一性不变量而有意收紧的接口，不应通过恢复公共 setter 来兼容不安全调用。

### 10.3 Watchdog journal

journal schema 仍为 2，新字段为 JSON 增量字段。旧 journal 缺失字段时默认未阻断、计数为 0。升级部署建议结束旧会话后创建新 session，不应复制或手工删除 journal 来绕过 V2.13.0.12 的阻断状态。

### 10.4 数据库与控制参数

本次差异没有修改：

- SQLite 业务表结构；
- 正反向电流阈值；
- 压力目标与容差；
- 15 秒试验周期和错峰策略；
- DAQ 采样频率与控制滤波；
- 高优先级安全 OFF 的基本判据；
- 正式圈、机械圈和事故圈的业务定义。

因此 V2.13.0.12 的核心变化是恢复状态一致性、监督和配置唯一性，不是重新标定卡钳控制算法。

## 14. 现场验收重点

### 14.1 正常运行

- 五通道运行时允许 `ActiveCycleCount=5`，但必须保持 `SoftwareRecoveryCount=0`；
- 没有真实恢复 owner 时 `RecoveryActive=false`；
- 不得出现 `ExternalRecoveryStageStalled -> RequestStopAll`；
- 正常长稳中 `RecoveryTelemetryInconsistent=0`。

### 14.2 EPB4/5 同组故障注入

分别注入 Dev1 回调空窗 120ms、1.2s、3.5s：

- 样本陈旧后先安全 OFF；
- 只生成一个根事故和 recovery owner；
- EPB4/5 完整 cohort 一起恢复或一起安全阻断；
- 不出现 `Paused + ManualPauseOwner=false + Timer=false + Runner=false`；
- 旧 Timer 迟到事件只能产生 `StaleTimerEventIgnored`；
- 30 秒内恢复成功或进入明确 `RecoveryBlocked`。

### 14.3 永久错误

注入重复配置、损坏 checkpoint 或包校验错误：

- 自动启动主程序次数为 0；
- UI 显示不会再启动主程序；
- 观察 30 分钟新增恢复 PID=0；
- 重启 sidecar 后同 session 仍为 `RecoveryBlocked`。

### 14.4 瞬态和未知错误

- 瞬态基础设施同 fingerprint 最多 5 次；
- 未分类软件错误同 fingerprint 最多 2 次；
- 达预算后持久阻断；
- 不得进入 2/5/15 分钟无限 CircuitProbe。

## 15. 已知边界和未改变事项

V2.13.0.12 已关闭“DAQ 空窗导致的软件状态丢失、误 StopAll、启动失败后无限拉起”故障链，但没有声称已经确定 Dev1 约 1.172 秒回调空窗的底层来源。该问题仍需：

- NI BeginRead/EndRead/Rearm 时间线；
- NI Task 状态和驱动错误码；
- Windows ETW、DPC/ISR、GC pause 和线程堆栈；
- Dev1/Dev2 设备、端口、线缆和供电 A/B；
- 经过验证的 NI 驱动升级/回退。

V2.13.0.12 的目标是：即使底层空窗再次发生，软件也必须安全断电、保持完整恢复 cohort、拒绝旧事件污染，并在不能恢复时有限收敛到人工处理，而不是无限重启。

## 16. 回退原则

若 V2.13.0.12 现场验收失败：

- 立即停止并保存完整日志、journal、dump、manifest 和项目配置；
- 不得因 V2.13.0.11 曾长期运行就回退到其无人值守模式；该版本存在已确认的误 StopAll 和无限恢复路径；
- 如必须临时恢复生产，应使用经过验证的稳定包并转为有人值守；
- 不得混用 V2.13.0.11 和 V2.13.0.12 的主程序、Watchdog 或 Protocol DLL；
- 不得通过删除 V2.13.0.12 journal 强行清除 `RecoveryBlocked`，应先修复失败原因并由操作员创建新会话。

## 17. 最终结论

V2.13.0.12 不是简单增加超时或重试次数，而是改变了四个关键不变量：

1. 通道业务状态只能由当前 Timer 代次和合法 owner 修改；
2. 正常活动圈永远不是恢复对象，恢复布尔值必须有结构证据；
3. 永久错误和超预算错误必须进入耐久终态，不允许再启动主程序；
4. EPB 通道 Id 在数据结构和启动快照两个层面均保持唯一。

代码和自动化测试层面，V2.13.0.12 已完成上述差异并通过 454/454 全量回归。发布状态仍应标记为“代码已完成，待正式包和现场故障注入/长稳验证”；只有通过实机注入、72 小时/100,000 圈门禁和 package manifest 校验后，才能正式替代 V2.13.0.11 并关闭现场问题。
