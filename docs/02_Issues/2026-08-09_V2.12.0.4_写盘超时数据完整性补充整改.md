# V2.12.0.4 写盘超时数据完整性补充整改

> **后续状态：** 本文保留 V2.12.0.4 的历史整改证据。V2.12.0.5 补齐主要恢复入口，V2.12.0.6 又封闭 Timer、硬期限清场、活动圈上限及正式/报警/学习圈终态旁路；现场验证版本应使用 V2.12.0.6。详见 [V2.12.0.6 全圈终态耐久一致性完成性整改](./2026-08-09_V2.12.0.6_全圈终态耐久一致性完成性整改.md)。

## 1. 结论

V2.12.0.3 已解决现场频繁自维护的主要故障链，但完成性审计发现一个会影响无人值守数据完整性的尾部缺口：当磁盘或网络存储连续不可写超过 `DaqPersistenceRecoveryTimeoutMs` 时，旧 worker 发布 `DaqPersistenceRecoveryTimeout` 后直接返回，随后 `finally` 无条件释放当前批次并推进 `LastPersistedSequence`。

这会产生三个后果：

1. 当前批次并未写入，却被停止流程当作“已持久化”。
2. 磁盘稍后恢复时只能继续写后续数据，失败圈中间留下不可补偿的数据缺口。
3. worker 在批次归还对象池后才读取 `batch.Device`；该字段已被清空，Dev1 的恢复状态可能错误归到 Dev2。

因此 V2.12.0.3 不能作为最终现场候选。本项修复迭代版本为 `V2.12.0.4`。

## 2. 根因代码

问题位于 `Controller/DaqPersistenceCoordinator.cs`：

- `WriteWithRetryAsync` 达到恢复时限后执行 `return`，没有保留失败批次。
- `WorkerLoop` 的 `finally` 无条件调用 `MarkPersisted`。
- `batch.Dispose()` 后继续调用 `EvaluateRecovery(batch.Device, ...)`。
- `GetSnapshot` 只区分 `Paused/Recovered`，已经超过恢复时限的失败状态不能持续出现在结构化指标中。

这不是简单的性能问题，而是“处理完成”和“真实落盘”语义混用。

## 3. V2.12.0.4 落地修复

### 3.1 超时不再丢弃当前批次

达到恢复时限后只发布一次 `DaqPersistenceRecoveryTimeout`，让控制层完成断能、圈作废和自维护；持久化 worker 保留原批次，以 `25/50/100/250 ms` 退避继续重试。只要存储恢复，原批次仍按 FIFO 顺序优先补写。

### 3.2 真实成功后才能推进边界，耐久完成后才能封圈

worker 新增 `boundaryHandled` 门控。只有以下情况才推进处理边界：

- 写入真实成功；
- 活动圈样本上限已经发布显式生命周期故障；
- 旧 DAQ 代次被恢复流程明确淘汰。

进程退出或取消发生在失败重试期间时，不能再伪装成已持久化。

控制层同时调整了截止顺序：所有受影响通道先暂停、断能和发起液压释放，再排空 Raw 后台管线，并等待截止设备满足“目标序号已处理、队列与在途写入为零、无未解决写故障”。只有这个耐久边界成立后，才把当前圈封为 `AbortedBySoftwareRecovery`。如果存储仍不可用，圈事务保持开放，自维护继续退避；不得先封圈、再让保留批次变成无归属写入，也不得提前重建和重入试验。

截止后被明确抑制的新批次可以推进“已处理序号”，但不能单独满足耐久边界；门禁还会检查 `DurabilityBlocked=False`。这避免较大的抑制序号越过前方仍失败或排队的真实批次。

### 3.3 失败状态参与 Stop 重启门禁

持久化快照保留 `FailureTimedOut` 状态；Stop 边界除了要求 Raw 已发布、Persisted 越过边界、队列为零，还要求持久化状态为 `Recovered`。只要仍是 `Paused/Failed`，`CanRestartInProcess=false`。

### 3.4 恢复设备号不再读取已释放对象

worker 在归还批次对象池前捕获 `batchDevice`，恢复状态发布只使用该稳定副本和队列快照，避免 Dev1/Dev2 串组。

### 3.5 切断“队列满 → 日志/恢复任务风暴 → 队列更慢”的正反馈

对封存目录 `10358-029_V2.12.0.2_0809_0001` 重新计数后确认：

- 23:58:55.780，Dev2 首次以 `Depth=101、Oldest=1009.6 ms` 进入持久化安全暂停；
- 23:59:08.706，Dev1 以 `Depth=100、Oldest=1008.8 ms` 进入安全暂停；
- 23:58:57.349 至 23:59:17.700，旧代码为每个被容量上限拒绝的批次各发布一次 `DaqPersistenceQueueFull`，共写出 **1491 条 ERROR**；
- UI 共收到约 1496 条“恢复失败”，每条又触发 UI 更新，并让控制层排队启动重复恢复任务。

这形成了明确的正反馈：写盘已经落后，重复 ERROR、UI 刷新和恢复任务继续占用 CPU、日志 I/O 和线程池，使写盘更难追平。V2.12.0.4 现已改为：

1. 队列第一次达到硬上限时，同步锁存 `PauseLatched` 和 `QueueFullLatched`；
2. 同一拥塞事件只发布一次 `DaqPersistenceQueueFull/Failed`，只允许创建一条恢复链；
3. 后续被拒绝批次只累加 `OverCapacityDroppedBatchCount`，不再刷 ERROR/UI；
4. 低水位恢复或明确恢复准入后才解除锁存；
5. 结构化现场指标输出 `OverCapacityDropped`，正式门禁强制其全程为 0。

该计数不是用来容忍丢批，而是让任何容量满都成为可审计的验收失败；受影响当前圈按软件恢复圈作废，不得计入正式完成数。

## 4. 自动化验证

新增回归“写盘超时保留原批次且存储恢复后按序补写”，模拟存储持续不可用超过 1 秒恢复时限，并验证：

- 超时后 `State=Failed`，`LastPersistedSequence=0`；
- `WaitForPersistedAsync(1)` 必须失败；
- 即使截止后抑制批次把处理序号推进到 3，真实批次未补写前耐久边界仍必须失败；
- 超时事件只发布一次，不形成恢复风暴；
- 同一次硬容量满只发布一次 Failed，后续拒绝批次进入结构化计数；
- 存储恢复后两个批次全部成功写入；
- 边界最终推进到 2，状态恢复为 `Recovered`；
- 恢复事件设备号保持 `Dev1`。

## 5. 上线条件

当前二进制只可用于代码审查和受控台架验证，不能直接恢复无人值守生产试验。正式放行仍须：

1. 审查并形成干净提交，从该提交重新构建。
2. `Tools/Verify-Release.ps1 -RequireDeploymentApproved` 通过。
3. 注入一次超过恢复时限的受控存储故障，确认原批次在存储恢复后补写，且无跨设备恢复状态；另注入一次队列容量满，确认整次事件只有一个 Failed/一条恢复链。
4. 完成 2 h 冒烟、24 h 六通道验收和 72 h 无人值守验证。
5. 对 24 h/72 h 封存副本执行：

```powershell
python Tools/validate_epb_field_gate.py "<封存目录>" `
  --expected-version V2.12.0.4 `
  --minimum-hours 24 `
  --performance-gates required `
  --artifact-scan full `
  --log-scan full `
  --database-scan full
```

72 小时最终门禁将 `--minimum-hours` 改为 `72`。

## 6. 最终判断

V2.12.0.4 关闭了 V2.12.0.3 遗留的“写盘已超时但边界虚假完成”缺口。软件现在能够在持久化长故障时先安全停机、保留原批次、持续等待存储恢复，并在真实补写完成前拒绝同进程重启。代码与自动回归已经完成；无人值守上线结论仍必须由干净发布身份和真实 24 h/72 h 硬件数据证明。
