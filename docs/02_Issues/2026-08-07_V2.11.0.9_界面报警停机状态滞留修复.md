# V2.11.0.9 界面报警停机状态滞留修复

> 整改版本：V2.11.0.10  
> 现场证据：`\\wj-epb\EPB_Data\10358-029`（只读核查，未修改现场数据）

## 现象与证据

EPB8 在 2026-08-07 11:36:35 因 `PeakEvidenceMismatch` 连续 3/3 报警，原 Timer 和 Runner 已按设计停止并移除。软件随后完成恢复预检、启动定位、2 圈资格复核，并在 11:37:14 创建新 Timer 重新加入正式节律。11:55 左右 EPB8 已运行至 Cycle 10052/10053，项目配置状态也为 `Running`，但界面仍可能显示旧的“报警停机”。

## 根因

控制层已经通过 `ChannelRuntimeStateChanged` 发布完整状态迁移，但 UI 使用 `BeginInvoke` 投递时携带的是历史事件对象，没有单调版本校验。UI 忙碌或多个后台线程并发发布时，旧的 `AlarmStopped` 回调可能迟于新的 `ResumeChecking`、`Qualification` 或 `Running` 回调执行。

同时，旧的 `ChannelAlarmRaised`、`ChannelPaused`、`ChannelResumed` 处理器还会直接修改 `EpbTestRecord.Status`，与统一运行状态形成第二条写入链。

## 修复

1. `ChannelRuntimeStateChangedEvent` 增加按通道单调递增的 `Revision`。版本只在状态被控制层原有规则接受后递增，不参与状态取舍，不改变报警、锁存或恢复状态机语义。
2. UI 收到状态事件时只接受更高版本，并在 UI 线程执行时重新读取该通道的最新状态，禁止排队中的旧消息覆盖新状态。
3. 解绑旧报警、暂停和恢复处理器的状态写入，改为仅保留用户日志；`EpbTestRecord.Status`、状态格、RUN/STOP 开关和汇总统一由 `ChannelRuntimeStateChanged` 更新。
4. 补齐启动定位硬件确认故障的统一运行状态发布，保证取消旧状态写入后仍显示 `AlarmStopped`。
