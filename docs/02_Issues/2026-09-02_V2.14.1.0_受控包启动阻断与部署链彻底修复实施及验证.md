# V2.14.1.0 受控包启动阻断与部署链彻底修复实施及验证

## 1. 结论与放行状态

截图中的 `V2.14.0.0` 无法开始试验不是硬件故障，也不是程序包传输损坏，而是发布包安装后的三道安全门禁互相不一致：

1. 安装器在 staging 目录生成槽证明，却把 staging 路径写进 DPAPI 封印；目录原子移动到 `Current` 后，Supervisor 必然报 `PackageSlotRootMismatch`。
2. 主程序只认可 `FORMAL_RELEASE_CANDIDATE` 和 VS 候选，不认可已经由正式发布流水线签发的 `FIELD_CANDIDATE_PENDING_168H`，因此标题显示 `非受控包:PackageNotApproved`。
3. 安装器新增的 `package-slot.v5.json` 不在原始发布哈希清单中，主程序会在修复第 2 项后继续报 `PackageFileSetMismatch`。

以上三个确定性阻断和同源的 LastKnownGood 隐患均已在 `V2.14.1.0` 修复。自动化发布门禁全部通过，已生成可部署的 `FIELD_CANDIDATE_PENDING_168H` 快捷包。

本结论的边界是：本次截图对应的软件启动链已被确定性修复并加入回归；真实远程工控机安装、实际 NI/CAN/液压/程控电源联机以及 24/72/168 小时长稳仍需现场执行。因此当前可以进入现场候选验证，尚不能冒充 168 小时正式无人值守放行。

## 2. 事故证据与根因映射

现场截图时间为 2026-09-02 01:05:44，窗口标题为：

```text
MT EPB需温疲劳测试 V2.14.0.0 [PID 13176] [非受控包:PackageNotApproved]
```

开始试验弹窗中的核心错误为：

```text
SupervisorLaunchRejected:
SupervisorRequestRejected:
SupervisorPackageSlotUnproven:

```

错误与代码根因的对应关系如下：

| 现场现象 | 直接原因 | 原实现缺陷 | V2.14.1.0 修复 |
|---|---|---|---|
| `[1/2]` 包身份和哈希验证通过，但开始试验被 Supervisor 拒绝 | 安装前包正确，安装后槽证明错误 | `Write-SlotDescriptor` 把 `.current-staging-*` 写入 `RootPath`，移动后与 `Current` 不相等 | 生成文件时显式传入原子切换后的 canonical `Current` 路径；保持 Supervisor 的严格比较不变 |
| 标题显示 `PackageNotApproved` | 主程序与发布流水线的状态枚举不一致 | `ReleasePackageVerifier` 未识别 `FIELD_CANDIDATE_PENDING_168H` | 仅在 `deploymentApproved=true`、`gitDirty=false` 且版本/提交/构建时间/配置哈希全部精确一致时认可现场候选 |
| 修复候选状态后仍可能报文件集合不一致 | 安装器追加了运行时槽证明 | 主程序把 `package-slot.v5.json` 当作未知程序文件 | 只豁免顶层精确文件名 `package-slot.v5.json`；其真实性仍由 Supervisor 使用 DPAPI、路径、manifest 和逐文件身份独立验证 |
| 168 小时后 LastKnownGood 可能无法回滚 | 与 Current 同源 | LKG 也在 staging 中封印 staging 路径 | LKG 写入最终 `LastKnownGood` canonical 路径并在切槽后立即解密复核 |
| 安装显示成功，点击开始才暴露槽错误 | 安装健康检查过浅 | 过去只检查槽描述文件存在，不解密验证内容 | 原子切槽后、服务启动前执行 `Assert-SlotDescriptor`，核对 schema、DPAPI、槽名、版本、最终路径、manifest 哈希和文件清单 |

`PackageSlotRootMismatch` 原本是正确的 fail-closed 行为。本次没有删除或放宽它，而是修正生产槽证明的一方，避免用“跳过安全检查”换取表面可启动。

## 3. 修复后的不变量

1. staging 目录只用于准备文件，任何可授权启动的槽证明必须绑定最终 canonical 路径。
2. `Current` 与 `LastKnownGood` 在原子移动后必须立即通过安装器本地解密复核；失败时保持 Supervisor 停止，不继续安装服务。
3. `FIELD_CANDIDATE_PENDING_168H` 不是宽松工程包：只有干净提交、正式流水线批准且所有身份精确一致才可运行。
4. `VS2022_RELEASE_CANDIDATE` 仍不得声明 `deploymentApproved=true`，也不能作为无人值守正式放行证据。
5. 只有顶层 `package-slot.v5.json` 被视为安装期生成文件；任意其他清单外文件仍触发 `PackageFileSetMismatch`。
6. 主程序的包校验与 Supervisor 的槽校验相互独立；任一失败均不签发启动许可。
7. 安装前包校验、安装后槽校验和 ZIP 外层哈希缺一不可。

## 7. 远程机升级步骤

针对已经安装但无法开始试验的 `V2.14.0.0`，不需要手工改服务、manifest、注册表或 `Program Files` 中的文件：

1. 在旧程序中执行安全停止，确认卡钳、液压、AO 和全部程控电源输出为 OFF，然后退出旧主程序。
2. 把整个 `V2.14.1.0 ... QUICKDEPLOY_R6.zip` 复制到远程机本地磁盘并完整解压；禁止在 ZIP 内直接运行，也不要从网络共享直接运行。
3. 双击新包内的 `一键修复.cmd`，接受管理员权限提示。首次未安装过时则双击 `一键安装现场候选.cmd`。
4. 必须看到完整包验证通过、安装成功；安装器还会在服务启动前验证新 Current 槽的 DPAPI 封印。
5. 双击 `检查运行状态.cmd`，确认 Supervisor 为 `Running`，SessionAgent 为 `Running` 或 `Ready`。
6. 从桌面 `MT EPB 试验系统 V2.14` 启动主程序。标题中不应再出现 `[非受控包:PackageNotApproved]`。
7. 先不上正式长稳，执行一次冷启动安全预检和一个正式圈；确认开始试验不再出现 `PackageSlotRootMismatch`，且首圈完整落盘后再进入 24 小时观察。

禁止采取以下“临时解决”：删除 `package-slot.v5.json`、修改 `build-identity.json`、手工把 `deploymentApproved` 改为 true、复制单个 EXE/DLL、关闭 Supervisor 门禁。这些操作会破坏可追溯身份或使安全证明失效。
