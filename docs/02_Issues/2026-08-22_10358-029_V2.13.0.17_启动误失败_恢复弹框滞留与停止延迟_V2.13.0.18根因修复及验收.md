# 10358-029 V2.13.0.17 启动误失败、恢复弹框滞留与停止延迟：V2.13.0.18 根因修复及验收

## 1. 结论

V2.13.0.17 本次“启动即报错”不是一项单独的卡钳硬件故障，而是一次真实但可恢复的程控电源启动瞬态，被软件新增加的恢复不变量错误放大成了批量启动失败。

现场共有三条相互关联、但需要分别修复的故障链：

1. **启动自愈被误判成孤儿恢复。** 电源 2 首次启动预检时输出电流为 `3.622 A`，没有新的保护触发证据，程序原本正确地进入 `PowerStartSelfHealing` 有界重试；约 1 秒后，恢复不变量仅凭 Reason 是否包含 `Startup` 判断批次生命周期所有权，错误地把 `PowerStartSelfHealing` 当成无 owner/无 task 的孤儿恢复，反向关闭了电源 2、4。后续启动定位因此连续读到 `ExpectedOutputDisabled`，最终报“连续 3 次软件瞬态未通过”。
2. **恢复完成只依赖已经失活的命名管道通知。** 新进程 PID 492 实际已在 `00:18:26.232` 提交恢复批次，但 `RecoveryBatchCommitted` 发送遇到 `SendBusy`；独立看门狗收不到提交消息，恢复弹框自然无法关闭。
3. **“停止自动恢复并关闭”先做同步管道写，按钮线程被卡住。** 操作员在 `00:17:21.014` 点击按钮后，Sidecar 的 `RequestStopAll` 管道写阻塞约 65 秒。主程序真正收到停止请求后，从 `00:18:26.369` 到 `00:18:26.661` 仅约 292 ms 就完成了 StopAll。因此慢的不是主程序安全停止，而是停止意图被堵在管道写入上。

另有一个放大项：首次启动失败收尾时，`StopAll` 已确认电机、电源、压力、Raw、持久化和数据连续性全部安全，所有 Timer/Runner/CTS/owner 也为 0，却把当前 `StartBatch` 调用栈自己持有的唯一生命周期租约判成 `LifecycleBusy=True`，从而错误要求进程回收。这不是本次最初故障源，但把一次本可本进程收口的启动失败升级成了自动重启。

修复已按下一版本 **V2.13.0.18** 落地。修复原则不是延长等待时间，而是：纠正所有权语义、给所有管道写设置硬截止、让读循环不再同步回写、并为“恢复已提交”和“人工停止撤权”增加独立于管道的耐久控制面。

## 4. 为什么 V2.13.0.15 启动时不会，而 V2.13.0.17 会

答案不是“V2.13.0.15 完全没有这段隐患”，而是**两次启动进入了不同的运行分支**。

V2.13.0.15 在 `2026-08-21 11:25` 的同一组通道 `[4,5,10]` 启动时：

```text
电源4 启动输出已稳定：Vout=11.992V Iout=-0.036A
电源2 启动输出已稳定：Vout=11.995V Iout=0.000A
程控电源启动实时预检通过：Groups=[2,4] Attempt=1
```

它第一次预检就通过，没有进入 `PowerStartSelfHealing`，所以没有触发“Reason 不含 Startup → 被判孤儿”这条缺陷分支，最终在 `11:27:36.091` 正常完成批量启动。

V2.13.0.17 本次首次预检遇到电源 2 的 `3.622 A` 非空载状态，需要进入 `PowerStartSelfHealing`；这个 Reason 恰好不包含字符串 `Startup`，于是在 1 秒孤儿检查点被误杀。到 Attempt 3 时电源预检其实已经通过，但所属电源又被孤儿清场关闭，启动定位只能得到 `ExpectedOutputDisabled`。

更重要的是，V2.13.0.15 数据在 `11:59:06` 以后也出现过多条 `OrphanRecoveryOwnerOrTaskMissing`，并在 `17:21:05` 出现过同类 `StartupPositioning / ExpectedOutputDisabled`。这证明旧版本“那次启动稳定”只说明触发条件没有在启动瞬间出现，不能证明恢复不变量和电源自愈的所有权协议是正确的。

所以版本对比应当表述为：

- V2.13.0.15 的首次启动电源空载稳定，避开了缺陷；
- V2.13.0.17 首次启动出现可恢复电流瞬态，进入了缺陷分支；
- 两个现场包都缺 manifest，不能把差异简单归结为某一个不可验证的 Git 提交；
- 需要修的是确定性的所有权和 IPC 协议，不能靠回退、提高阈值或期待每次电源第一次就稳定。

## 5. 根因一：批次生命周期恢复所有权识别不完整

### 5.1 原逻辑错误

恢复健康检查承认三类合法覆盖：DAQ 恢复上下文、后台恢复 task/owner，以及批次启动调用栈。但第三类原先只接受：

```text
BatchLifecycleGate.IsBusy && ReasonCode 包含 "Startup"
```

真实批次启动阶段使用的不止 `Startup...`，还包括：

- `DaqStartSelfHealing`
- `PowerStartSelfHealing`
- `LearningPersistenceSelfHealing`
- `HydraulicGenerationSelfHealing`
- `PowerSupplyRecoveredForStartup`

这些恢复由当前批次启动调用栈同步拥有，不会登记成后台恢复 task；用字符串包含关系猜所有权，必然制造假孤儿。

### 5.2 修复

在 `Controller/EpbManager.TimerRuntimeHealth.cs` 中增加明确的批次生命周期 Reason 分类，并在 `BatchLifecycleGate` 确实忙时承认这些状态具有执行覆盖。60 秒恢复硬截止仍然保留，后台恢复仍必须满足原有 task/owner/组恢复登记，不会把真正的孤儿恢复放行。

安全边界：

- 只有 `BatchLifecycleGate.IsBusy` 且 Reason 在明确白名单中才放行；
- 不使用宽泛的 `Contains("SelfHealing")`；
- 不取消 1 秒孤儿检查，也不延长 60 秒硬截止；
- 正式运行期无 task/owner 的 Recovering 仍会被清场。

## 6. 根因二：失败启动收尾把当前调用栈自己判成逻辑残留

### 6.1 现场证据

`00:15:27.951` 的 StopAll 结果：

```text
MotorDO=Confirmed; Power=Confirmed; Pressure=Confirmed;
RawStorage=Confirmed; Persistence=Confirmed; DataContinuity=Confirmed;
Logical=Pending;
LifecycleBusy=True Session=False Batch=Empty Timers=0 Runners=0 Energized=0
StopCts=0 CycleCts=0 Participants=0 Leases=0 DaqRecovery=0
ActiveCycles=0 SoftwareRecovery=0 RecoveryOwners=0
```

唯一 Busy 是正在执行 catch/finally 的 `StartBatchSynchronizedWithResultAsync` 本身；该唯一租约会在 StopAll 返回后由 finally 释放。把它判为未知后台残留会错误产生 `SafeButRestartRequired`。

### 6.2 修复

增加生命周期活动计数，并只在以下条件全部成立时，从失败启动 StopAll 的逻辑快照中去掉这个“当前栈瞬时 Busy”：

1. `Initiator == StartBatchSynchronizedWithResultAsync`；
2. Source 为 `StartupRollback` 或 `SystemFault`；
3. 批次 Session 已结束；
4. 活动生命周期操作数恰好为 1；
5. 其他 Timer、Runner、CTS、owner、恢复任务等仍按原规则逐项验证。

只要存在第二个排队/活动生命周期操作、Session 仍活动或调用来源不匹配，就不能忽略 Busy。该修复不会放宽真正并发重入或资源泄漏的重启门禁。

## 7. 根因三：双向命名管道死锁和无硬截止写入

### 7.1 死锁结构

主程序与 Sidecar 都在同一条全双工命名管道上执行“读到请求后立即同步回写”：

```text
Sidecar ReaderLoop --发送 Ping/刷新请求--> Main ReaderLoop
Main ReaderLoop    --同步发送 Heartbeat/Pong--> Sidecar ReaderLoop
```

当双方读循环同时进入写入、管道缓冲不能继续接受数据时，两个线程都等待对方先恢复读取。V2.13.0.17 虽然把发送锁从全局状态锁中分离，避免了整个 UI 都持有同一全局锁，但实际 `WriteLine` 仍没有硬截止，发送锁可以永久被一个陈旧写入占有。后续 Heartbeat、恢复提交和停止请求全部得到 `SendBusy`。

### 7.2 修复

主程序 `MTTfTest/WatchdogRuntime.cs` 与 Sidecar `MTTFTest.Watchdog/WatchdogHost.cs` 同时修改：

- 读循环收到 Ping 后只调度合并的异步响应，读循环立即继续排空输入；
- 发送串行锁最多等待 100 ms；
- 实际管道写最多等待 500 ms；
- 任一超时立即摘除并异步 Dispose 陈旧管道，不能继续占锁；
- 同一 Session 持续重连，不再只重连一次；
- 重连前检查人工撤权 marker，已经要求停止就绝不重新拉起恢复；
- 关闭/断开管道时不在全局状态锁内执行潜在阻塞 Dispose。

这条修复保证 IPC 失败会降级为“连接断开并重连”，不会再演变为无上限等待。

## 8. 恢复弹框和人工停止的独立耐久控制面

仅修复管道超时仍不够：管道本来就可能在进程切换、杀进程或重连期间不可用，所以关键控制语义不能只有一条易失消息。

### 8.1 恢复提交 marker

主程序在发送 `RecoveryBatchCommitted` 前，先原子写入：

```text
session-{SessionId}.recovery-committed
```

marker 同时写本机控制目录和项目 `WatchdogSessions` 目录，内容包含提交代次、UTC 和原因。Sidecar 每 250 ms 轮询，并取两处最大代次。以下任一证据都能确认恢复完成并关闭过渡窗：

- 管道 `RecoveryBatchCommitted` 消息；
- Heartbeat 中的提交代次；
- 耐久 `recovery-committed` marker。

因此即使管道已经断开，只要新批次正式提交，弹框也能自动关闭。

### 8.2 人工停止撤权 marker

“停止自动恢复并关闭”按钮现在先原子写本机和项目 `.revoked` marker，再尝试发送 `RequestStopAll`。主程序的传输监督和重连循环都会观察 marker，并在本地触发 StopAll；Sidecar 同时保留 15 秒身份匹配强制终止兜底。

顺序是：

```text
按钮点击
  → 先耐久撤销本 Session 的恢复/运行授权
  → 主程序通过管道或 marker 收到 StopAll 意图
  → 等待安全收口
  → 15 秒仍未收口才按 PID + ProcessStartUtcTicks 强制终止
```

Sidecar 不会因为读到自己刚写的 marker 就提前退出监督；它会继续等待主程序安全收口或执行最后兜底。

## 11. 现场验收门禁

V2.13.0.18 只有全部通过以下门禁才可替代现场版本。

### 11.1 启动自愈

1. 选择 `[4,5,10]`，分别做冷启动和电源已 ON/带残余电流的热启动。
2. 注入一次电源预检不稳定，使其至少持续超过 1 秒并进入 `PowerStartSelfHealing`。
3. 必须观察到有界重试；不得出现针对该 Reason 的 `OrphanRecoveryOwnerOrTaskMissing`。
4. 不得因孤儿清场产生 `ExpectedOutputDisabled`。
5. 电源恢复稳定后应继续启动；若 3 次都真实不稳定，允许安全失败，但必须保留原始电源证据，不得伪装成孤儿恢复。

### 11.2 真孤儿保护不退化

1. 在正式运行期构造没有 batch owner、没有恢复 task、没有组恢复登记的 `Recovering` 通道。
2. 1 秒孤儿检查仍必须触发受影响组安全清场。
3. 60 秒恢复硬截止仍必须生效。

### 11.3 失败启动本进程收口

1. 构造启动定位失败，确认物理和持久化资源全部清空。
2. 当仅剩当前 StartBatch 唯一租约时，结果应为可安全收口，不得仅因该租约要求重启。
3. 再构造第二个活动生命周期操作或保持 Session 活动，必须继续拒绝同进程重启。

### 11.4 管道故障注入

1. 分别阻塞主程序→Sidecar、Sidecar→主程序以及双向写入。
2. 任一单次发送必须在 500 ms 左右熔断陈旧连接，不能无限等待。
3. UI、监控循环和停止按钮必须保持响应。
4. 同一 Session 应持续重连；恢复期间不得创建第二个并行 Session。

### 11.5 恢复弹框

1. 在管道断开状态下完成恢复批次提交。
2. 必须生成 `session-{id}.recovery-committed`。
3. Sidecar 应在 2 秒内根据 marker 确认提交并关闭恢复弹框。
4. 日志必须记录 `Evidence=DurableMarker` 或其他等价提交证据。

### 11.6 “停止自动恢复并关闭”

1. 在管道正常、断开、写阻塞三种状态下分别点击按钮。
2. 点击后应立即写入 `.revoked`，按钮处理不得等待无上限管道写。
3. 主程序应通过管道或 marker 开始 StopAll；电源、DO 和压力安全收口时间按真实硬件确认决定。
4. 主程序正常收口后两个程序退出；超过 15 秒仍未收口，Sidecar 才执行身份匹配强制终止。
5. marker 存在后不得再次自动拉起主程序或新恢复批次。

### 11.7 发布可追溯性

正式包必须满足：

- `PackageVerified=True`；
- `GitCommit`、`BuildUtc` 非 unknown；
- 主程序、Sidecar、协议 DLL 和配置均进入 manifest；
- 现场启动日志中的逐文件哈希与发布 manifest 一致。

未满足该项不得只凭窗口标题中的 `V2.13.0.18` 判定为本次修复包。

## 12. 最终判定

本次 V2.13.0.17 失败的核心不是把电源电流阈值设得太严，也不是 StopAll 本身执行 60 多秒，而是：

```text
一次可恢复的电源启动瞬态
  → 被不完整的恢复 owner 判定误杀
  → 电源被软件反向关闭
  → 启动定位连续得到 ExpectedOutputDisabled
  → 失败收尾又把自身生命周期栈判成残留
  → 触发进程恢复
  → 双向管道写死锁
  → 恢复提交与人工停止意图均无法及时送达
```

V2.13.0.18 已在所有权判定、失败启动清场、IPC 活性和耐久控制面四层同时闭环。代码编译和 482 项自动回归已通过；仍需按第 11 节做带真实程控电源、NI DO/DAQ 和双进程故障注入的现场验收，验收通过后才能称为现场彻底解决。
