# 10358-029 V2.13.0.6 “系统自恢复假运行”、启动受阻与监控消失根因分析

## 1. 结论先行

本次现场现象不是一个故障，而是连续发生的三段独立故障及两个自恢复设计缺口叠加：

1. **09:47 开始的“所有启用 EPB 显示 STOP/系统自恢复、曲线继续、圈数不增”不是单纯 UI 卡住。** 主机墙上时钟相对单调时钟向前跳变约 `1.340 s`，而完整峰值捕获把 DAQ 样本时间轴与 `DateTime.Now` 墙上时钟直接比较。两者从此错开约 1.34 秒，代码却只等待固定 100 ms，于是 5 个通道每一圈都稳定失败为 `PeakCaptureInvalid / CutoffNotCovered`。
2. **控制软件恢复状态机没有真正停止和恢复。** `ReportFormalControlSoftwareRecovery` 只执行当前通道 OFF、液压释放和状态发布，没有暂停 Timer、取消 Runner，也没有调度隔离恢复或设置三次熔断。因此界面进入“系统自恢复”，物理循环仍每 15 秒继续一次；下一圈又以同一原因失败，永远没有机会通过“未来成功提交”返回 Running。
3. **数据库没有错误增加完成圈数，但发生了未计入完成数的实际机械动作。** 09:47～09:54 共留下 `137` 条 `AbortedBySoftwareRecovery`：EPB4/5/9/10/11 分别为 `27/28/27/27/28`。这些圈不能追认为合格完成圈，但应计入实物动作/磨损统计。
4. **操作员 09:57 发起的第一次重新开始实际上成功了。** 5 个通道各完成 10 圈自学习，09:59:04 进入正式运行，随后各新增 26～29 个合格正式圈。现场所说的“自学习后启动受阻”并不是这一轮；受阻发生在后面的 10:15 启动尝试。
5. **10:05 又发生了一次独立的 Dev1 DAQ 瞬态陈旧。** 本次恢复卡在 EPB4 `CycleExecutionQuiescenceTimeout`，StopAll 到硬截止时仍残留 `Timers=6、Runners=6、SoftwareRecovery=1`，看门狗于 10:06:39 终止旧进程并启动恢复进程。
6. **10:06 的恢复进程及 10:15 的人工启动都被电源通信预检挡住。** 4 组程控电源的 `*IDN?` 均在 2000 ms 超时，程序无法确认全断能，因此禁止重新学习/进入 `StartBlocked`。这一“失效安全地拒绝启动”是正确行为；错误在于通信恢复及 UI/Watchdog 生命周期处理。
7. **监控界面消失是代码主动关闭，不是绘图窗口自己崩溃。** 看门狗恢复子进程接管失败后，`ResumeWatchdogRunAsync` 记录“保持本轮授权，等待 Watchdog 退避重试”，但紧接着调用普通 `Close()`；关闭路径又写入 `ApplicationClosing` 撤销标记。Watchdog 把它当作人工/正常终止，设置 `ManualStopRequested=true` 并停止，实际没有后续退避重试。
8. **10:15 的普通启动失败也错误地终结了 Watchdog。** `BatchStartFailed` 被上报为 `RunStopped`，该消息同样撤销会话。之后界面虽然提示“等待 Watchdog 终止旧进程并重启到空闲模式”，但 Watchdog 已在 10:15:19 退出，无法执行提示中的动作。

最终根因不是卡钳硬件同时故障，也不是 SQLite 写盘堵塞，而是以下组合失效：

```text
墙上时钟发生跳变
  → 完整峰值截止点跨时钟域比较
  → 固定 100 ms 等待后永远 CutoffNotCovered
  → 控制恢复只改状态、不停 Timer/Runner、不做有界重建
  → 物理循环持续、完成圈数冻结
  → 后续 DAQ 瞬态恢复未清场
  → 看门狗接管时 4 组电源通信超时
  → 恢复失败被普通 Close/RunStopped 错误终态化
  → 监控消失且无人重试
```

**必须同时修复“同一时钟域截止屏障、控制恢复真正停转并有界重建、Watchdog 恢复失败不撤权、启动失败保持可见安全空闲并持续重试”四条链路。仅把 100 ms 改大，不能从根本上解决。**

## 4. 图 1 为什么会出现“STOP + 系统自恢复 + 曲线正常 + 圈数不增”

### 4.1 UI 没有单独卡死

当前 UI 映射为：

- `ChannelRuntimeState.Recovering` → 文本“系统自恢复”；
- `ChannelRuntimeState.Recovering` → `EpbTestStatus.Paused`；
- Paused 状态的开关显示 `STOP`。

对应代码：

- `MTTfTest/FrmEpbMainMonitor.PowerSupply.cs:440`
- `MTTfTest/FrmEpbMainMonitor.PowerSupply.cs:497`

因此图 1 的文字和开关确实反映了状态机中的 `Recovering`，不是控件漏刷新。真正的问题是：**控制状态已标记“恢复/暂停”，底层 Timer 和 Runner 却仍在活动。**

日志明确记录：

```text
09:47:11.706 EPB5  State=Recovering ... Timer=True Runner=True Energized=False
09:47:12.345 EPB11 State=Recovering ... Timer=True Runner=True Energized=False
09:47:26.389 EPB4  State=Recovering ... Timer=True Runner=True Energized=False
09:47:26.934 EPB10 State=Recovering ... Timer=True Runner=True Energized=False
09:47:27.106 EPB9  State=Recovering ... Timer=True Runner=True Energized=False
```

这里的 `Energized=False` 只是记录进入状态的瞬间已执行 OFF；由于 Timer/Runner 没停，下一周期仍会重新上电。曲线继续出现正反向电流与压力波形，正是下一圈仍在执行的结果。

### 4.2 圈数不增是数据库的正确结果

截图圈数与数据库冻结点逐项相符：

| EPB | 09:47 前完成数 | 09:47 最后一条完成圈 | 图 1 显示 | 09:47～09:54 作废圈 |
|---:|---:|---:|---:|---:|
| 4 | 56938 | +1 | 56939 | 27 |
| 5 | 56603 | +0 | 56603 | 28 |
| 9 | 56979 | +1 | 56980 | 27 |
| 10 | 57986 | +1 | 57987 | 27 |
| 11 | 57974 | +0 | 57974 | 28 |
| **合计** |  |  |  | **137** |

09:48～09:53，数据库每分钟、每通道都稳定出现 4 条 `AbortedBySoftwareRecovery`，没有 `completed`。所以：

- 曲线刷新只能说明 DAQ、绘图及部分控制动作还活着；
- 完成数只在正式圈控制成功且事务提交后增加；
- 这些圈的峰值证据不完整，不能计为合格正式圈；
- 但卡钳确实执行了机械夹紧/释放，应进入实际磨损附加计数。

### 4.3 首要技术根因：跨时钟域截止点比较

故障前后两设备的共同特征：

| 指标 | 09:47:02 | 09:47:14 | 说明 |
|---|---:|---:|---|
| 回调间隔 | 约 16 ms | 约 16 ms | DAQ 回调持续 |
| 队列 | 0～1 | 0～1 | 没有处理积压 |
| 单调时钟 drift | 约 28～30 ms | 约 24 ms | 采集节拍仍正常 |
| 墙上时间到达延迟 | 约 28～30 ms | 约 1364～1365 ms | 墙上时钟与样本 UTC 映射突变错位 |

两条 DO 日志也给出独立证明：

```text
09:47:00.809876  MonoTicks=4719902551433
09:47:09.268598  MonoTicks=4719973736259
```

两行墙上时间相差约 `8.459 s`，单调时钟只相差约 `7.118 s`，差值约 `+1.340 s`。这证明主机墙上时钟在中间向前跳变。封存数据没有 Windows 时间服务事件或系统事件日志，因此**能确认“发生了墙上时钟前跳”，不能仅凭项目数据断言是 NTP、人工改时还是其他系统组件触发。**

代码中的两个时间域：

1. `IO.NI/HighResolutionSampleClock.cs:321` 起，DAQ 样本时间轴以启动时的 UTC 为锚，随后按样本序号、采样率和 `Stopwatch` 单调时钟推进；墙上时钟跳变不会让既有样本时间轴同步跳变。
2. `IO.NI/TwoDeviceAiAcquirer.cs:5841` 在结束峰值捕获时直接使用 `DateTime.Now` 作为逻辑截止点。
3. `IO.NI/TwoDeviceAiAcquirer.cs:5899` 左右要求 `ProcessedThroughAt >= cutoffLocal` 才算覆盖。

墙上时钟前跳 1.34 秒后，逻辑关系变成：

```text
cutoffLocal(DateTime.Now) = DAQ 样本时间轴当前值 + 约 1.34 s
```

即使 DAQ 每 16 ms 正常产生和处理数据，样本时间轴也不会凭空追上已经永久错开的墙上时钟锚点。

### 4.4 固定 100 ms 等待把时间错位变成永久失败

`Controller/EpbCycleRunner.Adaptive.cs:1605` 固定：

```csharp
const int peakEvidenceDrainMs = 100;
```

并在约 `1677～1687` 行调用 `EndEpbCurrentPeakAsync(..., 100, cutoffAfterDelay:false)`。

`IO.NI/TwoDeviceAiAcquirer.cs:5847～5855` 最多等待 100 ms；超时后立即 `Finish`。现场每次结果都是：

```text
TailLag=∞ms Covered=False Drain≈106～124ms Quality=CutoffNotCovered Limit=100.0ms
```

注意：`Drain≈110ms` 只是等待任务和调度实际消耗时间，不代表只差 10 ms 就能成功。真正的时间域偏差约 1.34 秒，并且在当前 DAQ 生命周期内不会自动消除。

**因此，把 100 ms 临时改成 150 ms 或 1500 ms 都不是正确修复：**

- 150 ms 仍无法覆盖 1.34 秒；
- 1500 ms 可能暂时等到，但会让每圈延迟、统计窗口和安全语义依赖系统时钟跳变大小；
- 墙上时钟向后跳时还会产生相反方向的边界错误；
- 正确做法是用同一 DAQ generation 内的样本序列/单调水位完成封口。

### 4.5 次要但关键的根因：控制恢复只发布状态，不真正停转

`Controller/EpbManager.WarningSnapshots.cs:1031` 的 `ReportFormalControlSoftwareRecovery` 当前只做：

- 增加 `_formalControlRecoveryAttempts`；
- 尝试当前通道输出 OFF；
- 异步液压释放；
- 发布 `ChannelRuntimeState.Recovering`；
- 写日志。

它没有做：

- `timer.Pause(...)`；
- `CancelCyclePauseCts(channel)`；
- 撤销/等待 Runner；
- `UnmarkHydraulicParticipant(channel)`；
- `ScheduleIsolatedInfrastructureRecovery(...)`；
- 三次同指纹失败后的整批熔断。

同文件 `ReportFormalPersistenceRecovery` 在约 `1005～1028` 行却完整执行了上述暂停、取消和隔离恢复。两个恢复分支不对称，是本次“状态已恢复中、动作仍继续”的直接代码缺口。

`CompleteFormalSoftwareRecoveryAfterCommit` 只有等未来一圈成功提交才清除 Recovering；但下一圈还会遇到同一跨时钟域截止失败，所以成功提交永远不会发生，尝试次数只会持续增长。

## 5. “暂停、停止、重新开始、自学习后启动受阻”究竟发生了什么

### 5.1 09:57 的重新开始成功了

数据库与学习清单均证明：

- 09:57～09:59：5 通道各有 10 条 `learning_completed`；
- `LearningCycles/7213c0b51956474f9c9b170dfe827944/learning-run-manifest.json` 在 09:59:04 完成；
- 09:59:04.183：日志明确写“批量启动完成”；
- 09:59 后正式完成圈新增：EPB4/5/9/10/11 分别为 `26/26/28/29/29`。

这次重启还重置了 DAQ 样本时间轴锚点，因此 09:47 的 1.34 秒时间域错位随新 DAQ 生命周期消失，完整峰值证据重新有效。

### 5.2 10:15 的启动受阻发生在自学习之前

10:14:16 的“2. 自学习/开始试验”只是界面初始化提示。10:15:08 的“准备启动…自学习 10 圈”表示计划，不代表学习动作已经开始。

最新清单：

`LearningCycles/58e61a27acf24e0d87043552a9142782/learning-run-manifest.json`

其中：

- `PlannedLearningCycles=10`；
- `Learning=[]`；
- `Artifacts=[]`；
- `Reason=Failed:SoftwareSelfHealingExhausted Stage=PowerStartPreflight Attempts=3 Error=*IDN? 超时（2000 ms）`。

所以这轮没有任何学习圈，实际流程为：

```text
点击开始
  → 电源启动前预检
  → 创建/连接 4 组电源客户端
  → 查询 *IDN?
  → 连续三次 2000 ms 超时
  → PowerStartSelfHealing 熔断
  → StartBlocked
  → 未进入学习
```

### 5.3 为什么 4 组都 `*IDN?` 超时

`PowerSupply.Core/PswTcpClient.cs:54` 在 TCP 连接后立即执行：

```csharp
Identity = await QueryCoreAsync("*IDN?", token);
```

10:06 的安全接管和 10:15 的人工启动都看到 Group1～4 同样的 2000 ms 超时。这说明程序无法取得任何一组电源身份/状态，从而也无法给出可信的全断能确认。

可以确认：

- 不是某一个 EPB 的自学习算法失败；
- 不是数据库阻止启动；
- 不是五个卡钳同时损坏；
- 是启动前电源通信/身份查询阶段失败；
- 拒绝上电和拒绝学习属于正确的安全策略。

不能仅凭当前封存确认的外部根因：

- 电源交换机/网络链路是否中断；
- 4 台电源是否同时不可达；
- 电源是否只允许单连接，旧进程被强杀后 SCPI 会话尚未释放；
- TCP 已连通但仪器未响应 `*IDN?`；
- 主机网络栈或防火墙是否发生瞬态。

4 组同时失败更像共享通信基础设施或连接生命周期问题，而不像 4 个独立输出级同时损坏。后续版本必须增加连接阶段、目标地址、TCP Connect、写命令、读响应分别计时的证据，才能把外部根因进一步定位。

## 6. 为什么监控界面消失，且没有自动回来

### 6.1 10:06：恢复子进程的普通 Close 撤销了 Watchdog

`MTTfTest/Main_Frm.UnattendedRecovery.cs:84～126`：

1. 创建并打开 `FrmEpbMainMonitor`；
2. 调用 `ResumeFromWatchdogCheckpointAsync`；
3. 4 组电源 OFF 无法确认时抛异常；
4. catch 中记录“保持本轮授权，等待 Watchdog 退避重试”；
5. 调用 `WatchdogRuntime.RequestExternalRecovery(...)`；
6. 随后 `BeginInvoke(() => Close())`。

普通关闭最终调用 `WatchdogRuntime.NotifyApplicationClosing()`；`MTTfTest/WatchdogRuntime.cs:514～519` 会：

- 设置 `_sessionClosing=1`；
- 写 `ApplicationClosing` revocation marker；
- 发送 `ApplicationClosing`。

`MTTFTest.Watchdog/WatchdogHost.cs:320～327` 收到 `ApplicationClosing` 后：

- 设置 `_journal.ManualStopRequested=true`；
- 发布终态；
- `_stop.Cancel()`。

封存会话精确对应：

```text
10:06:50 TakeoverRequested: WatchdogRecoveryStartupFailed ... 4组 *IDN? timeout
10:06:55 ApplicationClosing, ManualStopRequested=true
```

代码日志说“等待重试”，生命周期协议却把它变成“永久终止”。这就是监控消失后没有再次拉起的确定原因。

### 6.2 10:15：BatchStartFailed 又被误报成 RunStopped

`MTTfTest/FrmEpbMainMonitor.cs:2489～2498` 在普通启动异常时调用：

```csharp
WatchdogRuntime.NotifyRunStopped(
    Detail = "BatchStartFailed:" + ...);
WatchdogRuntime.ShutdownLocalClient();
```

`WatchdogRuntime.NotifyRunStopped` 会写 `RunStopped` 撤销标记；WatchdogHost 同样把 `RunStopped` 当永久终态。

10:15 会话证据：

```text
10:15:19.517 client RunStopped Reason=BatchStartFailed:*IDN? timeout
10:15:19.519 sidecar RunStopped ManualStopRequested=true
```

之后 UI 又提示“停止超过安全截止，正在等待 Watchdog 重启到空闲模式”，但此时 Watchdog 已经退出。该提示与协议真实状态不一致。

### 6.3 这里的正确安全语义

- `ApplicationClosing`、`RunStopped`、Session revocation 只能代表用户明确停止、正常完成或明确退出；
- Watchdog 恢复子进程启动失败、外设临时不可达、启动预检失败都属于**可重试安全空闲**，不能撤销原会话；
- 在电源 OFF 未确认时绝不能继续学习或上电，但可以持续保持监控界面、重建连接、重复 OFF 查询并等待恢复。

## 8. 必须落地的解决方案

### 8.1 P0：峰值封口改为同一 DAQ 时钟域的序列水位屏障

禁止继续使用 `DateTime.Now` 与 DAQ 样本 UTC 做正确性比较。建议引入：

```text
PeakCutoffBarrier
  Device
  Generation
  CaptureId
  AcceptedSequence / ProducedSequence
  CutoffMonotonicTick
  OptionalInBatchSampleOffset
```

推荐流程：

1. 电机 DO OFF 时，在对应 DAQ generation 的生产者/处理流水线上原子插入一个 cutoff marker，或快照当时已接受的 sequence 水位；
2. 处理线程按原有顺序处理数据批次；
3. 当 `ProcessedSequence >= CutoffSequence`（或处理到 marker）时完成 `CutoffCovered`；
4. 同一批内需要精确裁剪时，使用样本序号或由同一单调时钟计算的 sample offset；
5. `DateTime` 只用于日志和展示，不再参与“证据是否完整”的布尔判定；
6. 等待超时使用 `Stopwatch` 单调时钟，超时只代表流水线未推进，不受系统校时影响。

建议修改位置：

- `IO.NI/TwoDeviceAiAcquirer.cs`
- `IO.NI/HighResolutionSampleClock.cs`
- `Controller/EpbCycleRunner.Adaptive.cs`

100 ms 可以保留为性能告警阈值，不能再同时承担正确性截止。超时上限应依据 generation、批长和处理水位定义，例如 `max(3×观测批间隔+jitter, 250ms)`，并设 1000 ms 绝对上限；但即使超时，判据仍必须是序列水位，不是墙上时间。

### 8.2 P0：FormalControlSelfHealing 第一次失败就停止后续物理圈

`ReportFormalControlSoftwareRecovery` 应与持久化恢复分支对齐：

1. 当前圈先完成安全反向释放；
2. 立即暂停该通道 Timer；
3. 取消并等待当前 Runner/周期 CTS；
4. 撤销液压参与者并确认 DO OFF；
5. 若错误属于设备级时间轴/DAQ generation，则暂停同一设备受影响通道；
6. 调度隔离基础设施恢复，而不是直接等待下一正式圈；
7. DAQ/水位恢复后先执行 1 个不计数资格确认圈；
8. 资格圈证据有效后恢复 Running 和 Timer；
9. 同指纹连续 3 次失败，升级为整批安全重建/进程重启；
10. 任一事故每通道最多允许 1 个无效物理圈，禁止形成无界作废循环。

必须增加运行时不变量：

```text
Recovering 持续超过机械释放宽限期
  => TimerActive == false
  && RunnerActive == false
  && Energized == false
```

宽限期结束仍违反时，独立 Watchdog 直接请求全批安全接管。

建议修改位置：

- `Controller/EpbManager.WarningSnapshots.cs`
- `Controller/EpbManager.CycleAttempts.cs`
- `Controller/EpbManager.DaqLiveness.cs`
- `Controller/ChannelRuntimeState.cs`

### 8.3 P0：增加“动作在继续但完成数不前进”的独立监督

仅监控进程、回调、队列和 UI 都无法发现本次假运行。Watchdog 心跳必须增加：

- 每通道最后 completed 时间；
- 连续 `AbortedBySoftwareRecovery` 数；
- 最近 DO Forward/Reverse 命令序号；
- `Recovering` 状态年龄；
- Timer/Runner/Energized 快照；
- 最近一次成功 peak cutoff barrier sequence。

接管规则至少包含：

```text
连续 2 圈 AbortedBySoftwareRecovery 且原因指纹相同
OR
完成数超过 max(3×周期, 60s) 不增长，同时仍有 DO/周期动作
OR
Recovering 超过 30s 且 Timer/Runner 仍活动
    => 安全暂停、断能并启动有界恢复
```

这样即使主逻辑再次遗漏熔断，独立监督也能在 30～60 秒内终止假运行，而不是持续 7 分钟、137 个无效动作。

### 8.4 P0：恢复子进程失败不得走普通 ApplicationClosing

新增与人工关闭完全隔离的生命周期协议，例如：

- `RecoveryAttemptFailed`：本子进程安全退出，但 Session 仍授权；
- `RecoveryChildDetached`：子进程释放 UI/资源，不写 revocation marker；
- `SafeIdleRetrying`：输出保持 OFF，UI 存活，等待下次连接；
- 只有 `UserStopIntent`、`RunCompleted`、`UserApplicationExit` 才允许撤销 Session。

`ResumeWatchdogRunAsync` catch 中必须：

1. 上报 `RecoveryAttemptFailed`；
2. 保留 Session 授权；
3. 不调用会触发 `NotifyApplicationClosing` 的普通 `Close()`；
4. 由 Watchdog 以 2、5、15、30 秒上限退避继续拉起，或让当前进程留在可见安全空闲页重试；
5. 无论重试多久，所有输出保持 OFF，开始按钮保持禁用；
6. 外设恢复、全 OFF 验证通过后，自动重新学习并续测。

建议修改位置：

- `MTTfTest/Main_Frm.UnattendedRecovery.cs`
- `MTTfTest/WatchdogRuntime.cs`
- `MTTFTest.Watchdog/WatchdogHost.cs`
- Watchdog 协议消息定义

### 8.5 P0：BatchStartFailed 不是 RunStopped

普通“开始试验”已经表达了明确的启动意图。若启动预检只因临时电源通信失败：

- 保存 `PendingStartIntent` 和所选通道；
- 进入可见的 `StartBlocked/SafeIdleRetrying`；
- 不发送 `RunStopped`、不撤销 Watchdog；
- 自动销毁旧 TCP 客户端并重建 socket；
- 对 4 组并行做分阶段通信诊断和有界退避；
- 全部电源可达且 OFF 验证通过后，自动重新执行完整自学习；
- 只有用户点击“停止/取消启动”才清除 PendingStartIntent。

若 4 组 `*IDN?` 同时失败，应合并为一个共享通信事故，避免每组独立刷屏和重复触发四套恢复。

建议修改位置：

- `MTTfTest/FrmEpbMainMonitor.cs:2489～2498`
- `Controller/EpbManager.BatchStart.cs`
- `Controller/PowerSupplyCoordinator.cs`
- `PowerSupply.Core/PswTcpClient.cs`
- `MTTFTest.Watchdog/WatchdogHost.cs`

### 8.6 P0：监控界面必须始终有可见安全态

恢复或启动失败时不能让用户只剩桌面。监控页至少显示：

- 当前状态：`安全空闲/恢复第 N 次/启动受阻`；
- 精确阶段：TCP Connect、`*IDN?` 写入、响应等待、OFF 查询；
- 受影响电源组与最后错误；
- 下一次自动重试倒计时；
- “所有电机 DO 已 OFF / 电源 OFF 未确认 / 压力证据状态”；
- 完成数最后增长时间、作废圈连续数；
- 取消自动恢复/人工停止按钮。

短暂机械释放期间不要显示普通 STOP；应显示“安全释放中”。进入 Recovering 宽限期后，不允许再有下一次正向动作。

### 8.7 P1：电源通信与停止流程加固

1. `PswTcpClient` 分别记录 DNS/Connect、写 `*IDN?`、首字节、完整响应耗时；
2. 每次重试前彻底 Dispose 旧 reader/writer/socket，并创建新客户端；
3. 看门狗杀旧进程后给仪器单连接释放留出短退避，再尝试新连接；
4. OFF 确认使用实际输出查询/电压电流遥测，不把 `*IDN?` 本身当作 OFF 证据；
5. `StopAll` 硬截止前必须清除或隔离 Timer/Runner，禁止再出现 `Timers=6 Runners=6`；
6. `RunBoundedStopSafetyAsync` 的所有电源任务必须被 await/观察并汇总，消除 `UnobservedTaskException`；
7. “等待 Watchdog 重启”提示必须读取 Watchdog 实时授权状态；若已 revoked，禁止显示该提示。

### 8.8 P1：补齐时间跳变和峰值封口证据

新增 `WallClockStepDetected`：

```text
wallDelta = UtcNow - previousUtc
monoDelta = StopwatchElapsed(previousMono)
step = wallDelta - monoDelta
```

当 `abs(step) > 100 ms` 时记录：

- 跳变方向和毫秒数；
- 当前 Dev1/Dev2 generation；
- Produced/Accepted/Processed/Persisted sequence；
- 当前 callback interval、monotonic drift、wall arrival delay；
- 活动 CaptureId、cutoff sequence、processed sequence；
- Windows 时间源/系统事件日志引用（若部署环境允许）。

正确改造后，墙上时钟跳变只能产生诊断告警，不能改变控制证据有效性或触发无效圈。

## 10. 必须通过的验收测试

### 10.1 时间域与峰值捕获

1. 运行中把系统墙上时钟向前跳 `+1.5 s`：
   - DAQ、正式圈和完成计数持续正常；
   - 不出现 `CutoffNotCovered`；
   - 只记录 `WallClockStepDetected`。
2. 运行中把系统墙上时钟向后跳 `-1.5 s`：同样不得影响控制、峰值窗口和计数。
3. 注入 120～250 ms 处理延迟，但 sequence 水位最终推进：峰值捕获应等待并成功，不作废正式圈。
4. 永久冻结处理水位：当前圈最多作废一次；释放后 Timer/Runner 停止，不得继续下一正向动作。
5. 同指纹连续三次恢复失败：自动整批安全重建并恢复学习，不得无限作废。

### 10.2 状态机不变量

1. `Recovering` 超过释放宽限期时断言 `Timer=false、Runner=false、Energized=false`。
2. 任何通道连续 2 条 `AbortedBySoftwareRecovery` 必须触发熔断，数据库不得出现本次现场的 27/28 连续作废。
3. 曲线继续更新但完成数 60 秒不增长、同时 DO 仍变化：独立监督必须接管。
4. UI 显示 STOP 后，不允许出现新的 Forward DO；释放中的动作必须显示“安全释放中”。

### 10.3 Watchdog、启动与电源

1. 看门狗恢复时让 4 组电源 30～120 秒不响应 `*IDN?`：
   - 保持所有输出 OFF；
   - 监控界面持续可见；
   - Session 不产生 `.revoked`；
   - Watchdog 按退避继续重试；
   - 电源恢复后自动完成 OFF 预检、自学习并进入 Running。
2. 普通开始时电源临时不可达：进入 StartBlocked，但不得发送 RunStopped；恢复后使用原 PendingStartIntent 自动开始。
3. 用户明确点击“停止/取消启动”：必须写 revocation，且不得再自动开始。
4. 自动恢复子进程失败退出：必须发送 `RecoveryAttemptFailed`，不能发送 `ApplicationClosing`。
5. UI 显示“等待 Watchdog”时，必须断言 sidecar 进程存活且 Session 未 revoked。

### 10.4 长稳与数据

1. 连续 48 小时运行，注入 DAQ 150 ms 空窗、GC、磁盘负载、墙上时钟校正和电源短时拒绝连接。
2. 任一故障发生后 2 分钟内必须满足二选一：恢复到 Running 且完成数继续增长，或保持可见的安全空闲并持续有界重试。
3. 不允许进程在没有监控界面的情况下继续有物理动作。
4. `index.db` 继续通过 integrity check；完成圈、作废圈、实际机械动作圈三者可审计。
5. 全程不得出现 `TaskScheduler.UnobservedTaskException`。

在以上 P0 改动和测试完成前，不应把“无人值守自恢复”判定为可验收。发布至少满足：

## 12. 修复上线前的临时现场措施

这些措施只能降低风险，不能替代代码修复：

1. 开始试验前完成一次系统时间同步，长试验期间避免人工改时；如现场时间策略允许，使用平滑校时而不是秒级跳变。
2. 开始前独立验证 4 组电源的 TCP 与 `*IDN?` 响应；任何一组不可达都不要强行启动。
3. 若再次出现“系统自恢复/STOP，但曲线仍有周期动作且完成数两个周期不增长”，立即暂停并停止，封存数据后重启；不要等待它自行恢复。
4. 继续保留所有 `AbortedBySoftwareRecovery`，并把实际动作圈纳入寿命附加统计。
5. 任何“电源 OFF 未确认”都按真实安全风险处理，不能绕过预检。

## 13. 对现场三个问题的直接回答

### 这是怎么回事？

09:47 主机墙上时钟向前跳约 1.34 秒，完整峰值捕获跨时钟域比较并只等待 100 ms，导致所有通道每圈都被判 `CutoffNotCovered`。状态进入“系统自恢复”，但恢复分支没有停 Timer/Runner，所以物理控制继续、曲线继续，而每圈作废不计数。这不是单纯 UI 假象，是**状态机假恢复、控制仍动作**。

### 为什么自学习后启动受阻？

09:57 那次自学习和启动实际成功。真正受阻的是 10:15 的后一次尝试，而且它在学习前的电源预检就失败了：4 组电源 `*IDN?` 连续三次超时，程序无法确认全断能，正确地进入 StartBlocked。界面“准备自学习”文字容易让人误以为学习已经开始，最新 manifest 证明没有任何学习圈。

### 为什么后面监控界面没了？

10:06 看门狗恢复子进程因 4 组电源通信超时而接管失败，catch 随后主动 Close；普通关闭写入 `ApplicationClosing` 撤销会话，Watchdog 误认为这是正常/人工终止并停止，所以界面消失且不再重试。10:15 启动失败又被上报为 `RunStopped`，重复了同类撤权问题。

**目标状态应是：任何软件、DAQ、系统校时或电源通信瞬态发生后，程序要么在有界时间内恢复 Running 并继续增加完成数，要么保持所有输出 OFF、监控界面可见并持续安全重试；绝不能再次出现“界面 STOP、机器仍循环、圈数不增”，也不能在无人值守恢复失败后把监控界面直接关掉。**
