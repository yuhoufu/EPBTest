## 1. 结论先行

本次 12:21 左右的主界面退出，**不是未处理异常导致的 WinForms 崩溃，也不是 Watchdog 因主进程失联而直接强杀**。

已确认的直接链路是：

1. 12:20:21 前后，Dev1、Dev2 同时出现 DAQ 回调陈旧、多个电源组遥测延迟以及 Dev1 落盘队列快速堆积，说明当时存在一次跨设备的公共调度/执行压力窗口。
2. EPB9 的周期心跳超过 30 秒，12:20:52 触发 `TimerHeartbeatStale` 自愈。
3. 当前实现先把 EPB9 对外发布为 `Paused`，之后才尝试登记恢复事件并发布 `Recovering` 所有者。EPB9 在 5 秒内没有完成这一步，因此形成了“`Paused`，但没有人工暂停所有者，也没有正式恢复所有者”的状态空窗。
4. Watchdog 按现有协议把该状态判定为 `ChannelPausedWithoutManualOwner`，于 12:20:57 对仍有响应的主程序发起 `ResponsiveApplicationControlRepairRequested`。
5. 主程序正常执行全局安全停机：电机输出关闭、液压释放、电源关闭、落盘边界收口完成；12:21:02 记录 `ApplicationExitRequested / TakeoverReplacementExit` 后受控退出。
6. 后续自动拉起没有成功，状态被永久封锁为 `SafeIdleRecoveryBlocked`，记录为 `UnhandledSoftwareStartup / OutcomeUnknown / RecoveryAttemptFailed`。现有证据不足以继续唯一定位到某一个启动函数或异常类型。

因此：

- **与同日此前 04:51 的退出不是同一个直接原因。**此前是主程序/UI 心跳消失后被 Watchdog 终止，随后又因 Supervisor 安全交接身份不匹配而无法恢复；本次主程序一直能够响应，Watchdog 是因 EPB9 自愈所有权空窗主动要求安全停机和替换退出。
- **两次事故属于同一类系统性问题。**共同点都是公共执行压力先触发多路次生恢复，再由运行状态、恢复所有权与 Watchdog 协议之间的边界缺陷把局部异常升级为整机退出。
- **当前仓库最新 V2.15.0.0 不能认定已经解决本次精确问题。**V2.15 已修复此前的 Supervisor 安全交接/拉起权限链，并改善 DAQ 积压与安全收口，但本次涉及的 Timer 自愈状态发布顺序和 Watchdog 的 `Paused` 判定逻辑在 V2.14.2.11 与当前 V2.15 代码间没有变化。

综合判断：**V2.15 对“上一次退出后无法拉起”和“公共 DAQ 压力”有明确改善，但对本次 `TimerSelfHealing -> 无所有者 Paused -> Watchdog 全局接管` 链路仍存在确定缺口。必须补充针对性代码修复和回归测试后，才能宣布该问题闭环。**

## 4. 根因分析

### 4.1 第一层：公共执行压力触发多路异常

同一秒内同时出现：

- Dev1、Dev2 DAQ 回调陈旧；
- EPB9、EPB12 采样新鲜度截止；
- 电源组 2、3、4 遥测均出现近 1 秒延迟；
- Dev1 落盘队列在极短时间内升至 256；
- 随后 EPB7、EPB8、EPB9 出现 Timer 心跳陈旧。

这组证据更符合**共享调度、线程池、同步阻塞、GC、磁盘/锁竞争等公共执行资源在短时间内被拖慢**，而不符合某一个 EPB 通道或某一块 NI 设备单点损坏。

现有日志不足以把这一层唯一归因到 NI 驱动、CLR/GC、磁盘 I/O、线程池饥饿或某个具体锁；因此本报告只将其定性为“公共执行压力窗口”，不做超出证据的单点结论。

### 4.2 第二层：EPB9 Timer 自愈存在恢复所有权发布空窗

当前 `Controller/EpbManager.TimerRuntimeHealth.cs` 的关键顺序为：

1. `failedTimer?.Pause("TimerSelfHealing:...")`；
2. 取消周期 CTS；
3. 解除液压参与者；
4. 捕获并封口软件恢复周期窗口；
5. 最后才调用 `TryBeginRecoveryIncident(...)`；
6. 只有该调用成功后的发布回调才把通道状态改为 `Recovering` 并带出正式 Timer 恢复所有者。

这意味着从步骤 1 到步骤 5 之间，外部可观测状态可能是：

```text
State=Paused
Timer=True
Runner=True
Energized=False
ManualPauseOwner=False
RecoveryOwner=空
```

本次 EPB9 在 5 秒内没有发布 `Recovering`。日志无法证明究竟是前置同步步骤耗时、恢复登记被拒绝，还是异常路径提前返回；但可以确定：**Pause 已对外可见，而正式恢复所有者没有及时出现。**

此外，`TryBeginRecoveryIncident(...)` 如果返回 `false`，调用方会移除 `_timerRuntimeRecoveries` 后返回，当前路径没有保证把已经发布的 `Paused` 收敛到带所有者的恢复态或明确终态，这使“孤儿暂停”可以长期存在。

### 4.3 第三层：Watchdog 将所有 `Paused` 默认解释为人工暂停契约

当前 `Watchdog.Protocol/WatchdogPolicy.cs` 对 `Paused/PausePending` 设置 `ManualPauseOwnerRequired=true`。当人工暂停所有者不存在时，`SelectInvariantCode` 返回：

`ChannelPausedWithoutManualOwner`

经过 5 秒不变量宽限期后，Watchdog 会升级为接管处理。

当前 `MTTfTest/FrmEpbMainMonitor.UnattendedRecovery.cs` 只有在通道已经进入要求恢复契约的状态（如 `Recovering/ResumeChecking`）时，才向 Sidecar 暴露正式恢复所有者。处于 `Paused` 的 Timer 自愈过渡态无法携带结构化恢复意图，因此 Sidecar 无法区分：

- 真正被遗弃的无主暂停；
- 人工暂停但所有权数据缺失；
- Timer 自愈已经开始，但正在安全去能/封口、尚未完成恢复登记。

因此本次 Watchdog 的行为符合现有协议，但协议与主程序的状态发布顺序不兼容。直接缺陷不应简单归为“Watchdog 太敏感”，而是**状态、意图、所有权三者没有原子交接**。

### 4.4 第四层：退出后的自动恢复再次失败

本次会话的确定事实为：

- `RecoveryFailureCode=UnhandledSoftwareStartup`
- `LastFailureDetailCode=RecoveryAttemptFailed`
- `LastFailureReason=OutcomeUnknown`
- `RelaunchConsecutiveFailures=1`
- `RelaunchProcessId=0`
- `LaunchIntentId=null`
- `CircuitOpen=true`
- 主程序端出现 `RecoveryFailureReceiptIgnored / UnknownCorrelation`

说明系统没有完成一次可确认的新主程序拉起，并在一次未知结果后进入永久阻断。封盘没有保留足够的异常载荷来继续证明失败发生在可执行文件创建、启动回执关联、检查点恢复还是其他启动阶段，因此这里不能复用上一次的 `SupervisorSafetyHandoffIdentityMismatch` 作为本次结论。

持续到封盘的 `RecoveryBlockedRestored / TerminalSessionObservedOnStartup` 高频记录还说明终态 Sidecar/观察流程存在反复启动迹象，需要单独收敛，避免在主程序已不可恢复时形成进程或日志风暴。

## 8. 必须落地的整改

### P0：消除 Timer 自愈的无所有者状态窗口

不能只把 5 秒超时放宽。应保证“安全动作、恢复意图、恢复所有者、对外状态”形成有界且可审计的原子交接：

1. Timer 自愈触发后，优先执行高优先级安全 OFF；
2. 在对外发布可被 Watchdog 解释的暂停状态前，先预留恢复事件 ID/代次并发布结构化 `FormalTimer` 所有者；
3. 对外状态直接进入带所有者的 `Recovering`，或使用专门的 `RecoveryPausePending` 契约；
4. 周期 CTS 取消、液压参与者解除、数据封口等可能耗时的步骤在所有者已经可见后继续；
5. `TryBeginRecoveryIncident` 若登记失败，必须立即落到明确的 `StartBlocked/SystemFault` 安全终态，清除 Timer/Runner，不允许留下无主 `Paused`。

### P0：让 Watchdog 识别结构化恢复暂停

心跳快照至少应增加或保留：

- `PauseOwnerKind`：`Manual / TimerSelfHealing / DaqRecovery / SystemFault`
- `RecoveryIncidentId`
- `RecoveryGeneration`
- `RecoveryStartedUtc`
- 安全 OFF/封口阶段

Watchdog 只应对“没有人工所有者、没有恢复所有者、没有有效恢复意图，且超过刷新宽限期”的真正孤儿暂停执行全局接管。不能仅依据字符串状态 `Paused` 推断人工暂停契约。

### P0：补精确回归测试

至少增加以下故障注入：

1. EPB9 连续运行时注入超过 30 秒的 `TimerHeartbeatStale`；
2. 同时让另一设备处于 DAQ 恢复，并把周期封口/液压解除延迟到 5 秒以上；
3. 分别在 Timer Pause、CTS 取消、液压解除、周期封口、恢复事件登记处注入延迟和失败；
4. 断言状态必须为“带 `FormalTimer` 所有者的 `Recovering`”或明确安全终态；
5. 断言任何时刻都不会出现可持续 5 秒的无主 `Paused`；
6. 断言不产生 `ResponsiveApplicationControlRepairRequested`、不执行全局 StopAll、主界面不退出；
7. 断言 Timer 重建后恢复循环，异常周期不计数。

### P1：补齐自动拉起失败证据链

- 持久化启动失败的原始类型、阶段、Win32/CLR 错误、启动者、目标路径、关联 ID；
- `RecoveryFailureReceiptIgnored / UnknownCorrelation` 必须保留收发两端关联信息；
- 对 `OutcomeUnknown` 不应在缺少明确失败证据时仅一次就永久打开恢复熔断；
- 新主程序未产生 PID 时，应明确区分“未发起”“创建失败”“启动后立即退出”“回执丢失”；
- 终态 Sidecar 不应约每秒反复启动并重复写入同类终态记录。

### P1：现场资源压力取证

后续版本应在 DAQ 陈旧或落盘队列达到警戒值时同步记录：

- CLR GC 暂停、线程池队列/可用线程；
- 关键执行器队列深度及最长等待；
- 磁盘写延迟而不仅是吞吐和队列长度；
- NI 回调进入、取样、分发、持久化各阶段时间戳；
- 关键锁等待和 UI 消息泵延迟。

这些证据用于定位第一层公共压力源，但不能替代 P0 的状态机修复。即使压力源将来再次出现，局部恢复也不应无故升级为整机退出。

## 9. 修复后的验收门槛

1. 新增的 Timer 自愈所有权专项测试全部通过；
2. 运行现有三类共享回归：控制/Watchdog、落盘、PowerSupply；
3. 安装目录下执行 LocalSystem Supervisor 端到端验证；
4. 验证主程序受控退出、强杀、启动失败、回执丢失、检查点失败等矩阵；
5. 现场带 NI、CAN、液压和电源完成不少于 24 小时无人值守运行，建议继续完成 48 小时长稳；
6. 人工注入 DAQ 陈旧和 Timer 心跳陈旧，确认局部恢复不触发主界面退出；
7. 验证恢复期间无误计数、无危险输出残留、数据库检查为 `ok`，且所有失败都能从单一关联 ID 追溯。

在上述 P0 修复和现场验收完成前，发布结论应写为：

> V2.15 已覆盖此前 Supervisor 安全交接和部分 DAQ/恢复闭环问题，但尚未完整覆盖 2026-09-03 12:21 的 Timer 自愈无所有者暂停链路；当前不应宣称该现场退出问题已彻底解决。
