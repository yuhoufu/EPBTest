## 2. 残余问题一：CircuitOpen 热轮询与半开失调度

### 2.1 原问题为什么仍可能造成无人值守阻断

旧 Monitor 循环固定约 250 ms 运行。进入 CircuitOpen 后，原顺序仍可能经过 `ObserveDurableSafetyState()`，间接读取 ApplicationExit、Closing 和旧 Permit；相同身份不匹配又会反复写 journal，并可能通过状态记录接口改写 `LastReason`。结果是：

- 永久阻断期间每秒约 4 次无效文件读取和 journal 写入；
- 同一故障原因被大量重复记录，掩盖真正的状态变化；
- 失败计数和恢复主状态存在被观察事件污染的风险；
- 旧主程序已经退出时 `_attached=false`，若半开判断依赖 attached 状态，则 30/60/300 秒自动半开可能永远不被调度；
- 本应保持 OFF 并等待冷却的系统，变成高频空转但不能推进的“假活跃”。

这不是 I0006/I0007 中 `maximumSamplesPerBatch` 的直接异常，但会使异常后的 CircuitOpen 难以自动退出，属于无人值守闭环的残余缺口。

### 2.2 实际修复

`WatchdogHost.MonitorAsync()` 的顺序改为：

```text
恢复未完成的 SafetyAgent 分阶段事务
  -> 判断 CircuitOpen/自动半开是否到期
     -> CircuitOpen 且未到期：本轮结束
     -> 到期且属于可恢复 MainLaunch：推进唯一半开事务
  -> 非 CircuitOpen 才观察 ApplicationExit/Closing/旧 Permit
  -> 执行正常附着和健康监督
```

具体约束如下：

- `ObserveSafetyHandoffProgress()` 与 ApplicationExit/Closing 观察完全拆分。CircuitOpen 仍允许完成当前 SafetyAgent 阶段事务，但不再借此轮询旧许可。
- `ShouldProbeCircuitHalfOpen(recoveryBlocked, attached)` 不使用 `_attached` 作为调度门禁；旧主程序已退出正是替换进程应被拉起的场景。
- `ScheduleNextCircuitHalfOpen()` 只接受非永久、属于 `MainLaunch` 家族的失败；冷却按 30、60、300 秒推进。
- 配置损坏、证据绑定失败、身份不一致和真实永久故障不创建周期性 Permit，也不进行高频探测。
- CircuitOpen 期间不增加失败计数、不生成新 Permit；只有冷却到期的唯一半开事务可以创建下一 generation。
- 观察事件只进入 event journal，不再调用会修改主状态和 `LastReason` 的 `Record()`。
- 新增 `RepeatedEventSummarizer`，使用 `Stopwatch`，键为：

```text
(EventType, SessionId, PermitGeneration, PermitId, Fingerprint)
```

- 首次事件立即写入；相同事件只在内存累加；每 30 秒写一次带 `SuppressedCount` 的汇总；身份或指纹变化才视为新事件。
- SafetyAgent 任务结束后会在 `finally` 释放本地运行标志，允许后续合法 handoff 启动；已终态的 receipt 不重复启动 Agent。

### 2.3 验证结果

专项使用 I0007 阻断身份模拟连续 5 分钟、每 250 ms 一次观察：

- 首次记录：`1` 条；
- 30 秒汇总：`10` 条；
- 被抑制重复：`1200` 次；
- 无 250 ms journal 写入；
- 身份变化后只增加一条新的首次事件；
- `_attached=false + CircuitOpen` 仍能触发自动半开；
- 永久及非 `MainLaunch` 故障不会进入周期探测。

## 3. 残余问题二：SafetyAgent 未形成独立安全边界

### 3.1 原问题为什么仍有共因失效风险

上一轮虽然把安全执行进程拆成 `MTTFTest.SafetyAgent.exe`，但它仍通过 `IO.NI` 和 `Config` 间接带入：

- `DataOperation` 与 SQLite；
- 完整生产采集和滤波链；
- 与主程序相同的业务配置加载路径；
- 不属于安全动作的 UI/业务程序集传播风险。

这意味着主程序和安全代理仍可能因同一个业务依赖、默认参数或持久化故障同时失效，不满足独立安全执行边界要求。

### 3.2 新增最小 `MTTFTest.SafetyHardware.dll`

新增 `.NET Framework 4.8/x86` 工程 `MTTFTest.SafetyHardware`，版本固定为 `2.13.0.43`。项目直接引用：

- NI `NationalInstruments.Common`、`NationalInstruments.DAQmx`；
- `PowerSupply.Core`；
- .NET Framework 的 `System`、`System.Core`、`System.Xml`、`System.Xml.Linq`。

SafetyAgent 项目现在只有两个项目引用：

- `MTTFTest.SafetyHardware`；
- `Watchdog.Protocol`。

明确移除的依赖为：

- `Config.dll`；
- `IO.NI.dll`；
- `DataOperation.dll`；
- `System.Data.SQLite.dll`；
- `Controller.dll`；
- `MTTFTest.exe`；
- WinForms/DevExpress/SunnyUI 等业务 UI 程序集。

对最终 SafetyAgent 二进制做递归引用读取，得到的闭包只包含系统框架、`MTTFTest.SafetyHardware`、`MTTFTest.Watchdog.Protocol`、`PowerSupply.Core` 和 `NationalInstruments.*`。其中 NI 基础程序集自身带有 `System.Windows.Forms/System.Drawing` 框架引用，但不存在任何业务 UI、生产采集、持久化或 SQLite 程序集。

### 3.3 配置先验门禁

`SafetyHardwareConfiguration.Load()` 直接读取安全快照目录中的最小配置：

- `AIConfig.xml`；
- `AOConfig.xml`；
- `DOConfig.xml`；
- `PowerSupplyConfig.xml`。

以下任一情况都在创建 NI Task 或连接电源之前抛出 `SafetyHardwareConfigurationException`，由 SafetyAgent 映射为 `SafetyAgentConfigInvalid`：

- 配置文件缺失或根节点错误；
- DO/AO/AI 物理通道为空或重复；
- 压力通道缺失、未启用或不能与 snapshot v2 精确绑定；
- 标定参数非有限数；
- 没有可用 DO、AO 或电源范围；
- AO 范围不包含 `0.0 V`；
- 电源身份、地址或启用范围非法；
- `SampleRateHz <= 0` 或 `SamplesPerChannel < 1`。

配置错误属于确定性配置失败，不打开硬件、不盲目重试主程序。硬件占用、断连或回读失败属于 `HardwareUnavailable`，保留同一 Permit 和已完成阶段，保持 OFF 并按既有退避复探。

### 3.4 独立安全动作

- DO：按设备分组创建启用线路；创建后第一次硬件写入就是全 `false`，从不写 XML 默认状态。
- AO：逐个启用物理通道写字面 `0.0 V`，不经过压力标定或业务换算。
- Power：执行输出 OFF，并读取遥测确认连接有效且 `OutputEnabled=false`。
- Pressure：只创建 snapshot 指定的压力 AI 通道；显式使用 `SampleRateHz/SamplesPerChannel`，样本新鲜度和稳定保持只用单调时钟。

生产 `TwoDeviceAiAcquirer` 保持原职责；旧 `IO.NI/SafetyPressureProbe` 已删除，安全压力探针只存在于最小安全程序集。

## 4. Webhook 选配语义

### 4.1 状态模型

新增 `UnattendedAlarmDeliveryState`：

| 状态 | 含义 | 是否阻断安全控制/自恢复 |
| --- | --- | --- |
| `LocalOnly` | Webhook 未启用或配置文件不存在；本地告警正常 | 否 |
| `WebhookHealthy` | Webhook 已显式启用且发送链健康 | 否 |
| `WebhookDegraded` | 仅在 `Enabled=true` 后发生配置、密钥、超时或发送失败 | 否 |
| `LocalPersistenceDegraded` | 本地耐久告警写入失败 | 否；异常隔离在告警接口内部 |

兼容属性 `DeliveryDegraded` 继续保留，但 `LocalOnly` 返回 `false`。

### 4.2 `Enabled=false` 或配置缺失

默认配置 `MTTfTest/Config/UnattendedAlarmConfig.xml` 为：

```xml
<UnattendedAlarm Enabled="false"
                 FailurePolicy="DegradeAndContinue"
                 Endpoint=""
                 SecretEnvironmentVariable="EPB_UNATTENDED_WEBHOOK_SECRET"
                 RequestTimeoutMs="5000"
                 RetrySeconds="1,5,15,30,60,300"
                 SpoolMaxBytes="16777216" />
```

此时程序：

- 状态为 `LocalOnly`；
- 写本地耐久滚动告警和 Windows Application Event Log；
- 不创建 `UnattendedAlarmSpool`；
- 不检查 `EPB_UNATTENDED_WEBHOOK_SECRET`；
- 不创建 `HttpClient` 和发送线程；
- 不写 `unattended-alarm-degraded.log`；
- 不产生网络请求或网络退避；
- 不把告警投递状态作为 SafetyAgent、CircuitOpen 半开或主程序自恢复的门禁。

因此，没有 Webhook 服务、没有网络、没有密钥，程序仍可按本地安全闭环稳健运行和自恢复。

### 4.3 显式启用 Webhook

只有配置 `Enabled=true` 后，才校验 Endpoint 和环境变量密钥，创建远程 spool 和发送线程。失败继续按 1、5、15、30、60、300 秒退避，并保留 HMAC-SHA256、唯一 EventId、去重压缩和重启重放。

从 LocalOnly 改为启用后，只发送启用后产生的新事件；LocalOnly 期间的历史告警仅保留本地，不补发为远程积压。

## 10. 最终判定标准

可以判定“这两项残余问题已解决”的软件标准已经满足：

- CircuitOpen 无高频旧许可轮询和状态 journal 改写；
- 自动半开与 `_attached` 解耦；
- SafetyAgent 依赖边界通过源码和递归二进制双重门禁；
- Webhook 关闭是健康 LocalOnly 且与恢复闭环解耦；
- 完整自动化和发布脚本通过。

可以判定“现场无人值守彻底解决”的标准尚未全部满足。只有第 9 节全部实机及耐久项目通过、干净工作区生成正式候选并经现场审批后，才能把现场发布状态从 `NO-GO` 改为 `GO`。
