## 1. 结论

本次启动失败不是 DAQ 故障、程控电源通信故障，也不是 V2.13.0.20 把 `0.5 A` 阈值改严。封盘证据表明：

- PSU2 上电后稳定负载平均约 `2.23 A`；
- PSU4 上电后稳定负载平均约 `1.56 A`；
- 两组均约 `12 V`，没有保护、恒流、限流或遥测丢失；
- 原代码在 DO 控制器初始化和全关之前先打开程控电源；
- 原代码发现非零负载后仅重复电源 OFF/ON 三次，没有改变下游 DO/继电器状态；
- 启动最终失败后，检查点尚未 Armed，Watchdog 却无条件杀进程并尝试恢复，随后必然报 `CheckpointDisarmed`。

V2.13.0.15 能稳定运行，是因为当时接手的硬件初态恰好干净，并不是它具备不同的安全启动逻辑。V2.13.0.15 与 V2.13.0.20 都存在“先开电源、后初始化 DO”的潜伏缺陷；V2.13.0.20 接手异常退出后的遗留负载，才使缺陷确定性暴露。

本次修复没有放宽电流门禁，而是消除了对现场初态的依赖，并封住 Watchdog 的二次放大链路。

## 2. 修复后的唯一启动顺序

批量开始现在严格执行以下顺序：

```text
创建 Run 身份并开始电源遥测
  -> 撤销本轮全部通道执行授权
  -> 四台程控电源全部 OUTP OFF
  -> 四台逐台实时回读并确认 OutputEnabled=false
  -> 无条件销毁并重建 NI DO 任务
  -> 12 路 EPB 正/反向 + 2 路压力 DO 再次原子写全零
  -> 全部 AO 压力命令写零并确认每一路成功
  -> 等待继电器触点释放 300 ms
  -> 液压协调器健康检查
  -> DAQ 健康检查
  -> 只对本轮需要的电气组设参并 OUTP ON
  -> 电压稳定 + |Iout| <= 0.5 A 连续 300 ms
  -> 颁发本 Run 的执行授权
  -> StartupPositioning / Learning / Formal
```

任何一步失败都会保持或重新回到全部输出关闭状态。尤其是：任意一台程控电源不能确认 OFF 时，代码不会进入 DO 初始化，更不会继续开启选择组电源。

空闲状态下的单通道新启动也已接入同一冷启动安全基线，避免从单通道入口绕过。已有其它通道运行时不会全局关闭四台电源，以免破坏在运行通道；该场景继续受现有 Run 的组级电源许可和执行代际约束。

## 3. 代码实施内容

### 3.1 冷启动安全基线事务

修改位置：

- `Controller/EpbManager.BatchStart.cs`
- `Controller/EpbManager.cs`
- `IO.NI/DoController.cs`
- `IO.NI/AoController.cs`

具体实现：

1. 新增 `ColdStartSafetyBaselinePolicy.ExecuteAsync`，把安全顺序固化为单一事务，禁止调用点任意重排。
2. 新增 `EstablishColdStartSafeBaselineAsync`，在批量启动生命周期锁内、所有其它硬件预检之前执行。
3. 电源安全关闭使用 `CancellationToken.None`。即使用户在启动中取消，安全 OFF 也不能被开始按钮的取消令牌中断。
4. 四台电源的 `PowerSafetyDisableResult` 必须全部为 `ConfirmedOff=true`；否则抛出 `ColdStartSafetyBaselineException(Stage=PowerOff)`。
5. 新增 `DoController.EstablishColdStartAllOffBaseline()`：
   - 无条件重新初始化 DO 任务；
   - 重新创建全部配置线路；
   - 初始化后再执行一次所有设备全零写入；
   - 初始化或写零任一步失败都拒绝继续。
6. 新增 `AoController.TryResetAll()`：
   - 配置通道数必须大于零；
   - Writer 数量必须与配置数量一致；
   - 所有配置通道必须逐路写入零压力并成功；
   - 不再把“零路 Writer”误认为复位成功。
7. 空闲单通道开始同样调用冷启动基线，封住旧入口。

通过日志 `ColdStartSafeBaselinePassed` 可以看到本次基线是否完成，以及继电器等待时间和目标通道。

### 3.2 继电器释放时间配置化

修改位置：

- `Config/PowerSupplyConfig.cs`
- `MTTfTest/Config/PowerSupplyConfig.xml`
- `Controller/PowerSupplyCoordinator.cs`

新增配置：

```xml
ColdStartRelaySettleMs="300"
```

合法范围为 `50～5000 ms`。当前采用 `300 ms`，后续可根据继电器规格和现场测量调整，但不得设为零或绕过。

### 3.3 稳定残余负载不再按普通软件瞬态盲目重试

修改位置：

- `Controller/PowerSupplyCoordinator.cs`
- `Controller/EpbManager.BatchStart.cs`

新增结构化异常：

- `ResidualStartupLoadException`：单个电气组的持续残余负载；
- `ResidualStartupLoadAggregateException`：多个电气组并行失败的完整汇总。

当输出电压已经建立、无保护、但电流持续超过 `StartupZeroCurrentA` 时，异常会记录：

- 电气组；
- 样本数；
- 最小电流；
- 平均电流；
- 最大电流；
- 最后一帧输出电压。

并行启动多个电气组时，代码从 `Task.WhenAll.Exception` 中提取所有残余负载异常，不再只保留第一个抛出的 PSU。PSU2、PSU4 同时存在负载时，会在同一终态中同时报告两组统计。

自动处理预算严格为一次：

```text
第一次检测到残余负载
  -> 全部电源回滚 OFF
  -> 再执行一次完整冷启动安全基线
  -> 再做一次零电流复核

第二次仍有残余负载
  -> 全部输出保持 OFF
  -> ColdStartSafetyBaselineException(Stage=ResidualLoadRecheck)
  -> 禁止启动
  -> 不进入三次相同电源循环
  -> 不触发未武装进程重启
```

原有 `StartupZeroCurrentA=0.50 A`、电压稳定门槛和连续 `300 ms` 判定全部保留，没有降低安全标准。

### 3.4 Watchdog 接管资格改为结构化门禁

修改位置：

- `Watchdog.Protocol/WatchdogProtocol.cs`
- `Watchdog.Protocol/WatchdogPolicy.cs`
- `MTTfTest/WatchdogRuntime.cs`
- `MTTFTest.Watchdog/WatchdogHost.cs`
- `MTTfTest/FrmEpbMainMonitor.cs`

协议新增 `WatchdogBatchStartFailureContext`，包括：

- 当前 RunId；
- 检查点 RunId；
- RunEpoch；
- FormalRunCommitted；
- CheckpointArmed；
- RecoveryProcess。

Sidecar 现在只有在以下条件全部满足时才允许因 `BatchStartFailed` 接管：

```text
CheckpointArmed == true
&& CurrentRunId != Guid.Empty
&& CheckpointRunId != Guid.Empty
&& CurrentRunId == CheckpointRunId
&& (FormalRunCommitted == true || RecoveryProcess == true)
```

缺少上下文、检查点未 Armed、RunId 为空、RunId 不一致或正式运行尚未提交时，Sidecar 只记录 `BatchStartFailedSafeIdle`，继续保持附着，但禁止 `BeginTakeover`、禁止杀主进程、禁止拉起无效恢复进程。

主界面提示也已修正，不再宣称“独立看门狗将安全接管并退避重试”，而是明确说明已经安全回滚、未提交正式运行时不会杀进程。

## 4. 与 V2.13.0.15 的最终差异

| 项目 | V2.13.0.15 / 原 V2.13.0.20 | 本次修复后 |
|---|---|---|
| 冷启动初态 | 依赖现场恰好为零 | 每次主动建立安全基线 |
| 四台电源 OFF | 无统一前置事务 | 全部 OFF 且逐台确认 |
| DO 初始化 | 第一次动作时懒初始化 | 电源 ON 前强制重建 |
| DO 全关 | 失败收尾才可能发生 | 电源 ON 前再次全零 |
| AO 归零 | 无启动前完整确认 | 配置路数和逐路结果均确认 |
| 继电器释放 | 无显式等待 | 配置化等待 300 ms |
| 残余负载重试 | 相同 OFF/ON 最多三次 | 清基线后只复核一次 |
| 多 PSU 异常 | 最终常只显示首个异常 | 同时汇总所有电气组 |
| 未 Armed 启动失败 | Watchdog 无条件接管 | SafeIdle，不杀进程 |
| 正式 Run 恢复 | 按消息类型判断 | Armed + RunId + 阶段共同判定 |

因此，新实现不再依赖 V2.13.0.15 当时的干净初态；即使上一版本异常退出并遗留 PSU/DO 状态，新进程也必须先关掉全部 PSU，再重建和归零 DO/AO，之后才允许上电。

## 6. 关键安全不变量

以下条件已经由代码和自动测试固化：

1. 电源 OFF 未全部确认，不得重建 DO，更不得开启选择组电源。
2. DO 重建或全零失败，不得开启电源。
3. AO 任一路缺失或归零失败，不得开启电源。
4. 零电流门禁不得通过放宽阈值绕过。
5. 残余负载自动清理最多一次，第二次失败必须保持 OFF。
6. 多个电气组同时失败必须保留全部诊断数据。
7. 正式 Run 未提交且检查点未 Armed 时，启动失败不得杀进程。
8. Watchdog 接管必须同时满足检查点、RunId 和运行阶段条件。

## 7. 失败后的预期现场表现

如果冷启动安全基线成功并且残余负载被清除，日志应按顺序出现：

```text
全部程控电源安全关闭并确认
DO 初始化完成
DO 全部关闭
冷启动安全基线已建立
AO 所有通道已复位
ColdStartSafeBaselinePassed
DAQ 启动健康检查通过
程控电源 OUTP ON
启动输出已稳定
```

如果硬件或外部线路仍造成真实残余负载，预期行为是：

```text
第一次：ResidualStartupLoad -> 全部OFF -> 完整清基线 -> 唯一一次复核
第二次：ResidualLoadRecheck -> 全部OFF -> 启动受阻 -> 主程序保持安全空闲
Watchdog：BatchStartFailedSafeIdle / TakeoverRejected=CheckpointDisarmed 或 FormalRunNotCommitted
```

不得再出现以下旧行为：

- 三次完全相同的 PSU OFF/ON；
- 失败三次后才第一次初始化 DO；
- 只报告 PSU2 而遗漏同时异常的 PSU4；
- 未 Armed 时 `TakeoverRequested`；
- 原进程被杀后新进程报 `CheckpointDisarmed`。
