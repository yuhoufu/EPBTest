# 2.14.2.12 原有恢复清单与外部仅兜底边界

日期：2026-09-12。依据修复工作树2.14.2.12-rc.2（HEAD 64681eb）源码静态检查，不是现场实时线程快照。用户最新要求：原有恢复逻辑与线程不改，新增独立程序只兜底。

## 1. 修正上一方案

上一份《独立监督与主程序解耦实施方案》中“迁移恢复决策、禁用原恢复权威、主程序改为外部命令执行器”的内容不再作为实施方向。本补充优先，保留旧文用于追溯。

新方向是外部观察与基础设施兜底：主程序及其现有Watchdog、Supervisor、SessionAgent、SafetyAgent继续完成日常恢复。新程序独立安装运行，不注入主程序、不改变恢复参数、不写旧恢复状态、不代替旧恢复决策。

## 3. 现有独立进程和后台角色

| 角色 | 执行入口 | 原有职责 |
| --- | --- | --- |
| Watchdog侧车 | MTTFTest.Watchdog/WatchdogHost.cs | 心跳与业务状态监督、同进程修复请求、Takeover、主程序退出观察、安全交接、跨进程恢复、退出截止处理 |
| Supervisor服务 | 同项目SupervisorServiceHost.cs | Windows服务宿主；管道受理、会话监测、侧车/安全代理启动及身份核验等 |
| SessionAgent | MTTFTest.SessionAgent/SessionAgentHost.cs | 用户会话侧代理，配合既有监督链完成会话与启动相关操作 |
| SafetyAgent | MTTFTest.SafetyAgent/SafetyAgentRunner.cs | 接管时安全硬件操作、绑定验证和安全结果；按需执行，不是主程序恢复线程 |

WatchdogHost内部有发送队列、TakeoverAsync、安全交接RunSafetyHandoffAsync、退出截止RunApplicationExitDeadlineAsync等异步任务；Supervisor包含AcceptLoop、会话监测任务。服务模式与侧车模式可来自同一可执行项目，但属于不同运行角色，不能只按EXE名称区分。

现有任务计划的精确名称、账户及现场启用状态须从实际安装清单或有界只读检查确认；本轮不凭源码虚构现场注册结果。

## 4. 新独立程序只做什么

优先级固定为：现有实时保护及恢复链先处理；外部程序观察、记录和告警，只有经过验证的基础设施故障才实施有限修复。

| 观察结果 | 外部程序动作 | 禁止动作 |
| --- | --- | --- |
| 试验正常或旧恢复有真实进展 | 保持安静，低负载采样 | 插手当前恢复、重置超时 |
| 单路/部分路长期不推进，主程序仍在 | 有界取证、明确指出卡住通道，通知人工；仅在旧系统已有可验证的正式请求接口时调用它 | 直接杀主程序、模拟点开始、写内部owner文件 |
| 主程序已退出，旧恢复链仍在工作 | 等待原阶段期限及总预算，跟踪动作/计数/落盘 | 并行拉起第二个主程序 |
| 已注册Supervisor服务意外停止 | 确认非维护/卸载、身份及安装配置正确后，通过既有服务入口启动原服务；让旧链自行调和 | 新建另一套Supervisor、伪造恢复许可 |
| SessionAgent缺失 | 只有已验证幂等的原安装启动入口才允许使用 | 任意用户会话重复启动代理 |
| 服务/侧车仍存活但疑似卡死 | 取证和告警；自动替换必须另有旧链支持的安全排他证据 | 仅凭心跳超时终止原监督进程 |
| 身份/配置/许可拒绝、熔断 | 输出具体原因，保持原安全限制 | 改配置放行、清预算、删除检查点 |
| 人工停止、目标完成、维护、后台保存 | 尊重原状态；不拉起试验 | 把无计数增长当作故障 |

外部程序不打开NI/液压/电源控制资源，不输出硬件控制，不写业务数据库，不生成恢复许可。检查按PID+启动时间+会话身份；逐通道观察，不能只看进程存活。

## 5. 完全不改原程序的能力上限

**独立观察和缺失服务补启动可以做；“原恢复已经卡死时，外部保证自动恢复试验”不能无条件承诺。**

原因是原侧车可能只是暂时延迟，随后仍会行动。外部程序即使等待很久，也不能用等待时长证明旧恢复权威已经放弃；若另外启动主程序，就可能双重拉起、串代或覆盖人工停止。

因此首版兜底定义为：识别业务停滞、发现原监督基础设施缺失、通过原受控入口修复基础设施、确认业务是否真正恢复；原许可链或安全接管本身失败时告警。这里“告警而非自动修复”的场景要明确显示，不能宣传为全自动兜底完成。

如果将来要求兜底在旧链卡死时也主动替换，必须先证明旧系统已有足够的排他接管接口、持久停止意图和安全凭证；否则需要另行允许最小接口改造。在用户当前“不改原逻辑”要求下，不实施这类改造，也不采用猜测日志后强杀的替代方法。

## 6. 实施与验收范围

先完成独立只读观察器和离线日志回放，再在jxcq验证服务缺失的受控补启动。新增任务计划只维持新观察器，不直接定时启动主程序。安装、维护标志及自身日志属于新产品，不修改旧试验意图。

必须验证：正常运行不干预；部分停滞能识别；旧恢复进行中不竞争；人工停止不拉起；Supervisor缺失时只补启动原服务；身份/配置拒绝不绕过；外部程序崩溃不影响原恢复；其重启不清除故障证据。

同机任务计划和外部进程无法覆盖Windows整体死机、断电或系统资源完全耗尽。诊断严格限制文件读取、内存、时间和返回大小，避免新观察器自身拖垮试验。

本轮仅核对源码和补充方案，没有改动2.14.2.12源码、参数、线程实现或现场任务计划。
