## 1. 结论

对封存目录 `\\wj-epb\EPB_Data\10358-029_V2.12.0.20_0809_1451` 的最终阶段复核表明，本次不是单一卡钳故障，而是一条软件故障链：

1. 程序刚启动时曲线连续，说明 NI 采集、时间轴和绘图基础链可以正常工作；
2. 运行时间增长后，UI 日志控件反复全量读取、重建和裁剪历史文本，累计制造分配、GC 和消息泵停顿，曲线才逐步出现短线；

V2.12.0.21/V2.12.0.22 已分别修复视觉断笔判据和 UI 日志长期退化；V2.12.0.23 进一步修复停止耐久边界和关闭流程。三项必须作为同一候选整体部署，不能只挑其中一项。

## 3. 为什么刚开始连续，后来才出现短线

V2.12.0.20 有两种不同的 UI 问题，运行初期都不明显：

- 绘图把“距上次实际绘出点的间隔”当作 DAQ 断点。UI 最新值邮箱为了保性能会主动覆盖中间显示帧；当 UI 稍慢时，覆盖后的显示间隔超过 300 ms，就被错误插入 `NaN`，视觉上形成短线。真实 DAQ 时间轴并没有断。
- 日志显示链已有有界增量追加，但另一个 `TextChanged` 处理器又在每批追加后遍历最多 2000 行、重建整个 `Text`、再次裁剪并滚动。文本越多、日志越密，单次成本越高；反复大对象分配和 GC 使停顿随运行时间增长。

所以“刚开始很连贯”不是反例，反而是累计型 UI 退化的直接特征。修复后断笔只依据相邻 DAQ 批次时间；UI 仍保持双设备最新槽、10 FPS 重绘、10 Hz 抽稀，不用增加点数或刷新频率换取观感。

## 4. V2.12.0.23 代码整改

### 4.1 分离分配序号与接收序号

`DaqPipelineSequenceState` 现在独立维护：

- `LastAllocated`：回调取得的诊断序号，队列拒绝时仍保留，用于事故追踪；
- `LastAccepted`：成功取得后台队列容量并移交 Raw 所有权的最后序号，只能由此形成停止、恢复和写盘截止边界。

后台队列容量准入成功后，先原子发布 `LastAccepted`，再把 Item 对消费者可见。这样停止线程不会漏掉真实在途批次；队列拒绝的末批也不会制造永远无法闭合的边界。

### 4.2 退出前冻结最终边界

`ApplicationClosing` 和 `ProgramExit` 在物理断能确认后先停止新 DAQ 回调，再排空最终已接收边界。普通人工停止仍保持 DAQ 可用于同进程后续操作，不受该退出策略影响。

这同时消除了“边界检查通过后、Dispose 前又来了新批次”的竞态。

### 4.3 弹框只提示一次

真实电机/电源安全确认失败或真实存储不可用时，窗口仍保持打开，不能以丢最后圈和报警证据为代价强制退出；但同一关闭故障只显示一次模态提示，后续关闭重试仅写日志，不再连续弹框。

现场这次 `1254944` 伪边界已从根因上修复，正常情况下不再进入持久化弹框分支。

### 4.4 长期 UI 退化修复保持不变

- 删除第二套 `TextChanged` 全量 Lines/Text 重写；
- 只保留唯一增量日志显示所有者；
- 原位删除越界头部，复用批次容器，自动滚动最多 2 Hz；
- 曲线断笔只看相邻 DAQ 采集时间；
- `FieldMetric UI` 分别记录 Delay、Flush、Append、Trim、Scroll，任一阶段超过 200 ms 都拒绝现场放行。

## 6. 部署与现场闭环

只能部署完整的 V2.12.0.23 正式候选目录，不得覆盖正在运行的旧目录，也不得混用旧 DLL/config。启动后先核对 UI/启动日志中的 ProductVersion、PID、EXE 路径、GitCommit、EXE SHA、配置 SHA 和 `GitDirty=false`。

封存后使用：

```powershell
powershell -ExecutionPolicy Bypass -File .\Tools\Invoke-Field-Acceptance.ps1 `
  -DataDirectory '\\wj-epb\EPB_Data\10358-029_V2.12.0.23_封存目录' `
  -MinimumHours 2
```

首轮 2 小时必须同时满足：

1. UI Delay/Flush/Append/Trim/Scroll 单次均小于 200 ms；
2. 两块 DAQ 无 QueueFull、CallbackStale、控制序号不连续；
3. 曲线无 UI 跳帧造成的短线；
4. 无派生的压力/电源遥测陈旧和自维护风暴；
5. 正常退出只有一次关闭流程，并生成 `SESSION Stop/Complete`；
6. 两设备 `STOP_PERSISTENCE Closed=true`；
7. 验收工具确认运行身份与已校验正式候选完全一致。

然后依次完成 8 h、24 h、72 h。同一 Git SHA、EXE/config SHA 和连续 RunId 的 72 小时证据全部通过前，结论只能是“根因已整改、候选待现场验收”，不能签字为无人值守生产完成。
