# V2.12.0.20 发布配置唯一性门禁

## 结论

V2.12.0.19 已形成 `gitDirty=false` 的正式候选，但继续检查实际发布目录时发现：主程序项目把 `TestConfig - 复制(2).xml` 和 `TestConfig - 复制(3).xml` 两份历史备份也标记为 `CopyToOutputDirectory`。因此包内同时存在正式 `TestConfig.xml` 和两份名称相似、内容不同的试验参数。

当前运行代码只读取 `Config/TestConfig.xml`，所以这不是已经证实的运行时多配置竞争；但它会造成部署人员误替换、配置清单歧义、审计误判和后续维护时选错文件。长时间无人值守候选不应携带这种不确定性。V2.12.0.20 将发布配置收口为唯一、固定的七份正式 XML，并在构建和独立校验两端同时强制检查。

## 根因

旧式 `MTTfTest.csproj` 中三份备份文件都作为 `Content` 展示，其中两份额外带有：

```xml
<CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
```

V2.12.0.19 的发布脚本正确地按项目声明生成配置身份，但没有进一步判断项目声明本身是否只包含生产配置，所以把错误的项目清单确定性地复制并纳入哈希。确定性清单解决了“包内文件无法追溯”，没有解决“被追溯的文件是否应该发布”。

## 整改

1. 保留三份历史文件在源码项目中供人工对照，但取消所有备份的 `CopyToOutputDirectory`。
2. 正式发布目录只允许以下七份配置：`AIConfig.xml`、`AlarmConfig.xml`、`AOConfig.xml`、`DOConfig.xml`、`PowerSupplyConfig.xml`、`TestConfig.xml`、`UIConfig.xml`。
3. `Build-Release.ps1` 在调用 MSBuild 前比较项目发布集合：缺少、增加或重复任一配置立即拒绝构建。
4. 构建后再次比较输出目录集合，再计算配置聚合 SHA；旧文件残留和意外复制都无法进入候选。
5. `Verify-Release.ps1` 独立执行相同允许列表检查，并继续执行递归文件清单、长度、SHA 和多余文件检查。
6. 程序、构建工具、现场门禁和清理工具版本统一迭代为 `V2.12.0.20`。
