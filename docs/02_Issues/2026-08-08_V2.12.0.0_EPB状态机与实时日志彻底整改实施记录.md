`2.12.0.0` 不再围绕某个超时值或 UI 文案做局部覆盖，而是统一修正以下三个系统不变量：

2. 批量启动尚未提交 Formal 时，单通道恢复不得创建正式 Timer；
3. StartBlocked 等非运行终态提交前，Timer、Runner、液压参与权和电机输出必须已经清场。

## 2. 已完成整改

### 2.1 日志持久化与实时控制解耦

涉及文件：

- `Config/ProjectLogStore.cs`
- `Config/IAppLogger.cs`
- `MTTfTest/FormLoggerAdapter.cs`
- `IO.NI/DoController.cs`
- `Controller/EpbManager.cs`

实施内容：

- `ProjectLogHub` 新增容量为 32768 的有界后台队列和独立低优先级写线程；
- Form 日志适配器的 Info、Warn、Error 只入队，不在调用线程写文件；
- Warn/Error 的 durable flush 改为后台请求，不再同步等待磁盘；
- 控制层 `FlushPersistentLog` 优先使用非阻塞 `RequestFlush`；
- 项目日志目录配置也进入同一 FIFO 队列，避免项目切换后的第一条控制日志同步创建目录或轮转；
- 队列满时记录丢弃计数并返回失败，绝不反压 DAQ、DO、AO 或安全状态机线程；
- 进程退出、人工查看日志等非实时入口仍使用带屏障的显式 Flush，保证队列排空；
- `SetEpbOffCore` 的安全 Worker 完成边界固定在 NI 写入和内存状态提交之后，日志由线程池延迟发布，不能再计入 100 ms OFF 期限；
- 高优先级 OFF 遥测增加 `HardwareCompletedUtc` 和 `LateHardwareSuccess`，调用方超时与硬件最终结果不再混为同一个 bool 事实；
- 迟到成功会更新电机去能量化位图和终端 OFF 证据，同时保留电源组失效安全，等待新鲜电流/电源回读完成最终对账。

这直接关闭现场 `NIWrite=1.058ms、Worker=169.245ms、CallerTimedOut=True、FinalResult=True` 的错误升级链。

### 2.2 批量启动阶段与报警恢复所有权隔离

涉及文件：

- `Controller/EpbManager.BatchStart.cs`
- `Controller/EpbManager.PauseResume.cs`
- `Controller/EpbManager.cs`

实施内容：

- 新增 `_formalPhaseCommitted`，每个新批次开始时清零，只有正式 Timer 全部建立并由 `MarkBatchRunning` 提交后才置位；
- `BeginRecoverableChannelRestartLoop` 在批次启动、定位、学习、资格阶段只等待批次协调器，不调用单通道正式恢复；
- `ResumeAlarmStoppedChannelAsync` 增加同样的入口门，人工或无人值守调用都不能越过批次阶段；
- `RejoinFormalChannelsAtSharedFutureSlot` 增加最终防线，Formal 未提交时直接拒绝任何独立重入；
- 正式批次暂停/恢复期间保持 Formal 已提交事实，因此合法的暂停恢复和正式期报警恢复不受影响；
- 原有 RunEpoch、恢复所有权、液压 epoch 和租约隔离继续作为迟到旧任务的第二层保护。

这关闭了“EPB8 在学习期单独进入 Formal Slot，屏障错误等待仍在学习的 EPB9/10/11”的双拥有者链路。

### 2.3 StartBlocked 与真实执行资源原子一致

涉及文件：

- `Controller/EpbManager.cs`
- `Controller/EpbManager.BatchStart.cs`
- `Controller/DoControlTrace.cs`
- `Controller/ChannelRuntimeState.cs`

实施内容：

- 新增 `RevokeChannelExecutionBeforeTerminalState`：依次撤销液压参与权、取消 Stop CTS、移除 Timer、执行高优先级 OFF、请求液压释放、移除 Runner；
- 新增唯一的 `PublishStartBlockedAfterCleanup` 入口；批量预释放失败、学习失败、资格失败、批量启动异常、单通道预检失败和单通道学习失败统一使用该入口；
- 只有 Timer/TimerCache、Runner/RunnerCache、Energized 全部归零且 OFF 已确认时才发布 StartBlocked；
- 如果清场或 OFF 无法确认，发布 `SystemFault/TerminalCleanupUnverified`，不再伪装为“已经停止的启动受阻”；
- Forward/Reverse 命令增加运行状态许可，NotEnabled、StartBlocked、AlarmStopped、InterlockStopped、ManualStopped、Completed、SystemFault、Paused 均不能继续加电；
- 运行状态事件增加 `RunEpoch、Enabled、FormalPhaseCommitted、TimerActive、RunnerActive、Energized` 资源快照；UI 悬浮提示可直接核对状态和执行资源。

这关闭了“批量流程写入红色 StartBlocked，但旧恢复 Timer 继续发 Forward DO”的状态/资源分叉。

### 2.4 禁用通道状态中央强约束

涉及文件：

- `Controller/EpbManager.cs`
- `MTTfTest/FrmEpbMainMonitor.PowerSupply.cs`

实施内容：

- 中央状态发布入口强制 `Enabled=false => NotEnabled`；
- 物理安全 OFF 仍可覆盖同组全部硬件成员，但运行状态不能污染禁用通道；
- UI 再做一次防御性归一，任何迟到 Recovering、Paused、AlarmStopped 事件遇到禁用记录都显示 NotEnabled；
- NotEnabled 持久化为 `EpbTestStatus.NotStarted`，不会再把 EPB6 写成 Paused。

### 2.5 打破 DAQ 与压力恢复的循环依赖

涉及文件：

- `Controller/HydraulicGroupCoordinator.cs`

实施内容：

- `HydraulicReleaseTimeoutException` 增加结构化压力证据属性，并明确识别 ReaderUnavailable、ReadFailed、NoSample、Invalid、Stale；
- 正常停止和正常代次释放仍严格要求新鲜低压证据，安全条件没有放宽；
- 仅在协调器/DAQ 重建路径中，若 DO/AO 已完成去能量化但压力不可观测，则执行有界机械稳定等待并继续重建协调器 epoch/Gate；
- 重建只恢复“获得新鲜证据的能力”，后续重新加入仍必须通过新 generation 的新鲜压力资格；
- 新鲜压力仍高于安全阈值时不会使用该例外，继续按真实液压释放故障处理。

这样不再出现“必须先用故障 Dev1 的新鲜压力证明安全，才允许重建 Dev1”的循环等待。

### 2.6 既有 V2.11.0.17 整改继续保留

以下能力作为 `2.12.0.0` 基础继续保留：

- 峰值证据按 LogicalCutoffUtc 同窗比较，排空墙钟时间不计入样本尾差；
- 液压租约作用域 Complete/Abort 和旧 epoch 隔离；
- StopAll 的软件逻辑清场快照与 `CanRestartInProcess`；
- 软件恢复三次无进展熔断和无人值守整批恢复出口；
- DAQ 恢复硬期限、恢复所有权和迟到旧代清理隔离。

## 5. 现场验收边界

自动化和 Release 构建已经完成代码级闭环，但 NI、液压、电源和磁盘组合时序必须继续按原方案做真实台架验收，不能把本地测试写成现场已验证：

- [ ] 至少 30 轮六通道“运行—报警注入—自恢复—暂停—停止—同进程启动”；
- [ ] EPB6 保持 Enabled=false，组级故障全过程始终显示未启用且 RunCount=0；
- [ ] 注入日志盘 200 ms、1 s 和 30 s 卡顿，确认 DO/DAQ 控制期限不受影响；
- [ ] 在 EPB8 学习圈注入可恢复报警，确认 EPB8 不在批次 Formal 提交前创建 Timer；
- [ ] 强制制造旧 Timer 回调，确认 StartBlocked 后任何 Forward/Reverse 命令均被拒绝；
- [ ] 注入 Dev1 `-200279` 和压力样本失新，确认先去能量化、重建后取得新鲜压力再重入；
- [ ] 六通道连续 8 小时运行，无 `-200279`、无控制队列持续增长、无终态与资源快照不一致。

现场包应重点检索：

```text
LateHardwareSuccess
DisabledChannelInvariant
FormalRejoinRejected
TerminalCleanupUnverified
ChannelExecutionPermitMissing
FormalCommitted=
TimerActive / RunnerActive / Energized
```

任一 `TerminalCleanupUnverified` 或非运行终态仍出现 `TimerActive=True / Energized=True`，均不得放行。

## 6. 结论

`2.12.0.0` 已在代码层把本次反复出现的问题收敛到统一机制：日志不能阻塞实时控制、启动期恢复不能争抢 Formal 所有权、非运行终态不能与活动执行资源并存、禁用通道不能接收业务运行态、故障 DAQ 不能成为自身重建的循环前置条件。

版本可进入真实台架候选验收；完成第 5 节现场清单后，才能标记为正式现场发布。
