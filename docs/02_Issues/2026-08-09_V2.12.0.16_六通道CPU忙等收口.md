# V2.12.0.16 六通道 CPU 忙等收口

## 结论

正式自适应控制已经由 2 kHz DAQ 快速样本事件驱动，控制等待线程挂起在 `TaskCompletionSource`，并不是长期 CPU 轮询。但完成性审计发现，学习和兼容路径仍有五处采样节拍代码采用“先 `Task.Delay(周期-1ms)`，再忙等到精确截止”的旧实现。每个通道每个采样周期可能主动占用最后约 1—2 ms；六通道并发学习、重新学习或恢复资格时会把这一小段放大为明显 CPU 占用，并与 UI、日志和设备恢复争抢调度时间。

V2.12.0.16 现在统一使用 `DelayUntilMonotonicAsync`：粗粒度区间由可取消的 `Task.Delay` 挂起，仅在距离单调截止不超过 0.2 ms 时允许短暂 `SpinWait`。正式控制的事件驱动安全判定、2 kHz 峰值捕获、Raw 持久化和 DO 高优先级链均未降频或改为轮询。

## 修改范围

| 路径 | 修改前 | 修改后 |
|---|---|---|
| 遗留学习反向衰减 | 每周期末约 1 ms 忙等 | 协作等待，最多 0.2 ms 精对齐 |
| 当前对齐学习反向衰减 | 每周期末约 1 ms 忙等 | 同一单调截止帮助器 |
| 旧斜率判定兼容路径 | 主动自旋对齐 | 同一单调截止帮助器 |
| 空行程离开兼容路径 | 主动自旋对齐 | 同一单调截止帮助器 |
| 六通道同时学习/恢复资格 | 忙等按通道叠加 | 大部分时间不占用线程 |

`ControlBatchRing` 中短暂的 CAS/发布可见性重试没有改动，它属于有界无锁临界区，不是按毫秒持续轮询。启动定位的保持观察已经使用 `Task.Delay(_sampleMs)`；正式自适应正向/反向判定继续使用快速样本事件。

## 自动反例

新增“六通道学习节拍协作等待不再整毫秒自旋”测试：

1. 六个并发通道各执行 120 个 3 ms 单调节拍。
2. 每次返回值必须达到或越过指定 `Stopwatch` 截止，不允许为了降 CPU 提前返回。
3. 整段进程 CPU 时间必须小于墙钟时间的 1.25 倍；旧的每通道忙等设计在多核机器上会随通道数叠加。
4. 已取消的等待必须立即抛出 `OperationCanceledException`。

本轮结果：控制/恢复综合测试 `309/309`、写盘 `28/28`、现场门禁 `17/17`、电源 `17/17`、Release `0 error`。

## 现场判定边界

截图中的任务管理器本身占用约 45.6% CPU，因此单张截图不能分离软件与任务管理器的贡献。真实台架仍必须在不打开高刷新任务管理器、不运行压缩/同步/全盘扫描的条件下，从程序每秒 HOST 指标验证：

- 正式稳定阶段进程 CPU 不持续增长或长时间占满单核以上；
- 学习、整批重建和恢复资格阶段不出现与通道数近似线性增长的持续 CPU；
- UI P95 `<200 ms`；DAQ callback 最大空窗 `<100 ms`；控制 subscriber P99 `<5 ms`、最大 `<20 ms`；
- 同时核对工作集、句柄数、线程数、磁盘队列和外部进程 CPU。

这些指标必须由 2/8/24/72 小时封存数据证明，不能由本地微基准替代。总体验收状态见[上线要求完成性追踪矩阵](./2026-08-09_V2.12.0.16_上线要求完成性追踪矩阵.md)。
