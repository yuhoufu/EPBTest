## 2. 已确认的问题与修订

| 项目 | 证据及修改 | 实际边界 |
| --- | --- | --- |
| R1 组内收尾误伤 | `CommitRecoveryIncidentStateForRelease` 原来对一个未重入通道调用整组安全终态。现场 EPB4 尚在 Recovering 时把已重入 EPB5 清掉。本轮改为单成员终态；新 Run/Epoch 或其他恢复所有者的状态不由旧 finally 改写 | EPB4 未重入仍须恢复或升级；不能把 EPB5 保住等同全部恢复 |
| R2 重启义务丢失 | 停止生产结果继承 `RequiresProcessRestart` 锁存；事务执行器最终投影保留该标志。物理安全成立但仍需替换进程时输出 `SafeButRestartRequired` 和接管义务 | 人工停止仍否决续测；不能用物理安全作为恢复授权 |
| R3 失败证据不足 | 正式圈安全边界日志增加 Closure disposition、Durable、Attempt、Run/Epoch、持久化版本及退场执行许可；退场等待最后一次 await 后重新核对参与者身份 | 不再仅凭 MotorOff/Pressure/Persistence 三项判断全部边界；未放宽门限 |
| R4～R6 | 保留 V4 的 busy 准入失败释放、IPC 总截止、恢复计数发布顺序和 SafetyOnly 不携带续测许可的实现，并重跑专项 | 旧版本已通过的数字不当作本轮通过结果 |
| R8 子窗释放 | 子窗已 Dispose 时不再等待不会到来的 FormClosed 事件；关闭调用后复核 Dispose 状态 | 这是可确定的漏事件边界修订，不能据此断言已解释现场全部 ChildWindowReleaseTimeout |

R7 的约 1.16 秒采样空窗首发来源仍未确定。现有证据不足以把它归因于某个驱动、GC 或硬盘，也不足以宣称根治。保留采样安全阈值和原控制策略；仍需用台架的 DAQ、调度及存储时序记录定位。

## 3. 独立数据库观察

`MTTFTest.FallbackGuard.exe` 不引用 Controller、不访问硬件，不在采集线程执行查询。它每 5 秒启动一个短命 x86 读取进程；读取进程总预算 2 秒、私有内存上限 256 MiB，结果上限 64 KiB。父观察器保留 128 MiB 上限。超限只结束本次创建的读取进程并确认退出。

连接使用 `ReadOnly=True;FailIfMissing=True;Pooling=False`，设置 `query_only=ON`、`busy_timeout=500`；不改变 journal_mode，不 checkpoint、不迁移、不复制运行中的 DB/WAL 文件拼装快照。每个应运行通道读取最新三条 `status='completed'` 且正圈号的记录。读取支持原 running 行更新为 completed，不能只观察最大 rowid。

数据库写入者仍是主程序。WAL 并发读写回归验证：未提交修改对读者不可见，提交后可见，关闭读连接后写者继续提交。锁等待或读超时记为 Unknown，不是停滞，也不会单独触发重启。

正式期停滞阈值为 `max(90 秒, 6×试验周期)`，达到阈值后要求三次成功且仍未推进的读取。按通道分别计时，其他通道仍有数据不能掩盖单路停测。机器墙钟不参与停滞计时，使用 Stopwatch。数据库路径或创建身份变化、计数倒退均拒绝作为正常推进。

### 身份和人工停止

首次绑定需要原执行链已准入的正式批次，以确定应运行通道、RunId、RunEpoch 和周期；绑定结果落为 `fallback-database-intent-<session>.json`。**绑定以后**即使原快照消失、心跳不更新或 RunActive 被清空，数据库观察仍独立持续。

本实现不是从任意陌生数据库自动推断“用户允许启动”。尚未进入正式批次且没有已绑定意图的启动/学习失败，仍由原恢复链负责；不能声称已覆盖独立启动阶段兜底。

人工停止被保存在账本和数据库观察意图中；原执行端再次核验人工停止、会话撤销和安全阻塞。新人工开始必须由原执行端绑定新批次并递增 fencing 代次；旧请求、旧停止凭证不能关闭或拉起新批次。完成或人工禁用通道从应运行集合剔除，不因故障状态就静默剔除未完成通道。

## 4. 受控重启与恢复判定

数据库确认停滞后保存 `fallback-last-database-request-<session>.json`，其中有各通道正式圈证据和批次身份，再经有总截止的控制管道请求接管。原端允许使用仍绑定当前进程身份的 `LastVerifiedActiveRun` 处理 RunId 已清空的故障全停。

本轮新增：原端收到数据库停滞请求后，在没有原恢复占用时进入既有 `BeginTakeover` 安全接管入口，主程序仍活着并不阻止发起受控替换。请求可重试，已准备的启动仍通过原持久许可、Supervisor、SessionAgent、旧 PID 退出证明与安全门禁执行。没有另加一条无许可 Process.Start 主程序的通路。

数据库验证以替换进程绑定后的新基线为准，所有应运行通道分别取得至少三条不同的有效 completed 记录，再观察至少两个周期；圈号跳过三格不等于三次有效提交。还需原动作证据验证器确认新进程、新批次的动作序列、机械计数和正式提交。只有二者都满足才记录 `DatabaseAndActionRecoveryVerified`。进程存活、管道应答、请求接受或启动握手都不是该结果。

### 必须明确的覆盖限制

- 观察独立于主程序；安全执行仍使用原安全链。原 Watchdog/Supervisor 本身永久阻塞、设备无法确认断能、OS 卡死或硬件永久故障时，本候选不会强杀后无许可启动。
- 原恢复持续 busy 时本候选持续观察并重试请求；尚未增加独立安全执行器对原恢复的强制抢占。方案中的“180 秒总预算后独立接管”尚未完整实现。
- 三条数据库记录和动作计数不是独立物理传感器测量，也没有逐条核验历史波形文件完整性。真实动作和波形完整性仍须台架确认。
- 本候选不能据此宣布已满足“任意部分/全停都无人自动恢复”总目标。启用主动模式前须完成对应台架注入。

## 5. SQLite 耐久性核查

V4 写连接仍为 WAL、`Synchronous=Normal`；本轮没有为了降低延迟改变该设置。仓库 2026-08-09 的存储设计文档已经记录 NORMAL，因此不能简单写成“本轮 V4 新引入”。它与其他工作树 Full 设置的差异仍需要按完整来源审计。

成功查询代表事务对读者可见，不是突然断电后的持久保证。已有写盘回归覆盖中断圈隔离、终态原子性、失败重试和重启指针；本轮没有做真实断电试验，不声称断电窗口零丢失。停机与恢复不重置计数、不自动补做不确定圈。

## 6. 使用及交付结构

一键目录保留 Base、安装/修复/卸载脚本、采证和 RecoveryGuard 验收入口。FallbackGuard 子目录增加 `System.Data.SQLite.dll` 和 `x86/SQLite.Interop.dll`，与主包一同进入哈希清单。候选默认观察模式。

独立入口 `Tools/Manage-FallbackGuard.ps1` 的 `ProjectDirectory` 是该项目的 **WatchdogSessions 目录**，SessionId 必须取该项目当前会话，不可猜测。支持 Install、Enable、Disable、Status、Run、Uninstall；`-BenchActive` 才启用主动请求。任务计划维持外部观察程序，不直接启动卡钳。登录条件沿用现有 Interactive 任务设计。

状态文件含 `DatabaseObserving`、`DatabaseStalled`、`DatabaseUnreadable`、`DatabaseManualStopped` 或验证结果。检查状态时同时检查数据是否推进，不能只看任务正在运行。

另保留既有自动绑定监控脚本，并增加“启用/禁用/查询/卸载独立数据库监督.cmd”。它们按主程序保存的项目配置和当前会话绑定，支持先独立开启、等待主程序就绪；**点击启用入口即选择主动请求模式**，普通主包安装不自动启用。非默认安装目录须传 `-InstallRoot`，脚本不能借猜测目录控制其他安装实例。

包装使用 `.7z`、LZMA2、`-mx=9`，保留原包，禁止覆盖同名候选。解压、SHA-256 和 RecoveryGuard 包检查不等于实物恢复验收。
