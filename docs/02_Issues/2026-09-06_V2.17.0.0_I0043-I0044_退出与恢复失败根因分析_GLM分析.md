# V2.17.0.0 I0043 / I0044 两次完全退出与恢复失败根因分析（GLM 分析）

日期：2026-09-06
分析对象：10243-028 台架，V2.17.0.0 候选构建（提交 `7170e902d77c8fdbf5cfeaebe6aa98b86235fc26`）
本文为独立复核分析：所有代码结论与日志结论均由 GLM 直接对源码、封盘日志和 sidecar 耐久事件逐条验证，并在第 7 节给出比此前分析更进一步的 V2.14.2.11 对照证据。

## 1. 结论先行

两次运行"完全退出、没有恢复回来"不是同一条故障链，但**最后都卡死在同一个确定性协议错误上**：

1. **I0043（第一次，09:09:49 启动，PID 18056）**：DAQ 采集启动仅约 11 秒后，Dev1 的有界原始读取分发队列（容量 64 批）溢出，触发 DAQ 恢复；恢复过程中又叠加 CTS 重复释放、活动学习圈残留（ActiveCycles=5）和持久化状态未收敛，同进程清场失败，升级到 Watchdog 接管。Watchdog 按设计终止旧进程、安全动作全部完成，但补建的关闭墓碑因 schema 版本错误被拒绝，替代进程始终为 PID 0。
2. **I0044（第二次，09:13:03 启动，PID 22976）**：正式阶段六通道首批回调分散约 596 ms，超过 300 ms 准入窗，EPB4/5/7 被连续排除、60 秒无实际动作，触发整批恢复。**同进程恢复实际上已经成功**（10 圈学习重学、manifest 发布 Successful、新正式运行建立），却在恢复完成的同一拍被空字符串竞态误判为"到达外部边界"，升级接管。随后关闭墓碑写入失败，主程序等满 30 秒硬期限强制退出；写失败又产生 `.revoked` 标记，把唯一能拉起替代进程的 Watchdog sidecar 也终止了。

对用户三个问题的直接回答：

| 问题 | 回答 |
|---|---|
| 两次的根因是什么？ | 触发根因不同（I0043 是 DAQ 分发队列溢出 + 同进程清场失败；I0044 是准入窗饿死 + 成功恢复被误升级），但共用同一个"不能恢复"的根因：关闭墓碑 schema 7 / 仅接受 1—6 的确定性不兼容。 |
| 为何不能恢复？ | 只要走到跨进程接管，就必须建立合法关闭墓碑才能拉起替代进程；V2.17 生产者写 schema 7、校验器只接受 1—6，墓碑永远无效，重启前置条件永远 `MissingOrCorrupt`。这是代码确定性错误，不是概率问题。 |
| 为何比 2.14.2.11 更容易出现完全退出？ | 三层叠加：(a) V2.17 新增/收紧了三类监督入口，把更多事件更快送进恢复链；(b) V2.14 的恢复阻断是"90 秒启动预算超时"这种概率性失败，sidecar 存活并无限重试、偶有成功；V2.17 的阻断是确定性失败，重试永远不可能成功；(c) V2.17 新引入"墓碑写失败 → `.revoked` → sidecar 终止"的语义，把最后的恢复者也杀掉了，而 V2.14 从不这样杀 sidecar。 |

> 置信度说明：schema 不兼容、I0044 空字符串竞态、I0044 强制退出、I0043 同进程清场失败、I0043/I0044 退出方式均为代码 + 日志四方闭环，高置信。I0043 高 CPU 窗口的具体外部进程无法归因（证据导出因 SizeBudget 未包含全局 supervisor-audit.log，且无逐进程快照），只能确认"分发队列未被及时消费"这一直接事实。

## 5. 为何不能恢复：两条确定性协议错误的闭环

### 5.1 关闭墓碑 schema 7 / 仅接受 1—6（两次共同的最终根因）

代码四方闭环，全部本仓库直接核验：

1. 生产者：[SupervisorProtocol.cs:38](D:/Github/wanxiang/EPBTest/Watchdog.Protocol/SupervisorProtocol.cs:38) `SchemaVersion = 7`；主程序关闭路径（[WatchdogRuntime.cs:3508](D:/Github/wanxiang/EPBTest/MTTfTest/WatchdogRuntime.cs:3508)）与 Watchdog 崩溃恢复路径（[WatchdogHost.cs:3951](D:/Github/wanxiang/EPBTest/MTTFTest.Watchdog/WatchdogHost.cs:3951)）都把该值写入墓碑。
2. 消费者：[WatchdogClosingTombstone.cs `IsValidFor`](D:/Github/wanxiang/EPBTest/Watchdog.Protocol/WatchdogClosingTombstone.cs:83) 仍只接受 schema 1—6。
3. 执行：`WriteThrough` 写前校验失败即抛 `Watchdog closing tombstone identity is incomplete.`——I0044 `warning.log:247` 与 I0043 sidecar `MissingOrCorrupt` 的 Detail 逐字一致。
4. 历史：Git 确认 `cdf95f3`（V2.16）把墓碑校验上限升到 6，`fffbbe6`（V2.17）把 `SupervisorProtocol` 升到 7 但未同步墓碑校验——两次协议演进没有一起更新。

后果：V2.17 当前构建中，**任何**走到"需要关闭墓碑"的路径（正常接管退出、Watchdog 补建崩溃墓碑）都确定失败。没有合法墓碑，重启前置条件永远 `MissingOrCorrupt`，安全策略正确地拒绝拉起替代进程——这是 fail-closed 设计在正确地拒绝一个无效证据，问题出在证据本身永远无效。

### 5.2 墓碑写失败误杀唯一恢复者（I0044 特有，第二次更彻底的原因）

主程序捕获墓碑持久化失败后写旧式 `.revoked` 标记（[WatchdogRuntime.cs:3555](D:/Github/wanxiang/EPBTest/MTTfTest/WatchdogRuntime.cs:3555)），Watchdog 将其解释为 `LegacyRevocationMarker` 并把会话转成 `SessionRevoked`（[WatchdogHost.cs:2457](D:/Github/wanxiang/EPBTest/MTTFTest.Watchdog/WatchdogHost.cs:2457)）。I0044 的 `.revoked` 内容确为 `ClosingTombstoneWriteFailed`。

这在人工撤销场景合理，但在接管重启场景构成**语义错误：墓碑写失败 ≠ 用户撤销恢复**。结果是旧进程已退出、sidecar 已终止、批准的替代进程仍是 PID 0——连"无限重试"的机会都没有了。I0043 没有走到这条路径（旧进程由 Watchdog 主动终止，sidecar 存活重试），但 schema 错误使重试同样永远不可能成功。

## 7. 为何比 V2.14.2.11 更容易出现完全退出（含本次新增对照证据）

### 7.1 触发频率：V2.17 的监督入口更多、更敏感

依据[配置差异核对](D:/Github/wanxiang/EPBTest/docs/02_Issues/2026-09-06_V2.17.0.0与V2.14.2.11_配置参数差异核对.md)与本仓库代码：

| 层次 | V2.14.2.11 | V2.17.0.0 | 效果 |
|---|---|---|---|
| DAQ 入口 | 无独立有界分发路径 | `DaqReadDispatcher` 容量 64，满即 `DaqReadDispatchOverflow` | 0.6 秒级调度停顿即可转换成 DAQ 恢复事件（I0043 命中） |
| DAQ 存活监督 | Warn/Suspect/Trip = 250/1500/5000 ms，Trip 连续 3 次 | 75/100/250 ms，Trip 1 次，取 Callback/Sample/ControlEnqueue/ControlProcessed 最大年龄 | 更早进入保护/恢复 |
| 执行进展监督 | 无 | max(60s, 3×周期) 无实际动作期限 | I0044 这类"Timer 在但不动作"被主动升级 |

前两层方向并非错误（更早发现真实停顿）；问题是它们把更多事件送进了第 7.2 节所述"最后一层确定失败"的恢复链。

### 7.2 恢复终局：V2.14 的失败是概率性的，V2.17 的失败是确定性的（本次扫描新增证据）

对 V2.14.2.11 全部 12 次封盘（I0023—I0042）的 sidecar 耐久事件统计：

| 指标 | V2.14.2.11（12 次封盘） | V2.17.0.0（2 次封盘） |
|---|---|---|
| `RecoverySafetyPrerequisiteBlocked` 总数 | 1,308 | 14 |
| 阻断结局分布 | **100% `Outcome=TimedOut`**（90 秒启动预算超时），0 次 `MissingOrCorrupt` | 100% `Outcome=MissingOrCorrupt`（墓碑 schema 无效） |
| sidecar 是否被 `.revoked` 终止 | 从未因恢复失败终止；`.revoked` 内容均为 `SupersededByNewSession:...`（新会话正常顶替旧会话的良性轮替） | I0044 被 `ClosingTombstoneWriteFailed` 终止 |
| 真实替代进程 PID > 0 | 至少 I0027（PID 21744）、I0040（PID 21664/21708/2820）——**重试偶尔成功** | 0 次 |
| V2.14 关闭协议一致性 | I0040 `closing.json` 为 `SchemaVersion=5 / State=Terminal`，生产者与消费者一致 | schema 7 vs 1—6，确定不一致 |

这组对照改变了归因的精度：

- 用户观察"2.14.2.11 也会出现最终软件退出不能恢复，只是没那么频繁"**得到证据支持，且机制清楚**：V2.14 的接管链同样会卡（1,308 次阻断），但卡点是"替代进程 90 秒内没起来"这种概率性超时；sidecar 存活并无限退避重试（伴随 `SafetyHandoffWorkerFailed` 27,255 次、`TerminalSessionObservedOnStartup` 22,562 次的海量重试记录），有时最终能把进程拉起来（I0027、I0040）。
- V2.17 把这条链改成了**数学上不可能成功**：墓碑永远无效 → 前置条件永远 `MissingOrCorrupt` → 重试无意义；且 I0044 证明新语义还会把 sidecar 直接杀掉。所以 V2.17 不是"失败概率更高的同类失败"，而是"失败性质从概率性变成了确定性"。
- 结论：**V2.17 更容易完全退出 = 触发入口更多（7.1）× 终局确定失败（5.1）× 恢复者可被误杀（5.2）**。三者缺一都不会呈现"两次运行两次完全退出"的现象。

### 7.3 不应归咎于 V2.17 新增的部分

- 300 ms 准入窗语义在两版本间无代码差异；V2.17 新增的是能识别其饿死后果的监督。
- 空字符串竞态在 V2.14 参考代码中同样存在，是潜伏缺陷，本次因"恢复恰好在 500 ms 轮询间隔内完成"被命中。
- CTS `ObjectDisposedException` 在 V2.14 的 I0040 已出现（既有证据摘录），非 2.17 首次引入，说明清场所有权修复一直不完整。

样本量限制：本轮 V2.17 为 2 次运行、2 次完全退出，不能统计外推失效率；但 schema 错误是代码确定性的，"走到接管即失败"不依赖概率。

## 8. 修复优先级

### P0 —— 先恢复"退出后一定能回来"

1. **统一关闭墓碑 schema**：生产者、`IsValidFor` 校验、读取、Supervisor/SafetyAgent/sidecar 兼容策略使用同一权威版本常量；补 schema 7 往返测试。不是简单把 6 改 7，而是消除"两处常量各自演进"的结构。
2. **区分墓碑写失败与会话撤销**：接管恢复中写墓碑失败必须 fail-closed，但不得写 `LegacyRevocationMarker`；sidecar 应保留恢复所有权并重试/补证，或进入明确的人工介入终态。
3. **修复空字符串三态**：`boundaryReason == null` 改为 `string.IsNullOrWhiteSpace(boundaryReason)`（或改用可空枚举），并补"任务恰好在 500 ms 轮询间隔完成"的竞态回归测试。

### P1 —— 降低触发与同进程清场失败

4. 正式槽参与者在批次开始时显式声明，替代"首个回调后 300 ms 机会式收集"；保证计划通道不会永久 `AdmissionWindowClosed`。
5. 修正 CTS 所有权（唯一所有者执行 Cancel/Dispose）与 `ActiveCycles` 幂等清理；补并发回归测试。
6. 为 64 批分发队列增加可归因性（高水位、最老批次年龄、消费者阶段耗时），避免只靠扩容掩盖消费者阻塞；持久化终态与队列排空应一致收敛（I0043 的 `State=Failed/Closed=False`）。

### 必须通过的验证矩阵（摘要）

| 编号 | 场景 | 通过标准 |
|---|---|---|
| V1 | schema 7 写墓碑 | `WriteThrough` 成功、读回完整、达到 Terminal |
| V2 | Watchdog 补建崩溃墓碑 | 替代 PID > 0 且 Attached/Committed |
| V3 | 墓碑首次写失败注入 | sidecar 存活重试，不产生 `SessionRevoked` |
| V4 | 恢复在 500 ms 轮询窗口内完成 | 无空 `Boundary`、不撤销新运行 |
| V5 | 六通道首回调错开 700 ms | 计划通道不永久被排除 |
| V6 | 1—5 秒调度停顿注入 | DAQ 安全暂停恢复，不丢整个应用 |
| V7 | 学习取消/DAQ 重建/StopAll 并发 | 无 `ObjectDisposedException`、`ActiveCycles=0` |
| V8 | 现场完整接管演练 | 退出→安全→墓碑→拉起→提交→续跑六步均有耐久证据 |

P0 的 V1—V4 未全部通过前，不建议用长时间耐久运行验证；当前问题不是低概率压力缺陷，而是进入跨进程恢复后确定失败的协议错误。

## 9. 最终判定

1. **I0043 根因**：DAQ 有界分发队列在系统高负载窗口溢出（直接根因），叠加 CTS 重复释放、ActiveCycles 残留、持久化状态未收敛（同进程清场失败的根因），升级接管后关闭墓碑 schema 7/6 不兼容使替代进程永远无法启动（不能恢复的根因）。
2. **I0044 根因**：300 ms 准入窗饿死后到通道（触发根因），60 秒无动作监督触发恢复；恢复实际成功后，空字符串三态竞态把它误升级为外部接管（不应升级的根因）；墓碑写失败 → 30 秒强制退出 → `.revoked` 终止 sidecar（不能恢复且连重试都没有的根因）。
3. **两版本差异的本质**：V2.14 的"退出不能恢复"是概率性的（启动预算超时 + sidecar 无限重试、偶有成功）；V2.17 把触发入口增多、把终局改成确定性失败、还新增了误杀恢复者的语义。因此 2.17 呈现"更容易、且更彻底"的完全退出。
4. **第一优先级是协议闭环，不是调阈值。** 在 V1—V4 通过前，任何触发路径（DAQ、液压、执行无进展）走到跨进程接管都会复现完全退出。
