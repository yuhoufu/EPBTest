# 10358-029 V2.13.0.4 全卡钳停机不自恢复与人工停止卡死分析

## 1. 结论先行

本次不是“所有卡钳同时发生硬件故障”，也不是数据写盘堵塞导致整个进程失去响应。完整证据链为：

1. 2026-08-14 12:44:55，`Dev2` 在带电期间出现一次超过 100 ms 的 DAQ 回调空窗，独立存活监督立即触发 `DaqCallbackStale`。
2. `Dev2` 局部软件恢复连续三次未能确认电源组 3、4 已断电，恢复熔断后升级为“整批安全重建”。
3. 整批恢复按设计调用 `StopAll`，因此健康的 `Dev1` 卡钳 4、5 也被主动暂停、撤权和断能；这就是现场看到“所有卡钳彻底停机”的直接原因。
4. 物理 OFF 已经发出且各卡钳最终停止，但本次 `StopAll` 没有走到逻辑清场完成。它停在安全前导流程内，留下 `RunId` 已清空、通道仍为 `Paused`、Timer/Runner/DAQ Recovery 等对象仍残留的半终态。
5. 主进程心跳和 DAQ/电源遥测仍在继续，所以独立看门狗认为进程存活；同时心跳把 `RecoveryActive` 报成 `false`，现有接管策略又不检查“无活动 RunId + 有可恢复通道 + 有逻辑残留”，因此没有再次杀进程并拉起。
6. 12:50:36 操作员点击“停止试验”后，界面等待 `_epb.StopAllAsync(...)`。`StopAllAsync` 发现已有未完成的 `_stopSafetyTask`，直接返回同一个任务，人工停止因此永久等待在之前已卡住的系统故障停止流程上。
7. 更严重的是，人工停止消息一送达，看门狗立即永久撤销本 Session 的 Kill/重启资格并退出。于是操作员点击“停止”不仅没有打断旧任务，还主动关闭了最后的跨进程逃生通道；只能手工杀死进程。

**根本问题不是单一硬件故障，而是“过于敏感的 DAQ 存活触发 + 无总时限的 StopAll + 看门狗状态判定盲区 + 人工停止复用旧任务并提前撤销看门狗权限”的组合失效。**

## 4. 三个现场现象的直接解释

### 4.1 为什么所有卡钳都停了

最初只检测到 `Dev2` 的 DAQ 存活异常，影响卡钳为 9、10、11。局部恢复三次无法确认电源组 3、4 已断电后，恢复策略主动升级为一次整批安全重建。

整批重建调用 `StopAll`，会撤销整个批次、暂停所有 Timer、取消所有 Runner，并向所有活动通道发出高优先级 OFF。因此 EPB4、5 虽然没有 DAQ 故障，也会被安全停机。

结论：**“全部停止”是恢复策略的预期安全动作；异常之处在于停止后没有完成清场和重启。**

### 4.2 为什么等待后没有自恢复

V2.13.0.4 的 Watchdog 主要在以下情况接管：

- 主进程退出；
- 心跳超过 5 秒；
- `RecoveryActive=true` 且恢复阶段长时间无进度；
- `OrphanPaused=true`；
- `PowerDisablePending=true`。

本次主进程心跳正常，`OrphanPaused=false`、`PowerDisablePending=false`；心跳构造又把恢复活动状态取自通道恢复证据，通道进入普通 `Paused` 半终态后报告成了 `RecoveryActive=false`。即使同一心跳明确包含 `DaqRecoveryCount=1` 和大量逻辑残留，接管策略也没有使用这些字段。

因此形成盲区：

```text
RunId 已清空 + RunActive=false
        +
可恢复通道仍存在 + Timer/Runner/Recovery 对象仍存在
        +
主进程心跳正常 + RecoveryActive 误报为 false
        =
Watchdog 永远不接管，主程序也永远无法完成同进程恢复
```

### 4.3 为什么点击“停止试验”后一直卡顿

`FrmEpbMainMonitor.BtnStop_Click` 在禁用“停止”和“开始”按钮后，直接等待：

```csharp
await _epb.StopAllAsync(...)
```

而 `EpbManager.StopAllAsync` 的幂等实现是：只要 `_stopSafetyTask` 存在且未完成，就把这个旧任务原样返回。人工停止没有新的超时、没有独立的物理 OFF 通道，也不能隔离或替换已经卡住的系统故障任务。

所以人工点击实际发生的是：

```text
人工停止
  → StopAllAsync
  → 命中 12:45:08 已开始但未完成的 _stopSafetyTask
  → await 永久不返回
  → finally 不执行
  → 停止、开始按钮一直保持禁用/等待状态
```

与此同时，`WatchdogHost` 收到 `ManualStopRequested` 后立即设置永久撤权并 `_stop.Cancel()`。代码注释明确要求看门狗不再等待 `StopAll`，永久放弃 Kill/重启资格。这一策略假设主程序的幂等 `StopAll` 必然能自行结束，但本次事故恰好证明该假设不成立。

## 5. 代码级根因

### 5.1 起始触发过于敏感：单次 100 ms 空窗即可 Trip

V2.13.0.4：

- `MTTfTest/App.config`：`DaqLivenessWatchdogIntervalMs=20`、`DaqLivenessStaleThresholdMs=100`；
- `Controller/EpbManager.DaqLiveness.cs::EvaluateDaqLiveness`：只要带电设备出现一次超过阈值的 gap，或者当前 CallbackAge 超过阈值，就立即返回 Trip；
- 没有连续次数、持续时间、回调序列是否已经恢复、双设备是否同步停顿等消抖判据。

本次 12:44:55.237 触发后约 0.34 秒，Dev2 已重新出现新鲜回调。后续日志到 12:52 仍持续产生 DAQ 指标，证明不是 DAQ 永久消失。100 ms 可以作为告警/观察阈值，但直接驱动设备重建和整批停机过于激进。

### 5.2 `StopAll` 是可无限等待、且全局复用的单例任务

V2.13.0.4 `Controller/EpbManager.cs::StopAllAsync`：

- `_stopSafetyTask` 未完成时，后续所有停止请求直接返回同一任务；
- 没有总时限；
- 没有阶段进度超时；
- 没有“只重新提交物理 OFF”的独立应急路径；
- 没有把已卡死的旧逻辑任务隔离为不可再复用的 Faulted/Stalled owner。

`RunStopSafetyAsync` 在输出首个“收到停止全部 EPB 请求”标记前，会同步执行撤权、暂停 Timer、取消/移除运行对象、提交全部 OFF、启动电源 Disable 等动作。本次 OFF 已经成功提交，但首个后置标记没有出现，证明停止流程停在这段前导流程中。

**当前证据只能把卡点限定在“已开始全通道暂停/断能、尚未发布 StopAll 后置标记”的边界内。** V2.13.0.4 没有每个子步骤的 Enter/Exit 日志，也没有卡住时的线程转储，所以不能严谨地断言是某一把锁或某一个具体 API。

高风险候选包括：

- Timer/Runner 移除过程中同步触发的观察者或清理逻辑；
- 电源 `DisableAllAsync` 启动阶段及组级操作串行门；
- `PowerSupplyCoordinator.DisableGroupCoreAsync` 中 `Gate.WaitAsync(CancellationToken.None)`、监控停止和网络读写；
- Stop 前导流程内的任何同步日志/状态观察者。

这些候选都需要统一加阶段时限和转储证据，而不应只猜测并修改某一处。

### 5.3 同进程恢复没有外层硬截止

`UnattendedRecoveryCoordinator.RecoverInProcessOrRestartAsync` 无期限等待：

```csharp
await manager.PrepareForFreshRestartAsync(..., CancellationToken.None)
```

`PrepareForFreshRestartAsync` 又无期限等待 `StopAllAsync` 和批次生命周期屏障。只有 await 抛出异常后，catch 才会升级到进程重启；本次 await 永不返回，所以升级逻辑永远到不了。

### 5.4 Watchdog 只监督“进程是否活着”和部分恢复标志，没有监督停止事务

心跳已经包含 `DaqRecoveryCount`、逻辑对象计数和 `RunActive`，但接管决策没有建立以下不变量：

```text
若 RunActive=false / RunId 为空，
则经过短暂收尾窗口后 Timer、Runner、StopCts、Recovery owner 必须全部归零。
```

此外，Watchdog 没有权威的 `StopAllActive`、`StopStage`、`StopStartedUtc`、`StopProgressVersion`，无法判断停止流程是否卡在某一步。

### 5.5 人工停止过早撤销独立看门狗权限

当前协议把“操作员点击停止”直接解释为“Watchdog 永久放弃 Kill/重启权并退出”。但“停止意图已产生”不等于“主进程已安全且已逻辑终止”。

正确语义应是：

- 人工停止后禁止自动续测/自动重新上电；
- 但 Watchdog 仍应保留在超时后终止卡死进程的权限；
- 只有收到 `StopCompleted` 或确认主进程退出后，才结束 Session。

## 6. 排除项与证据边界

### 6.1 已排除

- **不是磁盘写队列堵塞。** 故障前两路队列均为空，`Persisted` 与 `Accepted` 基本追平；Dev2 后续差值来自恢复窗口的 `Suppressed`，不是排队积压。
- **不是整个进程失去调度。** 12:45 后主进程仍持续发送心跳、记录 HOST/AI 指标和电源遥测。
- **不是五个卡钳同时发生硬件报警。** 初始 Trip 只涉及 Dev2；Dev1 是由整批安全策略主动停止。
- **不是 Watchdog 重启次数达到上限。** 当前实现对后续重试延长退避时间，但不会因第 3 次之后永久禁用接管。

### 6.2 尚不能确定

- `StopAll` 前导流程究竟卡在 Timer/Runner 清理、电源操作启动还是其他同步回调；缺少分阶段日志和进程转储。
- Dev2 回调空窗的底层来源是 NI 驱动、系统调度/GC、USB/PCIe 总线还是应用侧短时占用；日志能证明它是瞬态，但不足以锁定最底层原因。
- 电源组 3、4 的“仍带电”是设备真实输出未关闭、遥测陈旧、通信操作门被占用还是回读超时；必须结合下一版的命令/回读分阶段证据确认。

因此整改必须先保证任何底层异常都不会再次把系统困在不可退出的半终态，同时补足下一次精确定位所需证据。

## 7. 整改方案

### 7.1 P0：先消除“停住且只能杀进程”

#### A. 将 StopAll 改为可监督的有界状态机

建议显式阶段：

1. `AuthorizationRevoked`
2. `AllMotorOffSubmitted`
3. `PowerDisableStarted`
4. `TimersCancelled`
5. `RunnersCancelled`
6. `RecoveryOwnersCancelled`
7. `DaqStoppedAndDrained`
8. `PersistenceClosed`
9. `LogicalQuiescent`
10. `Completed` / `SafeButRestartRequired`

每个阶段必须记录 `CorrelationId、RunId、RunEpoch、EnterUtc、ExitUtc、ElapsedMs、Result`。物理 OFF/电源断能保持最高优先级，逻辑清场全部有单项截止时间，整条 Stop 事务有总截止时间。

建议初始预算：

- 全通道 DO OFF 提交：≤ 1 秒；
- 人工停止界面获得明确终态：≤ 5 秒；
- 同进程逻辑清场：≤ 15 秒；
- 无人值守恢复升级到外部进程接管：≤ 30 秒。

最终数值需通过台架故障注入确认，但任何等待都不能继续使用无限期 `CancellationToken.None` 作为唯一终止机制。

#### B. 人工停止不能等待旧故障 StopAll

当已有 `_stopSafetyTask` 超过阶段预算仍未完成时：

1. 将旧任务标记为 `Stalled`，禁止后续人工停止复用；
2. 在独立安全执行器中再次幂等提交所有 DO OFF 与电源 Disable；
3. UI 在限定时间内返回 `SafeButRestartRequired`；
4. 明确提示“卡钳已断能，软件收尾失败，请安全重启程序”；
5. 禁止在当前进程中直接开始新试验，直到逻辑不变量全部通过；
6. 提供“安全退出并重启软件”入口，而不是让界面永久等待。

#### C. 为同进程恢复增加外层硬截止和必达升级

在 `RecoverInProcessOrRestartAsync` 外围增加独立 deadline。超时后不能再等待旧 `StopAll`，而应：

- 向 sidecar 发送 `ExternalRecoveryRequired`；
- 固化当前 Stop 阶段和逻辑残留；
- 捕获进程转储；
- 由 Watchdog 终止并拉起新进程；
- 新进程完整学习后再续测。

超时升级必须由独立计时源驱动，不能依赖被监督任务自己抛异常。

#### D. 修正 Watchdog 接管不变量

新增以下任一条件持续 5～15 秒即接管：

```text
EligibleChannels > 0
AND RunActive == false
AND (
    RunId 为空
    OR StopAllActive
    OR Timers/Runners/StopCts/RecoveryOwners/DaqRecovery 任一非零
    OR RecoveryStage 长期停在 Paused/Recovering
)
AND StopProgressVersion 不再前进
```

心跳新增：

- `StopAllActive`
- `StopSource`
- `StopStage`
- `StopStartedUtc`
- `StopStageStartedUtc`
- `StopProgressVersion`
- `StopPhysicalSafe`
- 独立结构化的 Timer/Runner/CTS/Recovery 残留计数

`RecoveryActive` 不得只从首个通道状态推断；只要 `DaqRecoveryCount>0`、Software Recovery owner 存在或 Stop 事务仍活动，就必须视为恢复/停止事务仍活动。

#### E. 重做 ManualStop 协议

将现有单消息改成握手：

1. `ManualStopIntent`：禁止自动续测和自动重新上电，但 Watchdog 保留超时 Kill 权；
2. `PhysicalStopConfirmed`：主程序已确认 DO OFF/电源安全；
3. `StopCompleted`：逻辑清场完成，Watchdog 可结束；
4. 若限定时间未收到 `StopCompleted`，Watchdog 捕获转储并终止进程；人工停止语义下默认不自动开始试验，可按产品要求只重启到 Idle。

绝不能在收到“点击事件”的瞬间就永久撤销 Watchdog。

### 7.2 P1：降低误触发并增强电源恢复韧性

#### F. DAQ 存活监督增加分级和消抖

建议从单阈值改为：

- 100 ms：`Warn`，只记录指标；
- 500 ms：`Suspect`，要求连续多次检查且 Produced/Processed 序列不前进；
- 1000 ms：`Trip`，仍未恢复才进入局部恢复；
- 如果 Dev1、Dev2 同时发生 gap，优先判断为进程/调度抖动，不立即把两个设备都判成硬件失联；
- 如果 Trip 前回调序列已恢复且数据连续性可证明，只记录瞬态事件，不做设备重建；
- 实际阈值需基于 2 kHz、每批 20 点的采样节奏和故障注入结果标定。

#### G. 拆分“电机 OFF”与“电源 OUTP OFF”证据

状态中分别表达：

- 每个卡钳 DO OFF 是否已执行；
- 每个电源组 OUTP OFF 命令是否已发送；
- 回读是否新鲜；
- 电流/电压是否为安全值；
- 操作门、监控任务、网络命令分别耗时多久。

所有 `Gate.WaitAsync`、`StopMonitorAsync`、网络命令和回读必须有 deadline。超时后关闭/废弃旧客户端连接并升级外部恢复，不能占用 StopAll 的全局完成权。

#### H. 卡点自动取证

当 Stop 阶段 3～5 秒无进展时：

- 输出所有 Stop 子阶段 Enter/Exit；
- 输出持有/等待的组级 operation gate；
- 输出 Timer/Runner/Recovery owner 的实例与状态；
- 由 Watchdog 在 Kill 前生成 MiniDump/WER dump；
- 将 dump、最后心跳、Stop 状态、线程摘要纳入封存。

这样下一次能精确回答“卡在哪个调用”，不再只能从缺失日志反推边界。

## 9. 验收与故障注入

以下场景全部通过后，才可认为问题闭环：

1. 注入 Dev2 回调暂停 150 ms：只能 Warn，不得整批停机。
2. 注入 Dev2 回调暂停 700 ms：应按设定进入 Suspect；回调恢复且序列继续后应自动解除。
3. 注入 Dev2 回调暂停 2 秒：应先局部安全恢复；失败时整批断能并在期限内同进程恢复或外部重启。
4. 分别卡住 Timer 停止、Runner 清理、Recovery owner、Power gate、网络读、遥测停止、持久化 flush；所有情况下 DO OFF 都必须优先完成，Stop 事务必须在总时限内转 `SafeButRestartRequired` 或外部接管。
5. 在 `SystemFault StopAll` 进行中点击人工停止：UI 5 秒内必须得到明确结果，Watchdog 不得丢失超时 Kill 权。
6. 构造“心跳健康、RunId 为空、EligibleChannels>0、Timers/Runners/DaqRecovery 非零”：Watchdog 必须接管。
7. 构造 `RecoveryActive=false` 但 `DaqRecoveryCount=1`：Watchdog 必须仍把它视为活动/残留恢复。
8. 任何 `SafeButRestartRequired` 状态下点击开始：必须拒绝同进程上电，直到新进程完整预检和学习。
9. Kill 前应自动产生 dump，封存中能看到最后 Stop 阶段、阶段耗时和等待资源。
10. 进行不少于 24 小时耐久运行并重复触发 4 次以上恢复，验证不存在重试次数盲区或恢复 owner 泄漏。
11. 检查异常圈在 SQLite、Raw/MMF 和正式圈统计中的边界一致性，保证恢复不会重复计圈或遗留 `running`。

建议硬性验收指标：

- 物理 OFF 提交：P99 ≤ 1 秒；
- 人工停止 UI 终态：P99 ≤ 5 秒；
- Stop 阶段无进度检测：≤ 5 秒；
- 同进程恢复失败到 Watchdog 接管：≤ 30 秒；
- 不允许出现“RunId 为空但运行对象长期非零且无人接管”。

## 10. 修复发布前的现场处置建议

在正式修复发布前，如果再次出现“所有卡钳停止且 30 秒内无恢复”：

1. 先确认各通道 DO 已 OFF、电源输出和电流处于安全状态；
2. **不要把点击“停止试验”当作一定能解除卡死的手段。** V2.13.0.4 中该按钮可能复用旧的卡住任务并撤销 Watchdog；
3. 若界面无恢复且日志仍增长，按现有安全操作规程终止进程；
4. 重启软件后必须完整预检、完整学习，再开始正式试验；
5. 保留整个数据目录，不要只拷贝 `error.log`；至少同时保留 Watchdog Session、所有滚动日志、`index.db`、电源遥测和 IncidentSnapshots；
6. 若条件允许，在结束进程前先采集进程 dump，以便锁定 StopAll 的精确同步卡点。

## 11. 最终定性

| 层级 | 定性 | 置信度 |
|---|---|---|
| 初始触发 | Dev2 出现瞬态 DAQ 回调空窗，100 ms 单阈值立即触发恢复 | 已证实 |
| 全部卡钳停止 | Dev2 局部恢复熔断后，系统主动执行整批 StopAll | 已证实 |
| 不自恢复 | StopAll 未完成；心跳正常且恢复标志/接管条件存在盲区 | 已证实 |
| 人工停止卡顿 | 人工停止 await 复用了同一个未完成 `_stopSafetyTask` | 已证实 |
| 只能杀进程 | 人工停止消息使 Watchdog 立即永久撤权退出，主进程又无法结束旧 StopAll | 已证实 |
| StopAll 精确卡点 | 位于安全前导流程后段、首个后置日志之前；具体 API 尚缺线程转储 | 边界已证实，精确点待取证 |
| Dev2 回调底层原因 | 驱动/系统调度/总线/应用侧短时停顿之一 | 待补证据 |

本次应按 P0 级可靠性缺陷处理。单纯放大 DAQ 阈值只能降低触发概率，不能解决 `StopAll` 无界等待、Watchdog 盲区和人工停止撤权问题；必须同时整改这三条逃生链路，才能保证下一次任何底层故障都能安全停止、明确收尾并恢复或重启。

## 12. V2.13.0.6 落地状态（2026-08-14）

本报告确认的四条故障链已在 V2.13.0.6 同步整改：

1. `StopAll` 外层改为 15 秒硬截止停止事务，事务携带 TransactionId、RunId、RunEpoch、阶段和单调进度版本；物理 DO OFF、禁止再上电栅栏和电源 Disable 均先于 Timer/Runner、恢复 owner、DAQ、液压及持久化清场。
2. 停止超时后返回 `SafeButRestartRequired` 或 `PhysicalSafetyUnconfirmed`，并永久锁存 `RequiresProcessRestart`；旧 owner 的迟到完成不能覆盖超时终态，也不能重新打开执行栅栏。
3. Watchdog 协议升级为 v2。`ManualStopIntent` 不再撤销 Session；5 秒无进展重发应急停止，15 秒未完成时校验 PID/启动时间、最佳努力采集 MiniDump、终止旧进程，并用 `--watchdog-idle-restart` 打开全断能且不读取旧检查点的空闲进程。
4. DAQ 存活监督改为 100/1000/2000 ms：100～999 ms 只 Warn，1000 ms 进入 Suspect，达到 2000 ms 且 Produced 不前进并连续确认三次才 Trip；已恢复历史 gap 只作废受影响在途圈，不事后重建 DAQ。
5. 电源安全关闭返回逐组结果；Gate、遥测退出、单组和全部关闭均有截止。未连接、连接失败或无法回读一律为 `PowerOffUnconfirmed`，一个组失败不会阻止其他组发出 OFF。

详细代码清单、测试入口与尚需台架完成的验收项见《2026-08-14_V2.13.0.6_全卡钳停机与停止卡死整改实施验收报告》。原封盘目录全程只读，未作任何修改。
