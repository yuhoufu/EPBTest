# V2.12.0.16 自维护有界熔断与整批自动重建整改

> **后续版本：** 自维护熔断策略保持不变；退出数据耐久边界的最终反证已在 V2.12.0.17 补齐。见[V2.12.0.17 退出数据耐久门禁与流畅运行补充整改](./2026-08-09_V2.12.0.17_退出数据耐久门禁与流畅运行补充整改.md)。

## 技术结论

V2.12.0.15 已经解决自维护风暴、旧 RunId 污染、恢复所有权冲突和 UI 积压，但完成性反证又发现一个不同的问题：**部分软件恢复入口虽然不会并发爆炸，却仍可以单任务无限退避重试，使通道长期停留在“自维护”，永远没有机会进入更高层的软件重建。** 这与现场“进程内反复自维护失败，退出并重新启动软件后恢复正常”的现象一致。

V2.12.0.16 将 DAQ、Timer、液压/电源受影响组清场、启动定位和普通可恢复卡钳资格复核统一接入有界恢复层级。相同运行内连续三次软件恢复仍未建立有效运行态时，系统不再继续显示第 4、5、6 次自维护，也不把它误报成卡钳硬件故障，而是只发布一次 `SoftwareRecoveryCircuitOpen`：立即保持全部受影响输出关闭，执行统一 `StopAll`，完成 Raw/SQLite/液压/任务生命周期收口后进行同进程整批重建和完整学习；同进程重建不满足安全不变量时，再由既有无人值守协调器执行进程重启。

这修复的是“恢复层级不前进”的根因。后续 CPU 完成性审计又将学习/兼容路径的整毫秒忙等收紧为最多 0.2 ms 精对齐；后台任务生命周期审计把主窗体关闭接入控制层任务/液压排空，防止迟到恢复任务访问已释放硬件。自动化结果为控制/恢复 `309/309`、写盘 `28/28`、现场门禁 `17/17`、电源调试器 `17/17`、Release `0 error`。候选包身份校验通过，但工作树仍为 dirty，因此当前只能用于受控台架，不能作为正式生产包。

## V2.12.0.15 为什么仍可能永远停在自维护

代码反证不是对现场日志的猜测，而是对所有恢复循环逐条检查所得：

| 恢复入口 | V2.12.0.15 已有保护 | 剩余缺口 |
|---|---|---|
| DAQ 自维护 | 单设备 single-flight、1/2/5/10/30 秒退避、硬件双重证据门槛 | `ScheduleDaqSelfMaintenance` 失败后递归重新登记，没有软件失败总次数上限 |
| Timer 自恢复 | 每通道 single-flight、RunId 检查、恢复所有权 | `while (CanContinueTimerRuntimeSelfHealing(...))` 可无限执行 |
| 液压/电源恢复 | 同组单所有者、60 秒硬期限、失败转受影响组清场 | 受影响组清场及其异常重登记分支仍可按同一运行无限重新登记 |
| 启动定位 | 真硬件证据会停止，软件瞬态保持断电 | 批量和旧学习入口都存在 `while (true)` 软件重试 |
| 可恢复卡钳报警 | 人工停止/项目禁用/硬件锁存可取消 | 普通可恢复报警的无人值守资格复核循环没有总次数上限 |

原有 `DaqRecoveryFailurePolicy` 的职责只是防止“没有两份独立硬件证据就锁存硬件报警”。它返回 `ContinueSelfMaintenance` 是正确的硬件分类，但不能同时被解释为“同一进程必须永远重试”。V2.12.0.16 将两个问题拆开：硬件分类仍保持保守，软件恢复失败则切换到整批软件重建。

本节使用精确状态表而不是趋势图，因为证据是离散的控制流与终态约束，图表会隐藏每条入口是否存在停止条件。

## 三次失败后恢复层级必须前进

统一策略如下：

| 阶段 | 行为 | 卡钳硬件结论 |
|---|---|---|
| 第 1 次软件恢复 | 安全断电、封闭当前圈、1 秒退避后重建 | 不判卡钳故障 |
| 第 2 次软件恢复 | 重新验证 DAQ/电源/液压/机械释放，2 秒退避 | 不判卡钳故障 |
| 第 3 次仍失败 | 打开本 RunId 的软件恢复熔断器，停止局部循环 | 仍不判卡钳故障 |
| 整批同进程重建 | 统一 `StopAll`，确认物理安全、Raw/SQLite 耐久边界和逻辑清场，再完整学习并续测 | 软件生命周期恢复 |
| 同进程重建失败 | 保存检查点并执行进程重启；旧 RunId 任务不得影响新运行 | 软件进程恢复 |
| 两份独立硬件探测均确认 | 才允许进入真实硬件报警/通道停用策略 | 已确认硬件故障 |

三次是连续软件恢复失败阈值，不是客户峰值报警的连续圈阈值。成功恢复会结束当前上下文；新正式运行会复位熔断器。人工暂停、人工停止、项目禁用和已经锁存的真实卡钳报警不会被该机制越权重新启动。

## 同一 RunId 只能请求一次整批重建

新增 `SoftwareRecoveryEscalationGate`，以 RunId 为键执行原子 `TryAdd`。DAQ、Timer 和两个液压组即使同一时刻达到阈值，也只有第一个调用者发布 `SystemFaultRaised`；其余恢复所有者看到熔断器已经打开后立即退出。新运行在 `BeginBatchSession` 中复位 gate，旧运行还在排队的任务会因 RunId/RunEpoch 不匹配被拒绝。

熔断发布顺序固定：

1. 对所有受影响通道执行立即安全 OFF。
2. 状态写为 `SystemFault/SoftwareRecoveryCircuitOpen`，留下结构化 FIELD 状态证据。
3. 发布普通 `ControlFaultRaised` 供 UI 和日志展示。
4. 只发布一次 `SystemFaultRaised`，策略为 `UnattendedBatchRecycle`。
5. 无人值守协调器执行 StopAll、同进程重建；失败才进程重启。

因此，熔断不会直接永久禁用 EPB4/5/8 等卡钳，也不会让多个恢复任务同时重启整批。

## 限制与台架验证边界

本次修复证明“自维护不会无限停留”，不等于证明所有外部设备故障都能自动恢复。以下结论仍必须由真实试验机给出：

- 第三次失败时所有真实 NI OFF 的 P99 `<50 ms`、最大 `<100 ms`，以及外部硬联锁是否独立动作。
- StopAll 后液压压力与机械释放是否满足安全条件，并能在同进程重新建压。
- DAQmx 真实空窗、驱动重建和设备离线/重新上线是否按预期完成。
- 同进程重建和进程重启后的 SQLite 正式圈计数、RunId、学习模型和最近 10 圈证据是否连续。
- 8/24/72 小时运行中没有第二次独立根事故、没有未终态圈、没有 UI 卡顿和资源持续增长。

现场门禁会选择同一连续 RunId 会话；中途发生整批重建后，旧会话不能冒充完整 24 小时结果。验证必须从新 RunId 重新累计要求时长。
