# 10358-029 V2.12.0.1 EPB4/EPB5 反复自恢复失败根因与 V2.12.0.2 彻底整改

## 1. 结论先行

V2.12.0.1 末段 EPB4、EPB5 反复自恢复不成功的主根因已确认为：

> **32 位主进程在启动时为 12 通道各预映射 64MB 写盘视图，仅视图就常驻约 768MB 虚拟地址空间。长时间运行后第一次重映射因地址空间/内存资源不足失败，而旧代码在新视图创建前先关闭了旧访问器，使通道进入“已关闭访问器”的持久损坏状态。**

之后的 DAQ Stop→Start、暂停→开始都只重建采集与运行状态，没有重建 `EpbDiskWriter` 及其访问器，因此同一进程内必然再次失败。完整退出软件后，新进程重建虚拟地址空间和写盘器，所以重启后又正常。用户的现场现象与日志、代码三者完全闭环。

EPB5 的 `OpenCircuitOrOutputFault I=0.016A` 是上述软件恢复链中程控电源处于 `PlannedTransition` 时的二次误判，不是本次数据能支持的卡钳真实开路结论。

**根因置信度：高。** 关键结论由封存日志原始异常、异常发生顺序、源码资源模型、同进程重试失败以及完整进程重启后恢复共同支持。

## 4. 根因分解

### 4.1 x86 地址空间被过度预留

V2.12.0.1 主程序明确以 x86 运行。旧 `EpbDiskWriter` 构造时一次性创建 12 个 64MB `MemoryMappedViewAccessor`，因此约 768MB 映射视图在程序刚启动就常驻。还未计算 WinForms/DevExpress、NI-DAQmx、SQLite、图表、原始数据缓冲、托管堆和本地 DLL。

32 位进程的约束是可用连续虚拟地址空间，因此任务管理器中“物理内存使用率不高”不能排除这类故障。

### 4.2 视图切换顺序使一次瞬态失败变成持久故障

V2.12.0.1 的旧顺序是：

1. `Dispose()` 旧访问器；
2. `CreateViewAccessor()` 创建新视图；
3. 更新数组引用。

第 2 步在 19:53:39 因内存资源不足抛出异常，第 3 步没有执行，但第 1 步已不可逆地完成。因此从 19:55:01 起稳定重复“已关闭访问器”。

### 4.3 恢复范围小于故障范围

DAQ 恢复管线会重建 DAQ 任务、运行代次、队列和定时器，但 `EpbDiskWriter` 是窗体生命周期对象，只在软件关闭时释放。所以“自恢复完成”只修复了上层，不会修复已损坏的写盘访问器。

### 4.4 EPB5 开路是基础设施恢复窗口内的误归因

20:10 时 EPB5 连续读到约 0.016A，同时 EPB4 明确记录程控电源许可缺失、原因为 `PlannedTransition`。这个时间窗不满足“稳定供电后卡钳电流仍接近零”的硬件开路判定前提。

旧策略仅根据近零电流连续 3 次进行不可恢复禁用，没有在最终提交前再核对 DAQ/程控电源是否处于恢复转换。这使软件故障被错标为卡钳硬件故障。

## 5. V2.12.0.2 已实施的彻底修复

### 5.1 从源头降低 x86 映射压力

- 视图窗口从每通道 64MB 降为 8MB。
- 从“12 通道构造时全映射”改为“通道第一次真正读/写时才延迟映射”。
- 六个现场活动通道的常驻视图从最高约 384MB 降为约 48MB；未使用通道为 0MB。
- 所有 12 通道同时使用时也仅约 96MB，相比旧版 768MB 下降 87.5%。

实现位置：`DataOperation/EpbDiskWriter.cs`。

### 5.2 视图切换改为事务式“先建后换”

- 先创建 replacement accessor。
- 创建成功后才替换引用、更新基址/长度。
- 最后才关闭旧访问器。
- 新视图创建失败时，旧访问器仍然可用，不再把一次瞬态资源失败放大为持久故障。

### 5.3 增加真正的进程内写盘自愈

`EpbDiskWriter` 新增可恢复映射故障识别，仅处理：

- `OutOfMemoryException`；
- Win32 错误 8/14/1455（内存/承诺限制）；
- `UnmanagedMemoryAccessor` 已关闭。

命中后会按通道顺序取锁，释放所有短视图，保留 MMF、文件和 SQLite 圈索引，然后立即重试当前批次。成功时不再触发整套 DAQ 暂停、电源切换和定时器重建。

真实磁盘 I/O 故障、活动圈容量超限等不会被该机制吞掉，仍按原安全暂停策略处理。

### 5.4 防止重试造成数据重复

设备批次写入前保存每个通道的 `TotalWritten`、圈内样本号、Free-Run 样本号和进度检查点。任一后续通道失败时先回滚记账，重试覆写同一组环形位置，不会让前面已写通道增加重复样本。

### 5.5 开路判定增加基础设施前置条件

当 `OpenCircuitOrOutputFault` 发生时，最终提交前再检查：

- 所属 DAQ 是否处于恢复；
- 所属程控电源组是否处于恢复；
- 供电许可是否有效。

任一条不满足，立即安全断电，当前圈按软件恢复作废，不累计卡钳硬件开路。只有在 DAQ 正常、电源不在转换且供电许可有效时，连续近零电流才保留原有不可恢复开路保护。

### 5.6 并发与退出清理

- Free-Run 导出读取期间持有通道锁，避免与写入重映射并发。
- `EpbDiskWriter.Dispose()` 使用幂等标记并在通道锁下释放视图/MMF。
- `DoController.Dispose()` 增加幂等关闭标记；关闭后 `Initialize/EnsureReady` 不得再创建 NI 任务，消除退出时的 `SetPressure` 空引用竞态。

### 5.7 UI 卡顿与 CPU 降载

- 实时曲线仅在显示层抽稀到 **10 Hz**；2 kHz 原始采集、快速控制、峰值判定和落盘数据完全不变。
- `FormLoggerAdapter` 不再为每条后台日志调用一次 WinForms `BeginInvoke`，只写线程安全队列。
- UI 信息框使用容量 **512 行**的有界待显示队列，每 **150 ms** 最多追加 **50 行**；故障风暴时保留最新消息，不能无限挤占 UI 消息队列。
- UI 待显示队列已提取为可回归的无锁 `BoundedConcurrentQueue<T>`；生产者永不等待 UI，容量满时丢最旧项并累计 `DroppedCount`。三个仅供遗留浏览的内存日志队列由每类 100,000 条降为 2,000 条，完整日志仍由 `ProjectLogStore` 按保留策略持久化。
- `RtbInfo.Lines` 只在可见行数超过 2,000 的水位时读取并裁剪到约 1,800 行，不再每追加一行就复制整个文本框。
- 主窗体历史 GBK 源文件已无语义转换为 UTF-8 BOM，后续补丁和代码审计不会再因混合编码漏改。

实现位置：`MTTfTest/FormLoggerAdapter.cs`、`MTTfTest/FrmEpbMainMonitor.cs`。

### 5.8 启动收口与 1 Hz 主机资源审计

- 启动时将超过 **2 小时**仍为 `running` 的历史孤儿圈标记为 `aborted_on_startup`；短时重启仍保留旧版“running 圈不覆盖、可导出”的兼容行为。
- 每秒采集并写入 `HOST` 项目运行日志，同时写入事故诊断环：PID、进程位数、进程/系统/外部负载合计 CPU、工作集、专用内存、虚拟内存、句柄、线程、系统可用内存、程序盘余量、物理磁盘队列及读写速率。
- 事故导出的 `daq_runtime.csv` 同步包含上述列；如果现场系统性能计数器不可用，磁盘列会为 `NaN`，该情况本身视为上线审计失败，必须修复计数器或用固定 PerfMon 数据采集器补齐。

实现位置：`DataOperation/EpbDiskWriter.cs`、`IO.NI/HostRuntimeProbe.cs`、`IO.NI/TwoDeviceAiAcquirer.cs`。

### 5.9 DO 实测延迟进入控流模型

- 自适应模型由 v3 升级为 **v4**，旧 v1/v3 XML 可直接读取；首次有效控流样本后自动按 v4 保存。
- 每个通道把“正向断电命令调用至 DO 驱动返回”的实测完成时间写入模型，分别维护 `DO completion median/MAD` 和“去除 DO 延迟后的物理尾升 median/MAD”。
- 下一圈预测提前量由“物理尾升中位数 + 本通道 DO 完成延迟中位数”组成，不再只用无法分解的总 Lead。
- 历史达到 5 个样本后，单圈新延迟和尾升观测限制在当前中位数的鲁棒步长内（至少 5 ms、或 3×MAD），线程调度尖峰不会一次污染长期模型。
- 失败或超时的 DO 命令不进入正常学习样本，仍按电源组失效安全联锁处理。

实现位置：`Config/EpbAdaptiveProfiles.cs`、`Controller/EpbCycleRunner.Adaptive.cs`。

### 5.10 统一后台任务监督与退出收口

- 新增统一 `TaskSupervisor`；所有 Controller 正式编译路径中的 fire-and-forget 任务均登记任务名、RunId、EPB 通道、开始时间和活动任务 ID。
- 每个任务无论成功、取消或故障都会从活动表移除；故障任务的 `Exception` 必定被读取，并以任务名、RunId、通道和根异常落日志，10 秒内同类故障去重。
- DAQ 看门狗、自维护、液压/电源恢复、报警串口刷新、证据导出、Timer、历史峰值封口等原先分散的后台入口均纳入监督；源码扫描已无裸 `_ = Task.Run(...)`、裸异步调用或裸 `timer.StartAsync(...)`。
- 最后一个遗漏的完整软预警证据 `Task.Factory.StartNew` worker 也已登记到 `TaskSupervisor`；应用关闭时会与其他后台任务一起限时排空，不再脱离退出生命周期。
- 释放硬件前限时排空 EpbManager 与液压后台任务；报警、电源协调器 Dispose 时取消所属任务并限时排空，未收口任务会形成明确警告而不再静默遗留。

实现位置：`Controller/TaskSupervisor.cs`、`Controller/EpbManager*.cs`、`Controller/EpbCycleRunner*.cs`、`Controller/Alarm/AlarmManager.cs`、`Controller/HydraulicGroupCoordinator.cs`、`Controller/PowerSupplyCoordinator.cs`。

### 5.11 峰值缺失时间戳与软预警风暴收口

- 峰值证据诊断现在有三个互斥结果：可量化尾差 ≤100 ms 不报警；仅尾差 >100 ms 使用 `PeakEvidenceLagWarning`；快速窗口或完整峰值时间戳缺失使用独立 `PeakEvidenceTimestampMissing`，不得显示成“100 ms 处理滞后”。
- 完整软预警证据新增并发门控：同一幂等键只准入一次、同通道同类别 600 秒限频、严格最多 **1 个运行 + 1 个等待**。默认/现场配置的 `FullEvidenceQueueCapacity` 已由 2 调整为 1（该值只表示等待位）。
- 预警风暴不会阻塞控制线程；被合并/容量拒绝的事件仍保留普通项目日志和标量诊断，不启动额外整圈导出。

实现位置：`Controller/Alarm/WarningSnapshotModels.cs`、`Controller/EpbCycleRunner.Adaptive.cs`、`Controller/EpbManager.WarningSnapshots.cs`、`Config/AlarmConfigModels.cs`、`MTTfTest/Config/AlarmConfig.xml`。

### 5.12 发布包身份与脏工作区门禁

- `Tools/Build-Release.ps1` 在构建前删除旧身份文件，避免把上一次的 `build-identity.json`/`SHA256SUMS.txt` 混入新包；身份清单不再自引用，校验和覆盖除 `SHA256SUMS.txt` 自身之外的完整 Release 文件集。
- 默认构建仍强制要求干净 Git 工作区；当前尚未提交的整改只能使用显式 `-AllowDirtyCandidate` 生成验证候选，并固定写入 `DIRTY_CANDIDATE_NOT_FOR_PRODUCTION`、`deploymentApproved=false`、`gitDirty=true`，不能被误当正式现场包。
- 新增 `Tools/Verify-Release.ps1`，同时核对 EXE/ProductVersion/x86、身份清单的长度与哈希、校验和的完整文件集合及逐文件 SHA-256；加 `-RequireDeploymentApproved` 时，脏候选会被明确拒绝。
- 已验证默认正式构建会拒绝当前脏工作区，正式部署校验会拒绝当前脏候选，而且两条拒绝路径均不会改写已有身份文件。

### 7.3 日志放行红线

以下任一条出现即不放行：

- `内存资源不足，无法处理此命令`
- `无法访问已关闭的访问器`
- 同一 Device 在 10 分钟内连续进入 3 个以上恢复 Epoch

## 8. 风险边界与后续建议

1. **软件修复已完成，但现场 72 小时验收仍是上线必要条件。** 自动测试不能完全替代 NI 驱动、真实程控电源、网盘和长时间 x86 地址空间组合负载。
2. 中期可评估将主程序迁移为 x64，但需先确认 NI-DAQmx、ZLG CAN、SQLite 和其他本地 DLL 均有 x64 版本并完成硬件在环回归。V2.12.0.2 的短视图修复不依赖该迁移，可先在现有 x86 环境上解决本次故障。
3. 任务管理器的 CPU 98% 和主程序约 42% 不是可接受的长时间稳态。现场验收应使用 60 秒以上时间窗观察，不以单帧截图作结论；若在无恢复、无压缩、无杀毒扫描时仍持续高于 80%，应停止上线并保留 ETW/CPU 采样证据。

## 9. 最终判定

- V2.12.0.1：**不可上线**。存在可重现的 x86 写盘视图资源风险、一次失败后的访问器持久损坏、同进程无法彻底恢复、恢复窗口开路误判等问题。
- V2.12.0.2：**代码整改和自动验证已完成，具备进入现场分阶段验收的条件；在 72 小时现场验收通过前，不宣布最终批量上线。**
