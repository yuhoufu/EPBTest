# 2.14.2.12 恢复逻辑与线程专项审查

日期：2026-09-12。审查对象：修复工作树HEAD `64681eb09733a4af4054037afe8e92c5142da30d`，2.14.2.12-rc.2候选。静态源码审查加两项候选Release协议程序集离线验证。没有修改生产源码、参数、任务计划或运行现场；不把本地候选身份等同于现场当前安装身份。

## 结论

发现4项需要处理的恢复风险，其中两项为本轮新增发现。当前不能给出“恢复逻辑和线程均无问题”的结论。没有证据支持把所有历史采样停顿归因于线程死锁，也没有执行完整线程栈分析。

P1表示应在宣称无人值守恢复可靠前处理；以下均不表示已观察到物理事故。

## F1 / P1：交接前置校验失败遗留已启动标志

位置：`MTTFTest.Watchdog/WatchdogHost.cs:6754–6795`；释放点`:7061`；`FailSafetyHandoff:6830`。

`BeginSafetyHandoff`先通过CompareExchange将 `_safetyHandoffStarted` 从0改为1，再验证配置快照及恢复许可。验证失败时调用FailSafetyHandoff后直接返回，没有启动RunSafetyHandoffAsync。清零只在RunSafetyHandoffAsync的finally；FailSafetyHandoff不清零。

因此第一次遇到SafetyConfigSnapshotInvalid或SafetyHandoffPermitMismatch后，同一个WatchdogHost实例中后续交接都会被已启动标志拒绝，即使新交接本身合法。当前失败回执应保持失败，但不应占住所有未来事务。若外围本来要求失败后只能重建整个侧车，该要求也应明确表达，不能以无任务的busy标志隐式实现。

确定程度：源码控制流确定；尚未执行完整WatchdogHost故障注入，不断言历史每次ConfigInvalid后均经历了此路径。修复方向：前置验证与启动占有权统一管理，所有未交付后台worker的路径释放标志，避免旧finally清除新owner；回归用同一Host先失败再提交不同合法handoff。

## F2 / P1：SafetyAgent启动IPC缺少端到端截止

位置：`MTTFTest.Watchdog/SupervisorSafetyAgentLaunchClient.cs:53–69`；调用方`WatchdogHost.cs:6983`。

客户端同步管道只有 `Connect(5000)`，后续 `request.WriteTo` 和 `Response.ReadFrom` 没有取消令牌、异步截止或外部主动关闭管道。Supervisor连接成功后若停止读取或不返回完整应答，调用可无限等待。该同步调用发生在交接后台Task中，期间无法继续检查_stop或交接回执，且_safetyHandoffStarted保持1。

`AwaitSafetyHandoffBeforeRelaunchAsync:3925`附近确有外围等待期限，但其结束不等于取消这里的同步管道操作。不能把“等待者超时”当成“被等待任务已经停止并释放资源”。

此外`:7023`直接等待worker.WaitForExit，未给这个等待自身提供截止。SafetyAgent正常流程返回不等于硬件调用挂死时也能返回；这属于需要独立故障注入的同类可用性风险。

确定程度：本地截止缺失由源码确定；未在真实Supervisor上制造阻塞。修复方向：在独立可取消I/O边界覆盖连接、写入、完整读取；超时关闭本连接并确认任务结束。不能仅Task.WhenAny返回后丢下阻塞任务。对进程等待应轮询身份和安全事务，不可因超时无条件强杀持有硬件的代理。

验收：独立测试管道使用随机名称，分别模拟连接后不读、不响应、只返回半帧、进程迟退，验证超时可观测、线程/句柄释放、迟到响应不写新事务。禁止占用现场正式管道复现。

## F3 / P1：液压恢复登记与心跳判据存在矛盾窗口

位置：`Controller/EpbManager.cs:10055`先TryAdd液压恢复组；`:10361`附近才TryBeginRecoveryIncident；`Watchdog.Protocol/WatchdogPolicy.cs:983`；`WatchdogHost.cs:2531`。

两次发布之间有冻结、断电提交和参与者退出等操作。仅软件恢复计数为1、结构化身份及恢复生命周期尚未发布时，当前ShouldPublishRecoveryActive返回false；Watchdog对RecoveryActive=false且恢复计数非零的输入判为InconsistentRecovery。

本轮重新执行现有离线探针：未发布结构化信息时false/矛盾true；已发布时true/矛盾false。证明策略输入反例成立；尚未在生产接缝固定线程交错，不能说每次TryAdd都会造成误接管。已有历史InconsistentRecovery链使其值得优先复现。

修复方向：一次发布带身份的登记态，或定义有owner、有期限的过渡状态；不能永久忽略真正不一致，也不能放宽采样保护门限。

## F4 / P1：纯安全交接被强制要求恢复许可

位置：`MTTFTest.Watchdog/SupervisorSafetyAgentLaunchClient.cs:37–38`直接复制回执许可；`Watchdog.Protocol/SupervisorProtocol.cs:188–189`强制正Generation和合法PermitId。

人工停止后仍可能需要独立安全收尾，但正确状态可以没有自动续测许可。当前正式安装启动路径仍要求该许可，足以触发SupervisorSafetyRequestInvalid。

本轮重新执行离线结构验证：无许可false、仅补有效许可后true。历史09-09人工停止会话有对应请求无效记录；完整历史请求未全部采集，不能断言当时只有这一字段不合法。

修复方向：区分SafetyOnly与允许恢复的准备请求，保留完整进程/会话/二进制身份核验；SafetyOnly绝不授予上电或续测权。不能靠给人工停止重新发恢复许可绕过校验。

## 线程协作审查结果及边界

| 检查项 | 当前观察 | 结论 |
| --- | --- | --- |
| DAQ巡检重入 | EpbManager.DaqLiveness.cs:333使用Interlocked忙标志，:604 finally清零 | 普通巡检重叠会跳过，不会为每拍额外堆积恢复巡检；回调永久阻塞仍需另查 |
| 通道巡检重入 | EpbManager.TimerRuntimeHealth.cs:313及:377同类保护 | 未发现缺少finally释放的问题 |
| 安全/诊断回调分离 | WatchdogRuntimeCallbackDispatch.cs:751/757两条显式后台线程，优先级不同 | 有隔离设计；不是“所有恢复都在UI线程” |
| 诊断队列 | 有容量上限、合并、拒绝及计数 | 未见该路径无限排队；不等于整程序不存在内存增长 |
| 恢复worker | 液压路径先创建未运行worker、登记状态，再Start | 已防止一种owner/task空窗，但未覆盖F3的更早计数发布 |
| 停止事务及旧Epoch | 已有当前候选专门处理，先前文档有对应回归 | 本轮未重跑完整并发套件，不宣称停止竞态全部排除 |
| 跨进程通信及等待 | 发现F1/F2 | 主要风险是等待无法收敛、标志不能释放，不是线程数量本身 |

Task、Timer、async方法不对应固定专用线程；本轮未访问现场，因此不提供虚构的实时线程数、CPU或阻塞栈。两个线程优先级不同也不保证操作系统资源耗尽时安全线程仍及时运行。

## 对独立兜底方案的影响

保留“不改原恢复”的用户约束，本轮只报告问题。外部观察器可以发现无进展及原服务缺失，但不能自动修复F1/F2内部卡住，也不能绕过F4许可。若原恢复永久阻塞而只靠外部补启动EXE，仍会留下双权威或安全收尾缺失风险。

建议先对这4项做可重复的隔离回归，确认最小修复范围，再决定是否允许修改原实现。当前没有足够证据建议替换整套线程架构，也不建议未经复现就提高超时或保护阈值。
