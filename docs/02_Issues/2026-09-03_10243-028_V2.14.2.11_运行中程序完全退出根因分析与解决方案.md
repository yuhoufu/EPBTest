# 10243-028 V2.14.2.11 运行中程序完全退出根因分析与解决方案

## 1. 结论

本次不是一个单独的“程序崩溃”，而是两段故障串联后形成的“主程序彻底退出且未自动恢复”：

1. 2026-09-03 04:51:19 起，Dev1、Dev2 的 DAQ 回调和程控电源遥测同时出现 0.6～1.75 秒级延迟，控制数据时间轴又已落后现场约 2.64 秒。陈旧样本触发液压/电机断电自愈，多个并发周期把尚在收口的安全状态放大为全局外部恢复。
2. 主程序 PID 8084 随后停止发送 Watchdog 心跳且不再存在可见顶层窗口，但进程仍存活、后台采集和主机指标日志仍在写入。这不是正常退出，也没有证据表明是未处理异常或资源耗尽。
3. Watchdog 按现有三次 UI 探测与心跳超时规则，于 04:52:02 先抓取 dump，再主动终止 PID 8084。截图 1 是约 34 分钟后才发现现场，不是程序刚退出的时刻。
4. Watchdog 已生成有效的重启许可和安全接管意图，但 Supervisor 连续 67 次拒绝启动独立 SafetyAgent，统一错误为 SupervisorSafetyHandoffIdentityMismatch。因为独立安全确认未完成，系统按 fail-closed 规则禁止自动拉起主程序。

因此：

- **直接导致主进程消失的动作**：Watchdog 于 04:52:02 主动终止失去心跳且没有可见窗口的 PID 8084。
- **导致无人值守恢复失败的确定根因**：Supervisor 安全接管身份校验不一致，SafetyAgent 未启动，新主进程也未启动。
- **触发恢复链的高置信原因**：双 DAQ/共享执行环境出现调度或读取停顿，陈旧数据触发故障风暴与全局安全收口。
- **尚不能唯一确定的首发点**：主窗口为何先于进程退出而消失、心跳为何在后台日志仍运行时停止。现有 dump 是约 30 秒后抓取，封存又缺少本次 IncidentSnapshot、Supervisor 侧审计及服务账户本地镜像，不能在没有证据的情况下归因到某一条 UI 线程调用。

本问题应按 **P0 无人值守可用性缺陷** 处理。V2.14.2.11 在完成本文 P0 整改和现场安装态故障注入前，不应继续作为无人值守版本运行。

## 4. 故障链

> 双 DAQ/共享调度停顿 → 陈旧样本触发液压与电机自愈 → 并发周期将“待安全收口”放大为全局外部恢复 → 主窗口和 Watchdog 心跳消失，但后台进程仍活 → Watchdog 抓 dump 并终止 PID 8084 → 生成接管许可 → Supervisor 身份校验不一致，拒绝 SafetyAgent → 安全前置条件无法提交 → 自动拉起被持续阻断 → 人工启动

这条链中，安全断电和禁止无证据重启的 fail-closed 原则是正确的；问题在于故障放大、进程可监管性、接管协议和可观测性没有形成闭环。

## 5. 分层根因

### RC1：DAQ/共享执行环境发生停顿，控制链使用了陈旧数据（高置信触发原因）

事故前后的特征不是单一传感器掉线：

- Dev1、Dev2 都出现 0.6～1.75 秒回调空窗。
- 同一时段三个程控电源遥测也同时变慢到 672～705ms。
- 回调恢复后 EndRead 和 Rearm 本身仅约 0.00～0.02ms，但数据批时间轴持续落后现场约 2.64 秒。
- 控制队列、原始队列、持久化队列深度均为 0，未记录丢包或不连续；本次也没有 NI -200279 缓冲区溢出。

因此可以确认“数据到达/调度时序失真”，但仅凭现有日志不能在 NI 驱动、CLR ThreadPool、GC、系统调度或应用锁竞争之间进一步唯一归因。V2.14.2.11 已配置约 10 秒 DAQ 输入缓冲，但事实证明“大缓冲”只能降低溢出风险，不能保证控制数据新鲜度，也可能让恢复后的陈旧积压继续被读取。

对应源码：

- IO.NI/TwoDeviceAiAcquirer.cs:1142：到达延迟定义；
- IO.NI/TwoDeviceAiAcquirer.cs:3213：异步回调处理入口；
- IO.NI/TwoDeviceAiAcquirer.cs:3467：业务处理完成后才重新 BeginRead；
- IO.NI/TwoDeviceAiAcquirer.cs:5093：输入缓冲配置。

### RC2：在途安全收口被并发故障放大为全局外部恢复（高置信放大原因）

EPB12 的正式圈边界失败发生时，MotorOff=True，而 HydraulicReleased=False、Persistence=False。随后几秒内液压和落盘实际完成；这说明记录的是“正在收口”，不等同于物理关断失败。

现有 EpbManager.BatchStart.cs:3873 的边界处理仅在满足特定液压恢复委托条件时等待，否则立即锁存失败、撤销上电许可并进入全局 StopAll。多个周期、液压自愈、DAQ 新鲜度保护与电源组保护同时运行，造成：

- 同一基础设施停顿被拆成多条 EPB/液压/电源故障；
- 重复 DO_OFF 和电源 OFF 请求；
- 仍可在限定时间内完成的安全收口被提前升级到进程级恢复。

### RC3：主进程失去可监管性，Watchdog 按策略将其终止（确定的直接退出原因）

WatchdogApplicationLiveness.cs:77 以后将“没有可见顶层窗口”判为 WindowMissing，连续三次失败再结合心跳过期触发接管。最后心跳停在 04:51:22，但主进程的后台 HostRuntime 与 DAQ 日志一直写到 04:52:00。

现有证据可确定：

- 不是主程序自行正常退出；
- 没有记录到未处理异常导致进程崩溃；
- PID 8084 是被 Watchdog 明确终止；
- 终止前进程处于“后台仍运行、UI 与心跳链失效”的半失活状态。

现有证据不能确定主窗口消失的第一条 UI 调用。04:51:29 的 WindowMissing 与 Watchdog 请求控制修复几乎同时发生，而最后一条心跳尚未标记 StopAllActive。必须通过现有 dump 配合与现场 EXE 完全匹配的 PDB，或在下一版本提前抓取线程 dump，才能确定 UI 线程在等待、关闭、隐藏还是已异常终止。

### RC4：Supervisor 安全接管身份校验不一致，自动恢复确定失败（确定的恢复根因）

Watchdog 已生成：

- HandoffId：0e4939f1b54043528f8613ae16fd43b8；
- RelaunchPermitGeneration：1；
- RelaunchPermitId：22e1b66b8a1f4ad696791cdc7dd63be1；
- RelaunchState：Approved；
- 旧 PID 精确身份已证明退出；
- 执行授权已撤销、回调已隔离、资源已释放。

但 SafetyAgent 从未启动。SupervisorServiceHost.cs:655～674 将读取失败、Schema、State、终态、HandoffId、Nonce、许可代次/ID、EXE 路径和哈希等多项校验统一折叠成 SupervisorSafetyHandoffIdentityMismatch。封存中的项目镜像内部看起来一致，但 Supervisor 运行于服务账户，协议读取又会在服务账户本地控制目录、项目镜像及备份中选择“最新有效记录”。封存没有包含 Supervisor 审计和服务账户本地镜像，因此不能诚实地断言究竟是哪一个字段不一致。

高风险设计点是：

- Sidecar 以当前内存中的 receipt 构造请求；
- Supervisor 收到请求后再次从多个镜像中读取“最新” receipt；
- receipt 在重试中仍会更新 revision/attempt；
- 请求对象与 Supervisor 最终选中的文件可能跨越不同版本或不同镜像，形成 TOCTOU/多权威源不一致。

这属于确定发生、但具体字段因诊断粒度不足而未能细分的协议故障。不得通过关闭身份校验来绕过。

### RC5：关键可观测性缺口延长了定位链（确定的工程缺陷）

- 本次 04:51 事故没有生成对应 IncidentSnapshots；最新重型快照停在 2026-08-31。
- dump 在接管约 30 秒后才抓取，错过了 DAQ 首次停顿和窗口首次消失瞬间。
- Supervisor 把多项校验统一成一个错误码，未记录失败字段、所选镜像路径和 revision。
- 项目封存没有包含 Supervisor 服务审计、服务账户本地 receipt 镜像和 Windows 事件日志。
- 正式包没有写入 GitCommit、GitDirty、BuildUtc，降低 dump 与源码对应的确定性。

## 7. 解决方案

### P0-1：把 Supervisor 安全接管改为单一权威、精确身份的事务

目标：保留 fail-closed，不再让项目镜像、本地镜像和正在更新的 receipt 之间产生歧义。

1. 确立唯一权威源。推荐由 Supervisor 持有并写入权威 receipt；若必须由 Sidecar 写入，则请求必须携带固定 receipt 的 CanonicalHash、Revision、绝对路径和事务 ID，Supervisor 只读取这一版，不能重新选择“最新”镜像。
2. 在同一文件锁/事务内完成：冻结 receipt → 原子落盘 → 计算哈希 → 发送请求 → Supervisor 精确读取并比较 → 记录消费结果。
3. 把 IdentityMismatch 拆成可操作错误码：ReadFailed、SchemaMismatch、StateMismatch、HandoffIdMismatch、NonceMismatch、PermitGenerationMismatch、PermitIdMismatch、ExecutablePathMismatch、ExecutableHashMismatch。
4. 审计记录应包含 expected/actual 的哈希或脱敏摘要、被选中的实际路径、revision、last-write、服务账户身份；不要把原始 nonce 写入普通日志。
5. Supervisor 审计、服务本地控制文件和安全接管结果必须自动复制进项目封存。
6. 增加安装态端到端测试：真实 Windows Service/LocalSystem + 交互用户会话，强杀主进程，验证 SafetyAgent 完成独立断电/释压确认、新主进程拉起、checkpoint 接续与首圈提交。

### P0-2：将 DAQ 读取与业务处理彻底隔离，并显式治理陈旧积压

1. 每台 DAQ 使用独立、长期存活的高优先级读取线程或 NI 专用连续读取机制，固定块阻塞读取；读取线程只做 EndRead/拷贝/立即续读，不执行液压、日志、落盘或控制业务。
2. 保留输入缓冲，但不能把扩大缓冲当作根治。控制保护必须同时检查：
   - CallbackAge；
   - 最新样本时间戳到当前单调时钟的 SampleAge/BufferBacklog；
   - 批序列连续性。
3. 回调恢复后若 BufferBacklog 仍大于安全阈值，必须在全部输出关闭状态下丢弃/快速排空陈旧批次；只有连续新鲜批次恢复且无序列缺口后，才允许恢复控制。
4. 保持 100ms 预警、250ms 断电边界，不通过放宽阈值掩盖问题。
5. 采集 CLR ThreadPool 可用线程、GC pause、DAQ 回调线程 ID、NI 读取耗时、锁等待和 Windows 调度延迟，使用小型滚动 ETW 缓冲，事故时冻结。

### P0-3：建立单一基础设施故障所有者和 PendingSafetyClosure

1. 双 DAQ 回调延迟、PSU 遥测延迟和 Watchdog 管道延迟在同一时间窗出现时，合并为一个 AcquisitionInfrastructureStall 关联事件，不为每个 EPB 重复创建根故障。
2. 正式圈满足 MotorOff=True、但 HydraulicReleased/Persistence 尚在进行时，进入有硬截止时间的 PendingSafetyClosure；复用原有安全任务和回执，禁止立刻把“未完成”解释为“失败”。
3. 在截止时间内完成时，将周期记为 SafeAborted 并由唯一恢复所有者决定是否局部恢复；超过截止、无进展或物理状态反向时，才升级全局 StopAll/外部恢复。
4. 同一设备/电源组只允许一个 StopAll/安全收口 owner；重复请求只加入现有事务，不生成新的恢复根因。

### P0-4：修复“后台仍活、UI/心跳已死”的可监管性

1. 将 Watchdog 心跳从 UI/业务调度链剥离为最小独立发送器，同时上报三个独立维度：进程存活、控制进度、UI 状态。
2. 所有受控 UI 关闭或隐藏前，必须先持久化并确认 typed exit/stop transaction，心跳明确带 StopAllActive、TransactionId 和硬截止时间。
3. Watchdog 只对经过验证的受控退出给予有限宽限；窗口缺失但无 typed transaction 时仍应 fail-closed，不能简单忽略。
4. 第一次双设备超过 250ms 共享空窗、第一次 WindowMissing、第一次心跳过期时分别触发轻量线程快照；接管前再抓完整 dump。这样可以区分首发阻塞与 30 秒后残局。
5. 人工启动新会话后，Supervisor 应按 SessionId/PID/StartTicks 精确终结旧 Sidecar 的重试事务，不能留下旧会话长期重复发起安全接管，也不能使用模糊进程名批量结束。

### P1：补齐发布与封存证据

- 构建产物强制写入 GitCommit、GitDirty、BuildUtc、PDB identity 和包清单；Unknown 时阻止标记为可无人值守正式包。
- IncidentSnapshot 要覆盖 DAQ freshness cutoff、双设备共享空窗、WindowMissing 和 SafetyHandoffIdentityMismatch。
- 封存脚本增加 Windows Application/System 日志、.NET Runtime/WER、NI 诊断、Supervisor/SessionAgent 审计和服务账户本地控制镜像。
- 将 identity mismatch 的字段级统计、SafetyAgent 启动成功率、自动恢复耗时、陈旧积压最大值纳入现场健康看板。

## 8. 临时现场措施

在 P0 修复通过前：

1. V2.14.2.11 只允许有人值守运行，不能将“守护进程还在”当作主程序可恢复的证明。
2. 不得关闭 Supervisor 身份校验，不得提高 250ms DAQ 安全阈值，不得禁用 Watchdog 来换取表面连续运行。
3. 发现主程序不在时，先独立确认电机输出全关、四组电源 OFF、液压低于安全阈值，再人工启动；不能只根据界面消失直接重启。
4. 立即封存项目目录，同时导出 Supervisor/SessionAgent 服务日志、ProgramData/服务账户本地控制目录、Windows 事件日志和 NI MAX/驱动诊断。
5. 新程序运行稳定后，应通过会话身份化工具终结旧 Session 的重试；不要用 taskkill 按进程名批量清理 Watchdog。

## 9. 验收标准

| 用例 | 注入条件 | 必须结果 |
|---|---|---|
| 单设备 DAQ 停顿 | Dev1 1.2s 无回调 | 250ms 内断电；只产生一个基础设施事件；陈旧批次不进入控制 |
| 双设备共享停顿 | Dev1/Dev2 同时 2s，恢复后积压 2.6s | 全输出安全关闭；先排空陈旧数据；新鲜度恢复后才允许继续 |
| 在途安全收口 | MotorOff=True，液压/落盘延迟 3s | 进入 PendingSafetyClosure；截止内完成不升级进程级恢复 |
| 主进程半失活 | UI 消失、业务心跳停、后台线程仍活 | 首次异常即留线程快照；Watchdog 抓 dump、终止旧进程并留下完整事务 |
| 自动安全接管 | 强制终止主进程 | SafetyAgent 在 LocalSystem 安装态成功启动并独立确认安全，新主程序自动拉起和接续 |
| receipt 单字段篡改 | 依次修改 ID、Nonce、代次、路径、哈希 | 全部 fail-closed，并输出对应字段级错误码 |
| 多镜像竞争 | 本地与项目镜像 revision 不同 | 只消费请求指定的固定 receipt；不得出现通用 IdentityMismatch |
| 人工恢复 | 自动链故意阻断后人工启动 | 新会话成功，旧会话精确退出，不残留重复重试 Sidecar |
| 稳定性 | 软件仿真 24h、硬件全通道 72h | 0 次意外退出；0 次身份不一致；无陈旧样本参与控制；数据库无 running 残留 |

## 10. 最终判定

本次事故的正式判定为：

> **双 DAQ/共享执行环境的时序停顿首先触发陈旧样本保护和并发恢复放大；主程序继而失去 UI 与 Watchdog 心跳但仍在后台运行，被 Watchdog 于 04:52:02 主动终止。终止后的安全接管因 SupervisorSafetyHandoffIdentityMismatch 持续失败，导致 SafetyAgent 与自动重启均未发生，最终只能人工启动。**

解决优先级应是：

1. 先修 Supervisor 单一权威 receipt 与字段级审计，恢复无人值守闭环；
2. 再完成 DAQ 读取线程隔离、陈旧积压治理和单一故障所有者，消除首发与放大链；
3. 同步补齐首发线程快照、Supervisor 服务侧证据和可追溯构建信息。

在以上三项完成并通过安装态故障注入前，不建议把 V2.14.2.11 判定为无人值守可接受版本。
