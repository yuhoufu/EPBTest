## 3. 为什么 V2.13.0.30 能长时间运行而 V2.13.0.33 失败

| 对比项 | V2.13.0.30 | V2.13.0.33 | V2.13.0.34 处理 |
| --- | --- | --- | --- |
| 学习/启动清场 | 不会留下未来正式槽退休事实 | `UnmarkHydraulicParticipant` 在正式阶段前写入仅按 Run+Channel 缓存的退休事实 | 没有正式租约时不允许请求正式退休 |
| 正式参与者身份 | 行为上由当次正式运行决定 | 缺少参与者代次；同 Run 的旧确认可污染稍后的正式参与者 | 身份固定为 RunId+RunEpoch+Channel+ParticipantGeneration |
| 首个正式槽 | 可正常进入并产生机械进度 | 四通道在 Slot 10～13 被判为 `FormalBatchSlotMemberAlreadyRetired`，共 16 次失败 | 全体正式通道先一次性注册代次，再启动任一 Timer |
| Watchdog 传输 | 存在旧式抖动但未与新接管链叠加 | Client 约 3 秒 ACK 超时早于 Host 5 秒 UI 探测，反复主动拆管道 | Client 退休阈值 5750ms，由 Host 先完成 5s+500ms UI 判定 |
| 进程存活判定 | 主要依赖心跳 | V2.13.0.33 已有 UI 探针，但事件会重复且连接仍抖动 | UI 可响应只退休精确连接；连续三次 UI 失败才形成无响应证据 |
| 接管后的检查点 | 没有 V2.13.0.33 的新交接冲突 | StopAll 后又执行 FreshRestart/ApplicationClosing，`Armed` 被撤销 | 先持久化交接；接管关闭全程保持 SystemFault 事务 |
| 退出消息 | 旧行为链较短 | 正确发送 `WatchdogTakeoverExit` 时检查点已被撤销 | 只有交接回读成功才能发送 typed takeover exit |

V2.13.0.33 现场的 40 个学习圈全部成功，故障发生在学习转正式后的参与者身份管理；60 秒后 Watchdog 因正式机械进度停滞而接管，是后果而非最初根因。V2.13.0.30 能稳定运行的核心原因，是它没有 V2.13.0.32/33 引入的“未来正式槽退休缓存污染”这条失败路径。

## 4. 修复一：启动定位成为可等待的安全事务

相关实现：

- `Controller/EmergencyPowerGroupLatch.cs`
- `Controller/EpbManager.StartupPositioning.cs`
- `Controller/EpbManager.cs`

### 4.1 新不变量

1. `TrySubmitEpbOffHighPriority` 被接纳后，即使 100ms 内没有完成，也不能被直接等同于机械失败；
2. 100ms 到期仍立即关闭同组电源，安全阈值不放宽；
3. 同一电源组、同一恢复代次只有一个恢复所有者；不同电源组可并行；
4. 原始 OFF 终结、组输出关闭、电源恢复回读、Run/Epoch 有效四项全部满足后，才能再次机械定位；
5. 恢复等待、`ExpectedOutputDisabled`、Runner 修复和许可刷新不消耗三次真实机械尝试；
6. 恢复硬截止、OFF 最终失败或 Run/Epoch 变化时保持断能。

### 4.2 已覆盖回归

- 启动 OFF 晚完成与同代组恢复共同终结；
- 恢复硬截止与旧 Run 均保持失败安全；
- 同组恢复所有权合并；
- 真实过流、保护动作和硬件写失败仍走原有硬件安全策略。

## 5. 修复二：正式参与者使用精确代次

相关实现：

- `Controller/FormalBatchSlotCoordinator.cs`
- `Controller/EpbManager.BatchStart.cs`
- `Controller/EpbManager.cs`
- `Controller/EpbManager.PauseResume.cs`（复用既有正式重入入口）

### 5.1 身份模型

正式参与者租约固定为：

```text
FormalBatchParticipantLease =
    RunId + RunEpoch + Channel + ParticipantGeneration
```

槽、退休请求、退休确认和异步安全栅栏都必须匹配同一个不可变租约。仅 RunId+Channel 相同不再足够。

### 5.2 生命周期顺序

```text
新 Run 启动
  -> 启动/学习阶段 Mark/Unmark（不存在正式租约，不产生正式退休）
  -> 学习全部完成
  -> 一次性为全部正式通道 RegisterParticipant
  -> 启动任何一个正式 Timer
  -> 每槽用精确租约冻结参与者
  -> 通道终态请求精确退休
  -> 电机 OFF + 液压释放 + 持久化边界 + 执行许可撤销
  -> 确认同代退休
```

正式重入会取得新的 `ParticipantGeneration`。旧代退休确认即使迟到，也会因 `SameIdentity` 失败被忽略，不能关闭新代参与者的未来槽。

### 5.3 对现场根因的直接封堵

V2.13.0.33 冷启动基线对 12 通道执行 `UnmarkHydraulicParticipant` 时，正式阶段尚未提交。V2.13.0.34 此时不存在 `FormalBatchParticipantLease`，因此不会写入 `_confirmedRetirements`。进入正式阶段后，EPB 4/5/11/12 获得全新代次，首个正式槽不会再看到启动阶段的退休事实。

新增回归用例明确验证：旧代退休完成后注册新代参与者，旧确认不能污染新代准入。

## 6. 修复三：Watchdog 管道单写所有权与独立 UI 存活证据

相关实现：

- `MTTFTest.Watchdog/WatchdogHostSendQueue.cs`
- `MTTFTest.Watchdog/WatchdogHost.cs`
- `MTTFTest.Watchdog/WatchdogApplicationLiveness.cs`
- `Watchdog.Client/WatchdogClientTransportEngine.cs`
- `Watchdog.Protocol/WatchdogPolicy.cs`

### 6.1 每代连接单写模型

- 每个 `ConnectionGeneration` 只有一个 `WatchdogHostSendQueueOwner` 和一个写 Worker；
- 生命周期消息队列容量 8，普通消息队列容量 248；生命周期队列始终优先；
- `Attached`、恢复回执、`RequestStopAll`、`ExternalRecoveryRequired` 不会被 Ping/普通消息饿死；
- 写入上限仍为 500ms；超时只退休发生故障的精确连接；
- 退休先停止准入、取消队列、关闭管道，再有界等待 Worker；旧代对象与新代连接对象不共享 Writer；
- 记录连接代次、队列等待、写入超时和退休原因；正常断连不再被泛化为进程无响应。

### 6.2 Client/Host 阈值对齐

| 判据 | 数值 |
| --- | ---: |
| 心跳怀疑 | 3000ms |
| Host UI 探测开始/心跳超时 | 5000ms |
| 单次 UI 探针上限 | 500ms |
| Client ACK 退休阈值 | 5750ms |
| UI 探针间隔 | 1000ms |
| UI 连续失败接管门槛 | 3 次 |
| 未收到 `MainUiReady` 启动宽限 | 15s |

Client 不再在约 3 秒 ACK 空窗时抢先拆管道；Host 有完整的 5 秒心跳门槛和 500ms UI 探测窗口。

### 6.3 UI 探针判定

Host 按 PID 和进程启动时间复核身份，通过 `EnumWindows` 找主进程可见顶层窗口，再使用 `SendMessageTimeout(WM_NULL)` 探测。

- UI 响应：记录一次 `HeartbeatTransportDegraded`，退休当前连接并等待重连，禁止杀主进程；
- UI 连续三次不响应/窗口缺失：确认 `HeartbeatUnresponsiveConfirmed`；
- 进程退出或启动时间失配：立即形成接管证据；
- `MainUiReady` 按进程附着代次保存，跨同进程管道重连不重置；
- 同一确认故障只报告一次，避免每 250ms 重复写事件；
- StopAll 硬截止、输出关闭无法确认、正式机械进度停滞等安全证据仍可独立接管，不受 UI 响应抑制。

## 7. 修复四：接管检查点与退出所有权是一笔事务

相关实现：

- `MTTfTest/UnattendedRecovery.cs`
- `MTTfTest/WinFormsWatchdogStopHandlerCore.cs`
- `MTTfTest/FrmEpbMainMonitor.WatchdogUi.cs`
- `MTTfTest/Main_Frm.WatchdogUi.cs`
- `MTTfTest/FrmEpbMainMonitor.cs`
- `MTTfTest/WatchdogRuntime.cs`

### 7.1 正常接管时序

```text
Watchdog RequestStopAll(correlation)
  -> 主程序校验精确 Session/Attach/Pipeline 身份
  -> PrepareWatchdogTakeoverHandoff
  -> 持久化 Armed=true + RestartPending=true + Session + Run + Correlation
  -> 重新读盘验证同一记录
  -> StopAll(Source=SystemFault)
  -> 电机/电源/液压/DAQ/落盘达到安全终态
  -> 返回 StopCompleted
  -> 发送 typed WatchdogTakeoverExit
  -> Main 将 takeover 意图传播给全部监控子窗
  -> 最终窗体关闭仍使用 Source=SystemFault
  -> 旧主程序退出，Watchdog 保留恢复所有权并只拉起一次
```

关键修复是最后两步。即使主窗体在 typed takeover exit 后再次执行关闭收口，也不会以 `ApplicationClosing` 调用授权撤销钩子。新增测试直接断言：Watchdog 所有的最终关闭解析为 `StopSource.SystemFault`，普通人工关闭仍解析为 `StopSource.ApplicationClosing`。

### 7.2 交接失败时的失败安全语义

如果检查点缺失、Session 不匹配、读回失败或记录无效：

1. 仍执行 StopAll 并通知真实设备安全结果；
2. 不发送 Watchdog 所有的退出请求；
3. 主程序保持可见、安全空闲，等待人工处理或链路恢复；
4. 不发生“回执丢失后主程序自杀式退出”。

人工关闭只有在明确退出事务中才发送 `ShutdownExpected`，并允许主程序与 Watchdog 一起正常退出。Watchdog 接管/恢复退出继续复用线上 v3 消息 `WatchdogTakeoverExit`。
