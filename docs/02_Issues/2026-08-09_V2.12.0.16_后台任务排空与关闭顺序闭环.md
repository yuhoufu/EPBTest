# V2.12.0.16 后台任务排空与关闭顺序闭环

> **后续版本：** 本文解决“先排空任务、后释放硬件”。进一步反证发现最后 Raw/SQLite 边界未确认时仍可能结束 writer；V2.12.0.17 已增加独立应用退出耐久门禁。见[V2.12.0.17 退出数据耐久门禁与流畅运行补充整改](./2026-08-09_V2.12.0.17_退出数据耐久门禁与流畅运行补充整改.md)。

## 结论

完成全部恢复入口和 CPU 忙等整改后，对当前参与编译的业务代码再次执行后台任务生命周期审计。审计确认：恢复、证据、DAQ、液压、UI 文件写入和无人值守任务已经由 `TaskSupervisor`、专用 worker、可等待任务字段或显式异常观察者纳管；当前项目不存在参与编译的裸 `_ = Task.Run(...)` 业务任务。

但反证发现一个真实的关闭顺序缺口：主窗口第二次关闭重入曾直接解绑并释放 `twoDeviceAiAcquirer`，却没有调用控制层已有的 `EpbManager.ReleaseHardwareForRestart()`。因此，`StopAllAsync` 已完成物理安全和持久化边界并不等于所有恢复/取证后台任务都已经退出；迟到任务仍可能访问随后释放的 DAQ、DO 或写盘对象，造成退出卡顿、已释放对象异常，或者留下只能靠重启清除的进程内状态。

V2.12.0.16 已把控制层排空接入窗口关闭主路径。关闭次序现在固定为：

```text
StopAll 物理安全与 Raw/SQLite 耐久边界
    -> EpbManager TaskSupervisor 限时排空
    -> 液压后台任务限时排空
    -> 控制层释放电源/DAQ/AO/DO
    -> UI 解绑；仅在控制层释放失败时执行采集器直接释放兜底
    -> 报警、写盘及其余窗口资源最终 Flush/Dispose
```

这封闭的是退出与整批重建交界处的资源生命周期竞态，不改变硬件故障判断，也不会绕过 `StopAll` 的断能确认。

## 审计范围与判定

静态扫描覆盖 `Controller`、`DataOperation`、`IO.NI`、`MTTfTest` 及相关项目文件，重点检查：

- `_ = Task.Run`、`Task.Factory.StartNew`、`ContinueWith` 和 `async void`；
- 任务是否由监督器登记、由对象字段持有并在 Dispose/Stop 中等待，或在 UI 事件边界由 WinForms 负责观察；
- 关闭时是否先停止接收新任务，再排空任务，最后释放任务可能访问的对象；
- 未观察异常是否带 operation、RunId 和通道身份留下证据。

扫描到的裸 `_ = Task.Run` 只存在于 `IO.NI/TwoDeviceAiAcquirer - 备份-20250903.cs`，该备份文件未包含在 `IO.NI.csproj`，不参与当前二进制。参与编译的 `Task.Run` 均处于以下一种受管形态：

| 形态 | 当前处理 |
|---|---|
| 控制层恢复、证据和故障发布 | `ObserveBackgroundTask` 登记到 `TaskSupervisor`，记录 operation/RunId/channel，观察异常并可排空 |
| 无人值守进程内恢复/进程重启 | 独立 `RecoveryTasks` 监督器登记，窗口关闭时排空 |
| DAQ、写盘、UI 文件与设备 worker | 对象字段持有；停止接收后等待 worker/队列到耐久边界 |
| `ContinueWith` | 用于监督器异常观察和活动表清除，不是脱离生命周期的新业务工作 |
| `async void` | 仅保留 WinForms 事件处理边界；内部长操作使用 `await`，异常在边界捕获或由关闭门禁处理 |

## 缺口与修复

### 修复前

`FrmEpbMainMonitor_FormClosing` 第一次进入时等待 `StopAllAsync`。安全确认后通过 `BeginInvoke(Close)` 第二次进入，随后直接对 `twoDeviceAiAcquirer` 执行 `Stop/Dispose`。此路径遗漏了 `EpbManager.ReleaseHardwareForRestart()` 已实现的两级排空：

1. `_taskSupervisor.DrainAsync(2000)`；
2. `_hydCoordinator.DrainBackgroundTasksAsync(2000)`。

风险窗口是“StopAll 已返回”到“采集器已 Dispose”之间。此时恢复资格、报警证据或设备故障任务可能已经获得任务所有权，但尚未完成退出观察。

### 修复后

主窗口第二次关闭重入先调用 `_epb.ReleaseHardwareForRestart()`。该调用完成任务监督器和液压任务排空，再释放控制层持有的电源、DAQ、AO、DO。只有该控制层调用抛出异常时，窗体才对采集器执行直接 `Stop/Dispose` 兜底；不再对已经由控制层释放的同一对象重复停止和释放。

日志新增明确失败证据：`关闭窗口时控制层后台任务/硬件释放失败`。既有两条排空超时证据继续保留：

- `释放硬件前后台任务未在2秒内收口`；
- `释放硬件前液压后台任务未在2秒内收口`。

这些信息必须在 2/8/24/72 小时退出验收中保持为零；出现任一条都视为生命周期门禁失败，不能仅因窗口最终消失就判为正常退出。

## 现场验收方法

每次 2/8/24/72 小时阶段结束都应分别验证“正常停止”和“关闭窗口”两条路径：

1. 运行中制造一个可恢复的软件/DAQ 瞬态，使至少一个受管恢复任务真实创建，然后立即执行正常停止；再进行一次窗口关闭。
2. 确认 DO 和程控电源先完成安全关闭，Raw/SQLite 到达停止时生产边界，`running=0`。
3. 日志中不得出现后台任务/液压任务排空超时、未观察异常、访问已释放对象、SQLite/MMF 已关闭或关闭窗口控制层释放失败。
4. 进程应在可接受时限内退出，退出后无残留 `MTTfTest.exe`；再次启动必须无需人工清理锁、文件或恢复所有权。
5. 使用同一 EXE/config SHA 封存日志、任务快照、SQLite 完整性和退出耗时；整批重建或进程重启后以新 RunId 重新累计长跑时长。
