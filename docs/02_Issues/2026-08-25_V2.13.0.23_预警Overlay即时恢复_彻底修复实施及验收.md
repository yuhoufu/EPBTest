# V2.13.0.23 预警 Overlay 即时恢复：彻底修复实施及验收

> 实施日期：2026-08-25（Asia/Shanghai）  
> 目标版本：V2.13.0.23  
> 对应现场：`D:\EPB_Data\10358-029a_V2.13.0.22_0825_1130`  
> 前置根因报告：`docs/02_Issues/2026-08-25_10358-029a_V2.13.0.22_EPB12运行预警不消失_实时数据根因与即时更新方案.md`

## 结论

V2.13.0.22 中 EPB12 的 `运行 · 预警` 不消失问题已在代码层闭环修复，目标版本升级为 **V2.13.0.23**。

修复后的语义是：

1. 软预警判定发生时，结构化 overlay 在 Runner 判定线程同步激活；生命周期仍保持 `Learning`、`Qualification`、`Running` 或 `Recovering`，不会重新污染生命周期所有权。
2. 预警所在圈即使完成，也不会在同圈清除。
3. 只有后续一个不同 `AttemptId` 的完整圈得到 `Success`，并且控制、圈证据及对应持久化均已提交，才尝试恢复。
4. 清除必须同时匹配 `RunId + RunEpoch + Revision + WarningCode`；旧圈、旧运行代次、旧预警类别和迟到回调不能清除新预警。
5. 清除成功后立即发布 `Active=false, Revision+1`；WinForms 状态格恢复为“运行”，汇总预警数减少，Watchdog 下一心跳同步为 `WarningActive=false`。

这不是固定超时清除，也不是 UI 定时刷新。恢复事实仍由完整、可信的下一圈数据驱动。

## 已消除的两条根因链

### 1. 旧生命周期条件不可达

V2.13.0.22 已把预警迁移到独立 `ChannelWarningOverlayStore`，但正式圈提交后仍检查 `ChannelRuntimeState.WarningRunning`。新模型有意不再进入该状态，因此正常圈永远无法触发旧清除分支。

V2.13.0.23 删除该旧分支，统一改为 `TryClearChannelWarningOverlayAfterTrustedCycle`，并接入：

- 学习圈：圈证据封存、模型保存及成功 receipt 均完成后；
- 资格圈：圈证据封存、模型保存及成功 receipt 均完成后；
- 批量正式圈、单通道正式圈、暂停恢复正式圈：控制成功且耐久圈提交完成后。

### 2. 字符串预警的异步迟到竞态

V2.13.0.22 由 `Task.Run` 投递字符串预警，再由 Manager 创建 overlay。这样存在以下竞态：

```text
旧圈判定预警 -> 字符串回调仍在线程池等待
下一正常圈提交 -> 清除 overlay
旧字符串回调迟到 -> 再次激活陈旧 overlay
```

V2.13.0.23 新增结构化 `WarningOverlayRaised(AdaptiveWarningEvent)`：

- overlay 在预警判定线程同步发布；
- `WarningCode` 使用稳定的 `AdaptiveWarningCode/FaultCode`，不再从中文原因首词推断；
- `OccurredUtc`、`AttemptId`、`CycleNumber`、`CorrelationId` 原样进入状态事件；
- 原字符串 `WarningRaised` 只保留日志和兼容 UI 通知，可以异步，但不再拥有状态写权限。

因此，旧字符串回调已经没有重新点亮 overlay 的能力。

## 原子恢复合同

`ChannelWarningOverlayChangedEvent` 新增以下审计字段：

| 字段 | 用途 |
|---|---|
| `RaisedAttemptId` / `RaisedCycleNumber` | 标识预警产生圈，禁止同圈自清 |
| `RaisedUtc` | 计算真实恢复延迟 |
| `ClearedAttemptId` / `ClearedCycleNumber` | 标识提供恢复证据的可信圈 |
| `ClearReason` | 记录学习、资格或正式阶段的恢复来源 |

`ChannelWarningOverlayStore.TryClearIfCurrent` 使用 `ConcurrentDictionary.TryUpdate` 做比较并交换。清除前必须满足：

```text
overlay.Active == true
AND overlay.RunId == recovered.RunId
AND overlay.RunEpoch == recovered.RunEpoch
AND overlay.Revision == expected.Revision
AND overlay.WarningCode == expected.WarningCode
AND recovered.AttemptId > overlay.RaisedAttemptId
AND recovered.CycleNumber != 0
AND outcome.Kind == Success
AND outcome.Stage == Released
```

若清除读取之后有任何新预警发布，Revision 就会变化，旧清除的 CAS 失败，新预警保持激活。即使新旧预警代码相同，Revision 也能阻止旧圈覆盖新事实。

`SuccessWithWarning`、`SoftwareRecovery`、`Canceled`、`HardFault`、未完成反向释放、圈证据未封存或模型/耐久落盘失败均不能清除。

## UI、汇总和 Watchdog 一致性

WinForms 仍采用事件驱动，不新增轮询：

```text
可信圈提交
  -> Store CAS 写入 Active=false / Revision+1
  -> ChannelWarningOverlayChanged
  -> BeginInvoke 重绘 EPB12
  -> “运行 · 预警”变为“运行”
  -> 汇总预警数减一
  -> Watchdog 下一心跳 WarningActive=false、WarningRevision=新值
```

UI 活跃判定统一校验通道和 `RunEpoch`，旧运行代次的 overlay 不再进入状态格或汇总计数。`Active=false` 的展示函数专项测试已验证立即返回“运行”。

## 现场发布与最终验收门禁

代码与自动化已经闭环，但“远程机彻底解决”还必须完成一次 V2.13.0.23 受控发布和现场验证：

1. 使用完整发布包部署，确认窗口标题不再出现 `PackageManifestMissing`；校验 manifest、可执行文件哈希、配置哈希和版本均为 V2.13.0.23。
2. 启动一轮 15 秒周期试验，确认预警发生时日志包含标准 `Code`、`Attempt`、`Cycle` 和 `Revision`。
3. 预警圈应保持橙色；不得在 `SuccessWithWarning` 圈末尾提前变绿。
4. 下一完整可信 `Success` 圈提交后，应出现 `WARNING_OVERLAY_CLEARED`。
5. 从清除事件到 UI 变为“运行”的目标延迟 `<=500 ms`；控制层发布目标 `<=100 ms`。
6. 同一时点检查 EPB 汇总预警数减少，Watchdog 下一心跳 `WarningActive=false` 且 `WarningRevision` 增加。
7. 整次试验不得出现 `WARNING_OVERLAY_CLEAR_MISSING`；若出现，必须封存该圈日志、warning event 和心跳，不得直接放行。

`PackageManifestMissing` 与本次 EPB12 overlay 锁存不是同一根因，但它会破坏现场版本可追溯性，因此仍是 V2.13.0.23 发布门禁，不能忽略。

## 最终判定

V2.13.0.23 已从状态生产、圈身份、持久化提交、并发原子性、UI 消费和 Watchdog 心跳六个层面修复 V2.13.0.22 的预警锁存问题。原来的确定性不可达清除分支和异步迟到重激活竞态均已消除。

在完成上述远程机受控发布门禁后，EPB12 这类单圈软预警将保持到下一可信正常圈，并在该圈提交后即时恢复；不会靠重启、超时或 UI 强刷掩盖状态。
