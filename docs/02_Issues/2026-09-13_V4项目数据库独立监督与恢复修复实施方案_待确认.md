# V4 项目数据库独立监督与恢复修复实施方案（待确认）

日期：2026-09-13。本轮仅设计，用户确认后执行。参考V4分支codex/independent-fallback-v4，文档核对时HEAD=9720540（前一实现提交6d53efa）。实施时重新核验分支与工作区，不覆盖其他任务成果。

## 1. 目标及改动边界

FallbackGuard独立读取指定项目数据库，逐卡钳判断正式数据是否推进；不依赖主程序心跳才能发现故障。原恢复优先，持续不推进后执行排他的安全重启，并从检查点续测，以各应运行通道重新提交有效数据验收。

同时解决I0016/I0017暴露的两个直接断点和此前审查的恢复问题。保留采集、控制算法和实时保护门限；必要修改集中于恢复终态、停止意图、外部重启义务、接管授权和可核验的数据进展接口。

“独立”指配置、生命周期、观测判断独立；主动控制仍须共享人工停止和排他接管事实。数据库停止增长不是安全许可，不得直接taskkill后上电。

## 2. 与当前V4的区别

| 当前行为 | 本轮目标 |
| --- | --- |
| 主要依赖心跳中的提交进展 | 直接读取当前项目index.db，心跳仅作辅助说明 |
| 主进程活着时拒绝接管 | 能处理活着但停测：先安全停机、确认旧实例释放，再受控替换 |
| 等待原链已有Approved许可 | 由独立持久运行意图与安全接管生成合法恢复事务，不依赖故障主程序先提出请求 |
| 组内未重入成员可触发整组终态清理 | 已重入成员不得被旧组事务误删除；剩余成员有明确恢复/升级义务 |
| StopAll完成后可能丢失重启义务 | 分开表达物理安全、数据收尾和是否仍需恢复试验 |

原任务计划仅维持FallbackGuard，不直接启动主程序。监督器未开启时原恢复照常工作；观察模式关闭立即退出；接管中关闭必须安全交还。用户禁用兜底后任务不得自动复活它。

## 3. 项目配置与运行意图

独立配置至少包含：ProjectId、规范化项目路径、index.db路径、安装路径、允许的程序身份、启用通道、周期/学习预算、每路目标口径、监督开关、自动恢复开关。可以从项目配置导入，但运行期按已确认的配置版本冻结，不依赖主程序存活自动发现。

一个ProjectId对应一个监督实例；机器级安装单例同时防止不同项目争用同一设备。项目切换、数据库文件替换、路径指向备份或旧数据、配置摘要改变均重新调和，禁止沿用旧进展基线直接重启。

运行意图单独持久保存：RunId、IntentRevision、应运行通道、开始时数据基线、目标、人工停止修订、允许自动续测。仅打开FallbackGuard不创建运行意图。首次接管已在运行的旧项目，必须有明确绑定流程，不能因历史数据存在就认为该项目应该运行。

主界面停止按钮立即执行原安全停机，同时可靠写入停止事实并通知独立监督。写入失败显示“续测授权未确认”，保持禁止新动作；接管、启动及首次上电前均再核验。外部也提供“停止无人值守”，撤销意图后请求原安全停止。目标完成、通道人工禁用、维护另行记录，不能根据主程序自报SystemFault就把应运行通道从监督名单删除。

## 4. SQLite并发读取方案

主程序保持唯一业务写入者，监督使用同机正常只读连接。V4当前DataOperation/EpbDiskWriter.cs写连接声明WAL、Synchronous=Normal；这是源码配置，不是本轮现场实测。此前旧工作区Full配置不能当作V4配置。实施前记录实际SQLite/provider版本及只读查询journal_mode结果。

WAL支持并行读取和写入，但长读事务可妨碍检查点推进，也仍可能返回BUSY。监督每轮查询完成立即结束事务，不进行checkpoint、VACUUM、DDL或业务写入；不修改现有日志模式。[SQLite WAL说明](https://www.sqlite.org/wal.html)

实时数据库禁止immutable=1，也禁止nolock。immutable会跳过锁和变化检测，只适用于不变文件；此前封盘分析的用法不能复制到现场监督。[SQLite URI参数](https://www.sqlite.org/uri.html)

使用经过目标System.Data.SQLite版本验证的Read Only连接参数，额外query_only作防误写。WAL/SHM存在及权限按该版本要求验证，绝不删除它们“解锁”。读取WAL必须通过SQLite，不复制单个index.db代替实时读取；不从共享网络路径直接读取WAL库。

建议初始预算：每5秒一轮、全轮2秒、busy等待最多500ms、最多一次短重试，总预算不叠加突破。查询放有界worker；超期关闭自己的连接/终止自己的读worker并验证释放，不能影响主写入者。正常查询目标P95<100ms，12路总返回<64KiB，实测不满足则优化而不是放宽到无限等待。

### 4.1 查询口径

当前表epb_cycles有epb_id、cycle_number、status、end_time等字段，现有(epb_id,cycle_number)索引。首版对每个应运行通道查询最新正式completed记录：

```sql
SELECT cycle_number, end_time, sample_count, mechanical_completed
FROM epb_cycles
WHERE epb_id = @channel AND cycle_number > 0 AND status = 'completed'
ORDER BY cycle_number DESC LIMIT 1;
```

这是候选查询，须EXPLAIN QUERY PLAN与历史大库实测。现有索引可能因大量非completed尾记录导致扫描过多；需要时由离线升级添加针对completed的部分索引或等效复合索引，监督自身不创建索引，不在现场试验中自动执行迁移。

“计数推进”比较同一项目/数据库世代、Run基线之后的正式提交，不仅比较时间戳；失败圈、负号学习圈、机械计数不能当正式完成。数据库已有行由running更新completed的语义应测试，不能只盯新增id。时间只作审计，静默持续时间使用监督进程本地单调时钟。

现有表不能完整证明RunId/Epoch时，开始时冻结基线并禁止数据库世代切换复用；若仍无法排除旧任务迟到提交，增加由原写入者在相同业务事务更新的少量提交身份字段/进展表。这属于条件性数据层适配，需迁移回退测试，不能靠心跳字段假装独立数据库证据。

### 4.2 读取错误不等于停测

结果明确分为Advancing、NoProgress、Unreadable、IdentityChanged。BUSY、锁等待、缺文件、损坏、权限错误先进入Unreadable并有界重试/告警，不积累“已证实无推进”次数，也不清零已有故障等待历史。连续不可读超过60秒转StorageFault，暂停自动上电；修复或获得可信证据后重新调和，不无条件循环重启。

## 5. 停滞判定与触发参数

以下为待确认并由台架验证的起始策略，不是新的物理保护门限。

| 阶段 | 判定 |
| --- | --- |
| 未授权/人工停止/维护 | 只观察，不自动开始 |
| 启动与学习 | 独立总预算初设max(300秒, 学习圈数×周期×2+60秒)，具体按配方验证；不能以没有正式圈立即重启 |
| 正式运行 | 任一路无正式推进≥max(90秒, 6×周期)进入确认；15秒周期为90秒 |
| 确认停滞 | 再取得3轮成功读取且仍不推进；重复提交、旧世代数据不算恢复 |
| 原恢复进行中 | 给有限阶段预算，不能靠心跳“恢复中”无限延期；正式停滞至接管申请初设总上限180秒，学习/重建另设有界阶段 |
| 重启后验收 | 每个应恢复通道基线后连续3条有效正式提交并观察至少2个周期；补核波形存在及动作反馈 |

数据库推进是业务证据，不单独证明真实机械动作或断能。学习阶段变化、长配方及多级重建必须有独立预算表；当前上限冲突时按明确定义阶段计算，不能同时启动互相矛盾的计时器。

## 6. 受控“整个软件重启”流程

1. 持久记录Incident与无推进证据，固定应恢复通道；再次核验非人工停止、目标未完成、预算允许。
2. 申请排他接管，冻结旧链新增恢复动作；原安全保护不取消。
3. 原程序能响应时，经原入口安全停止、泄压、断电并保存；不响应时使用经过台架验证的独立安全执行路径。
4. 确认实际安全、旧进程PID/启动时间及设备owner释放、没有未决启动或旧SafetyAgent控制；才允许结束旧主程序。没有独立安全证明时停机告警，不绕过。
5. 通常只替换主程序及其会话资源，保持健康Supervisor/SessionAgent服务；它们自身失效时另走明确的基础设施恢复事务，不按名称“一锅端”。
6. 按有效运行意图、新FenceGeneration和检查点建立恢复许可，通过排他启动入口拉起；不等待原故障主程序先生成Approved许可。
7. 启动应答丢失时查询已记录的启动事务/PID，禁止盲目再拉起；不确定结果保持Unknown调和。
8. 用数据库逐路提交及实际反馈验收后交还原恢复；不是把外部程序长期变成高频控制器。

如果Supervisor本身卡死或旧驱动无法释放，外部不能调用同一阻塞入口后声称已独立兜底。实现前必须定义独立的安全断能与精确基础设施修复能力；无法实现的场景列为明确不支持的故障类别。软件独立进程不能覆盖整机断电、OS死机和永久设备故障。

建议重启上限沿用原预算并取更严格值，初设滚动30分钟最多3次；计数跨监督/主程序重启持久保存，启动成功不清零。同源反复故障触发熔断并保留诊断，不以无限重启掩盖问题。

## 8. 数据完整性与WAL耐久核查

读到completed说明SQLite事务对读者可见，不必然意味着突然断电后绝不丢失；WAL的NORMAL与FULL耐久边界不同。[SQLite WAL耐久说明](https://www.sqlite.org/wal.html)

当前V4的Synchronous=Normal与此前基线不同，必须审查变更目的、提交回执与断电恢复设计。未经测试不在本轮文档中决定切换模式；实施时通过性能和崩溃窗口实验选择策略，禁止以降低持久性掩盖采样问题。

验证动作已完成但未提交、波形已写但索引未提交、索引提交后应答丢失；按Run/通道/周期身份幂等调和，不重置计数、不自动补圈。强杀进程的内存尾段不能保证保存，必须有可重放持久暂存或明确记录不确定周期。

## 9. 实施顺序与完成标准

1. 冻结经确认方案，核对V4最新提交和已有工作；建立隔离实现分支，先补R1/R2生产接缝回归。
2. 最小修复R1/R2/R3及关闭问题，复核R4～R6；不同时重写控制架构。
3. 实现只读数据库worker、项目身份/意图配置、状态机和资源预算，用I0016/I0017离线回放证明能识别两段停测。
4. 接入活进程受控退出、独立安全前置、持久排他启动及续测；模拟旧链失效，不只调用一个仍可能挂死的旧入口。
5. 本地Debug x86；AdaptiveControl、EpbDiskWriter、PowerSupplyDebugger、RecoveryGuard、停止/Watchdog及数据库并发/接管注入。
6. jxcq验证PS5.1、独立开关、任务计划、项目切换、安装修复卸载及模拟恢复。实物安全接管在独立台架验收，不对WJ-EPB当前试验注入故障。
7. 24h初验、168h耐久；比较有/无监督的写入延迟、采样空窗、WAL大小、读超时率、内存、CPU及线程/句柄趋势。

必测：单路/部分/全部停测、数据库正常但主心跳失效、心跳正常但全停、锁/不可读/磁盘满、人工停止并发、重复开始、机器时钟回拨、数据库替换、监督崩溃、启动半提交、旧代迟到命令、保存超过30秒、新会话接管及熔断跨重启。

主动恢复交付门槛：I0016/I0017对应故障注入可自行恢复所有应运行通道，不依赖人工点开始；任何安全/授权不明场景不启动；无双控、重复计数、未解释数据缺口；查询负载不造成可观测持续写入退化。只读观察阶段只是中间交付，不能作为最终“兜底续测已完成”。
