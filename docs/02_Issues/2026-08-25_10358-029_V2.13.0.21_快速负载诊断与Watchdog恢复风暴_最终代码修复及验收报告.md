## 1. 结论

V2.13.0.18～V2.13.0.20 的“刚启动即报警、看门狗多次恢复、最终无限恢复”不是单一阈值偏小，而是四条链路叠加形成的闭环缺陷：

1. 新增“负载快速上升、但尚无空载基线”检测后，诊断结果曾穿透到正式控制状态机，可能把学习期或负载上升期改写成异常终态。
2. DAQ 采样身份、Accepted/Processed/Cutoff 水位和恢复代次不够严格，迟到样本或不完整高频证据可能被当成本圈证据。
3. 恢复所有权、Stop 安全事务、DAQ 恢复终态和 Watchdog 心跳不是一个原子生命周期；旧恢复未真正闭合时，新恢复可以再次进入。
4. Watchdog/Sidecar/进程重拉缺少跨重启的唯一耐久授权和失败回执闭环；连接断开、回执丢失或进程崩溃点可能导致同一失败被再次登记、再次拉起。

V2.13.0.21 已把这些问题分别收口，并用统一身份、单一 owner、耐久 journal、唯一 permit 和 fail-closed 策略连接成完整安全闭环。快速负载提示现在只属于诊断侧通道，不再修改卡钳生命周期、不暂停、不触发 SafeIdle、不登记系统故障，也不会单独触发 Watchdog 接管或永久停机。

## 4. “当前电流=1.398 A”报警详解

原提示为：

> 警告：检测到负载快速上升，但本圈尚未取得空载电流基线：当前电流=1.398A；这是软预警，不会单独触发卡钳永久停机。

### 4.1 它表示什么

控制器在正向动作中观察到电流上升速度开始呈现“进入负载区”的形态，但本圈此前尚未累计出满足数量、持续时间、新鲜度和完整身份要求的空载电流基线。`1.398 A` 只是当时样本值，不等于过流，也不等于卡钳故障。

常见成因包括：

- 本圈从残余载荷附近开始，空行程过短；
- 首批样本已经接近负载上升区；
- DAQ 回调追赶、代次切换或 cutoff 使前段空载样本不具备完整资格；
- 单个毛刺或短暂上升满足“提示”条件，但不满足正式控制证据；
- 试验刚启动，自学习模型尚未稳定。

### 4.2 这个报警是否合理

作为“证据不足”的工程诊断，它是合理的；作为报警、暂停、故障或恢复触发条件，它不合理。原因是“尚未取得基线”描述的是软件证据质量，不是硬件已经故障。

V2.13.0.15 没有同名检测，因此不会产生完全相同的提示。V2.13.0.20 的问题不在于打印了文字，而在于该诊断曾能影响控制生命周期，随后又被 Watchdog 解释为失去进展。

### 4.3 V2.13.0.21 的最终语义

- 事件类型固定为 `DiagnosticOnly`。
- 去重键为 `RunId + Channel + Code`，跨 epoch/rejoin 不重复轰炸。
- 每个 Run/Channel 只写一次明细；Run 结束写一次汇总。
- 不调用 Warning/Alarm/RecoverableFault/Pause/RuntimeTransition/TimerPause/SafeIdle/Stop/SystemFault。
- 不改变 `AdaptiveStage`，不写卡钳永久停机，不创建恢复 owner。
- 诊断订阅者慢或抛异常时，回调在锁外隔离，不阻塞控制环。

生产 Runner 10,000 圈专项结果：上述九类控制/安全副作用计数全部为 0，明细 1 次、汇总 1 次。

### P0-4：DAQ 真实恢复事务与唯一 SafeIdle

主要文件：

- `Controller/DaqRecoveryTransaction.cs`
- `Controller/DaqRecoveryTerminalSupervisor.cs`
- `Controller/EpbManager.DaqRecoveryState.cs`
- `Controller/ChannelExecutionFence.cs`

实现：

- DAQ 恢复按真实阶段推进并校验 admission/physical receipt，不以日志 Detail 冒充进展。

- 任一步失败由同一 owner 自动重试；不得创建第二 worker、重复 OFF、整批重启或进程重启。
- 永久失联只执行一次 SafeIdle；`SystemFault/batch restart/process restart = 0`。

### P0-6：Sidecar 唯一权威和 UI/回调收口

实现：

### P0-7：跨重启的唯一恢复许可和失败回执

主要文件：

- `Watchdog.Protocol/DurableRelaunchAuthorityV4.cs`
- `Watchdog.Protocol/DurableRelaunchAuthorityFileStore.cs`
- `Watchdog.Protocol/DurableRelaunchAuthorityV4Validator.cs`
- `Watchdog.Protocol/RecoveryFailureProtocol.cs`
- `MTTFTest.Watchdog/StrictHostRelaunchOrchestrator.cs`
- `MTTFTest.Watchdog/GuardedProcessLauncher.cs`
- `MTTFTest.Watchdog/WatchdogHost.cs`
- `MTTfTest/WatchdogRuntime.cs`

最终协议和存储版本：

- Watchdog wire protocol：`Version = 3`，`MinimumCompatibleVersion = 3`，只接受 exact v3。
- Journal schema：`4`。
- Durable relaunch record：`RecordKind = DurableRelaunchAuthority`，`RecordFormatRevision = 2`。

最终事务：

1. 主进程先创建或只读打开严格 authority；正常启动必须 bootstrap 成功后才启动 Sidecar。
2. Runtime 发送 exact-v3 `RecoveryAttemptFailed` 原始载荷，并冻结 correlation、payload SHA、reporter nonce/PID/start 和 connection generation。
3. Host 在跨进程 mutex 内重新读取 authority，执行单次 CAS 决策并持久化 receipt；相同 correlation+payload 重放返回相同 receipt，不增加预算。
4. 回执若因管道断开丢失，Runtime 在同一 correlation/原始载荷下跨重连重发；Host 使用已冻结的首次 reporter identity 重放，不把连接代次变化误判为新故障。
5. 只有严格 authority 可以签发一次性 launch intent。`GuardedProcessLauncher` 在 `Process.Start` 前必须 consume permit，并在消费后再次核对 exe SHA，防止 TOCTOU。
6. Host 进程重拉状态按 Approved → LaunchIntent → Started → Attached → Committed 推进；每一步都保存 PID/start/nonce/generation/revision/SHA。
7. 任意崩溃点重启后，reconcile 对 alive/dead/unknown 做保守判定；不确定、损坏、不可读、CAS Busy 或任一持久化失败均 fail-closed，不能再次拉起。
8. 同一 decision 至多一次 Host `Process.Start`。Sidecar 自身启动由独立 `SystemSidecarProcessLauncher` 管理，不与主进程重拉 permit 混用。
9. invalid recovery intent 仅做本地审计；emergency checkpoint reject 只能 attach existing authority，发送永久失败并等待耐久回执后退出，不创建新 authority、不启动新 helper。

## 8. 本轮能够确认与不能确认的边界

### 已确认

- V20 现场 fixture 不再因快速负载诊断进入 `AbnormalLoadRiseDrop`。
- V15 fixture 仍能到达 `ClampReached`，没有为了消除 V20 误报而削弱 V15 正常控制。
- 快速负载诊断在 10,000 圈生产 Runner 中没有控制/报警/恢复副作用。
- 相同失败在断线、重连、回执丢失和进程重启后不会重复计预算或重复 `Process.Start`。
- Stop、DAQ、Sidecar、UI 和 journal 的主要竞态、超时、异常和崩溃点已由生产 seam/真实 pipe/真实子进程覆盖。

### 尚不能用本机自动化替代确认

- 本机没有连接现场 NI DAQ、真实 DO/AO、液压系统和四台程控电源，因此没有完成真实物理执行器验证。
- 没有在 10358-029 台架上完成 V2.13.0.21 连续 24 h 和 72 h 运行。
- 没有在现场真实断网、断电、拔 DAQ、Watchdog 进程强退、主进程强退条件下完成组合故障演练。
- 当前结论是“V2.13.0.21 代码候选满足软件发布门”，不是“现场耐久已完成”。

## 9. 现场部署与分阶段验证计划

### 9.1 上线前

1. 保留 V2.13.0.15 可执行目录、项目配置和完整数据封存，不覆盖原目录。
2. 用正式发布脚本生成 V2.13.0.21 独立目录、`build-identity.json` 和 `SHA256SUMS.txt`。
3. 核对主程序、Host、Protocol、Client 均为 2.13.0.21，协议为 exact v3。
4. 备份 `WatchdogSessions`；首次迁移 schema2/3/old4 后，确认写成 schema4/format2，再允许正式启动。
5. 确认现场 exe/config SHA 与正式包一致；哈希不一致禁止试验。

### 9.2 无负载/不上电观察

1. 冷启动并停留 30 min，确认只有一个主程序、一个 validated Sidecar，无重复 helper。
2. 不开始试验时观察 2 h：Watchdog recovery/relaunch、SafeIdle、SystemFault、TerminalClosureBlocked 均应为 0。
3. 人工打开/关闭监视页、切换项目、退出再进入；UI target、pipe 和进程句柄不得单调增长。

### 9.3 小批物理验证

1. 只选择 EPB4/5/10，先完成自学习各 10 圈，再运行 100 圈。
2. 核对每个快速负载诊断是否只写一次明细和一次汇总；不得同时出现 Pause/Recovering/Watchdog takeover。
3. 人工停止分别安排在空闲、建压、正向动作、液压释放、DAQ 排空和持久化阶段，确认严格阶段顺序和一次 SafeIdle。
4. 在安全监护下分别注入一次 DAQ 短断、程控电源通信超时和 Sidecar 重连，确认同 incident 只有一个 owner。

### 9.4 24 h 与 72 h

1. 通过 100 圈后扩大到目标通道，先连续 1,000 圈，再进入 24 h。
2. 24 h 全部红线为 0 后再进入 72 h；中间不复用已失败的 Session/permit。
3. 每阶段封存整个项目目录、WatchdogSessions、运行/警告/错误日志、进程清单、句柄/线程/内存趋势和正式包哈希。

现场放行红线：

- 非人工预期的 Watchdog recovery/relaunch 次数必须为 0。
- 不得出现恢复→失败→重新恢复的循环；同 correlation 只能有一个耐久 decision。
- 快速负载缺基线诊断不得导致 Pause、Recovering、AlarmStop、SafeIdle 或 SystemFault。
- 不得出现第二 helper、重复主进程、旧 Attached 接管新 Session。
- DAQ accepted/processed/cutoff 不得倒退；Raw/Stat/CSV/BIN 不得出现不可解释空洞。
- `TerminalClosureBlocked`、authority `Unproven`、journal corrupt/unreadable 任一出现时必须保持全断能并停止试验，不得自动继续。
- 内存、句柄、线程和后台任务数不得持续单调增长。

## 10. 回退原则

若现场红线未满足：

1. 立即人工停止并确认物理全断能。
2. 完整封存 V2.13.0.21 项目目录和 WatchdogSessions，不清理、不复用失败 Session。
3. 退出主程序和 Sidecar，核对进程均已结束。
4. 使用独立保存的 V2.13.0.15 程序目录启动；只迁移必要项目配置，不把 V21 schema4 authority/permit 作为 V15 的继续运行授权。
5. 回退只是维持生产，不代表关闭问题；必须以 V21 封存中的 correlation、receipt、authority revision 和波形证据继续定位。
