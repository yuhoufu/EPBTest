## 1. 结论摘要

分析对象为封存目录：

`D:\EPB_Data\10358-029_V2.13.0.15_0821_1750`

本次问题不是单一故障，而是三条链路叠加：

1. **报警前一圈 85992 确实发生了 DAQ 新鲜度故障。** 2026-08-21 17:33:10.808，Dev2/EPB10 的采集回调超过 100 ms 未更新，软件立即断电并将该圈封为 `AbortedBySoftwareRecovery`。这一圈的失效安全断电是合理的。
2. **85992 在反向释放过程中被中断后，系统仍自动开始了 85993。** 当前清零只能证明电气输出已经关闭，不能证明卡钳已经完成机械释放或回到下一圈允许的初始位置。因此 85993 的试验前提不完整，继续自动循环不符合预期。
3. **85993 的 `AbnormalHighCurrentPlateau` 是状态机边界缺陷造成的错误分类。** 该圈电流最终稳定在约 14.56 A，接近 15 A 目标值；但第一批有效的“冲击后”样本已经高于负载上升阈值，导致本圈空行程基线永远无法建立，状态一直滞留在 `EmptyTravel`，最终被通用“空行程高位平台”规则以 7.5 A 阈值判为硬故障。

因此应将“报警是否正确”拆开判断：

| 判断项 | 结论 |
| --- | --- |
| 在 85992 DAQ 中断且机械释放未确认的条件下，是否应停止继续自动循环 | **应停止** |
| 85993 是否有足够证据证明是“电流异常高位停滞” | **没有；报警原因分类不正确** |
| 硬故障发出后，计时器停止、DO 断电、液压释放、电源组关闭、声光报警是否执行成功 | **执行成功，停机执行链正确** |
| 整体停机逻辑是否符合预期 | **部分符合**：末端失效安全正确；前置恢复门禁、报警语义和证据落盘不符合预期 |

用户看到的两类异常 CSV 也已经定位：

- **“有波形但不是从未上电开始”**：2026-08-21 16:34:39 系统墙钟向前跳变约 1415 ms，而采样时间仍按单调时钟连续生成；圈起止边界使用新的墙钟。落盘线程按 UTC 时间比较后，把每圈前约 1.4 s 样本过滤掉。
- **“完全没有试验波形”**：85993 在实际上电约 1.4 s 后报警。其上电至报警的全部有效控制样本正好落在上述错误过滤区间内，CSV 只剩断电瞬间的电流衰减和后续零电流尾部。它不是“DAQ 完全没有采到”，而是“采到了，但在圈归属/落盘边界处被排除了”。

两个相邻 `Latest` 目录也不是两次报警，而是同一次报警停机触发了两次不同阶段的导出：第一次在快速停机时立即导出最近 10 个已完成圈；第二次在报警圈封账后再次导出，并强制包含 85993。两个目录中共同的 85983～85991 九个 CSV 的 SHA-256 均完全一致。

## 4. EPB10 报警与停机正确性

### 4.1 85993 的实际控制波形并未缺失

`adaptive-decision-timeline.csv` 中 85993 的关键样本如下：

| 上电后时间 | 电流 | 状态 |
| ---: | ---: | --- |
| 46 ms | 0.054 A | Inrush |
| 94 ms | 1.719 A | Inrush |
| 109 ms | 2.318 A | EmptyTravel |
| 141 ms | 2.054 A | EmptyTravel |
| 189 ms | 1.843 A | EmptyTravel |
| 283 ms | 2.975 A | EmptyTravel |
| 328 ms | 4.028 A | EmptyTravel |
| 531 ms | 6.926 A | EmptyTravel |
| 1044 ms | 12.973 A | EmptyTravel |
| 1233 ms | 14.548 A | EmptyTravel |
| 1373 ms | 14.552 A | EmptyTravel |
| 1404 ms | 14.546 A | Faulted |

故障窗口为 217 ms，窗口中位数 14.556 A，斜率 0.000563 A/ms。波形表现为持续上升后在目标附近形成平台，不是从空载阶段突然出现的孤立 14.5 A 异常点。

### 4.2 为什么状态没有从 EmptyTravel 进入 LoadRise

EPB10 稳定模型参数为：

- `ForwardEmptyCurrentA = 0.6135815 A`
- `ForwardEmptyMadA = 0.0251518 A`
- 正向目标电流 `15 A`

代码在 `EpbAdaptiveControl.cs:603-642` 中计算临时负载上升阈值：

```text
0.61358 + max(0.5, 4 × 0.02515) = 1.11358 A
```

但是当前实现同时要求：

1. 必须先在本圈建立 `_observedForwardEmptyA`；
2. 只有当前电流低于 1.11358 A 时才收集本圈空行程窗口；
3. 只有 `_observedForwardEmptyA > 0` 后，才允许进入 `LoadRise`。

85993 的第一条冲击忽略期后样本已经是 2.318 A，之后最低也约 1.843 A，始终没有回到 1.11358 A 以下。因此：

```text
无法收集空行程样本
    -> _observedForwardEmptyA 始终为 0
    -> 永远不允许 EmptyTravel -> LoadRise
    -> 14.56 A 平台仍被当作“空行程高电流平台”
```

随后 `EpbAdaptiveControl.cs:973-1030` 的通用高位平台规则发现状态仍为 `EmptyTravel`，并计算：

```text
abnormalThreshold = max(空行程基线 + 2 A, 目标电流 × 50%)
                  = max(约 2.614 A, 7.5 A)
                  = 7.5 A
```

于是接近目标的 14.556 A 平台被错误归类为“电流异常高位停滞”。

### 4.3 与相邻正常圈的对照

85990、85991 等相邻圈在冲击后曾下降到约 0.6～0.8 A，能够形成本圈空行程窗口，随后在电流重新超过阈值时正常进入 `LoadRise`。85993 没有出现这个回落，正好命中了状态机没有覆盖的“冲击后已直接越过负载上升阈值”边界。

已有“目标附近平台软完成”类测试通常先喂入约 1 A 的稳定空行程段，因此可以建立 `_observedForwardEmptyA`，没有覆盖本次真实序列。

### 4.4 正确性判定

#### 报警原因：不正确

14.556 A 小于 15 A 目标值，且同一时段其他正常圈也以约 14.2～15 A 的目标附近平台完成断电。现有证据不足以将 85993 定性为“异常高电流停滞”。它更准确的语义应为：

- “本圈未观察到空行程基线”；或
- “上一圈释放中断后，初始机械位置不可信”；或
- “快速进入负载，需停止并重新定位/复核”。

这类状态仍可采用失效安全断电，但不应冒充确定的电流硬件故障。

#### 停机执行：正确

一旦系统发出硬故障，实际执行链满足失效安全要求：

- 高优先级 DO 断电成功；
- 计时器停止并移除；
- Runner 移除，不再进入下一圈；
- 液压释放请求成功；
- 电源组 4 关闭；
- 通道报警和蜂鸣器均获得串口确认；
- 298 ms 后电流为 0.074 A，低于有效清零阈值 0.103 A。

需要保留一个证据边界：`PhysicalOffStatus=NotMeasured`，所以当前只能确认软件写入成功和电流代理清零，不能声称继电器触点已经通过独立反馈测量。

#### 停机前逻辑：不符合预期

85992 在反向释放阶段因 DAQ 新鲜度故障中止后，系统只确认了电流清零，没有确认机械释放完成，也没有执行重新定位/预释放后再放行下一圈。随后自动开始 85993，使该圈的起始机械条件不可信。

合理的预期应为：85992 断电后进入“待恢复/待重新定位”，完成 DAQ 重鉴定和机械释放前置条件后才允许新正式圈；如果无法确认，应保持暂停或升级为恢复故障，而不是直接继续计数。

正常参考 EPB4/84254 有 18592 个样本、时长 9.296 s，第一条电流为 0.016 A，前五条均处于未上电基线，之后才出现冲击电流。这与用户截图中的正常波形一致。

### 5.2 直接原因：同一圈使用了两个不同时间域

16:34:39 日志明确记录：

```text
Dev2 WallClockStepDetected Direction=Forward StepMs=1415.478
Dev1 WallClockStepDetected Direction=Forward StepMs=1415.521
```

采样时间线由高精度单调时钟推进，它不会跟随系统墙钟突然跳变；而 `BeginCycle`、DO 命令和圈终止边界使用跳变后的 `DateTime.UtcNow`。跳变之后两者永久相差约 1.415 s。17:33:20.871 的 Dev2 日志仍显示：

```text
到达延迟(尾)≈1443.02ms，到达延迟(首)≈1453.02ms
```

`TwoDeviceAiAcquirer.cs:3077-3085` 已经检测到了墙钟跳变，但当前处理仅调用日志函数；`TwoDeviceAiAcquirer.cs:3429-3468` 也只记录诊断信息，没有阻止新圈、重建时间映射或切换采集代际。

### 5.3 最终丢失点：落盘线程按 UTC 边界过滤

`EpbDiskWriter.cs:1247-1255` 对每批样本执行：

```csharp
while (from < to && tsUtc[from].ToUniversalTime() < state.CurrentCycleStartUtc) from++;
if (state.CurrentCycleEndUtc.HasValue)
    while (to > from && tsUtc[to - 1].ToUniversalTime() > state.CurrentCycleEndUtc.Value) to--;
```

由于 `CurrentCycleStartUtc` 已经处于跳变后的墙钟，而 `tsUtc` 仍来自连续的单调采样时间映射，前约 1.415 s 样本被判断为“早于本圈开始”并丢弃。

这也解释了两种表象：

- 对约 9～10 s 的正常圈，截掉前 1.4 s 后仍有完整的后半段，所以 CSV 从约 6 A 开始；
- 对上电约 1.4 s 即报警的 85993，整个上升过程几乎恰好都在过滤窗口内，第一条保留下来的数据已经是断电时的 14.495 A，随后立即衰减。

报警控制样本的时间戳也直接暴露了偏差：85993 的正向 DO 墙钟为 09:33:17.8399341Z，但“上电后 46 ms”的控制样本 UTC 却是 09:33:16.4481145Z，约早 1.392 s；它在单调时间上是正确的，在墙钟表示上却落到了圈开始之前。

### 5.4 为什么不是普通的 DAQ 队列丢数

报警附近的 Dev2 运行指标显示：

- Processing/Raw/Persistence 队列深度接近 0；
- `Discontinuities=0`；
- `Discarded=0`；
- `OverCapacityDropped=0`；
- Produced、Accepted、Processed、RawTransferred 等序号持续推进。

85992 确实发生过一次独立的 108.3 ms 新鲜度中断，但 85983～85991 固定缺少约 1.4 s、且 85993 的控制时间线仍完整，说明用户所见的主问题是**圈边界过滤**，不是 CSV 写入线程随机漏批或队列溢出。

### 5.5 `alarmCycleCsvAndBinComplete=false` 的含义

`alarm-metadata.json` 同时记录：

```text
alarmCycleStorageFormat = CsvOnly
alarmCycleCsvAndBinComplete = false
alarmCycleEvidenceComplete = true
```

因为配置本来就是 `CsvOnly`，没有 BIN 会使“CSV 和 BIN 均完整”字段为 false；这不是额外的 BIN 丢失故障。

但 `alarmCycleEvidenceComplete=true` 目前只表示按当前文件和样本数规则校验通过，并不代表“从未上电基线到断电尾部的语义波形完整”。85993 被错误认定为证据完整，说明完整性校验还缺少波形边界约束。

## 6. 为什么生成两批时间很接近的 Latest

### 6.1 两批目录的实际内容

第一批 `20260821_173319_336-000001`：

```text
85982, 85983, 85984, 85985, 85986, 85987, 85988, 85989, 85990, 85991
```

第二批 `20260821_173321_608-000002`：

```text
85983, 85984, 85985, 85986, 85987, 85988, 85989, 85990, 85991, 85993
```

共同的 85983～85991 九个文件逐一计算 SHA-256，结果全部相同。因此这不是两次采集，也不是两次报警。

85992 没有进入第二批，是因为它的状态为 `AbortedBySoftwareRecovery`。`GetLatestCyclesForStop` 默认只选 `completed` 和 `alarm`，仅允许“本次要求的终止圈”以其他非 running 状态强制进入；本次要求的终止圈是 85993，不是 85992。

### 6.2 两次导出的代码链

第一次导出来自 `EpbManager.cs:2637-2670` 的 `StopChannelOnAlarm`：

```text
快速停机
  -> 后台 recorder.FlushRecent(channel, 10)
  -> 此时 85993 尚未封为 alarm
  -> 导出最近 10 个 completed 圈：85982～85991
```

第二次导出来自报警快照后台链 `EpbManager.cs:2858-2867`：

```text
报警快照完成
  -> 提交报警圈终态
  -> EnsureLatestStopSnapshotAsync(channel, 85993, "AlarmStop")
  -> FlushRecentForStop(... requiredTerminalCycleNumber=85993)
  -> 导出 85983～85991 + 85993
```

`EpbDiskWriter.cs:1587` 虽然会复用“内容完全一致”的现有包，但两次圈号集合不同，所以第二次不能复用第一批，最终保留两个相邻目录。

这属于**确定性的重复导出设计问题**，不是并发偶发问题。第一批是临时视图，第二批才是包含报警终止圈的最终证据；但目录没有 `Provisional/Final` 语义，容易被误认为两次报警。

## 7. 根因树

## 8. 解决方案

### P0：统一圈边界与采样的时间域

不要再使用墙钟 UTC 判断采样点是否属于某圈。圈边界应使用与 DAQ 样本相同的单调标识，例如：

- `(DeviceGeneration, AcceptedSequence)`；或
- `(DeviceGeneration, MonotonicTicks)`；或
- 采集器提供的权威样本水位线。

建议接口语义：

```text
BeginCycle(channel)
  -> 从采集器读取 startWatermark
  -> 圈归属从该序号开始，并附带可配置的未上电预触发样本

End/Abort/AlarmCycle(channel)
  -> 取得 endWatermark
  -> 等待持久化前缀越过 endWatermark
  -> 再封账和导出
```

UTC 只用于显示、跨系统审计和目录命名，不再作为内部样本归属主键。

同时增加 200～500 ms 的每通道预触发环形缓冲，确保正式 CSV 至少包含未上电基线、上电沿和冲击电流。预触发必须同样以样本序号/单调时间归属，不能再次依赖墙钟。

### P0：墙钟跳变不能只记录日志

当 `WallClockStepDetected` 超过阈值（建议 50～100 ms）时：

1. 立即禁止受影响设备开始新圈；
2. 若有通道正在上电，按现有失效安全链断电并封为明确的时钟恢复终态；
3. 排空并切换采集 generation，重建 `Monotonic -> UTC` 映射，禁止一圈跨 generation；
4. 连续若干回调确认墙钟/采样映射偏差回到阈值内后，才允许恢复；
5. 若无法重建，保持恢复暂停并给出明确系统故障，不能继续产出“看似 complete”的 CSV。

如果不希望因系统校时中止试验，另一可行方案是整个控制、圈边界、DO 审计都使用同一个进程级 `MonotonicUtcMapper`，墙钟跳变只改变显示层，不改变运行期映射；但仍应按 generation 记录映射版本。

### P0：修复自适应状态机的“首样本已过阈值”边界

不能简单放宽 7.5 A 硬故障阈值，否则会削弱安全保护。建议显式处理基线缺失：

1. 在冲击忽略期内保留可用的低电流样本，排除冲击尖峰后尝试建立本圈空行程基线；
2. 若历史模型稳定，而第一条冲击后样本已经超过负载上升阈值，并且后续窗口呈持续正斜率，则允许进入新的 `RapidLoadRise` 或 `LoadRiseUnbased` 状态；
3. 若最终进入目标带附近的稳定平台，应优先走“目标附近平台”判定，不应因为 `_observedForwardEmptyA == 0` 就落入通用 `EmptyTravel` 高平台故障；
4. 若安全策略要求“本圈必须观察到空行程”，则应立即断电并分类为 `ForwardBaselineNotObserved/InitialPositionUncertain`，走可恢复的重新定位流程，而不是宣称 `AbnormalHighCurrentPlateau`；
5. 只有在电流明显超过目标允许上限、或有明确的无进展高负载证据时，才使用不可恢复的高电流硬故障。

必须加入精确回归样本：46 ms/0.054 A、94 ms/1.719 A、109 ms/2.318 A，之后持续上升到 14.56 A 平台。预期结果应是“快速负载上升/初始位置不可信”或目标附近停机，不得再输出 7.5 A 阈值的异常高位平台故障。

### P0：DAQ 中断后的下一圈增加机械前置条件门禁

当 DAQ 新鲜度故障发生在反向释放阶段时：

1. 立即断电并确认电流清零；
2. 将当前圈封为作废终态；
3. 通道进入 `ReleaseUnverified/PositionUnknown`，不允许计时器直接排下一正式圈；
4. 完成 DAQ 健康重鉴定；
5. 执行受控预释放或重新定位，并取得释放完成的电流/时间/位置证据；
6. 前置条件通过后才恢复正式循环，否则保持暂停并报警恢复失败。

需要明确：`ElectricalCurrentCleared=true` 只证明电气负载已经消失，不等于机械释放完成。

### P1：Latest 导出改为单一所有者和单次发布

推荐由一个 `StopSnapshotCoordinator` 统一管理，幂等键使用：

```text
RunId + Channel + FaultCorrelationId
```

报警停机时快速线程只负责断电和锁存导出请求；后台协调器等待报警圈封账及断电尾部完成后，一次性导出“最近 9 个正常圈 + 终止圈”。同一个关联号最多发布一个最终 Latest 目录。

如果现场确实要求停机瞬间立刻可见一批文件，则第一批必须显式命名为 `Provisional`，报警圈封账后原子替换/提升为 `Final`，不能留下两个语义不明的并列包。

同时建议在 Latest 包内增加 manifest：

- RunId、Channel、FaultCorrelationId；
- Trigger=`AlarmStop/ManualStop/NaturalCompletion`；
- RequiredTerminalCycle；
- CycleNumber、Status、SampleCount、SHA-256；
- Completeness=`Provisional/Final/EvidenceIncomplete`。

### P1：增加“语义完整性”校验

当前“文件存在 + 样本数一致”不足以判定波形完整。正式圈和报警圈导出前至少校验：

- 第一条样本时间不得晚于正向上电命令；
- 上电前必须有规定时长的预触发基线；
- 基线电流应接近 `PreEnergizationBaseline`；
- 必须覆盖上电沿、正向阶段、反向/终止阶段和断电尾部；
- 样本序号连续，且与 start/end watermark 一致；
- 若因时钟跳变或 generation 切换无法满足，应标为 `EvidenceIncomplete`，不得写 `alarmCycleEvidenceComplete=true`。

### P2：诊断与告警可观测性

建议新增以下字段和运行门禁指标：

- `SampleClockGeneration`、`CycleStartSequence`、`CycleEndSequence`；
- `SampleWallSkewMs`，超过阈值直接阻止新圈；
- `PreTriggerDurationMs`、`FirstSampleBeforeForwardMs`；
- `ObservedForwardEmpty=false` 时的明确原因；
- `PreviousCycleTerminalStatus`、`ReleaseVerifiedBeforeStart`；
- Latest 的 `ExportOwner`、`SnapshotState` 和幂等键。

## 9. 回归测试与验收标准

### 9.1 自动化测试

1. 运行中墙钟向前跳 1.5 s，所有圈仍从未上电基线开始，样本序号不丢失。
2. 运行中墙钟向后跳 1.5 s，不发生跨圈重复样本或倒序封账。
3. 墙钟跳变量大于报警发生时间，例如上电 1.0 s 后报警，报警 CSV 仍包含完整预触发和上升波形。
4. 精确回放 85993 的快速越阈值电流序列，不能再误报 `AbnormalHighCurrentPlateau threshold=7.5A`。
5. 反向释放阶段注入 `DaqSampleStale>100ms`，确认下一正式圈在释放/重新定位完成前不会开始。
6. 同一次报警只生成一个 Final Latest；并发调用导出也必须由幂等键合并。
7. 终止圈尚未封账、封为 alarm、封为 aborted 三种状态下，Latest 选择策略均有明确预期。
8. `CsvOnly` 模式下不得把“无 BIN”误报为证据丢失；但缺少预触发必须判为语义证据不完整。

### 9.2 封存数据验收

修复后每次报警封存应满足：

- 报警目录与 Final Latest 均包含同一终止圈；
- 终止圈 CSV 第一段是可识别的未上电基线；
- 控制时间线、DO 时间线与 CSV 可用 sample sequence 对齐，误差不超过一个采样批次；
- 不再出现固定约 1.4 s 的起点截断；
- 同一 `FaultCorrelationId` 只有一个 Final Latest；
- 报警原因能够区分“真实过流/堵转”“本圈基线未观察到”“上一圈释放未确认”和“DAQ 新鲜度故障”。

## 10. 建议实施顺序

1. **先修时间域和墙钟跳变门禁。** 这是证据可信度基础，未修前任何 CSV 波形结论都可能被边界过滤污染。
2. **再修 DAQ 中断后的机械前置条件门禁。** 避免在初始位置未知时继续正式试验。
3. **修复自适应状态转换和报警语义。** 保持失效安全断电，但避免错误归类为异常高电流硬故障。
4. **合并 Latest 导出所有权并补 manifest。** 消除同一报警的重复目录。
5. **补语义完整性校验和回归测试。** 用本次 85992/85993 数据做固定回放样本。

在以上 P0 项完成前，不建议仅通过提高 `AbnormalHighCurrentPlateau` 阈值或缩短/延长确认窗口来规避报警；那只能掩盖状态机和时间域根因，并可能削弱真正的堵转保护。
