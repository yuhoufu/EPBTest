## 3. 生命周期与预警完全解耦

### 3.1 新的双平面模型

通道现在同时维护两类互不覆盖的信息：

- `ChannelRuntimeStateChangedEvent`：唯一生命周期事实；
- `ChannelWarningOverlayChangedEvent`：可显示、可清除的软预警覆盖层。

预警不再通过 `PublishChannelRuntimeState` 发布。运行界面在保留 `Learning/Qualification/Recovering/Running` 主状态的同时附加“预警”文本和橙色提示。启动、完成和锁存终态会清除旧覆盖层。

`ResolveRuntimeStateForRunnerWarning` 现在保留原生命周期；正式运行中的软预警也不再切换到 `WarningRunning`。旧枚举只保留兼容读取，不再作为新预警发布入口。

### 3.2 恢复 owner 结构化

每条 `Recovering` 生命周期现在包含：

- `RecoveryOwnerKind`；
- `RecoveryOwnerId`；
- `RecoveryOwnerGeneration`；
- `RecoveryTargetPhase`；
- `SourceStateRevision`；
- `RunId + RunEpoch`。

首次进入 `Recovering` 必须显式提供 owner。缺失时会发布 `Unknown` 并记录 `RecoveryOwnerMissing`，使监督逻辑安全失败；同一恢复事务的后续更新只能继承上一条完整结构化 owner，不能从原因文本猜测。

`SourceStateRevision` 在同一个 owner 事务内保持稳定，避免恢复过程自身的状态刷新生成新的事故键。

## 4. 阶段路由与单一恢复所有权

### 4.1 阶段路由规则

- `Startup/Learning/Qualification`：只允许返回批次生命周期 owner；
- `Formal` 且 `FormalPhaseCommitted=true`：才允许受影响组复位和共享未来正式槽重入；
- owner 丢失或硬期限到达但仍处于预正式阶段：转入安全终态，不得“猜测”进入正式阶段。

学习期软预警完成安全断电、机械释放和数据截止后，会显式检查生命周期。只有已提交正式阶段且当前仍为 `Running` 的通道才能走正式软预警重入；学习/资格状态只交回原批次 owner。

### 4.2 受影响组复位入口零副作用门禁

`ExecuteAffectedGroupResetAsync` 在任何停止、断电、DAQ 重建、液压或电源动作之前同时验证：

1. `TargetPhase == Formal`；
2. 正式阶段已经提交；
3. `RunId/RunEpoch` 仍是当前运行；
4. 请求通道处于 `Recovering`；
5. owner 有效且 `OwnerGeneration == RunEpoch`。

任一条件不满足时只记录 `AffectedGroupResetRejected` 并返回，入口保持零副作用。

### 4.3 singleflight 去重键

恢复健康检查的事故键调整为：

```text
(RunId, RunEpoch, HydraulicGroup, SourceStateRevision, RecoveryTargetPhase)
```

同一现场异常即使被多个定时检查同时看到，也只能登记一个恢复升级任务；新运行、新源状态或不同目标阶段会生成新键，不会被旧事故永久吞掉。

## 5. 终态执行代际栅栏

### 5.1 每通道不可复用许可

新增 `ChannelExecutionFence`。每个通道的新运行在安全预检完成后取得：

```text
Channel + RunEpoch + Generation + Authorized + RevocationToken
```

自然完成、人工停止、报警、启动受阻和整批停止都先撤权，再提交终态。撤权同时：

- 递增 Generation，使全部旧副本失效；
- 取消 `RevocationToken`，打断在途硬件副作用；
- 取消相关通道/液压组恢复 owner；
- 移除并停止 Runner/Timer。

### 5.2 Runner 与 Timer 创建门禁

`GetRunner` 和 `GetTimer` 在每通道执行 gate 内完成以下原子检查：

- 通道启用且不处于终态；
- 不要求进程重启；
- permit 属于当前 RunEpoch/Generation；
- 创建前后 permit 都有效。

Runner 实例绑定创建时 permit，不能重新绑定到新代。旧异步任务即使持有旧 Runner 引用，也只能携带旧 permit 调用 DO/液压入口，因此无法借用新运行授权。

### 5.3 硬件副作用取消链

以下入口在执行前验证同一 permit，并把撤权 token 链接到硬件调用：

- 正向/反向 DO ON；
- 单通道和组液压 Generation 进入；
- 程控电源 `PrepareAndEnableAsync`；
- 受影响组恢复所有权等待及各阶段 deadline；
- 正式组共享槽重新加入。

终态发生后，新的上电/建压被拒绝，进行中的可取消调用收到取消；迟到返回还会再次校验 permit，必要时立即安全释压。

## 6. Watchdog 行为

### 6.1 严格终态契约保持不变

没有放宽或延长 `ChannelTerminalResourcesActive` 判定，也没有忽略 `StartBlocked + Runner`。人工注入真实终态资源泄漏时，Watchdog 仍应按原安全契约接管。

### 6.2 逐通道恢复 owner

Watchdog 心跳契约修订为 revision 2，并为每个通道携带显式恢复 owner、目标阶段、源状态 Revision 和预警覆盖层字段。`Recovering` 只有在 owner 与当前 RunEpoch 匹配时才算有合法恢复覆盖；全局恢复任务数量不能替代本通道 owner。

旧 revision 1 心跳仍兼容解析，相关传输回归已通过。

### 6.3 相同失败指纹熔断

独立 Watchdog 已保存恢复失败分类、指纹、连续次数和阻断时间。永久失败或同指纹达到有界次数后进入 `SafeIdleRecoveryBlocked`，禁止继续拉起完整主程序；人工停止、会话撤权和已持久化阻断均会在后续启动中保留正确语义。
