## 2. 修复后的总体行为

| 场景 | 修复前 | 修复后 |
|---|---|---|
| Windows 时间前跳/后跳 | `DateTime.Now` 与 DAQ 样本 UTC 比较，合法峰值窗可能被判失效 | 只用同一 DAQ generation、batch sequence 和 `Stopwatch` 单调时钟判定；墙钟仅显示 |
| 后台峰值处理延迟 120～250 ms | 固定最多等待 100 ms，误判 `CutoffNotCovered` | 排空预算下限 250 ms，并按 DAQ 批周期扩大，最大 1000 ms |
| 正式圈控制返回 `SoftwareRecovery` | 只置 `Recovering` 和 OFF，Timer/Runner 仍可能存在 | 首错立即暂停并移除 Timer、取消圈 token、移除 Runner、退出液压参与者，再执行有界恢复 |
| 局部恢复持续失败 | 旧圈可能继续重复物理动作，计数不前进 | 同液压组隔离恢复最多 3 次；仍失败则打开整批软件恢复熔断并交给无人值守回收 |
| Watchdog 恢复子进程启动失败 | `RequestExternalRecovery` 后普通 `Close`，被 `ApplicationClosing` 撤权 | 发送 `RecoveryAttemptFailed`；保留 session/checkpoint，退出后由 Sidecar 退避重试 |
| 普通批量启动失败 | 错发 `RunStopped` 并销毁 Watchdog session | 发送 `BatchStartFailed`；监控保持有效，Sidecar 安全接管并重试 |
| 程序有物理动作但圈数长期不变 | 仅靠 UI 状态和恢复阶段，可能长期假运行 | Watchdog 监督正式圈耐久计数；Timer/Runner/上电存在但超过 `max(90s, 4×周期+30s)` 无进展即接管 |
| 人工停止后重新开始 | 历史持久化/逻辑诊断可能继续阻挡新批次 | 已确认电机 OFF 与电源 OFF 即允许重新执行完整实时预检和学习；不复用旧运行对象 |

## 3. P0：峰值证据改为单调时钟水印

### 3.1 新的正确性模型

新增 `IO.NI/PeakCaptureWatermark.cs`。每个峰值捕获窗固定以下身份：

- DAQ device；
- DAQ generation；
- 捕获开始时的 accepted sequence；
- 捕获开始的 `Stopwatch.GetTimestamp()`；
- 截止时 accepted sequence；
- 截止 `Stopwatch` tick；
- 后台已处理 sequence 和已处理到的单调 tick；
- 最后纳入峰值的样本单调 tick。

样本只有在以下条件同时满足时才进入峰值统计：

1. 样本 generation 等于捕获 generation；
2. 样本单调 tick 不早于捕获开始；
3. 冻结后，样本单调 tick 不晚于截止点。

截止覆盖成立必须同时满足：

```text
same generation
AND processed sequence >= cutoff accepted sequence
AND processed monotonic tick >= cutoff monotonic tick
```

因此 NTP、Windows Time Service、手工校时、虚拟化宿主校时造成的 `DateTime` ±1.5 秒跳变，不再改变样本归属和截止覆盖结果。

### 3.2 DAQ 批次单调时间传递

`TwoDeviceAiAcquirer.Item` 新增 `BatchEndMonotonicTicks`，直接承接 `ClockDisciplinedSampleTimeline` 的同域批尾单调时间。后台逐样本扫描按有效采样率从批尾反推每个样本 tick，不再用 `DateTime` 做正确性过滤。

`PeakCaptureToken` 和 `PeakCaptureResult` 增加 generation、sequence、monotonic watermark 与 `EvidenceTailLagMs`。控制层优先使用 `EvidenceTailLagMs`；UTC 尾差只保留为旧结果兼容分支。

### 3.3 排空预算

`SelectPeakDrainTimeoutMs` 采用：

```text
min(1000ms, max(250ms, 请求排空时间, 4×DAQ批周期+50ms))
```

`cutoffAfterDelay=true` 时，原 `delayMs` 仍只定义统计窗口；冻结后另行等待排空，不会把统计窗口扩大到断电后。

## 4. P0：正式圈软件自恢复执行权撤销

`ReportFormalControlSoftwareRecovery` 和正式圈持久化恢复入口统一执行以下顺序：

1. Pause 当前 Timer；
2. Cancel 当前圈 pause/cycle token；
3. 从运行表和缓存表移除 Timer；
4. 从运行表和缓存表移除 Runner；
5. 取消液压参与者身份；
6. 提交高优先级 OFF；
7. 请求液压释放；
8. 发布 `Recovering`；
9. 调度同液压组隔离恢复。

新的强制不变量为：

```text
ChannelState == Recovering
=> 旧 Timer 不得继续触发新圈
=> 旧 Runner 不得继续持有执行权
=> 旧 cycle token 已取消
=> 通道不再是液压参与者
=> OFF 已提交；未确认时进入电源组安全恢复
```

局部恢复使用现有 `ScheduleIsolatedInfrastructureRecovery`，按 RunEpoch 和液压组去重，前两次局部恢复，第 3 次仍不能闭环时转入 `SoftwareRecoveryCircuitOpen`，执行统一 StopAll/整批回收。恢复任务使用首次事故硬期限，不允许异常重新登记无限延长。

这直接消除了截图中的矛盾状态：所有通道显示 `STOP/系统自恢复`，但 Timer/Runner 仍在、曲线继续动作且正式圈数不增加。

## 5. P0：Watchdog 可重试失败协议

### 5.1 新消息

协议新增两个非终态消息：

- `BatchStartFailed`：普通开始/预检失败；
- `RecoveryAttemptFailed`：已附着的恢复子进程接管或启动失败。

`WatchdogLifecyclePolicy` 明确：

- 上述两类消息是 retryable failure；
- 不是 `RunStopped`、`RunCompleted`、`ApplicationClosing` 或 `ShutdownExpected`；
- 不创建 session revocation marker。

### 5.2 恢复子进程失败

`ResumeWatchdogRunAsync` 捕获失败后：

1. 将监控窗标记为 Watchdog retry exit；
2. 发送 `RecoveryAttemptFailed`；
3. 保留 checkpoint 和 Sidecar 授权；
4. 执行安全关闭，但跳过普通 `ApplicationClosing` 撤权；
5. Sidecar 等待进程退出后按 5s、15s、30s、60s 退避重新启动。

即使程控电源暂时离线，也不会因为恢复子进程自身关闭而永久终止无人值守恢复链。

### 5.3 普通批量启动失败

普通 `StartNewBatchAsync` 失败不再调用 `NotifyRunStopped`/`ShutdownLocalClient`，而是发送 `BatchStartFailed`。Sidecar 收到后执行安全接管并使用已绑定的运行检查点重试；当前监控界面在接管开始前保持可见并输出明确的“自恢复”提示。

人工取消仍属于明确终止路径，继续使用原人工停止/停止完成协议。

## 6. P1：正式圈进展不变量

Watchdog heartbeat 新增：

- `CompletedCycleCount`：所有 EPB 已提交正式圈累计值；
- `ExpectedCyclePeriodMs`：配置周期；
- `EnergizedChannelCount`：控制层权威上电掩码计数。

Sidecar 使用进程内 `Stopwatch` 记录最近一次正式圈计数变化。满足以下条件时触发整批接管：

```text
RunActive
AND Phase == Formal
AND (TimerCount > 0 OR RunnerCount > 0 OR EnergizedChannelCount > 0)
AND 有可恢复通道
AND CompletedCycleCount 在 timeout 内无变化
```

其中：

```text
timeout = min(3600s, max(90s, 4×ExpectedCyclePeriod + 30s))
```

15 秒现场周期的接管门限为 90 秒；60 秒周期自动放宽到 270 秒，避免长周期合法运行误触发。

`LogicalQuiescenceSnapshot.IsQuiescent` 也已加入 `EnergizedChannelCount == 0`，不再允许“Timer/Runner 已清空但仍上电”被误判为逻辑静止。

## 7. P1：停止后重新开始与电源通信

### 7.1 显式停止后的新批次

`CanDiscardHistoricalStopChecksForExplicitRestart` 修正为只在以下条件成立时放宽上一批历史诊断：

```text
explicitlyStopped
AND MotorOffCommandSucceeded
AND PowerOffConfirmed
```

压力、历史持久化和旧逻辑清场问题保留为诊断，但新批次仍必须重新执行 DAQ、电源、液压和学习预检。电机或电源 OFF 未确认时绝不放行。

### 7.2 程控电源与 StopAll

当前工作区的电源安全关闭链已纳入本次编译和测试：

- OFF owner 不继承 UI 取消令牌；
- 电源 Gate、遥测退出、单组 OFF、全部组 OFF 均有独立硬截止；
- 断线、无连接回读、OUTP 回读不一致均不能伪装为关闭成功；
- 超时旧 owner 被退休，旧客户端被丢弃，新恢复使用新连接；
- `Task.WhenAny` 后继续观察迟到 I/O fault，避免 `UnobservedTaskException`；
- StopAll 先撤销上电授权并提交全部高优先级 DO OFF，再等待电源、DAQ、Raw/SQLite 和逻辑清场；
- StopAll 总硬期限为 15 秒，超时结果明确要求外部恢复，不复用永不完成的旧 Task。

## 10. 现场发布验收

自动测试不能替代真实 NI DAQ、程控电源、液压和 Windows 校时环境。发布前必须完成以下门禁：

1. 在试验空载或台架安全模式注入 Windows 时间前跳、后跳各 1.5 秒，确认没有 `FullRatePeakInvalid/CutoffNotCovered` 风暴；
2. 人工制造 120、180、250 ms 后台处理延迟，确认峰值窗正常封口且圈数继续；
3. 注入一次正式控制 `SoftwareRecovery`，确认首错后该通道 `Timer=False、Runner=False、Energized=False`，且仅产生一个作废圈；
4. 连续让局部恢复失败，确认第 3 次转整批回收，不产生重复物理圈；
5. 恢复启动时断开一个程控电源，确认 session 不撤权、Sidecar 持续退避重试；恢复电源后无需人工重启即可重新学习并续测；
6. 普通开始预检失败时确认监控界面保留、自恢复提示可见、Watchdog session 未变成 `RunStopped`；
7. 注入正式计数冻结但保留 Timer/Runner 的故障，确认达到自适应门限后 Sidecar 接管；
8. 人工“暂停→停止→开始”，确认电机/电源 OFF 后可以建立全新运行对象，不复用旧 Timer/Runner；
9. 连续运行至少 48 小时，核对 UI 圈数、SQLite 成功圈、Watchdog `CompletedCycleCount` 三者一致；
10. 封存 `WatchdogSessions`、项目日志、DAQ diagnostics、SQLite integrity check 与最终版本哈希。
