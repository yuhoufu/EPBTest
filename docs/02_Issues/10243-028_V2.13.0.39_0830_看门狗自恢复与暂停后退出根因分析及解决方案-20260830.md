# 10243-028 V2.13.0.39 看门狗自恢复与暂停后退出根因分析及解决方案

分析日期：2026-08-30  
数据包：`D:\EPB_Data\Backups\10243-028_V2.13.0.39_I0003_0830_1803`  
看门狗会话：`7f64816d6365472cbb171d80f8534acc`  
初始进程：PID 6732；恢复进程：PID 15836  
时间口径：正文使用现场本地时间 UTC+8；看门狗 JSON 中的 UTC 时间已统一加 8 小时。

## 1. 结论摘要

### 1.1 第一次自动恢复为什么发生

第一次自动恢复包含两个层次，必须分开：

1. **最先发生的业务异常**是 Dev1 的 DAQ 回调中断。15:54:02.197 时 Dev1 样本年龄已达 `948.032 ms`，而 Dev2 只有 `7.696 ms`；随后液压组 1 报 `HydraulicSampleStale`。当时压力值是 `71.253 bar`，高于最低要求 `60.000 bar`，只是样本已陈旧 `1111.7 ms`。因此这不是“液压真的掉到低压”，而是 Dev1 数据没有按时更新。
2. **最终让看门狗杀旧进程并重启的直接原因**不是 DAQ 空窗本身，而是全局安全停止事务的 `FreezeActiveWork` 阶段超过 2 秒硬截止，Watchdog 记录 `StageDeadlineExceeded:FreezeActiveWork` 后接管。物理断电实际已经很快成功：各通道 DO OFF 多数在约 `0.5～7.5 ms` 完成，4 个电源组在 15:54:02.519～.577 已关闭。

完整链路为：

```text
Dev1 DAQ 回调空窗
  -> 液压组1压力样本陈旧（实际压力仍高于最低值）
  -> EPB4/5 正式槽持久化边界未闭合
  -> FormalSlotSafetyBoundaryFailed，整批撤权并 StopAll
  -> FreezeActiveWork 超过 2 秒逻辑阶段截止
  -> Watchdog 接管、抓转储、终止 PID 6732
  -> 15 秒退避后启动 PID 15836
  -> 恢复预检、重新学习 10 圈、正常续跑
```

所以，要从根上避免“不必要的进程重启”，不能只调大 DAQ 阈值或看门狗等待时间，必须同时处理：

- Dev1 回调空窗的底层来源；
- 同一个 DAQ 事件被液压、正式槽、通道自愈多层重复放大的故障所有权问题；
- 已完成物理断电时，逻辑冻结阶段超时仍被永久升级为进程重启的问题。

### 1.2 暂停后的电源3异常是不是退出原因

**不是。** 电源3在 18:03:12.844 的异常是一次 `SOUR:CURR?` 响应行超时：收到 4 字节后未在 1500 ms 限期内得到完整响应行。程序把它正确归类为“通信降级”，配置要求连续 8 个正式动作槽无成功遥测才升级故障；18:03:12.859 已重新连接，18:03:13.864 已再次成功遥测。日志还明确写了“继续监控，不触发停机”。

同一时间窗中电源2遥测耗时 `2443.9 ms`、电源4耗时 `1548.2 ms`，Dev1/Dev2 同时出现 DAQ 空窗，看门狗命名管道也写超时。证据更符合一次**主程序或系统层面的共同执行停顿/调度空窗**，而不是只有电源3硬件独立失效。现有数据不足以在 GC 停顿、线程池/锁竞争、驱动调度、系统瞬时停顿之间继续唯一归因。

### 1.3 “自动恢复已阻断”的真正原因

“自动恢复已阻断”是一个确定的软件状态机缺陷，与电源3通信降级没有因果关系：

- PID 15836 最初由看门狗以“恢复进程”身份启动；其恢复许可后来已进入 `Committed`。
- 18:03:11.874 命名管道断开后，仍存活的同一个 PID 15836、同一个进程启动时间重新连接。
- 代码已经识别它为 `sameAuthorityReconnect`，但随后仍因为 `RecoveryProcess=true` 再次调用只允许 `Started/Attached` 状态的一次性恢复许可校验。
- 持久许可已经是 `Committed`，于是必然得到 `RecoveryAttachPermitIdentityMismatch`，继而打开恢复熔断并显示“自动恢复已阻断”。

也就是说，**把“这个进程最初从哪里启动”误当成了“本次 Attach 是新恢复进程还是同一进程重连”**。运行两个多小时后的正常恢复进程，只要命名管道重连，就可能稳定复现这个错误。

### 1.4 “停止自动恢复”是软件还是人工执行

结论明确：**停止动作由人工点击恢复过渡窗口中的红色按钮发起，最终终止由软件按该人工指令执行。**

证据如下：

- 18:03:32.703，Sidecar 记录：`OperatorCanceledAutomaticRecovery`，`Reason=TransitionWindowButton`，并把 `ManualStopRequested` 置为 `true`。
- 源码只有恢复窗口按钮 Click 事件会把标题改成截图中的“正在停止自动恢复”。
- 点击后软件等待最多 15 秒让主程序自行全断能退出；18:03:48.006，Watchdog 终止仍存活且身份匹配的 PID 15836。
- 会话最终终态是 `OperatorCanceledRecovery`，原因是 `OperatorCanceledAutomaticRecoveryFromTransitionWindow`。

对应源码为 `MTTFTest.Watchdog/RecoveryTransitionWindow.cs:218-227` 和 `MTTFTest.Watchdog/WatchdogHost.cs:3978-4030`。

责任拆分如下：

| 环节 | 责任主体 | 结论 |
| --- | --- | --- |
| 暂停试验 | 人工点击暂停 | 正常业务命令 |
| 自动恢复阻断 | 软件缺陷 | 同一恢复进程重连被一次性许可错误拒绝 |

## 4. 第一次事件的根因分层

### 4.1 已确认根因 A：DAQ 数据陈旧被误读为液压业务失败链的入口

`HydraulicSampleStale` 的分类本身是正确的，保护动作也应保留。但同一根 DAQ 空窗同时触发：

- DAQ 新鲜度断电；
- 液压释放/关闭作用域异常；
- 正式槽持久化边界失败；
- 通道自愈及电源组失效安全请求；
- 全局 `StopAll`。

这些层各自安全，但缺少统一 Incident 所有权和单一终态，造成“一个短空窗、多个恢复 owner、多个停止请求”的级联放大。日志中同一窗口出现旧执行代次、重复电源组 OFF、通道恢复和正式槽失败，正是该问题的表现。

### 4.2 已确认根因 B：逻辑冻结阶段超时覆盖了已完成的物理安全事实

当前安全停止顺序已先执行 `AdmitAndSubmitSafety`，同步撤权并提交 DO OFF/电源 Disable，然后进入 `FreezeActiveWork`。但 `FreezeActiveWork` 的 2 秒截止仍是强终态：一旦超时，Watchdog 按“需要进程接管”处理，即使物理 OFF 已完成。

该阶段声称是非阻塞 producer barrier，但实现仍同步遍历 Timer，并调用 `CancelCyclePauseCts`、`CancelStopCts`。`CancellationTokenSource.Cancel()` 可同步执行注册回调，Timer.Pause 也可能遇到锁或观察者链，因此“代码意图非阻塞”不等于运行时有界。本次能确定卡在该阶段，现有延迟抓取的 dump 不能再确定具体卡在哪一个 Timer、CTS 回调或锁。

相关源码：

- `Controller/EpbManager.StopSafetyOperations.cs:248-266`：立即物理安全边界；
- `Controller/EpbManager.StopSafetyOperations.cs:296-377`：`FreezeActiveWork` 及同步 Timer/CTS 操作；
- `Controller/EpbManager.StopSafetyHardening.cs:90-92,313-320`：该阶段硬截止为 2000 ms；
- `Controller/StopSafetyTransactionRunner.cs:720-729`：阶段超时固化为 `StageDeadlineExceeded:<stage>`；
- `Controller/EpbManager.BatchStart.cs:3673-3706`：正式槽边界失败直接撤销整批授权并发起 `StopAll`。

### 4.3 尚未闭合的底层根因：为什么 Dev1 回调会中断

当前证据只能定位到 Dev1 的采集回调路径，不能唯一指向 NI 设备、总线、驱动或主程序调度：

- 15:54 起点时 Dev2保持新鲜，反对“整机CPU/磁盘全面卡住”作为该次起点；
- Dev1在 15:29、15:54 以及恢复后的运行中均有约1.16～1.17秒级空窗，具有重复性；
- DAQ队列深度、持久化队列和异步日志没有显示积压；
- 数据包没有 NI-DAQmx 驱动事件、设备总线重置、Windows事件日志或回调线程 ETW。

因此不能把“更换DAQ硬件”“更新驱动”或“调大阈值”写成已证实结论，需要先补充针对性取证。

## 6. 恢复阻断的软件缺陷

### 6.1 代码路径

1. `MTTFTest.Watchdog/WatchdogHost.cs:1709-1780` 已能比较 Session、PID、进程启动时间和连接代次，并把同一存活进程的新管道识别为 `sameAuthorityReconnect=true`。
2. 但 `WatchdogHost.cs:1031-1046` 随后只看 `message.Session.RecoveryProcess == true`，无条件再次调用 `TryCommitAttachedPermit`。
3. `WatchdogHost.cs:3289-3310` 只接受恢复许可状态为 `Started` 或 `Attached`；已正常提交为 `Committed` 的许可返回 `RecoveryAttachPermitIdentityMismatch`。
4. 失败后代码立即打开永久恢复阻断并发送 `DurableRecoveryBlocked`。
5. 即使跳过上述错误校验，`WatchdogHost.cs:1146-1154` 仍会因为永久的 `RecoveryProcess=true` 再次激活并显示“主程序已重新启动”过渡窗口；同权威传输重连也必须跳过这段首次恢复 UI 逻辑。

现有“真实 Sidecar 同权威重连”测试只覆盖普通父进程，未覆盖“恢复进程 + 许可已 Committed + 同PID重连”组合，因此这个缺口没有被测试捕获。

### 6.2 最小正确修复

Attach 处理应按本次连接性质分流：

```csharp
if (sameAuthorityReconnect)
{
    // 必须再次严格确认 Session、PID、ProcessStartUtcTicks、当前权威和存活性。
    // 如果原进程来自恢复启动，还应确认 durable record 中的 ProcessId/Start 相同。
    // 这是传输重连，不得重新消费或提交一次性恢复许可。
}
else if (message.Session?.RecoveryProcess == true)
{
    // 只有新的恢复进程首次 Attach 才校验 Started/Attached 并提交许可。
    TryCommitAttachedPermit(...);
    // 也只有这个分支可以激活“主程序已重新启动”的恢复过渡窗口。
}
```

安全要求：不能简单地“允许 Committed 状态的任何恢复进程 Attach”。豁免只适用于 Session、PID、启动时间、当前权威、恢复许可进程身份全部相同且进程仍存活的重连；随后仍应等待该连接的第一条新鲜 Heartbeat，再取消传输接管观察。

更彻底的模型修正是拆开两个字段：

- `ProcessOrigin = Initial | WatchdogRelaunch`：进程来源，生命周期内不变；
- `AttachPurpose = InitialAttach | SameAuthorityReconnect | NewRecoveryAuthority`：本次连接目的。

不得再使用永久的 `RecoveryProcess` 标志决定每一次连接是否要消费一次性恢复许可。

## 7. 彻底解决方案

### 7.1 P0：先消除“暂停后退出”的确定软件问题

1. **修复同权威恢复进程重连**：按 6.2 分流，`Committed` 后相同 PID/Start 的新管道必须作为 transport reconnect 接受，且不得重新激活首次恢复过渡窗口。
2. **增加精确回归测试**：真实 Sidecar 启动恢复进程，依次走 `Started -> Attached -> Committed`，强制断开管道后以相同 PID/Start 重连；期望 `AttachedReconnectValidated`，禁止出现 `RecoveryAttachRejected`、`SafeIdleRecoveryBlocked` 和进程终止。
3. **覆盖暂停场景**：在 `ManualPausePending` 和最终 `Stage=4` 两个时点分别强制管道重连；暂停必须完成，进程必须保持存活，按钮回到“继续试验”。
4. **恢复窗口防误操作**：
   - “关闭提示”和“终止主程序”必须拆成两个动作；
   - 终止动作明确显示“将退出试验软件”，并二次确认；
   - 当耐久暂停记录已经 `Stage=4` 且主进程存活时，默认动作应是“保留主程序并关闭恢复提示”，不得把关闭窗口等同于杀进程。
5. **阻断态的防御性降级**：若当前权威进程仍存活且暂停安全证据持续推进，恢复许可异常只阻止“新进程拉起”，不得同时打断当前主程序的暂停收口。

### 7.2 P0：避免短 DAQ 空窗升级为不必要重启

1. 为同一个 DAQ gap 建立唯一 `IncidentId` 和唯一恢复 owner；液压、正式槽、电源、通道层只发布症状和安全 receipt，不得各自再发起全局恢复。
2. 正式槽终态应区分：
   - `SafeCommitted`：安全与持久化都完成；
   - `SafeAborted`：OFF和液压安全已确认，本圈因软件/DAQ异常作废，未来完整圈重试；
   - `SafetyUnproven`：OFF、压力安全或持久化是否半提交无法证明，才升级全局 StopAll。
3. 本次 `MotorOff=True`、`HydraulicReleased=True`、`Persistence=False` 不应立即等价于“进程必须重启”。先以事务化作废标记闭合该槽，只有无法判断数据库是否半提交时才进入 `SafetyUnproven`。
4. 保持250 ms新鲜度断电门槛，不建议用调大门槛掩盖空窗；保护门槛与进程重启策略应解耦。

### 7.3 P0：修复 `FreezeActiveWork` 有界性

1. 将 Timer.Pause 和 CTS Cancel 的所有用户回调从2秒硬阶段移出；硬阶段只做原子撤权、状态置位、DO OFF/PSU Disable提交和无回调的取消标志发布。
2. 为每个 Timer.Pause、每个 CTS Cancel 记录单独的开始/结束/耗时、通道和回调数量，超时后能直接指出卡点。
3. 逻辑清理采用 quarantine：物理OFF已确认时，迟到的逻辑 owner 只能完成收口，不能重新上电；其超时显示为“设备已安全，后台收口异常”。
4. `FreezeActiveWork` 迟到但物理安全 receipt 已完成时，不得永久污染同一进程的后续停止请求；新的 ManualUi/Watchdog 停止应得到新的幂等 OFF receipt 和独立预算。
5. Watchdog 接管条件必须同时考虑“无物理安全证据”和“无实质进展”；仅逻辑阶段超过2秒、而OFF已证实时，先隔离逻辑 owner，不应立即杀进程。

### 7.4 P1：定位并降低共同执行停顿

1. 增加每秒诊断：.NET GC代次、单次GC pause、线程池 active/pending/available、锁等待、最终器队列、进程挂起时间、Sidecar读循环延迟。
2. 在 DAQ 双设备同时空窗、电源多组慢查询或管道超时任一条件出现时，自动启动30秒 ETW 环形取证，至少包括 CLR GC/Threading、CPU sampling、File/Network、NI回调线程ID。
3. 电源遥测使用独立长生命周期工作线程/调度器，不与暂停收口、看门狗发送或 DAQ恢复共享可能耗尽的线程池路径。
4. 暂停开始后优先取消在途非安全 SCPI 遥测，先执行 DO OFF 和电源 OFF；普通 `SOUR:CURR?` 查询的迟到结果不得占用安全命令串行门。
5. 保留现有1500 ms单事务超时和8个正式槽确认门，不建议仅通过加大超时消除报警；它只会延后发现共同停顿。

### 7.5 P1：补齐 Dev1 DAQ 底层取证和现场排查

1. 每次回调空窗记录 NI 任务状态、设备名/序列号、任务代次、回调线程ID、最近 NI 错误、系统单调时间与硬件采样时间差。
2. 在现场导出 NI-DAQmx/NI MAX 设备自检、驱动版本、Windows系统事件和设备总线重置记录。
3. 核查 Dev1 设备供电、数据线、接插件、屏蔽接地及所在 USB/PCIe 链路；若是 USB，再核查选择性挂起和集线器省电。是否更换硬件应以设备重置/自检或换位复现结果决定。
4. 做 Dev1/Dev2 物理链路对调试验：若空窗跟随设备/线缆，偏硬件链路；若始终留在逻辑 Dev1 任务，偏驱动/任务配置/软件路径。

### 7.6 P1：电源3专项排查

1. 对 `192.168.1.103:2268` 做持续带时间戳的 TCP/SCPI 抓包，确认4字节后缺失的是终止符、剩余载荷还是本机读取调度。
2. 同步记录交换机端口错误、网卡丢包/重传、ARP变化、网卡节能状态和电源控制器服务日志。
3. 比较 PSU2/3/4 同窗事务：如果多个独立端点同时变慢，优先查主机调度和公共网络；只有 PSU3 独立重复时再查其控制器、线缆和端口。
4. 单次降级恢复后清晰显示“通信已恢复”，避免操作员把已恢复的电源告警误认为恢复阻断或即将退出。

## 8. 验收用例与通过标准

### 8.1 自动化测试

| 用例 | 注入 | 必须结果 |
| --- | --- | --- |
| 恢复进程已Committed后重连 | 相同Session/PID/Start，新管道代次 | 接受重连；无恢复阻断；进程不退出 |
| 伪造恢复进程重连 | PID或Start或许可进程身份不同 | 拒绝连接并保持fail-closed |

| 双DAQ 1.5～2.5秒共同空窗 | 同时阻断回调并恢复 | 在途圈安全作废；暂停意图优先；不改变为退出意图 |

### 8.2 现场验收

1. 使用受控、工作区干净且 `PackageApproved` 的 x86 Debug/正式发布包。
2. 连续运行至少24小时，覆盖多次暂停/继续；建议最终做48小时无人值守耐久。
3. 人工注入至少10次电源遥测超时、10次单DAQ空窗、5次双DAQ共同空窗、10次命名管道断开重连。
4. 通过标准：
   - `RecoveryAttachPermitIdentityMismatch = 0`；
   - 同权威重连成功率100%；
   - 暂停命令最终均为 `Stage=4` 且进程存活；
   - 未经人工明确确认，`OperatorCanceledAutomaticRecovery = 0`；
   - 已确认物理安全时，`StageDeadlineExceeded:FreezeActiveWork` 不再触发进程重启；
   - 所有作废圈不增加正式完成数，恢复后计数与SQLite一致；
   - Dev1回调空窗若仍存在，必须有可归属到驱动、设备、调度或GC的诊断证据。

## 9. V2.13.0.39 现场临时处置

在修复版本发布前：

1. 暂停后若出现“自动恢复已阻断”，先确认界面输出全OFF以及 `WatchdogSessions\session-<id>.manual-pause.json` 是否已达到 `Stage=4`。若希望保留软件继续观察或稍后继续试验，**不要点击“停止自动恢复并关闭”**；该按钮会在最多15秒后终止主程序。
2. 单次电源3通信降级且随后出现“已连接/遥测成功”时，不应直接重启电源或更换硬件；先保存日志和通信抓包。
3. V2.13.0.39 不适合在无人值守场景继续长期使用：恢复进程一旦发生传输重连，存在确定的恢复阻断缺陷。
4. 不要通过关闭DAQ新鲜度保护、取消压力样本时效检查或无限加大超时绕过问题，这会降低安全边界而不能修复状态机。

## 10. 转储分析边界

`MTTFTest_6732_20260830_075420_604.dmp` 没有异常流，包含58个线程；抓取时多数线程停在系统等待函数。转储是在 Watchdog 接管约15秒后生成，已错过 `FreezeActiveWork` 刚超时的瞬时栈，而且当前包未附匹配PDB和完整托管堆。因此它只能证明进程当时仍存活，不能从现有转储唯一指出哪一个 Timer、CTS 回调或锁造成2秒超时。

修复版需要把“阶段内每个子操作耗时”直接写入 Watchdog journal，并在阶段截止瞬间抓取带托管栈和匹配符号的转储，才能闭合该最后一层定位。

## 11. 最终判断

- 第一次自恢复是安全机制成功兜底，但属于可避免的软件级联：Dev1短时DAQ空窗被放大为正式槽失败，随后逻辑冻结超时触发进程重启；物理断电并未失败。
- 第二次电源3通信异常是同一共同停顿窗口中的暂态症状，已自动恢复，不是恢复阻断或软件退出的根因。
- 恢复阻断是 `RecoveryProcess + Committed许可 + 同权威重连` 未覆盖的软件状态机缺陷。
- 本次“停止自动恢复”由人工点击按钮发起；软件只是执行该人工请求并最终终止进程。
- 要做到“暂停就是暂停，不退出软件”，首要交付是修复同权威恢复进程重连、拆分恢复窗口的关闭与退出动作，并增加 `ManualPausePending/Stage=4` 下的端到端故障注入测试；随后再治理 DAQ 事件所有权、Freeze有界性和共同执行停顿的底层诊断。
