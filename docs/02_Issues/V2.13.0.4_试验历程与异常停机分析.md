# 10358-029 / V2.13.0.4 试验历程与异常停机分析

> 分析对象：`D:\EPB_Data\10358-029_V2.13.0.4_0814_1254`

> 分析方式：仅分析封存数据、SQLite 索引、配置、运行日志、看门狗事件和电源遥测；未修改程序及原始封存文件。

## 1. 结论先行

本次现场看到的“所有卡钳异常停机”，从封存证据看，准确表述应为：

1. **12:44:55 首发的是 Dev2 的 DAQ 回调陈旧（`DaqCallbackStale`），不是 5 个卡钳同时发生机械或电流硬故障。**
2. Dev2 故障先影响 EPB9、EPB10、EPB11；随后系统尝试安全断电和 DAQ 自维护，但程控电源组 3、4 一直返回“仍带电 / Output=true”，安全门不允许重建 DAQ。局部恢复 3 次耗尽后升级为 `SystemFault`。
3. `SystemFault` 触发全局 `StopAll`，因此 Dev1 上仍可运行的 EPB4、EPB5 也被一并暂停。**“所有启用通道都停”是系统级安全联锁的传播结果，不等于所有卡钳分别报警。**
4. 最终启用的是 EPB4、5、9、10、11，共 5 个通道；EPB8 在 V2.13.0.4 本轮启动前已被禁用，因此不属于 12:44 的“同时停机”。
5. 12:45 后主程序没有立即崩溃，系统保持在 Recovering/Paused；直到 12:50:36 记录“操作员点击停止试验”，看门狗会话才以 `ManualStopRequested` 结束。
6. 从 V2.13.0.4 启动到最终事故边界，本轮日志产生 19,527 条正式圈控制结果，其中最终 Dev2 的 3 圈因恢复边界作废；SQLite 可确认的**有效完成圈为 19,524 圈**。
7. 精确根因仍不能仅凭本封存包定死。最终窗口内 Dev1、Dev2 都出现约 140 ms、随后约 719 ms 的回调间隙，而 CPU、内存和磁盘没有资源耗尽特征，说明**共模采集链 / 驱动 / 总线 / OS 调度短暂停顿**比“单个 Dev2 板卡独立故障”更值得优先排查；这属于高可信方向判断，不是已证实根因。

综合判定：**直接触发明确，安全升级链明确，所有通道停机的传播机制明确；底层 DAQ 回调停顿的物理来源尚未闭环。**

## 6. 最终异常停机的秒级证据链

### 6.1 故障前 DAQ 正常

12:44:51.552：

- Dev1：`CallbackAgeMs=0.441`，`CallbackGapEvents=0`
- Dev2：`CallbackAgeMs=0.505`，`CallbackGapEvents=0`
- 两个设备的持久化状态均为 `Recovered`，当时没有耐久性阻塞。

### 6.2 回调间隙突然出现

- 12:44:55.237：Dev2 达到 100 ms 活性阈值，触发 `DAQ_LIVENESS Trip`。
- 12:44:55.581：Dev1 与 Dev2 都记录到一次约 140.6 ms 的回调间隙。
- 12:44:58.136：Dev1 最近回调间隙 718.735 ms；Dev2 回调年龄 719.565 ms，随后同一窗口的最近间隙约 719.6 ms。

这组数据说明最终窗口不只 Dev2 出现调度间隙。由于保护阈值由 Dev2 先越过，所以状态机以 Dev2 为触发设备；但两个设备同步出现大间隙，更像共模停顿，而不像单个卡钳造成的独立故障。

### 6.3 不是主机资源耗尽

事故前后主机指标：

- 12:44:54：进程 CPU 7.5%，系统 CPU 15.6%，可用内存约 11.53 GiB。
- 12:44:55：进程 CPU 8.0%，系统 CPU 13.9%，磁盘队列 0，写入约 0.85 MiB/s。
- 进程工作集约 200 MiB，磁盘剩余约 207 GiB。

因此没有 CPU 打满、内存耗尽、磁盘空间不足或持续高磁盘队列的证据。仍不能排除短时 DPC/驱动/总线阻塞，因为秒级 HostRuntime 指标无法观测这类微秒～毫秒级底层延迟。

### 6.4 安全恢复为何没有成功

Dev2 触发后，系统冻结其持久化边界并停止 EPB9、10、11。恢复要求先证明相关电源组已经关闭，但电源遥测在 12:45:05～12:45:08 仍显示：

- 组 3、4：`Output=True`
- 输出电压约 12 V
- 输出电流约 0 A
- 状态仍为 Armed

这里必须区分两个概念：

- 电机支路 DO_OFF 日志和约 0 A 的电源电流，支持“电机负载电流已清除”。
- 程控电源的输出状态仍为 True，且 `PhysicalOffStatus=NotMeasured`，表示系统没有独立物理接点证据证明整组已经下电。

安全策略按后者判定，因而拒绝重建 DAQ。它不是在断言卡钳电机仍持续吸收大电流，而是在“无法证明整组电源已关闭”时选择不继续恢复。

### 6.5 为何所有启用通道都停

```text
Dev2 回调陈旧
  → 冻结 Dev2 持久化边界
  → EPB9/10/11 暂停，末圈作废
  → 电源组 3/4 下电确认失败
  → 3 次局部自维护耗尽
  → SystemFault / SoftwareRecoveryCircuitOpen
  → 全局 StopAll
  → EPB4/5 同步暂停
  → 5 个启用通道全部停止
```

这就是“所有卡钳都异常停机”的完整传播链。

## 9. 原因分层与可信度

### 9.1 已证实

| 层级 | 结论 | 可信度 |
|---|---|---|
| 直接触发 | 12:44:55 Dev2 `DaqCallbackStale` 越过 100 ms 阈值 | 高 |
| 局部升级 | Dev2 相关电源组 3、4 的 Output-Off 状态未确认，DAQ 重建被拒绝 | 高 |
| 全局传播 | 局部恢复 3 次耗尽后进入 `SystemFault`，`StopAll` 暂停全部 5 个启用通道 | 高 |
| 会话终止 | 12:50:36 操作员点击停止试验 | 高 |
| 非独立卡钳群发 | 没有 5 个通道同时形成永久卡钳报警的证据；看门狗末次心跳中 `PermanentAlarmedChannels=[]` | 高 |

### 9.2 高可信方向判断，但尚未证实

1. 最终窗口 Dev1、Dev2 同时出现大回调间隙，优先怀疑共模采集链、NI 驱动、设备总线、OS/DPC 调度或进程级短暂停顿。
2. 02:27、07:36、12:15、12:44 多次出现“采集/证据陈旧 → 下电确认不能收口 → 外部恢复或系统故障”的重复模式，说明问题具有复现性，不是一次孤立偶发。
3. 程控电源“Output=true、约 12 V、约 0 A”说明问题更接近输出状态 / 关断确认链，而不是卡钳电机持续拉大电流。

### 9.3 当前不能下结论

- 不能确认 DAQ 回调停顿究竟由 NI 驱动、硬件设备、USB/PCI 总线、操作系统 DPC、GC/线程调度还是其他外部因素引起。
- 不能确认程控电源 Output-Off 状态未改变的底层原因是命令发送失败、设备拒绝、通信应答异常、状态刷新滞后还是接线/硬件问题。
- 不能仅凭 EPB8 的 223 条历史 alarm 断言其禁用原因；缺少人工操作记录或处置单。
- 不能把 07:36 EPB5 的 12.489 A 当作“断电后仍有 12.489 A”，因为该样本年龄已 1,139.9 ms，日志本身就是以“样本陈旧、无法确认”触发失效安全。

## 10. 建议的后续排查顺序（不涉及本次程序修改）

1. **先查共模 DAQ 环境**：导出 12:44:54～12:44:59 的 Windows 事件、NI MAX/驱动日志、USB/PCI 总线事件、DPC/ISR 延迟或硬件错误；同时比对 02:27、07:36、12:15 三个窗口是否有同类系统事件。
2. **复核电源组关断链**：对组 2、3、4 分别核对关断命令、设备通信应答、Output 状态刷新、物理输出电压以及急停/继电器链，重点解释为何日志能看到电机 DO_OFF 和约 0 A，但程控电源仍保持 Output=true。
3. **补齐物理断电证据**：当前 `PhysicalOffStatus=NotMeasured`，建议在台架侧用独立测量或硬接点记录验证“程序输出关闭”“电源输出关闭”“电机支路无电流”三个状态是否一致。
4. **按同一模板做 A/B 复现**：固定卡钳、线束、电源和负载，只改变 DAQ 设备/总线口/驱动环境，观察两个 DAQ 是否仍同步出现 >100 ms 回调间隙。
5. **保留下一次事故的外围证据**：本次最终 IncidentSnapshot 被有界门拒绝，且最新电源遥测文件为 `.csv.tmp`；下次封存时同步保存 Windows 事件和 NI 诊断，才能把“共模停顿”进一步落到物理根因。
