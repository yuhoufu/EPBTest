# V2.12.0.25 发布目录混包根因与不可变候选整改

## 技术结论

V2.12.0.24 的控制、持久化和 UI 整改自动证据仍然有效，但 2026-08-09 晚间现场实际启动的 `MTTfTest\bin\Release\MTTFTest.exe` **不是此前已经校验的那一份正式候选文件**。Visual Studio 和正式发布脚本共用同一个可变目录，后续普通编译覆盖了 EXE/DLL，却留下旧的 `build-identity.json` 和 `SHA256SUMS.txt`。因此窗口标题仍显示 V2.12.0.24，实际目录已经是“新二进制 + 旧发布清单”的混合包。

这不是曲线、卡钳或 DAQ 的新物理故障，而是发布流程缺少运行时强制校验。V2.12.0.25 从根上关闭该路径：

1. `bin\Release` 只作为构建暂存目录，永远标记为不可部署。
2. 正式包只能生成到带版本、Git 短 SHA 和 UTC 时间的独立不可变目录。
3. 新试验开始或跨进程恢复前，程序重新逐文件核对正式身份、完整文件集合和 SHA-256；缺文件、多文件、文件被覆盖、dirty、未批准或版本不符都拒绝启动。
4. 正式 SESSION 和现场验收同时要求 `PackageVerified=True`、`PackageCode=Verified` 和正数文件计数。

**当前状态：V2.12.0.25 代码、自动回归、独立构建和发布包正反校验已经通过；真实 NI、程控电源、液压和六通道 2/8/24/72 小时连续 RunId 仍待现场完成。因此可进入受控现场冒烟，不能提前签字为生产无人值守完成。**

## 2. 根因

### 2.1 直接根因：正式发布与 VS 输出目录重叠

旧 `Tools/Build-Release.ps1` 直接在 `MTTfTest\bin\Release` 生成正式清单；Visual Studio 的 Release 编译也写入同一目录。普通编译可以覆盖 EXE、Config.dll、Controller.dll 等文件，但不会同步更新旧清单。版本号由程序集属性提供，所以“标题版本正确”不能证明“整包身份正确”。

### 2.2 流程根因：只记录身份，没有在启动边界强制身份

V2.12.0.24 已把 Git SHA、EXE/config SHA 和构建时间写入日志，但新试验开始前没有逐文件核验。结果是日志能够暴露混包，却不能阻止混包继续运行。

### 2.3 为什么这是无人值守风险

- 现场数据无法可靠映射回源码提交和配置集合。
- 同版本号的两个 EXE 可能行为不同，导致日志根因判断失真。
- 旧清单会制造“看起来已批准”的假象。
- 在未验证包上做 24/72 小时长跑，即使界面正常也不能形成可审计上线证据。

## 3. V2.12.0.25 根治实现

### 3.1 程序内整包校验

新增 `ReleasePackageVerifier`：

- 强制存在 `build-identity.json` 和 `SHA256SUMS.txt`；
- 校验 ProductVersion、正式候选状态、`deploymentApproved=true`、`gitDirty=false`、Git SHA、BuildUtc 和配置集合 SHA；
- 枚举实际目录文件，拒绝清单外多余文件和清单内缺失文件；
- 对全部发布文件重新计算 SHA-256；
- 启动时缓存一次用于身份展示，新试验/跨进程恢复前强制刷新，避免程序打开后文件又被替换；
- 同进程人工暂停/继续不重复阻断当前安全收口，但新正式运行必须通过门禁。

校验失败时程序明确提示必须从独立正式候选目录运行，不允许从 `bin\Release` 启动正式试验。

### 3.2 不可变候选目录

发布脚本现在执行以下流水线：

```text
源码洁净提交
  -> VS/MSBuild 暂存输出 bin\Release
  -> 标记 BUILD_STAGING_NOT_FOR_DEPLOYMENT
  -> 复制到 .staging-<guid>
  -> 写正式身份和完整 SHA 清单
  -> 独立递归校验
  -> 原子改名为 V2.12.0.25-<gitsha>-<utc>
```

最终目录已存在时禁止覆盖。正式验收工具必须显式传入 `-ReleaseDirectory`；省略目录或传入默认 `bin\Release` 都不能获得部署批准。

### 3.3 现场证据门禁

正式 SESSION 新增：

- `PackageVerified=True`
- `PackageCode=Verified`
- `PackageFiles=<正数>`

现场校验器缺少任一字段或发现未验证包时直接失败，避免把旧日志、诊断运行或混包运行算入上线时长。

## 5. 现场部署与验收步骤

1. 结束当前从主仓库 `bin\Release` 启动的诊断进程；不要把其运行时长计入验收。
2. 只复制完整的 `artifacts\releases\V2.12.0.25-...` 目录；不得只复制 EXE 或若干 DLL。
3. 在交付目录执行：

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\Tools\Verify-Release.ps1 `
     -ReleaseDirectory '<正式候选绝对路径>' -RequireDeploymentApproved
   ```

4. 从该候选目录启动程序。开始试验前确认身份窗口和 `SESSION Start` 均为 `PackageVerified=True`、`GitDirty=False`。
5. 依次完成同一候选、同一配置口径下的 2、8、24、72 小时验收；每次进程重启必须产生新 RunId，并从零重新累计该阶段时长。
6. 每阶段用显式候选目录执行 `Tools\Invoke-Field-Acceptance.ps1`，保存 MD、JSON、完整封存目录、正式候选和 SHA 清单。

## 6. 放行与回退判据

以下任一项出现即不放行：

- 启动门禁报告包未验证、文件缺失/多余或哈希不符；
- 正式 SESSION 缺少 PackageVerified/PackageCode/PackageFiles；
- 试验期间从 VS 重新编译后继续使用同一目录；
- DAQ/持久化/UI/恢复/液压/控制任一现场红线失败；
- 通过重启拼接时长或使用截图累计时间代替连续 RunId。

回退时保留完整候选目录和失败封存，不得修改失败候选后继续沿用原目录名。修复后必须生成新的 Git SHA/UTC 目录并重新开始验收。

## 7. 与压力校正和曲线问题的边界

本轮提交只处理发布目录混包和运行时身份门禁，不合并用户正在编辑的压力校正、主窗口菜单及其测试文件。压力校正提交 `10955e8`/`a29d972` 与后续未提交工作保留原状，避免将正在变化的 UI/标定逻辑误纳入本次候选结论。

V2.12.0.20“启动初期连续、后期短线”的根因和 V2.12.0.24 的 UI/持久化整改仍按原报告结论执行；V2.12.0.25 不改变 2 kHz 控制、峰值判断、Raw/SQLite 耐久或 10 FPS 绘图策略，只保证现场运行的确实是经过验证的那一套文件。
