## 1. 结论先行

封存中存在两条不同的故障链：前序软件自恢复滞留，以及重启后的真实液压硬件故障。二者不能合并成同一条连续因果链。

1. **EPB10、EPB11进入“系统自恢复”的直接原因是控制链超时，不是已经确认卡钳损坏。** 05:34:33，Dev2出现 `124.7～440.4 ms` 的DAQ回调陈旧；随后EPB10在正式圈收尾时，高优先级OFF调用没有在100 ms软件期限内返回成功，触发电源组4失效安全联锁。EPB10、EPB11同属电源组4，EPB12未启用，所以界面上正好是两只卡钳一起进入恢复。
2. **EPB10、EPB11不能自恢复的根因是恢复owner同优先级互相抢占后发生“假移交”。** 电源组4恢复先取得液压2的恢复owner；毫秒级随后到达的电源组3恢复以相同优先级取消了它。旧任务把取消解释成“已移交给更高层”，但新任务只接管EPB9，没有继承EPB10/11。旧任务退出后没有重试、没有终态、没有60秒硬截止回收，形成无owner的孤儿 `Recovering`。
3. **截图证明该孤儿状态至少持续约1小时43分钟。** 05:34:35.539之后，EPB10/11没有新的运行状态迁移；07:16:59与07:17:52两张截图中EPB10仍为80030次、EPB11仍为79970次，而EPB4、5、9各前进3次。悬浮信息同时显示 `Timer=True Runner=True Energized=False`，说明资源对象尚存、机械动作已经停止，但实际恢复任务已经不存在。
4. **前序事件的电源组范围保护本身正确，恢复生命周期不正确。** EPB10/11共享电源组4，组级安全断电合理；但同液压2上的电源组3、4同时恢复时必须合并参与者或显式移交，不能让其中一个电源组永久遗留在Recovering。
5. **液压2后来确实发生了物理失压。** 08:33:30.912 液压2刚以 `68.921 bar` 通过建压资格，约 2 秒后压力降为 `-0.390 bar`；人工重启后连续三次只能达到 `0.268 / 0.259 / 0.284 bar`，而允许范围是 `60～80 bar`。这与现场确认的卡钳损坏一致，但现有证据不能证明05:34的软件超时就是后来卡钳损坏的起因。
6. **EPB9在后续失压前已经连续出现三个低电流平台圈。** 峰值依次为 `13.095 / 11.296 / 11.306 A`，而 EPB10、EPB11 同期基本正常。EPB9是高度可疑的故障关联点，但共享压力数据不能单独证明“损坏的一定是EPB9”；最终个体归因仍以现场拆检为准。
7. **后续先停止液压2的EPB9、EPB10、EPB11是合理的安全动作。** 三个通道共享液压2，任一接入卡钳泄漏或开裂都可能使整组无法保压；但液压1的EPB4、EPB5随后被全批次 `StopAll`带停，不是液压1故障，局部隔离逻辑不正确。
8. **两段操作反馈也要分开判断。** 前序PID 2568在07:18:06收到了暂停请求，约10.1秒后完成全部通道安全暂停；07:23:43收到人工停止，约0.35秒后七项StopAll证据全部确认。因此前序问题是自恢复无终点、过程反馈不足，并非后台完全没收到停止。后续PID 9796则确有终态闭锁、末段UI心跳停止及操作意图未进入后台的问题。
9. **Watchdog存在两种盲区。** 前序结构化快照只把DAQ恢复和暂停原因中包含`Daq`的通道认作活动/孤儿恢复，看不到 `PowerSupplySelfHealing`孤儿；后续Watchdog又对约93分钟的陈旧心跳没有升级为接管和重启。
10. **声光报警对应存在逻辑缺口。** 前序软件超时不应冒充卡钳硬件报警；后续第3次低压已达到 `HardwareConfirmed`，但启动/学习阶段的提前返回又跳过了 `Alarm.SetAlarmAsync`，封存不能证明灯和蜂鸣器收到动作请求。
11. **目标逻辑必须同时补齐两类收敛。** 电源/DAQ系统自恢复必须在三次尝试或60秒硬截止内走到“恢复成功、精确组停机、或系统恢复熔断”之一；液压三次新鲜低压确认后，则持久取消故障液压组当前参与成员EPB9、EPB10、EPB11，让液压1的EPB4、EPB5在同一进程自动继续。

## 4. 根因分析

### 4.1 前序EPB10/11为何进入“系统自恢复”

直接触发点是EPB10正式圈收尾的高优先级OFF调用没有在软件期限内返回成功：

```text
Dev2 DAQ回调出现124.7～440.4ms空窗
  -> 同设备的安全OFF与周期收尾集中到达
  -> EPB10 FormalCycleAttemptFinalizerOff未在100ms内返回成功
  -> RequestElectricalGroupEmergencyShutdown(EPB10)
  -> 电源组4成员[10,11,12]统一断电并进入PowerSupplySelfHealing
  -> EPB12未启用，界面可见成员为EPB10、EPB11
```

这里要区分“软件未在期限内确认命令成功”和“物理输出没有关闭”：

- `SetEpbOffHighPriority`的同步等待期限是100 ms；worker超时会返回`false`，即使排队的OFF稍后仍会执行；
- 05:34:35.510日志已经确认电源组4关闭；随后EPB10、11、12的逐路DO写均成功；
- 电源组4遥测也成功，只是耗时848.5 ms，超过500 ms诊断阈值；
- 电气组事件被记录为`DaqDerived=False`，因为直接入口是`FormalCycleAttemptFinalizerOff`，但其上游同一时段确有Dev2 DAQ新鲜度空窗和多路控制拥塞。

因此，EPB10/11进入恢复的性质是**系统控制链瞬态超时后的共享电源组保护**。按电源组4隔离两只已启用卡钳是正确的安全范围；当时没有证据把它定性成两只卡钳同时损坏，也没有证据表明液压2已经无法建压。

### 4.2 前序EPB10/11为何一直不能自恢复

问题不在“Raw与耐久边界一直写不完”，而在恢复任务进入边界处理前就被取消并丢失了终态责任。恢复时序如下：

```text
POWER:4:<89d...> 先取得液压2恢复owner，参与者=[10,11,12]
  -> POWER:3:<1d1...> 随后申请同一个液压2 owner，参与者=[7,8,9]
  -> 两者优先级同为PowerSupply
  -> owner协调器使用 priority >= current.Priority，组3取消组4
  -> 组4第1次尝试收到OperationCanceledException
  -> 外层统一记录“恢复所有权已移交给更高层恢复”并退出
  -> 组3仅恢复EPB9，于05:34:42.480成功重入
  -> 没有任何新任务继承EPB10/11、关联号89d...或电源组4恢复责任
```

这是一处“假移交”：日志文字称“更高层恢复”，实际上是**同优先级、不同电源组**的任务抢占；新owner的参与者集合里没有EPB10/11，也没有显式`HandoffAck`。

组4任务退出后又同时发生了三件事：

1. `finally`删除了电源组4的软件恢复任务登记；
2. 取消来源不是60秒`hardDeadline`，所以不会执行`ExecuteAffectedGroupResetAsync`兜底；
3. EPB10/11最后状态仍停在`Recovering / PowerSupplySelfHealing`，Timer处于Paused但对象与Runner仍保留。

于是运行时形成了违反状态机不变量的状态：

```text
UI State = Recovering
Timer = True / Paused
Runner = True
Energized = False
Active recovery task = False
Active recovery owner = False
Effective hard deadline = None
```

现有两层监视也没有把它识别出来：

- Timer一致性检查只对`Running / WarningRunning`做心跳陈旧自愈；`Recovering`会直接跳过；
- “孤儿暂停”只识别PauseReason中包含`Daq`的通道，`PowerSupplySelfHealing`不在范围内；
- 提供给独立Watchdog的结构化恢复快照只把活动DAQ恢复或DAQ孤儿暂停计为`ActiveRecovery`，看不到已经丢失任务的电源恢复。

所以60秒恢复硬截止没有生效，独立Watchdog也没有接管，最终只能由人工暂停/停止结束该Run。截图时间和状态日志共同证明，这不是单纯的界面残影，而是后台机械计数确实停止的孤儿恢复。

### 4.3 硬件根因：液压2接入回路无法保压/建压

证据满足“新鲜压力样本 + 多次独立代次复现 + 重启后复现”：

- 失压前可达到约69～70 bar，随后短时间跌至零附近；
- 同进程重新建压三次失败；
- 人工重启后重新建压三次仍失败；
- 液压1同时可正常达到71.144 bar；
- 现场已经确认卡钳损坏。

因此，不能把本次主要故障解释为DAQ陈旧、压力标定偶发毛刺、程序输出未下发或单纯软件误报警。08:32:40的DAQ短空窗已快速恢复，且后续压力失败使用的是年龄仅0.1 ms的新鲜样本。

EPB9的三个低平台圈是重要前兆，说明其夹紧载荷行为已明显偏离正常；但液压2是一条共享回路，单个压力传感器只能证明“液压2及其接入件存在故障”，不能在软件层唯一定位哪只卡钳开裂或泄漏。

### 4.4 软件根因一：液压恢复所有权没有完成移交

首次失压后，现有恢复流程同时存在以下身份：

```text
Active owner    = HYDRAULIC:2:<RunId>
Requested owner = GROUP-RESET:2:<RunId>
Requested owner = ACTIVE-CYCLE:9:<Cycle>:<CorrelationId>
```

组复位和活动圈恢复都等待旧 `HYDRAULIC:2` owner，连续三次各等待10秒仍无法取得所有权。也就是说，本来应由同一个液压组恢复事务完成的“撤销旧代次、释压、重建代次、复核压力”，被拆成了相互竞争的恢复入口。

这不是硬件损坏造成的必要结果。即使液压始终无法建压，恢复事务也应在每次尝试后释放owner并得到明确的 `HydraulicBuildTimeout`，而不是先用 `RecoveryOwnershipTimeout`耗尽软件恢复预算。

### 4.5 软件根因二：局部故障被统一启动异常处理扩大为全局回滚

启动核心已有“单通道启动定位失败后只隔离失败通道，健康通道继续”的局部成功能力；但液压建压异常从更外层抛出后进入通用 `catch`：

1. 对全部 `selected` 通道发布 `StartBlocked`；
2. 调用全局 `StopAllAsync`；
3. 停止所有Timer/Runner；
4. 关闭所有电源组和两个液压组；
5. 某些软件逻辑状态未收敛时设置 `RequiresProcessRestart`。

因此，液压2故障时EPB4、EPB5被停止是异常处理策略的结果，不是液压1的安全联锁要求。

当前逻辑的评价应分两层：

| 问题 | 是否正确 | 说明 |
|---|---|---|
| 液压2失压后停止EPB9/10/11 | 正确 | 三者共享故障液压组，无法在不隔离泄漏点的情况下安全继续 |
| 液压2恢复期间保持其输出OFF | 正确 | 避免无压力或不稳定压力下继续机械循环 |
| 用三个独立新鲜低压代次确认硬件故障 | 正确 | 可抑制单次压力毛刺误报 |
| 三次失败后停止液压1的EPB4/5 | 不正确 | 故障范围被软件扩大，健康组本可继续 |
| 三次失败后把所有启用通道写为StartBlocked | 不正确 | 应只持久禁用故障液压组的参与通道 |
| 已确认局部硬件故障后要求整个进程重启 | 不正确 | 确定性的局部硬件故障应收敛为组级终态，不应依赖重启修复 |

### 4.6 操作无响应不是单一“UI线程卡死”

前序PID 2568中，暂停和停止意图都进入了后台：暂停等待健康通道完成当前圈约10.1秒，停止则约0.35秒完成七项安全证据。因此该段“无反应”的核心是长时间自恢复没有进度、期限和终态提示，而不是安全停止代码没有执行。

重启后的PID 9796日志中没有出现停止按钮入口应立即产生的：

```text
WatchdogRuntime.NotifyManualStop("操作员点击停止试验")
StopContext Source=ManualUi Reason=操作员点击停止试验
```

所以PID 9796后台从未收到操作员停止意图。结合UI心跳，分为两个阶段：

1. **08:34:38之后的大部分时间是终态闭锁。** `SafeButRestartRequired`会把批次按钮改为“需重启软件”并禁用；处于 `SystemFault/StartBlocked` 且不可确认恢复的通道 RUN/STOP 也会禁用。点击禁用控件不会进入事件处理器，因此表现为“无反应”。
2. **08:56:53以后存在真实UI停摆证据。** UI心跳不再产生，而后台HOST监控仍在运行。由于没有PID 9796的hang dump，只能确认UI消息泵或其心跳定时器停止，不能凭日志指定是哪一把锁、哪个同步等待或哪个模态窗口。

这两个阶段都暴露了产品问题：用户需要明确、可操作的终态提示；即使当前批次已安全停止，“停止”按钮也应保持可审计、幂等可点击，而不是静默禁用。更重要的是，Watchdog必须在主程序无法完成进程交接时自动接管。

### 4.7 Watchdog根因：心跳早已陈旧，但没有进入硬截止接管

前序PID 2568的主进程心跳仍在，独立Watchdog只有依赖结构化恢复快照才能知道通道已失去恢复owner；但该快照不包含电源恢复任务，也只把PauseReason含`Daq`的通道当成孤儿暂停。因此EPB10/11即使超过60秒没有机械进展，Watchdog仍认为没有活动恢复需要接管。

后续液压故障运行的Watchdog Session为 `7d8ad947503e4d3a955170d6e26e99bc`：

- 最后心跳：07:25:03，本地时间；Sequence=17；当时仍是 `Learning`，所以其后心跳内容已经失真；
- 07:25:06：记录 `HeartbeatSuspect`，年龄3.182秒；
- 之后没有按心跳陈旧升级为停止、dump、终止或重启；
- 08:58:39：强杀后才记录 `PipeDisconnected`和`ProcessExitedUnexpectedly`；
- 08:58:41：操作员在过渡窗口取消自动恢复，Session终态为 `OperatorCanceledAutomaticRecovery`。

这说明看门狗的“管道读写/心跳异常检测”与“硬截止接管状态机”没有闭环。它能记录一次可疑状态，但仍允许一个没有新心跳的主进程存活约93分钟。

### 4.8 声光报警：静态映射正确，触发路径和审计不正确

前序05:34事件中，UI信息日志记录了电源组4“控制系统故障”安全提示，恢复路径同时明确写入“系统类故障进入组内自愈，不发布全局SystemFault”；截图标题栏也显示预警0、报警0。封存没有EPB10/11硬件报警输出请求。由于该段只有控制链超时而没有卡钳或电源硬件确认，**不点亮卡钳硬件灯、不启动蜂鸣器是正确分类**；问题是系统自恢复没有期限和终态，而不是少发了一次卡钳报警。

当前报警分类规定只有 `HardwareConfirmed`进入通道硬件灯和蜂鸣器链。液压建压失败前两次是 `SystemFault`，第3次才是 `HardwareConfirmed`，这个门槛设计正确。

但 `OnHydraulicFaultRaised`在“批次活动且不处于Running”时为避免并行恢复，发布 `ControlFaultRaised`后直接返回。08:34:35和08:59:21的第三次确认都发生在启动/学习恢复调用栈，因而没有执行后面的：

```text
ChannelAlarmRaised
StopChannelOnAlarm
Alarm.SetAlarmAsync
ExportAlarmSnapshotAsync
```

结论如下：

- 界面“硬件故障已确认”提示存在；
- COM8在07:24和08:58均成功打开；
- 没有液压硬件报警的 `SetAlarmAsync`调用路径；
- `AlarmManager`只记录串口打开和最终发送失败，不记录成功请求/响应，封存也没有保存当次运行的 `AlarmConfig.xml`；
- 因而不能证明声光设备动作，高置信判断是软件没有针对本次液压硬件确认发出声光请求。

当前源码中的静态映射为：

| 信号 | 模块 | DO线 |
|---|---:|---:|
| EPB9报警灯 | Device 2 | DO0 |
| EPB10报警灯 | Device 2 | DO1 |
| EPB11报警灯 | Device 2 | DO2 |
| 蜂鸣器 | Device 2 | DO4 |

地址映射本身与通道编号一致，但报警语义还需要修正：共享压力只能确认“液压2组故障、EPB9/10/11受影响”，不能把三个通道都表述成“三只卡钳已损坏”。界面和报警日志应区分“故障源”与“受影响通道”。

## 5. 目标处理逻辑

### 5.1 电源组“系统自恢复”的有界闭环

同一液压组内多个电源组同时发生系统类故障时，不能各自用不同owner竞争同一个液压资源。建议按液压安全范围建立一个可合并的恢复事务：

```text
Dev2/电源系统类故障
  -> 立即关闭精确受影响电源组的通道DO与共享电源输出
  -> 以HydraulicId建立CompositeRecoveryTransaction
  -> 合并同时到达的电源组与参与者，例如PSU3+PSU4 / [9,10,11]
  -> 原子封闭所有参与者当前圈时间窗与Raw/耐久边界
  -> 最多3次：电源实时预检 -> 输出稳定 -> 机械释放 -> 未来公共槽重入
       -> 任一次全部成功：所有已恢复参与者提交Running
       -> 电源组硬件证据连续3次失败：只持久禁用该电源组当前已选成员
       -> owner/DAQ/落盘等系统证据失败3次或60秒：SystemRecoveryCircuitOpen
            -> 精确组Stop→Start等价清场，仍失败则交给进程Watchdog
  -> 任一出口都必须提交终态并清理Timer/Runner/owner
```

必须建立以下强制不变量：

```text
Channel.State == Recovering
  => ActiveRecoveryTask(channel)
  && ActiveRecoveryOwner(channel)
  && RecoveryDeadlineUtc > Now
```

若任一条件不成立超过一个监视周期，就立即标记`OrphanRecoveryDetected`并补建事务；不能继续显示“系统自恢复”。具体约束如下：

1. 同优先级owner不得互相抢占。相同液压组、相同故障批次应合并参与者；不能合并时只能排队，不能用`priority >= current.Priority`取消对方。
2. 真正的owner移交必须携带`AffectedChannels`、圈截止边界、重试次数和硬截止，并由新owner返回`HandoffAck`；只有收到ACK后旧任务才能记录“已移交”并退出。
3. 取消原因必须强类型区分`RunStopped`、`HardDeadline`、`ExplicitHandoff`和`UnexpectedOwnerCancellation`。未知取消按恢复失败处理并重新调度，不能当成成功移交。
4. 60秒硬截止必须由不受owner令牌抢占影响的独立监督器持有。达到期限后无论任务登记是否被删，都要执行精确组兜底并发布终态。
5. 三次恢复预算只统计真实的电源预检/输出稳定失败；owner竞争、令牌取消和落盘等待属于软件系统失败，不得冒充三次电源硬件证据。
6. 若最终只确认电源组4不可用，持久取消EPB10、EPB11并让EPB9继续；若确认的是液压2硬件故障，才按后续液压状态机处置EPB9、10、11整个参与集合。

### 5.2 液压故障总体状态机

```text
液压组失压/建压失败
  -> 立即关闭该液压组参与通道的电机输出
  -> 释放该液压组并关闭仅服务于该组的无剩余参与者电源
  -> 新鲜、独立代次重试（最多3次）
       -> 任一次恢复：执行压力资格 + 2圈资格复核 -> 重新加入未来公共节律槽
       -> 第3次仍低于窗口：HardwareConfirmedHydraulicGroup
            -> 声光报警并锁存组故障
            -> 持久取消故障组当前已选成员
            -> 关闭/作废这些通道的在途圈并从ExpectedParticipants移除
            -> 重新计算健康通道计划
            -> 健康液压组在同一进程自动继续
            -> 若无健康通道剩余，则安全结束到Idle，不进入无意义重启循环
```

### 5.3 确认次数与证据规则

沿用当前液压硬件确认的三次门槛，但必须满足：

1. 每次来自不同的液压代次，不能把同一异常回调重复计数；
2. 压力样本必须有效、新鲜，年龄不超过项目配置；
3. AO/DO建压命令必须已成功提交，否则归为控制链或系统故障，不计卡钳/液压硬件失败；
4. 第1、2次显示“液压组恢复中 1/3、2/3”，不锁存硬件报警；
5. 一次完整建压和保压成功后清零连续失败数；
6. 第3次仍低于允许窗口才进入不可自恢复的液压组终态。

### 5.4 持久禁用范围

对本次配置，液压2硬件确认后的默认安全动作应为：

```text
EPB9.Enabled  = false
EPB10.Enabled = false
EPB11.Enabled = false
EPB4.Enabled  = true
EPB5.Enabled  = true
```

同时取消EPB9/10/11的运行勾选和曲线勾选，原子保存当前项目专用 `Config\TestConfig.xml`。复用现有不可自恢复卡钳的持久禁用能力：内存 `Enabled=false`、UI取消勾选、项目配置原子更新、保存失败高可见度提示。

不要无条件修改EPB7、EPB8、EPB12，因为它们本次本来就未启用；报警元数据可以保留完整液压组成员和本次参与成员两个集合。

重要安全边界：如果损坏卡钳仍物理连接在液压2上并泄漏，软件不能只取消EPB9后让EPB10/11继续使用同一条液压回路。只有在损坏件被物理更换/隔离，且液压2重新通过三次压力资格后，才允许剩余同组卡钳重新参与。没有分支隔离阀或独立压力证据时，软件默认只能禁用本次参与的整个故障液压组。

### 5.5 健康组自动续跑

确认液压2永久故障后：

1. 封存EPB9/10/11当前在途圈为明确的液压硬件中止，不增加正式完成数；
2. 从当前Run的期望参与者集合原子移除9/10/11；
3. 释放液压2所有lease、generation和recovery owner；
4. 电气组3、4在无其它健康参与者时保持OFF；
5. 不关闭液压1，不关闭仍服务EPB4/5的电气组2；
6. EPB4、EPB5保留既有圈数、学习模型和历史数据；
7. 从下一个未来公共15秒槽恢复正式调度，不重复全批学习；
8. Run保持活动，记录一次 `PartialBatchContinuation`以及被排除通道和原因。

如果故障发生在初次启动阶段，启动结果必须支持“部分成功”：液压1成功、液压2三次失败时，直接提交 `StartedChannels=[4,5]`、`DisabledChannels=[9,10,11]`，不能进入外层通用异常把五个通道全部写成 `StartBlocked`。

### 5.6 恢复所有权

液压组恢复必须只有一个事务owner。建议把以下动作合并在同一 `HydraulicGroupRecoveryTransaction`：

```text
FreezeAffectedCycles
 -> RevokeAffectedOutputs
 -> AbortOldGenerationAndLeases
 -> VerifyOwnerReleased
 -> ForceReleaseAndVerifyPressureSafe
 -> BuildNewGeneration
 -> QualifyOrCountFailure
 -> CommitRecovered / CommitPermanentGroupDisable
```

禁止 `HYDRAULIC`、`GROUP-RESET`、`ACTIVE-CYCLE`三个入口互相等待。若确需身份切换，必须使用显式owner handoff，并在交接前撤销旧owner；owner超时是软件系统故障，不能消耗液压硬件的三次低压确认次数。

## 6. 操作响应与Watchdog整改

### 6.1 UI操作

1. 所有暂停/停止点击在任何 `await`之前先写入 `UiCommandIntentAccepted`，包含命令、RunId和单调时钟；没有这条日志就表示事件未进入处理器。
2. “停止试验”是高优先级、幂等安全命令，不受开始锁、恢复owner、生命周期gate或 `RequiresProcessRestart`阻塞。
3. 如果系统已经物理安全停止，再点停止也应立即显示“已安全停止；无输出；正在等待自动恢复/重启”，并留下审计记录，不能静默无反应。
4. `SafeButRestartRequired`时，批次按钮应明确显示终态原因和Watchdog倒计时；不能仍让用户误以为可以“暂停”。
5. UI事件只提交命令并立即返回消息泵；进度由快照刷新，不在UI调用栈内等待完整恢复或重启。
6. UI心跳应记录独立的消息泵往返延迟，而不是依赖日志刷新恰好被调用；连续超过2秒无响应时生成hang诊断事件。
7. 非人工路径禁止弹出模态对话框；所有无人值守恢复结果使用非阻塞状态栏/过渡窗口。
8. “系统自恢复”卡片必须显示故障范围、恢复owner、当前阶段、`Attempt/3`、已用时和60秒剩余期限；owner丢失时立即转成红色“恢复任务丢失，正在补建/已熔断”，不能继续显示蓝色恢复中。
9. 批次优雅暂停等待当前圈时，应显示仍在等待的通道和最长剩余时间；前序10.1秒等待不能只有按钮状态变化而没有进度。

### 6.2 Watchdog

1. 心跳陈旧检测、命名管道读取和进程退出等待必须在互不阻塞的独立循环中运行。
2. 建议门槛：3秒进入 `HeartbeatSuspect`，10秒无新心跳进入 `TakeoverRequested`，总计30秒内完成dump、停止请求、必要时终止旧PID和启动新PID。
3. `HeartbeatSuspect`不能成为无后续动作的日志状态；每个可疑状态必须具有单调硬截止和唯一终态。
4. 在终止旧进程前自动采集hang dump；本次缺少PID9796 dump，导致最后106秒UI停摆无法定位。
5. 主程序进入 `ExternalRecoveryRequired`后，应主动向sidecar发送结构化handoff并等待ACK，但不能由已经不健康的主进程承担自行拉起新进程。
6. sidecar必须检查心跳年龄，而不能长期相信最后一帧中的 `Learning/RunActive=true`。
7. 如果安全关断未确认，优先执行独立安全关断链或硬件联锁；如果已经像本次一样七项全部Confirmed，则可以直接完成进程交接。
8. `CaptureWatchdogRecoverySnapshot`必须覆盖电源、液压、DAQ、Timer、组复位和活动圈等全部恢复登记，不能只以DAQ上下文代表所有恢复。
9. 任一启用通道处于`Recovering`，但不存在覆盖该通道的任务、owner或有效deadline时，1秒内发布`OrphanRecoveryDetected`并补建；补建失败进入精确组熔断。
10. 机械进展也必须作为结构化证据：`Energized=false`且`MechanicalCompletedCount`在恢复期限内不变时，不能因为`Timer=True / Runner=True`就判为健康。

## 12. V2.13.0.14首轮实施结果（已由V2.13.0.15补强）

本事故对应的软件整改已落地到 `V2.13.0.14`。本节记录实际实现，不改变前文对 `V2.13.0.13` 封存数据的事实判断。

### 12.1 EPB10/11孤儿“系统自恢复”闭环

1. `HydraulicRecoveryOwnershipCoordinator` 的抢占条件由“新优先级大于等于旧优先级”改为“严格大于”。相同 owner 的同一事务继续共享租约；同优先级不同 owner 严格排队，不再互相取消。
2. 电源组、液压组恢复任务按全部受影响通道登记，不再只留下一个无通道归属的后台任务。EPB10/11可由恢复任务登记、恢复owner和通道状态三方交叉核对。
3. 每个通道第一次连续进入 `Recovering` 时，同时记录UTC时刻和单调时钟。后续重试、理由文本刷新、owner变化或任务取消都不能重置60秒绝对期限；系统校时也不能延长该期限。
4. 500ms运行一致性扫描覆盖DAQ、电源、液压、Timer、单通道重启和受影响组复位。`Recovering`持续1秒后若没有有效任务/owner覆盖，立即登记唯一的受影响液压组清场任务。
5. 电源、液压软件恢复最多执行3次真实恢复尝试；第3次仍失败或达到60秒期限时，进入受影响组 `Stop→Start` 等价清场。清场失败继续发布明确系统恢复故障并交给无人值守恢复/独立Watchdog，不允许静默退出。
6. Watchdog结构化快照现汇总全部 `RecoveringChannels`、`OrphanRecoveryChannels`、最早恢复起点、硬期限、带电/断电状态和受影响通道。非DAQ孤儿恢复会复用现有 `OrphanPaused` 接管通道，使Sidecar在超时后执行接管。

因此，PID2568中的原路径现在变为：

```text
电源组4恢复先取得液压2 owner
 -> 电源组3同优先级恢复到达
 -> 电源组3排队，不取消电源组4
 -> 电源组4恢复10/11并提交Running/明确终态
 -> 电源组3随后恢复9

任一任务异常退出
 -> 500ms扫描在无owner/task持续1秒后识别孤儿
 -> 受影响组自动清场
 -> 最迟3次或连续Recovering 60秒进入明确终态/Watchdog接管
```

### 12.2 液压和电源确认硬件故障的精确隔离

- 液压短时低压、压力样本陈旧和软件屏障异常仍按系统自恢复处理，不产生卡钳硬件报警。
- 液压连续3代新鲜低压证据达到 `HardwareConfirmed` 后，不再进入无限软件恢复；只对故障事件中的当前启用成员执行高优先级OFF、报警停机、快照、项目配置 `Enabled=false` 和UI取消勾选。
- 10358-029本次液压2成员为EPB9/10/11，因此只永久禁用9/10/11；液压1的EPB4/5不撤销运行授权、不执行全批StopAll，可在同一进程继续。
- 若确认的是PSU4硬件故障，则只禁用电气组4事件成员EPB10/11并关闭PSU4；EPB9不属于电气组4，继续运行。
- 硬件锁存或报警停机一旦提交，同组旧软件恢复任务立即失效；即使旧任务仍持有Timer、Runner或批次身份，也禁止在隔离命令后再次使能电源。
- 禁用写盘失败时，本进程仍保持故障通道停机，并通过既有高可见UI事件提示人工确认；不得回退修改默认模板。

### 12.3 声光报警和按钮反馈

- `HardwareConfirmed`分支无论发生在正式运行还是启动/学习阶段，都会调用 `Alarm.SetAlarmAsync`，不再被启动阶段提前返回绕过。
- 报警初始化记录 `AlarmMappingLoaded`；每次灯或蜂鸣器输出记录 `AlarmOutputRequested`、`AlarmOutputAcked`或`AlarmOutputFailed`，包含Channel/Output、Device、Line、On/Off、尝试次数和耗时。
- `AlarmOutputAcked`只表示串口请求取得配置要求的响应；在无硬件读回的现场配置下，不表述为灯已物理点亮。最终对应关系仍须按第9节逐点联调验收。
- 暂停、继续和停止点击后立即写入命令受理日志并更新安全状态文字；停止命令使用同一个 `CommandId/CorrelationId`贯穿UI和控制层。长时间停止继续每秒显示安全阶段和Watchdog倒计时。

### 12.4 自动化验证

已新增并通过以下回归场景：

- 同优先级不同电源恢复排队且不取消旧owner；
- 恢复任务覆盖完整受影响通道并在任务终态清除；
