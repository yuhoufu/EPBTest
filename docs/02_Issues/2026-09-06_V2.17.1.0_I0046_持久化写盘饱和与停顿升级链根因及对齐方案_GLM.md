## 1. 结论先行

I0046 是 I0045 同一天的后续：第二段主进程在 13:30:54 拉起后健康运行约 16 分钟（13:31:12 整批自动续跑，13:33:57 学习对齐转正式），13:47:11 发生第二次持久化慢写/积压事件，升级链再次启动并走完全程：**短时持久化慢写和积压 → DAQ 局部恢复启动但断电截止迟滞 → 看门狗 `PowerOffUnconfirmedTimeout` 接管 StopAll → 安全退出 → 普通会话关闭消息（SessionClose→ApplicationClosing）取消了接管**——程序 13:47:24 消失，13:58 人工封存。这就是现场"新版正常运行时间很短"的直接构成。

三个关键判定：

1. **收紧的 75/100/250ms 三阈值与本案无关。** 全部日志没有 `DAQ_FRESHNESS_SAFETY_CUTOFF`、没有 `DaqReadDispatchOverflow`；`run.log` 的 `DAQ_LIVENESS Result=Configured WarnMs=75 SuspectMs=100 TripMs=250` 与配置哈希链（附录 A）证明它们确实生效但未被触发。把三个数值抄回旧版既无证据支持，也因代码钳制（200/249/5000）无法还原旧行为。
2. **持久化写入存在"短时慢写长尾"，但不是常态饱和。** 周期记录显示正常窗口队列深度 p50=0、年龄 p95≈20ms（约 70% 快照深度为 0），写入器有相当余量；但异常窗口内单次写入调用出现 215–794ms 长尾，吞吐降至到达率的 1/3–2/5，足以在 2–3 秒内把深度推过 1s 年龄暂停线。慢调用内部构成（通道锁 / raw 共享锁 / SQLite 提交 / ring 刷新 / 调度）现有分项无法归责，是 P2 要测量的对象。
3. **最终退出断点已定位到关闭类型被提前降级为普通 SessionClose**（详见第 4 节 P0）：接管事务完成 StopAll、替换资格已推进到 Approved 后，子窗体授权路径先以 `SessionClose` 发送了普通关闭，sidecar 按旧式关闭取消接管并停止监督，随后类型正确的接管退出无法撤回。`RelaunchDisposition=PreserveApprovedPermit` 表达的是退出时保留自动替换资格，不是"不重启"的决定本身。

## 2. 根因逐层分析

### 2.1 触发层：短时慢写长尾（非常态饱和，内部构成待测）

**正常水位（勘误后的量化口径）**：周期记录 `FieldMetric DAQ Phase=Running`（13:31:12.754–13:47:10.092，各设备 471 条，nearest-rank 分位，只代表离散快照分布）：

| 指标 | Dev1 | Dev2 |
|---|---:|---:|
| PersistenceDepth p50 / p95 / p99 / max | 0 / 2 / 5 / 9 | 0 / 2 / 6 / 10 |
| 深度为 0 的快照 | 362/471 | 330/471 |
| PersistenceOldestMs p50 / p95 / p99 / max | 0 / 19.9 / 50.7 / 83.0ms | 2.7 / 20.2 / 65.4 / 112.0ms |

正式期（13:33:57 起）p95 进一步降至 10.6/18.9ms。**日志中 107–110ms 的"持久化延迟"记录聚集是采样选择效应**：`DaqPersistenceCoordinator.EvaluateLag()`（HEAD 行号 1082）`if (age < 100) return;` 只在年龄跨越 100ms（硬编码，与 `ResumeAgeMs` 无关；后者仅在 `PauseLatched` 后参与恢复判定）时落日志，每设备约每秒一条。初版文档（v1）把告警样本误当稳态分布，推出"常态饱和/每批 fsync 10ms/零余量"，被周期记录否定。

**异常窗口的真实样貌**（IncidentSnapshots 两份 `daq_timing.csv`，各 1001 条 `Kind=Persistence`）：

- 异常前正常窗口（UTC 05:47:07–05:47:10.5）单次 `WriteBatch`（`ProcessingMs`，含整个提交路径）：p50=2.45/3.71ms（Dev1/Dev2），p95≈8–9ms，max≈35–53ms；
- 事件 2 中的慢调用：215.8 / 794.0 / 720.9 / 347.0 / 367.5ms；
- 事件 2 期间 `Persisted` 持续递增（吞吐≈70/42 批每秒对 100 批/秒到达），不是零进度；事件 1 同理（run.log:324–440 完成序列递增）；
- 该观测点的 `SqliteMs/RingWriteMs` 恒为 0（代码未填充），**无法把长尾归责到原始日志提交、索引提交、ring 刷新、通道锁或共享锁中的任何一项**——这正是 P2 分段计时的动机（工作区已有未提交的 `EpbDiskWriter.Timing.cs` 实现此方向，见第 6 节）。

**系统盘面**：事件 1 伴随写风暴（DiskWrite 91–104 MiB/s，DiskQueue 2–3，责任进程未定位，支持竞争假设）；事件 2 磁盘近乎空闲（≤8.8 MiB/s，DiskQueue 0–2）却出现同类长尾——低聚合吞吐与队列为 0 不能排除同步刷新长尾、过滤驱动或文件锁等待。两事件的共同点是**多秒级写入长尾跨越了 1s 年龄暂停线**；不同点要求整改不能押注单一归因。

### 2.2 放大层：升级链逐环——归并缺失与断电截止迟滞

```
持久化短时慢写/积压（1s 年龄安全暂停 / 256 批硬上限）
  →【事件 1 路径】暂停反压期间后台处理批次超 500ms 独立门限
      → 学习圈全速率证据作废（TailLag=∞, CutoffNotCovered）→ SoftwareRecoveryCircuitOpen(3)
      → 整批安全重建 → 进程内恢复失败（AbortCycle Expected=-616 Current=null；清场诊断值为空）
      → 外部接管 → 替换进程重启
  →【事件 2 路径】DaqPersistenceLag 局部恢复启动（预算 60s）
      → StaleDetected → OFF 提交迟滞 4.6–5.4s（对照事件 1 仅约 0.1s）
      → 越过看门狗 5s 断电确认预算 → PowerOffUnconfirmedTimeout 接管 StopAll（恢复仅进行 5.4s 即被取消）
      → TakeoverReplacementExit 退出 → 普通关闭取消接管 → 停机待人工
```

三个结构性问题：

1. **同一持久化事件多重升级**：事件 1 中队列满、处理时效超限、学习证据作废各自发布故障并各自消耗恢复/重试预算。归并到单一 CorrelationId、由单一恢复所有者收口，是低风险高收益的整改（详见 P3）。
2. **断电截止迟滞是事件 2 的直接扳机**：`StaleDetected→DoOffSubmitted` 之间 4.6–5.4 秒花在哪里（Timer.Pause、冻结边界、取消当前圈等同步阶段与回调）尚未分解——这是 P1 最需要补的测量。注意 5s 断电确认预算（`RequiredNoProgressSeconds=5.0`，旧版同值）与 60s 恢复预算约束不同对象，不能简单互相等待；但恢复进行中时，恢复截止阶段不应被写盘长尾/普通回调拖过断电预算。
3. **升级终点被关闭类型降级劫持**：见 2.3。

事件 1 暴露的两个恢复缺陷（现场构建 `3a954943` 堆栈行号）：`EpbDiskWriter.EnsureCurrentCycleIdentity`（EpbDiskWriter.cs:1414，经 `TryFinalizeManualStopCycle` EpbManager.cs:4661）拒绝 `Expected=-616 Current=null`；`PrepareForFreshRestartAsync` 清场不变量诊断输出空值（EpbManager.BatchStart.cs:1099）。它们是 HEAD 上 `3c000c8`/`fb498ba` 的修复对象，但**修复不等于本案闭环**（见第 3、4 节）。

### 2.3 终态层：接管退出被普通 SessionClose 提前取消

sidecar 同会话同接管事务的先后记录（sidecar-events.jsonl:27–35）：`TakeoverRequested`(16.861) → `StopCompleted CanClose=True`(23.747) → `RecoveryReplacementAdvanced State=Approved`(23.796) → `ApplicationExitRequested`/`TakeoverReplacementExitObserved`(23.811/816) → **`TakeoverCancelled Reason=ApplicationClosing`(23.962)** → `ApplicationClosing Reason=RuntimeShutdown`(23.964) → 连接结束。客户端在 23.951 已记录 `WatchdogClosingTombstoneReused Intent=SessionClose`。

生产代码链（现场构建与 HEAD 均如此，`git diff 3a954943..HEAD` 对相关文件为空）：

1. `Main_Frm.WatchdogUi.cs` `CompleteWatchdogCloseOnUiThreadAsync()` 先调用各监控子窗体 `AuthorizeApplicationExitAfterPreparationAsync()`，**之后**才按 `_watchdogExitIntent` 区分接管退出；
2. `FrmEpbMainMonitor.cs` 的该方法默认参数为 `RuntimeShutdownIntent.SessionClose`，安全边界允许关闭时调用 `ShutdownWatchdogSessionAndReleaseUiAsync`；
3. 会话关闭以 SessionClose 发出，`WatchdogRuntime` 将其映射为 `ApplicationClosing`；
4. `WatchdogHost` 收到旧式 `ApplicationClosing` 后设置 `ManualStopRequested=true`、`CancelAutomaticTakeover("ApplicationClosing")`、发布 ExpectedApplicationExit；
5. 主窗体随后再按接管类型关闭时只能复用已完成的关闭任务，无法撤回已发出的普通关闭。

最终 `application-exit.json` 仍声明 `TakeoverReplacementExit + PreserveApprovedPermit` 且六项安全终态为 true——**耐久退出意图与传输层关闭消息不一致**。墓碑 `OldProcessExitProven=false`、替换状态止步于 Approved、无新 PID 启动记录：现有证据是"安全退出交接中止"，不能写成重启全流程已走完。修复方向与回归用例见 P0 与 [Codex 复核](2026-09-06_V2.17.1.0_I0046_封存证据复核与版本对齐建议_Codex.md) 第 6 节。

## 3. 与 2.14.2.11 的语义对照（勘误后）

| 项目 | 两版核对结果 | 对齐意义 |
|---|---|---|
| 75/100/250、四年龄、Trip 一次确认 | 现场生效且未被触发（`DAQ_LIVENESS Result=Configured` + 哈希链） | 本案不能归因于这些参数；也不能据此宣称"所有场景零误报" |
| 持久化队列满反压 | **旧版已有**（`6ed4d47` DaqPersistenceCoordinator.cs:291 `q.Slots.Wait(_cts.Token)`） | 该耦合不是新版新增 |
| 后台处理 500ms 独立门限 | **旧版已有**（`6ed4d47` IO.NI/TwoDeviceAiAcquirer.cs:1392 `hardAgeMs=500`） | 相同阈值遇不同负载结果不同 |
| OFF 未确认 5s 接管 | **旧版已有**（`RequiredNoProgressSeconds=5.0` 两版同值） | 新版改变的是撞上该短窗的频率与场景，不是短窗本身 |
| raw-journal 持锁同步提交 | 新版新增（FULL、共享 gate、每设备批次事务在热路径） | 有性能与跨设备锁竞争风险，但**尚未证明是本次慢写根因**，需 P2 分段计时 |
| 恢复尾部抑制 | 新版 `TryHandleSuppressionUnderGate()` 对原始日志记录器返回 false，继续耐久写入 | **数据承诺改变了恢复负载**，是只比参数看不到的实质差异 |
| raw checkpoint | 新版 `CheckpointRawJournal()` 做 Flush(true)+索引提交后回收 frames | 诊断须覆盖整条耐久路径，不只量事务 Commit |

采样口径勘误：两版均为 2000Hz/20 点，名义 100 批/秒/设备；设备批次写入机会 ≈200 次/秒**不等于** 200 次真实 fsync（活跃圈、边界、空事务都会改变实际写入内容）；两设备共享 raw gate，单设备 10ms 到达间隔不能当作共享日志的单次同步成本。`RawDataLoggingEnabled=false` 不能关闭该路径；raw-journal.db 文件 647KB 不能推出历史写入量或 IO 成本（checkpoint 会回收 frames）。

## 4. 对齐方案（按优先级）

### P0：修通退出交接（置信度最高、可直接回归的确定缺陷）

按第 2.3 节链条整改：子窗体只提交硬件/数据释放凭证，最终传输关闭由主进程退出所有者带完整类型执行（或全程传递冻结的退出意图）；防止普通 SessionClose 覆盖已确立的接管退出；sidecar 收到旧式普通关闭时先核验同会话/租约/事务的有效替换退出凭证再决定取消。必须保留人工停止的明确撤权路径（PID+启动时间、代际、许可、事务身份核验），避免旧许可覆盖真实人工意图或产生双主进程。

对每次接管要求完整可审计结果：安全终态 → 旧 PID 退出证明 → 许可消费 → 新 PID 及启动时间 → 恢复提交；无法自动恢复时给出具体阻断原因，不允许静默消失。

### P1：先完成关电截止，再等待数据收口

围绕事件 2 的 `StaleDetected→DoOffSubmitted`（4.6–5.4s）补阶段计时：Timer.Pause、取消回调、圈边界冻结、各锁；避免同步业务回调挡住全组 OFF 投递。电源确认必须基于当前代际、当前操作、新鲜可回读的 OFF 证据：证据已满足而监督仍投影未关电则修投影；OFF 未发出或未确认则修截止执行并保留安全接管。数据排空与模型重建可用长预算，物理关电不应仅因 `RecoveryActive` 无限延后。

### P2：测量并优化完整写盘路径（先测量，后优化）

现有周期记录 + 逐批 CSV 已给出正常与异常总耗时；下一步是分段直方图（通道锁等待、raw gate 等待、原始事务准备/提交、索引事务、ring/MMF flush、checkpoint 回收、圈关闭/导出），记录线程与批次身份、数据卷延迟/IOPS，事件触发 ETW/线程栈。

优化原则：保持耐久语义优先——减少重复序列化/分配与 SQL 准备开销；评估有界 group commit；把可独立导出/清理移出关键持锁段（若移出通道锁，须先设计不可变批次所有权与提交复核）。**`Synchronous=Full→Normal` 不作为默认现场修复**：WAL+NORMAL 在 OS 崩溃/断电时可能回滚最近已提交事务（不限于"最后一批"），且本系统存在索引/ring/raw journal 之间的耐久先后关系，单降一项会改变跨文件恢复承诺；group commit 只能作为实验参数，须验证"提交前崩溃不提前认定持久化、提交后重放不漏不重"后才可上现场。Defender 排除项同理：先定位过滤驱动/扫描是否占用文件，有证据再做受控对照。

### P3：归并相关故障，保留有界升级

把同一持久化事件引起的队列满、处理时效告警归并到单一 CorrelationId，由当前恢复所有者收口，避免重复撤销执行体、重复消耗重试预算。**不做无条件豁免**：无法保存有效试验证据、持续无法确认关电、恢复执行体失效仍必须有界升级。正常处置序：短时延迟观察 → 达到积压边界安全暂停 → 同事件仅一次恢复 → 证据完整时恢复/重作废圈 → 长期无进展、真实数据缺口或物理安全未确认时升级。学习峰值证据不完整仍应作废相关尝试，不得继续更新学习模型或计有效圈。

3. **同机版本对照与长稳**：旧版/现场基线/修复版同机同工程同 6 通道，版本间用隔离数据副本；区分启动/学习/正式阶段重复试验。验收维度：
