# 10358-029 V2.13.0.9 人工暂停误接管与无限自启动失败根因及解决方案

## 1. 结论先行

对以下封存数据、5 张现场截图、两组 Watchdog 会话、事故 manifest、项目日志和 V2.13.0.9 对应源码进行只读交叉检查后，结论如下：

```text
封存目录：\\wj-epb\EPB_Data\10358-029_V2.13.0.9_0816_1754
程序版本：V2.13.0.9
现场启用通道：EPB04、05、09、10、11
试验周期：15 s
```

本次不是一个故障，而是前后相接的两个故障链：

1. **人工暂停误接管是确定性的程序门限缺陷。** 操作员在 `17:44:47.169` 点击暂停后，程序本来正在等待 5 个通道安全完成当前圈。Watchdog 仅等待约 5 秒，看到仍有通道带电，就在 `17:44:53.963` 将合法 `ManualPausePending` 判为 `ExternalRecoveryStageStalled`。实际当前圈直到 `17:44:55.186` 才能自然收口。因此，V2.13.0.9 的“人工暂停仍带电 5 秒即接管”门限短于正常当前圈的最坏收尾时间。
2. **弹窗不是普通暂停窗，而是 Watchdog 已经开始杀原进程前的安全接管窗。** 接管先启用 StopAll 安全栅栏，正在收尾的 EPB05、EPB11 随后被栅栏拒绝继续执行，暂停管理器再看到“停机或联锁”，于是人工暂停被反向升级为立即安全停止，最终出现截图中的“人工暂停安全确认异常”。
3. **第一次误接管最终确实安全回到了空闲态，没有自动续跑。** 原 PID `22824` 在 `17:45:09` 被结束，Watchdog 拉起 PID `1484`，新进程在 `17:45:14.490` 完成 Motor/Power/Pressure/Persistence/Logical 全项确认。随后是操作员在 `17:45:46` 再次主动开始试验。
4. **第二次开始后又发生了一个独立的真实基础设施异常。** `17:48:17` 前后 Dev1、Dev2 同时出现 DAQ 回调空窗，多个程控电源同时出现 SCPI 响应超时，继而触发 `PowerDisablePendingTimeout` 接管。这不是第一次人工暂停弹窗的延迟显示。
5. **无限自启动的直接原因是恢复预检每次都卡在电源断能证明，Watchdog 又没有最大重启次数。** 每个恢复进程都能启动、连接 Watchdog，但组 1、2、4 的 TCP/SCPI 会话在已写出 `*IDN?` 后，`1999 ms` 内收不到完整响应。恢复进程因此不能验证设备身份、不能取得可靠的 `OUTP OFF` 回读，正确地拒绝重新学习；随后 Watchdog 把 `RecoveryAttemptFailed` 当成永久可重试事件，按 `5/15/30/60/60...` 秒不断新建进程，形成截图中的第 4、5、6 次循环。
6. **不能为追求自恢复而绕过 Power OFF 证明。** 当前“未确认断能就拒绝学习”属于正确的 fail-closed 安全行为。需要修的是重试架构、连接生命周期和人工暂停门限，而不是把未知电源状态当成 OFF。
7. **第二次基础设施异常的最底层外部原因尚不能唯一归因。** 证据足以证明是跨双 DAQ、跨多个电源的共享异常，但封存目录没有完整事故 `daq_timing.csv/daq_runtime.csv`、Windows Time-Service/NIC/磁盘/NI 驱动事件，不能严谨地写成“某块 DAQ 坏了”“一定是 GC”或“一定是 Windows 校时”。高频成功通信日志和高磁盘负载是明确的风险放大项，但当前只能列为重要嫌疑，不能当作唯一已证实根因。

综合判定：**V2.13.0.9 不满足无人值守发布门槛，应停止继续扩大现场运行，先完成本文 P0 改造和故障注入验收。**

## 4. 为什么人工暂停没有直接变成“暂停”

### 4.1 正确语义不是瞬间显示“已暂停”

操作员点击暂停时，部分电机正在夹紧或释放。程序需要：

1. 阻止下一圈开始；
2. 让当前圈安全完成反向释放；
3. 确认 DO OFF；
4. 释放液压租约；
5. 排空 Raw/SQLite 持久化边界；
6. 最后才能宣布 `Paused`。

所以 UI 不应在点击瞬间伪称“已暂停”，而应立即显示 **“暂停处理中：等待当前圈安全释放”**，并在安全边界完成后切到“暂停”。本次错误不是“没有瞬间进入 Paused”，而是正常 `PausePending` 被 Watchdog 过早打断并弹出接管窗。

### 4.2 确定的代码根因

当前逻辑在 `MTTFTest.Watchdog/WatchdogHost.cs` 中记录人工暂停开始时间，并用以下条件作为人工暂停不安全：

```text
ManualPausePending/Active
AND EnergizedChannelCount > 0
AND ManualPauseAge >= 5 s
```

该条件在 `WatchdogHost.cs:503` 传给 `WatchdogTakeoverPolicy.ShouldTakeover`。`WatchdogPolicy.cs:112` 对人工暂停仅保留该 `manualPauseUnsafe` 结果。

问题是：

- 试验周期为 `15 s`；
- 本轮从约 `17:44:45` 开始；
- 操作员在 `17:44:47` 中途请求暂停；
- 当前圈实际到 `17:44:55` 才全部收口；
- `5 s` 门限在正常收尾完成前约 1～2 秒触发。

因此门限本身必然会在某些相位误报，属于确定性设计错误，不是偶发竞态。

### 4.3 为什么随后出现“EPB05、11 停机或联锁”

Watchdog 在 `17:44:53.963` 发出 `RequestStopAll` 后，Controller 建立停止安全栅栏。EPB05、11 仍在当前圈收尾，后续命令收到：

```text
InvalidOperationException:
停止安全栅栏已生效，拒绝 EPB05/EPB11 上电命令。
```

暂停管理器再检测到这两个通道已经进入停机/联锁，便按 fail-safe 规则取消优雅暂停并升级为立即停止。所以弹窗原因链是：

```text
5 秒门限过短
  -> Watchdog 误接管
  -> StopAll 安全栅栏生效
  -> 当前圈命令被拒绝
  -> EPB05/11 被标成停机/联锁
  -> 人工暂停失败并显示安全接管窗
```

EPB05、11 的“软件异常”是误接管造成的次生结果，不能倒过来当成人工暂停误接管的原始原因。

## 5. 为什么重新开始后陷入无限自启动

### 5.1 第二次开始本身成功

`17:45:46` 的重新开始完成了：

- 5 个通道重新学习 10 圈；
- `17:47:45` 学习 manifest 发布成功；
- 5 个正式 Timer 已创建；
- UI 输出“批量启动完成”。

因此“无限自启动”不是开始按钮一直没有执行，而是开始成功后又发生第二次基础设施异常，随后无人值守恢复一直通不过安全预检。

### 5.2 第二次安全接管的直接触发

事故 manifest 记录：

| 设备 | 触发 | 单调时钟观察到的最近回调空窗 | 受影响通道 |
|---|---|---:|---|
| Dev2 | `DaqCallbackStale` | `1360.013 ms` | 9、10、11 |
| Dev1 | `DaqCallbackStale` | `2684.024 ms` | 4、5 |

同一窗口还出现：

- 程控电源 `SOUR:VOLT:PROT?` 响应超时；
- 组 4 遥测任务 `2500 ms` 内不能退出；
- 电源遥测数据过期；
- 液压压力样本过期；
- DAQ 恢复因无法确认电源组断能而被禁止。

这说明触发层不是某一个 EPB 卡钳的机械故障，而是跨双 DAQ、跨多个电源通信的共享主机/系统/基础设施停顿。

### 5.3 每个恢复进程为什么都失败

恢复进程进入 `FrmEpbMainMonitor.ResumeFromWatchdogCheckpointAsync` 后，必须先执行：

```text
DO AllOff
-> StopAllAsync
-> MotorOffConfirmed
-> PowerOffConfirmed
-> PressureSafeConfirmed
-> 才允许重新学习
```

程控电源客户端在 `PowerSupply.Core/PswTcpClient.cs:114` 建立连接后先发送 `*IDN?` 验证仪器身份。错误文本为：

```text
Group1: PowerOffUnconfirmed: *IDN? response 超时（1999 ms）
Group2: PowerOffUnconfirmed: *IDN? response 超时（1999 ms）
Group4: PowerOffUnconfirmed: *IDN? response 超时（1999 ms）
```

`PswTcpClient.cs:284～370` 表明该错误发生在命令已写出之后的响应读取阶段，而不是配置文件缺 IP。至少可以确定：TCP/写命令阶段已经走到响应等待，但仪器没有在时限内返回完整响应。可能原因包括仪器 LAN/SCPI 服务无响应、旧会话未释放、共享交换机/主机网络异常或设备只允许有限连接；现有证据不能在这些候选中唯一选择。

身份无法验证时，客户端按安全策略禁止写控制命令；输出 OFF 又得不到可靠回读，所以恢复进程不能继续学习。这一拒绝是正确的。

### 5.4 为什么会无限重启而不是停在安全页

`MTTFTest.Watchdog/WatchdogHost.cs:731～813` 的 `RelaunchLoopAsync` 是无上限 `while`：

```text
Attempt 1 -> 5 s
Attempt 2 -> 15 s
Attempt 3 -> 30 s
Attempt 4+ -> 60 s
```

代码没有：

- 最大进程重拉次数；
- 同错误指纹熔断；
- “硬件仍不可用时留在同一个安全恢复进程内重连”的状态；
- 从“进程启动失败”切换为“硬件通信等待”的分类。

每个恢复进程在约 7 秒内以相同 `*IDN?` 错误退出，Sidecar 又创建下一个完整 GUI 进程。只要组 1、2、4 不恢复响应，这个循环理论上永远不会结束。

## 6. 第二次共享异常能确认到哪一层

### 6.1 已排除或不支持的说法

- **不是数据库/持久化队列积压。** 事发前 Dev1/Dev2 持久化状态为 `Recovered`，队列深度为 0，没有永久数据洞。
- **没有证据证明内存耗尽。** 事发前主机可用内存约 `9.6～10.2 GiB`，进程工作集约 `200～218 MiB`。
- **没有证据证明 CPU 打满。** 事发前进程 CPU 约 `6.8%～22.3%`，系统 CPU 约 `14.5%～39.8%`。
- **不支持“两块 DAQ 同时物理损坏”的直接结论。** 双 DAQ、多个电源通信和压力样本在同一窗口失效，更像共享主机、调度、日志/磁盘或网络基础设施异常。
- **不能写成已确认 Windows 校时跳变。** 本次封存没有 `WallClockStepDetected` 的持久证据，也没有 Windows Time-Service 事件。

### 6.2 明确的风险放大项：成功通信日志过量

从 `17:26:05` 到 `17:54:43`，仅 `run*.log` 就写入：

```text
总量 = 284,867,725 bytes = 271.67 MiB
平均 = 9.49 MiB/min
50 MiB 轮转文件 = 5 个
```

主要来源是每个电源遥测查询都记录：

- SCPI Write Started/Completed；
- Response WaitStarted；
- FirstByte Completed；
- FullLine Completed；
- 命令与端点详情。

这类成功路径日志以高频 Info 同时进入项目日志队列和 UI Info 队列。事发前 HostRuntime 还观察到磁盘队列 `6～21`，瞬时磁盘写入最高超过 `200 MiB/s`。这些证据不能单独证明日志就是 DAQ 空窗的唯一原因，但它显著增加分配、UI 队列、后台写盘、轮转和杀毒扫描压力，必须在下一版先治理。

### 6.3 事故证据仍有缺口

两个事故目录都只有：

- `build-identity.json`
- 仅包含 `00-trigger` 的 `manifest.jsonl`

没有实际落地：

- `daq_timing.csv`
- `daq_runtime.csv`
- 事故终态 manifest
- Windows 时间/NIC/磁盘/NI 驱动事件
- 电源最近 N 条通信环形缓冲快照

所以本文将“共享主机/基础设施停顿”作为已确认层级，把更底层原因保留为待验证项。

## 7. 必须落地的解决方案

### 7.1 P0：重做人工暂停 Watchdog 判定

禁止继续使用：

```text
ManualPause && EnergizedCount > 0 && Age >= 5 s
```

建议改为显式暂停协议：

```text
ManualPauseRequested
  -> PausePending(CurrentCycleDrain)
  -> PausePending(PhysicalOffConfirm)
  -> PausePending(PersistenceDrain)
  -> ManualPaused
```

Heartbeat 至少增加：

- `ManualPauseStage`
- `ManualPauseProgressVersion`
- `ManualPauseStageStartedMonotonic`
- 每通道当前机械阶段
- 每通道 `OffSubmitted/OffConfirmed`
- 当前仍带电通道清单，而不是只有数量
- Controller 计算出的暂停硬截止

Sidecar 判定规则：

1. 主进程死亡或心跳超过 5 秒，仍可立即安全接管；
2. `PausePending` 中只要阶段或带电集合持续收敛，就不得按恢复停滞接管；
3. 暂停硬截止应按控制硬时限计算，建议不小于：

   ```text
   max(30 s, 2 × Period, ForwardHardLimit + ReverseHardLimit + OffConfirm + 5 s)
   ```

4. 只有 Controller 明确发布 `ManualPauseSafetyFault`，或超过上述硬截止且同一带电集合无进展，才执行 `ManualPauseSafetyTakeover`；
5. 人工暂停安全接管仍只能 `LaunchIdleRestart`，绝不能自动续跑。

UI 行为同步改为：点击后立即显示“暂停处理中/等待当前圈安全释放”，正常完成后显示“暂停”；只有真实超过硬截止才显示异常接管窗。

### 7.2 P0：把“进程重拉”和“硬件通信等待”分成两种恢复

当前每次硬件不响应都退出并重建整个 GUI 进程，既不能清除仪器侧故障，又增加 socket、日志和进程生命周期复杂度。

建议状态机：

```text
Watchdog 启动恢复进程（最多 1 次）
  -> DO AllOff
  -> PowerSafetyProbe
     -> 成功：完整 StopAll 复核 -> 自学习 -> 正式运行
     -> 失败：保持同一恢复进程和安全页，进入 HardwareUnavailable
        -> 内部销毁全部电源客户端/socket
        -> 5/15/30/60 s 有界重连
        -> 恢复后从完整 StopAll 重新验证
```

只有以下情况才允许重新拉进程：

- 恢复进程本身崩溃；
- 20 秒内无法附着 Watchdog；
- UI/Controller 初始化失败；
- 进程心跳丢失。

`*IDN?`、TCP、仪器不可达等硬件通信失败不应反复创建新进程；应由一个可见的安全恢复进程原地等待。

### 7.3 P0：增加相同故障指纹熔断

至少按以下字段组成指纹：

```text
RecoveryStage + FailedGroups + Endpoint + Command + FailurePhase + ErrorCode
```

相同指纹连续 3 次时：

- 停止“新建进程”动作；
- 保持 DO OFF、禁止开始、禁止自学习；
- 状态切换为 `SafeIdleHardwareUnavailable`；
- 页面显示失败组、IP、阶段、最后成功时间、下一次通信探测倒计时；
- 继续低频通信探测，但不再增加 RecoveryProcess 数量；
- 提供“取消自动恢复/人工停止”按钮；
- 设备恢复后必须重新执行全部身份、OUTP OFF、遥测和压力验证，不能直接跳到学习。

### 7.4 P0：程控电源连接与断能证明闭环

1. 每次连接/查询异常后必须 Dispose `TcpClient/NetworkStream/Writer`，下一次创建全新客户端；
2. 旧主进程被强杀后增加明确的“仪器会话释放”阶段，但不能仅依赖固定等待；
3. 保存每组最近一次已验证 identity、连接 epoch、socket 本地/远端端点和最后正常响应 UTC；
4. 将 TCP Connect、SCPI Write、FirstByte、FullLine 分阶段失败写入故障指纹；
5. `*IDN?` 不响应时仍保持未知态，禁止把未知当 OFF；
6. `OUTP OFF` 最终必须有独立可靠证据：设备 `OUTP?`、电压/电流遥测，或经安全评审的外部接触器/硬件回读；
7. 如果仪器确认只允许单连接，应将连接所有权集中到常驻独立电源代理，而不是让每个恢复进程直接创建新会话。

### 7.5 P0：成功通信日志降噪，失败证据用环形缓冲保留

建议：

- 成功 `PowerCommPhase` 默认不写 Info 文件、不进入 UI；
- 每个电源只保留内存环形缓冲最近 256～1024 条阶段记录；
- 正常状态每 30～60 秒写一条聚合统计：P50/P95/P99/Max、超时数、重连数；
- 只有 TimedOut/Failed/Canceled 立即写 warning/error；
- 事故触发时把环形缓冲一次性导出到 IncidentSnapshot；
- 日志量门禁建议小于 `100 MiB/24h` 的日常运行基线，事故证据单独限额；
- UI Info 队列不接收逐命令通信详情。

### 7.6 P1：补齐共享停顿根因证据

下一版事故包必须原子写入：

- 双 DAQ 最近 60 秒 `daq_timing.csv`；
- `daq_runtime.csv`，包含 GC、CPU、内存、线程池、磁盘队列；
- `WallClockStepDetected` 直接进入事故 manifest，不只异步写普通日志；
- Windows Time-Service、NIC、Disk/StorPort、NI-DAQmx 相关事件；
- 电源通信环形缓冲；
- 日志队列深度、丢弃数、轮转耗时；
- 事故 terminal manifest 和导出失败原因。

若重证据导出失败，也必须先写一个小型、同步、可校验的 failure receipt，不能再次只留下 `00-trigger`。

### 9.1 人工暂停

## 11. 对现场问题的直接回答

### 为什么手动暂停没有直接到“暂停”，而弹出这个窗口？

暂停需要先安全完成当前圈，不能瞬间伪装成 Paused。V2.13.0.9 的错误是 Watchdog 只给了约 5 秒，正常当前圈尚未收尾就把“暂停处理中”判成异常；它启动 StopAll 后又让 EPB05、11 的收尾命令被安全栅栏拒绝，最终把本来正常的人工暂停制造成了安全停止弹窗。

### 为什么后面重新开始陷入无限自启动？

重新开始实际成功并完成了学习。之后双 DAQ 与多个电源通信在 `17:48:17` 附近发生共享异常。每个恢复进程都在安全预检阶段遇到组 1、2、4 的 `*IDN?` 响应超时，无法证明电源已 OFF，所以拒绝学习并退出；Watchdog 对这种失败没有最大次数，5/15/30 秒后固定每 60 秒创建一个新进程，因此形成无限循环。

### 应该怎么修？

把人工暂停门限改成“阶段进展 + 动态硬截止”，不要固定 5 秒；硬件通信失败时保留一个可见的安全恢复进程原地重连，不要反复拉新 PID；相同故障 3 次后熔断进程重拉并进入 `SafeIdleHardwareUnavailable`；继续保持“电源 OFF 未确认就绝不学习”的安全底线；同时把高频成功通信日志改成环形缓冲和故障时导出。

## 12. 最终判定

本次已能闭环解释两个用户可见现象：

```text
人工暂停弹窗
  = 合法 PausePending 被固定 5 秒安全门限误接管

无限自启动
  = 第二次共享基础设施异常
  + 恢复进程反复卡在 *IDN? / PowerOffUnconfirmed
  + Watchdog 无最大进程重拉次数
```

第一条根因已达到代码级确定；第二条的“无限进程重拉机制”和“每次失败门槛”已达到代码级确定，但触发第二次共享停顿的最底层 Windows/网络/日志/驱动原因仍需补齐事故证据。修复时必须同时解决状态机和取证能力，不能只把重试次数改大，也不能降低断能安全门槛。
