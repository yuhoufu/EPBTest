## 1. 结论先行

这两次不是同一种“启动后崩溃”，也没有证据证明是 CLR 未处理异常或 NI 硬件同时掉线。它们的前因不同，但最后都进入了同一条失效的跨进程恢复链。

| 运行 | 首个直接触发 | 同进程恢复结果 | 主进程如何退出 | 为什么没有恢复 |
|---|---|---|---|---|
| I0043，PID 18056，会话 `55b970...` | Dev1 的 64 批 DAQ 原始读取分发队列溢出；现场同时出现明显系统/其他进程 CPU 峰值和 UI 长延迟 | 失败：学习任务取消时使用了已释放的 `CancellationTokenSource`，清场还残留 `ActiveCycles=5`，Dev2 持久化状态一度为 `Failed` | Watchdog 接管约 31 秒后主动终止旧进程，不是进程自行崩溃 | Watchdog 构造 schema 7 的关闭墓碑，但存储校验只接受 schema 1—6；安全代理虽完成，重启前置条件仍一直判为 `MissingOrCorrupt`，新主进程 PID 始终为 0 |
| I0044，PID 22976，会话 `198307...` | 正式阶段首批回调相差约 596 ms；300 ms 准入窗先冻结，EPB4/5/7 连续被 `AdmissionWindowClosed` 排除，EPB4 60 秒无机械动作 | 实际已经成功：6 通道重新学习 10 圈、发布 Successful manifest、建立新正式运行；但监控竞态把“无边界”的空字符串当成真实外部边界，立即撤销刚恢复的批次 | 主程序收到 Watchdog 退出请求后，关闭墓碑写入失败，等满本地 30 秒硬期限后执行强制退出 | 同一 schema 7/仅接受到 6 的错误；墓碑写失败又生成 `.revoked`，Watchdog 将其解释为 `SessionRevoked` 并停止接管，因此不会拉起替代进程 |

最重要的共同根因是一个确定性的协议版本错误：

1. `SupervisorProtocol.SchemaVersion` 已升为 **7**；
2. 主程序和 Watchdog 都把这个值写进 `WatchdogClosingTombstone`；
3. `WatchdogClosingTombstone.IsValidFor` 仍只接受 **1—6**；
4. 所以 V2.17 当前构建只要走到关闭墓碑持久化，就必然抛出 `Watchdog closing tombstone identity is incomplete.`；
5. 没有有效墓碑，跨进程恢复被安全策略正确地阻止；I0044 又把写失败转换成会话撤销，连负责恢复的 Watchdog 也退出。

因此，对用户三个问题的直接回答是：

- **两次根因不同。** I0043 的起点是 DAQ 软件分发积压；I0044 的起点是正式槽准入窗口冻结造成通道长期无动作。
- **不能恢复不只是最初故障太重。** I0043 的同进程清场确实失败；I0044 的同进程恢复其实已经成功，却被空字符串竞态误升级。两次到了跨进程接管后，又都被关闭墓碑 schema 不兼容卡死。
- **V2.17 比 V2.14.2.11 更容易表现为整程序退出，是“更容易进入恢复 + 最后一级恢复确定失败”的组合。** V2.17 新增/收紧了 DAQ 分发与存活监督、实际动作无进展监督；与此同时 schema 版本升级遗漏了关闭墓碑校验，导致原本应当是“停机、重建、拉起”的路径变成“退出后无人拉起”。

> 置信度：关闭墓碑 schema 错误、I0043 的退出方式、I0044 的空边界误升级和强制退出均为高置信/代码与耐久记录直接证明。I0043 队列溢出的直接事实为高置信；造成消费线程长期得不到运行的具体外部进程，只能中等置信地归于当时的系统调度竞争，因为本次证据没有该秒的完整逐进程 CPU 快照。

### 1.1 不是所有进程退出都由 DAQ 新鲜度造成

必须区分三个概念：**首次运行故障、恢复升级原因、进程最终退出原因**。DAQ 新鲜度可能是上游触发，但只有在后续局部恢复、安全清场或跨进程接管不能收敛时，才会演变为进程退出；反过来，进程退出也可能完全由非 DAQ 路径或人工操作触发。

截至本次提供的封盘，结论如下：

| 证据范围 | 首次运行故障 | 进程退出的直接原因 | 是否可称为“DAQ 新鲜度导致退出” |
|---|---|---|---|
| V2.14.2.11 中有耐久回执的 7 次自动替换退出（I0024、I0030—I0035） | 7 次在退出请求前 90 秒内均有 `DAQ_FRESHNESS_SAFETY_CUTOFF` / `DaqSampleStale`；I0024 同时出现持久化队列满、DAQ 后台积压和 Timer 心跳陈旧；其余事件还出现 `HydraulicSampleStale`，其中 5 次继续扩大为正式槽安全边界/关断确认失败 | `TakeoverReplacementExit`；由停止安全监督/Watchdog 要求旧进程让位 | **上游均涉及 DAQ/压力样本陈旧，但不能说新鲜度是唯一根因。** 退出还依赖安全屏障、关断确认和恢复收口缺陷 |
| V2.14.2.11 I0040，PID 18504 | 20:34 有约 1,176 ms 回调空窗并触发 `HydraulicSampleStale` | 20:51:35 耐久事件明确为 `ManualStopIntent=操作员点击停止试验` | **直接退出原因不是 DAQ，而是人工停止/关闭**；此前 DAQ 空窗解释故障态，不应替代退出意图 |
| V2.17 I0043 | `DaqReadDispatchOverflow`：原始读取分发队列满；它是 DAQ 数据链故障，但并非一次 `DAQ_FRESHNESS` 比较器 Trip | 同进程恢复残留 `ActiveCycles=5` 等状态，随后 Watchdog 主动终止 PID 18056 | **宽口径属于 DAQ 起因；严格口径不是“新鲜度门槛触发”** |
| V2.17 I0044 | 300 ms 正式槽准入窗冻结，后到通道持续被排除，最终 `ExecutionProgressDeadline` | 同进程恢复成功后被空边界竞态误升级；关闭墓碑失败，30 秒期限后主程序强制退出 | **不是 DAQ 新鲜度原因** |

### 5.3 空字符串/`null` 判定错误把成功恢复误判成外部边界

## 7. 为什么比 V2.14.2.11 更容易出现完全退出

### 7.1 不是一个参数，而是四层组合效应

| 层次 | V2.14.2.11 | V2.17.0.0 | 对“完全退出”的影响 |
|---|---|---|---|
| DAQ 入口 | 没有 V2.17 的独立 `DaqReadDispatcher.cs` 有界原始读取分发路径 | 新增容量 64、满即 `DaqReadDispatchOverflow` 的明确故障入口 | 同样的 0.6 秒级调度停顿更容易被转换成 DAQ 恢复事件 |
| DAQ 存活监督 | Warn/Suspect/Trip 为 250/1500/5000 ms，Trip 连续 3 次，主要看 CallbackAge | 75/100/250 ms，Trip 1 次，取 Callback/Sample/ControlEnqueue/ControlProcessed 最大年龄 | 对短时调度和处理停顿更敏感，更早进入保护/恢复 |
| 执行进展监督 | 没有 `EpbManager.ExecutionProgress.cs` | 新增 max(60 秒, 3×周期) 无实际动作期限 | I0044 这类 Timer/Runner 存在但未动作的问题会被主动升级，不再无限挂住 |
| 跨进程恢复终态 | Supervisor schema 5，关闭墓碑接受 schema 5 | Supervisor schema 7，关闭墓碑只接受到 6 | 一旦升级到跨进程路径，V2.17 当前构建确定无法建立关闭墓碑，因而退出后无法正常替换 |

前 3 层本意是更早发现真实停顿，安全方向并非错误；真正导致“更容易整程序消失”的是它们把更多事件送进第 4 层，而第 4 层在当前包中确定失效。

### 7.2 V2.14 对照证据

V2.14.2.11 I0040 从 19:54:40 启动，正式运行后直到 20:34:49 才因液压样本过期进入局部软件恢复；它把相关通道收敛到 `HydraulicRecoveryTerminalWithoutRejoin`，没有在首分钟直接触发整进程接管，见 [既有证据摘录:349](D:/Github/wanxiang/EPBTest/docs/02_Issues/附件/I0037-I0040/证据摘录.md:349) 至 [既有证据摘录:415](D:/Github/wanxiang/EPBTest/docs/02_Issues/附件/I0037-I0040/证据摘录.md:415)。

### 7.3 哪些缺陷不是 V2.17 新增

需要避免把所有问题都归到版本新增：

- 全局正式槽协调器在 V2.14 与 V2.17 候选之间没有代码差异；I0044 暴露的是既有 300 ms 机会式准入在启动抖动下的饿死风险。V2.17 新增的是能在 60 秒后把它识别出来的执行进展监督。
- 空字符串/`null` 的恢复监控竞态在 V2.14 参考代码中也存在；它是潜伏缺陷，本次被成功恢复恰好落在 500 ms 监控窗口而触发。
- I0040 已出现多条 `CyclePauseCts.CancelDispose` 的 `ObjectDisposedException`，见 [既有证据摘录:416](D:/Github/wanxiang/EPBTest/docs/02_Issues/附件/I0037-I0040/证据摘录.md:416) 至 [既有证据摘录:419](D:/Github/wanxiang/EPBTest/docs/02_Issues/附件/I0037-I0040/证据摘录.md:419)。I0043 的 CTS 生命周期问题不是凭空在 2.17 首次出现，说明相关清场修复仍不完整。

所以更准确的表述不是“2.17 新增了所有 Bug”，而是：**2.17 增加了故障发现与升级入口，却同时引入了跨进程关闭协议的致命不兼容；既有恢复竞态和 CTS 生命周期残留因此更容易被放大成完整退出。**

### 7.4 样本量限制

本轮 V2.17 是 2 次运行、2 次完全退出；它足以证明当前构建存在可重复的结构性失败链，尤其 schema 错误是代码确定性的。但 2 次样本不能给出“退出概率提高多少”的统计结论。本文的“更容易”是基于执行机制与两次现场命中的因果链，不是用 2/2 估算长期失效率。

## 9. 修复优先级

### P0：先恢复“退出后一定能回来”的协议闭环

1. **统一关闭墓碑 schema。** 不应只把一处常量从 6 改到 7；应让墓碑生产者、存储校验、读取、Supervisor/SafetyAgent/sidecar 的兼容策略使用同一权威版本，并补 schema 7 往返测试。
2. **区分墓碑写失败与会话撤销。** 接管恢复中写墓碑失败必须 fail-closed，但不得写会让 sidecar 自行终止的 `LegacyRevocationMarker`；应保留恢复所有权、持续补建安全证据或进入明确的人工介入终态。
3. **修复空字符串三态。** 用 `IsNullOrWhiteSpace` 或强类型结果，并覆盖“任务恰好在 500 ms 轮询间隔完成”的竞态测试。

### P1：修复触发与同进程清场

4. **正式槽参与者应在批次开始时声明，而不是靠首个回调后的 300 ms 机会式收集。** 至少要保证计划参与通道即使首回调晚于 300 ms，也不会永久在每个槽被排除；扩大窗口只能降低概率，不能消除语义缺陷。
5. **修正 CTS 所有权和 `ActiveCycles` 终态清理。** Cancel/Dispose 必须由唯一所有者执行；清场完成时所有 active cycle 注册必须可幂等移除。I0043 的 CTS 异常与 5 个残留圈应有独立并发回归测试。
6. **为 64 批 DAQ 分发队列增加可归因性。** 记录高水位、最老批次年龄、消费者阶段耗时和线程停顿；避免仅通过扩大容量掩盖消费者阻塞。容量策略要能吸收经现场测量的启动调度抖动，同时保持数据连续性和安全暂停语义。
7. **持久化恢复状态应与“队列已排空”一致收敛。** I0043 出现 Published=Persisted、Depth=0 但 State=Failed/Closed=false，需检查状态机终态提交与 Stop 并发。

## 11. 最终判定

1. **I0043 根因：** Dev1 DAQ 有界分发队列在现场调度高负载窗口溢出；恢复阶段又命中 CTS 重复处置、活动圈残留和持久化状态未收敛，同进程重建失败。随后 Watchdog 按设计杀旧进程，但 schema 错误使安全墓碑无法建立，替代进程未启动。
2. **I0044 根因：** 300 ms 正式槽准入设计在约 596 ms 的启动回调分散下持续饿死后到通道，进展监督触发整批恢复；恢复实际完成后，空字符串竞态错误升级到外部接管。主程序因墓碑写失败无法正常终态化，30 秒后强制退出；`.revoked` 又终止 Watchdog，替代进程未启动。
3. **V2.17 更容易“完全退出”的核心：** 更严格/新增的监督使停顿更快进入恢复，而版本 7 的关闭协议没有完整升级、既有恢复竞态仍在，使“发现问题”没有落到“成功恢复”，反而落到“旧进程退出且无人拉起”。
4. **最高优先级不是调大阈值。** 先修复 schema 协议、撤销语义和成功恢复误升级；否则无论最初由 DAQ、液压、执行无进展还是其他软件故障触发，只要走到跨进程接管，都可能再次复现完全退出。
