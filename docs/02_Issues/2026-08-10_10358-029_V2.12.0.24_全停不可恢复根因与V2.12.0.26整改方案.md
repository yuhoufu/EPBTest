## 1. 结论先行

本次全停并不是“SQLite 写盘队列持续跟不上”，也不是简单把队列从 64 扩大就能解决。事故由以下闭环共同造成：

1. V2.12.0.24 把耗时的 Windows 主机运行探针放在每台 DAQ 唯一的后台处理线程中同步执行。首事故已观测到至少 546.5 ms 的数据陈旧，并伴随约 1.507 s 的 HostRuntime 日志空窗；二次故障空窗约 2.560 s。它们足以灌满仅有 64 批、约 0.64 s 的处理队列，触发 `BackgroundQueueFull`。
2. 数据在第一次告警后很快恢复流动，但旧恢复状态机没有认出新鲜样本，反而继续强制重建 NI 任务。
3. 同期圈收尾因 `SuppressAfter` 的错误谓词，在“边界已经写入、队列为零”的情况下仍必然超时；液压组复位与 DAQ 恢复互相抢占。
4. DAQ 恢复在 `StopDevice` 后响应取消，Dev1 被永久留在停止状态。
5. 后续启动逻辑先要求“新鲜、安全的压力”，再允许修复 DAQ；但 DAQ 已停止就永远没有新鲜压力，形成不可自解的循环门禁。
6. 局部故障最终升级为整机 `StopAll`，将正常的 Dev2 及其卡钳一起停掉；同组重试还存在 EPB4 丢失和跨 Run 累计重试次数的问题。

因此，现场看到的现象顺序——`BackgroundQueueFull`、反复自维护、EPB4/5 无法恢复、全部停机、停止后手动开始仍失败——是同一条软件故障链的不同阶段，不是多台卡钳同时发生硬件故障。

V2.12.0.26 的整改原则是：诊断不得阻塞采集；两台 DAQ 的处理、Raw 和持久化链彼此隔离；正式耐久窗口内的已接收批次只允许“原序成功、保留重试或显式声明数据缺口”，绝不静默跳过；恢复必须先保持全部输出断电，再修复输入 DAQ、取得新鲜压力，最后才允许重新上电；局部故障不得无条件拖停健康组。

## 4. 根因分解

### 4.1 直接根因：诊断探针阻塞唯一 DAQ 处理线程

旧 `TwoDeviceAiAcquirer.ProcessLoop` 在 `AppendDiagnostic` 内直接调用 `HostRuntimeProbe.Capture()`。该调用在全局锁内同步执行：

- `Process.Refresh()` 与线程枚举；
- `DriveInfo.AvailableFreeSpace`；
- 3 个物理磁盘性能计数器采样。

这些调用任何一次变慢，都会阻塞该设备唯一的处理消费者。外部压缩、复制或磁盘繁忙会提高出现停顿的概率，但即使磁盘吞吐不高，Windows 计数器/进程枚举也可能偶发阻塞。因此“外部复制”是诱因，关键链同步调用才是软件根因。

### 4.2 两种队列曾被错误混为一谈

| 队列 | V2.12.0.24 容量/阈值 | 职责 | 本次证据 |
|---|---:|---|---|
| DAQ 后台处理队列 | 64 批，约 0.64 s | 把 NI 回调数据转换并交给控制、Raw、持久化链 | 明确出现 `BackgroundQueueFull` |
| SQLite 持久化队列 | 容量 256、pause 128、resume 32 | 将已经处理的批次写入数据库/文件 | 未出现 `DaqPersistenceQueueFull` 或持续积压 |

事故 JSON 同时出现 `processingQueueCapacity=64` 和 `pauseDepth=128`，并不表示 128 的暂停阈值作用于 64 的队列；它们属于两套不同队列。仅把处理容量改大，只能延后报错并扩大陈旧数据窗口，不能根治阻塞。

### 4.3 `SuppressAfter` 让已经耐久的圈边界仍被判失败

现场圈收尾日志显示：

- `Boundary=2437260`；
- `Persisted=2438317`；
- `Depth=0`；
- `State=Recovered`。

按数据事实，边界已经写入。但旧 `WaitForDurablePrefixAsync` 只要看到 `SuppressAfterUtc.HasValue` 就永久返回 false，导致约 10 s 后仍判超时。由此触发的 FormalPersistence 自愈与 DAQ watchdog 恢复同拍，两个恢复流程互相取消和抢占。

### 4.4 Stop→Start 可取消窗口把 DAQ 留在半状态

旧恢复顺序在停止 NI 任务之后仍检查取消令牌。高优先级液压组复位到来时，流程在 `StopDevice` 完成、`StartDevice` 尚未执行的窗口退出。日志中的 `OperationCanceledException` 与随后 `Produced=0` 完整证明该半状态。

### 4.5 恢复门禁顺序形成压力闭环

旧手动/自动重启要求 `PressureSafeConfirmed`，之后才调用 DAQ readiness/rebuild。Dev1 已停采时压力必然陈旧，因而永远到不了能重新启动采集的步骤：

`DAQ 已停 → 压力样本陈旧 → 启动门禁拒绝 → DAQ 无法修复 → 压力继续陈旧`

这解释了为什么用户“停止后再手动开始”仍然报错；不是按钮无效，而是软件把恢复所需的输入放在恢复动作之前作为前置条件。

### 4.6 局部故障域与重试身份存在缺陷

- EPB5 触发恢复后，首轮可扩展为同液压组 EPB4/5；但运行对象被提前删除，下一轮只从原始请求 EPB5 重算，EPB4 成为孤儿，无法再次进入试验。
- 重试计数只按液压组编号保存，未按 Run 隔离，也未在新批次明确清除。一次旧 Run 的失败可使新 Run 直接接近熔断。
- 局部 Dev1 故障最终升级为整机 StopAll，违背“坏钳停止、健康组继续”的无人值守目标。

### 4.7 数据连续性和所有权的隐藏风险

进一步代码反证发现，旧链路在部分异常/拒绝路径上会：

- 无条件推进已发布水位；
- 在 `Enqueue(false)` 内释放对象，调用方又释放一次，存在池化对象 ABA 风险；
- worker 出队后写入异常就释放当前批并继续更大序号；
- recorder 暂时为空时直接返回，却仍把批次标记为已持久化；
- Raw 单全局 worker 可被一台设备的慢末端拖住，跨设备传递故障。

这些问题不一定都是本次首个触发点，但若不修复，就无法对 100000 圈作出数据连续性承诺。

### 4.8 无人值守重启、暂停/恢复和尾批冻结缺口

最终反证还发现三类会让“短时恢复正常、长时又卡死”的问题：

- 无人值守进程重启的 `_restartStarted` 在部分失败/取消路径不复位，第一次重启失败后，后续请求会被永久吞掉；
- Pause 只记录 Raw/SQLite drain 失败的 warning，却仍提交 `Paused`，Resume 又未拒绝永久 processing/Raw gap，可能让新 NI 回调继续进入已经死亡的消费者；
- StopAll 在 DAQ 尚未停止时冻结旧边界 A，后续又把 SQLite 边界扩大到 B，却复用“Raw 已排到 A”的结果，存在关闭时漏掉 A+1..B 尾批的窗口。

这些缺口均必须在 V2.12.0.26 正式提交前关闭：重启失败后恢复可调度状态并有界退避；Pause 只有完整 drain 成功才生效；Resume 必须通过连续性门禁；Stop DAQ 后使用同一个最终冻结边界同时验证 processing、Raw、末端 Flush 和 SQLite。

## 5. V2.12.0.26 整改矩阵

| 故障点 | V2.12.0.26 处理 | 预期不变量 |
|---|---|---|
| HostRuntime 阻塞处理线程 | 移到独立低优先级长驻线程；处理线程只读缓存 | 诊断阻塞不反压采集 |
| ThreadPool 饥饿 | 两台设备处理 worker、持久化 writer 使用独立 LongRunning 线程 | UI/线程池负载不夺走关键消费者 |
| 64 批瞬时容量 | 候选提供 1024 批突发储备，并新增独立 500 ms 队龄 watchdog | 容量只作缓冲；安全判断独立于容量 |
| 处理入口仍发生 `BackgroundQueueFull` | 在被拒绝序号处立即锁存永久 processing gap；该圈作废且不计数，禁止同进程伪恢复，按有界整批恢复升级到进程回收 | QueueFull 是显式连续性红线，不是继续扩容或无限自维护 |
| 单全局 Raw worker | Dev1/Dev2 各自 queue、slot、signal、worker | 单设备慢 Raw 不阻塞另一设备 |
| 批次异常后跳序 | 当前批保留并原序重试；只有真实所有权移交才推进水位 | 不静默跨越正式耐久窗口内的已接收序号 |
| 处理/Raw 永久不可恢复 | 30 s 有界重试后记录永久数据缺口，失败圈不计数，按 gap-1 安全边界退出并请求进程回收 | 明确失败，不伪造完整前缀，不无限自维护；同步 I/O 永久挂死时由外部监督或人工完成进程终止与重启 |
| 持久化 worker 异常 | 保留 `CurrentBatch`，监督器原批重试；恢复后发 `Recovered` | 大序号不能越过失败批 |
| recorder 为空 | 抛出可重试故障，不再伪成功 | 零写入不能推进耐久水位 |
| `SuppressAfter` 误判 | 截止时间用原子 ticks；截止不否定已写前缀 | `Persisted >= Boundary` 且无更早 in-flight 时可闭合 |
| 出队/in-flight 窗口 | 先公布 in-flight，再移除可见队头 | Drain 不能在最后一批尚未写入时假成功 |
| Enqueue/Shutdown 竞态 | 准入中的 enqueue 计数纳入 drain；关闭后不释放仍被使用的同步对象 | 不丢尾批、不访问已释放 signal |
| Stop→Start 取消 | 设备重启改为不可分割临界区；只在 Stop 前或 Start 后响应取消 | 不再把设备留在已停未启状态 |
| 压力陈旧闭环 | 全输出/电源确认 OFF → 输入 DAQ 修复 → 获取新鲜压力 → 安全确认 → 才允许上电 | 断电态可修复采集，同时不降低上电安全门槛 |
| EPB4 孤儿 | 同液压组完整 cohort 跨重试保持不变，运行对象延后处理/可重建 | 每轮恢复成员一致 |
| 跨 Run 重试污染 | 调度锁与 attempt 使用 `(runEpoch, hydraulicGroup)`；新批次清理旧计数 | 新 Run 第一次故障从 Attempt=1 开始 |
| 局部故障拖停健康组 | 可恢复故障保持在受影响液压组；确定性缺口才进入有界整批/进程连续性恢复 | Dev1 局部故障不无条件停止 Dev2 |
| 退出被弹框永久阻止 | 正常路径严格等待完整边界；永久数据缺口路径记录作废尾段并按安全前缀关停 | 既不假成功，也不形成无法退出的永恒门禁 |
| StopAll 旧/新边界混用 | Stop DAQ 后冻结一次最终边界；processing、Raw、末端 Flush、SQLite 均验证同一边界 | 不遗漏停止窗口中的 A+1..B 尾批 |
| 无人值守重启锁存 | 失败/取消后复位调度状态并按有界退避重试 | 一次重启失败不永久禁用后续恢复 |
| Pause/Resume 绕过连续性 | drain 失败不得提交 Paused；Resume 拒绝永久 gap 或死亡消费者 | 暂停不能掩盖数据链故障 |

### 5.1 关于 1024 容量的特别说明

1024 批在约 100 批/s 下约为 10.24 s，只是抵御瞬时调度抖动的储备，不是根治措施。真正的根治是把阻塞探针移出关键链、独立消费者、按队龄独立检测、保序重试与可闭合的失败语义。现场如果长期出现数百批积压，即使没有满 1024，也必须判为异常。

### 5.2 关于“零丢失”与“永不停止”的工程边界

软件可以保证：正式耐久窗口内的已接受批次不被静默丢弃、成功水位不跨越缺口、故障圈不计入目标次数、可恢复故障持续原序重试。Stop 请求冻结权威截止时间后才到达的批次会显式计入 `Suppressed`，不写入该圈 SQLite、不计为成功圈；其 Raw 尾批仍按最终冻结边界收口。软件不能保证故障硬盘、永久卡死的驱动或进程内存破坏时仍无限无损运行。

因此，正确的无人值守策略是：短暂故障局部自愈；确定性软件/数据连续性故障在安全断电后作废当前失败圈并回收进程；真实卡钳/硬件无法安全运行时只隔离对应故障域；任何情况下都不得伪造成功次数或绕过压力/输出安全门槛。

## 6. 关键安全与连续性不变量

V2.12.0.26 必须同时满足以下条件，缺一项都不算“彻底解决”：

1. DAQ 回调和处理关键线程不得执行磁盘、PDH、DriveInfo、UI 或同步日志重操作。
2. 每台设备的 processing、Raw 和 persistence 故障不得通过共享 worker 反压另一台设备；共享物理磁盘和 SQLite 的资源竞争仍必须通过现场负载试验验收。
3. 权威停止截止之前的每个 accepted sequence 只能按原序变为 durable、保持 pending，或被明确登记为永久 gap；截止后的批次必须显式计为 `Suppressed`，不得伪装成该圈真实 durable，也不得静默跳过。
4. 普通暂停/停止必须等待完整 `LastAccepted`；只有已登记永久 gap 的进程回收路径才允许以 `gap-1` 为安全前缀，并作废受影响圈尾段。
5. 任何上电前必须确认 DO、AO、电源和压力安全；但输入 DAQ 的断电态修复不得被陈旧压力提前拦截。
6. `StopDevice → StartDevice` 不得被取消切成半状态。
7. 恢复成员、attempt 和调度锁必须绑定当前 Run epoch，旧 Run 任务不得删除或吞掉新 Run 的恢复。
8. 退出不得因软件内部永远不可能满足的谓词反复弹框；未确认的真实写盘/物理安全条件仍必须阻止假退出。

## 8. 现场验证与上线门槛

### 8.1 构建与身份门槛

- 只能使用独立洁净工作树生成的不可变 V2.12.0.26 候选。
- `build-identity.json` 必须满足 `gitDirty=false`、`deploymentApproved=true`。
- 记录并锁定 Git SHA、EXE SHA-256、配置 SHA-256、BuildUtc。
- 禁止直接从 VS 的可变 `bin\Release` 目录执行生产试验。

### 8.2 分阶段长稳验证

同一正式候选依次执行：30 min 功能确认 → 2 h → 8 h → 24 h → 72 h。每个阶段都通过后，才开始最终 100000 圈真实耐久运行。15 s/圈的理论纯运行时间约 17.36 天，设备恢复、错峰和维护会使实际时间更长。

### 8.3 必做故障注入

1. 外部持续 100—200 MiB/s 复制/压缩，并观察至少 8 h。
2. 人工让 HostRuntime/诊断采样阻塞 0.6 s、3 s、30 s；采集处理深度应保持可控，另一设备不得被拖停。
3. 注入 processing、Raw、persistence 构建/交接/写入异常；验证同一批原序重试且没有水位跨越。
4. 模拟同步 writer 超过 10 s 后恢复；不得清队列、释放在用资源或伪造 durable。
5. Dev1 故障时验证 Dev2 卡钳继续运行；故障组恢复后完整 cohort 重新入试。
6. DAQ 停采造成压力陈旧后执行停止→开始；必须在断电态先恢复采集，再通过新鲜压力安全门槛。
7. 在 Stop 后、Start 前注入取消和 Start 异常；设备不能永久停在半状态。
8. 正常退出、持久化超时退出、永久 gap 退出均不得出现无限弹框；真实安全/耐久未确认时仍必须明确提示并保持断电。

### 8.4 红线指标

以下任一项出现即判阶段失败并重新计时：

- `BackgroundQueueFull`、`DaqPersistenceQueueFull`、静默丢批或未登记序号缺口；
- 正常运行时 processing 最老批次持续超过 100 ms，或深度持续大于 2；
- 单设备局部软件抖动导致健康设备全停；
- 同一恢复组成员丢失、恢复成功却没有 timer/runner、跨 Run attempt 继承；
- 普通成功圈缺 Raw/SQLite 终态，或失败圈被计入完成次数；
- UI 无响应、退出无限弹框、自动恢复长期停留在自维护；
- `gitDirty=true`、包内身份/哈希不一致或从可变目录启动。

## 9. 仍需诚实保留的风险

1. 日志能够确定同步 HostRuntime 探针阻塞了唯一处理链，但没有足够 ETW 权限精确指认首次 546 ms 是哪个 Windows API；不能无证据归因于某个单一 API 或 GC。
2. 独立 500 ms processing watchdog 是安全早检值，需要在真实 NI 与现场磁盘负载下调参；不能为了减少报警而简单放宽到 10 s。
3. 若底层同步磁盘写调用永久不返回，进程内线程无法安全“跳过”该写入；当前策略只能保留批次和资源、阻止伪成功并进入安全停机，随后由外部监督或人工终止进程、处理硬件/磁盘并重启，不能承诺进程内自行回收。
4. V2.12.0.26 完成代码整改和自动回归后仍只是候选。真实 72 h 与 100000 圈证据未完成前，不能把“根因已修复”写成“现场已经证明永久稳定”。

## 10. 最终判定

V2.12.0.24 不具备无人值守上线条件。其 `BackgroundQueueFull` 可以从根上解决，但必须同时修复关键线程阻塞、批次连续性、恢复抢占、Stop→Start 半状态、压力循环门禁、故障域和退出语义；单纯扩容或反复自动重启都不够。

V2.12.0.26 代码层已按上述故障链完成整改并通过自动回归，建立了可验证的安全/耐久不变量。正式候选只有在干净构建、故障注入、72 h 长稳和最终 100000 圈全部通过后，才可签字为无人值守生产版本。
