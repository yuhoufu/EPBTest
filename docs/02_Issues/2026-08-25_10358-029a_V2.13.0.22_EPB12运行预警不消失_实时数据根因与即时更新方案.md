## 根因：overlay 已独立，清除逻辑仍检查旧生命周期

### 预警产生链路是新的 overlay 模型

`Controller/EpbManager.cs:309-353` 明确规定：

- Runner 软预警不再产生 `WarningRunning`；
- 生命周期继续保持 `Learning`、`Qualification`、`Running` 或 `Recovering`；
- 预警状态单独写入 `_channelWarningOverlayStore`；
- `PublishChannelWarningOverlay` 将 `Active` 设置为 `true` 并发布 `ChannelWarningOverlayChanged`。

现场日志与该设计完全一致：

```text
FieldMetric WARNING_OVERLAY EPB=12 LifecyclePreserved=Learning LifecycleRevision=3
```

### 正常圈后的清除链路仍是旧模型

`Controller/EpbManager.BatchStart.cs:4919-4925` 当前逻辑为：

```csharp
var current = _channelRuntimeStateStore.Get(channel);
if (current?.State == ChannelRuntimeState.WarningRunning)
    PublishChannelRuntimeState(
        channel,
        ChannelRuntimeState.Running,
        "WarningCleared",
        "后续完整圈正常，软预警已解除");
```

该代码只尝试把旧的生命周期状态 `WarningRunning` 改回 `Running`，没有调用 `ClearChannelWarningOverlay`。

但 V2.13.0.22 的新不变量是：软预警不得修改生命周期。于是现场执行结果为：

```text
预警发生
  -> overlay.Active = true
  -> 生命周期仍为 Learning，随后为 Running
  -> 后续正常圈进入 OnFormalCycleCommitted
  -> current.State == WarningRunning 为 false
  -> 不发布 overlay.Active = false
  -> UI 永久显示“运行 · 预警”
```

这不是偶发竞态，而是确定性不可达分支。只要没有发生新的 `Starting`、`Completed` 或停机终态，overlay 就不会清除。

### 当前真正调用 overlay 清除的场景不包含正常圈

全仓库只有 `Controller/EpbManager.cs:694-697` 在以下生命周期转换时调用 `ClearChannelWarningOverlay`：

- `Starting`
- `Completed`
- 锁存停机状态

正常学习圈、资格圈和正式圈完成都不在该列表中。因此，当前 V2.13.0.22 中单圈软预警通常会一直保留到重新启动、自然完成或停机。

### UI 刷新链路本身工作正常

`MTTfTest/FrmEpbMainMonitor.PowerSupply.cs:321-337` 收到 `ChannelWarningOverlayChanged` 后立即通过 `BeginInvoke` 重绘对应通道；`364-384` 根据 `warning.Active` 组合显示 `运行 · 预警` 或 `运行`。

事件修订号也有严格单调比较：`Controller/ChannelRuntimeState.cs:262-268` 只接受更高 `Revision`，因此 UI 可以正确拒绝乱序旧事件。

现场的 UI 指标进一步排除了“刷新线程慢”：


所以只要控制层正确发布 `Active=false`，UI 可以在几十毫秒内恢复为绿色“运行”。当前没有该事件，任何提高刷新频率、增加定时器或强制 `Refresh()` 都无法解决根因。

## 影响范围

### 不是 EPB12 单通道问题

`ChannelWarningOverlayStore` 和旧清除分支都是通用代码，因此影响所有 1～12 通道和所有经该 overlay 发布的软预警。

封存末尾 11:33:04 又记录了 EPB5 的 `+0.803 A` 峰值过冲预警。由于封存数据在其后不足一个完整恢复窗口，不能据此判断 EPB5 是否已经恢复；但如果后续恢复，V2.13.0.22 仍会遇到同样的显示锁存。

### 当前影响主要是状态真实性，不是机械控制失败

已验证的影响：

- 通道状态格长期显示橙色 `运行 · 预警`；
- `EPB 控制` 汇总中的预警数量长期偏大；
- Watchdog 心跳中的 `WarningActive` 长期为真，降低诊断可信度；
- 操作员无法从状态格判断异常是否已经恢复。

现场数据同时证明 EPB12 控制循环、机械动作、计数与落盘仍在继续。因此本次不是 EPB12 停机、控制失效或 Watchdog 误接管。

当前 Watchdog 策略不使用 `WarningActive` 触发接管，所以该锁存不会单独杀进程；但陈旧的诊断状态不应进入长期运行版本。

## “即时更新”的正确语义

峰值过冲是否恢复，只有在下一次取得完整、可信的正向峰值证据后才能判断。不能在电流尚未完成上升时按瞬时值清除，也不能只因时间到了自动清除。

本项目周期为 15 秒，建议定义：

1. 预警圈自身为 `SuccessWithWarning`，overlay 保持激活。
2. 下一圈如果控制和持久化均提交、峰值证据完整、结果为 `Success`，并且没有再次产生同类预警，则在该圈提交点立即清除。
3. 清除事件从控制层发布到 UI 状态恢复的目标延迟：
   - 控制层发布：`<=100 ms`
   - UI 可见更新：`<=500 ms`
4. 如果下一圈为 `SuccessWithWarning`、证据不完整、软件恢复、硬故障、取消或落盘未提交，不得把“没有新预警日志”误判为恢复。

按该定义，本次 EPB12 应在 **11:25:41.369 后最迟 500 ms** 恢复显示，而不是等到 11:30 以后仍保持橙色。

## 可彻底解决的实现方案

### 方案一：由结构化圈结果驱动清除，不再检查 `WarningRunning`

建立统一的 `OnTrustedCycleCommitted` 入口，由学习圈、资格圈和正式圈共同调用，至少携带：

- `RunId`
- `RunEpoch`
- `Channel`
- `CycleNumber`
- `AttemptId`
- `EpbCycleOutcome.Kind`
- 本圈产生的结构化 `WarningCodes`
- 峰值证据是否完整可信

清除规则：

```text
同一 RunId/RunEpoch
AND 本圈控制与持久化已提交
AND Outcome == Success
AND 本圈没有产生待清除类别的预警
AND 当前 overlay 是本圈开始前已存在的版本
=> 发布 overlay.Active=false
```

不能只把 `OnFormalCycleCommitted` 中的条件简单改成“只要 overlay 激活就清除”，否则当前圈刚产生的预警可能在同一圈末尾被立即清掉。

### 方案二：清除必须使用带版本条件的原子操作

为 `ChannelWarningOverlayStore` 增加类似以下接口：

```csharp
TryClearIfCurrent(
    int channel,
    Guid expectedRunId,
    long expectedRunEpoch,
    long expectedRevision,
    string expectedWarningCode,
    Guid correlationId,
    string clearReason)
```

只有当前激活项仍与预期的运行身份、修订号和预警类别一致时才允许清除。这样可阻止以下竞态：

- 旧正常圈的迟到清除覆盖新一圈刚产生的预警；
- 上一个 RunEpoch 的回调清除新运行的预警；
- A 类预警的恢复错误清除同通道新产生的 B 类预警；
- UI 先收到新预警、后收到旧清除导致状态倒退。

### 方案三：overlay 必须使用结构化预警事件

当前 `ForwardPeakOvershootWarning` 的结构化 `AdaptiveWarningEvent` 已包含 `Code`、`AttemptId`、`OccurredUtc`、峰值和阈值；但 overlay 由异步字符串通知 `OnRunnerWarningRaised` 创建，`ExtractFaultCode` 面对中文原因时会把整段首词当成代码，现场 `WARNING_OVERLAY Reason=` 已表现为完整中文原因而不是标准枚举。

建议：

- 由同步的 `AdaptiveWarningEvent` 直接发布 overlay；
- `WarningCode` 使用 `AdaptiveWarningCode` 的稳定枚举值；
- 字符串事件只用于日志和兼容通知，不再拥有 overlay 状态；
- `OccurredUtc`、`AttemptId`、`CycleNumber` 和 `CorrelationId` 从控制判定点原样传递；
- 消除 `Task.Run` 的旧预警通知晚于新正常圈清除的可能。

### 方案四：按预警类别定义恢复判据

当前存储每通道只有一个 overlay。彻底方案应至少保存“当前类别 + 修订号”，更理想的是按 `(channel, warningCode)` 保存多个 overlay，再由 UI 合成通道级橙色状态。

建议恢复规则：

| 预警类别 | 可清除条件 |
|---|---|
| `ForwardPeakOvershootWarning` | 下一可信完整圈 `Peak-Target <= AdaptiveOvershootWarningDeltaA`，且该圈无同类预警 |
| `ForwardCurrentRiseStallWarning` | 下一可信完整圈不再满足低平台停滞判据，且结果为 `Success` |
| 峰值证据延迟/缺失/不一致 | 下一圈峰值证据时间戳、代次和完整性均通过 |
| 可恢复控制故障预警 | 恢复事务成功终态提交，并完成首个可信正常圈 |

这能避免“任意成功圈清掉所有类别”的过度清除。

### 方案五：继续使用事件驱动 UI，不增加轮询刷新

UI 当前的 `Revision`、`BeginInvoke` 和单通道重绘机制是正确的。修复应保留这条链路：

```text
可信正常圈提交
  -> Store 原子写入 Active=false、Revision+1
  -> ChannelWarningOverlayChanged
  -> UI BeginInvoke
  -> “运行 · 预警”变为“运行”
  -> 汇总预警数减 1
  -> Watchdog 下一心跳 WarningActive=false
```

不建议增加 UI 定时轮询，因为轮询无法判断控制证据是否可信，还会形成控制层与显示层两个事实源。

### 方案六：增加可审计的恢复日志和停滞监控

新增字段指标：

```text
FieldMetric WARNING_OVERLAY_CLEARED
EPB=12
Code=ForwardPeakOvershootWarning
RaisedRevision=1
ClearRevision=2
RaisedAttempt=8
RecoveredAttempt=9
RecoveredCycle=-42
ClearLatencyMs=...
Reason=SubsequentTrustedCycleHealthy
```

再增加诊断不变量：若 overlay 激活后已经存在一个满足其恢复判据的可信提交圈，却仍保持 `Active=true`，记录 `WarningOverlayClearMissing`。该不变量只报警诊断，不自动停机。

## 不应采用的表面修复

- **固定超时自动清除：** 数据中断时也会过期，可能把未知状态显示成正常。
- **每秒重绘 UI：** 只会重复绘制同一个 `Active=true`，不能生成缺失的恢复事实。
- **恢复使用旧的 `WarningRunning` 生命周期：** 会再次污染 Learning/Qualification/Recovering 的生命周期所有权，破坏 V2.13.0.22 的隔离设计。
- **任意 `Success` 直接清除当前 overlay：** 可能清掉同一圈刚产生的新预警或其他类别预警。
- **重启程序作为清除手段：** 能暂时复位显示，但无法防止下一次软预警再次锁存。
