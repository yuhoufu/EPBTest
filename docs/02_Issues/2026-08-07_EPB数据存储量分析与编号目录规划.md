# EPB 数据存储量分析与编号目录规划

> 盘点时间：2026-08-07（Asia/Shanghai）  
> 盘点对象：`\\wj-epb\EPB_Data\10358-029_V2.11.0.3_0807_1111`  
> 目标：先控制数据增长，再统一目录命名和编号；本文不删除、不移动现有数据。

## Executive Summary

- **容量主因是重复导出，不是 `index.db` 或普通日志。** 同一圈数据会以 CSV+BIN 形式重复出现在 `WarningSnapshots`、`AlarmSnapshots`、`IncidentSnapshots`、`Latest` 和 `LearningCycles`。示例目录估算约 **13 GiB**，其中 `AlarmSnapshots` 约 **7.3 GiB**，是第一控制对象。
- **当前两个关键限额实际没有发挥作用。** `SoftWarningQuotaMb="0"` 等于关闭软预警配额；`Latest` 每次导出都会创建新目录，代码中没有保留数量或覆盖机制。示例中 EPB8 已积累 **81** 个 Latest 包。
- **建议先实行“BIN 常驻、CSV 按需生成”。** 抽样单圈 CSV 约 1.0～1.1 MiB，BIN 约 0.5～0.6 MiB；仅取消重复 CSV 常驻即可明显降量，同时不丢失可回放的二进制证据。
- **目录统一采用“类别序号 + 项目号 + 运行序号 + 完整日期 + 版本”。** 新运行建议命名为 `00023_20260807_1111_V2.11.0.3`，不再使用缺少年份、顺序不稳定的 `项目_版本_MMDD_HHMM`。

### 1.3 为什么数据会迅速放大

1. **报警快照复制范围过大。** 报警时会把报警通道、受影响通道以及仍在运行的其他通道合并后逐通道导出；每个辅助通道又导出最近 N 圈。当前 N 来自 `HardAlarmLastNCycles="10"`。
2. **CSV 和 BIN 双份常驻。** 同一圈 BIN 约 0.5～0.6 MiB，CSV 约 1.0～1.1 MiB；CSV 体积通常约为 BIN 的 1.8～2 倍。
3. **同一圈跨目录重复。** 最近圈可能同时存在于 `HistoricalSnapshots`、`Latest`、软预警、硬报警和事故终态中。
4. **软预警没有生效配额。** `SoftWarningQuotaMb="0"` 会直接跳过配额处理；即使设置非零值，当前实现也只归档“非本次运行”的候选目录，单次长跑仍可能持续膨胀。
5. **Latest 没有保留上限。** 每次调用都创建一个新的时间戳目录，成功后不删除旧包。
6. **大量网络小文件拖慢运维。** 当前布局会显著拖慢目录统计、备份、复制、杀毒扫描和事故取证；这次只读盘点本身已体现该问题。

## 2. 先控制数据量：建议保留策略

### 2.1 建议目标

| 数据类别 | 新的热数据规则 | 归档规则 | 建议上限 |
|---|---|---|---:|
| Latest | 每通道只保留 1 个 `current` 和 1 个 `previous`；BIN 常驻 | CSV 由回放/导出功能按需生成 | 每通道 2 包；全项目约 100 MiB 内 |
| 软预警 | BIN + metadata + checksum；同一故障链只保留首圈、升级前圈、终止圈 | 超额后 ZIP；保留 30 天 | 当前运行 512 MiB 或 300 条，先到者为准 |
| 硬报警 | 报警通道保留最近 5 圈 BIN，故障圈保留 CSV+BIN；辅助通道各保留最近 2 圈 BIN | 20 次以后 ZIP，90 天后转冷归档 | 热区约 1～2 GiB |
| Incident | `trigger/cutoff/rebuild/validate` 仅保存诊断文件；只在最终 `recovered/failed` 保存完整圈证据 | 最近 10 个会话热存，其余 ZIP | 10 个会话 |
| Learning | 保留当前运行、最近一次成功、最近一次失败；默认 BIN | CSV 按需生成；旧运行 ZIP | 2～3 次运行 |
| Historical | 继续每通道保留 `N+2` 个 BIN | 不长期保存 CSV | 当前 12 圈/通道 |
| 电源遥测 | 按天或 100 MiB 切分 | 14 天热存，之后 ZIP，90 天转冷 | 热区 2 GiB |
| 日志 | 单文件 50 MiB 轮转，最多 10 个 | 30 天后压缩/转冷 | 500 MiB |
| index.db | 运行时保留索引；定期检查失效圈记录 | 停机窗口做备份、归档和 `VACUUM` | 建议不超过 200k 行或 100 MiB |

### 2.2 最小改动顺序

1. **立即启用软预警限额。** 把 `SoftWarningQuotaMb` 从 `0` 改为 `512`；同时修正实现，使当前运行也受上限保护，但必须始终保留故障链关键三点和硬报警关联证据。
2. **软预警关闭常驻 CSV。** 设置 `SaveCsv="false"`、保留 `SaveBin="true"`；需要人工查看时再由 BIN 生成 CSV。
3. **Latest 改为原子覆盖。** 每通道写入临时目录，校验成功后替换 `current`，原 `current` 改名为 `previous`；不得继续累积时间戳包。
4. **硬报警分级取证。** `HardAlarmLastNCycles` 可先从 10 调到 5，但代码应区分报警通道和辅助通道，不能所有运行通道一律复制相同 N 圈。
5. **学习运行按结果清理。** 新学习成功后只保留“本次成功 + 上次成功 + 最近失败”，并把 UUID 改为可排序运行编号。
6. **最后处理索引。** 先确认旧索引是否仍能指向环形 `.dat` 的有效记录，再决定删除或归档；不能只凭圈号直接删库记录。

> 安全边界：任何限额都不得删除当前故障圈、硬报警终态、`incident.json`、`warning-metadata.json`、校验和、配置和索引备份。容量控制只针对重复副本和可再生 CSV。

### 3.1 编号含义

| 编号段 | 含义 |
|---|---|
| `01`～`09` | 项目身份、配置、索引等基础信息 |
| `10`～`19` | 可滚动、可再生的圈缓存 |
| `20`～`29` | 安全证据：预警、报警、事故 |
| `30`～`39` | 学习和资格确认数据 |
| `40`～`59` | 遥测和日志 |
| `90`～`98` | 已封存、只读归档或人工导出 |
| `99` | 临时、待核对、隔离数据；必须有自动过期规则 |

### 3.2 运行目录命名

统一格式：

```text
<四位运行序号>_<yyyyMMdd>_<HHmm>_<版本>
```

示例：

```text
00023_20260807_1111_V2.11.0.3
```

规则：

- 运行序号按项目号独立递增，不因版本变化重置；
- 日期必须使用 8 位完整年份，避免 `0807` 跨年歧义；
- 版本只出现一次，不再把日期放在版本后作为不明后缀；
- 每个运行目录新增 `run-manifest.json`，至少记录项目号、运行序号、开始/结束时间、软件版本、通道、运行类型、状态和原始旧路径；
- 调试、验证、正式运行不要靠名称猜测，必须在 manifest 中写明 `RunType=Production|Validation|Debug`。

### 3.3 事件目录命名

统一使用“事件序号在前”，确保资源管理器按名称即为发生顺序：

```text
000086_20260807_110806_ALARM_EPB08_<FaultCode>
001055_20260807_110933_WARN_EPB08_C009942_ForwardPeakOvershoot
000020_20260807_105840_INCIDENT_Dev1_<ShortCorrelationId>
```

GUID 只保留在 metadata 中；目录名最多保留 8 位短关联号，避免路径过长。

## 5. 迁移落地步骤

### 阶段 A：先止增量

1. 在测试停止、程序关闭后备份 `Config` 和 `index.db`；
2. 启用软预警 512 MiB 配额并关闭软预警常驻 CSV；
3. 发布 Latest 只保留 current/previous 的修复；
4. 发布报警按通道分级取证和事件热区上限；
5. 连续观察一个完整班次，确认回放、报警链和事故导出均正常。

### 阶段 B：新目录先行

1. 创建编号目录树，但不移动正在使用的项目；
2. 新建 `project-runs.csv` 或小型 SQLite 注册表分配运行序号，禁止人工重复编号；
3. 新运行全部写入新结构；旧版本保持只读兼容；
4. UI 显示“项目号 / 运行序号 / 版本 / 开始时间”，不再要求用户阅读长目录名。

### 阶段 C：迁移已关闭运行

1. 生成旧目录清单：相对路径、大小、文件数、SHA-256、创建和修改时间；
2. 先复制到新位置，再按清单校验数量、总字节和哈希；
3. 校验成功后把旧目录改为只读，保留 7～14 天观察期；
4. 观察期结束后再移动到归档区；只有存在第二份已验证备份时才删除旧副本；
5. 对 CSV+BIN 重复数据先保留 BIN，随机抽样回放并重新生成 CSV，验证一致后才批量处理可再生 CSV。

### 阶段 D：归档和自动巡检

每天生成一次容量摘要，至少包含：

- 项目/运行总量；
- 各一级业务目录大小和文件数；
- 过去 24 小时增长量；
- Warning/Alarm/Incident 数量；
- 剩余磁盘空间和预计可运行天数；
- 超额目录、最老热数据和清理结果。

## 6. 验收标准

1. `Latest` 每通道目录数不超过 2；
2. 当前运行 `WarningSnapshots` 不超过 512 MiB 或 300 条；
3. 单次普通硬报警目标不超过 25 MiB，且故障圈 CSV+BIN、元数据和校验和完整；
4. `HistoricalSnapshots` 每通道保持 12 个左右的 BIN 圈文件；
5. 学习区只保留当前、最近成功和最近失败运行；
6. 新目录全部符合编号规范，按名称排序即为正确的类别和时间顺序；
7. 任取 10 个归档事件，能够从 manifest 定位原项目、运行、通道、圈号和报警链；
8. 同一示例规模的目录统计应在 30 秒内得到一级汇总，不再因大量重复小文件长时间阻塞；
9. 连续一个班次内无回放失败、哈希校验失败、报警证据缺失或因配额导致的当前故障圈丢失。

## 7. 仍需确认的问题

1. 硬报警辅助通道实际需要保留 2 圈还是 3 圈，需由故障分析人员确认；报警通道建议至少保留 5 圈。
2. 现场是否要求 CSV 作为法定/客户交付原件；若是，则改为事件关闭后 ZIP，不应直接取消。
3. NAS 是否支持服务端压缩、重复数据删除或快照；若支持，可以进一步降低归档成本，但不能替代应用侧限额。
4. `DataStore` 环形 `.dat` 当前位于程序运行目录，本报告未把本机固定大小的环形文件计入网络项目目录；后续应决定是否纳入统一监控。
5. 旧 `index.db` 中已被环形文件覆盖的记录是否仍有回放价值，需要先做有效性检查，再设计索引归档规则。
