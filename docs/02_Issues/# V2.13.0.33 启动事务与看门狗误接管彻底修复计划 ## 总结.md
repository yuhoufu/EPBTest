# V2.13.0.33 启动事务与看门狗误接管彻底修复计划

## 总结

针对 V2.13.0.32 的三条连锁故障同时修复：

- 启动定位 OFF 命令超时后，等待同组电源恢复完成再重试，杜绝 `ExpectedOutputDisabled` 连续消耗重试次数。
- 将“管道心跳异常”和“主程序无响应”拆成独立证据，管道阻塞不再直接杀进程。
- 恢复进程退出统一交还给看门狗管理，禁止误发 `ShutdownExpected` 导致主程序和看门狗一起退出。

交付版本固定为 `V2.13.0.33`，包含代码、自动化测试和新实施验证文档，不生成正式现场发布包。

## 实施变更

### 1. 启动定位改为可等待的安全事务

- 使用现有 `TrySubmitEpbOffHighPriority` 回调建立内部 `StartupPositioningOffReceipt`，精确区分：未接纳、100ms 内成功、已接纳仍在执行、最终成功、最终失败。
- 保留 100ms 失效安全阈值：超时仍立即关闭共享电源组，但不得把“已接纳、稍后成功”的 OFF 命令判成机械失败。
- 扩展 `EmergencyPowerGroupLatch`，为每个电源组暴露同一代次的完成任务；同组通道合并到唯一恢复所有者，不同电源组可并行。
- 恢复完成条件固定为：原始 OFF 命令已终结、组输出已关闭、程控电源恢复并通过回读、当前 run/epoch 仍有效。失败或超出既有恢复硬截止时保持断能，禁止重新上电。
- 每次实际机械定位前依次执行：等待电源组恢复、修复并复核执行许可/Runner、确认程控电源准入，再增加机械尝试次数并调用 `StartupPositioningAsync`。
- `ExpectedOutputDisabled`、恢复等待、Runner 修复和执行许可刷新均归类为框架恢复，不占用三次机械尝试；真实过流、保护动作和最终硬件写失败仍按现有硬件故障策略处理。

### 2. 重构看门狗 Host 管道发送模型

- 为每一代管道连接建立唯一发送所有者，采用单写线程和独立的生命周期/普通消息有界队列；`Attached`、恢复回执、`RequestStopAll` 等控制消息不能被 Ping/心跳类消息饿死。
- 写入仍使用现有 500ms 上限；超时只退休发生故障的精确连接代次，不直接形成进程接管证据。
- 连接退休时停止接纳、取消队列、关闭管道并有界等待读写任务结束，全部完成后才接受下一代连接；旧写任务不得清除或破坏新连接。
- 将正常断连和主动退休记录为结构化传输事件，保留队列等待、写入超时、连接代次和退休原因；预期清理不再记录成泛化的 `PipeLoopError`。

### 3. 增加独立的 Windows UI 存活探针

- 看门狗按 PID 和进程启动时间复核身份，通过 `EnumWindows` 查找主进程顶层窗口，再以 `SendMessageTimeout(WM_NULL)` 探测响应。
- 沿用 3 秒心跳怀疑和 5 秒心跳超时；达到 5 秒后每秒探测一次，单次 UI 探针上限 500ms。
- 已收到 `MainUiReady` 且窗口响应时，记录 `HeartbeatTransportDegraded`、退休当前管道并等待重连，禁止杀进程。
- 主窗口连续三次无响应才确认 `HeartbeatUnresponsive`；新进程尚未发送 `MainUiReady` 时提供 15 秒启动宽限，之后窗口仍缺失再按连续三次失败处理。
- 进程退出或身份失配仍立即接管；StopAll 硬截止、输出无法确认关闭、正式机械进度停滞等原有安全证据不受 UI 响应结果抑制。
- 同一进程的 `MainUiReady` 状态跨管道重连保留，仅在新 PID/启动时间正式附着时重置。

### 4. 修正恢复退出所有权

- 增加内部强类型 `WatchdogRecoveryExit` 意图，替换根据 reason 字符串前缀推断退出类型的逻辑。
- `WatchdogRecoveryExit` 复用现有线上消息 `WatchdogTakeoverExit`，协议仍保持 v3，不增加混合版本无法识别的新消息。
- 恢复失败通知返回强类型交接结果：
  - `RelaunchApproved` / `RelaunchAlreadyPending`：旧主进程交还所有权，看门狗保持运行并消费恢复许可。
  - `CircuitOpen` / `IdentityConflict`：旧主进程退出，看门狗保持在阻断状态并展示诊断，不重新拉起。
  - 已被精确 takeover correlation 接管：交还给现有接管事务。
  - 无活动会话、回执超时或回执无效：不得自行退出，保持安全空闲和可见诊断，等待人工处理或链路恢复。
- 只有明确的人工关闭继续发送 `ShutdownExpected`，并允许主程序和看门狗共同正常退出。
- 将 `SessionClosing` 的设置移到已确认的退出事务，避免回执获取失败时提前关闭传输会话。

## 测试与验收

- 启动事务回归：
  - OFF 超过 100ms 后最终成功，只产生一次组恢复，不消耗额外机械尝试。
  - 同组多个通道合并到一个恢复所有者；不同组互不阻塞。
  - 恢复期间出现 `ExpectedOutputDisabled` 时等待并恢复，不形成三连失败。
  - OFF 未接纳、最终失败、恢复硬截止、run/epoch 变化时保持断能且不重新上电。
- 看门狗传输与存活：
  - 模拟 0.5、3、6 秒发送阻塞且 UI 可响应，验证只重连、不接管。
  - 连续三次 UI 无响应、进程退出、PID 身份失配分别触发接管。
  - 15 秒启动宽限及 `MainUiReady` 跨连接状态得到验证。
  - 并发发送控制消息和普通消息、写入超时、旧代写任务晚完成、连续 100 次重连均不发生并行写或破坏新连接。
  - UI 可响应时，正式进度停滞和 StopAll 安全硬截止仍能接管。
- 退出语义：
  - 恢复许可获批后旧主进程退出、看门狗存活并只拉起一次。
  - 熔断/身份冲突时不拉起，但看门狗保持诊断状态。
  - 回执丢失时主程序不自杀式退出。
  - 人工关闭仍产生 `ShutdownExpected`，双方正常终止。
- 完整验证命令：
  - `msbuild TfTest.sln /p:Configuration=Debug /p:Platform=x86`
  - `msbuild TfTest.sln /p:Configuration=Release /p:Platform="Any CPU"`
  - `.\Tests\AdaptiveControlTests\bin\Debug\AdaptiveControlTests.exe`
  - `.\Tests\EpbDiskWriterTests\bin\Debug\EpbDiskWriterTests.exe`
  - `dotnet test .\Tests\PowerSupplyDebugger.Tests\PowerSupplyDebugger.Tests.csproj`

## 固定假设

- 运行环境为 Windows、.NET Framework 4.8，采用已选定的系统 UI 探针方案。
- 现有安全断电和恢复硬截止不放宽；UI 探针只消除纯传输故障造成的误杀。
- 本次不修改线上协议版本、不制作正式发布包、不执行依赖现场 NI/CAN/液压设备的长稳试验；这些限制和现场验收项必须写入新文档。
