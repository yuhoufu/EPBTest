# 10358-029：V2.13.0.18 学习阶段软预警触发 Watchdog 误接管——V2.13.0.19 根因修复及验收

## 1. 结论

V2.13.0.18 在 2026-08-22 09:20 的启动失败，不是卡钳、电源、DAQ 或液压硬件故障，也不是学习圈没有执行成功。

直接根因是：卡钳在 `Learning` 学习阶段产生 `RapidLoadRiseWithoutObservedEmpty` 软预警后，主程序把通道生命周期从 `Learning` 错误覆盖为 `WarningRunning`。Watchdog 对 `WarningRunning` 按“正式运行”解释，要求 `Timer=True` 且 `Runner=True`；但学习阶段的正确资源合同本来就是 `Timer=False`、`Runner=True`。因此 Watchdog 将一个合法的学习资源组合误判为 `ChannelExpectedRuntimeMissing`，持续 5 秒后执行接管并终止试验。

V2.13.0.15 也存在同一个生命周期覆盖错误。它之所以能继续运行，是因为旧版 Watchdog 在请求结构化心跳刷新后，读写循环发生停滞，只记录到 `HeartbeatSuspect`，没有继续执行 5 秒资源合同接管。V2.13.0.18 修复了 Watchdog 通信阻塞后，心跳与 ACK 能持续推进，反而使这个潜伏的生命周期错误稳定暴露。

正确修复不是退回 V2.13.0.15 的通信缺陷，也不是关闭 Watchdog，而是：

1. 软预警只作为告警叠加信息，不得覆盖 `Starting`、`Learning`、`Qualification`、`Paused`、`Recovering` 或终态等生命周期。
2. 只有通道已经处于正式 `Running` 时，软预警才可将展示状态变为 `WarningRunning`。
3. 保留 V2.13.0.18 的 Watchdog 有界异步写入、读循环解耦和 5 秒安全接管能力。
4. 将现场难以理解的英文预警码改为明确中文软预警，禁止再显示“已执行安全保护”这种与事实不符的硬故障兜底文案。

本次源码修复版本为 **V2.13.0.19**。Release/x86 完整构建成功，自动化回归 **483/483 全部通过**。实机连续运行验收仍须按第 9 节执行。

## 5. V2.13.0.15 与 V2.13.0.18 运行逻辑对照

### 5.1 两版本共同存在的状态错误

V2.13.0.15 的 `OnRunnerWarningRaised` 与 V2.13.0.18 事故版本一样，收到任何 Runner 软预警都会直接发布：

```text
ChannelRuntimeState.WarningRunning
```

这一步没有读取并保留当前生命周期。因此在 `Learning` 中产生软预警后，状态也会变成 `WarningRunning`。

Watchdog 的阶段合同在两个版本中的关键语义是：

| 生命周期 | TimerRequired | RunnerRequired | 正确性 |
|---|---:|---:|---|
| Learning | False | True | 学习由 Runner 负责，正确 |
| Qualification | False | True | 资格阶段由 Runner 负责，正确 |
| Running | True | True | 正式循环需要 Timer 和 Runner，正确 |
| WarningRunning | True | True | 仅适用于正式运行中的软预警 |

所以真正错误在状态生产端：将一个告警叠加错误当成了生命周期迁移。

### 5.2 V2.13.0.15 为什么表面正常

V2.13.0.15 对照运行在 11:25:46.658 出现相同现象：EPB5 处于学习阶段，软预警后变成：

```text
Phase=Learning
ChannelState=WarningRunning
Timer=False
Runner=True
TimerRequired=True
RunnerRequired=True
```

11:25:47.530，旧 Sidecar 已请求相同的 `ChannelExpectedRuntimeMissing` 刷新；客户端也记录了 `HeartbeatRefreshSent`。但 11:25:50.710 后只留下：

```text
HeartbeatSuspect Age=3.177
```

之后该 Sidecar 日志不再推进，没有到达资源不变量持续 5 秒的接管点，而主程序仍继续学习和正式运行。这说明 V2.13.0.15 的“成功”依赖 Watchdog 通信链停滞，是安全监督失效后的偶然结果，不能作为应恢复的正确逻辑。

### 5.3 V2.13.0.18 为什么稳定报错

V2.13.0.18 对 Watchdog 管道写入增加了有界截止，并把 Ping/刷新响应从读循环解耦。现场证据中每次 `ChannelRuntimeContractRefreshRequested` 后都有对应的 `HeartbeatRefreshSent`，心跳与 ACK 一直增加。

因此错误状态不再被旧通信卡死掩盖，而是正常经历：

```text
Learning
  -> Runner软预警
  -> 被错误覆盖为 WarningRunning
  -> Watchdog要求 Timer=True
  -> 结构化刷新后仍为 Timer=False
  -> 同一合同签名持续5秒
  -> Watchdog接管并StopAll
```

V2.13.0.18 的通信修复方向正确；本次不能通过恢复阻塞、延长接管时间或关闭资源合同监督来规避问题。

## 6. V2.13.0.19 修复内容

### 6.1 生命周期与告警叠加分离

在 `Controller/EpbManager.cs` 新增统一解析规则 `ResolveRuntimeStateForRunnerWarning`，并在两个软预警发布入口使用：

- `OnRunnerWarningRaised`；
- `PublishRecoverableControlFaultWarning`。

规则如下：

| 当前状态 | 软预警后的状态 |
|---|---|
| Running | WarningRunning |
| WarningRunning | WarningRunning |
| Starting | 保持 Starting |
| Learning | 保持 Learning |
| Qualification | 保持 Qualification |
| Paused | 保持 Paused |
| Recovering | 保持 Recovering |
| 已停止、完成、报警等终态 | 保持原终态 |

当软预警发生但生命周期被保留时，新增字段日志：

```text
FieldMetric WARNING_OVERLAY EPB=<n> LifecyclePreserved=<phase> Reason=<code>
```

这样现场既能看到软预警，又不会改变 Watchdog 对 Timer/Runner 的正确要求。

### 6.2 中文软预警文案

在 `Controller/Alarm/AlarmMessageLocalizer.cs` 增加：

- `RapidLoadRiseWithoutObservedEmpty` 中文解释：`检测到负载快速上升，但本圈尚未取得空载电流基线`；
- `ToUserWarningMessage` 软预警专用入口；
- 软预警明确追加：`这是软预警，不会单独触发卡钳永久停机`；
- 未知软预警不再套用“系统检测到异常，已执行安全保护”的硬故障兜底。

主监控界面的 `ChannelWarningRaised` 已改用软预警专用本地化入口。

### 6.3 保留 Watchdog 安全能力

本次没有放宽以下保护：

- 正式 `Running/WarningRunning` 缺少 Timer，仍会先刷新、持续 5 秒后接管；
- `Learning/Qualification` 缺少 Runner，仍会接管；
- 机械圈长期无进展，仍按独立的机械进展期限接管；
- Stop 阶段不推进、持久化边界未闭合、恢复 owner 矛盾等保护均保持；
- Watchdog 双端写入有界截止和读写解耦保持不变。

修复只让 Watchdog 收到真实生命周期，没有删除或绕过任何安全条件。

## 10. 最终判定

事故因果链已经由主日志、学习 manifest、Watchdog 双端日志、截图和录屏相互印证。V2.13.0.15 与 V2.13.0.18 的差异也证明：旧版本只是通过 Watchdog 通信停滞掩盖了相同状态错误。

V2.13.0.19 已从状态模型源头修复软预警覆盖生命周期的问题，同时保留 V2.13.0.18 的 Watchdog 通信与安全接管能力。代码、版本号、中文诊断和自动化回归均已落地；发布前剩余工作只有生成可追溯正式包并完成本节规定的现场实机验收。
