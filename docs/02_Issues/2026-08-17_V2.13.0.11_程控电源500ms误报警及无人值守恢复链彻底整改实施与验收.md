## 1. 交付结论

本次将版本迭代为 **V2.13.0.11**。这是兼容现有项目和数据格式的故障修复版本，不改变操作流程，不需要修改旧项目文件。

V2.13.0.10 的直接误报警链已经被拆除：

1. 成功快照的时间戳改为全部 SCPI 查询完成后的时间，另存轮询起止时间和真实耗时。
2. 单次成功轮询超过 500ms 只产生 `TelemetryDelayed` 诊断，不锁存故障、不退出监控、不撤销动作许可；重复日志按组限频为最多每分钟一条。
3. 真正的查询异常或断线进入 `CommunicationDegraded`，原地持续重连。任意一次完整成功遥测立即产生 `TelemetryRecovered` 并清零连续缺失圈数。
4. 通信降级期间，以已经完成且取得 DAQ 动作电流证据的**电源组正式动作槽**计数。同组多个 EPB 在同一槽只计一次；连续第 8 个槽仍无成功遥测才升级 `CommunicationUnavailableConfirmed`。
5. 没有正式圈推进时，以 120s 为通信降级硬上限，防止永久处于黄色状态。
6. 保护跳闸、持续限流、持续低压、意外 OFF、动作无电流、停机/恢复关断不可确认仍立即失效安全，不受“8 圈”延迟。

原运行历程中会放大故障或阻碍无人值守恢复的关联问题也已一并收口：StopAll 物理安全与逻辑清场分层、DAQ 恢复代次隔离、液压 generation 强制撤销、历史快照单 worker、事故取证乱序容错、checkpoint 共享读/原子替换重试、遥测临时段启动恢复。

## 3. 程控电源判据的最终实现

### 3.1 快照时间语义与查询减压

涉及文件：

- `PowerSupply.Core/PswModels.cs`
- `PowerSupply.Core/PswTcpClient.cs`

`PswSnapshot` 新增：

- `PollStartedUtc`
- `PollCompletedUtc`
- `PollDurationMs`

`TimestampUtc` 明确定义为 `PollCompletedUtc`。快照只有在 OUTP、设定值、测量值、状态和保护查询全部完成后才盖完成时间，因此不会再把一次已经成功返回的快照判成“返回时已陈旧”。超时判断使用 `Stopwatch` 单调时钟，不受系统校时影响。

OVP/OCP 不再每 100ms 重复读取。它们在连接/首次快照、设定值写回以及每分钟健康检查时刷新；常规轮询减少两条串行 SCPI 查询，直接降低拥塞和共同停顿时的放大效应。

### 3.2 三层状态与动作策略

涉及文件：

- `Controller/PowerSupplyCoordinator.cs`
- `Controller/EpbManager.BatchStart.cs`
- `Controller/EpbManager.PauseResume.cs`
- `Controller/EpbManager.cs`

| 状态 | 判定 | 系统动作 |
|---|---|---|
| `TelemetryDelayed` | 轮询最终成功，但耗时 ≥500ms | 只记录诊断；继续监控；不报警停机 |
| `CommunicationDegraded` | 查询异常、断线或无完整快照 | 黄色降级；每 500ms 重连；保留动作许可和旧的已确认供电状态 |
| `CommunicationUnavailableConfirmed` | 连续 8 个唯一正式组动作槽仍无成功遥测 | 锁存受影响电源组系统故障并进入安全停止 |
| `CommunicationUnavailableDeadline` | 降级持续达到 120s 且仍未恢复 | 即使没有圈推进，也锁存通信故障并安全停止 |

正式圈只有在控制成功且持久化提交完成后才调用 `RecordSuccessfulActionCycle`。这一提交点已经要求本圈具备关联到通道、圈号和命令窗口的新鲜 DAQ 动作电流证据，因此可以证明本次动作得到了供能。计数键使用公共正式相位槽，同一电源组的多个通道不会重复计数。

通信成功时，无论耗时是 100ms 还是 1.3s，都会立即：

- 更新最近成功遥测完成时间；
- 清除 `CommunicationDegraded`；
- 将 `ConsecutiveCommunicationMissCycles` 归零；
- 产生一次 `TelemetryRecovered` 恢复边沿。

### 3.3 配置值与兼容策略

涉及文件：

- `Config/PowerSupplyConfig.cs`
- `MTTfTest/Config/PowerSupplyConfig.xml`

| 配置 | V2.13.0.11 值 | 含义 |
|---|---:|---|
| `PollIntervalMs` | 100ms | 正常轮询目标周期 |
| `TelemetryDelayWarnMs` | 500ms | 成功慢查询诊断阈值，不再是停机阈值 |
| `TelemetryStaleMs` | 500ms | 仅保留给安全证据判鲜和旧配置兼容 |
| `CommunicationAlarmConfirmCycles` | 8 | 连续缺失的正式组动作槽确认数 |
| `CommunicationAlarmMaxMs` | 120000ms | 无圈推进时的最大通信降级窗口 |
| `CommunicationRetryMs` | 500ms | 通信异常后的重连节拍 |

旧配置没有 `TelemetryDelayWarnMs` 时会读取原 `TelemetryStaleMs` 作为诊断阈值；其余新项使用上述安全默认值。配置校验会拒绝小于两倍轮询周期的延迟阈值、非法确认圈数以及不合理的重连/最大降级窗口。

### 3.4 即时安全保护没有降级

“8 圈”只适用于**电源遥测通信不可用，但 EPB 动作电流仍证明供能正常**的场景。以下情况仍立即停止受影响组：

- 电源保护跳闸；
- 持续限流或持续低压；
- 运行中输出意外关闭；
- 动作命令后没有新鲜的关联电流证据；
- 停机/DAQ 恢复时 DO OFF、电流清零或电源 OFF 无法确认。

因此本改动降低的是通信诊断敏感度，不降低物理安全等级。

## 4. 共同停顿与恢复链整改

### 4.1 历史快照改为单一有界消费者

`Controller/EpbManager.WarningSnapshots.cs` 不再为每个通道调用一次 `Task.Run` 做同步导出、目录统计和旧目录删除。现在全局最多一个 `RollingHistoricalSnapshotWorker` 顺序处理，队列容量为 32，并按 `channel:cycle` 去重。

队列满时只跳过可选历史副本并记录计数；正式圈提交、实时控制、报警和原始数据落盘不受影响。这样消除了五通道同刻完成时 4～5 个重 I/O 任务同时启动的放大器。

已有 1Hz `HostRuntime` 和 DAQ 事故诊断会记录进程位数、GC 次数与 ETW GC pause、线程池可用 worker/I/O 线程、CPU、内存、句柄/线程、磁盘队列和磁盘吞吐。V2.13.0.11 暂不盲目切换 x64；应使用新封存数据先确认 NI 驱动兼容性和共同停顿的最终来源。

### 4.2 DAQ 事故取证不再因线程乱序丢失

`DaqIncidentEvidenceQueue` 现在允许 derived 或 terminal 在线程调度上早于 trigger 到达：先同步注册根上下文，但在 trigger 补齐前不启动无根导出。补齐后始终按 trigger → derived → terminal 顺序生成批次。

终态导出后的上下文保留有界 tombstone，迟到事件不会新建悬空根。拒绝原因不再统一为“有界门拒绝”，而是返回可统计代码，包括：

- `InvalidSubmission`
- `InvalidPhase`
- `SessionKeyMismatch`
- `SessionIdMismatch`
- `StorageSessionIdMismatch`
- `TerminalAlreadyRegistered`
- `TerminalAlreadyExported`
- `GlobalEvidenceQueueCapacity`

### 4.3 StopAll、DAQ 恢复和液压 generation

涉及文件：

- `Controller/EpbManager.StopSafetyHardening.cs`
- `Controller/EpbManager.DaqRecoveryState.cs`
- `Controller/ChannelRuntimeState.cs`
- `Controller/HydraulicGroupCoordinator.cs`
- `MTTfTest/UnattendedRecovery.cs`
- `MTTFTest.Watchdog/WatchdogHost.cs`
- `Watchdog.Protocol/WatchdogPolicy.cs`
- `Watchdog.Protocol/WatchdogProtocol.cs`

已落实的关键行为：

1. DAQ 100ms 带电陈旧首先撤销动作授权并并发发出整组安全 OFF；事故取证与正常恢复等待不能阻塞物理断电。
2. StopAll 先提交物理安全，再按 RunEpoch/Generation 强制摘除旧 Timer、Runner、恢复 owner、液压参与者和租约；迟到旧任务不能污染新运行。
3. 液压协调器支持 generation 强制中止，故障/StopAll 不再等待缺席成员走正常 15s barrier。
4. 强制清场、持久化边界和是否允许同进程重启分别记录；超时停止即使物理已安全，也只能交给新进程恢复。
5. Watchdog 心跳增加停止阶段、进展版本、残留资源、机械圈进展和恢复失败指纹；同一失败连续 5 次熔断，后续按 2/5/15 分钟低频探测，避免重启风暴。

### 4.4 checkpoint 与遥测文件并发

`Watchdog.Protocol/DurableJsonFileStore.cs` 使用允许 `ReadWrite|Delete` 的共享句柄读取，使 Watchdog 轮询不会阻止主进程 `File.Replace`。原子替换遇瞬时 sharing violation 会做最多 5 次、20/40/60/80ms 的有界重试。

checkpoint 不再在机械完成和正式完成两个观察者上重复写同一圈；机械完成事件作为进度权威来源，减少一半重复替换窗口。主文件、`.bak` 和项目镜像仍按 revision 选择最新有效授权，损坏或缺失均有分类结果。

电源遥测 writer 已具备启动扫描、校验并封存 `.csv.tmp` 的恢复流程；StopAll 只要求关键 writer/游标持久化在截止内完成，历史清理超时会留下证据供下一进程继续，而不会阻塞物理安全停止。

## 6. 发布与现场验收步骤

1. 使用 V2.13.0.11 的主程序、独立 Watchdog 和配套 XML 整包发布，禁止把新主程序与 V2.13.0.10 Watchdog 混用。
2. 发布包必须生成并保留 commit、配置摘要以及逐文件 SHA-256 manifest；启动日志应显示 `PackageVerified=True`、主程序和 Watchdog 均为 `2.13.0.11`。
3. 先做 30 分钟带设备故障注入：慢响应、断线后恢复、8 槽持续断线、保护跳闸、动作无电流和 OFF 不可确认。
4. 再做至少 24 小时连续运行，封存完整目录，统计：
   - `TelemetryDelayed` 次数、P99/P99.9/max 和最大连续簇；
   - `CommunicationDegraded/Recovered` 次数、恢复耗时和 8 槽升级次数；
   - DAQ callback gap 与 GC pause、线程池、磁盘队列的时间相关性；
   - StopAll 截止时 Timer/Runner/owner/participant/lease 残留；
   - checkpoint sharing violation、事故 manifest 完整率、SQLite `quick_check`。
5. 现场通过标准：
   - 所有成功慢响应均不触发系统故障；
   - 真实通信恢复后连续缺失计数均归零；
   - 只有连续 8 个组动作槽或 120s 上限才升级通信故障；
   - 动作无电流和硬件/关断安全故障仍在本圈立即停组；
   - 24 小时内无 StopAll 逻辑残留导致的人工介入，无 checkpoint sharing violation，无永久数据缺口。

## 7. 风险边界与最终状态

本次已经关闭 V2.13.0.10 中可由源码确定的直接根因和恢复链缺陷。以下不是遗留代码缺陷，而是发布前必须用真实硬件完成的验证：

- 0.5～1.3s 共同停顿的最底层来源需要由 V2.13.0.11 的 GC/线程池/磁盘/DAQ 同时序指标最终归因；历史快照并发 I/O 这一明确放大器已经移除。
- x64 切换涉及 NI 驱动和部署环境兼容性，本补丁不把未经验证的平台切换混入安全修复。
- 自动化测试不能替代 24 小时真实设备、真实网络、真实磁盘过滤驱动下的连续运行。

若现场验收出现异常，应保留完整封存和 V2.13.0.11 二进制 manifest 后回退整包；不得只回退主程序或只回退 Watchdog。
