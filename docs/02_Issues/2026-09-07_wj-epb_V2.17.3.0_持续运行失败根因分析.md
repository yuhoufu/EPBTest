# wj-epb V2.17.3.0 持续运行失败与旧版回退运行分析

分析日期：2026-09-07。时间统一为北京时间。依据[现场部署与运行观察](2026-09-07_wj-epb_V2.17.3.0_现场部署与运行观察.md)、本机封存日志、只读监控快照和发布提交源码。本文不执行现场操作，不修改产品代码；既有测试结果仅复核记录，没有重新运行硬件试验。

## 1. 结论与确定程度

**新版没有完成“原项目恢复后正式圈持续推进”的验收，原因是两段故障接力：第一次学习时持久化消费落后引发安全暂停和进程替换；替代进程完成学习后，正式启动与 Timer 健康检查发生竞态，自愈又被执行许可校验拒绝，最终再次整批重建。** 停止后的关闭收尾还有独立问题。

| 判断 | 确定程度 | 依据与边界 |
|---|---|---|
| 第一次直接触发点是持久化拥塞，之后背压扩展到 DAQ 后台处理 | 已证实 | 队列年龄、容量、故障顺序和代码一致；不是仅从进程消失推断 |
| 新增耐久写入提高了现场写盘成本，是拥塞的重要候选原因 | 有源码支持的推断 | 新增 FULL 同步原始日志、共享锁、耐久刷新；缺少故障时线程栈与各阶段延迟，尚不能唯一归因 |
| 第二次发生启动中间态被 Timer 检查当作故障的竞态 | 强证据 | 同一 Timer 先 Created，约42ms后 Running，却在同毫秒进入 TimerNotRunning 自愈；源码发布顺序存在窗口 |
| Timer 自愈被 StaleExecutionPermit 拒绝，达到三次阈值后扩大成整批重建 | 已证实 | ERROR、状态变迁和调用路径一致；具体哪一项许可谓词不满足尚未记录 |
| 这些 Timer/许可机制全部由新版新增 | 不成立 | 旧版标签也有同样的 Running 提前发布、TimerNotRunning 判定和 StaleExecutionPermit 检查 |
| 旧版在本次回退后的观察窗口运行更稳定 | 已证实，但有时间范围 | 同机同项目六通道正式圈、机械圈及实际写入表推进；不能推导旧版长期无故障 |

因此不能把问题归为“只需多重启一次”，也不能认为关掉保护、增大队列或放宽许可就完成修复。需要分别解决存储延迟、启动状态发布、自愈许可生命周期和停止收尾。

### 3.1 新旧写入路径确有实质差异

发布源码中的关键变化：

| 路径 | 旧标签 | V2.17.3.0发布提交 | 工程影响 |
|---|---|---|---|
| index.db同步策略 | WAL、Synchronous=Normal | WAL、Synchronous=Full（EpbDiskWriter.cs:338） | 更强耐久语义，也增加提交同步成本 |
| 原始批次日志 | 没有该新增RawJournal文件实现 | StageDeviceRawJournal，原始帧入FULL同步WAL后才写环形数据 | 活跃圈写入增加数据库事务和数据副本 |
| 多卡日志串行点 | 不适用该新增路径 | `_rawJournalGate`内设备批次事务提交 | 某次慢提交可能扩大另一卡的等待 |
| 环形数据耐久完成 | 原有MMF路径 | RawJournal.cs包含视图Flush及文件Flush(true)，随后索引/回收 | 需要区分批次日志提交与环形应用/回收，不把所有Flush都说成每批必执行 |

源码定位：`DataOperation/EpbDiskWriter.RawJournal.cs:83`（设备批次事务）、`:216`（日志连接FULL）、`:375`（环形文件耐久刷新）；`EpbDiskWriter.cs:1843`（批次日志入口）。行号均对应发布提交。

日志给出的采样配置为Fs=2000Hz、每批20点，即每卡名义100批/秒。**若两卡都连续存在需记录的活跃圈，设备批次事务名义需求可接近200次/秒**，还没有计入圈结束、索引和其他写入。实际事务数受活跃圈窗口影响，不能将该上界当成实测 IOPS。256批只提供约2.56秒的单卡输入缓冲量；1000ms年龄保护会更早触发。

18:48:01–02 HostRuntime记录系统CPU约16–17%、可用内存约11GB，磁盘写速率有26到102.61MiB/s的变化。它不支持“内存耗尽/CPU整体打满”结论；吞吐量也不能证明同步提交延迟合格。尚缺磁盘卷对应关系、提交P99/最大值、锁等待、线程栈和系统I/O跟踪，不能把原因确定为硬盘损坏、杀毒扫描或某个外部程序。

**较可信解释：新版增强耐久写入后，学习开圈等活跃写入窗口对现场存储延迟更敏感；本次出现了消费停顿。仍需测出停顿具体发生在RawCommit、索引、Flush、共享锁还是其他I/O。** 替代进程后来能完成10圈学习，也是反证：新路径不是任何时候都完全写不动。

## 4. 第二次失败：正式启动被自愈打断

18:51:24.511，两卡持久化深度均仅2批、最老约19ms，Discontinuities=0；多通道第10学习圈已封存。这段故障不能简单延续解释为首次队列满仍未恢复。

关键时序如下：

1. 18:51:27.022，EPB12 Timer创建，Instance=50054755，Generation=1，RunEpoch=3。
2. 18:51:27.064，ERROR报告“通道仍显示运行，但Timer状态为Created”。同一毫秒，run.log又记录同一实例进入Running、Reason=Start。
3. 紧接着同一实例进入PausePending/Paused，原因明确是 `TimerSelfHealing:TimerNotRunning`；首延迟约2978ms，尚未轮到第一次正式回调。
4. 18:51:27.093，通道变为Recovering。18:51:27.108，批次仍输出BatchFormal开始；监督后续还有交接成功记录。这些发布消息不能覆盖通道已经进入自愈的事实。
5. 18:51:31.168，自愈累计3次，以 `PowerEnableRejected StaleExecutionPermit` 升级整批重建，其他通道随StopAll终止。

### 4.1 启动状态的发布窗口有源码对应

`Controller/EpbManager.BatchStart.cs:2156`附近先遍历通道发布Running，再调用 `StartFormalPhaseTimers`。后者在约3398行取得Timer，还要查询上次圈号、计算剩余数，最后约3417行调用 `timer.StartAsync`。健康检查可以在两者之间看到“通道Running、Timer Created”。

`Controller/EpbManager.TimerRuntimeHealth.cs:839–895`对显示Running但 `!timer.IsRunning` 的情况立即返回TimerNotRunning自愈；该分支没有使用后面的心跳静默阈值。因此这次不是等了数秒仍无正式圈才判定，而是启动中间态就被处理。日志中Created到Running约42ms及同毫秒触发，强烈支持这一并发窗口。

需要保留精度边界：不同线程的日志并非原子追踪，无法用毫秒级打印唯一还原每次指令执行顺序；但“新Timer刚启动即被该自愈暂停”的实例身份和状态链是直接证据。

### 4.2 为什么自愈又失败

`BeginTimerRuntimeSelfHealing`（TimerRuntimeHealth.cs:971起）先暂停Timer、取消圈暂停源、封闭当前圈，取得恢复所有权，确认持久化边界，再检查DAQ和电源，最后才重新加入正式槽。

电源准备入口 `EpbManager.cs:10049` 捕获通道执行许可；检查失败就抛出StaleExecutionPermit。`:4317`的校验同时要求通道一致、fence当前有效、RunEpoch相同、通道启用、无需进程重启。因此错误名不能直接证明“拿到了迁移前旧nonce”，也不能唯一说明是哪次撤权导致。

现场证实恢复流程不能通过这项前置检查，但没有输出各谓词、permit generation、当前fence generation等必要细节。**应优先检查暂停/自愈撤权后，恢复许可的签发和消费是否顺序正确，以及启动线程与自愈线程是否并行改变代次。** 这是排查方向，不应冒充已经定位到某一行撤权的结论。

### 4.3 这不是一个可以简单归为“新版新增”的问题

比较旧标签可见：提前发布Running、TimerNotRunning分支和StaleExecutionPermit拒绝均已存在；TimerRuntimeHealth在两版本之间主要增加了一次 `InspectExpectedExecutionProgress()` 调用。因此更准确的描述是：**潜在窗口在此次新版实际运行中暴露，新增存储耗时或恢复路径可能改变触发概率，但现有证据不能证明唯一是哪项新改动造成。** 旧版一次顺利通过启动不等于该竞态不存在。

## 5. 停止与关闭问题应单独整改

18:52:05用户正常停止后，已记录四组电源关闭、两路低压、Dev1/2保存边界19553/19537、队列排空。18:52:08恢复任务出现OperationCanceledException，时间上在人工停止之后，不能倒因为最初故障。随后安全交接提交失败、18:52:10访问已释放PowerSupplyCoordinator、18:53:37关闭等待超过60秒，是停止任务与后台恢复/释放生命周期未完全收敛的证据。

物理安全及保存边界满足，并不自动证明后台任务都退出、交接已提交、主窗口可关闭。需要独立验证“停止取消恢复→等待安全任务→完成交接→释放资源→退出”的所有权和幂等性。用户授权后的精确残留终止只完成了本次维护退场，不是关闭缺陷已修复的证据。

### 6.2 能支持的原因与不能支持的推论

- **本次旧版成功穿过学习到正式的启动窗口。** 持续正式计数说明执行体和许可在当前会话中可用；不代表所有恢复分支已验证。
- **旧版活跃写入路径较少承担新版RawJournal的同步事务负担。** 这是同机表现不同的合理解释，有代码差异支持；尚不是同负载、同缓存条件的受控性能对照。
- **回退保留了原项目和新版11圈学习事实，未用清零换取可运行。** 后续旧版实际写入epb_cycles；新版cycle_receipts保留但不再推进，不能查错表误判旧版停滞。
- **旧版也有短时延迟，但未演变为持续保存失败。** 例如20:05:37、20:45:39、20:48:52、21:23:23出现约106–111ms持久化警告；后续队列归零、Produced/Persisted收敛、丢弃和不连续指标为0，正式圈继续推进。这与新版首次超过1000ms并达到256批是不同严重度。
- **运行环境并非严格相同。** 两次启动时间、缓存、存储历史、监督任务及恢复路径不同，旧版没有新版独立分钟健康任务。没有证据将健康任务、远程巡检或清理日志指定为本次根因。

更关键的是，[I0050凌晨事故分析](2026-09-07_V2.14.2.11_I0050_凌晨退出时间历程与V2.17.3解决性分析.md)已记录旧版约1.17秒DAQ空窗、样本陈旧、InconsistentRecovery退出，以及安全代理身份拒绝导致自动恢复不成。因此结论只能是“旧版在本次回退观察期持续推进，适合作为当前回退运行基线”，不能说“旧版天然稳定、新版所有机制都有问题”。

## 7. 为什么已有测试通过仍没覆盖现场

[安装包验收记录](2026-09-06_V2.17.3.0_I0048-I0049_故障恢复与关闭整改及安装包验收.md)记录控制759/759、写盘66/66、电源调试19/19、隔离测试机安装态恢复12/12，以及第二轮六小时组件模拟582轮通过。六小时结果明确 `hardwareTestPerformed=false`，测试器使用独立目录，且修过自身状态文件替换重试。

这些结果能说明对应断言在对应环境通过，不能证明现场双NI卡2000Hz、原项目、大量历史数据和真实存储延迟下仍符合预算；也未证明恰好在Timer Created到Start的几十毫秒插入健康检查后仍能正确收敛。安装拉起、RecoveryBatchCommitted、学习成功、正式耐久圈成功是四个不同验收层次。

## 8. 后续修复优先级和明确验收条件

| 优先级 | 修复/取证方向 | 可判定验收条件 |
|---|---|---|
| P0 | 正式启动发布原子性：启动期间使用明确状态/所有权，Timer就绪后再发布Running；健康判定二次核对实例、代次与启动状态 | 在Created到Start每个阶段设置确定性测试屏障并触发健康检查，不误自愈；真正未启动超过预算仍报警，不能永久忽略Created |
| P0 | Timer自愈许可生命周期 | 记录拒绝谓词及代次；撤权后以受控恢复授权完成准备并重新加入，人工停止/急停/旧代次永远不能上电 |
| P0 | 存储耗时定位与批量耐久提交设计 | 采集RawGateWait、RawCommit、RingFlush、IndexCommit及队列年龄P95/P99/最大值；隔离环境双卡等效流量、六通道学习和正式写入均在预算内，保存边界真实耐久且无丢弃 |
