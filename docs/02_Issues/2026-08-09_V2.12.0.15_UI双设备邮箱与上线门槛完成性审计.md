## 技术结论

V2.12.0.15 将 V2.12.0.14 的“UI 只保留最新工程值”从窗体内的私有实现提升为可独立验证的固定两槽邮箱。Dev1 和 Dev2 并发各发布 100,000 批、消费者全程阻塞时，邮箱最多只保留 2 个引用，恢复后每设备只返回最后一批，消费后无历史工作残留。采集层唤醒仍使用容量 1 的二值合并信号，因此“数据槽有界”和“唤醒数有界”现在都有压力反例。

主框架、设置窗体和实时监控窗体的遗留内存日志上限也已统一从每类 100,000 条收紧为 2,000 条。完整项目日志仍由进程级有界后台写入器持久化，所以这一改动只删减重复的 UI 浏览缓冲，不删减可审计日志。

自动化结果为控制/恢复 `308/308`、写盘 `28/28`、现场门禁 `14/14`、Release `0 error`。这些证据证明主报告第 8–10 节中可在本机模拟的软件条件已有代码与回归覆盖；但它们不能代替第 11 节要求的真实 NI、液压、电源、磁盘和 UI 联合 24/72 小时数据。因此当前结论仍是“软件候选完成，现场放行未完成”。

## 完成标准与证据边界

本审计使用三种状态：

- **已实现：** 当前代码明确存在所要求的机制。
- **已自动验证：** 有直接正例和/或反例触发该机制，不只是编译通过。
- **待台架：** 结论依赖真实驱动、物理设备、长时间调度或人工安全签字，本机模拟不能证明。

这一划分防止用单元测试对“无人值守可上线”做过度外推。

## UI 阻塞不再变成恢复后的历史追赶

### 固定两槽邮箱替代窗体内队列

`LatestPairMailbox<T>` 只有 Dev1/Dev2 两个位置，发布是覆盖而不是追加。`TryTake` 在同一个锁内读取并清空两个槽；处理期间到达的新批次会在本次处理结束后补调度一次。这保留了两设备隔离，同时把待处理引用上限从旧实现的 128 批固定为 2 批。

### 并发压力反例覆盖实际语义

两个生产任务并发向独立槽各发布 100,000 个对象，期间不启动消费者。验证要求为：

1. 发布结束后 `PendingSlotCount == 2`；
2. Dev1 返回序号 `99999`，Dev2 返回序号 `199999`；
3. 消费后 `HasPending == false`且 `PendingSlotCount == 0`；
4. 采集层另一反例连续 `Set` 10,000 次，唤醒计数始终为 1，消费后为 0。

因此，窗体层和采集层的合并语义都已被直接验证。这不证明真实 ZedGraph 在特定显卡/RDP 环境下必然满足 P95 200 ms，所以 UI 现场响应仍列为台架门槛。
