## 1. 结论先行

本次已在保留 V2.13.0.36 未提交修改的前提下，将 I0003、I0004、I0005 暴露出的恢复事务、物理断电证据、形式槽位、StopSafety、Watchdog、恢复标记、普通日志和发布身份问题统一整改到 **V2.13.0.37**。没有回退到 V2.13.0.30，也没有复制其旧实现；V2.13.0.30 只作为正常长稳行为的差分基准。

结论如下：

1. **代码已实现 / 本地已验证**：暂停中的 DAQ 恢复完成后终态为 `HeldForManualPause`，Timer、Runner、槽位和继续许可保持；不再由 10 秒外围等待取消 60 秒恢复事务，也不再错误转入 `StartBlocked`。
2. **代码已实现 / 本地已验证**：DAQ 恢复和 StopSafety 以带 RunEpoch/操作代次的真实物理回执为证据；仅“入队成功”或旧状态读取不再证明已断电，同代迟到成功可被接纳，旧代回写被拒绝。
3. **代码已实现 / 本地已验证**：压力数值与压力时间证据分流。约 70 bar 但样本年龄 1128 ms 的情形归类为“时间证据过期”，保持输出断能并恢复采样，不得报告真实低压硬件故障。
4. **代码已实现 / 本地已验证**：形式参与者终态改为 `SafeCommitted / SafeAborted / SafetyUnproven`。可靠作废只释放本槽、不计数、不撤销整批；只有物理或耐久边界无法证明时才触发批次安全失败。负槽位禁止写入正式终态。
5. **代码已实现 / 本地已验证**：恢复 worker 正常返回、异常、取消和 Stop 跨代隔离均确定性收口；漏发终态自动先 OFF 后进入安全终态，旧代 worker 只保留审计，不能继续占有活动 owner 或污染新代。
6. **代码已实现 / 本地已验证**：StopSafety 改为“物理事务单飞、请求回执独立”。多个同时到达的请求可加入同一活动物理事务；旧事务超时/隔离后，新请求创建新代次并重新执行幂等安全动作，不再在 52～75 ms 内返回历史 Freeze 超时。
7. **代码已实现 / 本地已验证**：Watchdog 分别判断 Transport、Application、Control、Physical 健康。PID 和 UI 仍存活时，逻辑源/心跳过期只触发传输修复和安全停止，不直接杀主进程；同 authority 重连并取得新鲜证据后撤销旧 takeover。
8. **代码已实现 / 本地已验证**：恢复标记升级为带 RunId、Epoch、Stage、生成代次和内容哈希的格式；旧格式兼容但限频。标记具备 Accepted/Rejected/Deferred 账本、退避、每分钟至多一条汇总日志和终态归档，不再产生 5625 条 `ContextMissing` 热循环。
9. **代码已实现 / 本地已验证**：普通日志新增接收/耐久水位、最后成功/失败、队列和丢弃健康快照；仅在存在未耐久积压或明确失败超过 5 秒时报告 stall。项目路径故障时转入 16 MiB 独立应急 spool，恢复后按序回放；无日志流量不误报。
10. **代码已实现 / 本地已验证**：Debug x86、Release Any CPU、主要测试工程、字段门禁和脏工作区候选构建均已执行。候选明确标记 `DIRTY_CANDIDATE_NOT_FOR_PRODUCTION`，不得当作正式现场包。
11. **待现场验证**：R1 的底层 DAQ/主机 0.28～2.05 秒时隙空窗仍不能仅凭三份封盘唯一归因；2 小时、8 小时/100 轮、24 小时、72 小时和 7 天硬件长稳均尚未执行。本报告不宣称现场长稳已经通过。

当前放行结论：**V2.13.0.37 的软件整改和本地自动化已形成验证候选，但工作区不清洁且硬件长稳门禁未完成，禁止生成或使用正式生产包。**

### 3.1 可作为差分基准的稳定行为

原报告从 V2.13.0.30 对照封盘确认：

V2.13.0.37 保留这些行为目标：正常周期不因诊断或短传输故障改变正式计数；通信异常优先重连；旧代状态不得跨槽、跨 Run 或跨 writer 生效。

### 3.2 为什么不回退或照搬

V2.13.0.30 同样潜伏以下缺陷：

- worker 完成但不发布终态；
- StopSafety 历史结果缓存；
- 暂停后 DAQ 已恢复仍可能转 `StartBlocked`；
- 约 70 bar 的陈旧压力样本仍可能被错误描述；
- 已关闭管道的未观察异常。

V2.13.0.30 与 V2.13.0.35 在 `2.13.0.28` 后分叉；两版本差异约 112 个文件、+15,054/-785 行。V2.13.0.35 叠加了更多恢复状态、owner、检查点和 Watchdog 阶段，却没有给这些状态建立统一事务边界，因此复合故障更容易放大为连续停机。正确做法是以 V2.13.0.30 的正常输出作为 oracle，在新实现中补全可证明的安全状态机，而不是回到旧代码。

## 5. 接口、回执与状态机变化

### 5.1 统一恢复阶段

恢复单调阶段为：

```text
Detected
  -> SafetyOffSubmitting
  -> SafetyOffConfirmed
  -> DaqRebuilding
  -> FreshnessConfirmed
  -> PersistenceClosed
  -> HeldForManualPause | RejoinedRunning | SafeIdleFault | Superseded | CancelledByStop
```

实现约束：

- 阶段只能前进；`SafeIdleFault` 后拒绝回退。
- 正常返回漏终态、同步/异步异常和取消都由协调 wrapper 的 finally 补成安全终态。
- `HeldForManualPause` 必须同时具备断电、新鲜度和持久化边界证据。
- 60 秒内不能证明闭环时进入 `SafeIdleFault`，输出保持断能并要求人工处置。

### 5.2 `SafetyOffReceipt` 与电源安全接口

新增/扩展：

- `SafetyOffReceipt`：命令 ID、关联 ID、目标类型/编号、RunEpoch、操作代次、提交/完成时间、证据来源、状态和错误。
- `PowerSafetyDisableResult`：电源组、操作代次、最终 outcome、`ConfirmedOff`、硬件/读回证据和错误。
- `IPowerSupplyCoordinator.DisableGroupForSafetyAsync` / `DisableAllForSafetyAsync`：供 DAQ 和 StopSafety 使用；原 `DisableGroupAsync` 保留兼容。

判定规则：

- DO 以高优先级 worker 的真实硬件完成回执为准；入队成功不是 OFF。
- 电源只接受本 Run/代次且 `ConfirmedOff=true` 的结果。
- 同代迟到成功可完成当前事务；旧代回调只观察，不修改新代状态。

### 5.3 形式圈关闭回执

新增 `CycleAttemptClosureReceipt`，并把形式参与者终态明确为：

| 终态 | 含义 | 计数/批次处置 |
|---|---|---|
| `SafeCommitted` | 机械循环与耐久提交均完成 | 正常计数并释放槽位 |
| `SafeAborted` | 本圈不计数，但持久化中止边界可靠且物理安全 | 释放槽位，不撤销整批权限 |
| `SafetyUnproven` | 断电、释压或持久化边界无法证明 | 阻断后续槽位并进入批次安全失败 |

槽位号小于零时拒绝提交正式终态，设备保持断电，转恢复或安全故障；不会再生成 `Slot=-1` 正式记录。

### 5.4 StopSafety 请求与物理事务

新增 `StopRequestReceipt` 和 `StopAllWithReceiptAsync`，保留原 `StopAllAsync` 签名。

```text
Stop request A ─┐
Stop request B ─┼─> active physical safety transaction (single-flight)
Stop request C ─┘

terminal/timeout/quarantine
        -> next request creates a new generation
        -> repeats idempotent OFF/power-disable actions
```

Stop 顺序调整为：建立控制栅栏并立即提交 DO OFF/启动电源禁用，再冻结 Timer/Runner 和执行非关键清理。接近截止但已经产生有效物理进展时重新核验，可报告“设备已安全、后台收口延迟”，但一次 Freeze 超时不会成为进程终生结果。

### 5.5 Watchdog 健康和传输代次

统一健康判断按四层执行：

| 层 | 证据 | 默认处置 |
|---|---|---|
| Transport | pipe/heartbeat/ACK/connection generation | 退休旧连接、重连、重置新鲜度宽限 |
| Application | PID、进程启动时间、UI 响应 | PID/UI 活着时禁止仅凭逻辑失鲜杀进程 |
| Control | aggregate、owner、checkpoint、逻辑源新鲜度 | 请求安全停止/自恢复；NoWork 完整回滚 |
| Physical | OFF、电源、压力、持久化边界 | 仅硬截止无法证明安全时允许强制接管 |

Client 的 writer 与精确连接 owner 原子安装；同步 guarded send 使用独立发送线程，避免 ThreadPool 被同步调用占满时 writer 无法推进。关闭帧真实写入后，即使 Sidecar 立即按协议退休连接，也保留成功物理发送结果；健康状态回写仍受精确代次 CAS 保护。

### 5.6 marker 和日志

- marker 新格式：RunId、Epoch、Stage、Generation、UTC、内容 SHA-256；旧格式兼容读取但走限频等待。
- marker 账本：`Accepted / Rejected / Deferred`；退避重试；每指纹每分钟最多一条汇总；成功或终态拒绝后原子归档。
- `ProjectLogHub` 健康：AcceptedVersion、DurableVersion、LastSuccess、LastFailure、QueueDepth、DroppedRecords、EmergencySpool。
- stall 条件：有“已接收未耐久”积压或明确写入失败持续超过 5 秒；没有日志流量时不报错。
- 应急 spool：默认 16 MiB；项目目录失败时按项目根哈希隔离到 `%LOCALAPPDATA%`；恢复后按序回放。
- 日志故障进入心跳、告警和审计，但不单独作为杀进程依据。
