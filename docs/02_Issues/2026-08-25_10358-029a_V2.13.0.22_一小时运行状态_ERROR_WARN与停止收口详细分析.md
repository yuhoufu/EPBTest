## 5. 预警状态为何仍不可信

### 5.1 本次不只是 EPB12，EPB5/11 也被旧预警锁存

`run.log` 有 11 次 `WARNING_OVERLAY`，没有一次 `WARNING_OVERLAY_CLEARED`。最终 Watchdog 心跳中：

|---|---|---:|---|---|

| EPB5 | 12:17:25 | 37 圈 | 14.861 A / Success | `WarningActive=true` |
| EPB11 | 11:50:10 | 146 圈 | 15.397 A / Success | `WarningActive=true` |
| EPB12 | 12:24:26 | 9 圈 | 14.969 A / Success | `WarningActive=true` |

这组证据排除了“界面一直橙色是因为每一圈都还在异常”的解释。根因是 V2.13.0.22 只发布预警激活事件，没有在后续可信健康圈封存后发布清除事件；Watchdog 和 UI 都继续读取旧 overlay。

实际影响：

- 不会单独触发永久停机，Watchdog 本次也没有以软预警接管进程；
- 会让操作员无法判断当前圈是否已经恢复；
- 会使汇总“预警数”和远程监控状态长期偏大；
- 长期锁存会造成告警疲劳，掩盖后来真正的新预警。

当前工作树中 V2.13.0.23 已加入后续可信健康圈的 overlay 清除路径和 `WARNING_OVERLAY_CLEARED` 证据，详见同目录文档：

- [V2.13.0.23 预警 Overlay 即时恢复彻底修复实施及验收](./2026-08-25_V2.13.0.23_预警Overlay即时恢复_彻底修复实施及验收.md)

但本报告的数据全部来自 V2.13.0.22，**不能用来证明远程机上的 V2.13.0.23 已经正确清除预警**。V2.13.0.23 必须用新封盘验收。

## 7. 两条 ERROR 的详细根因

### 7.1 ERROR 1：Watchdog `TaskScheduler.UnobservedTaskException`

#### 现象

11:24:41.278 记录 `WatchdogConnectException: Watchdog命名管道不可用：操作已超时`，堆栈位于：

- `WatchdogClientTransportEngine.ConnectOwnerAsync`；
- `ConnectAsync`；
- `ConnectFirstOrLaunchAsync`。

但同一会话的事实是：

- 11:24:41.057 Sidecar helper 已启动；
- 11:24:41.261 Attach 握手完成；
- 11:24:41.338 UI 显示 Watchdog 就绪；
- 后续心跳序号和确认序号均到 3656；
- `RecoveryAttempt=0`、`RelaunchGeneration=0`、`DroppedEventCount=0`；
- 最终状态 `ManualStopCompleted`。

因此这条 ERROR 不是“Watchdog 本次没有工作”，而是 connect-first 的首次预期失败被重复留在一个无人等待的共享任务里。

#### 代码级原因

当前源码 `Watchdog.Client/WatchdogClientTransportEngine.cs` 的 `ConnectAsync` 使用 `ConnectReservation.Completion` 给并发 joiner 共享首次连接结果。owner 在首次连接失败时：

1. `reservation.Completion.TrySetException(ex)`；
2. 同时 `throw` 给 `ConnectFirstOrLaunchAsync`；
3. 上层正确捕获 `PipeUnavailable` 并拉起 Sidecar；
4. 如果当时没有 joiner 等待 `Completion.Task`，该 TCS 的故障无人观察；
5. GC/终结器稍后触发 `TaskScheduler.UnobservedTaskException`。

也就是说，同一个首次连接异常有两份传播载体：owner task 已被观察，reservation completion 没有被观察。

#### 影响和彻底方案

本次影响仅为 ERROR 污染，没有触发退出、恢复或控制中断。但全局 ERROR 中出现“未处理异常”会掩盖真正的异步故障，必须修复。

建议：

1. 连接 owner 和 joiner 共享同一受监督 task，避免再复制一个故障 TCS；或在 owner 发布共享故障后显式观察该 completion 的 Exception，同时保留 joiner 的 await 语义。
2. 首次“管道不存在”作为 connect-first 的正常分支记录 INFO/DEBUG；只有 Sidecar 拉起后仍 Attach 失败才升级 ERROR。
3. 增加确定性测试：无现存 Sidecar、0 个 joiner、多个 joiner、首次超时后成功拉起；强制 GC 后 `UnobservedTaskException` 必须为 0。

### 7.2 ERROR 2：`AO 冷启动安全基线写零失败；至少一路未确认归零`

#### 现象与反证

12:27:04.071 出现 AO ERROR，但此前已经有完整反证：

- 12:27:03.934 两组压力均已确认低于 5 bar；
- 12:27:04.000 两个 Cylinder 都成功记录 `CommandPressure=0.0bar`；
- 12:27:04.000 记录 `AO 所有通道已复位为 0%`；
- 12:27:04.002 记录 `DO 全部关闭（所有设备）`；
- 12:27:03.967 双 DAQ 持久化边界已闭合。

所以这不是“至少一路物理 AO 没有写零”，而是写零成功后又对已释放对象执行了一次 Reset。

#### 代码级原因

当前关闭路径有重复硬件所有权：

1. `FrmEpbMainMonitor_FormClosing` 调用 `_epb.ReleaseHardwareForRestart()`；
2. `EpbManager.ReleaseHardwareForRestart()` 先 `_ao.ResetAll()`，再 `_ao.Dispose()`；
3. `AoController.Dispose()` 清空 `_tasks` 和 `_writers`；
4. 随后的 `FrmEpbMainMonitor_FormClosed` 又调用 `_ao.ResetAll()`；
5. `TryResetAll()` 发现配置仍有设备，但 `_writers.Count=0`，于是返回 false 并写出“冷启动安全基线失败” ERROR。

12:27:04.000 的成功日志和 12:27:04.071 的失败日志顺序与该路径完全一致。

#### 影响和彻底方案

本次为关闭阶段假 ERROR，物理输出已经安全。彻底方案不是把 ERROR 改成 WARN，而是消除双重所有权：

1. 人工停止、FormClosing、FormClosed 共享一个幂等的 `ShutdownTransaction/StopSafetyReceipt`；已经成功停止后，窗口关闭不得再次执行完整 StopAll。
2. `EpbManager` 作为硬件唯一 owner；`ReleaseHardwareForRestart` 成功后 UI 不再直接 Reset/Dispose 同一 `_ao/_do/_acq`，并立即清空 UI 引用。
3. `AoController` 增加明确的 disposed 状态；Dispose 幂等，禁止在 disposed 后把“无 writer”误报成物理写零失败。
4. 验收顺序必须是“最后一次真实 AO/DO 安全写入并取证 → 单次 Dispose → 不再有任何硬件写命令”。

## 10. V2.13.0.23 的落地优先级和验收门禁

### P0：预警即时恢复

1. 预警圈保持 `SuccessWithWarning` 和橙色；
2. 后续同 RunId、同 RunEpoch 的机械完整、持久化已提交 `Success` 圈完成后，用 Revision/Code CAS 清除旧 overlay；
3. 日志必须出现 `WARNING_OVERLAY_CLEARED`；
4. UI 在一轮刷新内恢复“运行”，Watchdog 下一心跳 `WarningActive=false`；
5. 旧圈、迟到回调、其他 warning code 不得清除新预警。

### P0：关闭链单一所有权

1. 人工停止成功后的 FormClosing 复用既有 safety receipt，不再执行第二次完整 StopAll；
2. AO、DO、DAQ 只由一个 owner 释放一次；
3. 不允许 Dispose 后再次调用 ResetAll/AllOff；
4. `error.log` 不再出现 AO 冷启动基线假失败；
5. 人工停止到可关闭仍应小于 10 秒。

### P0：Watchdog 首连异常必须完全受监督

1. 首次 pipe unavailable 后成功拉起 Sidecar 时，`error.log` 为 0；
2. 强制 GC 后 `TaskScheduler.UnobservedTaskException=0`；
3. 0/1/N 个并发 joiner 都只共享一个已受监督的连接结果；
4. Watchdog 仍必须完成 Attach、心跳、人工停止 receipt 和资源释放。

### P1：发布和诊断数据完整性

1. 正式包必须携带 manifest，标题不得出现 `PackageManifestMissing`；
2. manifest 包含 Git commit、BuildUtc、ReleaseConfig hash、EXE/依赖哈希；
3. 低峰值预警和过冲预警都写入结构化 WarningSnapshots；
4. `index.db` 增加 `outcome_kind/warning_flags`，避免 `completed` 掩盖 `SuccessWithWarning`。

### P1：12～24 小时长测门禁

建议继续使用 4 通道、15 秒周期，至少运行 12 小时，24 小时更稳妥：

- 所有启用通道正式圈数一致，不得出现残留 `running` 圈；
- `HardFault=0`、非注入条件下 `SoftwareRecovery=0`、Watchdog takeover=0；
- `Published=Persisted=TerminallyHandled`，所有 drop/discard 为 0；
- 正式运行期 UI `Dropped/FileDropped=0`，不出现秒级持续卡顿；
- 预热 2 小时后，Working Set 和 Handles 应进入平台；若后 10 小时仍保持单调上升，抓取 handle type、任务/定时器注册表和对象分配快照定位；
- 人工停止只生成一笔 shutdown transaction，不再出现压力重复取证、遥测 worker 模糊超时或 AO 二次复位 ERROR。

## 11. 方法、限制与置信度

### 方法

1. 按 PID、时间窗、RunId 和 Watchdog SessionId 隔离当前会话；
2. 用 `run.log` 解析 988 条自适应圈结果；
3. 用 SQLite `epb_cycles` 独立核对圈数、状态和机械完成标志；
4. 用 Watchdog session/manifest 验证 Attach、心跳、恢复次数和停止终态；
5. 用 STOP_PERSISTENCE、日志队列和遥测 manifest/SHA 交叉验证数据完整性；
6. 将两条 ERROR 的时间顺序与对应源码调用路径对照；
7. 对 warning.log、结构化 WarningSnapshots 和最终 Watchdog warning 投影做一致性对账。

### 限制

- 只有约一小时 V2.13.0.22 数据，不能证明超长运行稳定性；
- 没有提供 V2.13.0.23 的新封盘，因此不能评价 V2.13.0.23 现场结果；
- V2.13.0.22 缺少发布 manifest，无法把现场二进制严格绑定到某个 Git commit；代码根因依据日志中的精确堆栈、固定日志字符串和当前源码路径，置信度高，但发布追溯本身仍不闭环；
- UI 延迟指标能证明消息处理延迟，不能完全替代现场录像或操作员主观感受；
- 本报告使用精确事件表而未绘图，因为异常事件稀疏，时间、通道、结果和恢复证据用表格更易审计。

### 置信度

| 结论 | 置信度 |
|---|---|
| 988 圈全部机械完整、无漏圈 | 高 |
| 无硬故障、恢复、Watchdog 接管 | 高 |

## 12. 最终建议

V2.13.0.22 本次试验数据可以保留并继续用于寿命累计：没有证据表明 988 圈、最后数据边界或人工停止物理安全失效。

升级到 V2.13.0.23 的方向是合理的，但不能只看“程序还在跑”。下一份 V2.13.0.23 封盘至少要同时验证：

1. 预警后下一健康圈是否真实出现 `WARNING_OVERLAY_CLEARED`；
2. Watchdog 最终 `WarningActive` 是否回到 false；
3. `error.log` 是否消除首连未观察任务异常和 AO 二次复位假 ERROR；
4. 人工停止是否只执行一次安全事务；
5. 12～24 小时内 Working Set/Handles 是否平台化；
6. 正式发布包是否补齐 manifest 和受控构建身份。

只有上述门禁全部通过，才能把“本次核心运行稳定”提升为“版本可长期无人值守运行”。
