## 1. 当前结论

V2.13.0.20 不能认定为已解决，也不能进入生产使用。自动化测试通过只说明隔离测试中的类和规则满足断言，没有覆盖真实项目 `10358-029` 上“旧检查点/恢复任务 + 启动定位 + Watchdog + 双液压 + 三个活动卡钳”同时存在的启动事务。

已经确认：

1. V2.13.0.15 与 V2.13.0.20 发布目录内 8 个关键配置文件的 SHA-256 完全一致，问题不是 XML 阈值、通道映射、液压压力、电源参数或程序 `.config` 被改动；
2. 两者真正差异是控制代码与 Watchdog。以 V2.13.0.15 commit 为基线，当前控制/主程序/Watchdog 范围共有 38 个文件变化，约 `2728 insertions / 457 deletions`；
3. V2.13.0.15 的 DO 上电门禁主要检查“全局停止栅栏 + 通道 Enabled + 当前生命周期”；V2.13.0.20 在此基础上增加了 `RunEpoch + Generation + RevocationToken` 的通道执行代际许可，并把 Runner、Timer、液压、程控电源和恢复任务都绑定到该许可；
4. 正常、无并发干扰的批量启动顺序是成立的：DAQ/电源预检完成后颁发执行许可，再发布 `Starting`，随后进行液压资格和启动定位。首次电源预检直接调用电源控制器，不经过新增的执行代际许可，因此“电源预检发生在颁发许可之前”不是本次首因；
5. 真正的高风险回归发生在启动过程被另一条恢复/终态链打断时：只要旧恢复任务或 Watchdog 在首个动作前后改变 `State`、`RunEpoch` 或撤销 permit，V2.13.0.20 会立即拒绝后续 Runner/液压/DO 动作；当前预释放循环又会把这类已经终态化的异常当作软件瞬态继续重试，形成“终态—旧任务重试—资源仍活动—Watchdog 接管”的放大链。

因此，V2.13.0.20 相比 V2.13.0.15 的本质区别不是“保护不够”，而是增加了多套彼此耦合的保护和恢复所有权；这些门禁缺少一个覆盖真实启动事务的单一 owner，正常启动一旦被异步状态更新插入，就可能被自己的保护系统判定为非法执行。

### 2.2 首次程控电源预检顺序

批量开始的代码顺序确实是：

```text
DAQ ready
→ PowerSupply PrepareAndEnable（实时预检）
→ AuthorizeFreshRun
→ AuthorizeChannelExecution
→ Publish Starting
→ Hydraulic qualification / Startup positioning
```

但首次电源预检调用 `EnsurePowerSupplyReadyBeforeStartCoreAsync`，它直接调用 `_powerSupply.PrepareAndEnableAsync`，没有走 `EnsurePowerSupplyReadyForChannelsAsync` 的新 permit 校验。因此不存在“还没发 permit 就被首次电源预检拒绝”的确定性死锁。

### 2.3 单纯硬件故障

V2.13.0.15 使用相同现场硬件、相同项目和相同配置稳定运行。除非 V2.13.0.20 本次日志给出新鲜的保护回读、DAQ 独立探测或物理压力失败证据，否则不能把本次首启失败归因于卡钳、DAQ、液压或程控电源硬件。

## 3. V2.13.0.15 与 V2.13.0.20 的关键运行逻辑差异

| 环节 | V2.13.0.15 | V2.13.0.20 | 回归风险 |
|---|---|---|---|
| 通道上电许可 | 根据 Enabled、全局停止栅栏和当前生命周期判断 | 在旧判断上增加绑定 Runner 的 `RunEpoch/Generation/RevocationToken` | 异步状态或代次变化会立即使旧 Runner 全部失效 |
| Runner/Timer 创建 | 缓存获取/创建并重新激活 | 创建前后都要求当前执行 permit；Runner 永久绑定创建时 permit | 终态或新 Run 插入后，旧启动任务不能继续，但必须被正确取消和等待退出 |
| 液压进入 | 以液压 Generation/成员快照协调 | 额外捕获所有成员 permit，并链接每个撤权 token | 任一成员撤权可取消整组正在进行的液压进入 |
| 终态清场 | 主要停止 Runner/Timer、DO 和液压参与权 | 先撤 permit，再移除运行对象；撤一个通道时还会取消所属液压组恢复 owner | 单通道终态可能扩大为液压组级取消 |
| 学习/资格/正式恢复 | 依靠状态和原因文本判断 | 显式 `OwnerKind/OwnerId/OwnerGeneration/TargetPhase` | owner 发布、继承或注册稍有时序差异，就会被判定为孤儿恢复 |
| 双液压节拍 | 两个压力组各自建压、各自生成资格后的电机窗口 | 新增全局双液压槽，同时建压、共同生成电机锚点 | 任一组失败时健康组也跳过当前槽；参与成员/代次必须完全一致 |
| 软预警 | 可能改写运行状态或原因 | 新增 Warning Overlay，设计目标是不改生命周期 | 半迁移代码或旧状态残留会造成“界面是预警，生命周期却仍是 Recovering” |
| Watchdog | 协议和契约较简单 | 心跳 revision 2、逐通道 owner、终态资源严格契约、恢复失败熔断 | `StartBlocked + RunnerActive` 会被严格接管；主程序清场窗口若不原子会触发自恢复 |

## 4. 已有 V2.13.0.19 封盘证明的真实事故链

下面证据来自：

`D:\EPB_Data\10358-029_V2.13.0.19_0822_1113`

它不是本次 V2.13.0.20 的日志，不能直接替代本次首因；但它证明了新增恢复系统曾经怎样把一个启动阶段的软件状态问题放大成整批 Watchdog 接管：

1. `11:09:20.381`：EPB4 启动定位出现 `StartupReverseEndpointReached` 软预警，现场生命周期为 `Recovering`；
2. `11:09:22.113`：液压组 1 被执行 `AffectedGroupResetFailed`，错误是 `FormalRejoinRejected ... FormalCommitted=False`；也就是正式阶段尚未提交，却启动了正式组复位/重新加入；
3. `11:09:23.312`：健康检查报告 `OrphanRecoveryOwnerOrTaskMissing`，继续发起受影响组 Stop→Start 清场；
4. `11:09:25.805` 起：仍在执行的启动定位任务连续报告 `ChannelExecutionPermitMissing Channel=4 State=StartBlocked`；
5. `11:09:30.542`：同一终态许可错误被预释放循环重试 3 次后升级为 `SoftwareSelfHealingExhausted`；
6. `11:09:31.215`：独立 Watchdog 检测到 `ChannelTerminalResourcesActive: EPB=4, State=StartBlocked, Runner=True`，执行整批接管。

该链条的关键不是 EPB4 硬件异常，而是：

```text
启动阶段软事件/恢复状态
→ 被错误路由到正式组恢复
→ 通道先进入 StartBlocked
→ 原启动任务仍持有 Runner 并继续重试
→ Watchdog 看到“终态但资源仍活动”
→ 整批停止/重启
```

V2.13.0.20 的新增执行 fence 能阻止旧任务再次上电，但如果没有同时做到“撤权时取消整个启动 owner，并等待其任务退出后再发布终态”，它只会把旧任务从“错误上电”变成“连续抛 permit 异常”。这可以提高物理安全，却没有自动解决启动事务的正确性。

## 5. 当前静态审计发现的两个剩余高风险点

### 5.1 单通道撤权扩大为液压组恢复取消

`RevokeChannelExecutionPermit(channel, reason)` 在撤销本通道 fence 后，直接调用：

```text
_recoveryOwnership.CancelGroup(hydraulicGroup)
```

这没有验证被取消的 group owner 是否属于当前通道、当前 Run、当前启动阶段。启动时任一通道进入终态，可能取消同液压组健康兄弟通道正在持有的恢复/资格事务。对于现场通道 4、5 同属液压组 1，这一点尤其危险。

### 5.2 终态 permit 异常仍被当作可重试瞬态

`PreReleaseBatchWithPlanAsync` 对 `StartupPositioningAsync` 抛出的普通异常统一执行安全 OFF 后重试，最多三次。当前没有在 catch 入口首先区分：

- permit 已撤销；
- `RunEpoch` 已变化；
- 生命周期已经是 `StartBlocked/AlarmStopped/SystemFault/ManualStopped/Completed`；
- 真正可恢复的软件瞬态。

因此一旦别的 owner 已经把通道终态化，旧启动任务仍会继续进入重试循环。V2.13.0.19 的封盘已经出现过这一行为；V2.13.0.20 新 fence 会让这类重试更快失败，但不会自动退出整个启动事务。

以上两项足以解释“一个启动阶段异常迅速扩大为全组/整批失败”的机制；**尚不能在没有 V2.13.0.20 日志的情况下断言，二者中的哪一个是本次第一触发点。**

## 6. 为什么 V2.13.0.15 反而稳定

V2.13.0.15 并非没有安全门禁；它也会在 `StartBlocked` 等终态拒绝 DO 上电。它稳定的主要原因是启动链更简单：

1. 没有 Runner 绑定式的不可复用 Generation permit；
2. 没有逐通道结构化 recovery owner 与 orphan owner 定时升级的组合；
3. 没有双液压全局槽对两个压力组实施强耦合；
4. Watchdog 不会使用当前这么严格的“终态资源契约 + owner 协议”参与启动阶段决策；
5. 一个软预警或局部恢复状态更不容易同时触发通道终态、液压组取消和整批 Watchdog 接管。

也就是说，V2.13.0.15 的稳定来自更少的并发状态机和更小的故障传播范围。V2.13.0.20 的每个新增保护单独看都有安全目的，但组合后形成了当前尚未被真实启动集成测试覆盖的闭环竞争。

## 7. 建议的彻底解决方案（暂不实施）

### 7.1 先恢复 V2.13.0.15 的启动控制基线

生产继续使用 V2.13.0.15。下一候选版不要在当前 V2.13.0.20 上继续叠加异常分支，先把“点击开始→电源预检→液压资格→启动定位→学习→正式计时器”恢复为 V2.13.0.15 的单一主流程，只保留不改变控制行为的诊断落盘。

### 7.2 建立唯一的 Startup Transaction Owner

一次人工开始必须只有一个根 `StartupTransaction`，至少包含：

```text
RunId + RunEpoch + StartupGeneration + RootCancellationToken + TaskCompletion
```

所有预释放、学习、资格、恢复和 Watchdog 判断都引用它。发布 `StartBlocked/AlarmStopped/SystemFault` 前必须执行：

```text
撤销本 Startup owner
→ 取消根 token
→ 等待所有启动子任务退出
→ 确认 Runner/Timer/液压 lease/DO 均清零
→ 最后发布终态
```

禁止先发布终态，再等待旧任务自行发现 permit 失效。

### 7.3 预正式阶段禁止进入正式恢复路由

在 `FormalPhaseCommitted=false` 时：

- Timer 健康检查不得调用正式组复位；
- Watchdog 不得用“正式运行 orphan owner”逻辑接管合法的启动 owner；
- 软预警只记覆盖层和证据，不发布 `Recovering`；
- 启动阶段软件异常只交给 Startup owner；达到预算后由 Startup owner 一次性清场。

### 7.4 缩小撤权和恢复取消范围

撤销一个通道 permit 时，只取消：

- 该通道持有的任务；
- 明确登记为该通道/该 Run owner 的恢复租约；
- 必须物理联锁的电气组或液压组动作。

禁止无 owner 校验地调用整个液压组 `CancelGroup`。物理安全 OFF 可以是组级，软件恢复所有权取消必须有作用域和代次。

### 7.5 终态/旧代错误不得重试

启动定位 catch 必须先检查：

```text
token canceled OR permit stale OR RunEpoch changed OR state terminal
```

任一成立立即退出当前启动 owner，不计入“软件瞬态三次重试”。只有通信超时、DAQ 新鲜度短暂不足、可证明已完成安全 OFF 的可恢复异常才进入有界重试。

### 7.6 真实启动集成门禁

下一候选版至少增加以下整链测试，而不只是测试孤立类：

1. 使用现场活动通道 `[4,5,10]`、真实电气组/液压组映射执行完整启动；
2. 在 EPB4/5 启动反向释放注入 `StartupReverseEndpointReached`，确认仍进入学习且生命周期不变；
3. 在学习阶段注入 `RapidLoadRiseWithoutObservedEmpty`，确认不创建正式组恢复任务；
4. 在液压组 1 单通道失败时，EPB5 和液压组 2 的 EPB10 不被软件 owner 级联取消；
5. 在撤权与启动定位并发时，根启动任务一次退出、无 permit 重试风暴、无 `StartBlocked + Runner=True` 窗口；
6. Watchdog 只在主进程失活、启动 owner 超过硬期限且清场失败时接管；
7. 相同项目连续执行“失败→清场→重新开始”，第二次不继承上一代 Runner、permit、液压成员或恢复 owner。
