# 10358-029a V2.13.0.32 启动误接管与主程序、看门狗共同退出根因分析

> 分析日期：2026-08-29  
> 现场数据：`D:\EPB_Data\10358-029a_V2.13.0.32_0828_1911`  
> 故障会话：`983c2c54b4ed4af1bd726709ddbbb6bb`  
> 稳定对照会话：`3dba90f8b1e2462e80a00fcf2ff60bfb`（V2.13.0.30）  
> 文档性质：封盘日志、Watchdog Journal、两份进程转储和当前源码的只读复盘；本轮未修改业务代码。

## 1. 结论

本次不是单一硬件故障，也不是主程序持续卡死。V2.13.0.32 暴露了三条相互放大的软件链路：

1. **启动定位的瞬态延迟被升级成组级断能，后续重试又被自己的断能状态拒绝。** 19:03:59 附近同时出现 DAQ 回调陈旧、Watchdog ACK 超时和电源遥测接近 1 s。启动定位的高优先级 OFF 未在同步等待窗内确认后，程序对电源组 2、4 连续发起失效安全联锁；DO 遥测随后实际均记录为成功，但两组电源已被关闭。下一轮定位仍继续执行，于是得到 `PowerSupplyEnergizationPermitMissing ... ExpectedOutputDisabled`，EPB4 最终三次软件瞬态失败。该链属于启动事务、断能事务和重试许可衔接错误，现有证据不支持把它定性为卡钳或程控电源硬故障。
2. **Watchdog 把命名管道传输失活当成主程序失活。** V2.13.0.32 在 7 分 48 秒内出现 12 次 `HeartbeatSuspect`、5 次 `SendFailed`、5 次 `PipeLoopError` 和 3 次 `TakeoverRequested`。主、辅双方的心跳/ACK 同时丢失，Sidecar 的 Ping 写入超过 500 ms，随后出现“流正在由其上的前一操作使用”。两份转储中 WinForms 主线程都存活并停在正常消息循环 `WaitMessage -> RunMessageLoop -> Application.Run`，不是持续死锁。Watchdog 仍分别终止 PID 8420、16016，属于**传输故障触发的误接管**。
3. **第三次恢复失败后的退出意图发错，导致主程序和 Watchdog 一起正常退出。** PID 3056 报告 `RecoveryAttemptFailed` 后，Sidecar 已登记 `RelaunchApproved`，日志也写明“保持本轮授权，等待 Watchdog 退避重试”。但主窗体把 `RecoveryStartupFailed` 走成普通 `ApplicationExit`，发送 `ShutdownExpected:RuntimeShutdown`。Watchdog 收到后立即撤销第 3 次接管、发布 `ExpectedApplicationExit`，并在主进程退出后结束自身。因此最终“双进程都不见了”是协议路径主动收口，不是两个进程同时崩溃。

综合判断：

- **主根因 A（已确认，P0）：** Watchdog 的“传输存活”和“应用存活”没有分层，单一管道短时失活可直接升级为强杀进程。
- **主根因 B（已确认，P0）：** `RecoveryAttemptFailed -> RelaunchApproved` 后又发送 `ShutdownExpected`，把负责下一次拉起的 Sidecar 一并终止。
- **伴随根因 C（高置信，P0/P1）：** 启动定位 OFF 超时、组级断能和定位重试不是一个原子事务，出现“先断电、再以电源未使能为由拒绝重试”的自锁。
- **发布缺陷（已确认，P1）：** 现场包为 `PackageManifestMissing`，不能证明其与当前 V2.13.0.32 标签源码逐文件一致；这不是本次直接触发条件，但已经妨碍精确版本追溯。

当前 V2.13.0.32 不具备无人值守放行条件。短期应整体回退到现场已证明稳定的 V2.13.0.30；修复版必须同时关闭上述三条链，不能只放宽心跳时间或只增加重启次数。

## 5. 根因分析

### 5.1 根因 A：启动 OFF 确认超时与组级断能、定位重试互相打架

启动时先后有以下直接证据：

1. 电源组 2、4 都已成功连接、输出 ON，并达到约 12 V 稳定状态；
2. 19:03:59.897 出现 565.3 ms DAQ 回调陈旧；随后电源遥测虽然成功，但耗时约 950～979 ms；
3. EPB4/5/12 的高优先级 OFF 没有在同步等待窗内确认，程序立即发起组级失效安全联锁；
4. 同期 `FIELD DO_OFF` 记录中的实际 NI 写结果为 `Result=True`，说明“调用方未及时得到确认”和“物理 OFF 最终失败”被混为了一类；
5. 电源组被关闭后，定位重试没有等待电源恢复事务重新建立 `ExpectedOutputEnabled`，直接因 `ExpectedOutputDisabled` 再次失败；
6. 同一组在约 300 ms 内收到多次重复联锁，组 2 的 `RequestCount` 一度达到 7，进一步增加并发清场和状态翻转。

当前 `SetEpbOffHighPriority` 的语义是：专用 worker 超过等待窗就向调用方返回失败，但已排队的 OFF 仍可能稍后完成。上层却把这个 `false` 直接升级成组级断能。安全优先本身正确，缺陷在于后续重试没有消费“晚完成成功”，也没有等待组级 OFF 事务结束并重新获取电源许可，最终形成：

```text
短时调度/采集延迟
  -> OFF 未在等待窗内确认
  -> 关闭整个电源组
  -> 启动定位继续重试
  -> ExpectedOutputDisabled
  -> 再次自愈/断能
  -> 三次失败、通道隔离
```

这条链应归类为软件启动事务失败。日志没有 `ProtectionTripped`、持续通信断开、输出电压建立失败或卡钳独立过流证据，不能把 EPB4 或电源组 2 判为硬件根因。

### 5.2 根因 B：Watchdog 将管道传输故障等同于应用卡死

故障会话里双方记录互相印证：

- 主程序侧：`WatchdogHeartbeatAckTimeout; AckAgeMs≈3000; AuthorityAlive=True`；
- Sidecar 侧：`HeartbeatAgeSeconds≈3`，随后 Ping 写入超过 500 ms；
- 管道循环：`流正在由其上的前一操作使用`、管道中断、重连；
- 每次达到接管阈值后，Sidecar 等待、抓 dump，再终止主程序。

两份 dump 使用与现场一致的 .NET Framework 4.8.4400 x86 DAC 检查，结果如下：

| Dump | 托管线程数 | WinForms 主线程 |
| --- | ---: | --- |
| PID 8420，19:06:13 抓取 | 51 | `WaitMessage -> RunMessageLoopInner -> RunMessageLoop -> Application.Run` |
| PID 16016，19:08:47 抓取 | 53 | `WaitMessage -> RunMessageLoopInner -> RunMessageLoop -> Application.Run` |

这证明接管完成前主程序不是持续 UI 死锁，至少在强杀前仍能正常泵送消息。dump 抓取发生在首次心跳超时后约 15 s，因此不能排除超时瞬间存在短暂停顿；但可以否定“主程序持续无响应直至被杀”这一解释。

当前 Watchdog Host 的发送链仍采用同步入口：启动 `WriteLineAsync`，500 ms 未完成就断开管道；断开与读循环、旧写任务、重连代次没有形成可证明的单所有者收口。现场紧接着出现“前一操作仍在使用流”，与旧连接 I/O 未完全退休、重连又开始的状态一致。该实现是管道错误风暴的高置信代码原因；由于现场包缺少 manifest，精确到某一现场二进制指令的归因仍需用受控构建复现确认。

更关键的设计问题是：即使管道为何失活尚未完全确定，也不应仅凭同一条管道的心跳失败推断整个应用已经卡死。当前系统没有独立的第二健康信号，也没有在抓 dump 后重新判断 UI/工作线程是否恢复，因而把可恢复的传输故障升级成了进程强杀。

### 5.3 根因 C：恢复失败后的退出协议自相矛盾

现场最终顺序是：

```mermaid
flowchart LR
    A[PID 3056 恢复批量启动失败] --> B[RecoveryAttemptFailed]
    B --> C[Sidecar: RelaunchApproved]
    C --> D[主程序请求 RecoveryStartupFailed 退出]
    D --> E[实际发送 ShutdownExpected / ApplicationExit]
    E --> F[Sidecar 撤销 Takeover]
    F --> G[主程序退出]
    G --> H[Sidecar 发布 ExpectedApplicationExit 并退出]
```

当前源码的关键路径为：

- `MTTfTest/Main_Frm.UnattendedRecovery.cs:315-322`：先调用 `PrepareForWatchdogRetryExit()`，通知 `RecoveryAttemptFailed`，再调用 `RequestWatchdogOwnedExit("RecoveryStartupFailed")`；
- `MTTfTest/FrmEpbMainMonitor.UnattendedRecovery.cs:92-96`：`PrepareForWatchdogRetryExit()` 设置的是监控窗体自身的 `_watchdogTakeoverExit`；
- `MTTfTest/Main_Frm.WatchdogUi.cs:171-185`：主窗体只有 reason 以 `WatchdogStopAllCompleted:` 开头时，才设置主窗体的 `_watchdogTakeoverExitRequested`；`RecoveryStartupFailed` 不满足；
- `MTTfTest/Main_Frm.WatchdogUi.cs:348-357`：未设置该标志就走 `RuntimeShutdownIntent.ApplicationExit`；
- `MTTFTest.Watchdog/WatchdogHost.cs:1348-1356`：`ShutdownExpected` 会标记 `ManualStopRequested`、取消自动接管、发布 `ExpectedApplicationExit`，并在主进程退出后结束 Host。

因此两个不同窗体/对象上的“保留重启授权”标志没有传递到最终退出意图。日志“等待 Watchdog 退避重试”与实际发出的 `ShutdownExpected` 正好相反，这是最终双进程退出的直接代码原因。

### 5.4 第三次恢复为何变成“全部通道学习阶段被隔离”

PID 3056 在 19:09:21 通过全断能安全预检，继续恢复 4、5、11、12。19:11:37.555 Sidecar 又因管道心跳触发 `TakeoverRequested`，主程序随即执行 StopAll；19:11:37.851 批量启动逻辑发现全部参与通道都已在学习阶段被隔离，于是抛出异常。

这不是一个独立的四通道同时硬故障，更像“恢复批量启动”和“Watchdog 接管 StopAll”并发后的预期保护结果。应由恢复协调器识别 `supersededByTakeover` 并完成同一授权下的进程交接，而不是再登记为普通启动失败后走应用退出。

### 5.5 `PackageManifestMissing` 不是直接触发条件，但必须阻断发布

现场三个 PID 使用同一 EXE/配置哈希，故本次会话内部没有发现进程间换包；窗口标题的 `PackageManifestMissing` 也没有直接触发启动定位或 Watchdog 接管。

但它造成以下问题：

- 无法确认主程序、Watchdog、Protocol、Client DLL 是否来自同一次构建；
- 无法把现场 `ae0b0e...` 精确映射到 Git commit；
- 当前实施文档已明确写明本地 Dirty 构建不得作为正式包，现场却仍使用了另一个无 manifest 的 V2.13.0.32；
- 协议类问题尤其依赖主、辅程序集成套，混装风险不能排除。

所以它不是事故第一张多米诺骨牌，但必须作为下一版生产发布的硬阻断项。

## 6. 解决方案

### 6.1 立即处置

1. **停止 V2.13.0.32 无人值守运行。** 不建议通过增加最大重启次数继续试跑；当前配置已允许 8 次，增加次数只会延长误杀和重启风暴。
2. **整体回退 V2.13.0.30。** 使用现场已经稳定运行的完整目录及配套配置，不得只替换 `MTTFTest.exe`，不得混入 V2.13.0.32 的 Watchdog/Protocol/Client DLL。
3. 因 V2.13.0.30 同样缺少正式 manifest，回退前先封存原目录并记录主程序、Sidecar、所有 Watchdog DLL、配置 XML 的 SHA-256，形成临时不可变基线。
4. V2.13.0.32 仅允许有人值守诊断；不得靠关闭 Watchdog、屏蔽 StopAll 或无依据放大硬件安全期限来换取“看似稳定”。
5. 保留本次两份 dump 和完整 `WatchdogSessions`，后续受控候选必须用同一故障注入矩阵作 A/B 对照。

### 6.2 P0：修复 Watchdog 健康判定和管道所有权

#### 6.2.1 分离三类状态

Watchdog 状态至少拆分为：

- `TransportDegraded`：管道写超时、ACK 超时、连接代次切换；
- `ApplicationHealthUnknown/Unresponsive`：独立应用探针也失败；
- `SafetyTakeoverRequired`：输出状态或应用健康达到必须接管的条件。

`TransportDegraded` 只能触发重连和安全降级，不能单独强杀主程序。进程替换至少需要独立于当前命名管道的第二健康信号，例如专用健康通道、UI 消息探针或进程内独立应答端点；进程存在只能作为辅助信号，不能单独证明健康。

#### 6.2.2 Host 发送链改为单写者

- Sidecar 所有出站消息进入有界的专用 writer worker，不再由任意线程直接执行 `WriteLineAsync + Task.WhenAny(500ms)`；
- 每个连接代次只有一个 reader 和一个 writer；
- 写超时时原子摘除当前连接，取消该代所有 I/O，并等待旧 reader/writer 明确退休后再发布新代可用；
- 所有消息携带连接代次，旧代完成、异常和 ACK 不得污染新代；
- 记录“入队延迟、实际写耗时、取消原因、旧代退休耗时”，区分 writer 堵塞、管道断开和调度暂停。

#### 6.2.3 接管前必须重判

- 进入 `TakeoverRequested` 后，抓 dump、StopAll 和终止进程之前都重新读取独立健康信号；
- 同一 authority 的新鲜心跳或独立探针恢复时，取消尚未执行的强杀；
- 启动、学习、DAQ/电源自维护等已知重负载阶段采用独立 grace，阈值由故障注入测量确定；
- 即使应用健康不明，也可先执行有界安全断能，但“断能”和“终止进程”必须是两个决策。

### 6.3 P0：修复恢复失败退出语义

建议新增强类型退出意图 `RecoveryRelaunchExit`，不要再用 reason 字符串前缀推断退出所有权。

必须满足以下不变量：

1. `RecoveryAttemptFailed` 已返回 `RelaunchApproved` 后，旧主进程只能发送 `RecoveryRelaunchExit`/`WatchdogTakeoverExit`，不能发送 `ShutdownExpected`；
2. Sidecar 收到该意图后保持运行，等待旧 PID 退出，再消费已批准 permit 并按退避启动下一 PID；
3. `ShutdownExpected` 只允许用户关闭、明确停止并关闭应用或恢复授权被显式撤销的路径发送；
4. 当 relaunch state 为 `Approved` 且没有 manual stop 时，Host 即使收到普通 `ShutdownExpected` 也应拒绝覆盖恢复授权，记录协议冲突并保持 Sidecar；
5. `PrepareForWatchdogRetryExit()` 的状态必须设置在最终决定 `RuntimeShutdownIntent` 的 Main_Frm 所有者上，不能只设置子监控窗体字段。

### 6.4 P0/P1：修复启动定位自锁

#### 6.4.1 使用可区分的 OFF 结果

高优先级 OFF 不再只返回 `bool`，至少区分：

- `CompletedOff`；
- `AcceptedPending`；
- `TimedOutButStillQueued`；
- `Rejected`；
- `HardwareWriteFailed`。

`TimedOutButStillQueued` 应等待同一 command id 的晚完成结果或进入明确的组级安全事务，不能马上与永久硬件失败等价。

#### 6.4.2 将组级断能和重试做成单事务

启动定位重试顺序固定为：

1. 冻结本电气组的新上电命令；
2. 等待所有相关 OFF command 到达终态；
3. 需要时关闭并回读电源组；
4. 退休旧恢复 owner、旧 runner 和旧 execution permit；
5. 重新执行 `PrepareAndEnableAsync`，确认 `ExpectedOutputEnabled/Active/TelemetryOutputEnabled`；
6. 生成新 execution permit 和 runner；
7. 仅启动该代定位尝试。

任何一步失败都保持安全 OFF，但不得在 `ExpectedOutputDisabled` 状态下直接计一次新的机械定位失败。

#### 6.4.3 合并重复联锁

- 同一组、同一 run epoch、同一根因只允许一个恢复 owner；
- 后续请求加入现有任务，只更新受影响通道，不重复撤销许可和重复启动恢复 worker；
- 组事务完成前，兄弟通道的定位重试挂起，不得一边关闭组电源、一边继续发正反转命令；
- `DaqSampleStale`、OFF 确认超时、电源通信降级和硬件保护分别计数，禁止互相冒充。

### 6.5 P1：恢复发布门禁

下一候选必须由干净提交和独立空目录生成，至少满足：

- `PackageVerified=True`；
- Git commit、dirty 状态、BuildUtc、版本号可查；
- 主程序、Sidecar、Protocol、Client 及配置逐文件 SHA-256 全部进入 manifest；
- 启动时主程序和 Sidecar 双向校验协议版本及关键程序集哈希；
- `Verify-Release.ps1 -RequireDeploymentApproved` 通过，否则禁止进入耐久试验。

## 7. 回归与现场验收矩阵

### 7.1 自动化故障注入

| 场景 | 期望结果 |
| --- | --- |
| Host/Client 单向写阻塞 0.5 s、3 s、6 s | 进入 `TransportDegraded` 并重连；独立健康探针正常时不得杀主进程 |
| 旧连接 write 未完成时触发重连 | 新代只有一个 reader/writer；不得出现“流正在由前一操作使用” |
| UI 线程真实阻塞且输出可能带电 | 先完成安全断能，再按策略抓 dump、终止并重启 |
| 心跳恢复发生在 dump 前、dump 后、kill 前 | 每个边界都能取消尚未执行的误接管 |
| `RecoveryAttemptFailed + RelaunchApproved` | 旧 PID 退出后 Sidecar 保持，按退避启动下一 PID |
| 用户关闭程序 | 主、辅进程按 `ShutdownExpected` 正常共同退出，不再自动拉起 |
| OFF 调用等待超时、100～1000 ms 后晚成功 | 不重复组级联锁，不计为硬件故障，恢复后只产生一次新定位尝试 |
| 电源组关闭期间定位重试到期 | 重试挂起，待新许可建立后开始，不得报 `ExpectedOutputDisabled` 三连败 |
| 4、5 共组和 11、12 共组并发瞬态 | 每组一个 owner，不牵连另一组，不出现全部通道被隔离 |

### 7.2 同机 A/B 验证

在同一主机、同一 NI/程控电源/液压硬件、同一 4/5/11/12 配置下执行：

1. V2.13.0.30 基线冷启动 20 次，记录启动耗时、管道事件、DAQ 最大 callback age；
2. 修复候选冷启动至少 100 次；
3. 运行中人工注入管道延迟/断开至少 100 次；
4. 真实卡死注入至少 20 次，验证该接管时仍能接管；
5. 恢复启动连续失败覆盖第 1～8 次预算，验证 Sidecar 始终留存到终态；
6. 完成 2 h、8 h、24 h、72 h 阶梯长稳；
7. 最终再执行每通道 100000 个有效正式圈目标。

### 7.3 放行标准

以下条件必须同时满足：

- 100 次冷启动中 `HeartbeatUnresponsive` 误接管为 0；
- 所有管道延迟/断线注入中 `PipeLoopError` 为 0，旧连接均有明确退休记录；
- 独立健康正常时，因单一 transport timeout 终止主进程次数为 0；
- 真实应用卡死时，安全断能和自动恢复成功率 100%，且有 dump、代次和授权闭环；
- `RelaunchApproved` 后非人工路径的 `ExpectedApplicationExit` 为 0；
- 启动重试中 `ExpectedOutputDisabled` 不再作为机械定位尝试失败计数；
- 无“全部选中通道均在学习阶段被隔离”与 Watchdog StopAll 竞态；
- 正式包 `PackageVerified=True`，所有逐文件哈希通过；
- 72 h 运行无非预期主程序/Sidecar 退出，数据连续性和圈数一致。

## 8. 建议实施顺序

1. 先修复 `RecoveryStartupFailed` 的退出意图和 Host 侧协议不变量，阻止双进程共同退出；
2. 再完成 Host 单写者、连接代次原子退休和独立应用健康探针，阻止误接管；
3. 修复启动定位 OFF 晚完成、组恢复和 execution permit 的原子衔接；
4. 补齐上述定向自动化并运行现有控制、Watchdog、持久化三套回归；
5. 生成受控候选，在同机完成 100 次冷启动和故障注入；
6. 通过阶梯长稳后再替换 V2.13.0.30。

## 9. 最终判断

V2.13.0.32 的“一闪而过、多次自动恢复、最终主程序和 Watchdog 都退出”已经形成完整证据链：

```text
启动阶段瞬态延迟
  -> OFF 确认超时与组级断能/重试自锁
  -> Watchdog 管道反复失活
  -> 把传输故障误判为应用持续卡死
  -> 两次终止仍存活的主程序
  -> 第三次接管与学习启动并发，全部通道被隔离
  -> RecoveryAttemptFailed 已批准继续拉起
  -> 错发 ShutdownExpected
  -> 主程序与 Sidecar 共同正常退出
```

所以解决方向不是“换卡钳”“提高重启上限”或“把 3 s 改成更大的单一数字”，而是修正传输与应用健康分层、恢复退出协议、启动安全事务三处系统性缺口。在三处同时闭环并完成受控发布与长稳验证前，V2.13.0.32 不应继续作为无人值守生产版本。
