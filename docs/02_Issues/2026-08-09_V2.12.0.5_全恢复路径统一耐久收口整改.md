# V2.12.0.5 全恢复路径统一耐久收口整改

> **后续状态：** 本文保留 V2.12.0.5 的阶段性整改证据。后续反证审计发现 Timer、受影响组硬期限清场、活动圈上限和正式/报警/学习圈终态仍存在少量旁路，已在 V2.12.0.6 全部接入耐久协议；现场验证版本应使用 V2.12.0.6。详见 [V2.12.0.6 全圈终态耐久一致性完成性整改](./2026-08-09_V2.12.0.6_全圈终态耐久一致性完成性整改.md)。

> 状态：代码整改与自动回归已完成；当前构建是脏工作树验证候选，不得直接生产部署。  
> 适用问题：频繁进入自维护、自维护后无法重新进入试验、恢复过程中出现未封存圈或原始数据归属不确定。  
> 最终目标：除卡钳具有完整、连续、独立的硬件故障证据或目标次数完成外，系统必须安全自愈并持续测试。

## 1. 结论

V2.12.0.2 频繁自维护不是卡钳普遍损坏，而是公共 DAQ 时间异常触发软件恢复后，机械释放、圈封存、错峰计划和恢复所有权没有形成闭环。V2.12.0.3 修复了这条主故障链；V2.12.0.4 又修复了写盘超时仍释放批次、虚假推进耐久边界，以及队列满错误风暴。

继续做完成性审计时发现，V2.12.0.4 仍有一个跨恢复类型的不一致：整台 DAQ 恢复已经执行“停止采集并等数据耐久化后才废止当前圈”，但液压、电源、非 DAQ 电气和普通可恢复软件预警仍可能直接调用圈废止。此时后台 Raw 批次可能稍后才到达；圈事务已经结束，迟到数据便可能失去明确归属，下一次恢复还可能遇到状态竞争。

V2.12.0.5 从根上统一为：

`暂停动作/断能 → 锁定本次圈号和截止时间 → 排空 Raw 发布边界 → 等待受影响设备的耐久前缀 → 废止失败圈 → 清理恢复状态 → 资格验证 → 自动重入`

任何一步未满足，都保持 `Recovering` 并受控重试；不得提前宣告恢复成功，不得让该通道重入正式试验，也不得把软件/基础设施故障升级为卡钳永久停用。

## 2. 为什么此前会频繁进入自维护

现场故障由多层问题叠加，而不是单一阈值过严：

1. 两块 DAQ 时间同时落后主机约 1.16 s，旧代码只判断正残差，过期数据没有被及时隔离。
2. 峰值完整性失败后旧控制路径提前返回，没有完成反转机械释放，下一圈从夹紧状态开始并触发时序异常。
3. 资格圈和学习圈异常退出时没有可靠终态，后续恢复被“上一圈尚未封存”永久阻塞。
4. 单通道恢复复用了不包含该通道的全局错峰计划，失败路径又残留 `Recovering` 状态和恢复所有权。
5. 写盘队列满在约 20 秒内重复产生 1491 条 ERROR，日志、UI 和重复恢复任务反过来继续消耗 CPU/I/O，形成故障风暴。
6. 写盘长故障曾把“超时”错误当成“已处理”，使停止门禁和圈封存建立在虚假耐久边界上。
7. 不同恢复入口对“何时允许结束当前圈”规则不一致，迟到 Raw 批次仍可能与圈终态竞争。

所以，调高自维护次数、延长超时、增大队列或自动重复点击启动只能推迟故障，不能消除闭环。

## 3. V2.12.0.5 的统一事务协议

### 3.1 两种耐久边界

- **整台设备边界**：DAQ 自身重建时，该设备先停止产生新批次，要求 Raw 发布完成、持久化序号到达目标且队列为零，随后才允许封失败圈。
- **通道/组耐久前缀**：液压、电源、电气或普通软件恢复只影响同一 DAQ 上的部分通道；健康兄弟通道仍会产生更晚批次，因此不能等待整台队列为零。新 `WaitForDurablePrefixAsync` 只要求目标序号及以前的批次全部真实处理，允许更晚健康流量继续存在。

前缀门禁同时拒绝以下伪完成状态：采集被抑制、设备代次变化、写入超时/未解决故障、队列满锁存、目标序号尚未写入、目标及以前批次仍在写入或仍位于队头。

### 3.2 恢复入口全部统一

以下路径现均使用同一耐久收口协议：

- 普通可恢复软件预警；
- 液压自维护；
- 电源自维护；
- 非 DAQ 电气组紧急恢复；
- DAQ 派生电气故障（由整台 DAQ 截止协议收口）；
- DAQ 时钟、回调和持久化故障。

代码不再允许这些入口直接、立即废止当前圈。只有确认 Raw 已发布且对应耐久前缀已经完成后，才执行 `DiscardCurrentCycleForSoftwareRecovery`。如果磁盘持续失败，通道保持安全断能和恢复态，写盘批次继续有界退避重试；恢复前不得重新计数。

### 3.3 圈数据窗口只允许收紧

同一故障可能先后被电气、液压或电源恢复观察到。`SealCycleWindow` 现在只取最早截止时间；后来的恢复请求不能延长已关闭的数据窗口。这样能够防止恢复并发时把故障后的迟到数据重新纳入已封闭圈。

## 4. 关键代码落点

- `Controller/DaqPersistenceCoordinator.cs`
  - 记录 `InFlightSequence`；
  - 新增 `WaitForDurablePrefixAsync`；
  - 队列满按一次拥塞只发布一次 Failed，并累计 `OverCapacityDroppedBatchCount`。
- `Controller/EpbManager.cs`
  - 新增恢复圈捕获、截止窗口封闭和耐久后终态化三个统一步骤；
  - 液压、电源、普通软件预警和电气紧急路径全部接入；
  - 耐久失败时不重入，保留安全状态继续重试。
- `DataOperation/EpbDiskWriter.cs`
  - `SealCycleWindow` 改为单调收紧，防止并发恢复重新打开数据窗口。
- `Controller/EpbManager.FieldMetrics.cs`、`Tools/validate_epb_field_gate.py`
  - 现场持续输出并强制检查 `OverCapacityDropped=0`、持久化边界、停止边界及性能红线。

## 7. 上线验证与放行标准

先完成 2 小时受控故障注入，再依次完成 24 小时和 72 小时真实台架长跑。正式 24 小时门禁：

```powershell
python Tools/validate_epb_field_gate.py "<24小时封存目录>" `
  --expected-version V2.12.0.5 `
  --minimum-hours 24 `
  --performance-gates required `
  --artifact-scan full `
  --log-scan full `
  --database-scan full
```

72 小时验收将 `--minimum-hours` 改为 `72`。以下任一项发生即不放行：

- `OverCapacityDropped` 非零、持久化序号倒退或不连续、停止 Raw/耐久边界未闭合；
- 存在 `running`/孤儿圈、上一圈尚未封存、恢复所有权残留、启动回滚循环；
- 软件/DAQ/磁盘故障后必须人工重启才能恢复；
- 硬报警缺少报警圈及最近 10 圈 CSV/BIN/清单；
- 任何卡钳在没有完整硬件故障证据时被永久停用；
- 系统 CPU P95、DAQ 回调、DO OFF、持久化或 UI 响应超过报告规定红线。

## 8. 最终边界

代码层面已经切断“异常触发自维护后，数据与圈状态竞争，最终不能重入”的剩余路径；软件恢复不再依赖放宽报警阈值，而是依赖可证明的安全、数据和状态事务。

但“彻底解决”必须分成两层判断：V2.12.0.5 已完成根因代码整改和自动回归；是否能够无人值守上线，仍须由干净正式发布身份以及 2 h/24 h/72 h 真实硬件数据证明。在这些证据齐全前，结论只能是“代码候选完成，现场放行未完成”。
