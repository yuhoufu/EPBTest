> 日期：2026-08-19
> 适用项目：10358-029
> 问题版本：V2.13.0.12
> 修复版本：V2.13.0.13
> 现场数据：`\\wj-epb\EPB_Data\10358-029_V2.13.0.12_0819_1602`
> 根因分析文档：[2026-08-19_10358-029_V2.13.0.12_启动即ChannelExpectedRuntimeMissing误接管与循环恢复根因及解决方案.md](./2026-08-19_10358-029_V2.13.0.12_启动即ChannelExpectedRuntimeMissing误接管与循环恢复根因及解决方案.md)

## 1. 结论

V2.13.0.12 的现场故障不是卡钳、DAQ、程控电源、项目配置或重复 EPB ID 导致，而是新加入的 Watchdog 通道资源不变量把合法的学习阶段错误解释成资源缺失：

```text
Learning 的合法资源形态：Timer=False, Runner=True
V2.13.0.12 的错误规则：Learning 要求 Timer=True 且 Runner=True
结果：持续 5 秒后触发 ChannelExpectedRuntimeMissing
```

该错误随后引起整批 `RequestStopAll`。恢复进程再次进入 Learning 后又命中同一错误规则，因此表现为软件关闭、重新启动后不断出现自动恢复窗口。

V2.13.0.13 已完成以下闭环整改：

1. 建立唯一、显式、按生命周期阶段区分的运行资源契约；
2. 将机械进展、Timer 必需性、Runner 必需性完全拆开；
3. Learning 和 Qualification 只要求 Runner，不再错误要求正式计数 Timer；
4. 仍然保留 Learning/Qualification 的机械完成进展监督，未留下监督盲区；
5. 不变量去抖绑定 `RunId + RunEpoch + Channel + InvariantCode + State + 期望/实际资源`；
6. `StateRevision`、DO 序号或峰值水位刷新不能掩盖真实故障；
7. Watchdog 自己发起 StopAll 所导致的取消不再登记为新的恢复启动失败，也不消耗重启预算；
8. `SafeButRestartRequired` 后，开始按钮由中央 UI 状态函数永久闭锁，迟到事件不能重新打开；
9. 主程序与 Watchdog 版本均迭代为 `2.13.0.13`；
10. 已完成专项回归、主程序构建和 DAQ 回归复验。

## 2. 现场故障链与代码根因

### 2.1 首次启动为什么约 5 秒就停机

现场心跳中，EPB4、EPB5、EPB9、EPB10、EPB11 均处于：

```text
State=Learning
Timer=False
Runner=True
```

这是合法状态。学习阶段运行机械动作、采集电流并生成自适应模型，但正式计数调度 Timer 尚未建立。

V2.13.0.12 的旧判定把 `Learning` 加入 `stateAllowsCycles` 后，又统一执行：

```csharp
stateAllowsCycles && (!TimerActive || !RunnerActive)
```

因此 `Timer=False` 被错误认定为运行资源缺失。5 秒去抖到期后，Watchdog 生成：

```text
ChannelExpectedRuntimeMissing:EPB=4;
AgeSeconds=5.0;
Timer=False;
Runner=True;
State=Learning
```

随后 sidecar 发出 `RequestStopAll`，造成所有参与通道安全停机。

### 2.2 为什么停止后同一进程不能再开始

Watchdog 接管触发的是系统故障 StopAll，不是普通人工暂停。StopAll 完成后控制器将旧进程锁存为：

```text
SafeButRestartRequired
```

该状态的安全语义是：物理输出已安全收口，但旧进程的运行授权已经撤销，不能在同一 PID 内重新开始。

因此“停止后再次点击开始仍报错”是接管后的二次表现。真正的首发故障仍是 Learning 资源契约误判。

### 2.3 为什么关闭软件后持续弹自动恢复窗口

检查点仍为 Armed，sidecar 按设计启动恢复进程。恢复进程通过检查点校验和安全预检后，再次进入 Learning：

```text
Learning -> Timer=False, Runner=True
```

V2.13.0.12 sidecar 又在约 5 秒后触发同一个 `ChannelExpectedRuntimeMissing`，形成：

```text
恢复启动
  -> Learning
  -> 5 秒资源误判
  -> RequestStopAll
  -> 结束恢复进程
  -> 退避重启
  -> 再次 Learning
```

这不是多个独立故障，而是同一错误规则在恢复进程中反复命中。

### 2.4 为什么日志中还出现 UnhandledSoftwareStartup

Watchdog 发出 `RequestStopAll` 后，主程序中的恢复等待任务会收到 `OperationCanceledException`。V2.13.0.12 没有携带取消 owner 和原 StopAll 关联号，因而把自己引起的取消再次分类为：

```text
UnhandledSoftwareStartup
```

这会污染恢复失败统计，并可能推动额外的进程重启或熔断。它是循环恢复的放大因素，不是最初的触发原因。

## 3. V2.13.0.13 的阶段化资源契约

V2.13.0.13 引入 `WatchdogRuntimeContractPolicy`，以通道生命周期阶段作为唯一资源语义来源。

| 通道阶段 | 机械进展预期 | Timer 必需 | Runner 必需 | 其它不变量 |
|---|---:|---:|---:|---|
| Starting | 否 | 否 | 否 | 由批次启动硬截止监督，不臆造资源要求 |
| Learning | 是 | 否 | 是 | 合法形态为 `Timer=False, Runner=True` |
| Qualification | 是 | 否 | 是 | 合法形态为 `Timer=False, Runner=True` |
| Running | 是 | 是 | 是 | 任一资源缺失持续 5 秒触发接管 |
| WarningRunning | 是 | 是 | 是 | 与 Running 相同 |
| Recovering | 否 | 否 | 否 | 必须有 recovery owner；Timer/Runner 只检查单边残留，超时 30 秒 |
| ResumeChecking | 否 | 否 | 否 | 必须有 recovery owner；服从恢复阶段硬截止 |
| PausePending | 否 | 否 | 否 | 必须有人工暂停 owner |
| Paused | 否 | 否 | 否 | 必须有人工暂停 owner；否则 5 秒后按孤儿暂停接管 |
| NotEnabled/Completed/各停止终态 | 否 | 否 | 否 | Timer、Runner、Energized 必须全部退出，残留 5 秒触发接管 |

### 3.1 为什么不能直接排除 Learning

若只是把 Learning 从 `stateAllowsCycles` 删除，虽然不会再误报 Timer 缺失，但也会失去学习阶段的机械卡死监督。

本次采用三维独立契约：

```text
MechanicalProgressExpected
TimerRequired
RunnerRequired
```

所以 Learning 同时满足：

- `Timer=False, Runner=True` 不误报；
- Runner 真正缺失时，5 秒后接管；
- Runner/输出仍活动但机械完成数不增长时，仍按配置周期的机械进展期限接管；
- DO、峰值或状态版本持续刷新不能伪装机械完成。

### 3.2 主程序发布、sidecar 复算

心跳为每个通道新增以下可审计字段：

```text
LifecyclePhase
RuntimeContractRevision
MechanicalProgressExpected
TimerRequired
RunnerRequired
ResourcesMustBeInactive
ManualPauseOwned
RecoveryOwned
PhaseHardDeadlineUtc
```

主程序负责发布显式契约，sidecar 同时根据 `State` 独立复算权威契约。若同版本的发布值与复算结果不一致，将报告：

```text
ChannelRuntimeContractInconsistent
```

这样既能从日志直接理解每个阶段的资源预期，又不让主程序单方面伪造安全判断。

## 4. 不变量计时隔离

V2.13.0.13 的资源不变量计时签名为：

```text
RunId
+ RunEpoch
+ Channel
+ InvariantCode
+ State
+ ExpectedTimer/ExpectedRunner/ResourcesMustBeInactive
+ ActualTimer/ActualRunner/Energized
+ ManualPauseOwned/RecoveryOwned
```

以下变化会建立新的去抖窗口：

- 新 `RunId`；
- 新 `RunEpoch`；
- 阶段/契约发生变化，例如 Learning 切换为 Running；
- 实际资源形态变化；
- owner 变化；
- 不变量类型变化。

以下诊断刷新不会重置同一个真实故障的计时：

- `StateRevision`；
- DO 命令序号；
- 峰值 cutoff 水位；
- 非机械完成类日志或 UI 刷新。

这同时解决两类相反风险：

1. 旧运行的异常计时不能串入新运行；
2. 同一运行中持续刷状态版本不能永远推迟接管。

## 5. Watchdog 自取消归因修复

协议新增：

```text
RecoveryFailureOwner
RecoveryFailureCorrelationId
```

处理流程如下：

1. sidecar 发出 `RequestStopAll`，生成唯一 `CorrelationId`；
2. 主程序收到请求后保存该关联号和接管原因；
3. 若恢复任务因该 StopAll 被取消，失败消息回传：
   - `RecoveryFailureOwner=WatchdogTakeover`；
   - `RecoveryFailureCorrelationId=<原 RequestStopAll CorrelationId>`；
4. sidecar 仅在同时满足下列条件时判定为自取消：
   - 当前确有活动接管；
   - owner 为 `WatchdogTakeover`；
   - 关联号精确一致；
   - 异常证据为 `OperationCanceledException`、`TaskCanceledException` 或等价取消文本；
5. sidecar 记录 `RecoverySupersededByTakeover`，不调用恢复失败登记，不增加连续失败数，不启动第二条重拉链。

关联号不一致、没有活动接管或不是取消异常时，仍按真实恢复失败处理，不会吞掉业务故障。

## 6. 同进程重启闭锁与界面修复

### 6.1 中央按钮闭锁

`ApplyBatchPauseState` 现在首先检查控制器的 `RequiresProcessRestart`。一旦为真：

```text
按钮文字：需重启软件
按钮状态：Disabled
```

该检查位于中央状态回写函数中，所以以下路径都不能重新打开按钮：

- 迟到的 BatchPauseStateChanged；
- 开始处理函数的 finally；
- StopAll 后的状态归一化；
- 旧任务的异步完成回调。

### 6.2 点击入口二次保护

开始按钮事件入口也增加了 `RequiresProcessRestart` 短路。即使 Windows 消息队列中已有迟到点击，也只记录：

```text
当前进程已被安全闭锁，不能再次开始；
请等待 Watchdog 重启，或关闭软件后重新启动。
```

不会再次进入批次启动、再次清场或重复弹出状态转换失败框。

### 6.3 停止提示纠正

界面不再把所有需要重启的停止结果描述为“超过安全截止”。现在区分：

- `TimedOut`：超过安全截止，等待 Watchdog 接管；
- `SafeButRestartRequired`：已经安全收口，但诊断状态要求重启，同一进程永久禁止再次开始；
- `CompletedSafe`：允许关闭或在同一进程重新开始。

## 9. 现场验收方案

自动化验证不能替代实机长时间验证。V2.13.0.13 发布后必须按以下顺序验收。

### 9.1 包身份验收

启动前确认：

- 主程序窗口显示 `V2.13.0.13`；
- `MTTFTest.exe` 与 `MTTFTest.Watchdog.exe` 的文件版本均为 `2.13.0.13`；
- 正式发布 manifest 已生成且包校验为 `PackageVerified=True`；
- 主程序和 Watchdog 必须来自同一个发布包，禁止混用 V2.13.0.12 sidecar；
- 记录 GitCommit、BuildUtc、EXE SHA256 和配置 SHA256。

### 9.2 启动与学习验收

使用 10358-029 原配置启动 EPB4/5/9/10/11：

1. 保持 Learning 至少 30 秒；
2. 核对每个学习通道心跳：
   - `LifecyclePhase=Learning`；
   - `RuntimeContractRevision=1`；
   - `TimerRequired=False`；
   - `RunnerRequired=True`；
   - `Timer=False`；
   - `Runner=True`；
3. 不得出现 `ChannelExpectedRuntimeMissing`；
4. 不得出现 `TakeoverRequested`；
5. 学习机械完成数应继续增长；
6. 转入正式运行后，Timer 与 Runner 均应为 True。

### 9.3 故障注入验收

在台架安全条件允许且有人员监护时执行：

| 场景 | 预期 |
|---|---|
| Learning 正常 Runner、无 Timer | 不接管 |
| Learning 人为阻断 Runner | 5 秒后 `ChannelExpectedRuntimeMissing` |
| Running 人为丢 Timer | 5 秒后 `ChannelExpectedRuntimeMissing` |
| Paused 无人工 owner | 5 秒后 `ChannelPausedWithoutManualOwner` |
| Recovering Timer/Runner 单边残留 | 30 秒后 `ChannelRecoveryInvariantStalled` |
| Completed 残留执行资源 | 5 秒后 `ChannelTerminalResourcesActive` |

故障注入必须优先保证物理断能，不得为验证而绕过电源和 DO 安全链。

### 9.4 停止与重启验收

1. 正常停止结果为 `CompletedSafe` 时，允许同进程重新开始；
2. 人为制造 `SafeButRestartRequired` 后：
   - 开始按钮显示“需重启软件”；
   - 按钮不可点击；
   - 迟到状态事件不能重新打开；
   - 日志明确提示等待 Watchdog 或关闭后重启；
3. Watchdog 接管导致恢复任务取消时：
   - sidecar 记录 `RecoverySupersededByTakeover`；
   - 不得新增 `UnhandledSoftwareStartup` 连续失败计数；
   - 不得产生第二条并发恢复重拉链。

### 9.5 长时间运行验收

建议至少完成：

- 24 小时连续运行；
- 48 小时连续运行；
- 覆盖至少一次正常停止/同进程重启；
- 覆盖至少一次 Watchdog 安全接管/检查点恢复；
- 核对正式机械完成数、CSV/BIN/Raw/SQLite 持久化边界一致；
- 确认无 `ChannelExpectedRuntimeMissing` 的 Learning 误报；
- 确认无循环恢复窗口；
- 确认 Watchdog 连续恢复失败预算未被自取消消耗。

## 10. 发布与回滚规则

### 10.1 发布规则

V2.13.0.13 只有同时满足以下条件才允许替换现场版本：

1. 正式 Release 包构建成功；
2. 主程序和 sidecar 版本、哈希、manifest 一致；
3. Watchdog 专项 26/26；
4. 10358-029 事故专项 56/56；
5. DAQ 实时组 102/102；
6. 台架启动/学习验收通过；
7. 至少一次安全停止和一次恢复演练通过。

### 10.2 回滚规则

V2.13.0.12 不得继续用于无人值守长时间试验，因为其 Learning 资源误判已被现场证实。

如 V2.13.0.13 现场验收未通过，可临时回退 V2.13.0.11 以恢复生产，但必须注意：V2.13.0.11 不包含 V2.13.0.12 针对孤儿暂停、看门狗恢复边界和重复键启动失败的全部整改，不能视为最终版本。

回滚前必须：

1. 正常停止试验；
