# V2.10.2.3 现场日志复盘：DaqSampleTimelineFuture 修复验证与新增问题

## 1. 技术摘要

本次分析对象为 `\\wj-epb\EPB_Data\10358-029_V2.10.2.3_0805_1950`，对照文档为[《2026-08-05_V2.10.2.2_DaqSampleTimelineFuture误报警根因与无人值守修复方案》](./2026-08-05_V2.10.2.2_DaqSampleTimelineFuture误报警根因与无人值守修复方案.md)。

结论分为两层：

1. **V2.10.2.2 的直接问题已解决。** 在 V2.10.2.3 本次约 3 小时 05 分的应用日志、4 份报警快照及相关事故快照中，未出现 `DaqSampleTimelineFuture`、`TimelineFuture`、`DaqClockModelInvalid` 或 `DaqClockRecoveryLimitExceeded`。报警窗口中的 `SampleLeadMs` 均未超过 0 ms，更没有跨过旧版的 `+20 ms` 未来阈值；自适应采样率、时钟偏差和状态字段均有有效变化，说明 `ClockDisciplinedSampleTimeline` 路径已经实际运行。
2. **V2.10.2.3 仍不能按“无人值守永久修复”放行。** 本次记录中出现 5 次 DAQ 事故恢复，全部在 `Fresh=0/10` 或 `1/10` 处超时；另有一次 EPB5 真实高电流平台报警。到 19:08:38，所有仍在运行的通道均已退出试验。当前数据只覆盖约 2 小时 29 分的试验活动，未达到原方案规定的 24/72 小时稳定性验收。

最高优先级的新问题是：

- DAQ 恢复验证器要求轮询连续看到每一个 `sequence+1`，与现场“约 15 ms 间隔后紧跟突发回调”的实际节奏不兼容，导致采集已恢复仍被判为恢复失败。
- 反向动作刚启动后，控制状态机没有拒绝 `tick < powerStartTick` 的历史/积压样本，能够在约 33 ms 墙钟时间内拼出 `confirm=202 ms` 的释放窗口，疑似导致 EPB5 未充分释放，下一次正向动作出现 14.473 A 高电流平台。
- 终态断电命令在 DAQ 控制分发链路中同步执行。18:26:24 一次 94.024 ms 的 EPB10 断电调用造成 Dev2 控制队列积压，EPB11 随后以 `DaqSampleStale>100ms` 停机；此时 DAQ 回调仍正常，属于控制消费者自阻塞引发的误分类/误报警。
- 16:48:44 两台 DAQ 同时出现约 163～171 ms 回调空窗，随后集中补发。证据更符合进程级暂停；同期 GC 计数增长异常快，GC/分配压力是高概率因素，但缺少 ETW/GC Pause 事件，尚不能作为唯一根因定案。

## 6. 新发现的问题

### 6.1 P0：恢复验证器会把正常突发回调判成恢复失败

#### 现场证据

- 5 次 DAQ 事故恢复全部失败，最终只有 `Fresh=0/10` 或 `1/10`。
- 启动健康检查也出现 `Fresh=0/3`。
- 16:48 恢复前后的 DAQ 数据显示，回调常呈“约 15 ms 间隔 + 紧随其后的亚毫秒突发”模式；回调已经继续生成，并非 3 秒内完全无数据。

#### 机制

[当前源码 `TwoDeviceAiAcquirer.RecoverDeviceAsync`](../../IO.NI/TwoDeviceAiAcquirer.cs#L1941) 每 5 ms 读取一次快照，并且只有在 `LastProcessedSequence == lastSequenceAfterRecovery + 1` 时才增加连续新鲜计数。轮询线程无法保证观察到突发中的每一个中间序号；一旦从 N 直接看到 N+2 或更大，代码就把 `freshCount` 清零。

因此，这个验证器验证的不是“DAQ 是否连续恢复”，而是“5 ms 轮询是否恰好逐个采到每一次序号变化”。现场回调节奏下后者没有可满足性保证。

#### 影响

- 自动恢复即使已经重建成功，也会被报告为失败。
- 启动预检可能阻止本来健康的设备开始试验。
- 每次可恢复故障最终升级为通道组停机，直接破坏无人值守连续运行。

#### 修复要求

- 在 DAQ 消费者内部维护“已验证的新 generation 新鲜批次数/连续序号状态”，恢复线程等待该事件或累计计数，不再依赖外部轮询逐个观察序号。
- 或至少允许快照序号向前跨越，并以 generation 不变、序号单调递增、消费者内部无 gap 标记、年龄满足阈值作为恢复证据。
- 预检与事故恢复必须复用同一套可验证语义。

### 6.2 P0：方向切换后可能把启动前积压样本纳入新的反向释放窗口

#### 现场证据

EPB5 第 3291 圈：

- 17:55:39.286 下发反向命令。
- 17:55:39.319 即判定 `Released` 并断电，墙钟仅约 33 ms。
- 日志同时声称释放确认窗口 `confirm=202ms`，电流仍接近基线约 0.013 A。
- 该圈记录的反向持续时间约 218 ms，而相邻正常循环约为 1187～1218 ms。

紧接着第 3292 圈正向动作，在约 531 ms 内进入中位数 14.473 A 的高电流平台，明显高于 7.500 A 阈值。报警本身有连续电流平台证据，不是 DAQ 时间线误报警。

#### 机制推断

当前源码在 [`ResetDirection`](../../Controller/Adaptive/EpbAdaptiveControl.cs#L970) 时会清空窗口并记录 `_powerStartTick`，但 [`OnSampleReusable`](../../Controller/Adaptive/EpbAdaptiveControl.cs#L424) 对随后到达的样本没有检查 `tick < _powerStartTick`。如果控制队列中已有“采集时间早于新方向上电时刻”的积压样本，它们可以在状态机完成 Arm 后进入新窗口。[`EvaluateReverse`](../../Controller/Adaptive/EpbAdaptiveControl.cs#L799) 只要求窗口跨度和统计量合格，于是能在 33 ms 墙钟内使用旧时间戳构造 202 ms 窗口。

这是与日志完全相容的高置信度解释，但由于现场二进制的 Git commit 未记录，仍应以原始回放或带 sequence 的新增诊断做最终确认。

#### 修复要求

- Arm 每个方向时冻结 `generation`、`baselineSequence` 和 `powerStartTick`。
- 丢弃/忽略 `captureTick <= powerStartTick`、`sequence <= baselineSequence` 或 generation 不一致的控制样本。
- 至少收到第一批“上电之后”的新鲜样本后，才允许启动释放确认窗口和样本新鲜度 watchdog。
- 释放确认时同时记录窗口首尾 `captureTick`、首尾 sequence、Arm tick 和墙钟耗时，保证审计可以证明整个确认窗口位于本次上电之后。

### 6.3 P0/P1：同步终态断电阻塞同设备其他通道的实时控制消费

#### 现场证据

18:26:24：

- EPB10 的终态断电命令耗时 94.024 ms。
- 同期 Dev2 控制队列深度升至 7，随后达到 8；最老项约 62.4 ms。
- EPB11 在 18:26:24.917 以 `DaqSampleStale>100ms` 硬停机。
- DAQ 回调最大间隔仅 23.326 ms，序列没有报告 gap，`QualityFlags=None`；即采集源并未停止。
- 事故分类时重新读取到的年龄已经恢复为 Callback 9.7 ms、Enqueue 9.7 ms、Processed 8.7 ms，因此最终理由一边写 `DaqSampleStale>100ms`，一边展示不到 10 ms 的快照，语义自相矛盾。

#### 源码对应

[`DispatchAdaptiveDecisionInSafetyOrder`](../../Controller/EpbCycleRunner.Adaptive.cs#L374) 在控制分发线程中直接调用 `terminalOff`；[`EnsureAdaptiveTerminalPowerOff`](../../Controller/EpbCycleRunner.Adaptive.cs#L526) 又同步执行 `CommandOffHighPriority()`。一个通道的慢 DO 调用因此会阻塞同设备其他通道的样本处理。另一个证据一致性问题是，[`OnRunnerRecoverableFaultRaised`](../../Controller/EpbManager.cs#L1417) 在触发之后重新读取 freshness 并进行分类，而不是使用触发瞬间的冻结快照。

#### 修复要求

- 断电请求仍需最高优先级、立即发起和幂等，但执行应进入独立、受监控的安全执行通道，DAQ 控制消费者不能等待硬件 I/O 返回。
- 为安全执行通道设置严格 deadline、失败后组级联锁和可观测队列；不允许与持久化、快照导出共用消费者。
- 在触发 watchdog 的瞬间冻结 callback/enqueue/processed 三层年龄及对应 sequence。后续分类必须使用触发快照，不能在队列追平后重新采样并改写原因。
- 区分 `DaqCallbackStale`、`ControlEnqueueStale`、`ControlProcessingStale`；18:26 事件应归类为 `ControlProcessingStale` 或等价故障，而不是 `DaqSampleStale`。

### 6.4 P1：存在进程级长暂停，GC/分配压力需要专项治理

16:48:44，Dev1 和 Dev2 几乎同时停止回调约 163～171 ms，随后各自快速补发约 17 个回调。两块独立 DAQ 同时产生相近空窗，较难由两块硬件独立故障解释，更符合 CLR、调度器或进程级临界区暂停。

运行时快照显示高 GC 活动：16:48:26～16:48:44 约 18.2 秒内，Gen0/Gen1/Gen2 分别增加约 104/103/14 次；进程又是 32-bit。其他报警前也存在频繁 Gen2 回收。由此可以把 GC/高分配列为高概率诱因，但当前日志没有单次 GC pause duration、分配速率、LOH 或线程停顿事件，无法证明每次 DAQ 空窗都由 GC 直接造成。

建议：

- 增加 GC pause duration、allocation rate、LOH size、各代回收原因和线程池饥饿指标。
- 在长暂停阈值触发时保存轻量 ETW/EventPipe 窗口或等价诊断。
- 对 DAQ/控制热路径做 allocation profile，消除每批/每样本临时对象、字符串和集合扩容。
- 评估迁移到 64-bit；该项不能代替分配治理，但可降低 32-bit 地址空间和堆压力风险。

### 6.5 P1：事故证据封存存在竞态

16:45 EPB5 报警快照的循环证据为空，校验信息显示“Cycle=3036 已由其它收尾路径封存，当前圈为 null”。这说明报警、循环结束和快照导出存在多条收尾路径争抢所有权。恰好最需要取证的首次故障没有得到完整循环 CSV/BIN。

建议把循环封存改为单一所有者、一次性状态转移；报警快照只引用不可变封存结果，并在封存未完成时等待有界 completion，而不是再次抢占当前圈。

### 6.6 P2：时钟模型锁定和告警噪声仍需优化

- 报警窗口中 `ClockState` 多数为 `Adjusting`，锁定状态持续性不足。需要用 24/72 小时数据统计每台设备的 Locked 占比、重热身次数、校正幅度和残差分布。
- 日志中大量出现“控流观测无效，未更新预测模型”等重复警告。它们不直接造成上述停机，但会放大字符串分配、I/O 和 GC 压力，并降低真正告警的可见性。应按原因聚合、限频，并以计数器替代逐次文本日志。

### 6.7 P1：构建身份不可追溯

`gitCommit` 和 `gitDirty` 均为 `unknown`。在源码快速迭代、现场二进制与工作区可能不同步的情况下，这会显著降低根因分析可信度。发布流程应把 commit、dirty 状态、构建时间、配置版本和关键程序集哈希作为强制字段；缺失时阻止生成可发布包。

## 8. 验收与回归测试

### 8.1 旧问题回归

- 2、4、24、72 小时分别检查：`TimelineFuture` 为 0、有效批次丢弃为 0、每设备独立 ppm 估计稳定。
- 注入正/负频偏、突发补回调、短暂停顿和 generation 重建；自适应时间线不能把有效样本投到未来。
- 报告 Locked 占比、残差 P50/P95/P99、最大校正速率和重热身次数，不只报告“没有报警”。

### 8.2 恢复验证器

- 用 16:48 的“15 ms + 亚毫秒突发”节奏回放；即使 5 ms 观察线程跳过多个 sequence，也必须正确累计消费者确认的新鲜批次。
- 覆盖一次补发 2、3、10、20 批以及真正 sequence gap；前者成功，后者失败并保留准确 gap 证据。
- 预检和事故恢复均应在真实回调已恢复时稳定通过 3/3、10/10，不允许再出现 0/10 假失败。

### 8.3 方向切换

- 在 ArmReverse 前预置 200～500 ms 积压样本，Arm 后再送新样本；所有 pre-arm 样本必须被拒绝。
- 释放确认窗口的首尾时间戳和 sequence 必须全部晚于 Arm；墙钟不足确认时长时绝不能输出 `Released`。
- 回放 EPB5 第 3291/3292 圈，验证不会在约 33 ms 提前释放，下一正向圈不再进入 14 A 平台。

### 8.4 实时控制隔离

- 注入 100、200、500 ms 的 DO 调用延迟；安全断电请求应立即进入专用通道，DAQ 控制消费延迟不得跨 100 ms，其他通道不能误报 DAQ stale。
- 分别注入 callback、enqueue、processed 三层停顿，故障码和冻结快照必须准确对应。

### 8.5 无人值守放行门槛

- 24/72 小时连续运行期间，无 `TimelineFuture`、无恢复假失败、无 pre-arm 样本进入控制窗口、无因其他通道慢 I/O 造成的控制超时。
- 所有故障注入均能自动恢复，且恢复后 generation、序号、时间戳连续性和循环边界可解释。
- 事故快照完整率 100%，构建身份包含有效 Git commit 和配置哈希。

## 9. 局限性与不确定性

- 本次现场活动只有约 2 小时 29 分，不能外推为 24/72 小时稳定。
- 16:48 的进程级暂停缺少 ETW/GC pause 事件；“GC/分配压力”为高概率推断，不是已证明的唯一原因。
- 17:55 的 pre-arm 样本机制与现场时间线高度吻合，但二进制没有 Git commit，仍需用原始数据回放或新增 sequence 诊断最终闭环。
- 19:08 只确认 Dev1 出现真实回调空窗，无法仅凭现有日志区分 NI 驱动/硬件停顿与进程线程停顿。
- 本文没有把日志中的每一条软警告逐项归因；只纳入了会影响旧问题验证、报警正确性、自动恢复或无人值守连续性的事件。

## 10. 最终判定

**V2.10.2.3 已解决 V2.10.2.2 的 `DaqSampleTimelineFuture` 误报警链路，但没有解决“无人值守长期可靠运行”这一更高层目标。**

本次试验没有出现旧的未来时间线误判和有效批次丢弃，说明自适应时钟修复方向正确；然而恢复验证器的结构性假失败、反向释放窗口的样本边界缺陷、同步 DO 对实时控制队列的阻塞，以及尚未解释清楚的进程级长暂停，仍会触发组级停机。应完成第 7、8 节整改与回归后，重新开始 24/72 小时验收。
