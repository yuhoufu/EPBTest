# V2.12.0.19 发布依赖去重与递归身份闭环

## 结论

V2.12.0.19 解决了三个此前被“能够编译”掩盖的发布问题：

1. `MTTfTest` 无业务代码使用 `ZlgCanComm`，却把它作为项目依赖带入现场包；两个程序集又包含同命名空间、同名称的 DevExpress UI 类型，产生大量 `CS0436` 冲突警告。
2. 主程序自己的 `Editors\ToggleButton.cs` 已存在，但旧式非 SDK 项目没有将其加入 `Compile` 清单；移除 `ZlgCanComm` 后立即暴露 15 个 `ToggleButton` 缺失错误，证明主程序此前实际依赖了外部 DLL 中的重复副本。
3. 旧发布清单只哈希 Release 根目录文件，未覆盖 `Config`、`x86/x64` SQLite 互操作库和语言资源；配置聚合哈希还受 PowerShell 排序规则影响，并错误包含未发布的备份 XML。

当前主程序使用本地 `ToggleButton` 源码和本地 HTML/CSS 资源，不再引用或发布 `ZlgCanComm.dll`。发布脚本从经过绝对路径校验的空 Release 目录构建，按序数相对路径递归记录全部文件，并只对 `MTTfTest.csproj` 明确复制的配置计算聚合 SHA。Windows PowerShell 5 与 PowerShell 7 对同一配置计算出的 SHA 完全一致。

## 代码整改

### 1. 去除无用运行依赖

- 从 `MTTfTest.csproj` 删除 `ZlgCanComm` 项目引用。
- 将 `Editors\ToggleButton.cs` 显式加入主程序旧式项目的 `Compile` 清单。
- 发布预检新增 `ToggleButton.cs` 文件存在和项目登记双检查。
- 从独立 `ZlgCanComm.csproj` 删除没有任何源码使用的失效 `EntityFramework` 引用；独立项目仍保留在解决方案中并能单独编译。

结果：主程序输出和两份发布清单中 `ZlgCanComm.dll` 均为 0 命中；缺失 EntityFramework、重复 UI 类型和位域符号扩展警告全部消失。

### 2. 空目录、递归发布清单

`Tools/Build-Release.ps1` 现在：

- 只允许清理解析后精确等于 `MTTfTest\bin\Release` 的目录；
- 构建前清空该专属输出目录，禁止取消依赖后的陈旧 DLL 残留；
- 递归枚举全部发布文件，路径统一使用 `/`，并以 `StringComparer.Ordinal` 排序；
- `build-identity.json` 记录全部非自引用文件；
- `SHA256SUMS.txt` 使用 UTF-8 无 BOM，能够无损记录中文配置文件名；
- 校验器拒绝绝对路径、`..` 越界、重复路径、缺失文件、多余文件、长度变化和哈希变化。

### 3. 配置身份确定性

发布配置集合不再使用“源目录下所有 XML”，而是解析 `MTTfTest.csproj` 中带 `CopyToOutputDirectory` 的 `Config\*.xml`。构建前按输出相对路径和内容计算 SHA，构建后再对实际 `bin\Release\Config` 重算；两者不同立即拒绝生成。

`Verify-Release.ps1` 会再次从实际包重算配置聚合 SHA，并与 `build-identity.json` 比较。这样 SESSION 中记录的配置 SHA 对应实际发布配置，而不是未发布备份文件或某个 PowerShell 版本的区域排序结果。

## 上线边界

上表保留的是代码提交前的可重复性审计基线，不是最终正式包身份。整改范围审阅、提交完成后，必须在无未提交文件的工作树上重新执行 `Tools/Build-Release.ps1`，并用 `Tools/Verify-Release.ps1 -RequireDeploymentApproved` 验证。最终 Git SHA、BuildUtc、EXE/config SHA、文件清单和 `gitDirty=false` 以正式候选目录内 `build-identity.json`、`SHA256SUMS.txt` 为唯一依据。

`gitDirty=false` 和 `deploymentApproved=true` 只证明软件来源与包内容可追溯；真实硬件 2 h 故障注入、8 h 压力、24 h 六通道联合验收和 72 h 无人值守验证仍必须完成。发布完整性闭环不能替代 NI、程控电源、液压、网络共享和外部硬联锁的现场证据。
