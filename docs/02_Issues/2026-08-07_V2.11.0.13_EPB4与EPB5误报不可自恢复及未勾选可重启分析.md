# V2.11.0.13 EPB4/EPB5 误报不可自恢复及未勾选仍可重启分析

> 分析日期：2026-08-07  
> 现场项目：`10358-029`  
> 程序版本：`2.11.0.13`  
> 现场数据：`\\wj-epb\EPB_Data\10358-029`  
> 关键运行 ID：`b9f0aef715da46fea7f1e6fa8af0920e`  
> 关键 DAQ 事故关联号：`96157db84cb242c18f7db65a8f560e42`

## 1. 结论

EPB4、EPB5 本次并非同时发生真实开路或卡钳硬件损坏，而是一次 **Dev1 DAQ 回调短时中断之后，学习阶段自恢复遗漏重新接通共用程控电源** 所造成的二次误报警。

完整因果链为：

1. Dev1 的采集回调超过 100 ms 未更新，EPB4、EPB5 按失效安全立即断开 DO；
2. 因断电电流无法由陈旧 DAQ 样本确认，程序进一步关闭 EPB4、EPB5 共用的电源组 2；
3. DAQ 任务重建成功，但当时处于学习阶段，通道没有登记在 `_timers` 中；
4. DAQ 恢复逻辑只把 `_timers` 中的正式运行通道纳入“重新接通电源并重新加入节律”，因此 EPB4、EPB5 被漏掉；
5. 程序在电源组 2 仍为 OFF 时继续执行学习圈重试，向 EPB5、EPB4 发出正向 DO；
6. 两路自然只能测到基线电流 `0.016 A`、`0.010 A`，随后被 `OpenCircuitOrOutputFault` 连续 3 次确认；
7. 该故障码被配置为 `NonRecoverableDisableChannel`，所以 EPB5、EPB4 分别停机并将当前项目 `Enabled` 持久写为 `false`；
8. 操作员单独点击重启 EPB4、EPB5 时，单通道恢复入口重新执行了程控电源预检并接通电源组 2，两路随即正常运行。这一结果反证了“真实开路/卡钳损坏”。

因此，本次主要根因是 **学习阶段与正式阶段使用了不一致的 DAQ 恢复参与通道判定**，不是开路判定阈值本身错误。

同时确认一个独立的操作权限缺陷：**不可自恢复报警已取消 EPB4、EPB5 的项目启用勾选，但界面仍残留可点击的 RUN/STOP 按钮，且实际恢复入口也不校验 `Enabled`，导致未重新勾选就能越过项目禁用状态启动通道。**

## 3. 首发 DAQ 故障能够确认到什么程度

事故快照 `00-trigger` 给出的直接证据为：

- `faultCode = DaqCallbackStale`；
- 回调、控制入队和控制处理年龄同时约为 `112.7～112.8 ms`；
- `queueDepth = 0`；
- 受影响通道只有 Dev1 上的 `[4,5]`；
- 故障前处理耗时通常小于 1 ms，工作线程仍有约 1015 个可用；
- Dev1 最后记录到的回调批次为 Generation 2、Sequence 5893，之后出现超过 100 ms 的空窗；
- 重建后 Generation 变为 4，新鲜样本验证通过。

这足以确认 **NI/DAQ 生产回调链发生了短时停顿**，但现有证据不足以进一步唯一判定是 NI 驱动、DAQ 任务本身、USB/总线、系统调度还是未记录到的 GC 暂停。运行时快照中的 GC ETW 状态为 `Access Denied`，因此没有 GC pause 的直接证据。

目前不应把某个未经证明的系统原因写成确定根因。对本次 EPB4/EPB5 停机而言，DAQ 短暂停顿本应是可恢复软件故障；真正将其放大成永久停机的是恢复后的电源状态遗漏。

## 4. 代码根因

### 4.1 DAQ 恢复只识别正式阶段 `_timers` 通道

`Controller/EpbManager.cs` 的 DAQ 恢复上下文用 `_timers.ContainsKey(channel)` 记录 `PreviouslyRunningChannels`，恢复提交时又要求通道仍在 `_timers` 中：

```csharp
var rejoinChannels = (context.PreviouslyRunningChannels ?? context.AffectedChannels)
    .Where(channel =>
        _timers.ContainsKey(channel) &&
        !IsAlarmStopRequested(channel) &&
        !_channelPausedUtc.ContainsKey(channel))
    ...;
```

只有 `rejoinChannels.Length > 0` 时，后续才执行：

```csharp
_powerSupply.PrepareAndEnableAsync(channels, ct)
```

但学习阶段由 `RunLearningPhaseAsync` 直接创建并等待通道任务，尚未建立正式阶段计时器。因此 EPB4、EPB5 虽然有 Runner、正在参与液压和学习圈，却都不满足 `_timers.ContainsKey`。

结果是：

- DAQ 恢复认为两路不需要重新加入；
- 电源组 2 的 `PrepareAndEnableAsync` 被整段跳过；
- 恢复结果仍被提交为成功；
- `WaitForDaqRecoveryAsync` 返回后，学习圈自恢复仅重新建立液压阶段，没有重新检查/接通程控电源；
- 下一次电机 DO 在无主电源条件下执行。

现场事故快照已经直接证明该状态：`90-recovered` 的 `result` 是 `90-recovered`，但同一文件中的电源状态仍是：

```json
{"group":2,"expectedOn":false,"active":false,"telemetryOn":false}
```

“恢复成功”和“受影响通道供电未恢复”同时存在，是本缺陷最明确的机器证据。

### 4.2 开路判定缺少电源许可前置条件

`Controller/Adaptive/EpbAdaptiveControl.cs` 在涌流忽略期后，只要电流持续不高于 `NearZeroA` 约 200 ms，就生成：

```csharp
OpenCircuitOrOutputFault I=...
```

该状态机默认“正向 DO 已发出”等价于“电源实际可用”。本次电源组 2 实际为 OFF，这个前提不成立，但近零计数仍然累计。

因此，即便上层恢复流程将来还有其它遗漏，开路判定也应增加以下硬前置条件：

- 电源组控制状态为 Active/ExpectedOn；
- 遥测确认 `OUTP ON`；
- 输出电压达到启动稳定门槛；
- 该确认发生在本次上电动作之前且未过期。

任一条件不满足时，应归类为 `PowerSupplyUnavailable/RecoveryBarrierIncomplete` 软件或联锁故障，立即断 DO，但不得增加卡钳开路的连续次数。

## 5. “取消勾选后仍能单独启动”的逻辑缺陷

该现象由两个缺陷叠加造成。

### 5.1 UI 禁用事件没有刷新 RUN/STOP 可操作状态

不可自恢复报警异步持久化时，运行状态 `AlarmStopped` 会先发布。此时项目内存中的 `Enabled` 仍可能是 `true`，`UpdatePauseResumeChannelUi` 看到：

- 当前状态可被 `CanAcknowledgeChannelAlarm` 接受；
- 当前 `Enabled=true`；

于是把 RUN/STOP 按钮置为可点击。

稍后 `OnNonRecoverableChannelDisableRequested` 才执行：

- `Enabled=false`；
- 取消 `CtrlJoinTest` 勾选；
- 取消曲线勾选；

但该方法没有再次调用 `UpdatePauseResumeChannelUi` 或 `ApplyAllChannelOperationStates`。因此配置勾选已取消，按钮的 `Enabled` 属性却保留了前一时刻的可点击值。

这与截图中“EPB4/EPB5 勾选已取消，但两路仍显示可操作的运行按钮”一致。

### 5.2 控制入口没有校验项目 `Enabled`

更严重的是，按钮残留可点击并非只影响显示。`CanAcknowledgeChannelAlarm` 只检查运行状态是否属于：

- `AlarmStopped`；
- `InterlockStopped`；
- `ManualStopped`；
- `StartBlocked`；
- `SystemFault`。

它不检查 `_cfg.Test.GetEpbRecord(channel).Enabled`。

`ResumeAlarmStoppedChannelAsync` 在进入恢复流程前也没有校验 `Enabled`。所以即使 UI 刷新问题被修复，只要存在其它调用入口，仍能绕过项目禁用状态。

这与既有规则“只有人员明确重新勾选启用后，卡钳才能参加新的试验”冲突。当前行为实质上把一次普通 RUN 点击同时当成了“重新启用项目通道 + 确认硬件故障已排除 + 启动”，但既没有恢复勾选，也没有先持久写回 `Enabled=true`，形成配置状态与运行状态分裂。

## 6. 报警快照导出失败是伴随故障，不是停机原因

截图中的 `WarningSnapshotExportFailed` 发生在近零预警之后，不参与 DO 断电或最终报警判定，因此不是 EPB4/EPB5 停机原因。

但它暴露出另一个证据链缺陷：预警导出器按内部学习圈号（例如 `-790`、`-757`）从当前环形索引读取时得到 `SampleCount=0`，历史回退又没有检索到已经封存的 `LearningCycles` 文件，于是报告“没有可导出的样本”。

现场实际上存在对应文件，例如：

- `LearningCycles/.../EPB05/Learning_0005/EPB5_Cycle_-000790.bin`；
- `LearningCycles/.../EPB04/Learning_0005/EPB4_Cycle_-000757.bin`；
- 后续尝试 `-791/-792/-758` 也已有 CSV/BIN。

说明不是现场完全没有数据，而是 **预警快照的历史恢复路径未覆盖学习圈目录/尝试目录，或导出任务与封圈元数据存在竞态**。建议作为独立缺陷修复，避免下次真正硬件报警时缺少预警快照。

## 7. 修复要求

### P0：恢复屏障必须覆盖学习、资格和正式三个阶段

1. DAQ 事故发生时记录“实际活跃且曾带电的通道”，不能只依赖 `_timers`；至少应覆盖 Runner、学习/资格任务、液压参与者和正式计时器。
2. 受影响通道需要继续运行时，DAQ 恢复成功终态必须包含：
   - DAQ 新鲜样本通过；
   - 旧 DO 全关确认；
   - 程控电源重新预检、`OUTP ON`、电压稳定；
   - 必要的机械释放/定位完成；
   - 最后才允许学习、资格或正式任务继续。
3. 如果没有需要继续的通道，可以保持电源 OFF；但等待中的学习任务必须收到“不可继续/已隔离”，不能把只恢复 DAQ 的结果当作可重新上电许可。
4. `_emergencyPowerGroupLatch` 只能在电源恢复屏障成功后清除。

### P0：电机动作前增加最终供电门禁

Forward/Reverse DO 的统一入口在真正写 DO 前，必须核验所属电源组的控制态和新鲜遥测。未满足时：

- 禁止动作；
- 当前尝试圈作废；
- 进入电源/DAQ恢复；
- 不累计 `OpenCircuitOrOutputFault`。

这是防止任何上层漏检再次变成“假开路”的最后一道安全门。

### P0：项目禁用必须成为控制层权限

1. `CanAcknowledgeChannelAlarm` 增加 `Enabled=true` 校验；`Enabled=false` 时明确返回“请先在试验设置中重新启用该卡钳”。
2. `ResumeAlarmStoppedChannelAsync` 在进入互斥门前和取得互斥门后各校验一次 `Enabled`，防止检查与执行之间状态变化。
3. `StartChannelAsync`、批量启动和所有恢复入口统一调用同一个通道启用门禁，不能只依赖 UI。
4. 如确需运行中恢复不可自恢复通道，应提供显式“重新启用”流程：人工确认、写回 `Enabled=true`、恢复勾选、清零故障连续数，再执行完整预检；不能由普通 RUN 点击隐式完成。

### P1：立即同步 UI

`OnNonRecoverableChannelDisableRequested` 修改记录和勾选后，应立即刷新该通道运行按钮和状态摘要。按钮显示必须由当前权威配置与运行状态共同计算，不能依赖上一次状态事件。

### P1：修复学习圈预警快照历史回退

警告快照导出失败后，应按运行 ID、通道、负学习圈号和 Attempt 顺序检索 `LearningCycles`，复用已封存 CSV/BIN；同时消除封圈元数据尚未提交就开始后台导出的竞态。

## 8. 必须增加的回归测试

1. **学习阶段 DAQ 中断**：EPB4/EPB5 正在学习时注入 `DaqCallbackStale`；验证电源组先 OFF，DAQ 重建后必须重新 ON 且电压稳定，随后才允许任何 Forward/Reverse DO。
2. **资格阶段 DAQ 中断**：执行同样验证，不能只覆盖正式计时器阶段。
3. **电源未恢复保护**：强制 `PrepareAndEnableAsync` 未执行或失败；验证近零样本不增加 `OpenCircuitOrOutputFault` 连续数。
4. **恢复结果不完整**：当事故快照中受影响组 `telemetryOn=false` 且仍有待继续通道时，禁止提交 `Recovered=true`。
5. **不可自恢复禁用 UI**：发布 `AlarmStopped` 后延迟触发 `ChannelDisableRequested`，验证勾选、RUN/STOP 按钮和状态摘要最终一致，按钮不可点击。
6. **控制层越权**：`Enabled=false` 时直接调用 `ResumeAlarmStoppedChannelAsync` 和 `StartChannelAsync`，均必须被拒绝且不得接通电源或写 DO。
7. **显式重新启用**：先人工写回 `Enabled=true`，再启动；验证配置、勾选、状态和实际运行一致。
8. **学习圈快照**：对负圈号及 `Attempt_0002/0003` 导出预警证据，验证能复用 `LearningCycles` 中已封存的 CSV/BIN。

## 9. 现场验收判定

修复版本只有同时满足以下条件才算通过：

- 任意阶段的 Dev1 DAQ 短暂停顿都可以安全断电并自恢复；
- 恢复日志中必须先出现电源组 ON 与输出稳定，再出现 EPB4/EPB5 正向或反向 DO；
- 事故恢复快照不得再出现“需要继续运行但 `Recovered=true` 且 `telemetryOn=false`”；
- 电源 OFF 场景不会累计卡钳开路连续数；
- 不可自恢复报警取消勾选后，EPB4/EPB5 的 RUN/STOP 立即不可点击；
- 未明确重新勾选并保存 `Enabled=true` 前，任何控制入口都不能启动该通道；
- 重新启用后必须执行 DAQ、电源、机械定位和资格复核，真实故障仍存在时应再次停机；
- 学习圈软预警和最终硬报警均能形成可读快照。

## 10. 最终定性

| 项目 | 定性 |
|---|---|
| Dev1 `DaqCallbackStale` | 首发可恢复软件/采集链瞬态；更底层成因现有证据不足 |
| 电源组 2 安全关闭 | 正确的失效安全动作 |
| DAQ 恢复后未重新接通电源 | 本次永久停机的主要程序根因 |
| EPB4/EPB5 `OpenCircuitOrOutputFault` | 由电源 OFF 制造的假开路二次报警 |
| 持久写入 `Enabled=false` | 对该故障码的既定终态动作本身正确，但输入故障被误分类 |
| 未勾选仍可单通道重启 | 独立的 UI 状态刷新缺陷 + 控制层权限缺失 |
| `WarningSnapshotExportFailed` | 独立证据导出缺陷，不是停机触发原因 |

在修复前，不建议把本次 EPB4、EPB5 的永久禁用作为卡钳硬件损坏结论；应按“DAQ 自恢复期间电源恢复屏障遗漏导致的误报警”处理。

### 11.2 现场复验项

自动化测试不能替代真实 NI 与程控电源联调。部署 `2.11.0.14` 后，仍需在 10358-029 项目执行一次学习阶段 Dev1 DAQ 中断注入，确认日志严格满足：

1. EPB4/EPB5 DO 先关闭，电源组 2 随后安全 OFF；
2. Dev1 DAQ 新代次及新鲜样本验证通过；
3. 电源组 2 出现 OUTP ON，允许 4～5A 短暂浪涌，并在电流回零、输出电压稳定后签发动作许可；
4. 许可签发后才出现 EPB4/EPB5 Forward/Reverse DO；
5. 故意保持电源 OFF 时，动作被门禁拒绝且不得增加 `OpenCircuitOrOutputFault` 连续数；
6. 将 EPB4/EPB5 `Enabled=false` 后，勾选和 RUN/STOP 均不可操作，直接调用控制入口也被拒绝。
