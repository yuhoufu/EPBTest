## 1. 结论先行

三份封盘不是三个彼此无关的问题，而是一条连续的复合故障链：

```text
主机/DAQ 短时调度空窗
  -> DAQ 回调或压力样本失鲜
  -> 安全断能动作实际成功或随后成功
  -> 控制状态机先读到旧状态，或把时间证据缺失当成物理故障
  -> 恢复 owner / 正式槽 / StopSafety 进入不可逆失败状态
  -> Watchdog 又把传输或逻辑源失鲜升级成进程接管
  -> 接管被检查点身份拒绝后没有回滚，监督会话被污染
  -> 后续自愈提交被拒绝，人工停止复用旧超时结果
  -> UI 显示“永久禁止再次开始、等待 Watchdog 接管”
```

综合判定如下：

1. **没有证据证明本次首先发生了真实液压失压。** 两次关键报警的压力分别为 `69.997 bar` 和 `70.566 bar`，均高于 `60 bar` 下限；失败项是样本年龄约 `1.1 s`，不是压力值不足。UI 追加“检查泄漏、制动液、泵输出”的提示会误导现场。
2. **实际触发源是 DAQ/主机时序空窗。** I0004 中 Dev1 从 `280 ms` 安全截止继续扩大到约 `1009.958 ms`；I0003 同期还出现两路程控电源遥测约 `2.05 s`。这支持“主机调度、驱动、阻塞 I/O 或线程池停顿”的共同上游问题，但仅靠本次封盘不能唯一判定是 NI 驱动、DPC、GC、磁盘还是串口调用。
3. **设备安全方向动作总体有效。** 关键故障时电机 OFF、整组电源 OFF、最终压力安全与持久化排空均有证据。真正失效的是“安全后如何恢复、如何交接、如何重试”的控制面，而不是程序完全没有执行断能。
4. **V2.13.0.35 将可恢复的时间异常放大成了不可恢复的进程级状态。** 具体包括旧遥测竞态、10 秒外层取消覆盖 60 秒恢复事务、`StartBlocked` 永久化、`Persistence=False` 触发全批撤权、恢复 owner 无终态、Watchdog 双重健康判定冲突、`RejectedNoWork` 后不回滚、耐久 marker 日志风暴和 StopSafety 超时缓存。
5. **截图中的 15:26“停止超时”不是本次点击真的等待了安全截止。** 同一 PID 在 `15:23:25.033` 已启动过一笔 StopSafety，`FreezeActiveWork` 的 2 秒阶段截止为 `15:23:27.033`，物质进展在 `15:23:27.041` 才到达，仅迟约 `7.965 ms`，却被永久缓存为超时。`15:26:09` 人工停止在约 `52 ms` 内直接取回旧结果，因此立即显示“超过安全截止”。
6. **V2.13.0.30 的长期运行证据真实，但不能解释为“所有异常都处理正确”。** 对照封盘有 675 个正式圈、两次管道写超时后继续、零 `TakeoverRequested`，现场截图累计约 `09D 22H 37M`；同时 V2.13.0.30 自身也出现过暂停后 DAQ 恢复转 `StartBlocked`、陈旧压力样本和停止/退出收口问题。它的优势是正常正式周期状态较简单、作用域正确，且短传输异常没有污染控制状态；不是所有边界都已经完善。
7. **V2.13.0.35 不是 V2.13.0.30 的线性后继。** 两条代码线在 `2.13.0.28` 后分叉；`2.13.0.30..2.13.0.35` 共 112 个文件、约 15,054 行新增和 785 行删除。因此不能用版本号大小推断 0.35 已包含 0.30 的全部稳定行为。
8. **V2.13.0.35 原实施记录明确是候选版。** 当时现场 100 轮组合故障为 `0/100`、8 小时长稳为 `0/8h`，且未生成正式包。本次窗口标题又明确显示 `PackageManifestMissing`、`PackageVerified=False`。该目录不应继续作为无人值守正式包使用。

发布判定：**V2.13.0.35 不具备无人值守继续放行条件。** 当前工作区已有的 V2.13.0.36 未提交改动可保留作为 I0003 的阶段性修复，但尚未覆盖本报告确认的 Watchdog Host、恢复 owner、液压陈旧样本、正式槽、StopSafety 缓存和日志失活问题，不能按“完整修复版”发布。

## 4. I0003：暂停后双 DAQ 恢复为何仍变成 StartBlocked

### 4.1 DAQ 和断能实际上已经恢复

Dev2 与 Dev1 的恢复证据分别为：

| 项目 | Dev2 | Dev1 |
| --- | ---: | ---: |
| 时钟模型失效 | 14:22:52.145 | 14:22:53.117 |
| 第一次读到“电源仍 ON” | 14:22:52.313 | 14:22:53.206 |
| 电源组实际 OFF | 14:22:52.317 | 14:22:53.245 |
| 旧读数与 OFF 收敛差 | 4 ms | 39 ms |
| 首批新鲜数据 | 14:22:53.531 | 14:22:54.370 |
| 持久化截止闭合 | 14:22:53.533 | 14:22:54.370 |
| 从恢复开始到新鲜数据 | 约 1.378 s | 约 1.253 s |

因此，DAQ 设备不是持续不可恢复，电源也不是持续无法关闭。第一处代码缺陷是：`TryEnsureDaqRecoveryGroupDeenergized` 在 Disable 动作刚发出时读取了运行态/遥测快照，并立即把旧 ON 状态解释成“禁止重建”；它没有等待同一 `CommandId/CorrelationId` 的 OFF 回执或有界状态收敛。

### 4.2 60 秒事务被 10 秒外层等待提前取消

恢复进度明确记录 `HardDeadlineMs=60000`，而 UI/协调屏障在约 10 秒时取消了等待。DAQ 已经有新鲜数据、压力复核和持久化边界，剩余失败项是暂停态的恢复终态/共同槽退出。较短的外围取消传播到内部，使通道落入：

```text
DaqRecoverySafeTerminal
  -> DaqRecoveryTerminalWithoutRejoin
  -> StartBlocked
```

这违背 V2.13.0.35 设计文档声明的 `HeldForManualPause`。问题不是没有定义该枚举，而是真实竞态下没有保证所有分支都只能从同一恢复事务提交这个终态。

### 4.3 “继续”不是一个原子事务

`14:23:25` 继续预检后，电源/恢复动作、执行许可、RunEpoch、Timer 创建和正式槽身份没有一次性提交。`14:23:26.202` EPB4 已经到 Timer 创建，却仍是 `StartBlocked`。随后 EPB11/12 以 `Slot=-1` 报正式槽安全失败，且日志里的 `MotorOff=True HydraulicReleased=True Persistence=True`。

“槽号不存在但三项安全证据全部成立”说明这是控制协议不变量失败。正确处理应是保持 OFF、撤销本次继续、恢复到可重试的 `Paused`，而不是把整个进程永久撤权。

### 4.4 该模式在同一累计日志中并非首次

同一封盘的累计日志在 `10:24` 已出现同类链：DAQ 很快恢复新鲜数据和持久化边界，随后 4/5 转 `StartBlocked`，再出现 `Slot=-1` 和整组关闭。`14:22` 是复发，不是一次孤立点击竞态。这也说明仅靠重启可以暂时恢复运行，却没有清除代码路径。

## 5. I0004：为什么“液压样本过期”最终杀掉了主进程

### 5.1 第一原因仍是 Dev1 DAQ 失鲜

`14:42:49.073` 的第一条安全事件为：

```text
DAQ_FRESHNESS_SAFETY_CUTOFF Device=Dev1 EPB=5
CallbackAge=280.0ms Action=MotorOffAndAbortCurrentCycle
```

到 `14:42:49.802`，Dev1 状态快照中的 CallbackAge 已扩大为 `1009.958 ms`；Dev2 同时只有约 `5.510 ms`。因此本轮主要是 Dev1 路径失鲜，不是两组液压同时物理掉压。

### 5.2 液压异常的故障码分类改对了，处置策略仍错

V2.13.0.35 已把异常码从笼统的 `HydraulicPressureLost` 改成 `HydraulicSampleStale`，这是正确改进；但后续仍把它当作正式圈不可恢复安全边界失败：

- 实际压力 `69.997 bar`；
- 最低压力 `60.000 bar`；
- 样本年龄 `1128.6 ms`；
- 电机 OFF 已确认；
- 液压 lease 最终已释放。

正确语义应是“不能用旧样本证明当前压力”，先保持输出 OFF，并把它与同一 Dev1 callback gap 合并为一个 DAQ 时间事故。当前实现却同时：

1. 让 EPB4 进入隔离软件恢复；
2. 让 EPB5 正式圈 finalizer 以 `Persistence=False` 报 `FormalSlotSafetyBoundaryFailed`；
3. 撤销整批执行授权并启动 StopAll；
4. UI 又追加“压力不足、检查泄漏”的物理故障提示。

这把一个共同上游时间空窗分裂成“DAQ 故障、液压故障、正式槽故障”三个事故，导致重复 owner、重复断能和错误升级。

### 5.3 `Persistence=False` 不应自动等于物理安全失败

EPB5 在 `Slot=59` 的终态为：

```text
MotorOff=True HydraulicReleased=True Persistence=False
```

这说明物理动作已经安全结束，但本圈没有形成耐久成功记录。正确做法应是把该圈原子标记为 `Aborted/Invalid`、关闭持久化 attempt、在未来完整圈重试；只有“无法证明是否已经写入半条正式圈”或数据库边界不可封闭时，才需要整批停止。

当前代码把任何非报警通道的 `Persistence=False` 都直接调用 `ReportFormalSlotSafetyBoundaryFailure`，安全上偏保守，但可用性上把可封圈的软件异常升级成不可逆全局故障。

### 5.4 StopAll 为什么无法自行结束

StopAll 在 `ClearRecoveryOwners` 看到：

```text
IsolatedInfrastructureRecovery[WorkerCompletedWithoutTerminal;EPB=4/5]
ExternalRecoveryEmergencyPowerOff[WorkerRunning]
```

`RecoveryTaskRegistry.DrainThroughEpochAsync` 对 `WorkerCompletedWithoutTerminal` 的实现是立即返回失败；它不会把“Task 已完成但 owner 漏报终态”自动对账成异常终态，也不会移除残留 lease。于是账面残留直接阻断 StopSafety。

Sidecar 随后以该 StopSafety 阶段失败为理由：

- `14:43:06` 抓取 PID 12968 Dump；
- 终止旧进程；
- 退避 15 秒；
- `14:43:21` 拉起 PID 21080；
- `14:43:26` 完成安全预检并继续恢复。

Sidecar 这次跨进程恢复流程本身执行成功，但根因是主进程的恢复 owner 协议残留，而不是设备仍处于危险输出。

## 6. I0005：恢复后为什么 Watchdog 和人工停止都不能自收口

### 6.1 普通诊断日志在恢复中途失活

I0004 中：

- `warning.log` 到 `14:43:23`；

### 6.4 `RejectedNoWork` 保护了进程，却没有恢复监督状态

检查点身份已变化时拒绝发放重启许可是正确的；它避免了 Sidecar 在没有一致恢复事实时杀掉仍活着的 PID 21080。但当前状态机只“停止继续杀进程”，没有：

所以 `15:22:56` UI 已显示 EPB5 恢复运行，而 Sidecar 在 `15:22:50～58` 仍产生 35 条 `RecoveryBatchCommitRejected`。主程序能自愈，监督控制面却不再接受自愈结果。

### 8.2 它在正常路径上的优势

1. V2.13.0.30 的正式槽退休只作用于当时已存在的槽，没有跨未来槽缓存旧退休证据，正常正式参与者作用域更简单。

### 8.3 V2.13.0.30 并不是把本次所有问题都处理好了

源码和历史封盘同时表明：

- `RecoveryTaskRegistry.DrainThroughEpochAsync` 在 V2.13.0.30 与 V2.13.0.35 之间没有差异；`WorkerCompletedWithoutTerminal` 缺陷是共同的潜伏问题。
- StopSafety 的“超时后缓存进程终生结果”语义在 V2.13.0.30 已存在；V2.13.0.35 主要增加事务身份字段，没有消除缓存问题。
- V2.13.0.30 的历史现场数据在人工暂停后也发生过“DAQ 已恢复但仍等待运行态重入，约 10 秒后转 StartBlocked”。
- V2.13.0.30 也有 `HydraulicPressureLost` 实际约 70 bar、失败仅因样本年龄约 1.12 s 的记录。
- V2.13.0.30 两次管道写超时中还出现过一次已关闭管道的 `UnobservedTaskException`。

因此更准确的回答是：

> V2.13.0.30 能长期运行，主要因为正常正式调度作用域正确、状态较少，而且当次长跑没有同时击中 DAQ 空窗、恢复 owner 残留、Watchdog 错误接管和 StopSafety 缓存这组复合条件；不是因为它已经完整实现了本次异常的自维护。

### 8.4 为什么 V2.13.0.35 反而更突出

两条源码线的共同祖先是 `9d9a175`（tag `2.13.0.28`）：

```text
  755ce0f  暂停恢复、报警重学习与正式周期收口

  24f7d68  正式参与者代次和 Watchdog 交接
  9b2c050  暂停停止与 Watchdog 恢复所有权

```

`git diff 2.13.0.30..2.13.0.35` 为 112 个文件、15,054 行新增、785 行删除。新版本加入了更多正确但互相耦合的安全门：精确暂停身份、正式参与者代次、恢复 batch commit、耐久 permit、closing tombstone、UI liveness probe、StopSafety 身份等。问题在于这些门没有由一个统一事故/代次状态机协调：

- 一个门看到 UI 响应，另一个门仍看到逻辑源 stale；
- 一个门看到新 Run 已提交，另一个门仍拿旧 checkpoint generation；
- 一个门看到电源命令已执行，另一个门先读到旧 ON；
- 一个门看到 DAQ 已恢复，另一个 10 秒等待先取消；
- 一个门看到物理 OFF/液压已安全，正式槽因 persistence 未提交仍全局撤权；
- 一个门拒绝无工作重启，却没有把原进程恢复为活动 authority。

安全检查数量增加了，但“安全事实、恢复事实、监督事实”没有原子一致性，所以新版本更容易把短时异常锁成永久失败。

## 9. 为什么 637/637 自动化通过仍没有发现

V2.13.0.35 的实施文档已经诚实注明：本机测试通过，但真实 NI/CAN/电源/液压 100 轮组合与 8 小时长稳未执行。现有测试主要覆盖单个 seam 和预期顺序，没有覆盖以下真实组合：

1. Disable 指令后 4～39 ms 才形成 OFF 记录，而调用方先读旧 ON；
2. DAQ 在 1.3 秒内恢复，但外围 10 秒屏障仍等待错误的运行态重入；
3. 压力值健康、压力时间证据陈旧、正式圈 persistence 未提交同时发生；
4. 恢复 worker Task 已完成但漏掉 terminal，另一个 emergency worker 仍运行；
5. UI 探针响应、Sidecar 主动退休连接、重连失败、逻辑源 8.3 秒 stale、随后重连成功；
6. Takeover 已开始，但 durable checkpoint 在许可前改变身份；
7. `RejectedNoWork` 后原 PID 继续运行并再次进行进程内自愈；
8. marker 上下文缺失持续 20 分钟，验证日志速率和资源趋势；
9. 前一 StopSafety 在第一阶段仅迟 8 ms 超时，再点击人工停止；
10. 恢复后 run/error/warning sink 停止写入而 UI/Journal 继续。

单元测试证明各零件在孤立输入下能工作；本次现场证明组合状态和跨进程代次仍没有被端到端验证。

## 10. 完整解决方案

“完整解决”应定义为：关闭本次全部已确认软件因果链，并通过同类硬件故障注入与阶梯长稳；不是简单放大超时、重启进程或隐藏报警。

### 10.1 立即现场处置

1. 停止使用现有 V2.13.0.35 作为无人值守正式版本；不要增加重启次数继续消耗试件。
2. 若必须恢复生产连续性，可**整体**回退到已封存验证的 V2.13.0.30 完整目录及匹配配置，禁止只替换 `MTTFTest.exe` 或混用 V0.35 的 Host/Client/Protocol DLL。
3. 回退只作为有人值守的临时风险控制。V2.13.0.30 有已知暂停恢复和退出缺陷，暂停/继续、DAQ 空窗及 Watchdog 断线仍需人工监控。
4. 不得关闭 Watchdog、删除物理 OFF 门禁、把 250 ms DAQ 截止无依据地放大，或在 `StartBlocked` 后连续点击继续。
5. 完整保留 I0003～I0005、两份 Dump、V0.30 对照目录和当前包哈希；后续候选使用新数据目录，禁止混写这些证据。

### 10.2 用统一的恢复事故事务取代多个松散布尔量

建立不可变 `RecoveryIncident`：

```text
IncidentId
+ RunId / RunEpoch
+ SourceDevice / AffectedChannels / PowerGroups / HydraulicGroups
+ TriggerKind / TriggerMonotonicTimestamp
+ SafetyOffReceiptSet
+ DaqGeneration / RecoveryGeneration
+ PauseLease（可空）
+ PersistenceBoundary
+ RecoveryDeadline
+ TerminalDisposition
```

状态只能单调迁移：

```text
Detected
  -> SafetyOffSubmitting
  -> SafetyOffConfirmed
  -> DaqRebuilding
  -> FreshnessConfirmed
  -> PersistenceClosed
  -> HeldForManualPause | RejoinedRunning | SafeIdleFault | Superseded
```

DAQ callback gap、`HydraulicSampleStale` 和同时间窗内的电源遥测迟缓必须合并成同一 IncidentId，不能各自创建恢复 owner 和 StopAll。

### 10.3 引入强类型、可验证的 OFF receipt

不能把“Disable Task 返回”“状态字典为 OFF”“电流代理清零”混成一个布尔量。建议定义：

```text
SafetyOffReceipt
  CommandId / CorrelationId
  TargetKind / TargetId
  SubmittedUtc / CompletedUtc
  DriverWriteSucceeded
  DeviceAckReceived
  RuntimeStateObservedOff
  ElectricalProxyObservedOff
  EvidenceGeneration
```

规则：

1. DO OFF 和 PSU Disable 必须先提交，且不受调用方取消阻断。
2. 刚提交后读到旧 ON 时，在单调时钟下等待同一命令的回执和状态收敛，不立即判失败。
3. `Task completed` 只能证明调用完成，不能单独伪造物理 OFF；至少要有设备回执、运行态精确写序列或电流代理中的一项可信证据。
4. 超时后迟到成功必须能被同一 Incident 消费，不能继续沿用早先的 false。
5. 所有证据绑定 generation；旧命令的迟到回执不能放行新代次上电。

### 10.4 统一恢复期限，禁止短外层取消覆盖长事务

1. 一个 Incident 只有一个总硬截止，例如 60 秒；子阶段截止只用于诊断和进入安全 idle，不得取消仍在推进的总事务。
2. 使用“无物质进展窗口”代替多个互相冲突的绝对超时。只要收到新 OFF receipt、新鲜批次、压力复核或持久化边界，进展时钟就更新。
3. 精确人工暂停存在时，恢复终态必须是 `HeldForManualPause`，不进入运行态共同槽。
4. 到总截止仍无法恢复时，保持 OFF、发布一个结构化 `SafeIdleFault`；不得先写 `StartBlocked`，再让继续按钮触发更多失败。
5. “继续”应先在锁内原子完成：新 RunEpoch/Permit、DAQ generation、压力资格、持久化边界、正式参与者 lease、Timer/Runner 预留；全部成功后才允许任何电源 ON。

### 10.5 正式圈失败分离“物理不安全”和“本圈无效”

正式槽终态至少分三类：

| 分类 | 条件 | 处理 |
| --- | --- | --- |
| SafeCommitted | OFF、液压释放、正式圈耐久提交均完成 | 正常进入下一槽 |
| SafeAborted | OFF、液压释放完成；本圈因 DAQ/软件异常未提交 | 原子写作废/无效边界，未来完整圈重试，不全批撤权 |
| SafetyUnproven | OFF 或液压释放无法证明，或持久化无法判断是否半提交 | 全批安全停止并交接 Watchdog |

`Slot=-1` 不得进入正式终态提交；它只能记录 `FormalLeaseMissing` 并保持 OFF。若三个安全布尔量都为 True，禁止再发布 `FormalSlotSafetyBoundaryFailed`。

### 10.6 RecoveryTaskRegistry 必须保证每个 worker 有唯一终态

1. 每个 lease 由 `try/finally` 或 `IAsyncDisposable` 自动发布 `Completed/Failed/Cancelled/Superseded`，业务代码不能遗漏。
2. worker Task 完成回调与 registry 绑定；若业务未报 terminal，registry 自动发布 `WorkerCompletedUnexpectedly` 并移除活动 owner，而不是永久残留。
3. StopAll 可以用更高代次 `SupersedeThroughEpoch` 隔离旧 owner。账面 residue 不得阻止电机 OFF、电源 Disable 和液压释放。
4. 仍在运行且不可取消的旧 worker 进入 quarantine；所有晚到写操作受 generation/permit 栅栏拒绝。
5. `ClearRecoveryOwners` 失败应携带 owner、Task 状态、最后进展和 quarantine 结果，不能只输出拼接字符串。

### 10.7 Watchdog 健康判定必须共用一个结论

至少分离并统一以下信号：

- TransportHealth：管道、ACK、发送队列；
- ApplicationLiveness：PID/start ticks、WinForms UI 探针；
- ControlProgress：正式机械进展、StopSafety 物质进展；
- PhysicalSafety：带电、OFF 回执、液压与持久化边界。

策略：

1. PID 存活且 UI 响应时，心跳/逻辑源 stale 只能进入 `TransportRepair`，不得发起进程接管。
2. UI 响应触发连接退休后，必须给予新连接独立 grace；不能用旧 logical-source 时间戳立即接管。
3. 同 authority 重连并收到新心跳时，原 takeover generation 必须原子取消；已安排的 Dump/kill/permit 任务检查 generation 后退出。
4. 只有 PID 退出、UI 连续多次无响应，或 PhysicalSafety/StopSafety 到真实硬截止时，才能接管。
5. ControlProgress stalled 可以请求主程序安全停机；但 UI/进程响应时应先使用精确 StopAll 回执，不能直接等 15 秒后杀进程。
6. 所有接管原因必须记录参与决策的四类信号，避免以后仅凭一条 stale 文本推断。

### 10.8 Takeover/Permit 必须支持无损回滚

建议状态机：

```text
Active
  -> Suspect
  -> TakeoverPending
  -> PermitApproved
  -> OldProcessTerminating
  -> Relaunched
  -> RecoveryCommitted

任一阶段若确认原 PID 健康且无可消费工作：
  -> TakeoverCancelled
  -> Active（同 authority，新 generation）
```

`DurableCheckpointIdentityChanged` 不是 `UnhandledSoftwareStartup`：

- 若原进程仍活着，取消 takeover、重新快照当前 Run/checkpoint 并恢复 Attached；
- 若原进程已退出，按新 checkpoint 决定是否有工作；没有工作则形成干净终态，不污染下次 Session；
- `RejectedNoWork` 必须清理 takeover root、permit、failure fingerprint 和旧恢复上下文；
- 后续进程内 `RecoveryBatchCommitted` 必须能被新 authority 接受。

### 10.9 恢复 marker 必须一次消费并限频

1. marker 包含完整 `SessionId + RunId + RunEpoch + RecoveryStage + Generation + Hash`，不能只存 generation。
2. Sidecar 对每个 marker 只处理一次；结果为 Accepted、Rejected 或 Deferred-with-next-retry。
3. `ContextMissing` 使用指数退避，例如 1、2、4、8、30、60 秒；同 fingerprint 每分钟最多一条汇总日志。
4. 新 Run commit 成功后原子更新 `LastRecoveryBatchCommitGeneration` 并删除/归档旧 marker。
5. journal 记录累计次数和首次/最后时间，不再每 250 ms 写一条大 JSON。

### 10.10 StopSafety 分离“物理安全核心”和“本次调用回执”

1. 物理安全动作保持 single-flight，但每次 ManualUi/Watchdog/系统故障调用获得独立 `StopRequestReceipt` 和真实开始时间。
2. 前一 core 超时后进入 quarantine，不允许迟到代码重新上电；但新的人工停止仍可重新发出幂等 OFF/Disable/释放/排空动作。
3. 不得因 `_cachedTerminalResult` 存在就让新请求零耗时返回旧超时。历史结果仅作为 `PreviousIncident` 审计字段。
4. 2 秒 `FreezeActiveWork` 应先提交所有安全方向命令，再等待逻辑冻结；阶段晚 8 ms 但物质进展已到时，不应永久毒化进程。
5. UI 的“超过安全截止”必须由本次请求的单调 elapsed 和当前 deadline 计算，并显示具体阶段、当前物理证据和是否已安全。
6. 物理 OFF、液压安全、持久化排空已完成时，即使逻辑 owner 仍在 quarantine，也应显示“设备已安全，后台收口异常”，并允许有界退出；不能继续显示“等待安全接管”。

### 10.11 日志管线成为被监督资源

1. run/error/warning 每个 sink 维护最后成功写入序号和心跳。
2. 运行中超过 5 秒无日志 sink 进展且 UI/Journal 仍活动时，产生独立 `DiagnosticSinkStalled`，切换到 emergency spool。
3. 进程恢复后重新打开文件，验证目录、句柄、编码和滚动状态；失败不能静默。
4. Watchdog Journal 的重复事件必须聚合，日志压力本身不得挤占控制线程。
5. 封盘脚本校验“活动运行期间普通日志最后时间不得早于 checkpoint/Journal 超过允许窗口”。

### 10.12 发布包身份成为硬门禁

正式候选必须包含并校验：

- Git commit、dirty 状态、BuildUtc；
- 主程序、Sidecar、Client、Protocol、Controller、配置文件逐项 SHA-256；
- 完整 PackageManifest；
- `PackageVerified=True`；
- 主辅组件统一版本；
- 禁止从 `D:\debug\...` 开发输出目录直接作为现场正式包。

当前工作区已有 V2.13.0.36 部分实现。它没有直接修改 `MTTFTest.Watchdog/WatchdogHost.cs`、`Controller/RecoveryTaskRegistry.cs`、`Controller/HydraulicGroupCoordinator.cs`、`Controller/EpbManager.BatchStart.cs`、`Controller/FormalBatchSlotCoordinator.cs` 和 `Controller/StopSafetyTransactionRunner.cs`，也没有本报告 R4～R10 的组合故障验收证据，因此不能视为已覆盖这些根因。建议最终候选使用新的明确版本号（例如 V2.13.0.37）；若 V2.13.0.36 从未出包，也可在全部 P0 合并且重新完成整套验收后再统一定号，禁止复用已经流转过的同号二进制。

## 11. 推荐实施顺序

每一步独立提交和回归，禁止再把控制器、Watchdog、UI、版本号和文档混成一个大提交：

1. `test(recovery): 复现I0003双DAQ暂停恢复与OFF回读竞态`

3. `test(control): 复现健康压力陈旧样本与SafeAborted正式圈`
4. `fix(control): 分离时间证据故障、正式圈作废和物理安全失败`

6. `fix(recovery): 自动终结恢复lease并隔离迟到worker`
7. `test(watchdog): 复现响应式UI连接退休后逻辑源误接管`

9. `test(watchdog): 复现checkpoint身份变化与marker风暴`

基线策略建议：以 V2.13.0.30 的正常正式周期作为差分 oracle，而不是把 V2.13.0.30 整体当成最终源码。可在干净修复分支中逐项移植已经证明必要的安全能力；每移植一个子系统，都必须证明相同正常输入下正式圈顺序、机械计数和持久化边界不劣于 V2.13.0.30。

### 12.3 上游 DAQ/主机空窗专项取证

为了最终定位 R1，候选长稳期间同步采集：

- Windows WPR/ETW：CPU、CSwitch、DPC/ISR、Disk I/O、File I/O、.NET GC/ThreadPool；
- NI-DAQmx 驱动日志、任务状态、设备错误、回调线程和实际采样时钟；

- Windows Time-Service 和系统/应用事件；
- 控制线程、日志线程、Watchdog writer、DAQ callback 的单调时钟延迟。

## 13. 长稳与正式放行门禁

按同一受控包、同一配置、独立数据目录逐级晋级：

1. 2 小时功能观察：完成全部 T01～T14 定向注入；
2. 8 小时组合注入：至少 100 轮暂停/继续、停止/再开始及真实 Sidecar 接管；
3. 24 小时连续长稳：四通道正式圈持续推进，无人工干预；
4. 72 小时注入长稳：定时执行 DAQ 空窗、管道断连、日志 I/O 延迟和 checkpoint 竞态；
5. 7 天无人值守长稳：保持正式负载，验证资源趋势和恢复次数。

必须同时满足：

- 非预期 `TakeoverRequested=0`；
- UI 响应时接管次数 `=0`；
- `WorkerCompletedWithoutTerminal=0`；
- `RecoveryBatchCommitDeferred ContextMissing` 无热循环，单 fingerprint 不高于 1 条/分钟；
- `RecoveryBatchCommitRejected` 只出现在测试预期身份冲突，且随后有明确终态；
- `FormalSlotSafetyBoundaryFailed Slot=-1=0`；
- 健康压力陈旧样本不产生 `HydraulicPressureBelowMinimum`；
- 每个 Stop 请求都有独立 started/deadline/result，人工停止不复用旧 elapsed；
- 普通日志、Journal、checkpoint 时间连续，无静默 sink；
- 所有启用通道机械计数、正式圈记录、数据库边界一致；
- 进程、句柄、线程、日志容量无持续增长；
- `PackageVerified=True`，现场哈希与验收记录一致。

任一级失败都回到代码/测试阶段；禁止只通过增加超时、减少日志或提高重启上限继续晋级。

## 14. 最终建议

短期最稳妥的运营方案是：停用当前 V2.13.0.35 无人值守包，必要时整体回退已封存的 V2.13.0.30，并将其明确标为“有人值守临时基线”。

永久方案不是单点修复某一条异常文本，而是统一五个事务边界：

1. 安全 OFF 的可验证回执；
2. DAQ/液压/持久化共用的恢复 Incident；
3. 正式圈 SafeCommitted/SafeAborted/SafetyUnproven 三分法；
4. Watchdog 健康、接管、NoWork 与 marker 的可回滚代次；
5. StopSafety 当前请求与历史事故分离。

V2.13.0.30 应作为正常正式周期的差分行为基线；V2.13.0.31～0.35 中有价值的安全能力应按子系统、带故障注入逐项前移，不能再次整体叠加。完成本报告 P0、100 轮硬件组合、24/72 小时和 7 天长稳、并生成受控 manifest 之前，不应再宣称“问题已经完美解决”或批准无人值守正式运行。
