## 1. 技术结论

### 1.1 一句话结论

本次不是 EPB4、EPB5 卡钳硬件同时损坏，也不是实际液压压力不足；直接起点是 **Dev1 DAQ 采集回调失去新鲜度**，随后 Dev1、Dev2 同时出现约 **2.983 秒回调空窗**，Dev1 最终报出 NI-DAQmx `-200279`（应用未及时读取导致硬件采集缓冲区溢出）。旧压力值虽然仍高于最低压力，却因样本年龄超过 1.1 秒被安全逻辑正确拒绝使用，EPB4/5 因共享液压组和 Dev1 采集链被联动安全停止。

事故被放大的原因不是单点，而是四个软件闭环同时存在缺口：

1. DAQ 连续采集没有配置足以覆盖调度抖动的输入缓冲区，且下一次异步读取要等当前回调完成业务入队后才重新挂起；约 3 秒的回调调度停顿直接变成缓冲区溢出。
2. 同一根故障被拆成多个通道、液压组、电源组和周期屏障故障，13 秒内产生 423 条运行事件，并重复发起暂停、OFF、封圈和 StopAll；持久化终态发生竞态，EPB4、EPB9 各残留一条 `running` 记录。
3. 主程序的业务/控制心跳在 19:10:02 停止更新，但 Win32 窗口仍能响应 `WM_NULL`。Watchdog 因此把进程判为“界面响应”，只发了控制修复请求，没有在有界期限后升级为接管，故障状态持续到 19:38 人工强杀。
4. 强杀后 Watchdog 已证明旧进程精确退出，却又强制要求由旧主程序写出的 `ClosingTombstone`。强杀进程天然无法补写该凭据，因此恢复在第一次尝试、尚未生成 `LaunchIntent` 前就永久阻断。

此外，现场运行的是 `PackageNotApproved / DIRTY_CANDIDATE_NOT_FOR_PRODUCTION` 包，且 V2.13.0.42 的遗留 Watchdog 与 V2.13.0.43 Watchdog 同时运行。这两项不是本次 DAQ 溢出的直接根因，但属于必须随本次一起关闭的发布与生命周期缺陷。

### 1.2 对现场问题的直接回答

| 现场问题 | 结论 |
|---|---|
| EPB4、EPB5 为什么同时异常 | 两者同属液压组 1，并依赖 Dev1 采集链。Dev1 样本陈旧后，组级安全策略同时停止 4、5；不是两只卡钳独立同时坏。 |
| 压力是否真的不足 | 否。液压组 1 旧值为 70.410 bar，最低要求 60.000 bar；液压组 2 旧值为 39.704 bar，最低要求 30.000 bar。失败原因是 `StaleSample`，不是 `BelowMinimum`。 |
| EPB4 为什么显示“系统故障” | EPB4 的周期终态未持久化闭合，`Persistence=False` 触发 `FormalSlotSafetyBoundaryFailed`，源码明确将该通道发布为 `SystemFault` 并撤销整批授权。 |
| EPB5 为什么显示“启动受阻” | EPB5 同圈已封存为 `AbortedBySoftwareRecovery`，但整批执行授权已被 EPB4 的持久化边界失败永久撤销，清理后的终态因此表现为 `StartBlocked`。两种颜色是恢复阶段差异，不是两种硬件故障。 |
| 为什么信息框提示“压力不足” | UI 文案映射只识别 `PressureSample`/`NoPressureSample`，没有识别实际故障码 `HydraulicSampleStale`，错误落入“压力不足”的默认提示。 |
| 是否为整机资源耗尽 | 否。事故后进程 CPU、系统 CPU、内存、磁盘队列都很低，HOST 探针和部分 DAQ 后台线程仍运行；这是采集完成调度、控制事务和业务界面的逻辑失活，不是整机满载。 |
| 为什么 Watchdog 没及时处理 | Watchdog 把“窗口消息能响应”当成了禁止接管的依据，业务心跳陈旧时只请求 StopAll，没有控制修复硬期限后的升级接管。 |
| 为什么强杀后没有自动拉起 | 强杀后缺少只能由旧主程序生成的 `ClosingTombstone`，Watchdog 把它判为永久安全前置条件缺失，在第一次恢复尝试即打开熔断。 |

### 1.3 当前处置结论

- V2.13.0.43 当前现场包不应继续用于无人值守正式试验。
- EPB4/5 应按“采集基础设施故障引起的安全停机”处理，现有证据不足以判定卡钳硬件故障。
- 事故圈不得计入正式完成数；EPB4、EPB9 两条开放周期必须通过受审计的数据修复工具闭合，禁止手工删除 SQLite 行。
- 未完成本文 P0 整改与验证前，不得通过放宽 250 ms 新鲜度阈值、屏蔽 4/5 报警或忽略 Watchdog 凭据来恢复生产。

### 2.3 DAQ 直接故障证据

事故前 19:10:01，两台 DAQ 的处理队列均为空，持久化状态为 `Recovered`，控制处理耗时低于 0.1 ms。这排除了“后台落盘队列逐渐堆满”作为直接起点。

事故中出现了三组相互印证的数据：

1. Dev1、Dev2 的回调同时停顿约 2.983 秒，而期望批间隔只有 10 ms（20 点、2 kHz）。
2. Dev1 最终报告 NI-DAQmx 状态码 `-200279`，明确指出应用没有及时读取采集数据。
3. 源码连续采集只把 `_samplesPerChannel` 传入 `ConfigureSampleClock`，事故配置为 20 点；显式输入缓冲区配置仍被注释。参见 [TwoDeviceAiAcquirer.cs](../../IO.NI/TwoDeviceAiAcquirer.cs#L5077)。

当前回调路径还存在结构性暴露窗口：`EndReadMultiSample` 后，要完成快照计算、控制环入队、后台处理入队，最后才调用下一次 `BeginReadMultiSample`。参见 [TwoDeviceAiAcquirer.cs](../../IO.NI/TwoDeviceAiAcquirer.cs#L3208)。只要 NI/.NET 完成回调约数秒得不到调度，硬件继续采样而应用没有保持足够的缓冲储备，便会出现本次溢出。

同日 15:51 的前序 RunId 中，两台 DAQ 已分别记录约 1899.6 ms、1899.9 ms 的历史回调空窗；当前 RunId 在事故前也已有 Dev1 9 次、Dev2 7 次回调空窗记录。因此这不是一次孤立的传感器毛刺，而是持续存在的采集调度裕量不足。

### 2.4 为什么高度怀疑共享异步完成调度停顿

以下现象同时成立：

- Dev1 和 Dev2 的 NI 异步回调几乎同相停顿；
- PSU2、PSU3、PSU4 的 SCPI 异步响应/续体在同一窗口出现 1.8～2.0 秒延迟；
- 独立 HOST 探针仍每秒运行，WinForms UI 定时器仍运行到 19:10:11，Windows 消息探针可应答；
- 进程 CPU、系统 CPU、内存和磁盘队列都不高；
- 多通道在同一正式槽错相启动，应用大量使用 `Task.Run`、异步续体和若干同步等待路径，但没有进程级 ThreadPool 最低线程保护或事故时线程转储。

这组特征最符合 **共享 CLR 异步完成调度/ThreadPool 短时饥饿，或 NI 完成回调调度层同时停顿**。但封盘没有保存 19:10 的线程栈、ThreadPool 可用线程快照、GC ETW 或 DAQ 当前事故重证据，因此本文将其标为“高置信推断”，不把两种可能强行二选一。

整改目标不依赖该二选一结果：DAQ 读取改成每设备独立的专用采集线程、显式大缓冲、回调/读取路径只做 O(1) 所有权转移，即可同时消除 ThreadPool 饥饿和业务回调过重对采集连续性的影响；新增转储和 ETW 后再精确消灭最初的线程占用者。

### 2.5 EPB4/5 并非卡钳硬件故障

EPB4、EPB5 的共同点是液压组 1 和 Dev1 采集链，而不是共同卡钳硬件：

- 19:10:01.067 液压组 1 已稳定合格，实际 70.981 bar；
- 19:10:03.167 被拒绝的旧样本仍为 70.410 bar，高于最低 60 bar；
- 故障码为 `HydraulicSampleStale`，源码也把它与 `HydraulicPressureBelowMinimum` 明确分开。参见 [HydraulicGroupCoordinator.cs](../../Controller/HydraulicGroupCoordinator.cs#L393)；
- EPB4/5 的 DO 高优先级关闭均成功，电流代理确认也通过；
- EPB5 的事故圈已经封存为 `AbortedBySoftwareRecovery`，EPB4 的问题是终态持久化未闭合。

UI 的“压力不足”提示来自错误的字符串分支：`GetHydraulicFaultHint` 没有识别 `HydraulicSampleStale`，落入默认提示。参见 [FrmEpbMainMonitor.PowerSupply.cs](../../MTTfTest/FrmEpbMainMonitor.PowerSupply.cs#L831)。这会误导现场去检查制动液和卡钳，应作为 P0 文案修复。

### 2.6 持久化边界存在语义竞态

`index.db` 物理结构完整，但当前事故的 7 条周期记录显示：

| EPB | 周期 | 终态 | 说明 |
|---:|---:|---|---|
| 4 | 5557 | `running` | `end_time` 比 `start_time` 早 27.681 ms，终态未闭合 |
| 5 | 5557 | `AbortedBySoftwareRecovery` | 已安全封存 |
| 7 | 5374 | `failed` | 软件恢复链失败 |
| 8 | 5406 | `AbortedBySoftwareRecovery` | 已安全封存 |
| 9 | 5406 | `running` | `end_time` 比 `start_time` 早 19.562 ms，终态未闭合 |
| 11 | 5406 | `AbortedBySoftwareRecovery` | 已安全封存 |
| 12 | 5406 | `AbortedBySoftwareRecovery` | 已安全封存 |

全库只有两条 `running`，正是 EPB4 和 EPB9 事故圈。说明“周期开始记录”和“迟到关闭/作废回调”之间存在顺序竞态，`end_time` 可先于正式 `start_time` 提交，随后状态仍回到或保留为 `running`。

与此同时，19:10:12 的恢复检查点写着 `PersistenceDrained=True`。这只能证明队列已排空，**不能证明当前 RunId 的所有周期都已有耐久终态**。恢复门禁把“队列空”误当成“业务语义闭合”，必须修正。

源码在每个通道发现 `Persistence=False` 时都会调用 `ReportFormalSlotSafetyBoundaryFailure`，并各自异步发起 `StopAllAsync`。参见 [EpbManager.BatchStart.cs](../../Controller/EpbManager.BatchStart.cs#L3822)。这解释了同一槽内多通道同时失败时的重复 StopAll 和事件扇出。

### 2.7 故障风暴与界面“卡顿”的真实性质

19:10:00～19:10:12 共记录 423 条运行事件，峰值为 19:10:07 单秒 164 条，其中：

- 50 条“定时器已暂停”；
- 30 条“已有同方向 OFF 在执行”；
- 40 条包含 `OutputOffCommandFailed`；
- 21 条包含 `FormalSlotSafetyBoundaryFailed`；
- 20 条包含 `ExternalRecoveryRequired`。

日志适配器本身已经直接写入并发队列，没有为每条日志 `BeginInvoke`，这部分设计是正确的。工程值绘图也已有 latest-only 合并。然而，通道运行态、告警覆盖层、电源遥测和安全状态仍存在逐事件 `BeginInvoke` 路径，例如 [FrmEpbMainMonitor.PowerSupply.cs](../../MTTfTest/FrmEpbMainMonitor.PowerSupply.cs#L310) 与 [FrmEpbMainMonitor.PowerSupply.cs](../../MTTfTest/FrmEpbMainMonitor.PowerSupply.cs#L870)。故障风暴会同时制造控制任务、持久化终态任务和 UI 投递。

证据不支持“整个进程死锁”：

- UI 指标在 19:10:11.768 仍完成一次批量刷新；
- Watchdog 在 19:10:14.760 收到 `WmNullAcknowledged`；
- HOST 探针、部分 DAQ 回调和日志一直运行到 19:38；
- 强杀前系统 CPU、进程 CPU 和磁盘队列都很低。

更准确的定义是：**采集/控制业务心跳停止推进，故障事务和 UI 状态投递发生扇出，窗口消息泵仍能偶尔响应，但业务界面严重滞后且无法完成控制闭环。** 现场看到的“其余 EPB 仍运行”不应当被解释为后台真的健康运行，很可能只是最后一次成功投影。

### 2.8 Watchdog 在强杀前的逻辑活性缺口

当前 Watchdog 把接管确认条件限定为“进程退出”或“心跳失效且 UI 探针也确认不响应”。源码中的 `applicationTakeoverConfirmed` 明确只包含这两种情况；随后通道监督失败、逻辑残留和正式进度停顿也必须与它组合后才允许接管。参见 [WatchdogHost.cs](../../MTTFTest.Watchdog/WatchdogHost.cs#L2114)。

本次业务心跳自 19:10:02.401 后不再更新，但 UI 的 `WM_NULL` 仍可应答，于是：

1. Watchdog 反复退役并重连管道；
2. 19:10:12、19:10:19 两次请求 `ResponsiveApplicationControlRepair`；
3. 主程序没有发布新的 StopAll 事务或业务心跳；
4. Watchdog 没有“控制修复请求后 N 秒无进展则接管”的硬期限；
5. 直到 19:38 人工强杀前，没有自动接管。

这说明“进程活着”“窗口能响应”“控制业务健康”三个概念被错误合并。无人值守系统必须分别监督。

### 2.9 强杀后的恢复凭据形成逻辑死结

强杀后，Watchdog 已成功写入：

```text
Exact old process exit proven
```

但在进入安全代理和生成拉起意图之前，`AwaitSafetyHandoffBeforeRelaunchAsync` 先读取主程序 `ClosingTombstone`；文件不存在、schema 不足、许可不匹配中的任一情况都会立即返回 `MissingOrCorrupt`。参见 [WatchdogHost.cs](../../MTTFTest.Watchdog/WatchdogHost.cs#L2969)。

本次事务因此停在：

```text
RecoverySafetyPrerequisiteBlocked
Outcome=MissingOrCorrupt
Detail=ClosingTombstoneMissingCorruptOrPermitMismatch
ConsecutiveFailures=1
CircuitOpen=true
LaunchIntent=null
```

这不是“重试 8 次都失败”，而是第一次尝试就被设计成永久阻断。强杀/崩溃场景中，旧主程序不可能再写关闭墓碑，所以这是恢复协议的必然死结。

## 3. 范围、数据和定义

### 3.1 纳入分析的数据

- I0010 封盘中的 `log/run.log`、`error.log`、`warning.log`、`ui-info.log`；
- `index.db` 及其业务终态；
- `Recovery/unattended-run-checkpoint.json(.bak)` 与审计日志；
- 当前和遗留 `WatchdogSessions` 会话、许可、replacement、client/sidecar 事件；
- `Config/runtime-build-identity.json`；
- `IncidentSnapshots`、`WarningSnapshots` 与电源遥测；
- 5 张现场截图；
- 当前仓库 V2.13.0.43 对应 DAQ、控制、UI、持久化、Watchdog 源码。

### 3.2 术语

- **样本陈旧**：最后可用 DAQ 工程值的单调时间年龄超过安全阈值；不等于数值本身越限。
- **物理安全**：DO 已关闭、电源已 OFF、液压已释放，并由新鲜独立证据确认。
- **持久化闭合**：当前周期恰好一次提交为完成、失败或软件恢复作废，且不存在开放周期。
- **业务活性**：正式周期、控制逻辑、状态投影和 Watchdog 业务心跳持续推进。
- **UI 活性**：WinForms 消息泵能处理消息；它不等价于业务活性。
- **崩溃接管墓碑**：由 Sidecar 在证明旧进程精确死亡后，以自身权威写出的强类型接管围栏；与主程序的优雅关闭墓碑不同。

## 4. 分析方法

1. 先复算封盘清单全部 SHA-256 和文件长度，确认分析材料未损坏。
2. 以本地时间对齐主日志、错误/警告日志、UI 指标、Watchdog 心跳和截图。
3. 对 `index.db` 执行只读 `integrity_check`，查询事故窗口所有周期和开放终态。
4. 对比恢复检查点前后 revision，确认事故后安全交接状态。
5. 读取当前 Watchdog 强杀后的 replacement、relaunch authority、终态会话和事件序列。
6. 用错误码、时间间隔、队列深度和主机资源指标排除压力不足、单通道故障、磁盘满、CPU 满、内存耗尽等竞争解释。
7. 将每个已验证现象映射到 V2.13.0.43 源码决策点，并对无法由封盘直接证明的调度层原因保留不确定性。

## 6. 完整改造方案

### 6.1 P0-A：重构 DAQ 连续读取边界

#### A1. 显式配置输入缓冲区

不得再把单批 20 点同时当作连续采集缓冲提示。每设备缓冲按安全调度 SLA 推导：

```text
InputBufferSamplesPerChannel =
    ceil(SampleRateHz × (最大允许调度停顿秒 + 追赶窗口秒 + 安全余量秒))
```

首版建议按 2 kHz、至少 10 秒配置，即每通道不少于 20000 点；最终数值必须用 5 秒强制停顿注入验证后定版。配置要有最小值、最大值、实际 DAQmx 分配值回读和启动日志，不能静默回退。

#### A2. 每设备独立专用读取线程

- Dev1、Dev2 各自使用 `LongRunning`/显式专用线程执行固定 20 点的阻塞读取循环，不依赖 CLR ThreadPool 派发 NI 完成回调；
- 读取线程只完成 `Read -> 时间戳 -> 预分配环所有权转移 -> 下一次 Read`，禁止日志、UI、文件 I/O、网络 I/O、恢复事务和同步等待；
- 控制代表值计算如无法严格证明为有界 O(1)，移到独立的实时控制消费者；
- 两设备不得共享读取锁、任务门或可阻塞的故障发布路径。

如果继续使用异步 API，也必须在 `EndRead` 后最早位置重新挂起下一次读取，再处理上一批；但专用同步读取线程更容易证明调度隔离和单生产者语义。

#### A3. 连续性与溢出策略

- `-200279` 必须强类型归类为 `DaqInputBufferOverflow`，锁存永久序号空洞；
- 同 RunId 禁止在溢出后“恢复并继续计数”，必须完成安全停机、耐久封圈后以新 RunEpoch 重启；
- 回调/读取年龄达到 100 ms 时先记录预警证据，250 ms 时按现有失效安全关闭输出；不得仅提高 250 ms 阈值；
- 新增硬件缓冲可用量、读取积压批数、追赶速率、ThreadPool 可用 worker/IO、GC pause、线程 ID 和最长回调间隔的持续诊断。

#### A4. 捕获真正的第一阻塞者

首次出现 `CallbackAge > 100 ms` 或 PSU 多路同步延迟时，在不阻塞控制链的独立诊断进程中：

1. 保存 30 秒循环 ETW/EventPipe（ThreadPool、Task、GC、Contention）；
2. 保存主进程全线程小转储；
3. 保存 NI Task 状态、输入缓冲容量/占用和 DAQmx 扩展错误；
4. 保存当时所有硬件 Actor 的队列深度和在途命令；
5. 先写轻量触发清单，再异步复制重证据，确保强杀前可用。

### 6.2 P0-B：根故障归并和安全事务单一所有者

引入 `SafetyIncidentCoordinator`，以 `RunId + RunEpoch + RootCorrelationId` 作为唯一事故身份：

- 两台 DAQ 同时失鲜、多个电源遥测同时超时，应合并为一个 `AcquisitionInfrastructureStall`；
- 在任何通道自愈、液压释放或电源联锁前先锁存根事故，再把同一关联号传给所有下游动作；
- 整个事故只允许一个 StopAll 事务、一个安全检查点、一个 Watchdog 交接事务；
- 通道层只提交“参与者终态”，不得各自再次创建全局 StopAll；
- 重复 OFF 请求只加入同一在途任务，禁止再次执行完整逐路关闭和重复发布故障；只有第一次失败或物理状态发生新变化才允许重试；
- 事件、UI 和日志按 `RootCorrelationId + Code + ChannelGroup` 合并，首条立即输出，后续按 1 秒汇总计数。

当前 `OffCurrentUnverifiableDaqStale` 在 DAQ 根事故尚未锁存时可能被登记为 `DaqDerived=False`，从而产生新的电源组关联号。必须把根事故锁存提前到任何通道安全动作之前。

### 6.3 P0-C：周期持久化改为单调事务

#### C1. 原子状态机

周期记录只允许：

```text
Prepared -> Running -> Completed | Failed | AbortedBySoftwareRecovery | AbortedByProcessTermination
```

- 上电前先耐久写入 `Prepared`，再 CAS 为 `Running`；
- `start_time` 只能由一次权威开始事务写入；
- 终态用 `WHERE status IN ('Prepared','Running') AND attempt_id=?` 的条件更新恰好一次；
- `end_time` 必须大于等于 `start_time`，不满足时拒绝提交并保存竞态证据；
- 迟到完成、取消、故障 Finalizer 只能读取已有终态，不能把终态改回 `running`；
- 每条 closure receipt 必须绑定 RunId、RunEpoch、EPB、Cycle、AttemptId 和数据库 revision。

#### C2. 恢复门禁

`PersistenceDrained` 不能只看队列深度。它必须同时满足：

1. DAQ 原始/工程值队列均排空；
2. 当前事故涉及的所有周期 closure receipt 已耐久；
3. `SELECT COUNT(*) ... WHERE run_id=? AND status IN ('Prepared','Running')` 为 0；
4. 没有 `end_time < start_time`；
5. checkpoint 保存上述查询 revision 和摘要哈希。

启动时若发现旧进程遗留开放周期，只能通过一次受审计事务改为 `AbortedByProcessTermination`，不得自动续计数，也不得手工删行。

#### C3. 当前数据修复

另行实现只读预检 + 双人确认的数据修复工具，对 EPB4/5557、EPB9/5406：

- 先验证文件样本、RunId、事故窗口、现有状态与封盘哈希；
- 备份数据库；
- 单事务改为 `AbortedByProcessTermination`，写修复原因、原值和新值审计；
- 再跑 `integrity_check`、开放周期查询和计数核对。

本报告不直接修改封盘数据库。

### 6.4 P0-D：业务 UI 全面 latest-only 化

- 通道运行态、告警覆盖层、电源遥测、恢复阶段分别使用固定槽位 mailbox；
- 每类最多只有一个待处理 `BeginInvoke`，UI 每 100 ms 消费各槽最后一个 revision；
- 相同通道/组旧 revision 直接覆盖，不在消息队列排队；
- 所有 UI 处理设置单帧时间预算，超过预算延迟到下一帧；
- 禁止在 UI 线程执行硬件 I/O、日志 Flush、数据库等待、StopAll 等待和 `Task.Result/Wait`；
- 增加 UI 投递队列深度、丢弃旧 revision 数、帧耗时和最长业务状态年龄指标。

状态语义同步修正：

- `HydraulicSampleStale` 显示“采集样本过期，已安全停机”，同时显示实际值、最低值和样本年龄；
- `HydraulicPressureBelowMinimum` 才显示“压力不足”；
- 同一根采集故障下，EPB4/5 主状态显示“基础设施故障安全停机”，持久化未闭合另列为恢复阻断原因，不伪装成卡钳硬故障；
- UI 显示状态采集时间和 `stale` 标识，超过 2 秒未刷新时禁止继续显示绿色“运行”。

### 6.5 P0-E：Watchdog 三轴活性和有界接管

分别监督：

1. **ProcessAlive**：精确 PID + StartUtcTicks；
2. **UiResponsive**：窗口消息探针；
3. **ControlProgress**：业务心跳、逻辑源 revision、周期进度、StopAll 事务进度。

推荐有界策略：

| 条件 | 动作 |
|---|---|
| 控制心跳陈旧 3 秒 | Ping + 请求立即刷新，不改变输出 |
| 陈旧 5 秒且 UI 可响应 | 只发一次结构化 StopAll，生成 repair transaction |
| repair transaction 5 秒内无新 revision/无 StopAll 身份 | 不再因 `WM_NULL` 成功而抑制接管；进入 Sidecar 安全接管 |
| 旧进程退出无法证明 | 禁止拉起，保持物理安全并提示人工 |
| 旧进程精确退出已证明 | Sidecar 成为崩溃接管权威，进入独立 SafetyAgent |

Control repair 必须拥有 hard deadline、进度 token 和一次性升级门，不能像本次一样发出两次请求后静默等待 28 分钟。

### 6.6 P0-F：拆分优雅关闭与崩溃接管凭据

#### F1. 优雅关闭

人工停止、正常退出继续使用主程序写出的 `ClosingTombstone`，它应撤销自动拉起许可并证明主程序已完成停止事务。

#### F2. 崩溃/强杀接管

Sidecar 在满足以下条件后写 `CrashTakeoverTombstone`：

1. 精确旧进程身份被冻结；
2. 精确旧进程已退出，排除 PID 重用；
3. 旧连接和旧执行许可已撤销；
4. 新 relaunch permit 与 Session/Run/Generation/Nonce 强绑定；
5. 写入 replacement 事务 revision 和旧进程退出证据哈希。

随后流程必须是：

```text
CrashTakeoverTombstone
  -> SafetyAgent 使用不可变配置快照执行全断能
  -> 新鲜压力/电流/电源 OFF 证据
  -> SafetyHandoffReceipt
  -> LaunchIntent
  -> 新进程精确 Attach
  -> 恢复检查点业务闭合校验
  -> 受控续跑或保持安全待命
```

缺少“主程序优雅关闭墓碑”在崩溃路径中不再是损坏证据；只有 Sidecar 自己的崩溃接管墓碑、许可或安全回执不匹配时才永久阻断。不得简单删除现有门禁或无证据重启。

### 6.7 P1：正式发布和 Watchdog 全局唯一性

#### 正式发布门禁

- 现场无人值守模式只接受 `Tools/Build-Release.ps1` 产生的正式包；
- 必须同时具备 tag、Git commit、dirty=false、BuildUtc、ReleaseConfigSha256、文件清单和签名/哈希；
- 标题栏出现 `PackageNotApproved` 时禁止开始正式试验；
- 版本号相同但 EXE 哈希不同必须视为不同构建，不得覆盖发布目录。

#### Watchdog 生命周期

- 增加以“物理试验台 ID + 项目根目录”命名的全局 owner lease，而不是只按 SessionId 单例；
- 新版本启动前枚举并验证同试验台旧 Sidecar：目标主进程已不存在、会话已阻断且无安全事务时，写终止清单并退出旧 Sidecar；
- 活跃安全事务不能粗暴杀掉，必须完成移交或明确人工确认；
- `TakeoverExitPermitIdentityMismatch` 等稳定重复事件采用指数退避和汇总，不得每 265 ms 永久写盘。

## 8. 不应采用的“修复”

- 不得把 DAQ 新鲜度阈值从 250 ms 简单放大到 1～3 秒；这会让电机继续使用旧电流/压力证据。
- 不得屏蔽 EPB4/5 报警；安全停机是正确的，错误的是根故障归类、事务扇出和提示文案。
- 不得只增大 DAQ 缓冲而保留 ThreadPool 回调依赖、过晚 re-arm 和缺失诊断；增大缓冲只是必要条件，不是完整解。
- 不得让 Watchdog 在任何缺少安全证据时直接重启；应建立 Sidecar 崩溃接管凭据和独立 SafetyAgent 证据链。
- 不得手工删除 EPB4、EPB9 的 `running` 行；必须审计修复并保留事故证据。
- 不得继续用 `PackageNotApproved` 包做正式无人值守试验。
- 不得把本次旧压力值解释为“压力确实不足”，也不得据此直接更换卡钳或液压件。

## 12. 最终判定

本次事故应定性为：

> **DAQ 连续采集抗调度抖动能力不足导致双设备样本失鲜和 Dev1 缓冲区溢出；多通道故障事务与持久化竞态将单一采集故障放大为整批授权撤销和业务界面失活；Watchdog 又因 UI 活性判据及崩溃关闭凭据设计缺口，未能及时接管并在人工强杀后永久阻断自动恢复。**

安全逻辑拒绝旧样本、关闭输出的方向是正确的，不能通过放宽阈值或屏蔽报警绕开。完整解决方案必须同时完成 DAQ 读取隔离、事故事务归并、周期单调持久化、UI latest-only、Watchdog 三轴活性、崩溃接管凭据、全局 Sidecar 唯一性和正式包门禁，缺少其中任一项都不能称为无人值守闭环。
