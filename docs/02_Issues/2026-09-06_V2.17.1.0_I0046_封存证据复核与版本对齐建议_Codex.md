## 1. 结论：方向部分正确，但 GLM 文档不能直接作为整改依据

**本次最终停机的可证实链条是：短时持久化慢写和积压 → DAQ 局部恢复 → 电源 OFF 未确认监督触发接管 → 安全退出 → 普通会话关闭消息取消了接管。** 最值得先修的是退出交接中的类型丢失；最值得先测的是写盘调用内部及恢复截止阶段的延迟。没有证据支持直接放宽 DAQ 三阈值，也不支持为了保持窗口存活而取消数据完整性和物理安全保护。

GLM 正确找到了持久化异常入口、最终 `PowerOffUnconfirmedTimeout` 接管和退出后未继续运行的现象。但以下关键论断需要纠正：

1. **“写入器常态饱和、每批 fsync 恰好 10ms”不成立。** 正常窗口各设备 472 条周期记录显示：持久化队列深度中位数均为 0；最老批次年龄 p95 约 20ms。109ms 告警来自一个只在年龄 ≥100ms 时记录的筛选器。
2. **“两设备同时零进度约 3.7s，已证明进程内停顿”不成立。** 逐批 CSV 有大量写入完成，周期记录中的 `Persisted` 也持续增加；实际存在数百毫秒的慢调用。它们可能含锁等待、文件刷新、SQLite 和调度延迟，现有分项不足以归责。
3. **`PreserveApprovedPermit` 的含义不是“不重启”。** 它表达退出时保留自动替换资格。真正的断点是随后的 `ApplicationClosing` 被 sidecar 按普通关闭处理，取消接管并停止监督。
4. **“持久化只应标记缺口，不得触发暂停/重建/接管”过度放宽。** 无法保存有效试验原始证据、持续无法确认关电、恢复执行体失效，仍然需要有界保护。应消除重复升级和错误归因，并把恢复闭环修通。
5. **PID 22792 是看门狗辅助进程，不是失败的替换主进程。** 该误读同时使 GLM 对第一次自动拉起成功的论证失效。

因此建议对齐的是**物理安全、数据有效性、恢复所有权、耐久完成边界这四项行为契约**，不是把新版的三个数值复制成旧版。

## 4. 正常期与慢写期：重新量化

### 4.1 正常期远没有达到“常态 109ms、零余量”

取 `13:31:12.754 ≤ 时间 ≤ 13:47:10.092`、`FieldMetric DAQ Phase=Running`，每设备 472 条：

| 指标 | Dev1 | Dev2 |
|---|---:|---:|
| 队列深度 p50 / p95 / p99 | 0 / 2 / 5 | 0 / 3 / 6 |
| 深度为 0 的快照数 | 363 / 472 | 330 / 472 |
| 最老批次年龄 p50 | 0.000ms | 2.660ms |
| 最老批次年龄 p95 | 20.492ms | 20.319ms |
| 最老批次年龄 p99 | 52.099ms | 67.269ms |
| 最老批次年龄最大记录值 | 82.983ms | 112.028ms |

正式期 `13:33:57.106–13:47:10.092` 各 391 条，最老批次年龄 p95 进一步为 10.569 / 18.875ms。深度不包含所有在途工作的情况需结合 `PersistenceInFlight` 看；上述指标足以否定“始终深度 10–11”，但不足以量出磁盘极限吞吐。

GLM 误判来自 [DaqPersistenceCoordinator.cs](../../Controller/DaqPersistenceCoordinator.cs) `EvaluateLag()`（1069 行起）：

```csharp
if (depth >= _pauseDepth || age >= _pauseAgeMs) { /* Paused */ }
// 未触发暂停时，仅记录年龄达到 100ms 的观察点，每设备最多约每秒一条。
if (age < 100) return;
```

所以日志在 107–110ms 附近集中，是跨越记录门槛时的样本选择效应。第二段运行首次暂停前共有 **57 条**“持久化延迟”告警；它们不是持续饱和的采样，也不是 57 次安全暂停。

`EvaluateRecovery()` 仅在 `PauseLatched != 0` 时使用 `ResumeAgeMs`。因此“ResumeAge=100 小于常态 109，导致全程延迟↔恢复抖动”也没有成立。普通延迟告警的 100ms 是硬编码门槛，修改恢复年龄不会直接改变它。

### 4.2 逐批时序支持“短时慢写”，不能分解成 fsync 成本

两份事故 CSV 均有 1001 条 `Kind=Persistence` 记录。异常前 UTC `[05:47:07,05:47:10.5)`：

| 写入完成时刻（本地） | 设备 | 本次 WriteBatch 耗时 | 完成时该批年龄 | 队列深度 |
|---|---|---:|---:|---:|

计时范围由 `DaqPersistenceCoordinator.WriteWithRetry()` 及 [TwoDeviceAiAcquirer.RecordPersistenceTiming()](../../IO.NI/TwoDeviceAiAcquirer.cs) 确定：`ProcessingMs` 包含整个 `WriteBatch`，而 `PersistenceWaitMs` 传入的是完成时 `batch.AgeMs`，**包含本次写入耗时，不能当作纯排队等待再与 ProcessingMs 相加**。

这些 Persistence 记录的 `SqliteMs/RingWriteMs` 全部为 0；代码在该观测点未填这两项，不能解读为 SQLite 或文件写入没有耗时。尚不能区分原始日志提交、索引提交、ring flush、通道锁和共享锁各占多少。

### 4.3 两次异常都不是“全程零进度”

第一段：`run.log:324–440` 的持久化完成序列分别从 Dev1 `2369→2449→2517`、Dev2 `2368→2411→2449` 递增，同时队列增长到 256。说明区间吞吐不足，并非连续约 6 秒完全不写。

第二段：`13:47:10.092→13:47:13.583`，Dev1 `Persisted 96703→96949`，Dev2 `96696→96841`。13:47:13.583 两设备 `ProcessingDepth=0`，控制处理年龄约 14ms。13:47:15.975 两设备 `PersistenceDepth=0` 且 `Accepted=Persisted`。

恢复期部分圈可能已经封为异常，尾部原始记录的业务归属还需逐圈核对。`OverCapacityDropped=0` 只证明相应计数器未记录超容量丢弃，不能单独证明整场所有原始证据、有效圈、峰值和机械状态都没有缺口。

HOST 的第二次异常窗口实际记录 `DiskWrite=8.40、2.96、5.62、6.12、8.76 MiB/s`，不是“始终 ≤6”。[HostRuntimeProbe.cs](../../IO.NI/HostRuntimeProbe.cs) 使用 `PhysicalDisk/_Total` 系统计数；低吞吐和某次队列为 0 不能排除同步刷新长尾、驱动或文件锁等待。第一段出现约 91–104MiB/s 的较高系统写入，支持竞争假设，仍未定位责任进程。

6. 主窗体随后即使再按接管类型调用关闭，也可能复用已完成的 `_watchdogShutdownTask`；类型正确的后续分支无法撤回已发出的普通关闭消息。

这是本次**置信度最高、可以直接设计回归用例的退出链缺陷**。上述判断来自生产源码和事件吻合，尚未在真实窗体与 sidecar 集成测试中复现；并未用仅供测试的 `WinFormsWatchdogUiProductionSession` 当作现场调用来源。

修复应让子窗体只提交硬件/数据释放凭证，最终传输关闭由主进程退出所有者带完整类型执行；或者全程传递冻结的退出意图。还应防止普通 SessionClose 请求或缓存任务覆盖已确立的接管退出。sidecar 收到旧式普通关闭时，应先核验同一会话、租约、事务的有效替换退出凭证，不能无条件取消接管。

该防御不能让旧许可覆盖真正的人工停止。必须保留当前人工意图的明确撤权路径，并验证 PID+启动时间、代际、许可及事务身份后再替换，避免双主进程。

## 7. 与 2.14.2.11 对齐时，哪些语义确实不同

| 项目 | 本次核对结果 | 对齐意义 |
|---|---|---|
| 75/100/250 与四种年龄、Trip 一次确认 | 与用户源码对比方向一致；本包没有对应新鲜度切断或读取分发溢出记录 | 不能将本案归因于这些参数，也不能据此证明所有场景“零误报” |
| 持久化队列满反压 | **旧版已经有** `q.Slots.Wait(_cts.Token)` | 不能说这种耦合全是新版新增 |
| 后台处理 500ms 独立监督 | **旧版已经有** `const double hardAgeMs=500.0` | 相同阈值遇到不同负载可能有不同结果 |
| OFF 未确认 5s 接管 | **旧版已经有** PowerOffUnconfirmedTimeout | 不能说新版首次引入该短窗 |
| raw-journal 与持锁同步提交 | 新版确实新增，FULL、共享 gate、每设备批次事务在实际路径中 | 有性能和跨设备锁竞争风险，但不等于已证明本次慢写根因 |
| 恢复尾部抑制 | 新版 `TryHandleSuppressionUnderGate()` 对 `IRawJournalCycleRecorder` 返回 false，继续走耐久写入；旧版直接计 suppressed/terminally handled | **数据承诺改变了恢复负载**，是仅比参数看不到的实质差异 |
| 后续 raw checkpoint | 新版 `CheckpointRawJournal()` 对 ring 做 Flush(true)、索引提交后回收 raw frames | 诊断应覆盖整条耐久路径，不只量事务 Commit |

证据：[DaqPersistenceCoordinator.cs](../../Controller/DaqPersistenceCoordinator.cs)；[TwoDeviceAiAcquirer.cs](../../IO.NI/TwoDeviceAiAcquirer.cs)；[EpbDiskWriter.RawJournal.cs](../../DataOperation/EpbDiskWriter.RawJournal.cs)。历史行为可用 `git show 6ed4d47:<路径>` 复核。

两版采样都是 2000Hz、20 点/批，即每设备名义 100 批/s；两设备最多约 200 次/s 的设备批次写入机会不等于 200 次真实 fsync：活跃圈、边界、重复序列等会改变实际写入内容，空事务也不能当作有 WAL 写入的事务计数。两设备共享 raw gate，不能把单设备的 10ms 到达间隔直接当作共享日志的每次同步成本。

`RawDataLoggingEnabled=false` 不能关闭这条原始耐久日志路径。raw-journal.db 文件大小 647168 字节只能证明文件存在，不能推出历史写入量或 IO 成本；帧会被 checkpoint 回收，SQLite 文件大小也不等于有效内容量。

本包有 4 条 `ObservedUnenergizedGap`，约 339.8ms/298.4ms，明确标为未上电观察。没有 `DAQ_FRESHNESS_SAFETY_CUTOFF` 与 `DaqReadDispatchOverflow`，不代表没有超过 75ms 的任何观测，更不能把普通 `DaqPersistenceLag` 恢复中的通用“DAQ回调陈旧/失联”提示当作真正 liveness Trip。

## 8. 建议实施顺序

### P0：修通退出交接，保持安全和许可身份约束

先实施第 6 节关闭类型贯穿和单一最终关闭所有者。明确区分：人工停止/退出、普通会话解绑、看门狗接管退出、恢复退出。对每次接管给出完整结果：安全终态、旧进程真实退出、批准许可消费、新 PID 及启动时间、检查点恢复提交；若无法自动恢复，应给出具体阻断原因，不能以静默消失收尾。

整套构建与相匹配的看门狗组件共同验证，现场记录精确 GitCommit、EXE/config 哈希。把已存在的 `fac7d60/3c000c8/fb498ba` 纳入修复基线，但不能称为已解决 I0046。

### P1：先完成关电截止，再等待数据收口

围绕第二段 `StaleDetected→DoOffSubmitted` 补阶段计时与超时证据，检查 Timer.Pause、取消回调、圈边界冻结和各锁，避免同步业务回调挡住全组 OFF 的投递。保持边界和代际一致，不能为绕开等待而污染当前圈归属。

电源确认使用当前代际、当前操作、新鲜且可回读的 OFF 证据。若证据已满足而监督仍投影未关电，修投影；若 OFF 尚未发出或未确认，修截止执行，保留安全接管。数据排空和模型重建可用较长预算，物理关电不应仅因 `RecoveryActive` 就无限延后。

### P2：测量并优化完整写盘路径

现有日志已能提供正常期和事故逐批总耗时。下一步新增低开销分段直方图或环形诊断：通道锁等待、raw gate 等待、原始事务准备/提交、索引事务、ring/MMF flush、checkpoint 回收、圈关闭/导出。记录线程与批次身份、数据目录所在卷的延迟/IOPS，并用事件触发 ETW/线程栈识别长尾来源。

优先考虑保持耐久语义的优化：减少重复序列化/分配和 SQL 准备开销；评估有界 group commit；把可独立导出和清理移出关键持锁段。若移出通道锁，必须先设计不可变批次所有权与提交复核，维护 Run/Generation/Cycle 身份、FIFO、截止和重试幂等。

**不建议把 `Synchronous=Normal` 当作默认现场修复。** SQLite 官方明确：WAL+NORMAL 维持一致性，但操作系统崩溃或断电可能回滚已提交事务；损失不能承诺只限“最后一批”。本系统还有索引、ring 和 raw journal 之间的耐久先后关系，只降低其中一项会改变跨文件恢复承诺。[SQLite synchronous 官方说明](https://www.sqlite.org/pragma.html#pragma_synchronous)

如果使用 group commit，必须仅在真正同步提交成功后推进 `Persisted`；同步前的数据由有界队列持有，冻结边界/终态要等待其覆盖。100ms/10 批只能作为实验参数，不能在未测量和未验证崩溃恢复前定为现场方案。需检查 group commit 自身的等待是否挤占 100ms 恢复门槛。

Defender 排除项不是本包能够推出的必需措施。先定位过滤驱动/扫描是否占用对应文件；有证据时再做受控对照，不把全数据目录排除作为默认整改动作。

### P3：归并相关故障，保留有界升级

可以把同一持久化事件引起的队列满、后台处理年龄告警归并到一个 CorrelationId，由当前恢复所有者收口，避免重复撤销执行体、重复增加重试预算。不要直接豁免所有 >500ms 告警：先判断控制证据是否独立有效、当前接受的数据是否可保存、队列是否持续恶化。

正常处置应是：短时延迟观察；达到积压边界安全暂停；同事件只启动一次恢复；证据完整时恢复/重做无效圈；长期无进展、真实数据缺口或物理安全未确认时升级。学习峰值证据不完整仍应作废相关尝试，不能继续更新学习模型或算有效圈。

### P4：最后做参数对齐

| 参数组 | 本案建议 | 调整前需要的证据 |
|---|---|---|
| Liveness 75/100/250 | 暂保持 | 带电期间四种数据年龄的全量/事件前分布及真实误切断复现 |
| ControlHardFaultAge=100ms | 保持独立保护 | 控制闭环允许的数据年龄及保护动作验证 |
| Persistence capacity=256，pause=128/1000ms | 先不改 | 写盘分段耗时和可承受无服务窗口；256 批在 100 批/s 下约是 2.56s 名义容量，不是固定容忍时间 |
| Persistence resume=32/100ms | 先不改 | 暂停后的连续恢复证据；普通 100ms 延迟告警与此分开配置/命名 |
| ReadDispatch capacity 默认64 | 本包无溢出证据，先不改 | 独立该队列的高水位/消费者停顿；不能由 ProcessingCapacity=1024 代替 |

后续可将 Warn 的“观察门槛”和执行器数据截止门槛拆成语义明确的设置，首版保持现有效果，只修复命名和可观测性。若恢复旧值，当前代码会把 Warn/Suspect 限成 200/249ms，且四年龄/一次确认逻辑仍在，不能声称还原了旧版。

## 9. 验证方案与完成标准

### 9.1 先验证确定的退出缺陷

使用真实 MDI 主/子窗体与 sidecar，覆盖 `RequestStopAll→StopCompleted→TakeoverReplacementExit` 的生产路径，断言：

- 子窗授权不会先以 SessionClose 终止 sidecar；保留许可的接管不出现本案 `TakeoverCancelled Reason=ApplicationClosing`。
- 同会话重复关闭、进行中关闭任务、断连重连、晚到消息均不改变已确定的退出类型。
- 人工停止仍撤销自动运行；旧事务/旧租约许可不能覆盖新的人工停止。
- 必须看到旧 PID 退出证明、唯一新 PID、许可消费和恢复提交；仅见 Approved 或六项安全 true 不算通过。

修代码时按仓库要求执行 Debug x86、相关真实 sidecar/UI 回归及三套控制/写盘/电源测试。**本次只做分析和脚本复算，没有运行构建或这些测试。**

### 9.2 再做存储及截止阶段故障注入

在仿真或输出被可靠隔离的测试环境，分别注入 raw gate 等待、SQLite 提交慢、ring flush 慢、回调同步阻塞，持续 100/500/1000/3000ms，另测永久无进展。每次核对当前圈、数据边界、立即 OFF 投递、当代 OFF 确认、恢复次数和最终有效圈数。

对于 group commit 或锁范围改造，还需验证：提交前崩溃不会提前认定持久化；提交后重放不漏不重；停止冻结边界不扩大；掉电/系统崩溃后的索引与原始数据不相互矛盾。

### 9.3 最后做同机版本对照与长稳

旧版、新版现场基线、修复版使用相同电脑、工程、6 通道、采样、数据卷和其他系统负载；不同版本使用隔离数据副本，避免旧版直接读写新版持久化格式。区分启动/学习/正式阶段，重复试验；不能用单次“活了 16 分钟”计算长期可靠性。

主要验收项是有效圈、首次保护、恢复成功率及最终完成，而不仅是窗口不消失：

| 维度 | 基线/本案 | 验收方向 |
|---|---|---|
| 正常写盘 | 周期 p95 约20ms，存在短时长尾 | 保持正常分布并减少长尾；同时给逐批分布，不能拿告警样本冒充 p99 |
| 关电截止 | 恢复阶段约4.6–5.4s才记 DoOffSubmitted | OFF 投递不被写盘/普通回调长等待挡住，确认受独立预算监督 |
| 短时存储积压 | 暂停并作废部分圈 | 单一恢复所有者收口；数据/安全未满足前不重新上电、不计有效圈 |
| 进程替换 | Approved 后取消接管，无替换完成记录 | 安全终态→旧PID退出→新PID→恢复提交全链可审计 |
| 数据完整性 | 局部计数器无超容量丢弃，未做全库审计 | 有效圈证据完整；异常圈明确归属，不靠静默丢数据换存活 |
| 长稳 | 第二段从启动到退出约16.5分钟；正式期至首次暂停约13分14秒 | 先完成故障注入，再覆盖≥24h现场长稳及所要求的有效圈数；时长只是门槛，不是可靠性证明 |
