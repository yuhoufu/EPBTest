# V2.10.2.2：1505 与 1507 两次软件报警根因及无人值守永久整改

> 分析日期：2026-08-05  
> 现场版本：`V2.10.2.2`  
> 数据备份：  
> `\\wj-epb\EPB_Data\10358-029_V2.10.2.2_0805_1505`  
> `\\wj-epb\EPB_Data\10358-029_V2.10.2.2_0805_1507`  
> 范围说明：本项目是 C#/.NET、NI-DAQmx、数字量 I/O 和程控电源程序；本分析不涉及 LabVIEW。

## 1. 结论先行

1. **这两份备份新增的报警都没有达到“确凿硬件故障”的证据标准，不应锁存为硬件报警。**
2. 两次报警的直接触发因素不同：
   - `1505` 备份：`Dev1 BackgroundQueueFull`，即程序内部 DAQ 后台完整处理队列满；其后又发生自动恢复、电源监控和恢复超时之间的软件竞态。
   - `1507` 备份：`Dev1 DaqCallbackStale>100ms`，即一次约 `113.6 ms` 的 DAQ 回调空窗；程序在恢复之前就直接锁存了设备组硬故障。
3. 两次不是同一个直接原因，但属于同一类系统性问题：**软件把“数据链暂时不可信”直接等同于“硬件已经损坏”，而且恢复流程没有单一、原子的最终状态。**
4. `1505` 的最终硬报警可以确认是软件问题：程序主动关电被旧监控误判为 `UnexpectedOutputOff`；同一关联号随后在相邻毫秒内同时记录“自动恢复完成”和“恢复超时硬故障”。
5. `1507` 只证明主机在 `113.6 ms` 内没有收到/处理新的 Dev1 回调，不能证明采集卡、线缆、传感器或卡钳硬件损坏。现场 DAQ 在约 `1.232 s` 内完成任务重建并连续获得 `10/10` 个新鲜批次，程控电源也没有保护跳闸、低压或通信异常证据。
6. 当前 `V2.10.2.2` **尚不满足长期无人值守验收条件**。需要完成本文第 7～10 节的代码整改和故障注入测试后，才能重新判定可无人值守。

### 3.2 第一层直接触发：后台处理消费者停顿

`BackgroundQueueFull` 来自 `TwoDeviceAiAcquirer.EnqueueForProcessing()`，实际对应：

- 配置项：`DaqProcessingQueueCapacity=64`
- 队列类型：每台 DAQ 一条 `BoundedConcurrentQueue`
- 消费者：每台设备只有一个 `ProcessLoop`
- 生产节拍：配置理论为 10 ms/批，现场实际约 15～16 ms/批

因此队列 64 批填满，意味着 Dev1 的后台处理消费者大约有 **0.64～1.0 秒** 没有跟上生产者。该消费者同步执行以下工作：

- `OnRawBatch` 订阅者；
- 工程值转换与滤波；
- 峰值计算；
- 写盘批次构造和分发；
- 限频后的 `OnEngBatch` UI 订阅者；
- 大量诊断对象创建。

所以第一层故障发生在主机软件的后台处理链，不在 DAQ 硬件电流值本身。

但是，**现有备份不能再精确指出是哪一个同步步骤阻塞了约 1 秒**，原因是事故快照实现存在证据覆盖问题：

1. `20260805_145459...` 事故目录内的 `daq_timing.csv` 最终写入的是 15:00:47～15:01:11 左右的数据，而不是 14:54:59 触发瞬间的数据。
2. 暂停、恢复成功、恢复失败多条路径共用同一个文件名并发导出，最终出现文件占用异常。
3. `incident.json` 写的是持久化队列容量 `256`，而真正触发 `BackgroundQueueFull` 的后台处理队列容量是 `64`，两个队列被混在了一份事故摘要中。

因此，本次可以确认“后台处理消费者停顿导致 64 批队列满”，但不能在现有证据上武断声称一定是磁盘、UI、GC 或某一个订阅者。软件必须先修复快照和耗时埋点，下一次才能把阻塞点精确到方法。

### 3.3 第二层根因：恢复和电源监控的软件竞态

这是本次最终硬报警的确定性软件根因。

当前代码链为：

1. `EpbManager.OnDaqDeviceFaultDetected()` 收到 `BackgroundQueueFull`；
2. `BeginDaqAutoRecoveryAsync(... restartDaq:true)` 暂停 EPB4/5 并重建 Dev1；
3. Dev1 在 203 ms 内恢复后，`TryCompleteDaqAutoRecoveryAsync()` 调用 `PowerSupplyCoordinator.PrepareAndEnableAsync()`；
4. `PrepareAndEnableAsync()` 发现电源原来为 ON，会主动执行 OUTP OFF 后再做完整预检；
5. 但原电源监控没有在计划关电前被可靠停止/标记，监控线程看到 OFF 后按 `UnexpectedOutputOff` 生成硬故障；
6. 恢复成功路径和 10 秒超时路径不是互斥的原子终态。超时任务不会在成功时可靠取消，成功路径也没有在每次 `await` 后重新确认关联号、人工停止状态和终态所有权；
7. 结果是同一关联号既“恢复完成”又“恢复超时”，甚至在操作员已经点击停止后仍把通道恢复为运行状态。

这不是阈值不合适，而是状态机缺少以下基本约束：

- 一个关联号只能有一个最终状态：`Recovered` 或 `Failed`；
- 人工停止必须取消恢复，取消后绝不能自动恢复通道；
- 程序计划内的电源切换不能被监控解释为硬件意外断电；
- 恢复电源、监控和通道状态必须由同一个设备组串行事务拥有。

### 3.4 为什么不能判为硬件故障

- 报警码是主机内存队列满，不是 DAQmx 硬件错误码。
- EPB4/5 在安全关断时电流已接近零。
- Dev1 重建后 203 ms 即获得 10 个新鲜批次，之后数分钟持续有正常回调。
- 电源 2 无保护跳闸；OUTP OFF 是软件恢复流程主动发出的动作。
- 最终“恢复超时”与“恢复成功”在同一毫秒级窗口内同时出现，只可能说明软件终态竞态，不能说明硬件同时好和坏。

## 4. `1507` 备份：DaqCallbackStale>100ms

### 4.1 现场时间线

以下均为北京时间：

| 时间 | 证据 |
|---|---|
| 15:06:02.200 左右 | Dev1 generation 2 最后一组正常回调/处理记录；队列很浅，处理耗时约 0.2 ms |
| 15:06:02.311～.314 | 控制侧发现样本陈旧；快照显示 `CallbackAge=113.6ms`、`ControlEnqueueAge=113.6ms`、`ControlProcessedAge=113.6ms` |
| 15:06:02.317 | EPB5、Dev1 设备组被直接锁存硬报警，受影响通道为 EPB4/5 |
| 15:06:02.325 | Dev1 开始自动恢复 |
| 15:06:03.381 | Dev1 重建为 generation 4 |
| 15:06:03.559 | UI 记录 `DAQ恢复 Dev1：成功，新鲜样本=10/10，1232ms` |

事故摘要同时显示：

- 控制队列深度：`0/64`
- 最老控制批次年龄：`0 ms`
- 最近控制处理耗时：`0.020 ms`
- 最大订阅者耗时：`0.001 ms`

因此这次不是控制队列或后台处理队列积压，而是 **generation 2 在约 114 ms 内没有产生新的可用回调**。

### 4.2 程控电源没有提供硬件故障证据

报警前后，电源组 2 的遥测为：

- `Output=True`
- 输出电压约 `11.997 V`
- `ProtectionTripped=False`
- `CC=False`
- 无低压、限流、功率限制或通信错误

报警时电源电流约 7.505 A，只表示当时组内有负载动作，既没有超过配置限制，也没有触发电源保护。15:06:02.529 的 `Output=False` 是报警后软件执行组关断的结果，不是报警前硬件自行掉电。

`alarm-metadata.json` 还明确写明：

- `doCommandResult` 只表示软件 DO 方法返回成功，不代表继电器触点或负载端物理状态；
- `physicalOffStatus=NotMeasured`；
- `physicalPowerState=NotMeasured`。

所以该快照不能证明继电器、线束、卡钳或 DAQ 硬件损坏。

### 4.3 当前软件为什么会误锁存

当前分类逻辑只要：

```text
CallbackAgeMs > 100
```

就分类为 `DaqCallbackStale`。随后名称为 `OnRunnerRecoverableFaultRaised()` 的处理方法，却在执行 `RecoverDaqDeviceAsync()` **之前** 直接调用 `LatchDaqGroupHardFault()`。

这造成逻辑矛盾：

- 故障在代码概念上是“可恢复故障”；
- 现场也确实在 1.232 秒内恢复；
- 但通道硬报警已经永久锁存，恢复结果无法撤销错误的硬件结论。

100 ms 可以继续作为带电安全截止线，但不能单独作为硬件损坏的判定线。Windows/.NET 不是硬实时系统，一次 GC 停顿、线程调度延迟、NI 驱动回调交付延迟或短时系统负载，都可能造成类似空窗。

### 4.4 GC/运行时压力是可疑共同诱因，但现阶段不能写成唯一根因

该事故的 `daq_runtime.csv` 在报警前约 18.16 秒内记录：

- Gen0 GC：`838 -> 885`，增加 47 次；
- Gen1 GC：`787 -> 816`，增加 29 次；
- Gen2 GC：`154 -> 167`，增加 13 次；
- 托管内存在约 35～52 MB 间快速波动；
- 可用工作线程仍约 2039～2042，并没有普通线程池耗尽证据。

如此频繁的 Gen1/Gen2 回收对长时间稳定采集不利，GC 或托管运行时停顿是 `113.6 ms` 空窗的重要嫌疑。但当前诊断只记录 GC 次数，没有记录每次 GC 的开始、结束和暂停时长，无法证明恰好是哪次 GC 覆盖了报警窗口。因此正确结论是：

> 回调短时中断已确认；高频 GC 是高概率软件诱因之一；硬件故障未确认；必须增加 GC 暂停和线程调度证据后再细分根因。

## 5. 两次是不是同一个因素

### 5.1 不是同一个直接触发

- `1505`：DAQ 回调仍能生产数据，但 Dev1 后台完整处理消费者没有及时消费，最终 64 批队列满。
- `1507`：后台和控制队列均不拥堵，但 Dev1 新回调本身出现约 114 ms 空窗。

### 5.2 存在共同的软件系统因素

两次都暴露以下共同问题：

1. 主机实时性余量不足，存在高频托管 GC、同步订阅者或线程调度停顿风险。
2. “暂时没有可信数据”和“硬件已经损坏”没有分层。
3. 安全动作、自动恢复、系统故障、硬件报警共用硬故障锁存路径。
4. 单点时间阈值一旦越界就永久报警，没有利用恢复结果反证硬件故障。
5. 事故快照会被后续状态覆盖或并发写失败，导致最关键的首发证据丢失。

因此可以说它们属于同一类软件架构缺陷，但不能说两次都是同一个底层阻塞调用造成的。

## 6. 无人值守必须采用的判警原则

必须明确：**安全断电不等于硬件报警。**

| 状态 | 立即安全动作 | 后续行为 | 最终分类 |
|---|---|---|---|
| 回调超过 100 ms、队列满、写盘积压、GC/调度停顿 | 立即 DO OFF；当前圈作废；共享资源按组进入安全态 | 自动重建、验证新鲜批次，从下一完整圈继续 | `SoftwareTransientRecovered`，不锁存硬件报警 |
| 软件恢复连续失败、进程失去心跳、数据服务不可用 | 保持断电；禁止带电盲跑 | 看门狗重启应用；完整预检后恢复；超过重启预算则远程通知 | `SystemFault`，不是硬件报警 |
| DAQ 设备查询失败且任务重建重复失败，并有明确 DAQmx/设备不存在错误；或电源保护跳闸有新鲜回读；或过流有两路独立新鲜证据 | 立即断电 | 锁存、人工检查和复位 | `HardwareFaultConfirmed` |

以下报警码本身永远不能直接作为硬件故障：

- `BackgroundQueueFull`
- `ControlQueueFull`
- `DaqPersistenceLag`
- `DaqPersistenceRecoveryTimeout`
- 单次 `DaqCallbackStale`
- 单次 `DaqSampleStale`
- 日志/数据库/网络共享写入失败
- GC、线程调度或 UI 卡顿

这些都属于软件数据链或系统可用性故障。它们可以触发立即安全关断，但只有额外硬件证据成立时才能升级为硬件报警。

## 7. P0：必须立即实施的代码整改

### 7.1 把 DAQ 恢复改为单一终态状态机

涉及：`Controller/EpbManager.cs`

将当前“恢复任务 + 独立 fire-and-forget 超时任务”改为一个受控状态机：

```text
Running
  -> Pausing
  -> Rebuilding
  -> VerifyingDaq
  -> VerifyingPower
  -> Resuming
  -> Recovered

任一步失败 -> Failed
人工停止/新一代任务 -> Cancelled
```

实现约束：

1. `DaqAutoRecoveryContext` 增加原子终态和 `CancellationTokenSource`。
2. 成功、超时、人工停止只能通过同一个 `CompareExchange`/状态迁移入口争夺终态；只有胜者可以发布结果。
3. 成功后立即取消超时；超时获胜后禁止执行 `_persistence.ResumeAdmission()`、`timer.Resume()` 和 `ChannelResumed`。
4. 每个 `await` 返回后重新核对：设备、关联号、DAQ generation、人工停止 generation、通道是否已有独立故障。
5. 人工“停止全部”必须先取消所有恢复上下文，再执行停止；取消后的恢复任务只能清理资源，不能恢复运行。
6. 同一关联号必须恰好生成一个 `Recovered`、`Failed` 或 `Cancelled` 终态。
7. 不允许把 `BackgroundQueueFull` 的恢复失败直接写成“DAQ设备级硬故障”；应写成 `SystemFault/DaqRecoveryFailed`。

### 7.2 消除程控电源计划切换与监控之间的竞态

涉及：`Controller/PowerSupplyCoordinator.cs`、`Controller/EpbManager.cs`

1. 每个电气组增加一个覆盖 `Prepare / Enable / Disable / Monitor transition` 的串行操作门。
2. 计划执行 OUTP OFF 前，必须先停止并等待该组监控任务退出，或者登记带关联号的 `CommandedOutputTransition`；只有同一事务内的预期 OFF 才可忽略 `UnexpectedOutputOff`。
3. DAQ 短时重建时不要对仍健康的活动电源调用完整 `PrepareAndEnableAsync()`。优先新增幂等的 `RevalidateActiveGroupAsync()`：
   - 输出原本为 ON、身份/电压/保护状态健康时，只校验，不做 OFF/ON 循环；
   - 确实需要循环电源时，先进入计划切换状态，停监控，再关电、预检、开电和重启监控。
4. `UnexpectedOutputOff` 只有在“没有计划切换事务”的情况下才是硬件候选证据。
5. 电源恢复完成前不得恢复 EPB 定时器；人工停止或组故障出现后不得恢复。

### 7.3 把回调陈旧改为“立即安全关断 + 自动恢复”，而不是立即硬报警

涉及：`Controller/EpbManager.cs`、故障本地化和 UI 状态代码

建议初始策略：

1. `CallbackAge > 100 ms`：立即关断受影响设备组，当前圈标记为无效，进入 `DaqRecovering`；保留当前安全灵敏度。
2. 强制重建 DAQ，要求新 generation 连续 `10` 个回调、样本年龄不超过 `100 ms`、控制与后台队列健康。
3. 在 3 秒内恢复：记录软件瞬态，直接从下一完整圈继续，不触发通道硬件报警、不要求人工复位。
4. 单设备 10 分钟内连续 3 次短时中断：触发系统级自愈和进程看门狗重启，仍不冒充硬件报警。
5. 只有满足以下任一条件才升级为采集硬件故障：
   - 两次独立重建均返回明确 DAQmx 设备不存在/硬件访问错误，并且设备枚举或自检也失败；
   - DAQ 驱动返回不可恢复硬件错误码；
   - 采集卡断开、供电异常等有独立物理/系统证据。

### 7.4 修复事故快照，保证首发证据不可覆盖

涉及：`Controller/EpbManager.WarningSnapshots.cs`、`IO.NI/TwoDeviceAiAcquirer.cs`

1. 首发时立即冻结内存环形缓冲的副本，不等恢复完成后再读取“最近窗口”。
2. 同一关联号的不同阶段使用独立文件：
   - `trigger/daq_timing.csv`
   - `recovered/daq_timing.csv`
   - `failed/daq_timing.csv`
3. 每个关联号设置一个导出门；先写临时文件，完成后原子改名，禁止多个任务同时覆盖同一路径。
4. `BackgroundQueueFull` 摘要必须记录真实队列类型、容量 `64`、首发深度、最老批次年龄、最后一个处理阶段和订阅者耗时，不能用持久化队列容量 `256` 替代。
5. 增加 GC 开始/结束、暂停时长、线程 ID、进程 CPU、磁盘/数据库等待和 UI 分发耗时，才能判断下一次是否为 GC 或具体订阅者阻塞。

### 7.5 发布身份必须可复现

1. `build-identity.json` 必须写入完整 Git commit、分支、构建时间和 `gitDirty=false`。
2. 发布脚本拒绝从 dirty 工作区生成正式现场包。
3. EXE、配置和依赖 DLL 全部生成 SHA-256 清单。
4. 报警快照保存该清单，确保数据能精确对应源码。

## 8. P1：降低再次发生的运行时压力

### 8.1 把后台处理链中的同步订阅者隔离出去

当前 `ProcessLoop` 同步调用 `OnRawBatch`、持久化分发和 UI 订阅者，任何一个订阅者长时间不返回都会填满 64 批队列。

整改要求：

1. `ProcessLoop` 只做固定上界的计算和 O(1) 所有权转移。
2. 原始数据旧管线 `DaqAIContext.EnqueueRawData/EnqueueStatData` 使用独立有界消费者，并明确数组所有权；禁止把随后会被原地转换的同一个 `double[,]` 同时借给异步队列。
3. 当前统计定时器已注释，但 `EnqueueStatData()` 仍持续保存最多 100 批引用；确认无业务依赖后删除这条旧路径，若仍需要则建立真正的持续消费者。
4. UI 继续只保留最新数据，不允许 UI 消息队列反压 DAQ 处理。
5. 每个同步步骤设置耗时直方图和最大值，发生队列预警时记录“正在执行的方法/订阅者”。

### 8.2 降低托管分配和全代 GC

1. 用 ETW/EventPipe 或等价运行时事件记录 GC 暂停时长，而不只记录次数。
2. 复核每批创建的诊断对象、字典、数组、字符串和 UI 点集；热路径使用池化结构或预分配环形缓冲。
3. 诊断 CSV 导出只能在冻结快照后由低优先级单消费者执行，不能与采集热路径争用大量分配和文件句柄。
4. 评估 NI-DAQmx 与全部本地依赖的 64 位兼容性；兼容后再把现场进程从 32 位迁移到 64 位。不能在未验证驱动兼容性的情况下直接切换。
5. 仅扩充 `DaqProcessingQueueCapacity` 或仅把 100 ms 改大都不是修复，会延迟发现并增加丢失窗口。

## 9. 长期无人值守的进程级自愈

应用内部恢复之外，还需要一个独立于主进程的 Windows 服务/守护进程：

1. 主程序每秒写一次单调时钟心跳，并报告 DAQ generation、两级队列深度、最后新鲜回调、恢复状态和当前试验计划检查点。
2. 连续 5 秒无心跳或发生未处理异常：守护进程先调用独立安全输出路径确保全部 DO OFF，再重启主程序。
3. 重启后先执行：全部输出安全化、DAQ 枚举和新鲜度验证、电源身份/保护/电压验证、液压安全预检、数据文件一致性检查。
4. 所有预检通过后，只能从“下一完整圈”恢复，不能从半圈中间继续。
5. 建议重启预算为 10 分钟内最多 3 次；超过预算保持断电并远程通知 `SystemFault`。这仍不是硬件报警，除非随后取得硬件确认依据。

无人值守不等于任何情况下都带电继续。数据不可信时必须立即安全关断；无人值守能力体现在软件能够自动定位、重建、完整预检并继续下一圈，而不是隐去系统故障。

## 10. 必须通过的测试与验收门槛

### 10.1 自动化竞态测试

至少补齐以下确定性测试：

1. `BackgroundQueueFull` 发生时电源监控正在读：计划关电不得产生 `UnexpectedOutputOff`。
2. 恢复成功和超时在同一时刻竞争：同一关联号只能出现一个终态。
3. 恢复过程中点击“停止全部”：后续不得出现定时器恢复、通道恢复或电源重新开启。
4. 暂停、成功、失败同时请求快照：不得覆盖、不得文件占用，每个阶段证据完整。
5. 注入 120 ms 回调空窗后恢复正常：必须安全关断、自动恢复、从下一整圈继续；不得产生硬件报警。
6. 回调持续陈旧但设备仍可枚举：触发 `SystemFault` 和看门狗，不得伪报硬件。
7. 拔掉 DAQ 或注入明确设备不存在错误：重复重建和设备查询失败后，必须产生硬件确认报警。
8. 注入程控电源真实保护跳闸：必须锁存硬件组报警，不能被软件恢复自动清除。

### 10.2 压力和故障注入

- 人为阻塞原始数据订阅者 2 秒；
- 人为阻塞 SQLite/文件写入 2 秒、10 秒；
- 网络共享不可用、磁盘满、文件被占用；
- UI 线程阻塞 5 秒；
- 注入 50、100、250、1000 ms 的托管/调度停顿；
- 电源监控读事务正在进行时触发 DAQ 恢复；
- 恢复的每一个 `await` 点同时注入人工停止；
- 连续多次 DAQ generation 重建和旧回调迟到。

### 10.3 无人值守验收指标

建议分两阶段：先 72 小时预验收，再 168 小时正式老化。

| 指标 | 验收标准 |
|---|---|
| 误硬件报警 | 0 次 |
| 恢复终态 | 每个关联号恰好 1 个终态 |
| 人工停止后自动复活 | 0 次 |
| 计划关电被判 `UnexpectedOutputOff` | 0 次 |
| 处理队列满 | 正常稳态 0 次；注入时能安全恢复且不伪报硬件 |
| 短时回调空窗 | 安全关断并自动恢复，下一完整圈继续 |
| 内存 | 无持续增长；长稳态无周期性大幅抖动 |
| GC | 记录真实暂停时长；稳态不得出现导致控制超过 100 ms 的托管停顿 |
| 快照 | 首发、恢复、失败证据均完整且不可覆盖 |
| 真实硬件故障 | 必须可靠锁存并要求人工复位 |

## 11. 最终判定

### `1505` 备份

直接触发是 Dev1 后台处理队列满；最终无法自动继续和产生硬报警的决定性原因，是恢复状态机、电源计划切换和监控之间的软件竞态。**不是硬件故障。**

### `1507` 备份

直接触发是 Dev1 一次约 113.6 ms 的回调空窗；DAQ 随后快速重建成功，程控电源和队列没有硬件异常证据。高频 GC/运行时压力值得重点整改，但当前快照不能证明唯一暂停来源。**不能判为硬件故障。**

### 是否同因

不是同一个直接触发，但都是软件实时性、恢复编排和故障分类设计不完整造成的误硬件报警。永久解决必须同时完成：

1. 数据不可信时立即安全关断；
2. 软件瞬态自动恢复并继续下一完整圈；
3. 恢复失败单独归类为系统故障并由看门狗自愈；
4. 只有取得独立、可复核的硬件证据，才允许锁存最终硬件报警。
