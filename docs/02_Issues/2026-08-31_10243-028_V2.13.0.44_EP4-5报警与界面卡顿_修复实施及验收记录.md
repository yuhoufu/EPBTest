## 1. 实施结论

V2.13.0.44 已完成本次事故的代码级闭环整改：

- DAQ 显式建立 10 秒输入缓冲裕量，NI-DAQmx `-200279` 被强类型识别为 `DaqInputBufferOverflow`，交给现有唯一恢复状态机安全停机和自处理；
- 同一正式槽的重复根故障只允许触发一次安全失败和一次 StopAll，避免 EPB4/5 同源故障扇出成关闭、日志、持久化与 UI 风暴；
- 周期终态改为单向、单调更新，禁止终态回写为 `running`，并在启动时审计闭合旧进程遗留周期；
- 高频 UI 状态采用 latest-only 合并投递，每类状态最多保留一个待执行回调，避免故障风暴堵塞 WinForms 消息队列；
- Watchdog 在窗口仍响应但控制进度停止时，先给主程序一次自处理机会；5 秒内没有确认即升级为安全接管，不再无限等待；
- 主程序被强杀、崩溃且无法生成优雅关闭墓碑时，Watchdog 以启动时预置的哈希绑定凭据、精确旧进程退出证据和独立 SafetyAgent 物理安全回执完成自恢复；
- 新版本启动时可受控撤销并清退同产品旧版本孤儿 Watchdog，避免 V2.13.0.42 与当前 Sidecar 长期并存；
- 主程序及恢复链所有程序集版本统一为 V2.13.0.44，并创建带说明的 Git 标签 `2.13.0.44`。

代码构建与自动化回归已经通过。由于本机不能替代 NI、CAN、液压、电源和现场负载，本文不把现场 24/72 小时验证虚报为已完成；V2.13.0.44 的代码候选状态为 **PASS**，正式无人值守现场放行状态为 **条件放行，完成第 9 节现场验证后转 GO**。

## 2. 修复目标与安全边界

本次实施遵循以下目标：

1. 正常运行路径不新增数据库、网络或硬件同步等待，不降低 2 kHz DAQ、10 ms 控制批次和 UI 主线程的实时性；
2. 软件故障先在进程内合并、自处理，避免把一个 DAQ 根故障放大成多个通道硬件报警；
3. 进程内无法恢复时，由 Watchdog 在有界期限后接管；
4. 任何自动拉起必须先取得独立物理安全证据，不能为了“自动恢复”绕开 fail-closed；
5. 不放宽 DAQ 新鲜度阈值，不屏蔽 EPB4/5 报警，不把旧压力值当作新鲜安全证据；
6. 崩溃后的历史试验圈只能闭合为作废终态，禁止续算正式完成数。

| EPB4/9 出现 `running`、`end_time < start_time` | 终态条件更新只允许从开放态进入终态；终止时间不早于开始时间；终态不可回退；启动恢复审计闭合遗留开放圈 | 正常写盘仍使用既有后台事务；没有 UI/控制线程同步等待 |

| 强杀后旧主程序无法写 `ClosingTombstone`，恢复永久阻断 | 启动期预置崩溃恢复种子；精确证明旧进程退出后生成 schema 4 崩溃安全交接；SafetyAgent 独立断能、复核并签发回执后才拉起 | 种子只在会话启动时耐久写入；运行期无持续额外负载 |
| V2.13.0.42 旧 Sidecar 长期存活 | 只对同产品、旧版本、旧主进程已退出且身份精确匹配的 Sidecar 先撤销会话，再等待退出，必要时才精确结束该进程 | WMI 发现失败时保持 no-op；不会模糊结束其他程序或活跃安全事务 |

## 4. 自处理与自恢复流程

### 4.1 进程内自处理

```text
DAQ 样本失鲜或缓冲溢出
  -> 锁存唯一 DAQ 根事故和关联号
  -> 各受影响通道加入同一安全事务
  -> 每个电气组复用在途 OFF，整机只创建一个 StopAll
  -> 周期终态单向封存
  -> UI 只显示最新安全状态
  -> DAQ 恢复由既有唯一恢复状态机换代执行
```

安全停止仍然保留。V2.13.0.44 消除的是错误报警归因、重复事务和界面风暴，不会让 EPB4/5 在失去新鲜电流/压力证据后继续运行。

### 4.2 窗口可响应但控制失活

```text
ControlProgress 陈旧、窗口仍响应
  -> Watchdog 只发送一次 ResponsiveApplicationControlRepair
  -> 主程序拥有 5 秒自处理窗口
  -> 收到 StopAll/控制进度确认：继续受控观察
  -> 期限内无确认：ResponsiveControlRepairDeadlineExceeded
  -> Watchdog 进入逻辑接管，不再被 WM_NULL 成功阻止
```

### 4.3 强杀或崩溃后的无人值守恢复

```text
会话启动时写入哈希绑定 CrashRecoverySeed
  -> Watchdog 冻结旧进程 PID + StartUtcTicks + 映像身份
  -> 精确证明旧进程已退出，排除 PID 重用
  -> 撤销旧执行许可
  -> 生成 CrashRecoverySafetyHandoff（不伪造优雅关闭）
  -> 独立 SafetyAgent 执行 DO OFF / AO 安全值 / PSU OFF / 压力复核
  -> 校验新鲜、完整、身份绑定的安全回执
  -> 生成 LaunchIntent 并拉起唯一新主进程
  -> 新进程启动审计闭合旧 running 圈
  -> 保持安全待命或按既有受控恢复策略继续
```

以下任一条件不满足时仍保持安全阻断，不自动拉起：旧进程退出身份不确定、种子/许可哈希不匹配、SafetyAgent 失败、输出未确认 OFF、压力或电源证据不完整。

## 5. 不影响正常运行的设计说明

| 关注点 | 约束与实现 |
|---|---|
| DAQ 实时性 | 仍按原有每设备异步连续读取和固定批大小工作；新增缓冲位于 NI 驱动侧，未把日志、文件或 UI 工作移入回调 |
| 控制链 | 根故障门为常数时间原子状态；只在事故时抑制重复 StopAll，不改变正常启停顺序 |
| UI | 生产者不等待 UI；旧状态允许被新 revision 覆盖；消息队列不随事件量增长 |
| 持久化 | 仍由后台写盘；新增的是 SQL 终态条件和启动审计，不在 DAQ/控制线程查询 SQLite |
| Watchdog | 健康时只执行原有探针；5 秒接管期限只在控制心跳陈旧且已发修复请求后生效 |
| 崩溃凭据 | 会话种子不证明设备安全，只提供身份连续性；物理安全必须由退出后的独立 SafetyAgent 重新验证 |
| 旧版清理 | 先撤销、等待，再精确结束；目标必须同时满足同产品、旧版本、旧主进程死亡和身份匹配 |

## 6. 配置与可观测事件

新增配置位于 `MTTfTest/App.config`：

```xml
<add key="DaqInputBufferSeconds" value="10" />
```

- 有效范围：2～30 秒；
- 缺失、非数值、NaN、Infinity 或越界时回退到 10 秒；
- 实际每通道点数按 `sampleRate × seconds` 计算、按批大小对齐，并限制为不超过 1,000,000 点；
- 现场不得通过减小该值或放宽样本新鲜度阈值掩盖问题。

重点事件码：

| 事件码 | 含义 |
|---|---|
| `DaqInputBufferOverflow` | 捕获 NI `-200279` 或等价缓冲覆盖信息，进入采集根事故处理 |
| `ResponsiveApplicationControlRepairRequested` | 窗口可响应但控制失活，已给主程序一次自处理机会 |
| `ResponsiveControlRepairDeadlineExceeded` | 5 秒内未收到控制修复确认，Watchdog 升级接管 |
| `CrashRecoverySeedCommitted` | 主程序启动时已持久化哈希绑定的崩溃恢复种子 |
| `CrashRecoverySafetyHandoffCreated` | 旧进程精确退出后，Sidecar 已生成崩溃安全交接 |
| `StaleSidecarRetired` | 同产品旧版本孤儿 Sidecar 已受控撤销并退出 |
| `RecoveryReady` | 独立安全回执及恢复前置条件完整，可以生成拉起意图 |

## 11. 最终说明

本次方案的核心不是“遇错直接重启”，而是：正常运行不增加阻塞；故障先归并并在进程内自处理；控制失活时在有界期限后由 Watchdog 接管；主进程强杀后由独立 SafetyAgent 重新证明物理安全；只有证据完整时才自动拉起。这样才能同时满足“不影响程序运行”“自处理”“自恢复”和安全不可绕过四个目标。
