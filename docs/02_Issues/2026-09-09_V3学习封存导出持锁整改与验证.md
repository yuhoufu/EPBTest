# V3 学习封存导出持锁整改与验证

## 结论与范围

B轮现场的首个故障是持久化积压，恢复许可RunId不一致是后续第二个故障。本轮修复一条确实能阻塞同设备写入的生产路径：学习结束使用SealAndExportCycle，旧实现持有通道Gate完成CSV/BIN编码、发布和文件重读校验；设备批次写入又需要取得该设备所有通道Gate。一个通道慢导出会阻塞同设备其它健康通道。

现场时序与此机制相容，但现存快照没有完整捕获Dev1在途调用栈，因此不能把这条路径称为唯一现场根因。此前JXCQ探测只调用CompleteCycle，未覆盖实际学习封存导出，本轮已纠正该覆盖缺口。

## 已实施

- 锁内领取圈并复制样本；设置SealInProgress，保留当前圈身份，阻止重复领取和其它终态修改。领取后的新批次不能继续归入已冻结的圈；生产调用方仍须先通过既有TryWaitForCycleDurableCutoffAsync。
- 对独立样本副本执行文件编码、原子发布和校验时释放通道写入锁。未领取的同设备通道继续写入。
- 重新取得通道锁后验证语义、提交数据库终态，只有真实验证及提交成功才发布成功进度。失败路径仍封存为failed，不伪造成功或跳过耐久校验。
- 增加封存生命周期读写门。Dispose先拒绝新的封存申请，等待在途封存提交后再把存储置为已关闭；避免导出线程收尾时数据库或MMF先被释放。
- 同时保留上一轮Watchdog恢复许可RunId修正及生产准入回归。
