## 2. 结论先行

V2.13.0.29 已完成根因文档列出的七项 P0 最小修复：

1. 正式圈和启动定位共用“欠目标高负载平台约 200 ms 即 OFF”的保护，禁止再等待 5 秒或 9 秒时限。

## 3. 高负载平台零容忍保护

### 3.1 判据

V2.13.0.29 沿用现有自适应窗口，不另建一套易漂移模型。正向电流满足以下全部条件时，判定为 `ForwardUnderTargetHighLoadStall`：

```text
高负载下限 = max(max(1A, 空载基线) + 2A, 目标电流 × 60%)
合格完成下限 = min(目标电流 - 可接受欠量, 目标电流 × 90%)

有效峰值 >= 高负载下限
有效峰值、当前电流 < 合格完成下限
连续窗口跨度 >= ForwardProgressConfirmMs（安全归一化后至少 200ms）
窗口 P10 >= 高负载下限
窗口 P90 < 合格完成下限
窗口斜率 <= ForwardMinimumRiseSlopeAperMs
```

对本项目 15 A 目标，60% 高负载区从 9 A 起，90% 合格线为 13.5 A。9 A 至 13.5 A 之间如果形成连续约 200 ms 的无进展平台，本圈立即作废并提交高优先级 OFF；不得继续保持到 5000/9000 ms。

### 3.2 为什么既安全又不过敏

- 单点尖峰、短促换向扰动或不足确认窗的过渡不会触发，因为要求完整窗口且 `P10` 也处在高负载区。
- 正常持续上升不会触发，因为斜率必须低于最小进展斜率。
- 达到 13.5 A 合格线的平台仍由既有近目标/低目标逻辑带预警完成，不会被欠目标堵转规则误报。
- 永久报警与物理断电分层：单圈平台立即 OFF；普通故障连续确认仍由管理层按默认 3 圈门槛决定是否锁存停机。保护不能为了降低报警敏感度而延长本圈带载时间。

### 3.3 断电闭环

- 正式圈的所有 `HardFault/ClampReached/ReleaseCompleted` 继续先调用高优先级终态 OFF，再发布轨迹和处理状态。
- 启动定位检测到相同平台故障后，先执行 `StartupForwardTerminalProtection` 高优先级 OFF，再轮询确认电流清零。
- OFF 命令失败、DAQ 样本陈旧或电流未清零，均禁止进入后续定位；电流未清零路径继续升级对应电源组安全隔离。

- `Controller/EpbCycleRunner.Adaptive.cs`
- `Controller/EpbCycleRunner.StartupPositioning.cs`

## 4. 恢复、启动与批量归因修复

### 4.1 `RetryReady` 与安全终态分离

新增 `CommitRecoveryIncidentStateForRetry`，只允许恢复到 `Starting`、`Learning`、`Running` 或 `WarningRunning`。提交前必须逐通道校验同一 RunId、RunEpoch、OwnerKind、TargetPhase、OwnerId 和 OwnerGeneration。

学习落盘重试回到 `Learning`，启动定位重试回到 `Starting`；两者都保留 Runner、Timer 和执行许可。只有真正无法恢复的 `SafeTerminal` 才撤权、移除运行资源并进入 `StartBlocked`。

### 4.2 可恢复预警 Owner-first

原链路先请求 Timer 暂停，随后才尝试恢复，因此可能出现 `Paused + Owner=None`，被看门狗在 5 秒后正确接管。新链路顺序为：

```text
单圈保护 OFF
  -> 登记不可变 RecoveryIncident/FormalTimer Owner
  -> 发布 Recovering + 精确 owner 身份
  -> Owner 内请求 Timer 暂停、液压释放和持久化截止
  -> 未来完整正式槽重入或提交安全终态
```

看门狗仍保留原来的孤儿暂停接管规则；修复的是主程序不得再制造无 Owner 的暂停状态，而不是放宽看门狗。

### 4.3 启动定位真实重试

每次机械定位尝试计数前先验证 Runner 和执行许可。若旧终态路径曾错误撤权，只在以下条件全部成立时原位修复：同一活动 RunId/RunEpoch、生命周期仍为 `Starting`、未撤销全局上电授权、无需重启、通道仍启用且输出已确认 OFF。

框架修复失败使用独立计数，连续 3 次才熔断为 `StartupPositioningExecutionFramework`；它不冒充机械定位失败。所有定位熔断异常携带 `FailedChannel`。

### 4.4 批量失败不连坐健康卡钳

- 有 `FailedChannel` 的熔断只把该通道发布为 `StartBlocked`。
- 已有 `ChannelStartFault` 证据时只使用证据通道。
- 无通道身份的 DAQ、全局电源或基础设施熔断仍按整批作用域处理。
- 健康同批通道执行安全清场并进入 `ManualStopped/StartPeerFailedSafeStopped`，保留再次启动资格。

主要修改文件：

- `Controller/EpbManager.cs`
- `Controller/EpbManager.BatchStart.cs`
- `Controller/EpbManager.StartupPositioning.cs`
- `Controller/SoftwareSelfHealingLoop.cs`

## 5. 停止与关闭修复

### 5.1 停止阶段职责

`RevokeExecutionAuthorization` 的 2 秒预算现在只做常数时间动作：关闭批次/正式阶段准入、锁存上电撤销、递增 RunEpoch、撤销通道执行许可、终止液压代次。

`EndBatchSession`、Timer/Runner/CTS 和液压参与者清理统一进入 `ClearTimerAndRunner` 的 5 秒预算。这样不降低立即隔离能力，同时避免正常四通道清场长尾被误判为 `SafeButRestartRequired`。

### 5.2 主窗体共享退出任务

人工停止、实时监控关闭、Watchdog 请求退出和主窗体“×”共用 `_watchdogShutdownTask` 与 `_watchdogCloseTask`：

- 任一入口取得 `RuntimeShutdownReceipt.IsTerminal=true` 后统一设置关闭授权；
- 重复点击不再静默返回，而是加入正在执行的退出任务；
- 等待中显示“正在安全退出…”；
- 子窗体释放、Watchdog 终止或资源释放失败时恢复窗口状态，允许再次安全收口。

主要修改文件：

- `Controller/EpbManager.StopSafetyOperations.cs`
- `MTTfTest/Main_Frm.WatchdogUi.cs`
