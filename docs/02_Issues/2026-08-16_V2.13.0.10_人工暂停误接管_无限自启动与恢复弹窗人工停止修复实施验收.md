# V2.13.0.10 人工暂停误接管、无限自启动与恢复弹窗人工停止修复实施验收

## 1. 实施结论

本文落实了 [V2.13.0.9 根因及解决方案](./2026-08-16_10358-029_V2.13.0.9_人工暂停误接管与无限自启动失败根因及解决方案.md) 中与本次现场故障直接相关的 P0 整改，并将主程序与独立 Watchdog 统一升级为 **V2.13.0.10**。

本次代码级整改结果：

1. 人工暂停不再采用“带电超过固定 5 秒即接管”的错误规则，改为 Controller 发布权威暂停阶段、进展版本、带电通道清单和动态硬截止，Watchdog 只在明确安全故障，或超过硬截止且确实无进展时接管。
2. 操作员点击暂停后，界面立即显示“暂停处理中”，并区分“等待当前圈”“确认断能”“保存数据”；完成全部安全边界后才显示“暂停”。
3. 恢复预检遇到 `*IDN?`、Power OFF 未确认等硬件不可用问题时，不再退出当前恢复进程并反复创建新 PID；改为同一恢复进程内按 `5/15/30/60 s` 原地重新探测。
4. Watchdog 对恢复进程启动、附着或初始化失败增加最多 3 次进程级重拉上限；同一失败指纹连续 3 次后打开熔断器，禁止继续 `Process.Start`。
5. Watchdog 所有恢复过渡弹窗新增红色按钮 **“停止自动恢复并关闭”**。点击后先请求全断能，等待最多 15 秒；仍未退出时只终止身份严格匹配的恢复进程，写入双位置撤销标记并结束 Watchdog，不再自动启动新进程。
6. 程控电源仍坚持 fail-closed：身份或 OFF 状态未确认时绝不进入学习；失败连接会被销毁并在下次探测建立新连接。
7. 高频成功 SCPI 分阶段日志改为内存环形缓冲和 60 秒聚合；失败、取消、超时仍立即落日志，并附带最近通信轨迹。

因此，截图中“只能通过任务管理器杀进程”的操作缺口已经从 Watchdog 自有窗口内闭环；V2.13.0.9 的无限 GUI 自启动链也已被拆成“有界进程重拉 + 单进程低频硬件探测”。

> 边界说明：本次已完成代码、Release 构建和自动化回归。真实 EPB、DAQ、程控电源及网络故障注入仍需按第 9 节做现场验收，不能用开发机测试代替物理断能验证。

## 2. 故障链与修复后的行为

### 2.1 人工暂停

V2.13.0.9：

```text
人工暂停
  -> 正常等待当前圈释放
  -> 固定 5 秒仍带电
  -> Watchdog 误判停滞并建立 StopAll 栅栏
  -> 当前圈收尾命令被拒绝
  -> 暂停被制造成安全异常
```

V2.13.0.10：

```text
ManualPauseRequested
  -> CurrentCycleDrain
  -> PhysicalOffConfirm
  -> PersistenceDrain
  -> Completed / ManualPaused
```

对 15 秒试验周期，动态暂停硬截止为：

```text
min(300 s, max(30 s, 2 × Period + 30 s)) = 60 s
```

Watchdog 判定规则变为：

- 阶段、进展版本或带电通道集合持续收敛时，不得接管；
- 已全部断能而正在排空持久化时，不得仅按耗时接管；
- Controller 明确发布 `ManualPauseSafetyFault` 时立即安全接管；
- 超过 Controller 给出的硬截止，并且仍有带电通道且至少 5 秒无进展时才接管；
- 已宣告 Paused 却仍有带电通道并持续 5 秒，按状态矛盾接管；
- 人工暂停异常接管仍只能回到空闲态，不能自动续跑。

### 2.2 硬件不可用与自动恢复

V2.13.0.9：

```text
恢复进程启动
  -> *IDN? / Power OFF 预检失败
  -> 进程退出
  -> Watchdog 5/15/30/60/60... 秒反复创建新 PID
```

V2.13.0.10：

```text
Watchdog 有界启动恢复进程
  -> 完整 StopAll / PowerSafetyProbe
  -> 硬件不可用
  -> 当前恢复进程进入 HardwareSafetyProbePending
  -> 5/15/30/60 s 原地建立新连接并重新完整预检
  -> 同指纹第 3 次后 SafeIdleHardwareUnavailable
  -> 继续单进程低频探测，禁止开始和学习
  -> 硬件恢复后再次完成完整 StopAll
  -> 只有全部 CanRestartInProcess 证据成立才恢复学习
```

“继续低频探测”不是继续自启动：PID 不变，不产生新的 GUI 进程，不允许机械动作，并且操作员可随时点击弹窗按钮彻底取消。

## 3. 恢复弹窗人工停止闭环

恢复过渡窗原来关闭按钮被禁用，窗口关闭事件又只执行隐藏；遇到恢复循环时操作员只能进入任务管理器。现在窗口固定提供：

```text
停止自动恢复并关闭
```

按钮采用单次触发，点击后的安全顺序为：

1. 在与所有 `Process.Start` 共用的互斥门内锁存 `ManualStopRequested`，禁止任何后续退避或进程重拉；
2. 向当前主程序发送 `RequestStopAll`；
3. 窗口显示“正在安全停止”“不会再次自动启动”，按钮禁用，避免重复操作；
4. 最多等待 15 秒接收 `StopCompleted`、`PhysicalStopConfirmed` 或进程自然退出；
5. 超时仍存活时，使用 PID、进程启动时间、可执行路径等身份条件复核，只终止属于当前会话的进程；
6. 在本机 Watchdog 目录和项目封存目录分别写入撤销标记；
7. 发布终态 `OperatorRecoveryCanceled`，关闭恢复窗并结束 Sidecar；
8. 不调用空闲重启，也不再创建任何新进程。

`StopCompleted`、`RunStopped`、`ApplicationClosing` 等普通回执在此期间只作为停止确认，不再抢先发布普通终态；弹窗人工停止流程是唯一终态所有者，可避免“按钮已点击但另一接管任务仍启动空闲进程”的竞态。

如果通信管道已经断开，步骤 2 可能无法送达，但步骤 5 的身份匹配终止、步骤 6 的持久撤销和步骤 8 的禁止重拉仍能保证取消动作收口。按钮不是跳过断能证明的“强制继续”，而是“停止恢复并关闭”的安全出口。

## 5. 不可降低的安全约束

以下规则在本次修复中没有放宽：

- `*IDN?` 失败不能把未知设备当成目标电源；
- `OUTP OFF` 没有可靠回读时，`PowerOffConfirmed=false`；
- Motor、Power、Pressure、Persistence、Logical 任一项未通过，均不得 `CanRestartInProcess`；
- HardwareUnavailable 状态禁止开始、禁止学习、禁止新机械动作；
- 清理旧进程重启锁存必须发生在新恢复进程中，且以最新 StopAll 全项成功证据为前提；
- 过渡窗人工停止只能取消恢复并关闭，不能“忽略报警后继续”。

## 6. 日志容量治理

`PswTcpClient` 不再为每次成功命令持久写入 Transmit、FirstByte、FullLine 等全量 Info。成功阶段保留在最多 256 条的内存轨迹中，并每 60 秒输出一次数量和最大耗时聚合。

以下事件仍即时落盘：

- TCP/SCPI 超时；
- 发送、读取、解析失败；
- 取消；
- 连接或流被销毁；
- 事故发生时的最近通信轨迹。

这样既降低正常 2 kHz 长稳期间的日志放大，也保留定位 `*IDN?` 卡在 Connect、Write、FirstByte 还是 FullLine 的证据。

## 9. 现场验收清单

### 9.1 人工暂停

1. 在正向刚开始、峰值附近、反向刚开始和 OFF 确认阶段分别暂停；
2. 当前圈收尾持续 5～20 秒时确认 PID 不变，界面显示正确暂停阶段，Watchdog 不接管；
3. 确认最终所有通道 DO OFF、电源 OFF、压力安全、持久化边界闭合，再显示“暂停”；
4. 注入阶段持续进展但总耗时超过 5 秒的情况，确认不会误报；
5. 注入带电集合不收敛并超过动态截止，确认 Watchdog 安全接管且只回空闲态；
6. 暂停处理中结束主程序，确认 Sidecar 断能并回空闲，不自动续跑。

### 9.2 电源不可达与人工取消

1. 让组 1、2、4 的 `*IDN?` 连续 5 分钟不响应；
2. 确认只存在一个恢复主进程，PID 不随 60 秒探测变化；
3. 确认所有输出保持 OFF、开始按钮禁用、无学习和机械动作；
4. 第 3 次同指纹失败后确认状态为 `SafeIdleHardwareUnavailable`；
5. 点击“停止自动恢复并关闭”，确认 15 秒内安全退出，必要时只结束当前身份匹配进程；
6. 观察 2 分钟，确认主程序和 Watchdog 都没有再次自动出现；
7. 不点击取消时恢复仪器通信，确认系统从完整身份、OUTP OFF、遥测、压力和持久化预检重新开始，不能跳过任一项。

### 9.3 长稳与证据

1. 使用现场双 DAQ、5 通道和 2 kHz 配置运行 48 小时；
2. 注入网络短断、仪器 SCPI 无响应、磁盘高负载和日志轮转；
3. 确认没有无限 `Process.Start`、未观察任务异常和无界日志增长；
4. 确认事故包包含失败指纹、最近通信轨迹、恢复尝试和最终终态；
5. 正式包生成并验证 manifest、Git commit、dirty 状态和全量 SHA-256。

## 10. 发布建议

V2.13.0.10 已达到代码级修复和针对性自动化验收条件，但在完成第 9 节真实设备故障注入与长稳前，应标记为现场验证候选版本，不应直接宣称完成无人值守量产验收。

现场发布时必须同时替换主程序和 Watchdog，不得混用 V2.13.0.9 Sidecar；启动后先核对窗口版本与产物哈希，再开始试验。若任一 Power OFF 证据无法确认，应保持安全等待并排查设备，禁止通过修改配置或跳过 `*IDN?` 强行续测。
