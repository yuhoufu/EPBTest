# V2.14.2.0 取消发布审批门禁与正式包简化部署说明

## 1. 结论

按现场使用方决定，`V2.14.2.0` 改为正式包直接安装、直接运行：软件不再根据 `releaseStatus`、`deploymentApproved`、`gitDirty` 或 24/72/168 小时记录批准或拒绝安装、主程序启动和 LastKnownGood 晋升。程序的投入运行、停用和现场验收状态由操作人员负责。

本次取消的是行政/流程审批门禁，不是设备安全门禁。以下底线继续保持：完整包逐文件 SHA256、版本和运行身份一致性、DPAPI 槽封印、Supervisor 单实例许可、旧进程退出证明、物理断电回读以及确认硬件故障隔离。文件损坏、版本混装、槽身份不符或无法形成安全证明时，系统仍会 fail-closed。

## 2. 为什么此前显得复杂

`V2.14.1.0` 同时把三类事实混在“是否允许启动”中：

1. 包是否完整、是否被替换；
2. Supervisor 是否能证明单实例和安全接管；
3. 这个版本是否已被流程批准、是否完成 168 小时现场验证。

前两类决定软件能否安全执行，必须由机器强制校验；第三类属于版本管理决定。此前第三类也被写成机器启动门禁，导致完整包即使可以安全运行，仍可能出现 `PackageNotApproved` 或候选状态不被识别，增加部署复杂度。

`V2.14.2.0` 将两者分离：机器只强制包完整性与设备安全，发布状态由操作人员管理。

## 3. 门禁变化矩阵

| 检查项 | V2.14.1.0 | V2.14.2.0 | 原因 |
|---|---|---|---|
| `FIELD_CANDIDATE_PENDING_168H` | 安装/启动要求 | 不要求 | 发布状态由操作人员决定 |
| `deploymentApproved=true` | 安装/启动要求 | 仅保留为兼容记录，不参与批准 | 不再让布尔字段代替现场决定 |
| `gitDirty=false` | 决定是否批准 | 仅参与自身运行身份匹配 | 防止错包，但不审批用途 |
| 24/72/168 小时证据 | LKG 晋升硬门禁 | 可记录，不阻断操作人员显式晋升 | 长稳结论由现场负责 |
| 文件 SHA256 | 强制 | 强制 | 防止缺失、替换和传输损坏 |
| EXE/组件版本一致 | 强制 | 强制 | 防止版本混装 |
| DPAPI 槽路径和 manifest | 强制 | 强制 | 防止错误槽获得启动权限 |
| 旧 PID/启动时间/permit | 强制 | 强制 | 防止 PID 重用和双主进程 |
| 物理断电与两次回读 | 强制 | 强制 | 防止未断能时恢复或换进程 |
| 硬件故障最小域隔离 | 强制 | 强制 | 防止故障设备自动重新上电 |

## 4. 实施内容

### 4.1 正式包身份

- 主程序、Controller、Watchdog、Protocol、Client、SafetyAgent、SafetyHardware 和 SessionAgent 统一升级到 `2.14.2.0`。
- 干净发布流水线写入 `releaseStatus=FORMAL_RELEASE`。
- 正式发布仍执行全量自动化回归；这是出包质量检查，不再被解释为现场运行审批。

### 4.2 安装与修复

- 安装器不再检查 `releaseStatus`、`deploymentApproved` 和 `gitDirty` 的批准组合。
- `Verify-Release.ps1` 删除 `RequireDeploymentApproved` 参数和候选状态白名单。
- 一键入口改名为 `一键安装正式版.cmd`，流程只显示“验证文件和 SHA256”与“安装运行环境”。
- `一键修复.cmd` 使用相同的完整性校验，不再要求候选批准。
- 快捷部署安装逻辑修订为 `QUICKDEPLOY_R7`；外层交付压缩在后续升级为 `QUICKDEPLOY_R8`，固定使用本机 7-Zip Ultra/LZMA2 固实压缩并生成独立 SHA256。

### 4.3 主程序与 LastKnownGood

- `ReleasePackageVerifier` 不再返回 `PackageNotApproved`。
- 任意状态的完整包均可由操作人员管理；非 VS 包仍必须与编译进程序的 commit、buildUtc、configSha256 和 gitDirty 精确匹配。
- `deploymentApproved` 字段改为可选兼容信息，值为 false 不阻断运行。
- 操作人员显式执行 LastKnownGood 晋升时，不再要求 168 小时 PASS JSON；槽仍需重新验证、封印并原子切换。

## 5. 修复不变量

1. 取消发布审批不能扩大对错包、损坏包或混装包的信任。
2. `releaseStatus` 只描述用途，不授予物理上电权限。
3. LaunchCapability 仍必须绑定 Session、permit、桌面会话、EXE 路径和哈希、参数哈希、nonce 与有效期，并持久 CAS 单次消费。
4. 进程替换前仍必须形成旧进程退出、逻辑静止、回调隔离和硬件资源释放证明。
5. 任意恢复仍先断能、封圈、重建、复核，再恢复上电。
6. 确认的卡钳、液压或电路硬件故障不得因取消发布审批而自动重新使能。
7. 包无法验证或安全证明无法形成时，保持断能并进入安全等待/告警，而不是绕过检查。

## 6. 正式包的最短使用方法

1. 在旧程序中安全停止，确认卡钳、液压、AO 和程控电源均已 OFF，然后退出旧程序。
2. 把完整 ZIP 复制到远程工控机本地磁盘并完整解压。
3. 双击 `一键安装正式版.cmd`；已安装旧版时也可以直接安装覆盖，异常时运行 `一键修复.cmd`。
4. 安装成功后双击桌面的 `MT EPB 试验系统 V2.14`。
5. 软件不再要求填写或修改候选/批准状态；现场是否持续运行由操作人员决定。

禁止只复制单个 EXE/DLL，禁止手工修改 `build-identity.json`、`SHA256SUMS.txt` 或 `package-slot.v5.json`。这些文件用于证明运行的确实是同一个完整包。
