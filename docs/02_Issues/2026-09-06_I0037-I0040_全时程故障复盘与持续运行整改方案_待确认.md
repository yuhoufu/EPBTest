# I0037—I0040 全时程故障复盘与持续运行整改方案

事件日期：2026-09-05　｜　文档日期：2026-09-06　｜　状态：待用户确认，尚未实施产品修改

分析对象：试验 10243-028；V2.16.0.0 与回退后的 V2.14.2.11；启用卡钳 4、5、7、8、9、12。

## 1. 先回答最关心的问题

**你的判断有证据支持：2.16 没有解决持续稳定运行问题，而且相对 2.14.2.11 确实增加了新的故障路径。回退后再次发生“启动受阻、系统故障”，说明还存在两个版本共有的恢复缺陷。** 当前不能把任何一个版本视为已经通过现场无人值守稳定性验收。

这次不仅核对了截图，还读取了四份封存的运行、警告、错误和界面日志、数据库、运行配置、恢复检查点、事故快照、看门狗事件及退出回执，并对照 2.16 实际发布源码。另用原发布包程序集完成了两个不接硬件的缺陷复现。

| 核心结论 | 证据强度 | 对运行的影响 |
|---|---|---|
| 2.16 新增的“丢弃陈旧批次”路径同时跳过原始数据持久化，遇上严格连续序号校验后永久重试 | 现场反复出现序号断裂；源码闭环明确 | 四个写盘阻塞事件、六条设备级断序错误，进而导致系统故障、退出受阻 |
| 2.16 新增的新鲜度快照存在时间戳读取竞争，能够把新鲜数据判成无限超时 | **原发布 DLL 已确定性复现** | 可无谓触发 DAQ 停机恢复；17:35、18:59 两次异常高度可疑，但触发瞬间字段不足，不能逐次断言 |
| 2.16 自动重启身份校验对同一 SHA-256 的大小写敏感 | **原发布 EXE 中对应逻辑已确定性复现**；现场三组同类拒绝事件 | 程序已经退出，却不能自动拉起，必须再次人工启动 |
| 19:24 DAQ“恢复成功”后，学习任务和业务执行没有真正恢复 | 截图、状态日志、命令日志、数据库一致 | 至少 6 分 36 秒没有新的运行动作和新圈，却显示“运行/学习” |
| 恢复结束时会按整组清理，撤掉刚恢复的通道；旧参与者退出又触发全局故障 | 2.14.2.11 现场有明确前后顺序；2.16 仍保留相关路径 | 回退后仍会先启动受阻，再扩大成其他卡钳系统故障 |
| 停止、关闭、重建、看门狗交接共享状态不一致 | 多份现场回执与源码相互印证 | 停止后继续重试、重复释放对象、等待数据关闭、到期限后强制结束主程序 |

**整改方向应从“单点补异常”转为“完整恢复事务 + 每个运行阶段的真实进展监督 + 数据可恢复提交 + 独立安全退出”。** 不能靠吞异常、反复重启、统一放宽超时、强制显示运行来实现稳定。

软件可以做到：可恢复故障自动恢复、不可恢复故障明确停在可解释的安全状态、所有中断可追溯、没有假运行和无限等待。硬件失效、失电或安全证据无法确认时，无法承诺卡钳仍持续动作；这种情况下正确结果必须是停止并明确提示，而不是未经确认继续上电。下面给出可验证的工程目标，不作“任何故障下绝对不停”的承诺。

### 2.3 结论标记

- **已确认**：现场事实直接可见，或缺陷已由原发布程序集复现。
- **高可信归因**：现场顺序与具体代码路径闭合，但没有该时刻线程栈或每个原始批次的完整追踪。
- **待确认**：底层抖动来源、缺失证据和运行策略选择。不会把这些写成已经查实的硬件故障。

日志中的“系统故障”是应用程序状态，不等于 Windows 操作系统故障。所附截图没有证明蓝屏、系统重启或操作系统崩溃。

### 3.1 程序退出到底是什么性质

| 类型 | 本轮直接证据 | 应如何理解 |
|---|---|---|
| sidecar 结束旧主进程并拉起 | 16:25:09、19:23:23、19:42:57，原因均为 `PowerOffUnconfirmedTimeout` | 确实发生外部强制终止；“无法确认断电”不等于已证明当时还在上电 |
| 应用 30 秒硬期限结束主进程 | 16:52:41、19:49:39，`ExactMainProcessTerminatedAt30SecondDeadline` | 退出期限达成，安全/数据完整关闭没有达成；两张“正在安全关闭”截图不能代替最终回执 |
| 主进程在硬期限前退出，自动重启被拒绝 | PID 4428、2956、14052 的 `MainProcessExitedBeforeDeadline`，随后哈希身份拒绝 | 不应把回执文件最后更新时间当成进程退出时间，也不能统称未处理异常崩溃 |
| 人工停止后取消启动/关闭 | PID 21664 的 19:31 事件 | 有取消和关闭证据；当前没有与前三类一样齐全的退出回执，保留这一边界 |

## 4. 根因、版本归属与具体解决方式

### P01：原始批次被静默丢弃，确定性数据错误被当成暂时写盘失败

**高可信归因；新增路径相对 2.14.2.11 存在于 2.16。**

代码链为：

1. [EpbManager.cs:9296](D:/Github/wanxiang/EPBTest-v2.16-stability/Controller/EpbManager.cs:9296) 以电机当前上电掩码判断设备是否控制活跃。电机此刻 OFF，并不等于没有尚未封口的正式圈或学习圈。

**整改要求：** 按事故关联号保留触发前后短窗口，假运行和阶段无进展也必须触发抓栈；启动预热有独立状态，避免早期误告警消耗真正事故的取证预算。取证异步、有大小和频率上限，记录其自身暂停耗时；ETW 不可用时明确降级到轻量调度/队列/进展日志，不能令业务停止。健康上报至少带：期望阶段、实际任务存活、最后命令及回执、最近有效数据年龄、最后完成圈、耐久序号、下一期限、阻塞拥有者。

## 6. 让未知问题也能被处理：通用运行保障方案

通用方法不是一个 catch 或一个看门狗，而是让任何执行路径都具备 **有限期限、明确拥有者、可验证进展、可重放结果、确定升级出口**。未知软件异常也被纳入同一规则。

### 6.1 按真实共享资源隔离

现场 Dev1 关联 1–6，Dev2 关联 7–12；当前启用的分别为 4/5 和 7/8/9/12。电源组对应 1–3、4–6、7–9、10–12。液压共享范围也必须从实际配置建立资源关系，不能把 DAQ 组、电源组、液压组当成同一种“组”。

| 故障范围 | 恢复动作 | 健康部分的行为 |
|---|---|---|
| 单钳算法/学习异常 | 安全释放该钳、作废当前尝试、重建该钳执行任务 | 共享资源允许时继续；不把失败传播成整批学习永不返回 |
| 单 DAQ / 液压共享组异常 | 冻结受影响成员、确认断能、重建采集或协调器、重新资格验证 | 无共享依赖的另一组继续 |
| 持久化暂时失败 | 使用有界耐久缓冲，恢复写盘；按容量/时间余量决定暂停 | 不用无限 RAM 队列撑住表面运行；不牺牲完整数据继续计有效圈 |
| 主程序任务死锁/原生调用卡住 | 独立监督确认安全接管，结束旧进程，重放耐久数据和未完成事务，重建新进程 | 仅在恢复许可和安全条件成立后自动继续 |
| 真正硬件故障、急停、压力或断电无法证明 | 按实际共享影响范围停机，保持硬件联锁，报告明确阻塞原因 | 不自动越过硬保护；共享安全无法隔离时整机停止 |

必须验证独立安全通路是否能在主程序/NI 驱动卡死时仍实际断能。若安全动作依赖同一个被卡住的进程或独占句柄，单加 Windows 看门狗仍不能形成可靠的安全接管；需要结合现有电源和控制硬件能力评审实施。

### 6.2 以可验证结果定义状态机

推荐阶段：准备 → 学习 → 资格动作 → 正式运行；异常后进入安全暂停 → 数据收口/异常终结 → 资源重建 → 资格动作 → 正式运行。人工停止和硬故障锁定具有独立终态。

以下规则必须是程序约束，而不仅是 UI 文案：

1. 每个被要求运行的通道，都有当前阶段对应的执行任务、拥有者和下一进展期限；监督从“应该存在的任务”出发，不能只遍历当前字典中已有任务。
2. Running 必须有当前代次执行租约、已完成资格、健康采样及可接受的数据写入状态；圈间正常不通电允许存在，但持续超出合法阶段期限必须退出 Running。
3. 恢复成功至少分为“采样已恢复”“执行已恢复”“首圈已验证”；前两者不能冒充第三者。
4. 任一等待都有期限、取消路径和升级动作；重试次数耗尽后形成终态，不能靠重建任务重置总期限而无限循环。
5. 超时推进只到下一个完整周期，绝不为了追上计数压缩间隔或补发积压动作。
6. 旧代次的回调、恢复 finally、Stop/Dispose 只能触碰它自己持有的资源；新代次资源不受旧清理影响。
7. 进程死亡后，由耐久的机械回执、原始数据和事务记录恢复事实；UI 状态、内存布尔值和旧心跳都不能作为完成证明。

### 6.3 两种时间预算分别管理

**安全期限**由电机最大通电时间、采样新鲜度、压力释放、电源读回等物理约束决定，须保持独立。**恢复期限**决定一次软故障允许重试多久、何时重建任务/进程。不能为了减少停机把两者一起调大。

建议实现时给每个阶段配置预算，并在现场验证后冻结：单通道先有界重试，连续同因失败升级资源组；组重建失败再升级进程；规定滚动窗口内的最大重启次数，超过后停在明确等待维护状态。当前代码已有 10 秒、30 秒、60 秒、300 秒等多个期限，但它们并不构成完整的统一恢复预算。需盘点并统一所有入口，尤其学习、退出、持久化队首错误和旧 sidecar 的路径。

不在本文直接指定一个未经硬件验证的“万能超时值”。阶段期限到达时应产出 `BlockedBy`、拥有者、最后进展、下一动作及最终结果，用户无需根据长时间不动的进度条猜测状态。

### 6.4 数据先可恢复，再允许进程重建

建议建立受控的原始数据耐久日志/WAL，并由独立持久化工作者推进：接收批次 → 耐久确认 → 索引/曲线生成 → 幂等圈提交。每一步记录源代次和序号。

控制实时链路不能被文件写入阻塞；缓冲必须有容量和耐久风险上限，达到上限就安全暂停受影响范围。进程异常结束后，后台重放已耐久数据；确实未保存的区间明确标 gap/aborted。原始证据保留时可以重建索引，证据不存在时不能重建成有效曲线。

这样，未知的软件异常可以被“安全停住、重建执行环境、重放事实、验证后继续”处理，代价和数据边界都可说明，不再依靠某个故障刚好被某个 catch 识别。

## 8. 怎样验证“彻底解决”，避免再交付一个看似通过的版本

### 8.1 必测故障矩阵

测试必须穿过实际 Controller、NI 调度、持久化和 watchdog 的组合入口；仅测一个函数返回值或只检查状态字符串不够。

| 场景组 | 必须注入的情况 | 必须观察到的结果 |
|---|---|---|
| 数据批次 | 1 个/多个缺口；重复；乱序；旧 generation；电机 OFF 但圈未封口；仅控制拒绝旧样本 | 原始证据有去向；异常圈有缺口终态；后继可推进；没有伪造连续前缀 |
| 写盘故障 | 暂时文件占用、磁盘满、权限失败、写入变慢、确定性非法数据、WAL 重放中断 | 可恢复错误有界恢复；不可恢复错误明确隔离/暂停；无无限重试和内存无限增长 |
| 新鲜度并发 | now/publication 交错；reset/发布交错；真实 80/120/300/1000 ms 空窗 | 不发生时间戳竞争误 Trip；真正陈旧时按有效配置保护；日志显示真正超限字段 |
| 学习恢复 | 六钳学习中断；7/8/9 上电许可撤销；单成员失败；DAQ 先恢复、学习任务未完成 | 每个成员都有结果；失败任务被撤销重建；没有“运行/学习”且长期无动作 |
| 正式运行恢复 | 一钳刚重建 timer，另一钳恢复失败；旧 finally/退休超时延迟到新代次 | 新 timer/runner 不被旧事务删除；旧参与者正确退役；健康组继续 |
| 共享资源 | Dev1 故障、Dev2 健康；共享液压/电源组一成员故障；并发多组恢复 | 按真实资源关系隔离；不存在日志说“健康组继续”而实际随后无谓全停 |
| 停止与关闭 | 恢复任意阶段人工停止；先停止再关子窗再关主窗；连续点关闭；数据未收齐；压力陈旧 | 同一停止事务；人工停止持久优先；无已释放对象异常；最终回执真实完整 |
| 看门狗身份 | 哈希大小写等价、真实不同 EXE、旧 session/PID、旧 lease、旧终态回执 | 合法恢复成功；真正身份不符保持拒绝；旧会话永不继续拉起 |
| 进程故障 | UI 卡住、学习任务不进展、控制原生调用不返回、管道阻塞、主程序被结束、sidecar 重启 | 正确取证、确定拥有者、独立安全接管；符合条件才重启；没有进程风暴 |
| 数据与计数 | 机械完成后立刻退出；提交回执丢失；数据库与检查点跨时刻封存；重复恢复 | 动作不重复计数；缺曲线不计有效正式圈；可按 AttemptId 对账 |
| 诊断失效 | ETW 建立失败、dump 写入慢、日志队列满 | 业务按安全规则继续/恢复；诊断明确降级，不能因诊断本身拖死控制 |
| 现场环境 | 真正 NI、电源与液压；LocalSystem/用户会话；远程连接切换；受控 CPU/I/O 负载 | 实际动作、波形、计数和回执全部一致；不得只用模拟 UI 通过 |

### 8.2 发布门槛

1. 修复阶段按仓库要求完成 Debug x86 构建及控制/看门狗、落盘、电源相关测试；使用完整实际发布包进行跨进程联调，不能只测试源码旁的临时 exe。
2. 建议现场按 12 → 24 → 72 → 168 小时递进验收，覆盖六钳、学习、正式运行和正常收工。具体时长可确认，但至少要长于这次故障出现的窗口，并有故障注入恢复记录。
3. 验收期间不得有未解释的全局撤权、无限恢复、假运行、旧进程循环、重复机械计数、无标记数据缺口。每次“恢复成功”必须能追到第一圈有效动作和耐久结果。
4. 记录有效正式圈产出率、自动恢复耗时、每类失败次数、无进展最长时间、数据缺口数、CPU/内存/句柄/队列趋势。计划注入导致的受控中断单列，不能混入正常运行时长掩盖停机。
5. 任一关键场景失败则修复并重做受影响验收。安装包 SHA、配置有效值、服务版本和源码提交必须一并封存，避免“测试的包”和“现场运行的包”不同。

通过以上验收能支持明确环境和运行范围内的稳定性结论，不等于数学意义上的零故障保证。持续运行的衡量对象应是**可验证的有效圈持续产出**，不是程序进程活着或绿色按钮一直亮着。
