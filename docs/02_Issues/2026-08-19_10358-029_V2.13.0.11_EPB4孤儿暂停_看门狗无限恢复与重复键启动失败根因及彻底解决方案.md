## 1. 结论先行

本次不是一个单点故障，而是四个问题串成的故障链：

1. **直接诱因是 Dev1 DAQ 回调中断约 1.172 秒。** EPB5 带电时样本年龄超过 100ms，程序先安全断电；随后压力和断电电流也因同一份陈旧样本被判定不可用，同时启动了多条自愈路径。安全断电动作是正确的，但恢复仲裁出现竞争。
2. **EPB4 不是人工暂停，而是程序自愈造成的“孤儿暂停”。** 程序已停止并移除 EPB4 的 Timer 和 Runner，并把状态发布为 `Recovering`；同一个旧 Timer 随后迟到发布 `Paused`，又把通道覆盖成普通 `Paused`。恢复选择器只接收 `Recovering/SystemFault`，于是 EPB4 被排除，只恢复了 EPB5。
3. **手动点击 EPB4 启动无法恢复是必然结果。** 单通道恢复要求同时存在人工暂停时间戳、Timer 和 Runner；EPB4 三者均不存在，所以界面提示“不处于可恢复的安全暂停状态”。界面显示“暂停”与内部资源事实矛盾。
4. **所有卡钳停机的高置信初始触发是看门狗误判“恢复停滞”。** 正式运行中的 5 个 `_currentCycleNumberByChannel` 被错误计入 `SoftwareRecoveryCount`，使健康运行心跳成为 `RecoveryActive=true`；事发版看门狗在这个假恢复状态 15 秒没有“恢复进度”变化后，按 `ExternalRecoveryStageStalled` 主动发送 `RequestStopAll`，从而关闭所有卡钳。停机后的恢复循环再由“重复键永久启动失败 + 无终点看门狗探测”共同造成。
5. **重复键令停机后的自动启动持续失败。** 截图中的 `已添加了具有相同键的项` 与事发版本启动代码中 `Dictionary.Add(epbRecord.Id, ...)` 完全对应，说明启动时内存中的 `EpbRecords` 至少有一个重复 Id。看门狗连续失败五次后虽然打开熔断器，却仍按 2/5/15 分钟不断启动主程序做 `CircuitProbe`，因此不是有限恢复，而是降频后的无限恢复。

三个用户问题的结论如下：

| 用户问题 | 根因结论 | 当前最新源码是否已解决 |
|---|---|---|
| EPB4 突然暂停、看门狗不恢复、手动启动也失败 | 已确认：自愈撤销运行对象后，旧 Timer 的迟到 `Paused` 事件覆盖 `Recovering`；恢复候选过滤又把 EPB4 排除 | **未解决**。当前 HEAD 仍缺少 Timer 实例/代次栅栏，仍允许 `Recovering -> Paused` |
| 所有卡钳停机后无限进入看门狗恢复 | 高置信初始触发：正常活动圈被计入 `SoftwareRecoveryCount`，导致假 `RecoveryActive`，15 秒后看门狗以 `ExternalRecoveryStageStalled` 主动 `RequestStopAll`；之后重复键使启动永久失败，五次后进入无终点 `CircuitProbe` | **未解决**。当前 HEAD 仍把 `_currentCycleNumberByChannel.Count` 计入恢复数；虽然事后把无硬期限的 15 秒改为 60 秒，仍未修正状态语义，且 `CircuitProbe` 仍无限 |
| 卡钳无法启动 | 已确认直接异常：重复 `EpbRecords.Id` 被写入新字典时抛出重复键异常；最终封存配置已是 12 个唯一 Id，因此重复项的最初生成路径无法仅靠本数据唯一确定 | **基本修复但未形成结构性保证**。事后提交已在加载、保存和启动边界归一化并通过测试，但 `EpbRecords` 仍是可变 `List`，尚未从类型上禁止再次插入重复项 |

因此，**不能把当前仓库最新源码表述为“已经彻底解决”**。在完成本文 P0 改造、故障注入和长稳验收前，不应作为无人值守最终版本发布。

## 4. 问题一：EPB4 为什么会变成无法恢复的“暂停”

### 4.1 直接触发是 Dev1 DAQ 回调空窗

11:38 前后系统资源并不紧张：

- Process CPU 约 8%～13%，System CPU 约 16%～22%；
- 可用内存约 11.3GB；
- 磁盘队列为 0，写入约 0.4～0.8MiB/s；
- DAQ 控制、处理、Raw、持久化队列均为 0，`AsyncLogDropped=0`；
- Dev2 CallbackAge 小于 1ms。

因此这次事件不支持“日志堆积、磁盘写满或 CPU 满载拖死程序”。已证实的最底层事实是 **Dev1 单设备回调链出现约 1.172 秒空窗**。长期日志中，超过 1 秒的 DAQ 空窗并非孤例：

| 日期/设备 | 大于等于 1 秒的设备事件数 | 范围 |
|---|---:|---:|
| 08/17 Dev1 | 6 | 1162.1～1267.7ms |
| 08/18 Dev1 | 15 | 1004.4～1435.7ms |
| 08/18 Dev2 | 2 | 1004.9～1435.7ms |
| 08/19 Dev1 | 12 | 1161.7～3315.5ms |
| 08/19 Dev2 | 3 | 1439.9～3315.4ms |

08/19 Dev1 在 00:25、01:06、01:33、06:29、09:10、10:21、11:01、11:24、11:38 均出现约 1.16～1.18 秒的单设备空窗；11:46 和 11:48 的双设备长空窗另与界面/通信停顿重合。

这说明 DAQ 空窗是需要独立解决的长期稳定性问题。但现有数据没有 NI 驱动任务状态、Windows DPC/ISR、GC Stop-the-world、USB/PCIe 错误或线程堆栈，**不能把底层原因武断归结为 GC、NI 硬件或某一根线缆**。软件必须先保证任意空窗都不会造成通道丢失，同时补齐下一次定性的证据。

### 4.2 已确认的生产代码竞态

当前 [EpbManager.WarningSnapshots.cs](../../Controller/EpbManager.WarningSnapshots.cs#L1104) 中正式控制自愈顺序为：

```text
timer.Pause
  -> RemoveTimerRuntime
  -> RemoveRunnerRuntime
  -> UnmarkHydraulicParticipant
  -> Publish Recovering
  -> ScheduleIsolatedInfrastructureRecovery
```

而 [EpbManager.TimerRuntimeHealth.cs](../../Controller/EpbManager.TimerRuntimeHealth.cs#L38) 使用匿名事件订阅：

```csharp
timer.StateChanged += update => OnTimerRuntimeStateChanged(channel, timer, update);
```

事件处理器没有检查：

- 回调来源 Timer 是否仍是 `_timers[channel]` 的当前实例；
- Timer 是否属于当前 RunEpoch/RecoveryEpoch；
- 事件订阅是否已在移除时注销；
- 当前 `Recovering` 是否允许被普通 `Paused` 覆盖。

相反，[同文件 60～64 行](../../Controller/EpbManager.TimerRuntimeHealth.cs#L60) 明确把 `Recovering + Timer.Paused` 当作可接受的 `pauseTransitionOwned`，并在 94～101 行再次发布普通 `Paused`。现场日志恰好给出了这一顺序：

```text
11:38:19.740 EPB4 State=Recovering Timer=False Runner=False Revision=261
11:38:19.740 old Timer Instance=30410852 State=Paused
11:38:19.740 EPB4 State=Paused Timer=False Runner=False Revision=262
```

这是确定性的因果证据，不是推测。

### 4.3 为什么只恢复 EPB5

[EpbManager.RecoveryCoordination.cs](../../Controller/EpbManager.RecoveryCoordination.cs#L665) 的恢复候选筛选只允许：

```text
ChannelRuntimeState.Recovering
ChannelRuntimeState.SystemFault
```

恢复调度最初会从请求通道、Timer、Runner 和液压参与者冻结同组 cohort；但真正执行前又按实时 UI 生命周期状态过滤。此时：

- EPB4 已被迟到事件改为 `Paused`，所以被过滤；
- EPB5 仍为 `Recovering`，所以进入 `AffectedGroupReset`。

日志随后只出现 EPB5 的 Timer/Runner 移除、启动定位和重新创建，完整印证了该过滤结果。

### 4.4 为什么看门狗没有介入

看门狗看到的是一个仍有心跳的主进程：

- 其余 5/9/10/11 持续产生机械圈；
- EPB4 被标记为 `Paused`，看起来像合法暂停；
- EPB4 已没有 Timer，Timer 健康监督也失去了被监督对象；
- 当时心跳没有单独表达“用户暂停令牌”与“程序恢复令牌”的区别，也没有把“正式授权通道缺少 Timer/Runner”作为必须接管的不变量。

因此看门狗的沉默不是证明状态正确，而是监督模型存在盲区。

### 4.5 为什么人工点击无法恢复

[EpbManager.PauseResume.cs](../../Controller/EpbManager.PauseResume.cs#L408) 要求：

```text
_channelPausedUtc[channel] 存在
_timers[channel] 存在
_runners[channel] 存在
```

EPB4 是程序自愈造成的假 `Paused`，没有人工暂停 checkpoint，Timer 和 Runner 又已移除，三项检查必然失败。停止整批并重新启动会重建全部资源，所以能够恢复。这进一步排除了“EPB4 卡钳硬件永久损坏”。

## 5. 问题二、三：为什么整机恢复循环且卡钳无法启动

### 5.1 问题 2 中所有卡钳停机的初始触发

最后一份封存心跳提供了此前遗漏的关键证据。11:50:48 时：

```text
Phase=Formal
RunActive=true
EnabledChannels=[4,5,9,10,11]
五个通道 State=Running、TimerActive=true、RunnerActive=true
DaqRecoveryCount=0
RecoveryOwnerCount=0
RecoveryStage=""
RecoveryIncident=""
RecoveryContext=""
RecoveryActive=true
SoftwareRecoveryCount=5
```

这不是一个真实的恢复状态：五个通道已正常进入正式运行，没有 DAQ 恢复、恢复 owner、恢复阶段或事故上下文。`SoftwareRecoveryCount=5` 恰好等于五个运行通道数。

直接代码原因位于 [EpbManager.cs](../../Controller/EpbManager.cs#L8684)。`CaptureLogicalQuiescenceSnapshot()` 将多种真实恢复容器相加后，又错误追加：

```csharp
+ _currentCycleNumberByChannel.Count
```

`_currentCycleNumberByChannel` 保存的是各通道**当前正常执行的机械圈号**，不是软件恢复任务。随后 [FrmEpbMainMonitor.UnattendedRecovery.cs](../../MTTfTest/FrmEpbMainMonitor.UnattendedRecovery.cs#L260) 只要 `SoftwareRecoveryCount > 0` 就上报 `RecoveryActive=true`。

事发基线 `f72d480` 的 `WatchdogTakeoverPolicy.ShouldTakeover()` 对这个状态使用：

```csharp
return recoveryActive && stageAgeSeconds >= 15;
```

而恢复进度签名只包含 `SoftwareRecoveryCount` 的**数量**，不包含当前圈号、机械圈完成数或普通运行进度。当五个通道的字典数量保持为 5 时，即使卡钳仍在正常运行，恢复进度签名也不会变化。15 秒后 sidecar 会把它判成恢复阶段停滞，生成兜底原因：

```text
ExternalRecoveryStageStalled
```

[WatchdogHost.cs](../../MTTFTest.Watchdog/WatchdogHost.cs#L620) 的 `BeginTakeover()` 随即先发送：

```text
RequestStopAll
```

因此，问题 2 的完整故障链应更正为：

```text
五个卡钳正常正式运行
  -> 正常活动圈数被误报为 SoftwareRecoveryCount=5
  -> 心跳假报 RecoveryActive=true
  -> “恢复进度”数量 15 秒不变
  -> 看门狗误判 ExternalRecoveryStageStalled
  -> 主动 RequestStopAll，所有卡钳安全断电
  -> 自动启动时遇到 EpbRecords 重复键
  -> 启动持续失败
  -> 五次后进入无终点 CircuitProbe
```

这也解释了为什么“所有卡钳一起停”：不是五个卡钳同时发生硬件故障，而是 sidecar 发出一次全局安全接管命令。

证据等级需如实说明：封存数据在 11:50:46 结束，缺少 11:51 左右原始 `TakeoverRequested` 事件，因此不能引用该事件的现场原文；但“最后健康心跳的错误字段 + 事发源码 15 秒判据 + `BeginTakeover` 必发 `RequestStopAll` + 后续第 5/6 次恢复截图”构成闭合的软件机制证据，属于**高置信直接触发**。若要把证据等级提升为完全确认，需找回现场 12:00 前原始 `session-*.sidecar-events.jsonl` 或 `AutomaticTakeover` dump，核对其中是否为 `ExternalRecoveryStageStalled`。

### 5.3 看门狗为什么会无限恢复

当前 [WatchdogHost.cs](../../MTTFTest.Watchdog/WatchdogHost.cs#L972) 在连续恢复失败达到 5 次时记录 `SafeIdleRecoveryBlocked`，界面文案也称“快速恢复已暂停”。但下一行仍调用 `ScheduleCircuitProbe()`。

`ScheduleCircuitProbe()` 的行为是：

1. 第 1 次等待 2 分钟；
2. 第 2 次等待 5 分钟；
3. 第 3 次及以后等待 15 分钟；
4. 每次都重新启动主程序一次；
5. 启动仍失败时再次进入 circuit-open 并继续排程；
6. 调度器自身异常时也会递归再次排程。

因此当前实现仅限制了**单次探测频率**，没有限制**总探测次数、总时间或同一故障指纹的总进程启动数**。截图显示 `CircuitProbe` 第 5 次、随后第 6 次，与源码完全相符。

重复键属于确定性的配置/程序不变量错误。重新启动相同二进制、加载相同数据，结果不会自行变化。看门狗把永久性失败当成瞬态硬件通信失败处理，必然形成安全断电但无法收敛的恢复循环。

### 5.4 11:46 的短时停顿不是 12:00 的无限循环

11:46:02 看门狗 ACK 超时与 PSU4 的 SCPI 读超时同时发生：

```text

PSU4 SOUR:VOLT? ElapsedMs=3308.263 Timeout=2000ms
```

两块 DAQ 同时记录约 3315ms 空窗，但同一 PID 在 11:46:48 恢复运行。这说明 11:46 是一次进程级长停顿/通信等待并成功恢复，不能拿来替代 12:00 后缺失的首次退出日志。

## 7. 必须实施的彻底解决方案

以下 P0 项必须作为同一个版本交付，不能只修弹窗或调整重试次数。

### 7.1 P0-1：为 Timer 事件增加实例、代次和恢复 owner 三重栅栏

每个通道维护不可复用的 `TimerGeneration` 和 `RecoveryEpoch`，事件订阅必须保存可注销的 delegate，禁止匿名订阅后失去解绑能力。

推荐顺序：

```text
获取通道生命周期锁
  -> 冻结 RunId/RunEpoch/RecoveryEpoch/完整 cohort
  -> 先发布 Recovering(owner=本次 RecoveryEpoch)
  -> 递增 TimerGeneration，使旧 Timer 立即失效
  -> 注销旧 Timer.StateChanged
  -> Pause/Stop/移除 Timer 和 Runner
  -> 确认 DO OFF、电源/液压安全
  -> 重建 Runner/Timer，新 Timer 获得新 generation
  -> 校验完整 cohort 后原子提交 Running
```

生产事件处理器必须满足：

```text
ReferenceEquals(_timers[channel], sourceTimer)
sourceGeneration == current.TimerGeneration
sourceRunEpoch == current.RunEpoch
```

任一不满足时只记录 `StaleTimerEventIgnored`，绝不能修改 UI 生命周期状态。状态存储层再增加硬规则：没有有效 `ManualPauseToken` 时，禁止 `Recovering -> Paused`；内部暂停只能显示 `Recovering` 或 `FaultStopped`。

涉及文件：

- [EpbManager.TimerRuntimeHealth.cs](../../Controller/EpbManager.TimerRuntimeHealth.cs)
- [EpbManager.WarningSnapshots.cs](../../Controller/EpbManager.WarningSnapshots.cs)
- Timer 创建/移除的并发资源管理文件
- Channel runtime state store

### 7.2 P0-2：恢复对象以“冻结事务”而不是实时 UI 状态为准

当前代码虽然冻结了 requested cohort，执行前却再次按易变的 UI 状态过滤。应改为 `RecoveryTransaction`：

```text
RecoveryTransaction {
  RunId, RunEpoch, RecoveryEpoch, RootIncidentId,
  FaultDevice, HydraulicGroup,
  ExpectedChannels[],
  SafeOffEvidence[],
  Stage, HardDeadline,
  CommitGeneration
}
```

`ExpectedChannels` 必须在任何 `RemoveTimer/RemoveRunner/UnmarkParticipant` 之前，根据本次 Run 的授权、完成、永久报警和人工禁用事实一次性冻结。后续是否恢复由 transaction owner 决定，不能再因 UI 被迟到事件改成 `Paused` 而丢通道。

提交成功条件必须逐通道校验：

- 仍属于当前 RunId/RunEpoch；
- Runner 是当前实例；
- Timer 是当前实例并已启动；
- 没有上代 CTS、owner、participant、lease 残留；
- 状态为 `Running`；
- 下一圈锚定未来完整周期；
- 本事故圈已恰好作废一次且未计入正式成功。

只要 cohort 中任一通道不满足，禁止“部分成功后悄悄结束恢复”。应保持全部受影响通道 OFF，并在 30 秒硬期限内升级为一次整批回收；整批回收仍失败则进入终态人工处理。

### 7.3 P0-3：把“人工暂停”和“程序自愈”拆成不可混淆的状态

建议将界面/协议状态明确拆分：

| 状态 | 必需 owner | UI 文案 | 允许操作 |
|---|---|---|---|
| `ManualPaused` | `ManualPauseToken` | 人工暂停 | 恢复、停止 |
| `Recovering` | `RecoveryTransaction` | 程序恢复中（显示原因和倒计时） | 停止；禁止普通 RUN |
| `RecoveryBlocked` | 持久失败 fingerprint | 恢复已阻断，等待处理 | 确认后重试、停止 |
| `FaultStopped` | Alarm/Fault token | 故障停机 | 处理故障、停止 |
| `Running` | 当前 Timer/Runner generation | 运行 | 暂停、停止 |

普通“暂停”只能由人工路径写入。Timer 为内部安全而暂停时，Timer 状态是资源细节，不能直接覆盖通道业务状态。

### 7.4 P0-4：看门狗必须有真正的终态，禁止永久错误无限启动进程

先对失败分类，再决定重试：

| 分类 | 例子 | 自动策略 |
|---|---|---|
| 确定性/永久性 | DuplicateEpbId、配置 schema 错误、checkpoint 不变量错误、程序集/包校验失败 | 0～1 次；随后立即 `RecoveryBlocked`，不得 `CircuitProbe` 拉起主程序 |
| 瞬态设备通信 | NI 设备短时不可用、网络电源超时、端口暂时占用 | 5/15/30/60 秒退避；同 fingerprint 最多 5 次且总时长不超过 15 分钟 |
| 未分类软件异常 | NullReference、ArgumentException、启动后立即退出 | 最多 2 次；保存 dump/stack 后终态阻断 |
| 硬件离线 | 明确拔除、驱动设备不存在 | 主程序保持关闭；sidecar 可做不启动主程序的低频硬件探测 |

终态行为：

1. 所有控制输出保持 OFF，并持续显示物理安全证据；
2. 持久化 `RecoveryBlocked`、failure code、fingerprint、首次/末次时间和 PID 历史；
3. 不再启动新的主程序进程；
4. 声光/界面明确报警，不再显示“预计若干分钟后继续”；
5. 只有操作员确认、配置哈希改变、二进制哈希改变或明确的硬件恢复 nonce 才能清除阻断；
6. sidecar 自身重启后仍从 durable journal 恢复相同预算，不能把次数清零。

若仍保留 `CircuitProbe` 名称，它只能探测设备存在性，不能启动整个 `MTTFTest.exe`。当前 [WatchdogHost.cs](../../MTTFTest.Watchdog/WatchdogHost.cs#L1017) 的循环调度必须移除或加总次数/总时长终点。

### 7.5 P0-5：从数据结构上保证 EpbRecord Id 唯一

### 7.6 P0-6：同一个 DAQ 空窗只能有一个根恢复 owner

### 7.7 P0-7：补齐 DAQ 空窗底层定性证据

每台设备保留至少 30 秒内存环形诊断，在大于 100ms 空窗或 Windows Watchdog 接管时一次性导出：

- 每次 NI `BeginRead/EndRead/Rearm` 的单调时间、线程 Id、任务 generation 和返回/异常；
- NI Task 状态、设备 reset/USB/PCIe 错误码；

### 7.8 P0-8：看门狗增加跨层运行不变量

首先修正心跳字段语义：

- 从 `SoftwareRecoveryCount` 中永久删除 `_currentCycleNumberByChannel.Count`；
- 新增独立诊断字段 `ActiveCycleCount`，它不得参与 `RecoveryActive` 判定；
- `SoftwareRecoveryCount` 只能统计有明确 recovery owner/transaction 的恢复对象；
- `RecoveryActive=true` 必须同时有非空 `RecoveryCode`、`RecoveryStage`、`RecoveryIncident`、有效开始时间/硬期限和至少一个恢复候选；
- 普通机械圈完成数不得刷新恢复进度；同样，普通活动圈数量也不得创建恢复状态。

心跳需直接发布每通道：

```text
ExpectedActive
ManualPauseToken
RecoveryEpoch/Stage/Deadline
TimerActive/TimerGeneration
RunnerActive/RunnerGeneration
LastMechanicalCycleUtc
Energized
```

以下任一情况超过 5 秒必须接管或要求主程序整批恢复：

- `ExpectedActive=true`，不是完成/永久报警/人工暂停，但 Timer 或 Runner 缺失；
- `State=Paused` 但没有 `ManualPauseToken`；
- `RecoveryEpoch` 存在而 owner/Stage 不推进；
- UI 状态为 Running，但资源实例或机械进度不一致；
- recovery cohort 提交时成员数少于冻结值。

这能让看门狗识别本次 EPB4，即使其他通道仍在正常跑也不会放任单通道永久丢失。

同时增加反向协议门禁：若心跳声称 `RecoveryActive=true`，但所有通道均为正常 `Running/Learning`，且没有 recovery owner、事故 Id 和阶段，sidecar 必须记录 `RecoveryTelemetryInconsistent` 并请求一次结构化状态刷新；在机械进度仍健康时不得直接按 `ExternalRecoveryStageStalled` 全局 StopAll。连续刷新仍矛盾时进入明确的软件协议故障终态，而不是把普通运行误当成恢复。

8. **瞬态故障预算测试**：同 fingerprint 最多 5 次/15 分钟，sidecar 重启后预算不清零；人工确认或配置哈希改变后才能开启新预算。
9. **结构化错误测试**：无人值守初始化失败必须在子进程退出前把 code、permanent、stack、config hash 发给 sidecar。
10. **健康运行不得假恢复**：五个通道持续正式运行，`ActiveCycleCount=5` 时必须保持 `SoftwareRecoveryCount=0、RecoveryActive=false`；运行 10 分钟不得产生 `ExternalRecoveryStageStalled` 或 `RequestStopAll`。

### 8.2 故障注入验收

在 EPB4/5 同液压组运行、EPB5 带电且 EPB4 正在正式圈时，分别注入 Dev1 回调空窗 120ms、1.2s、3.5s：

- 样本年龄越过 100ms 后，受影响通道高优先级 OFF 命令应在 150ms 内提交；
- 不允许把陈旧压力写成真实低压；
- 每次只有一个 RootIncidentId 和一个 recovery owner；
- 4/5 必须作为完整 cohort 清场和重建；
- 30 秒内恢复成功，或转入明确 `RecoveryBlocked`；
- 任意时刻不得出现 `Paused + ManualPauseToken=false + Timer=false + Runner=false`；
- 事故圈恰好作废一次，机械/正式计数不重不漏；
- 连续注入 100 次，Timer/Runner/CTS/owner/lease/participant 数量回到基线。

### 8.3 长稳发布门禁

候选版本至少满足：

- 72 小时或 100,000 机械圈长稳，取先到者之后再连续运行 24 小时；
- 人工注入上述 DAQ、PSU 超时、配置损坏和主进程退出故障；
- `OrphanPaused=0`、`RecoveryOwnerLeak=0`、`DuplicateEpbIdAtStart=0`；
- 没有无限进程拉起；同一永久 fingerprint 的 PID 数符合有限预算；
- 每次 StopAll 都有 MotorDO/Power/Pressure/Persistence/Logical 明确终态；
- 数据库、Raw 和正式证据边界一致，恢复前后 RunId/RunEpoch/计数连续；
- 生成并验证 package manifest，运行日志必须显示 GitCommit、BuildUtc、ExeSha256、ConfigSha256 和 `PackageVerified=True`。

任何一项失败都不得靠增加重试次数放行。

## 10. 现场临时处置（不是最终方案）

在新版本通过验收前：

1. 若通道显示暂停，但详情含 `FormalControlSelfHealing`、`Timer=False` 或 `Runner=False`，应按“程序孤儿状态”处理，**不要反复点击单通道 RUN**；先停止整批并确认所有 DO/电源/压力安全，再重新启动。
2. 遇到重复键异常，备份实际运行目录和项目 `TestConfig.xml`，核对 `EpbRecords` 是否恰好 12 个唯一 Id；使用包含 `497f9ed` 的候选程序只能作为修复验证，不能据此跳过其余 P0。
3. 看门狗进入第 5 次或 `CircuitProbe` 后，应人工停止自动恢复并保存当次 session/journal/dump；不要放任它长期重复启动同一永久错误。
4. 现场继续运行时必须有人值守，并记录 Dev1/Dev2 设备序列号、端口和每次空窗时间，直至 P0/P1 完成。

## 11. 最终判定

- **问题 1 已定根因**：EPB4 是程序自愈后的旧 Timer 迟到事件造成的孤儿暂停，不是人工操作；看门狗监督不变量不足，手动恢复入口与假状态不匹配。
- **问题 2 已定高置信触发链**：正常活动圈被误计为软件恢复，使看门狗把健康运行误判为 `ExternalRecoveryStageStalled` 并主动 `RequestStopAll`；随后永久启动失败又被当成可探测瞬态故障，五次熔断后仍无限 `CircuitProbe`。封存缺少首次 `TakeoverRequested` 原文，找回 sidecar journal 后可将“高置信”提升为完全确认。
- **问题 3 已定直接失败点**：内存中重复 EPB Id 进入 `Dictionary.Add`；事后源码已做有效归一化，但仍需不可变/唯一数据结构和正式包验证。
- **DAQ 空窗底层原因尚未最终定性**：已排除本次时刻的 CPU、内存、磁盘和日志队列饱和，但还缺 NI/ETW/硬件 A/B 证据。无论底层诱因为何，软件都必须在空窗下安全、完整、有限地收敛。

当前最新源码 **不满足“彻底解决”发布条件**。只有完成第 7 节全部 P0、通过第 8 节生产竞态/故障注入/长稳门禁，并生成可追溯正式包后，才能关闭本问题。
