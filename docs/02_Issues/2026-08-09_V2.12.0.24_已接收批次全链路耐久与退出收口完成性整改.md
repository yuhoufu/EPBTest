# V2.12.0.20 长期退化全量复盘与 V2.12.0.24 根因整改

## 技术摘要

对本地完整封存 `E:\00_万向\EPB_数据\10358-029_V2.12.0.20_0809_1451` 进行全量日志、事故证据、SQLite 和性能门禁复核后，结论是：**V2.12.0.20 的故障不是六个卡钳同时损坏，而是 UI/后台消费长期退化后使两块 DAQ 同时失新，再级联为压力、电源遥测陈旧、液压自维护风暴、持久化空洞与无法退出。**

关键反证是：本次正式会话中 6 个通道共 4,114 个正式圈全部在合格带内，最大峰值不超过 15.799 A，SQLite `integrity_check=ok`；而在 14:44:13 两设备后台队列同时积压、14:44:16 同时接近 64 批硬上限后，回调空窗增长到 65–104 秒。这是进程级消费链故障，不是单卡钳物理故障。

V2.12.0.24 已将修复收口到以下不变量：

1. 运行中 UI 只消费最新显示值，曲线只根据真实 DAQ 时间断笔，日志不再全量重建。
2. 一旦 DAQ 批次成功进入后台工程队列，generation 切换、Raw 发布队列满、SQLite 队列满都不能再撤销其耐久义务。
3. 下游真正接收所有权后才推进 `Published`；空洞不得被后续大序号掩盖。
4. 程序退出要求真实耐久边界闭合，但不再被“DAQ 已停止后还要等新鲜批次才恢复状态”这一不可能条件永久阻止。

**当前状态：代码整改和自动回归已完成；真实 NI、程控电源、液压与主机负载下的 2/8/24/72 小时验收尚未完成，因此不能提前声称已满足生产无人值守。**

## 3. 定量证据与反证

### 3.1 曲线为什么刚开始连续、后来断续

正式会话中共有 1,251 个 UI 结构化窗口，单窗口 P95 延迟最大 1,672.022 ms，单次 Flush 最大 1,301.683 ms。扩展到整个日志的 1,287 个窗口：

| 指标 | 结果 |
|---|---:|
| `DelayMax >200 ms` | 463 / 1,287 |
| `FlushMax >200 ms` | 507 / 1,287 |
| `DelayMax` 最大 | 5,868.308 ms |
| `FlushMax` 最大 | 1,301.683 ms |
| UI 队列 `Dropped` / 文件队列 `FileDropped` | 0 / 0 |

因此数据没有在 UI 邮箱内溢出，而是 V2.12.0.20 旧断笔逻辑把 UI 为保性能主动覆盖的中间显示帧当作 DAQ 断流，同时日志 `TextChanged` 又按批全量读取、重建和裁剪文本。文本与分配越累越多，所以启动初期连续，后期才断续。

14:44:13 积压时程序 CPU 约 7.3%、系统 CPU 约 12.2%，磁盘队列为 0。所以不能用“CPU 满了”解释这个具体触发点。但用户截图中系统 CPU 98%、本程序约 42% 如果持续，属于不可接受的风险状态，会显著放大 UI 与后台消费尾延迟，必须由 24/72 小时主机指标门禁拒绝。

## 4. 根因分层

### 4.1 长期卡顿与视觉断线

V2.12.0.20 同时存在两个累积问题：

- 日志显示已有增量消费器，但 `TextChanged` 又每批遍历最多 2,000 行、重建 `Text`、再裁剪和滚动，制造大对象分配和消息泵停顿。
- 绘图用“距上次实际绘出点”判断断流。UI 最新值邮箱正常覆盖中间显示帧后，被错误插入 `NaN`。

### 4.2 自维护为什么频繁且不能回到试验

压力实际已低于 5 bar，但安全协议必须使用新鲜样本，不能将冻结的低值当成实时证明。因此液压重建每次都在同一个 `PressureSampleStale` 上超时。旧恢复编排又在 generation 切换时撤销已接收批次的归档，使恢复边界无法提交，最终出现“反复自维护—重建—边界待定—再自维护”。

### 4.3 退出为什么反复弹框

V2.12.0.20 把“已分配但后台 64 批队列未接收”的序号也作为停止耐久边界。Dev1 因此永久等待从未进入流水线的 1254944。每次关窗又重新调用 10 秒 StopAll，同一个不可能完成的条件持续失败，所以弹框不会自己消失。

## 5. V2.12.0.24 完成性审计发现的七个耐久缺口

V2.12.0.23 只修正了第一层伪边界。继续做所有权与退出故障注入后，又识别并修复以下路径：

| 缺口 | 旧行为 | 新不变量 |
|---|---|---|
| generation 失效 | 跳过已接收批次，却推进磁盘序号 | 旧代次只退出实时副作用，仍 `ArchiveOnly` |
| Raw 发布队列满 | Dispose 当前快照 | 后台线程有界背压，不占 NI 回调线程，不丢所有权 |
| SQLite 队列满 | Dispose 并返回 false | 每设备独立容量槽，同事故只报一次，FIFO 继续补写 |
| 接受新 generation | 清理旧 generation FIFO 并伪装已写 | generation 仅作身份/诊断，不撤销已入队耐久义务 |
| DaqAIContext Raw 队列满 | 删除队头 | 容量满锁存一次故障并背压，不删除已接收批次 |
| DaqAIContext 首次/写入失败 | 首次 Flush 主动删数据；写失败后吞异常且批次已 Dispose | 首次真实写入；失败回滚文件长度、FIFO 回队并抛异常等待重试 |
| 下游拒绝仍推进 Published | 后续大序号可掩盖中间空洞 | 只有唯一 SQLite 消费者真正接收所有权才推进 Published |

## 6. 运行、恢复和退出的根治策略

### 6.1 正常稳态不增加 UI 工作量

- 继续使用双设备最新值邮箱、10 FPS 重绘和 10 Hz 抽稀。
- 断笔只看相邻 DAQ 批次时间，UI 覆盖显示帧不再制造短线。
- 日志只保留唯一增量显示所有者，原位删除超限头部，复用批次容器，滚动最多 2 Hz。
- 六通道 2 kHz 真实 SQLite 负载测试最大持久化深度仍为 2。

### 6.2 未启用连续 Raw 时不再白白复制后丢弃

现场封存中没有 `DAQ_*_Raw_*.bin`，源码中 `InitDaqLogTimer(500)` 也处于注释状态。因此 V2.12.0.20 日志的 `RawDrained` 是采集内部“Raw 所有权移交边界”，不能解读为连续 Raw 文件已存盘。

V2.12.0.24 现在按配置语义处理：

- DaqAIContext 未初始化时，不订阅 `OwnedRawBatchReady`，采集端直接标记“无 Raw 消费者”，不创建矩阵副本、不进入空队列、不伪称生成 Raw 文件。
- 未来显式启用 DaqAIContext 时，才进入已修复的无丢弃、首次真写、失败可重试 Raw 链。
- 当前生产主耐久链仍是 `EpbDiskRecorder + index.db + 按圈 BIN/CSV/Latest/报警快照`。

### 6.3 退出耐久门禁与同进程续测门禁分离

- 人工暂停后要在同进程续测：仍要求持久化 `State=Recovered`，低水位后必须有 10 个新鲜批次，不降低续测安全条件。
- 关闭程序/进程退出：先停止新 DAQ 回调，对最终已接收边界排空与 Flush，要求 `Published/Persisted >= Boundary`、队列为 0、`DurabilityBlocked=false`、`Discarded=0`、`OverCapacityDropped=0`。
- 如果只剩“等新鲜批次恢复状态”的历史锁存，数据完整时允许退出；真实写失败、丢批或边界未越过时仍保留进程重试。
- 关窗与一个在途非退出 Stop 竞争时，前者链接一次最终退出 Stop，不复用较弱的停止结果。

## 9. 限制、风险与稳健性边界

1. 自动测试证明代码不变量与故障注入，不能代替真实 NI 驱动、机械负载和电源网络尾延迟。
2. “无丢弃有界背压”优先保证数据不被静默删除。若磁盘长期不可写，系统必须安全暂停而不是无限缓冲；“稳定持续测试”仍依赖现场存储容量和尾延迟达标。
3. 封存副本的 `index.db-wal` 约 4.16 MB，SQLite 可正常回放且完整性为 `ok`；它仍证明程序未通过正常封账结束。
4. 14:50 后系统出现 100 MB/s 级读写与剩余空间快速变化，时间上晚于 14:44 根故障，可能与封存/备份活动重叠；它不能解释最初触发，但现场验收期间应避免同时压缩或复制整个活跃数据目录。

## 10. 部署和现场闭环

只能部署完整的 V2.12.0.24 正式候选目录，不得混用 V2.12.0.23 或旧 DLL/config，不得直接覆盖正在运行的目录。启动后先核对窗口标题和日志中的 ProductVersion、PID、EXE 路径、GitCommit、EXE/config SHA、BuildUtc 和 `GitDirty=false`。

每次封存后执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\Tools\Invoke-Field-Acceptance.ps1 `
  -DataDirectory '\\wj-epb\EPB_Data\10358-029_V2.12.0.24_封存目录' `
  -MinimumHours 2
```

验收必须同时满足：

1. UI Delay/Flush/Append/Trim/Scroll 单次全部小于 200 ms，`Dropped=0`、`FileDropped=0`。
2. 两块 DAQ 无 QueueFull/CallbackStale/ClockInvalid，回调最大空窗小于 100 ms。
3. 曲线无 UI 跳帧造成的假断线，真实 DAQ 断点仍应正确断笔。
4. `Discarded=0`、`OverCapacityDropped=0`，正常退出两设备 `RawDrained=true`、`Published/Persisted >= Boundary`、`Closed=true`。
5. 只有一个 `SESSION Start` 和一个 `Closed=true` 终态，无 running 圈、无通道滞留自维护。
6. 正常恢复必须回到试验；同根事故不重复进入自维护，超过有界重试时只执行一次整批重建。
7. 六通道合格圈比例不低于 99%，无 >17 A，CPU、工作集、句柄、线程、磁盘队列和剩余空间无长期恶化。

## 11. 进一步问题

- 是否需要产品化启用“连续原始 Raw 流”，还是继续以按圈 BIN/CSV/Latest/报警证据为正式存储合同？若启用连续 Raw，必须先定义存储带宽、容量与保留策略，不可直接打开旧定时器。
