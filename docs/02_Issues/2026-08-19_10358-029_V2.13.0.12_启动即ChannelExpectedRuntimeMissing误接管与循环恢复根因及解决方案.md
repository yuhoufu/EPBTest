## 1. 结论先行

本次不是 EPB 配置重复、DAQ 掉线、程控电源故障或卡钳硬件故障，而是 **V2.13.0.12 新增的 Watchdog 通道资源不变量范围错误**。

学习阶段的生产设计为：

```text
State=Learning
Runner=True
Timer=False
```

这是合法状态。学习圈由批次学习调度直接调用 Runner 执行，正式高精度 Timer 必须等全部学习/资格阶段完成后才创建。

V2.13.0.12 却把 `Learning` 纳入“Timer 和 Runner 必须同时存在”的状态集合，并执行：

```csharp
expectedActiveResourcesMissing = stateAllowsCycles &&
                                 (!TimerActive || !RunnerActive);
```

因此每次开始试验都会稳定形成：

```text
合法 Learning + Timer=False + Runner=True
  -> 持续 5 秒
  -> ChannelExpectedRuntimeMissing
  -> sidecar RequestStopAll
  -> 全部学习通道被取消并安全断电
  -> 当前 PID 被标记 SafeButRestartRequired
  -> 同 PID 再点启动被永久撤权门禁拒绝
  -> sidecar 根据 Armed checkpoint 启动恢复进程
  -> 恢复进程再次进入 Learning
  -> 5 秒后再次被同一规则接管
  -> 再次弹出恢复/停止窗口
```

V2.13.0.11 没有这条新增的 `ChannelExpectedRuntimeMissing` 规则，所以相同的合法学习资源形态不会被接管。这与“换回 V2.13.0.11 无此现象”完全一致，构成版本回归证据。

## 2. 三个现场现象分别是什么

### 2.1 新版开始试验就报错

开始试验后五个通道正常进入学习阶段，Runner 均已创建，第一学习圈也已经开始。约 5 秒后 sidecar 错误认为 EPB4 缺少运行资源并发送全局 StopAll，学习任务因取消令牌退出，最终界面显示：

```text
全部选中通道均在学习阶段被隔离，未启动正式试验。
```

“全部通道被隔离”是 Watchdog StopAll 的结果，不是五个通道同时发生了真实学习故障。

### 2.2 停止后再点启动仍报错

第一次误接管已经使当前进程进入：

```text
SafeButRestartRequired
```

安全层永久撤销该 PID 的重新上电资格。再次点击启动时，`ThrowIfProcessRestartRequired()` 正确拒绝同进程重启，并显示：

```text
上一次停止事务未完整清场，当前进程已永久撤销上电授权；
必须由 Watchdog 重启软件。
```

这条拒绝是误接管之后的次生安全动作，不是本次首要根因。不能通过删除该门禁或强行允许同 PID 上电来修复。

现场同时存在一个 UI 文案矛盾：Stop 终态实际是 `SafeButRestartRequired`，界面却又提示“停止试验完成；可以关闭软件或重新开始”。这会诱导操作员再次点击启动，必须一并修正。

### 2.3 关掉软件后不断弹恢复窗口

独立 sidecar 的职责是在主程序异常退出或被接管后，根据 Armed checkpoint 自动重启主程序。第一次误接管后：

1. sidecar 终止旧 PID；
2. 退避 5 秒；
3. 启动恢复 PID；
4. 恢复 PID 校验 checkpoint 并通过安全预检；
5. 恢复 PID 再次从学习阶段开始；
6. 同一错误不变量再次在 5 秒后触发；
7. sidecar 再次进入接管/恢复界面。

所以弹框不是多个无关错误，而是同一确定性误判在原进程和恢复进程中重复发生。

V2.13.0.12 已有限重试预算，因此单个 session 最终会阻断，不是旧版无边界 CircuitProbe；但每次人工重新启动都会创建新 session，错误条件又从头成立。对操作员而言仍表现为“每次启动都反复恢复”。

## 5. 直接代码根因

根因位于 [WatchdogPolicy.cs](../../Watchdog.Protocol/WatchdogPolicy.cs) 的 `WatchdogChannelProgressTracker.Evaluate()`。

V2.13.0.12 将以下状态全部并入 `stateAllowsCycles`：

```text
Running
WarningRunning
Learning
Qualification
Recovering
ResumeChecking
```

然后新增：

```csharp
var expectedActiveResourcesMissing = stateAllowsCycles &&
                                     (!item.TimerActive || !item.RunnerActive);
```

并对该条件使用 5 秒硬阈值：

```text
ChannelExpectedRuntimeMissing
```

问题是 `stateAllowsCycles` 原本表达“该状态需要监督机械进展”，并不等价于“该状态必须同时拥有正式 Timer 和 Runner”。V2.13.0.12 把两个不同概念错误复用了同一个布尔值。

### 5.1 生产启动顺序证明 Timer=False 合法

[EpbManager.BatchStart.cs](../../Controller/EpbManager.BatchStart.cs) 的实际顺序是：

```text
Publish State=Learning
  -> RunLearningPhaseAsync
  -> 可选 RunPausedQualificationAsync
  -> 确认学习/资格完成
  -> Publish State=Running
  -> StartFormalPhaseTimers
```

因此：

- `Learning`：Runner 必需，正式 Timer 不存在是正确状态；
- `Qualification`：仍处于正式 Timer 创建之前，Timer 不应被要求；
- `Running/WarningRunning`：正式阶段才要求 Timer 与 Runner 同时存在；
- `Recovering/ResumeChecking`：资源是否存在由 recovery owner/stage 决定，不能无条件要求两者同时存在。

### 5.2 为什么总是先报 EPB4

五个通道在同一时间进入 Learning 并同时满足错误条件。sidecar 按通道顺序遍历，EPB4 是第一个符合条件的 eligible channel，因此原因总是显示 EPB4。它不表示 EPB4 硬件比其他通道先坏。

## 9. 为什么 V2.13.0.11 没有该现象

`ChannelExpectedRuntimeMissing` 是 V2.13.0.12 为解决“授权通道缺少 Timer/Runner”而新增的规则。V2.13.0.11 不包含该规则，因此不会把学习阶段的 `Timer=False` 判成丢失资源。

这证明 V2.13.0.12 是明确的软件回归，但不代表 V2.13.0.11 已经安全。V2.13.0.11 仍存在已确认的：

- 正常活动圈误计入 `SoftwareRecoveryCount`；
- 假 `RecoveryActive` 可能导致全局 StopAll；
- EPB4 旧 Timer 迟到覆盖 `Recovering`；
- 永久失败后的无终点 CircuitProbe。

因此 V2.13.0.11 只能作为短期有人值守回退，不得恢复无人值守长时间运行。

## 11. P0 最小修复

建议修复版本号迭代为 `V2.13.0.13`，不得覆盖原 V2.13.0.12 文件而不改版本。

### 11.1 拆分“机械进展状态”和“资源契约”

不能简单从 `stateAllowsCycles` 删除 Learning，否则会同时失去学习圈机械进展监督。必须拆成三个独立概念：

```text
MechanicalProgressExpected
TimerRequired
RunnerRequired
```

最小正确映射：

| 业务状态 | 监督机械进展 | TimerRequired | RunnerRequired | 监督方式 |
|---|---:|---:|---:|---|
| Starting | 否 | 否 | 否 | 批次启动/预检硬期限 |
| Learning | 是 | 否 | 是 | Runner + 学习圈进展/学习硬期限 |
| Qualification | 是 | 否 | 是 | Runner + 资格圈进展/资格硬期限 |
| Running | 是 | 是 | 是 | Timer + Runner + 正式机械圈进展 |
| WarningRunning | 是 | 是 | 是 | Timer + Runner + 正式机械圈进展 |
| Recovering | 按 owner | 否 | 否 | Recovery owner/stage/hard deadline；只检查非法单边残留 |
| ResumeChecking | 按 owner | 否 | 否 | Recovery owner/stage/hard deadline；只检查非法单边残留 |
| Paused | 否 | 不推断 | 不推断 | 必须有 ManualPause owner |
| Completed/Stopped/NotEnabled | 否 | 否 | 否 | 必须无活动执行资源 |

生产逻辑至少应改为：

```csharp
var formalRuntimeRequired =
    StateIs("Running") || StateIs("WarningRunning");

var stagedRunnerRequired =
    StateIs("Learning") || StateIs("Qualification");

var expectedActiveResourcesMissing =
    (formalRuntimeRequired && (!item.TimerActive || !item.RunnerActive)) ||
    (stagedRunnerRequired && !item.RunnerActive);
```

`Recovering/ResumeChecking` 继续使用 recovery owner、stage、hard deadline 和 Timer/Runner 单边不一致检查，不得复用正式运行资源契约。

### 11.2 给不变量计时器增加身份

当前 `_invariantTimestamps` 只按 channel 保存时间。如果通道从一种不变量切换到另一种不变量，旧计时可能被新状态继承。

应保存：

```text
RunId
RunEpoch
Channel
InvariantCode
State
ExpectedTimer/Runner
ActualTimer/Runner
SinceMonotonic
```

当 Run、Epoch、State 或 InvariantCode 改变时重新开始计时。禁止把 Learning 中的旧计时带入 Running。

### 11.3 正式资源缺失触发前请求一次结构化刷新

对非立即危险的资源矛盾：

1. 连续观察相同 Run/Epoch/状态/资源签名；
2. 先记录 `ChannelRuntimeContractInconsistent` 并请求 Ping/状态刷新；
3. 刷新后仍满足相同正式资源缺失，且超过 5 秒，才全局接管；
4. Energized 且控制证据陈旧等直接安全风险仍保持快速 OFF，不受该刷新流程影响。

该措施不能替代状态契约修复，只作为第二道防线。

## 12. P0 完整修复

### 12.1 心跳显式发布资源契约

长期方案不应让 sidecar 仅凭状态字符串猜测。建议每通道新增：

```text
LifecyclePhase
RuntimeContractRevision
TimerRequired
RunnerRequired
ManualPauseOwned
RecoveryOwned
PhaseHardDeadlineUtc
```

主程序从统一状态机生成契约，sidecar 使用同一份纯策略映射反向校验。若主程序发布的 required 标志与业务状态不一致，记录协议错误，但不能把合法 Learning 直接全局 StopAll。

### 12.2 区分“Watchdog 自己造成的取消”

PID 18120 的：

```text
OperationCanceledException: 已取消该操作
```

是 sidecar 第二次 `RequestStopAll` 主动取消学习任务造成的，却被分类为：

```text
UnhandledSoftwareStartup
MaximumProcessRelaunches=2
```

应携带 TakeoverCorrelationId/取消 owner。若取消由当前 sidecar 接管引起，应上报：

```text
RecoverySupersededByTakeover
```

并禁止把它作为新的独立启动失败再次增加重拉预算，避免 Watchdog 对自己制造的取消继续恢复。

### 12.3 修正停止后的 UI 状态

当 Stop 终态为 `SafeButRestartRequired`：

- 禁用“开始试验”；
- 不显示“可以重新开始”；
- 显示“安全停止已完成，当前进程不可再次上电，请等待 Watchdog 或关闭后启动修复版本”；
- 同一原因只显示一个非阻塞状态面板，避免重复 modal 弹框；
- 展示根原因 `ChannelExpectedRuntimeMissing` 和当前 session id，不只展示次生的“永久撤权”。

安全撤权逻辑本身应保留。

## 13. 必须新增的测试

### 13.1 状态/资源契约单元测试

1. `Learning + Timer=false + Runner=true` 连续 10 分钟不得触发资源缺失；
2. `Qualification + Timer=false + Runner=true` 连续 10 分钟不得触发资源缺失；

5. `Running + Timer=true + Runner=false` 达到 5 秒必须触发；
6. `Running + Timer=true + Runner=true` 不得触发；
7. `Recovering + Timer=false + Runner=false + 有效 owner/stage/deadline` 不得按运行资源缺失接管；

### 13.3 端到端测试

1. 五通道完成完整 10 圈学习并进入正式 Timer，期间无 `TakeoverRequested`；

5. sidecar 自己触发的取消不得被重新分类为独立 `UnhandledSoftwareStartup`；
6. `SafeButRestartRequired` 时 UI 禁止点击开始且不显示相互矛盾文案；
7. 连续执行 100 次“启动学习 -> 完成 -> 正式 -> 停止”，无 PID 泄漏和弹框风暴。

## 16. 最终判定

- **开始即报错的直接原因已确认**：V2.13.0.12 把合法 `Learning + Timer=False + Runner=True` 错判为 `ChannelExpectedRuntimeMissing`。
- **停止后同 PID 不能启动是次生安全门禁**：误接管产生 `SafeButRestartRequired` 后，当前 PID 的上电授权被永久撤销；不能删除该门禁来掩盖根因。
- **关窗后反复恢复的原因已确认**：sidecar 按 Armed checkpoint 拉起新 PID，新 PID 再次进入 Learning 后被相同规则接管。
- **V2.13.0.11 无此现象符合代码差异**：该版本没有新增的错误资源不变量，但仍存在其他已确认风险。
- **配置、checkpoint、DAQ 和物理安全链不是本次根因**：12 个 EPB Id 唯一，checkpoint 校验和安全预检通过，DAQ gap 为 0，最终输出已安全关闭。

在阶段感知资源契约修复、专用回归和正式包现场验收完成前，不得重新部署 V2.13.0.12。
