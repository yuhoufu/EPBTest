## 1. 结论

V2.13.0.33 本次失败已经能够由封盘日志、Watchdog Journal、恢复检查点和分支源码完整解释。它不是卡钳、电源、液压或 DAQ 随机故障，也不是纯管道故障误杀，而是三条软件缺陷串联：

1. **首要根因（P0，已确认）：正式周期参与者被冷启动清场留下的“退休证据”全部提前退休。**  
   冷启动安全基线在正式槽尚不存在时，对 12 个通道执行 `UnmarkHydraulicParticipant`。V2.13.0.32/33 新增的退休协调逻辑把这次清场永久缓存为当前 run 的 `_confirmedRetirements`，键中只有 `runId + channel`，没有阶段、参与者代次或重入租约。学习结束后，EPB 4、5、11、12 虽重新加入正式运行，但旧退休证据没有清除。首个正式槽创建时，协调器先应用旧证据，再把四个健康通道全部判为 `FormalBatchSlotMemberAlreadyRetired`。
2. **接管原因（P0，已确认）：看门狗因真实的正式机械进度停滞而接管，不是心跳误杀。**  
   四个通道每 15 秒进入一次定时器回调，但均在槽准入前抛异常，未发生任何正式机械动作。最后一次学习机械进度约在 01:44:41，01:45:41 Watchdog 以 `FormalProgressStalledAggregateFallback` 发起接管，符合 60 秒正式进度硬门禁。StopAll 的电机断能、电源关闭、液压释放和落盘排空均成功。
3. **恢复风暴根因（P0，已确认）：接管退出仍走了普通关闭清场，撤销了本应交接的恢复检查点。**  
   StopAll 完成后，旧进程又执行 `PrepareForFreshRestartAsync` 和 `ApplicationClosing`，在 01:45:44 将检查点从 `Armed=true` 改为 `Armed=false`，原因是 `ApplicationClosing: 主窗体关闭`；最终镜像又记录 `MonitorClosing`。01:45:54 虽正确发送了 `WatchdogTakeoverExit`，但为时已晚。新 PID 15464 在 01:46:10 只能得到 `CheckpointDisarmed:MonitorClosing`，因此拒绝续跑并进入后续恢复尝试。
4. **独立伴随缺陷（P1，已确认）：Watchdog 客户端连接生命周期仍有竞态，且客户端/Sidecar 超时策略不一致。**  
   约 3 分钟内出现 9 次 ACK 超时、9 次同 Session 重连、13 个 Sidecar 连接代次和一次 `CancellationTokenSource 已释放` 的未观察任务异常。V2.13.0.33 的 UI 探针成功避免了纯传输故障直接杀进程，但客户端仍在约 3.1 秒 ACK 空窗时主动拆连接，早于 Sidecar 的 5 秒 UI 复核门槛，因此持续制造连接抖动。

**综合判定：V2.13.0.33 不具备无人值守放行条件。** 推荐修复版本定为 `V2.13.0.34`，以 `codex/recovery-v2.13.0.30` 的稳定正式周期行为为基线，审计式前移 V2.13.0.33 已验证有价值的安全修复；不建议把 V2.13.0.32/33 的两个大提交整体合并到稳定分支，也不建议只在当前代码中删除一条异常判断后直接现场试跑。

## 4. 首要根因：冷启动清场污染正式参与者代次

### 4.1 确定性代码链

当前 V2.13.0.33 行为链如下：

1. `StartBatchCoreUnderLifecycleGateAsync` 先生成 `_activeBatchId`，随后调用 `EstablishColdStartSafeBaselineAsync`。
2. 冷启动基线对 1～12 通道全部执行 `UnmarkHydraulicParticipant`，这是正确的物理/液压清场意图。
3. 新版 `UnmarkHydraulicParticipant` 无条件调用 `RequestFormalParticipantRetirement(runId, runEpoch, channel, ...)`。
4. 退休安全栅栏在通道已断能、无液压租约、执行许可未授权时立即成立，并把结果写入 `_confirmedRetirements`。
5. `_confirmedRetirements` 的键仅为 `runId:channel`，没有 `runEpoch`、学习/正式阶段或参与者代次。
6. 学习阶段和正式阶段的 `MarkHydraulicParticipant` 只恢复液压参与集合，不撤销旧的正式退休证据。
7. 正式 Timer 首次调用 `EnterAsync` 时，新槽先执行 `ApplyConfirmedRetirementsUnderLock`，四个健康成员都被从 `Pending` 移除。
8. 同一回调随后检查自身不在 `Pending`，抛出 `FormalBatchSlotMemberAlreadyRetired`。

因此该故障不是概率竞态。只要走“新 run -> 冷启动全通道清场 -> 学习 -> 正式”的正常路径，就具备必现条件。

### 4.2 为什么现有测试没有发现

当前 `FormalBatchSlotCoordinatorTests` 覆盖了：

- 退休请求在安全证据确认前不能释放槽；
- 不安全退休必须 fail-closed；
- 重复进入同一槽必须拒绝；
- 退休确认后，携带旧参与者快照的迟到槽必须关闭。

这些用例都从“通道确实已经退休”出发，没有覆盖真实生命周期：

```text
新 run 创建
  -> 冷启动基线 Unmark（此时没有正式成员）
  -> 学习阶段 Mark/完成
  -> 正式阶段重新 Mark
  -> 首个正式槽应准入
```

因此测试验证了局部退休算法，却没有验证“清场、学习、正式”跨阶段组合不变量。

### 4.3 为什么 V2.13.0.30 不发生

稳定分支的 `FormalBatchSlotCoordinator.RetireParticipant` 只遍历**当时已经存在**的 `_slots`，从现有槽的 `Pending` 中移除成员；它没有 `_retirementRequests`、`_confirmedRetirements` 或跨未来槽缓存。

冷启动基线发生在正式槽创建之前，所以 V2.13.0.30 的清场不会影响未来正式槽。正式阶段冻结参与者后，EPB 4、5、11、12 可以正常进入屏障、执行机械动作并提交圈终态。V2.13.0.30 的优势不是“忽略安全证据”，而是**退休证据的作用域与当时存在的正式槽一致**。

## 5. Watchdog 传输问题：未误杀，但仍不稳健

### 5.1 现场事实

V2.13.0.33 在约 3 分钟内记录：

- 9 次 `WatchdogHeartbeatAckTimeout`，`AckAgeMs=3040～3246`；
- 9 次同 Session 重连成功；
- 3 次 Attach 发送失败；
- Sidecar 连接代次从 1 增长到 13；
- 2 次 `HostTransportWriteTimeout`，均为 Ping，写入上限 500 ms；
- UI 探针返回 `WmNullAcknowledged`，证明当时主 UI 可响应；
- 1 次 `TaskScheduler.UnobservedTaskException`，根异常为 `CancellationTokenSource 已释放`，位置在 `ConnectOwnerAsync` 创建 Reader Task 的 lambda。

纯传输故障期间 Sidecar 没有杀进程，说明 V2.13.0.33 新增的 UI 存活复核是有效的。01:45:41 的真正接管原因明确是 `FormalProgressStalledAggregateFallback`，不能把它归因于上述 ACK 抖动。

### 5.2 仍然存在的设计缺陷

1. 客户端约 3 秒未收到 ACK 就把连接判死并重连；Sidecar 的策略却是 3 秒怀疑、5 秒后才做 UI 探针。客户端总在 Sidecar完成独立判定前拆管道。
2. `Task.Run(() => ReaderLoopAsync(lifetime.Token, ...))` 在 worker 真正运行时才读取 `lifetime.Token`。如果连接在排队期间被退休并释放 CTS，lambda 会在后台抛 `ObjectDisposedException`，且没有统一观察。
3. Host 已有单写 owner，但客户端也存在独立发送 owner、连接安装、Reader/Heartbeat 启动和退休的交叉窗口；连接资源没有被一个不可分割 owner 管到底。
4. 进程退出后 Sidecar 在 RecoveryBackoff 状态约每 250 ms 重复记录 `HeartbeatUnresponsiveConfirmed`，共 43 次；这既不符合“每秒探针”的设计，也制造无意义日志风暴。

## 6. 恢复退出问题：消息类型正确，关闭事务仍然错误

V2.13.0.33 已把 `WatchdogRecoveryExit`/`WatchdogTakeoverExit` 与人工 `ShutdownExpected` 分开，Sidecar 收到 `WatchdogTakeoverExit` 后也确实保持运行并拉起了新进程。这部分修复是正确的。

未闭环的是消息发送前的 UI/控制清理：

- `WinFormsWatchdogStopHandlerCore` 对接管请求调用 `PrepareForFreshRestartAsync`；该方法不仅做 StopAll，还清空旧批次逻辑状态，语义适用于同进程人工重新开始，不适用于跨进程恢复交接。
- Main 的强类型退出意图没有在关闭子监控窗体前写入 `FrmEpbMainMonitor._watchdogTakeoverExit`。
- 子监控窗体关闭时仍把自己视为普通关闭，进入 `ApplicationClosing` 并撤销恢复检查点。
- Checkpoint 在 01:45:44 已失效，直到 01:45:54 才发送正确的 `WatchdogTakeoverExit`，消息类型无法补救已被删除的恢复授权。

因此“强类型退出”必须覆盖从接管开始到最后一个子窗体关闭的整个事务，而不能只影响最后一条管道消息。

## 8. V2.13.0.34 彻底修复设计

### 8.1 正式参与者改为强类型、带代次的租约

引入不可变 `FormalParticipantLease`，至少包含：

```text
RunId + RunEpoch + Channel + ParticipantGeneration + FormalPhaseGeneration
```

协调器接口调整为：

```text
BeginRun(runId, runEpoch)
RegisterFormalParticipant(channel) -> FormalParticipantLease
EnterAsync(lease, slotOrdinal, frozenParticipants, ...)
RequestRetirement(lease, reason)
ConfirmRetirement(lease, terminalEvidence)
EndRun(runId, runEpoch)
```

必须满足以下不变量：

1. 没有有效正式租约的 `Unmark` 是幂等清场，不能创建未来退休证据。
2. 学习阶段液压参与者与正式阶段参与者分开建模；学习开始/结束不得调用正式退休接口。
3. 正式成员只在学习/资格阶段全部终结后统一注册，再创建 Timer。
4. 暂停后重入或恢复重入必须生成新的 `ParticipantGeneration`；旧异步退休栅栏即使晚完成，也只能写旧代次并被丢弃。
5. 退休确认只影响同一 run、epoch、正式阶段代次和参与者代次；不得跨 run、跨阶段、跨重入生效。
6. `EndRun` 原子撤销所有租约、槽、退休请求和确认；晚到任务只记录 `StaleFormalParticipantLeaseIgnored`。
7. 合法的永久报警退休仍必须等待电机 OFF、液压租约关闭、圈持久化终结和执行许可撤销，安全边界不放宽。

禁止采用下面两个“快速补丁”：

- 在 `MarkHydraulicParticipant` 中简单删除 `_confirmedRetirements`：旧的异步 `ConfirmRetirement` 仍可在删除后晚到并再次污染新成员。
- 遇到 `AlreadyRetired` 时直接忽略异常继续做机械动作：这会绕过真实永久报警成员的安全退休证据。

### 8.2 把冷启动、学习、正式三类参与状态拆开

建议将当前复用的 `_hydraulicParticipants` 拆成明确状态：

- `BaselineSafeOff`：只有断能/清场语义；
- `LearningParticipant`：只参与学习液压协调；
- `FormalParticipant(lease)`：参与正式全局槽；
- `RetirementPending(lease)`：已封住下一圈，等待安全栅栏；
- `Retired(lease)`：同代次正式退休完成。

任何状态迁移必须校验 run/epoch/lease。正式首槽前增加一次同步不变量检查：四个 Timer 计划成员、正式租约成员和冻结槽成员必须完全相等；不一致时在机械动作前立即 StopAll 并输出唯一诊断，不再等待 60 秒才由 Watchdog 推断进度停滞。

### 8.3 客户端与 Sidecar 共用一套心跳/ACK 策略

1. 协议 v3 可保持不变，但所有阈值从 `WatchdogPolicy` 单一来源读取。
2. 3 秒只进入 `TransportSuspect`，客户端不得立即销毁管道。
3. 5 秒后由 Sidecar按 PID/启动时间和 UI 探针判定；UI 可响应时只退休精确连接并重连。
4. 客户端只在明确 EOF/IO 错误、Session 被撤销，或超过 `5 秒 + 500 ms 探针 + 调度余量` 后退休连接。
5. 控制消息队列继续高于 Ping/Heartbeat，Host 和 Client 都只能有一个 writer owner。

### 8.4 连接资源由单一 owner 完整持有

建立 `ClientConnectionOwner`，一次性持有：

```text
Pipe + Reader + Writer + CancellationTokenSource + captured CancellationToken
+ SendWorker + ReaderWorker + HeartbeatWorker + ConnectionGeneration
```

关闭顺序固定为：

```text
StopAccepting
  -> Cancel（不 Dispose）
  -> Close Pipe 解除阻塞
  -> 有界等待并观察三个 worker 终态
  -> Dispose Reader/Writer/Pipe/CTS
  -> 发布 Retired
  -> 允许安装下一代连接
```

`CancellationToken` 必须在创建 worker 前捕获为值，lambda 内不得再读取可能已释放的 `CancellationTokenSource.Token`。所有 `Task.Run` 和 `TaskCompletionSource` 的异常都必须由 owner 统一观察；自动化测试结束时 `TaskScheduler.UnobservedTaskException` 必须为 0。

### 8.5 Watchdog 接管改为两阶段持久交接

新增强类型 `WatchdogTakeoverHandoff`，把“安全停机”和“恢复授权转移”组成一个事务：

#### 阶段 A：冻结恢复事实

1. 收到精确 takeover correlation 后，冻结 active run、run epoch、通道、剩余机械次数和最后持久化边界。
2. 原子写入 `Armed=true, RestartPending=true` 的 checkpoint，并生成 revision、SHA-256 和 takeover correlation。
3. Sidecar 收到并持久化 `CheckpointPrepared` 回执后，才允许控制器进行破坏性逻辑清场。

#### 阶段 B：安全停机并交还进程

1. 调用专用 `StopForWatchdogTakeoverAsync`，只执行电机 OFF、电源关闭、液压释放、落盘排空和 worker 收口；禁止调用 `PrepareForFreshRestartAsync`。
2. `StopCompleted` 必须携带同一 correlation、checkpoint revision/hash 和物理安全摘要。
3. Main 在关闭任何子窗体前，把 `RuntimeShutdownIntent.WatchdogTakeoverExit` 发布给所有 UI owner。
4. Takeover/Recovery exit 路径禁止 `ApplicationClosing`、`MonitorClosing` 或任何 `Disarm`；只允许显式人工关闭撤销 checkpoint 并发送 `ShutdownExpected`。
5. Sidecar 验证旧 PID 退出后只消费一次 relaunch permit；新进程用同一 checkpoint hash 恢复。
6. 若 checkpoint 准备或回执失败，旧进程保持断能、可见诊断，不退出；不得留下“看门狗准备拉起、检查点却被旧进程删除”的半事务。

### 8.6 确定性软件不变量不得无限重启

`FormalBatchSlotMemberAlreadyRetired`、`FormalBatchSlotImmutableMismatch` 等框架不变量必须携带稳定 fingerprint。若同一二进制、同一配置、同一根因 fingerprint 在恢复启动前再次出现：

- 保持设备断能；
- 打开恢复熔断；
- Watchdog 保持运行并展示诊断；
- 不继续第 2、3……次拉起同一确定性缺陷二进制。

这不会替代根因修复，但能防止未来同类软件缺陷演变为无限闪屏和进程风暴。

### 8.7 发布身份成为无人值守准入条件

现场候选包必须生成并校验：

- Git commit、dirty 状态和 BuildUtc；
- 主程序、Watchdog、Client、Protocol 及配置文件哈希；
- 统一 `2.13.0.34` 版本；
- `PackageVerified=True`。

`PackageManifestMissing` 的开发目录可用于台架调试，但不得被标记为“封盘合格包”，也不得用于最终无人值守验收。

## 9. 自动化测试与验收矩阵

### 9.1 正式参与者生命周期

- 新 run 建立后对 12 通道做冷启动 `Unmark`，再让 4/5/11/12 完成学习并注册正式租约；首个正式槽四通道均成功准入。
- 学习阶段正常结束不得生成任何正式退休记录。
- 同一通道暂停、重入后旧代次 `ConfirmRetirement` 晚到，必须记录 stale 且不能影响新槽。
- 真正永久报警成员在安全证据未齐前不能释放兄弟成员；证据齐全后只退休同代次成员。
- 同组成员合并、跨液压组并行、迟到回调、重复准入、取消前撤回和 `EndRun` 后晚到任务全部覆盖。
- 用 1000 次随机并发时序验证无死锁、无重复 scope、无跨代污染。

### 9.2 端到端批次

- 模拟 4/5/11/12 两电气组、两液压组：冷启动基线 -> 10 圈学习 -> 至少 100 圈正式运行。
- 断言学习 40 圈后必有正式 `FieldMetric CYCLE`；`FormalBatchSlotMemberAlreadyRetired=0`。
- 学习软预警、落盘 100～200 ms 短滞后、DAQ 短空窗和电源遥测短延迟均不得污染正式成员租约。
- 第一条正式框架不变量异常必须直接形成唯一故障，不得连续 4 圈重复相同异常后才接管。

### 9.3 Watchdog 传输

- 注入 0.5、3、6 秒写阻塞；UI 响应时只能重连，不能接管。
- 并发控制消息与普通消息，验证控制队列不被 Ping/Heartbeat 饿死。
- 精确连接在 `Task.Run` 排队、Reader 启动、Heartbeat 启动、Attach 发送和退休各窗口被关闭，均不得产生已释放 CTS/管道异常。
- 连续 100 次重连、旧 worker 晚完成、旧 writer 超时后，新连接不受破坏。
- 测试结束强制 GC，断言 `UnobservedTaskException=0`。
- UI 无响应连续三次、PID 退出和 PID/启动时间不匹配仍必须触发接管。
- `HeartbeatUnresponsiveConfirmed` 每个进程代次只发布一次；RecoveryBackoff 不继续每 250 ms 刷同类事件。

### 9.4 恢复交接

- 正式运行中注入 `FormalProgressStalled`：先持久化 armed checkpoint，再 StopAll，再 typed exit；旧进程退出后 Watchdog 只拉起一次，新进程恢复原 run。
- Takeover exit 的整个日志中不得出现 `ApplicationClosing`、`MonitorClosing` 或 `Armed true -> false`。
- 人工关闭仍必须 disarm checkpoint、发送 `ShutdownExpected`，双方正常退出。
- checkpoint 写入失败、Sidecar 回执丢失、correlation 不匹配时，旧进程保持安全可见，不退出。
- 同一确定性 fingerprint 复现时打开熔断，不进行无限拉起。

### 9.5 稳定基线差分

以 `codex/recovery-v2.13.0.30` 对同一模拟输入运行差分测试：

- 正式首槽和后续墙钟槽序一致；
- 机械成功圈、持久化边界和液压释放顺序一致；
- V2.13.0.34 可增加安全证据，但不得把 V2.13.0.30 的正常正式圈改判为退休、暂停或恢复；
- Watchdog 传输故障不得改变控制器正式参与者状态。

## 10. 现场验证与放行标准

软件测试通过后仍需 NI/CAN/液压设备验证，不能用单元测试代替。

### 10.1 建议步骤

1. 使用受控 V2.13.0.34 包，新建独立数据目录，不覆盖 V2.13.0.30 稳定证据。
2. 全断能执行 100 次“启动 -> 关闭 -> 再启动”及 100 次 Watchdog 管道重连测试。
3. EPB 4/5/11/12 完成 10 圈学习，确认首个正式周期立即产生机械动作和正式圈证据。
4. 连续运行至少 2 小时，期间人工注入 3 秒与 6 秒管道阻塞；UI 响应时不得接管。
5. 注入一次可恢复的主进程退出，确认 checkpoint 保持 armed、只拉起一次并续接原 run。
6. 连续运行 24 小时后复核机械计数、正式圈数、数据库边界、Watchdog Journal 和进程/句柄趋势。
7. 通过 24 小时门槛后再进行 7 天长稳；期间保留 V2.13.0.30 可回退包，但不得混用同一运行目录。

### 10.2 必须同时满足

- `FormalBatchSlotMemberAlreadyRetired=0`（除测试主动退休通道的预期迟到诊断）；
- 学习完成后正式首圈成功，正式机械进度持续前进；
- `TaskScheduler.UnobservedTaskException=0`；
- 纯传输故障接管次数为 0；
- 每次注入的真实进程故障最多拉起 1 次；
- Takeover exit 不撤销 checkpoint；
- 无主程序/Watchdog 双退出；
- 电机、电源、液压和持久化安全边界没有放宽；
- `PackageVerified=True`，版本和哈希与验收记录一致。

## 12. 最终判断

V2.13.0.33 的安全停机本身有效：没有证据表明接管时设备仍带电或落盘未完成；新增 UI 探针也阻止了管道故障直接误杀。问题在于两个跨生命周期的不变量仍未建立：

1. **清场/退休证据只能约束创建它的正式参与者代次，不能约束后来重新加入的健康成员；**
2. **Watchdog 接管退出必须保留并交接恢复检查点，只有人工关闭才能撤销。**

V2.13.0.30 能长期运行的核心原因是正式调度状态简单且作用域正确；V2.13.0.34 应在这一稳定行为上增加可证明的安全事务，而不是继续让跨阶段字典、异步退休任务和窗口关闭事件隐式共享状态。完成本文自动化、台架和 24 小时现场门槛前，不应宣称问题已彻底修复。
