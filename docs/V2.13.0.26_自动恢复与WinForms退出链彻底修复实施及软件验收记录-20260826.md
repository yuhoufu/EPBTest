## 1. 结论

针对 2026-08-26 的两次 V2.13.0.25 封盘，已在 V2.13.0.26 同时修复自动恢复停滞、恢复任务/租约残留、Watchdog 接管顺序错误、授权闭环缺失、管道半帧、实时监控子窗消失及主壳无法退出等相互耦合的问题。

本次不是通过放宽安全条件或隐藏弹窗来规避现象，而是把“停止接纳—安全清场—耐久授权—旧进程退出—新进程启动”的所有权和状态机闭环落到生产代码。Debug x86、Release Any CPU 构建以及仓库规定的三套完整回归均已通过。

软件层面已经具备进入现场验收的条件，但在完成 2 小时故障注入、100 次硬件接管循环、24 小时和 72 小时长稳之前，**不得把 V2.13.0.26 宣布为已批准的无人值守现场版本**。V2.13.0.25 仍禁止无人值守长时间运行。

## 3. 根因与修复对应

| 根因 | V2.13.0.25 风险 | V2.13.0.26 修复 |
|---|---|---|
| 恢复登记只有“是否存在”，缺少残留类型和有界排空 | 已完成但未发布终态的任务可能形成热循环；StopAll 等待失控 | `RecoveryTaskRegistry` 增加结构化残留分类、变更信号、取消传播和最大 60 秒有界排空；“任务已完成但无终态”立即识别 |
| StopAll 与新恢复接纳存在竞态 | 清场过程中仍可能创建新 Timer、Runner、CTS 或租约 | 增加恢复接纳闸门；停止、撤权与新恢复创建线性化；停止理由纳入自愈资格判断 |
| 恢复合约混淆逻辑所有权和物理安全范围 | 禁用成员可能阻塞逻辑恢复，或安全补偿覆盖不完整 | 合约拆分 `OwnedChannels` 与 `SafetyAffectedChannels`；状态/登记按逻辑所有权，OFF/液压补偿按物理安全组执行 |
| 安全终态先发布、资源后释放 | 外部接管看到 `ChannelTerminalResourcesActive`，在“正在确认设备安全状态”停滞 | 发布安全终态前先移除 CTS、Timer、Runner 和液压参与状态；资源计数改为去重后的真实数量 |
| Watchdog 接管阶段可乱序或悬停 | Permit 已批准但 Dump、终止、启动未形成强制顺序；许可可能永久停在 Approved | Host 使用生产阶段执行器，严格执行 Dump → Permit → 可选终止 → Relaunch；2 秒记录停滞，5 秒撤销/熔断；取消和失败耐久写入 Revoked/CircuitOpen/Superseded |
| 普通会话关闭和真正进程退出共用同一消息语义 | Sidecar 可能在正常会话切换时误认为 PID 必须退出，也可能在子窗尚未安全清理时提前计时 | 区分 `ApplicationClosing` 与 `ShutdownExpected`；只有真正应用退出才要求 PID 消失，并在所有 MDI 子窗安全关闭后才启动 5 秒 PID 观察 |
| MDI 旧退出守卫否决 Watchdog 终态关闭 | 实时监控窗消失后只剩灰色主壳，退出又被“仍有试验”提示拦截 | Watchdog 终态授权绕过旧 MDI 守卫；普通用户退出仍保留原安全检查；子窗最长等待 15 秒，失败保留可见主壳并允许重试 |
| 实时监控窗 `async` 关闭链可重入 | 子窗先消失，StopAll、持久化或 DAQ 释放仍在后台，状态与 UI 生命周期脱节 | `FormClosing` 同步取消首次关闭，启动唯一 Task 清理；StopAll、持久化、DAQ 和资源释放全部完成后才执行最终 Close，异常统一捕获 |
| 命名管道使用裸 JSON | 超时或断连可能留下半帧/串帧，Sidecar 无法可靠判断命令完整性 | 引入 WDG4 长度 + SHA-256 + Base64 帧，4 MiB 上限；兼容旧 JSON；半帧和损坏帧统一判为 `TransportInterruptedPartialFrame` 并失败关闭 |
| x86 长时恢复缺少明确内存防线 | 恢复任务泄漏可能最终触发 OOM，使接管链雪崩 | 增加 600 MiB 警告、800 MiB 拒绝和 30 秒增长监测；连续 100 次恢复验证无所有权和 Failure 残留 |

## 4. 关键实现范围

### 4.1 恢复与停止安全

- `Controller/RecoveryTaskRegistry.cs`
- `Controller/RecoveryIncidentCoordinator.cs`
- `Controller/ChannelRuntimeState.cs`
- `Controller/EpbManager.cs`
- `Controller/EpbManager.StopSafetyOperations.cs`
- `Controller/EpbManager.StopSafetyHardening.cs`
- `Controller/EpbManager.TimerRuntimeHealth.cs`

形成以下不变量：

1. StopAll/StopSafety/ApplicationClosing 期间不接纳新恢复。
2. 清理等待有硬截止、有取消传播，不允许无限轮询。
3. 逻辑状态所有权与物理安全补偿范围分别计算。
4. 安全终态发布时不得残留 Timer、Runner、CTS、液压参与状态或恢复登记。
5. x86 内存超过拒绝线时不再创建恢复任务，保持安全阻断并输出诊断。

### 4.2 Watchdog 接管与传输

- `MTTFTest.Watchdog/WatchdogHost.cs`
- `MTTFTest.Watchdog/StrictHostRelaunchOrchestrator.cs`
- `Watchdog.Protocol/TakeoverTransactionCoordinator.cs`
- `Watchdog.Protocol/DurableRelaunchAuthorityV4.cs`
- `Watchdog.Protocol/WatchdogProtocol.cs`
- `Watchdog.Client/WatchdogClientTransportEngine.cs`

形成以下不变量：

1. 接管阶段只能单调推进，禁止跳过 Dump 或 Permit。
2. Permit 每次状态变化带耐久时间戳；已批准但未消费必须在 2 秒被观察、5 秒被撤销或进入熔断。
3. 只有完整且校验通过的帧才能被执行；超时、半帧和哈希不一致均失败关闭。
4. `ShutdownExpected` 后 5 秒内旧 PID 未退出，Sidecar 捕获证据并终止同一进程身份；普通会话关闭不触发该规则。

### 4.3 WinForms 生命周期

- `MTTfTest/FrmEpbMainMonitor.cs`
- `MTTfTest/Main_Frm.WatchdogUi.cs`
- `MTTfTest/Main_Frm.cs`
- `MTTfTest/WinFormsWatchdogUiCloseCoordinator.cs`
- `MTTfTest/MainWatchdogUiLifecycleAdapter.cs`
- `MTTfTest/WatchdogRuntime.cs`
- `MTTfTest/ShutdownRetention.cs`
- `MTTfTest/Program.cs`

新的退出顺序为：

1. 取得唯一退出所有权。
2. 逐个请求 MDI 子窗执行安全清理并等待 `FormClosed`。
3. 子窗在 15 秒内全部关闭后，发送真正的进程退出语义。
4. 授权主窗关闭；Sidecar 开始 5 秒 PID 消失观察。
5. 子窗清理失败或超时则记录 `MainProcessExitStalled`，保留可见主壳，不制造不可操作灰壳。

## 8. 现场验收与放行门槛

### 8.1 2 小时故障注入

分别注入 DAQ 陈旧、恢复超时、电源组故障、Watchdog 管道中断和子窗关闭延迟，核对：

- 物理输出先进入 OFF；
- 日志阶段单调推进；
- 旧进程按预期退出；
- 新进程只在许可有效且预检通过时启动；
- 健康组继续、故障组安全阻断；
- 不出现灰色主壳和不可操作空壳。

### 8.2 100 次硬件循环

连续执行“故障—StopAll—接管—旧进程退出—新进程预检—恢复或安全阻断”100 次。每次结束都必须满足：

- `RegistryLeases=0`、`Contracts=0`；
- 无活动 Timer、Runner、CTS 或液压参与残留；
- Permit 最终为 Consumed、Revoked、Superseded 或 CircuitOpen，不得永久停在 Approved；
- 同一根 RunId/RunEpoch 的阶段不回退；
- x86 私有内存不持续单调增长。

### 8.3 24/72 小时长稳

先通过 24 小时观察，再执行 72 小时无人值守候选测试。以下任一事件出现即判失败：

- `TimerRuntimeStateLost Reason=StopAll:*`；
- `ChannelTerminalResourcesActive` 长期不收敛；
- `Approved + LaunchConsumed=False` 超过 5 秒；
- `ShutdownExpected` 后旧 PID 超过 5 秒仍存在且 Sidecar 未处置；
- 实时监控窗消失但同一 PID 仍可重新开始试验；
- 主界面消失或只剩不可操作灰壳；
- 内存超过熔断线或随恢复次数持续增长。

只有 T1—T12、2 小时故障注入、100 次硬件循环、24 小时和 72 小时长稳全部通过，才批准无人值守运行。
