## 1. 实施结论

本次已经修复导致“重启软件可以恢复、Watchdog 连续失败后却永久停机”的完整软件故障链。修复不是单纯把重试次数从 3 改成 5，而是同时完成以下闭环：

1. 100 ms 样本陈旧只负责当前周期快速 OFF，不再直接拥有整套 DAQ 重建；
2. Controller 向 Watchdog 提供真实的 `OutputsConfirmedOff`、`PowerOffUnconfirmed` 和跨进程可比较的绝对恢复截止时间；
3. StopAll 先撤销旧 Run 的 Timer、Runner、液压 Lease/Generation，再独立执行物理断能与压力确认，不再等待缺员的正常液压屏障；
4. 恢复检查点由 LocalAppData 单点改为本机主副本、项目主副本、Watchdog 日志镜像和追加审计；
5. 只有新进程完成安全预检并真正提交恢复批次后，才清零连续失败计数；普通心跳、进程附着和窗口打开均不算恢复成功；
6. 快速恢复允许连续 5 个新进程尝试，5 次均未提交后转入设备保持 OFF 的低频单实例探测，不再永久放弃无人值守监督；
7. 新进程启动时立即把旧进程遗留的 `running` 周期收敛为 `aborted_on_startup`，避免孤儿周期永久污染统计；
8. 自动接管强杀旧进程前进行 3 秒有界 MiniDump，转储失败只影响诊断，不阻止安全退出。

自动化回归和两套工程编译已通过。真实 NI 硬件故障注入、72 小时注入运行及 7 天无人值守长稳尚未在本次源码环境执行，因此本修复应作为新版本候选包进入第 8 节的现场验收，不能直接把现有 V2.13.0.10 原包重新标记为已合格。

## 3. 关键实现说明

### 3.1 安全关断与基础设施恢复分层

修复后保留 100 ms 快速安全门限。活动周期发现 `DaqSampleStale` 时仍立即撤销本圈并关闭输出，但只记录 `DAQ_FRESHNESS_SAFETY_CUTOFF`，不再从 runner 回调直接调用 DAQ 自动恢复。

独立 DAQ liveness 监督仍是设备任务恢复的唯一 owner：

- 100 ms：Warn，活动输出立即进入安全关断；
- 1000 ms：Suspect；
- 2000 ms 且连续 3 次扫描异常：允许局部 DAQ 恢复；
- 回调自行恢复而未达到重建条件：必须连续 500 ms 保持 callback、enqueue、processed 全部新鲜，才允许进入下一圈。

这样既没有放松安全关断速度，也避免一次短空窗被重复升级为周期层恢复、DAQ owner 恢复和进程级恢复。

### 3.2 Controller/Watchdog 契约与时限所有权

心跳新增：

- `OutputsConfirmedOff`：受影响输出已经获得权威 OFF 证据；
- `PowerOffUnconfirmed`：仍处于安全切断阶段，至少一个电源组缺少 OFF 确认；
- `RecoveryHardDeadlineUtc`：Controller 恢复流水线的绝对 UTC 截止时间；
- `RecoveryProgressVersion`：内部恢复有进展时递增；
- `RecoveryBatchCommitGeneration`：恢复批次提交代次，后续心跳重复发送。

Watchdog 现在只在两类条件下接管：

1. 严格的 `PowerOffUnconfirmed` 持续越过 5 秒安全断能期限；
2. Controller 已越过自身绝对硬截止，且连续 5 秒没有恢复进展。

`ActiveRecovery`、`ExpectedOutputEnabled` 或恢复过程中的逻辑 Active 不再等价于“硬件仍带电”。这消除了事故中 Controller 允许 60 秒、Watchdog 却约 5 秒抢占的时限倒置。

### 3.3 StopAll 强制收敛

StopAll 新顺序如下：

```text
撤销上电授权并推进 RunEpoch
  -> ForceAbortRun：撤销旧 Run 的液压 scope/generation/gate/barrier
  -> 强制暂停并移除 Timer、Runner，取消其 CTS
  -> 提交 DO/AO OFF 与程控电源关闭
  -> 执行原有 Stop 核心清理
  -> 独立确认电源 OFF、DO/AO 回零和新鲜压力证据
  -> 返回 Safe / SafeButRestartRequired / Unsafe
```

`ForceAbortRun` 只声明软件 owner 已被撤权，不会把压力安全伪装成成功；物理压力与输出仍由 StopAll 后半段独立验证。因此缺少液压组成员不会再占满整个 15 秒预算，同时安全证据没有被削弱。

### 3.4 可恢复、可审计的检查点

现场用户 `mt` 的文件布局为：

| 用途 | 路径 |
|---|---|
| 本机主副本 | `\\wj-epb\Users\mt\AppData\Local\MTTFTest\unattended-run-checkpoint.json` |
| 本机备份 | `...\unattended-run-checkpoint.json.bak` |
| 本机审计 | `...\unattended-run-checkpoint.audit.jsonl` |
| 项目主镜像 | `{StoreDir}\{TestName}\Recovery\unattended-run-checkpoint.json` |
| 项目备份 | `{StoreDir}\{TestName}\Recovery\unattended-run-checkpoint.json.bak` |
| 项目审计 | `{StoreDir}\{TestName}\Recovery\unattended-run-checkpoint.audit.jsonl` |
| 全部候选读取失败归档 | `{StoreDir}\{TestName}\Recovery\CheckpointFailures\{UTC时间}\` |
| Sidecar 镜像 | Watchdog Journal 的 `LastCheckpointMirror` |

写入采用 `temp -> Flush(true) -> 原子 Replace/Move -> .bak`。每次检查点变更增加 `Revision`，记录 SHA-256、前后 Armed、Reason、RunId、RunEpoch、WatchdogSessionId、PID、本机/项目路径和项目镜像写入错误。

恢复读取会检查以下候选，候选顺序固定为：

1. 本机主副本；
2. 本机 `.bak`；
3. 项目主镜像；
4. 项目 `.bak`。

系统不会简单采用第一个有效文件，而是在全部有效候选中选择最大 `Revision`；只有 Revision 相同时才按上述顺序选择。这样在本机主文件损坏、本机 `.bak` 仍是旧 `Armed=true`、项目镜像已经写入新一版 Disarm 时，不会让旧备份反向恢复已经撤销的授权。

读取结果不再把所有异常吞成 `null`，而是区分 `Missing`、`JsonInvalid`、`IoError`、`Valid`。若全部失败，日志和项目失败目录会保留每一个候选的路径、分类与错误信息；若最新状态为 `Armed=false`，会报告具体的 `CheckpointDisarmed:<reason>`。

项目盘暂时不可写不会破坏已经落盘的本机主副本；镜像错误会进入审计。新进程消费成功后把实际来源和 SHA 发给 Sidecar，后续可以回答“恢复到底用了哪一个副本”。

### 3.5 连续 5 次与低频安全探测

新的计数定义是“从上一次 `RecoveryBatchCommitted` 之后，连续有多少个恢复进程未能提交批次”。普通心跳、窗口创建、进程启动、Pipe 附着、checkpoint 读取成功和安全预检成功都不能清零。

快速拉起安排为：

| 恢复进程 | 拉起前退避 | 失败后的动作 |
|---:|---:|---|
| 1 | 5 秒 | 进入第 2 次 |
| 2 | 15 秒 | 进入第 3 次 |
| 3 | 30 秒 | 进入第 4 次 |
| 4 | 60 秒 | 进入第 5 次 |
| 5 | 60 秒 | 暂停快速拉起，设备保持 OFF |

五个进程都未提交后，Sidecar 不退出、不再并发创建进程，而是在保持全部输出 OFF 的前提下按 2 分钟、5 分钟、15 分钟上限进行低频单实例探测。任一探测进程完成安全预检并提交正式恢复批次后，`RecoveryBatchCommitted` 及心跳中的提交代次会幂等清零失败计数和探测计数。

该策略满足用户要求的连续 5 次重试，同时避免网络/NI 设备长期不可用时无界 Process.Start 风暴，也避免一次快速熔断后永久无人监督。

### 3.6 数据收敛和故障取证

新 `EpbDiskWriter` 在创建本进程新周期之前，把数据库中所有前任进程遗留的 `status='running'` 改为 `aborted_on_startup`，原有 `end_time` 保留，没有 `end_time` 才填当前时间。重复执行不会再次修改已收敛记录。

自动接管必须终止旧进程时，Watchdog 在身份校验通过后先尝试最多 3 秒的 MiniDump，保存在 Watchdog 会话目录的 `dumps\{SessionId}` 下；只保留最近 3 个且总量不超过 256 MiB。转储超时或失败会记录事件，然后继续终止旧进程，避免诊断反向阻塞安全恢复。

## 4. 恢复成功的唯一判据

恢复过程新增三个显式里程碑：

```text
RecoveryCheckpointValidated
  -> SafetyPreflightPassed
  -> RecoveryBatchCommitted
```

- `RecoveryCheckpointValidated`：只证明某个合法副本已通过 Run/Session/配置/Nonce 等校验；
- `SafetyPreflightPassed`：只证明 StopAll、孤儿收敛和硬件安全预检通过；
- `RecoveryBatchCommitted`：证明目标通道已经以新的 RunEpoch 成功提交并启动，是唯一可以清零连续失败的事件。

提交代次同时存在于即时 IPC 消息和后续心跳中。即使提交瞬间 Pipe 消息丢失，Sidecar 也能从下一次心跳补收；重复消息通过单调代次幂等处理。

## 6. 运行时可观测性

现场验收和后续事故排查应优先检索下列事件：

| 事件/字段 | 含义 |
|---|---|
| `DAQ_FRESHNESS_SAFETY_CUTOFF` | 100 ms 安全关断已触发，但不代表 DAQ 任务一定需要重建 |
| `OutputsConfirmedOff=true` | 受影响输出 OFF 已获得权威确认 |
| `PowerOffUnconfirmed=true` | 仍缺少至少一个电源 OFF 确认，5 秒安全门有效 |
| `RecoveryHardDeadlineUtc` | Controller 对当前恢复事务负责到何时 |
| `RecoveryCheckpointValidated` | 已记录实际副本来源、SHA、Revision |
| `SafetyPreflightPassed` | 安全预检完成，但尚不能清零失败计数 |
| `RecoveryBatchCommitted` | 恢复真正成功，可清零连续失败 |
| `ConsecutiveStartupFailures` | 自上次批次提交后的连续未提交进程数 |
| `RelaunchGeneration` | 历史拉起单调代次，只用于审计，不参与连续失败清零 |
| `SafeIdleRecoveryBlocked` | 已完成 5 次快速尝试，转入低频单实例探测 |
| `MiniDumpRequested` / `MiniDump` | 自动终止前转储请求及结果 |
| `CheckpointReadFailed:<path|status|detail>` | 四份 checkpoint 均无法消费的精确分类 |

建议现场告警条件：

- `PowerOffUnconfirmed` 超过 5 秒：立即高优先级告警；
- 连续 2 个恢复进程未提交：运维预警，但 Sidecar 继续自动恢复；
- 连续 5 个恢复进程未提交：高优先级告警，设备保持 OFF，Sidecar 进入低频探测；
- 任意项目镜像写失败或 `CheckpointFailures` 目录生成：存储/权限告警；
- 出现 MiniDump：必须和对应 Watchdog Journal、checkpoint audit 一起封存。

| 丢失 `RecoveryBatchCommitted` IPC 消息 | 下一心跳的 commit generation 补收并清零计数 |
| 液压成员卡死/不再到达屏障 | StopAll 不等待正常 barrier；软件 owner 快速归零，物理输出和压力独立确认 |
| 恢复进程前 4 次退出、第 5 次成功 | 第 5 个进程仍能成功提交；计数清零；不中断无人值守任务 |
| 连续 5 个恢复进程均退出 | 转入 2/5/15 分钟低频单实例探测；输出持续 OFF；不得永久退出监督 |
| 旧进程强杀 | 留下 MiniDump、Watchdog Journal、checkpoint audit；数据库无 `running` 孤儿 |
| 72 小时组合故障注入 | 可恢复注入零人工介入、零永久停机、零重复周期提交、零输出安全违规 |
| 至少 7 天正式无人值守长稳 | 无不可解释中断；无 checkpoint 单点丢失；数据库无孤儿 `running`；资源无持续增长 |

只有上述硬件故障注入和长稳门禁全部通过后，候选包才能标记为无人值守正式版本。

## 9. 尚未证实但已与“永久停机”解耦的事项

事故中的约 0.9 秒 DAQ 回调空窗发生在应用消费之前。现有证据仍不足以在以下候选中唯一定位：NI-DAQmx 驱动、设备/总线、Windows DPC/ISR 或线程调度、设备时钟调整。

这项未知不再是发布软件恢复闭环的阻塞原因，因为本次已经保证短空窗快速安全 OFF、持续异常由单一 liveness owner 恢复、进程恢复有多副本授权和持续监督。它仍是降低故障发生率的 P1 诊断任务，现场长稳应同步采集：

- NI-DAQmx task 状态、buffer 可用量/overflow、回调批次和错误码；
- callback/enqueue/processed 三段单调时间戳；
- Windows ETW 的 DPC/ISR、CPU 调度及 USB/PXI 事件；
- GC pause、主线程和 DAQ 回调线程调度延迟；
- 设备与驱动版本、机箱/总线拓扑和电源管理状态。

在取得上述证据前，不应盲目调整 NI buffer、采样率或把 100 ms 安全门限调大。

## 10. 最终判定

针对 0817 事故中已经证实的永久中断链，代码修复已经闭环并通过 441/441 自动化回归：偶发 DAQ 空窗不会再因时限倒置、StopAll 屏障残留、checkpoint 单点丢失和错误累计熔断而直接结束无人值守监督；即使 5 个快速恢复进程连续失败，系统也会保持输出 OFF 并继续低频单实例探测。

当前状态可定义为：**软件修复完成，候选包具备进入目标台架故障注入和长稳验收的条件；在 72 小时注入及 7 天长稳完成前，不宣称正式发布验收完成。**
