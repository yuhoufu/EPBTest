# 联合安全反馈：液压范围覆盖审查

## 当前源码事实

`Controller/EpbManager.PhysicalSafetyFeedback.cs` 中 `ConfirmJointPhysicalSafetyAsync` 拒绝 null 液压数组和重复 ID，但不拒绝空数组，也没有在此处证明传入液压组覆盖所有受影响通道。采样名由传入数组生成；空数组时只有电流，没有压力项。

全局停止入口 `ConfirmJointPhysicalSafetyForStopAsync` 传入配置中 Enabled 的液压组，通道则包括启用通道和本次停止事务内通道。仅凭该局部代码，不能证明两个范围之间完整对应。

## 结论边界

这是尚未闭合的范围证明，不是已经复现的现场误恢复。需要核实禁用液压组的业务含义、配置加载约束、停止期间配置可变性，以及受影响通道是否曾使用未包含的液压组。不能未经核实就把所有无液压工况强制改成故障，也不能把只取得电流的证据表述为已确认电流和压力均安全。

## 下一步及验收要求

1. 从运行事务冻结的实际受影响范围及配置映射推导必须确认的液压组，而非在反馈阶段临时缩小范围。
2. 明确无液压工况是否被当前产品支持及其授权口径；支持时必须以显式工况证据表达，不以空数组隐含放行。
3. 对丢组、重复组、null 项、停用但仍可能受影响的组、换代/配置变更补生产路径反例，并保留正常受支持工况。
4. 以动作后的全范围新鲜压力和电流安全证据验证续测门禁；当前全量回归计数不能代替这些反例的覆盖证明。

本次只做源码审查，未修改运行逻辑或进行现场操作。整体“所有恢复条件均统一”仍未证明，不能据此晋级正式自动恢复包。

## 后续核实与修复

配置加载允许空液压列表；`HydraulicController.BuildAndHoldAsync` 对缺失或禁用组直接返回，不能仅凭空数组否定所有既有无液压运行路径。仓库默认配置包含启用的 1、2 两组，但这不等于现场配置证据。

已核实更具体的不一致：`ConfirmPressureSafeForStopCoreAsync` 对所有已配置液压组（未按 Enabled 筛选）执行 ForceRelease，随后联合反馈入口却再次按 Enabled 缩小范围。本轮将全局停止的联合反馈改为包含所有已配置组，与此前实际卸压范围一致。未新增对无液压配置的笼统拒绝，也未修改阈值或 I0050 状态发布。

这处源码修改尚待补回归及重新构建验证，不覆盖运行期间配置可变、事务范围冻结或所有恢复入口的映射闭包问题。此前 Debug/Release 回归结果不覆盖此后改动，当前不能据旧结果生成正式包。

## 普通设置入口互斥的核实

`Main_Frm.TsmSetting_Click` 会遍历 MDI 子窗口：存在 Text 为“实时监视”的窗口时直接提示并返回，不创建设置页；`FrmEpbMainMonitor.Designer.cs` 当前确实将该窗口 Text 定义为“实时监视”。设置页使用 `ShowDialog(this)` 模态打开。因此不能仅凭配置对象可写就断言正常设置 UI 可与实时监视并发修改配置。

实际保存事件 `BtnSaveTest_Click` 使用 `_busy` 防本页重复保存，然后写回 Basic、EPB 和液压参数；这个 `_busy` 不是控制层恢复事务锁。监视关闭路径有数据耐久性及后续资源收尾处理，但部分明确停止/压力证据不可用情形允许继续退出，不能把“窗口已关闭”直接等同于全部物理安全或旧异步任务已被证明终止。

本轮未增加未经证明必要的 UI 禁用或新全局锁。下一步需检查程序化配置写入以及关闭后仍存活的恢复/硬件任务，避免把标题检查当成全局配置不可变性证明；现有检查也没有证据表明设置能修改当前联合窗口已捕获的阈值局部数组。该结论缩小了待查范围，但不关闭所有事务范围一致性问题。
