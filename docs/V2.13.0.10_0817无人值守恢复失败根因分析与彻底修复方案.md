# V2.13.0.10（0817）无人值守恢复失败根因分析与彻底修复方案

> 分析对象：`D:\EPB_Data\10358-029_V2.13.0.10_0817_0056`  
> 软件版本：V2.13.0.10  
> 分析日期：2026-08-17  
> 时间口径：正文均为北京时间（UTC+8）；`IncidentSnapshots` 部分目录名中的时分秒采用 UTC。  
> 数据保护：本次只读分析封存数据，未修改数据库、日志、配置和试验结果。

## 1. 结论先行

当前 V2.13.0.10 **不满足无人值守连续运行要求**，应在完成本文 P0 修复和故障注入验收前暂停作为无人值守正式版本发布。

本次中断不是“DAQ 已永久损坏”，也不是“电脑资源耗尽”。日志能够闭合的真正故障链是：

1. Dev1 出现了约 0.9 秒的上游 DAQ 回调空窗；控制处理队列、落盘队列均为空，CPU、内存和磁盘没有耗尽。
2. 单周期控制在样本陈旧超过 100 ms 时立即安全关断，这是合理的安全动作；但它同时绕过配置中的三级存活策略，直接升级成整套 DAQ 恢复。
3. 内部 DAQ 恢复允许 10 秒首阶段、60 秒总时限；外部 Watchdog 却把语义过宽的 `PowerDisablePending` 当成未断能，在约 5 秒时开始抢占。内外恢复时限倒置。
4. 内部实际上已经完成 DAQ 重建，所有电源也已确认关闭；但 Watchdog 仍执行 `StopAll`。停止流程又等待正常液压屏障，15 秒液压超时与 15 秒 StopAll 硬时限相同，必然发生竞态。最终物理输出安全，但逻辑上残留 2 个 Timer、2 个 Runner、3 个 Lease，Watchdog 因而杀掉旧进程。
5. 新进程以 Watchdog 恢复身份启动时，持久化恢复检查点不存在或已非 `Armed`，于是主动上报 `RecoveryCheckpointRejected` 并退出。截图里的 `ProcessExitedUnexpectedly` 是后继进程退出后的二次表象，不是最初故障。
6. Watchdog 的 `RecoveryAttempt` 没有在之前一次成功恢复提交后清零；它把累计拉起次数当成“连续失败次数”。因此最终事故只发生了 2 次相同的检查点拒绝，却在计数到 3 时开路，并错误显示“连续 3 次恢复失败”。

因此，彻底修复不能只做“增加重试次数”“把 100 ms 调大”或“失败后再杀一次进程”。必须同时修复：

- 安全关断与可用性恢复的策略分层；
- Controller 与 Watchdog 的状态语义和时限所有权；
- 停止路径的强制资源撤权；
- 跨进程恢复检查点的持久化与交接协议；
- 连续失败计数和熔断策略；
- 中断周期的事务化收敛和取证能力。

### 2.4 现场 LocalAppData 补充取证

已只读检查用户补充的现场路径 `\\wj-epb\Users\mt\AppData\Local\MTTFTest`，结论如下：

1. 目录当前存在 `unattended-run-checkpoint.json`，但其内容已属于事故后 01:49 左右人工重新启动/重新运行产生的新授权：取证时为 `Armed=true`、`LastReason=FormalCycleCommitted`，RunId 和 WatchdogSessionId 均不是事故会话。它不能代表 00:55:31 的磁盘状态。
2. 该目录没有 checkpoint `.bak`、版本历史或 Arm/Disarm/Consume 事件流水；正常保存使用临时文件原子替换，但没有保留旧版本。现有 VSS 只有 2026-08-14 的快照，没有事故前后的 2026-08-17 副本，因此不能还原事故时 JSON。
3. `WatchdogControlV2\session-3d69919041d44463a4d45329858df6a9.revoked` 的内容为 `OperatorCanceledAutomaticRecoveryFromTransitionWindow`，创建时间是 00:57:41.427；两次 checkpoint 拒绝发生在 00:55:31.711 和 00:56:02.376。该 marker 是操作员随后停止自动恢复的结果，不是最初拒绝原因。
4. 两个拒绝均发生在全新进程中，进程内 `RevokedRuns` 静态集合不会继承旧进程状态。因此 [`TryConsumeWatchdogRecovery`](../MTTfTest/UnattendedRecovery.cs#L208-L227) 的首个失败分支只剩：`current == null` 或 `current.Armed == false`。
5. `LoadUnsafe` 把“不存在、共享/读取错误、JSON 反序列化错误”全部静默合并成 null，见 [`MTTfTest/UnattendedRecovery.cs`](../MTTfTest/UnattendedRecovery.cs#L1003-L1013)。所以现有日志中的“已撤权或没有可恢复检查点”无法继续区分磁盘文件不存在、不可读/损坏，还是文件存在但 `Armed=false`。
6. 当前版本源码没有删除正式 `CheckpointPath` 的正常调用；它通过 `File.Replace`/`File.Move` 覆盖保存。若事故时文件确实不存在，原因应在外部删除、I/O/共享异常或构建差异中查找，而不是假定某个已知 `File.Delete` 调用。

因此应把原结论从笼统的“未证实”修正为：**已排除 00:57 的 Watchdog revoke marker 和新进程内存撤权；已将失败严格缩小到事故时磁盘 checkpoint 非 Armed，或读取层返回 null。由于事故版本被覆盖且读取异常被吞掉，无法用现存证据唯一指认具体撤权调用点。**

V2.13.0.10 中可以找到 3 个 DAQ 触发快照：

|---|---|---|---|

| 2026-08-16 20:36:38.415 | Dev2 | `DaqCallbackStale` | 触发前 CallbackAge 150.99 ms，最近回调空窗 53.68 ms |
| 2026-08-17 00:54:48.509 | Dev1 | `DaqCallbackStale` | 触发前 CallbackAge 128.28 ms，最近回调空窗 892.17 ms |

前两个快照属于 20:36 附近的同一轮恢复过程。该轮 Watchdog 的第 1 次拉起最终成功：20:39 左右完成无人值守运行交接，之后连续运行约 4 小时 18 分钟。

所以截图里的“连续 3 次恢复失败”与日志不符。最终 00:54 事故中：

- `attempt=1` 是 20:36 那次已经成功的历史拉起；
- `attempt=2`（PID 4656）因检查点拒绝退出；
- `attempt=3`（PID 8672）因同一原因退出；
- Watchdog 用累计次数触发熔断，误报成连续 3 次失败。

这不是措辞问题，而是会导致少给一次有效恢复机会、并在无人值守时永久停机的状态机缺陷。

## 6. 根因树

### 6.1 触发层：偶发 DAQ 回调空窗

**确认事实：** Dev1 的新样本在应用回调入口之前中断约 0.9 秒。  
**未确认：** 是 NI 驱动、USB/PXI 链路、Windows DPC/ISR、设备时钟校正还是其他调度原因。

补查现场 Windows 事件和用户目录后，没有发现 20:36、23:54、00:54 三个相关窗口内的 NI Software、USB、WHEA、磁盘、NTFS 或驱动报错；`CrashDumps`、WER 队列/归档不存在，National Instruments 用户目录在事故窗口也没有新诊断文件。20:37 和 01:00 附近只有与性能计数器相关的 Perflib/PerfNet 错误，时间上出现在进程拉起/性能查询附近，且不能解释 DAQ 回调空窗，不作为根因。

“没有事件”只说明没有被现有日志捕获的显式硬件/驱动故障，不能排除瞬时 DPC/ISR、DAQmx buffer、总线调度或设备时钟问题；这些必须依靠预先开启的 ETW 和 DAQmx 指标取证。

这属于应诊断和降低概率的上游故障，但它不是无人值守永久中断的主根因。系统设计本应容忍短暂断流并在安全关断后恢复。

### 6.2 策略层：100 ms 安全门限被错误等同于 DAQ 任务故障

配置明确写着三级策略：100 ms Warn、1000 ms Suspect、2000 ms 且连续 3 次才局部恢复，见 [`MTTfTest/App.config`](../MTTfTest/App.config#L109-L113)。

但活动周期控制在 100 ms 直接返回 `DaqSampleStale>100ms`，见 [`Controller/Adaptive/EpbAdaptiveControl.cs`](../Controller/Adaptive/EpbAdaptiveControl.cs#L583)。之后 `EpbManager` 把它分类成 `DaqCallbackStale` 并立即进入整套 DAQ 自动恢复，见 [`Controller/EpbManager.cs`](../Controller/EpbManager.cs#L3268-L3357)。

正确语义应为：

- **100 ms：** 当前带电通道立即 OFF，终止本周期，保证安全；
- **是否重建设备：** 由独立的 DAQ 存活监督依据 1000/2000 ms、连续采样、任务错误码和回调是否自行恢复决定；
- **回调恢复：** 重新建立新鲜样本窗口、完成安全预检后继续后续周期，不默认重启进程。

不能简单把 100 ms 调大，因为这会牺牲安全关断速度；要拆开“安全动作门限”和“基础设施故障判定门限”。

### 6.3 协调层：Watchdog 时限倒置、`PowerDisablePending` 语义过宽

Controller 的 DAQ 恢复硬时限为 60 秒，断能阶段本身允许 5 秒，见 [`Controller/EpbManager.RecoveryCoordination.cs`](../Controller/EpbManager.RecoveryCoordination.cs#L141-L143)。实际 pipeline 首阶段又会等待 10 秒。

Watchdog 却在 `PowerDisablePending` 持续约 5 秒时接管。更关键的是，pending 判定把以下任一个条件都视为“断能未完成”：

- 断能任务尚未结束；
- `ExpectedOutputEnabled`；
- `TelemetryOutputEnabled`；
- `state.Active`。

见 [`Controller/EpbManager.BatchStart.cs`](../Controller/EpbManager.BatchStart.cs#L719-L725)。其中 `Active` 或预期重新使能只代表协调器正在处理，不等于硬件仍带电。这个错误语义使 Watchdog 在输出已经 OFF、内部恢复仍有进展时杀死 owner。

这是本次恢复由“本可局部收敛”升级成“必须杀进程”的直接原因。

### 6.4 停止层：正常液压屏障被错误复用于强制退出

StopAll 硬时限是 15000 ms，见 [`Controller/EpbManager.StopSafetyHardening.cs`](../Controller/EpbManager.StopSafetyHardening.cs#L12)。事故中液压屏障也恰好在 15000 ms 超时；StopAll 通过正常的 `AbortHydraulicLeaseForChannelAsync` 释放仍在运行的代次，见 [`Controller/EpbManager.cs`](../Controller/EpbManager.cs#L1889)。

正常周期屏障允许等待其他成员，但紧急停止不能再等待正常成员到齐。相同的 15 秒上限使两条路径必然在边界竞态，导致“输出已安全、内存 owner 未收敛”。

### 6.5 跨进程层：恢复授权只存在本机易失单点，且没有完整审计

恢复检查点只保存在 `%LocalAppData%\MTTFTest\unattended-run-checkpoint.json`，见 [`MTTfTest/UnattendedRecovery.cs`](../MTTfTest/UnattendedRecovery.cs#L83-L86)。新进程的恢复入口在 `TryConsumeWatchdogRecovery` 检查不到可用 `Armed` 状态时直接拒绝，见 [`MTTfTest/UnattendedRecovery.cs`](../MTTfTest/UnattendedRecovery.cs#L208-L227)。

现场 LocalAppData 已补查：当前 checkpoint 是 01:49 后人工运行写入的新状态，事故版本已被覆盖；没有 `.bak`、审计流水或可用的事故时 VSS 副本。00:57:41 的 Watchdog `.revoked` marker 晚于两次拒绝，不能解释 00:55:31 的首次失败。由于后继进程的内存撤权集合为空，可以严格确认它当时只可能遇到以下两类状态：

- checkpoint 存在，但 `Armed=false`；
- `LoadUnsafe` 因文件不存在、读取错误或 JSON 反序列化错误返回 null。

当前实现会吞掉 `LoadUnsafe` 的具体异常，并把这两类状态合并成同一句提示；同时每次写入直接替换旧文件而不留备份。因此不能从现存证据精确指认某个 Disarm/Clear 调用，也不能证明当时发生了物理文件删除。

这本身就是 P0 设计缺陷：一个无人值守系统不能让唯一恢复授权脱离项目封存、Watchdog 会话和事务审计。

### 6.6 熔断层：累计拉起次数被当作连续失败次数

Watchdog 每次拉起前递增 `_journal.RecoveryAttempt`，连接成功后没有在正式批次提交时复位；收到失败后又用 `RecoveryAttempt >= 3` 直接开路，见 [`MTTFTest.Watchdog/WatchdogHost.cs`](../MTTFTest.Watchdog/WatchdogHost.cs#L369-L380) 和 [`MTTFTest.Watchdog/WatchdogHost.cs`](../MTTFTest.Watchdog/WatchdogHost.cs#L812-L821)。

这使 20:36 已成功的历史恢复仍消耗最终事故的一次失败额度。

## 7. 为什么人工重启软件能恢复

人工普通启动能够恢复，正好反证了设备不是永久故障：

1. 新进程不继承旧进程里的 Timer、Runner、Lease、取消令牌和卡住的液压代次；
2. NI DAQ 回调在事故后已经恢复，重新建任务可以工作；
3. 普通人工启动不走 `--watchdog-recover` 的检查点消费门禁，操作者可以重新加载试验并启动；
4. 设备已被上一进程和 Watchdog 关断，启动时处于安全初态。

但人工重启只是绕过了“内存残留 + 恢复授权”两个软件问题，并没有修复它们。下次同类抖动仍会中断无人值守试验。

## 8. 从根上解决：目标状态机

建议把恢复协议明确拆成以下状态：

```text
Running
  -> SafetyCutoffRequested
  -> OutputsConfirmedOff
  -> LocalObservation
      -> CallbacksFresh -> Revalidate -> ResumeNextCycle
      -> DAQStillStale -> RebuildDaqTask -> Revalidate -> ResumeNextCycle
      -> NoProgress/HardDeadline -> HandoffSealed
  -> ForceQuiesce
  -> OldOwnerTerminated
  -> NewOwnerAttached
  -> CheckpointValidated
  -> SafetyPreflightPassed
  -> RecoveryBatchCommitted
  -> Running
```

任何阶段都必须满足：只有一个 owner；输出在恢复预检完成前保持 OFF；状态持久化先于不可逆动作；每个动作可重放且幂等。

## 9. 必须实施的修复

### P0-1：重新定义 Controller/Watchdog 契约和时限所有权

新增明确字段，禁止用 `state.Active` 推断带电：

- `OutputsConfirmedOff`：每个关联组的 OFF 命令 receipt 已完成，并由输出遥测或硬件读回确认；
- `PowerOffUnconfirmed`：仅在 OFF receipt 未完成、读回仍 ON、或读回不可得且安全确认超时才为真；
- `RecoveryProgressUtc`：内部恢复最近一次有效进展；
- `ControllerRecoveryHardDeadlineUtc`：Controller 对本轮恢复承诺的绝对截止时间；
- `RecoveryPhase`：Cutoff / Observe / Rebuild / Validate / Reenable / Commit；
- `HandoffReady`：Controller 已封存检查点并可让外部接管。

Watchdog 策略：

1. 真正的 `PowerOffUnconfirmed` 可保留 5 秒安全接管门限；
2. 一旦 `OutputsConfirmedOff=true`，不得因为 `Active`、ExpectedOn 或 re-enable 准备而触发 5 秒接管；
3. 内部恢复有进展时，Watchdog 等待 Controller 发布的硬时限；建议静态兜底为 60 秒 + 5 秒交接余量；
4. 同时设置 15 秒“无进展”门限，防止 Controller 虚假续租；
5. 只有 `PowerOffUnconfirmed`、无进展超时、Controller 硬时限到期或进程失联才接管。

### P0-2：为紧急停止提供独立的 ForceQuiesce 原语

新增类似 `ForceAbortRunGenerationAsync(runId, epoch, deadline)` 的专用路径，不能复用正常周期屏障：

- 原子提升 RunEpoch，旧 owner 的所有提交立即失效；
- 取消该代次所有 Timer、Runner、DAQ 恢复任务和液压/电源 Lease；
- 液压组将全部 pending 成员直接标记为 `AbortedBySafetyStop`，清除 scope、gate、generation；
- 并行发出 DO/AO OFF、压力释放和电源 OFF；
- 每个步骤幂等，重复执行不重新使能、不重复计数；
- 目标 2 秒内完成逻辑撤权，5 秒内给出最终安全 receipt；
- 若仍不能收敛，持久化残留清单后允许 Watchdog 杀进程，不能在退出路径再等待 15 秒普通屏障。

StopAll 的硬时限必须大于其内部所有子步骤的最坏上限，且测试中禁止“子超时 = 外层硬时限”。

### P0-3：持久化、可审计、可交接的恢复检查点

恢复授权至少三副本：

1. 项目目录内：`Recovery\unattended-run-checkpoint.json`；
2. `%LocalAppData%` 原位置的原子主/备份文件；
3. Watchdog journal 内的只读镜像和一次性交接 nonce。

每次 Arm、Disarm、SealHandoff、Consume、Commit 都要以结构化事件记录：

- RunId、SessionId、RunEpoch、配置哈希、通道和目标次数；
- 上一状态、新状态、原因码、操作者/系统来源；
- checkpoint revision、nonce、文件路径、SHA-256；
- 最后已提交周期、各通道剩余次数；
- 时间戳和进程身份。

读取接口不能再返回模糊的 null。应返回可审计的判定枚举，例如 `Missing`、`IoError`、`JsonInvalid`、`SchemaInvalid`、`Unarmed`、`SessionMismatch`、`Valid`，并记录 Win32/HResult、文件长度、最后写入时间和原始文件 SHA-256。新进程第一次消费失败时，必须先把原始 checkpoint 和异常详情复制到本 Watchdog session 的事故目录，再显示或重试，防止随后人工启动覆盖唯一证据。

写入流程必须是 `temp -> flush -> fsync -> atomic replace`，保留上一版 `.bak`，并按 SessionId/Revision 追加不可覆盖的审计记录。交接协议必须先写 `HandoffPending` 和 nonce，再停止旧 owner；系统故障接管不得执行 Disarm。只有以下事件可撤权：

- 明确的人工停止；
- 全部目标已完成；
- 经分类确认的不可恢复硬件故障，并已记录证据。

新进程按 `主副本 -> 备份 -> Watchdog 镜像` 验证。三者都不可用时，只能进入**安全待机恢复服务**并持续告警，不能退出造成 `ProcessExitedUnexpectedly` 循环，更不能自动使能。只有校验通过的 nonce 才允许完成预检并恢复运行。

### P0-4：修复恢复计数和熔断

将现有字段拆成：

- `RelaunchGeneration`：只增不减，用于审计；
- `ConsecutiveStartupFailures`：只统计上一次 `RecoveryBatchCommitted` 之后的失败；
- `FailureFingerprintCount`：同一根因指纹的连续失败数；
- `LastCommittedRunId/Revision`：成功提交证据。

只有收到新进程的 `RecoveryBatchCommitted` 才把连续失败清零；仅 Pipe Attached 不算成功。界面必须分别显示“本会话累计拉起”和“自上次提交后的连续失败”。

即使同一纯软件失败达到 3 次，也不要永久停止监督：保持输出 OFF，进入 2/5/15 分钟上限退避的安全探测，并远程告警。真正的不可恢复硬件故障才可锁存到人工确认。

### P1-1：拆开 100 ms 安全关断和 DAQ 基础设施恢复

保留带电通道 100 ms 立即 OFF，但将事件类型拆分：

- `DaqFreshnessSafetyCutoff`：只终止当前周期并关断；
- `DaqLivenessWarn/Suspect/Trip`：由独立监督器依据 100/1000/2000 ms 和连续 3 次判定；
- `DaqTaskError`：NI 明确错误码可直接进入局部重建；
- `ControlConsumerStall`：回调正常但控制消费陈旧，重启消费管道而不是 DAQ 任务；
- `PersistenceStall`：单独处置，不能冒充 DAQ 断流。

回调在 Trip 前自行恢复时：要求连续 N 个新鲜批次、时钟残差收敛、输出保持 OFF，随后从下一周期继续，不重做已提交周期。

### P1-2：启动时事务化修复孤儿周期

所有启动路径（人工启动、Watchdog 恢复、同进程批次回收）必须复用同一事务：

1. checkpoint 当前 WAL；
2. 找出旧 PID/RunEpoch 下的 `running`、有结束时间但未终态、或开始后无 owner 的周期；
3. 幂等改为 `AbortedBySoftwareRecovery`，写入原状态、事故 SessionId 和原因；
4. 重新计算每通道正式完成数和剩余数；
5. 唯一约束保证已提交周期不会重复计数；
6. 再生成恢复计划并 Arm 新 owner。

本次 EPB9 cycle 60697、EPB10 cycle 61317 应按该规则处理；建议只在封存副本或正式迁移工具中执行，不直接修改原封存。

### P1-3：补齐底层诊断，降低 DAQ 空窗发生率

下一版本应同步记录：

- NI-DAQmx task state、error/warning code、buffer available samples、overflow/underflow；
- 回调入口 QPC、线程 ID、线程优先级、GC pause、进程 working set；
- Windows ETW 的 DPC/ISR、CPU 调度、磁盘和 USB/PXI 事件；
- 系统电源策略、USB selective suspend、NIC/总线节能状态；
- 设备序列号、槽位、驱动/NI-DAQmx 版本和拓扑。

Windows System/Application 日志和 NI Error Reporting 只能作为辅助证据，不能代替上述高频时序指标。本次现场在事故窗口没有相关 NI/硬件事件，恰好说明仅依赖事件查看器无法完成最底层归因。

建议把 DAQ 采集与 UI/落盘解耦到固定优先级线程或独立采集进程，使用预分配无锁环形缓冲；UI、日志格式化和磁盘写入不得占用 DAQ 回调线程。是否需要调整 NI buffer/回调批大小，应在 ETW 和 DAQmx 指标证实后决定，不能凭本次日志盲改。

### P1-4：构建与事故证据必须可复现

正式包启动时校验并封存：

- Git commit、dirty 状态、Package Manifest；
- EXE/关键 DLL 哈希、.NET 和 NI 驱动版本；
- 生效配置快照和哈希；
- checkpoint 主/备份、Watchdog journal；
- 若由 Watchdog 主动杀进程，杀前生成 hang dump 和线程栈，而不是只等待崩溃 dump。

本次最终事故没有对应崩溃 dump，与“旧进程由 Watchdog 主动终止、后继进程因门禁主动退出”的证据一致。19:56 的 dump 属于更早的会话，不能用于解释 00:54 事故。

| 用例 | 注入 | 通过标准 |
|---|---|---|
| 短回调空窗 | Dev1 暂停 120/300/900 ms | 带电通道及时 OFF；只中止当前周期；回调恢复后本进程继续；不重启进程 |

| 进程被杀 | 正式运行中强杀 owner | 新进程验证 nonce 和 checkpoint，安全预检后恢复；无重复计数 |
| 历史成功后再故障 | 第一次恢复成功，数小时后制造新故障 | 连续失败从 0 开始；界面不显示 attempt 2/3 的假连续值 |

| 数据中断 | 写库中途杀进程 | `quick_check=ok`；孤儿周期转为 Aborted；完成数/剩余数准确 |
| UI/磁盘压力 | UI 卡顿、日志慢盘 | DAQ 回调线程不被阻塞；分类为正确故障域 |
| 多设备同时抖动 | Dev1/Dev2 同时断流 | 一个去重的基础设施恢复事务；不创建并发恢复 owner |
| 长稳 | 72 小时注入 + 7 天正式运行 | 所有可恢复注入零人工介入、零永久停机、零重复周期提交 |

发布门槛：

- 任意时刻最多一个有权使能输出的 owner；
- 输出未完成安全预检绝不使能；
- 可恢复故障不导致无人值守永久停机；
- StopAll 后 Timer/Runner/Lease 全为 0；
- 数据库没有悬挂 `running` 周期；
- “连续失败”由提交事件复位且显示真实；
- 事故包足以复现构建并解释每次 Arm/Disarm/Handoff。

## 13. 不应采用的“伪修复”

- 只把 100 ms 调大：降低安全性，且仍存在状态机和交接缺陷；
- 只把恢复次数从 3 改成更多：会重复相同的检查点拒绝；
- 只延长 StopAll：正常屏障仍可能永不收敛；
- 每次都重启 NI 服务或整机：没有永久设备故障证据，且会扩大中断；
- 自动点击 UI 或循环杀/拉进程：没有可靠 checkpoint 时可能丢进度或错误使能；
- 把 `ProcessExitedUnexpectedly` 当根因：它是检查点拒绝后的结果；
- 直接把两条 `running` 改成 completed：会污染寿命计数。

## 14. 修复完成前的临时运行建议

1. 不把 V2.13.0.10 作为完全无人值守版本；安排远程告警和人员接管；
2. 保留当前快速 OFF 策略，不通过放宽门限换取表面稳定；
3. 每次异常完整封存项目目录、`%LocalAppData%\MTTFTest` checkpoint、Watchdog 会话、Windows 事件和 NI 诊断；
4. 人工重启前确认所有输出 OFF，并以启动事务收敛孤儿周期；
5. 若先做热修，最小集合也必须同时包含：pending 语义/时限、ForceQuiesce、checkpoint 交接、连续失败复位。缺少任意一项都不能宣称彻底解决。

## 15. 最终判定

本次事故的底层触发是短暂 DAQ 回调空窗；**无人值守中断的根本原因是恢复架构内部的契约、时限、资源撤权和跨进程状态不一致**。人工重启之所以有效，是因为它清空了内存残留并绕过了 Watchdog 恢复门禁，而不是修好了硬件。

按本文 P0～P1 方案实施后，系统应做到：短空窗只安全终止当前周期，持续断流优先局部重建，只有真正无进展才进行有检查点的进程交接；即使检查点异常也保持安全监督和告警，不再以进程退出和熔断结束无人值守试验。
