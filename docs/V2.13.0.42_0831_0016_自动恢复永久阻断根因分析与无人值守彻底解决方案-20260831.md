# V2.13.0.42 自动恢复永久阻断根因分析与无人值守彻底解决方案

- 版本：`V2.13.0.42`
- 项目：`10243-028`
- 封盘数据：`D:\EPB_Data\Backups\10243-028_V2.13.0.42_I0006_0831_0016`
- 事故日期：`2026-08-31`
- 文档日期：`2026-08-31`
- 分析性质：根因分析与整改设计，**本文没有实施代码修改**

## 1. 结论先行

| 项目 | 结论 |
| --- | --- |
| 问题定性 | **确定的软件缺陷**，不是卡钳、NI DAQ、磁盘或主机资源耗尽自然导致“重试两次仍失败”。 |
| 最终直接根因 | 独立安全工作进程从 `Program.Main` 的特殊入口直接运行，不创建 `Main_Frm`；但压力确认路径仍从 `ClsGlobal` 读取只有 `Main_Frm` 才加载的 DAQ 参数。新进程中的 `SamplesPerChannel` 保持默认值 `0`，因此在 `MedianStreamCausal(maximumSamplesPerBatch: 0)` 构造时必然抛出 `ArgumentOutOfRangeException`。 |
| 是否偶发 | **不是偶发。** 只要真实进入“旧主进程退出后，由独立工作进程重新断能并确认压力”的路径，当前实现就会以相同方式失败。平时没有暴露，只是因为该分支很少真正执行。 |
| 为何显示 `UnhandledSoftwareStartup, Count=2` | 现场没有发生两次主程序启动失败，恢复主程序实际上一次也没有被放行。计数在批准恢复许可和旧进程退出阶段已经变为 2；同一许可又被“自动接管”和“应用退出监督”两个流程同时观察，随后分别得到安全工作进程失败和墓碑/许可不匹配，统一被错误显示为主程序启动失败。 |
| 前置触发 | 00:04:30.988 检测到 Windows 墙钟相对单调时钟向前跳变约 `1142.354 ms`。首次 DAQ 恢复成功；约 30 秒后两卡时钟模型又同步判为无效，触发第二轮整组断能、DAQ 重建和机械重入。 |
| 接管原因 | 第二轮恢复重入期间，DAQ 回调出现约 `895~897 ms` 空窗，EPB4/5 启动定位拿到陈旧电流；同时 Watchdog 命名管道多次写入超时，Sidecar 以 `PowerOffUnconfirmedTimeout` 接管。 |
| 当时硬件/数据状态 | 主进程退出回执记录 `MotorsOff=True`、`PowerOff=True`、`PressureSafe=True`、`PersistenceDrained=True`、`DataContinuityVerified=True`。没有发现已接收数据前缀丢失证据。独立安全工作进程没有形成最终完整安全回执，因此 Watchdog 按 fail-closed 阻止重启是安全的。 |
| 是否能靠调大重试次数解决 | **不能。** 这是确定性初始化缺陷，重启 8 次或无限次都会在相同位置失败；盲目重试只会反复占用硬件、污染日志并增加状态竞争。 |
| 完全解决方向 | 需要同时完成三组 P0：①建立不依赖 UI/全局状态的独立安全代理；②把安全代理、主程序重启和证据校验拆成单一所有者、独立计数的耐久状态机；③把墙钟映射故障与真实 DAQ 控制故障分离，避免时间校正放大为整组机械重启。只修异常行不构成完整闭环。 |

**最简短的答案：V2.13.0.42 在最关键的独立安全接管分支中依赖了主窗体初始化的全局 DAQ 参数，导致安全工作进程必然以 `SamplesPerChannel=0` 崩溃；随后恢复协议又把同一接管事务误计为两次主程序启动失败并永久熔断。**

## 4. 完整因果链

```text
Windows 墙钟前跳约 1.142 s
        ↓
程序把 UTC 映射异常直接升级为两卡整组断能、DAQ 重建和机械重入
        ↓
第一轮恢复成功，但新时钟模型在约 30 s 后同步判 Invalid
        ↓
第二轮恢复仅验证约 356 ms 即进入电源/机械重入
        ↓
DAQ 回调约 0.9 s 空窗 + Watchdog 管道写超时
        ↓
启动定位拿到陈旧电流，Sidecar 以 PowerOffUnconfirmedTimeout 接管
        ↓
主进程安全停机并退出，独立安全工作进程启动
        ↓
工作进程未创建 Main_Frm → ClsGlobal.SamplesPerChannel 仍为 0
        ↓
压力确认构造完整 TwoDeviceAiAcquirer
        ↓
MedianStreamCausal(maximumSamplesPerBatch: 0) 必然抛异常
        ↓
安全前置条件未闭环，恢复主程序不得启动
        ↓
同一许可被两套观察流程处理并错误计数/分类
        ↓
UnhandledSoftwareStartup, Count=2，进入持久永久阻断
```

链条中真正造成“永远不能自恢复”的点是安全工作进程的确定性初始化缺陷；墙钟跳变和第二轮恢复负责把程序带到这条平时很少执行的分支。

## 5. 源码级根因

### 5.1 P0 根因一：独立工作进程依赖主窗体初始化

安全进程入口位于 `MTTfTest/Program.cs:40-52`：

1. 命令行匹配 `--watchdog-safety-shutdown`；
2. 立即调用 `WatchdogSafetyShutdownWorker.Run(...)`；
3. 随后 `return`；
4. 不会执行 `new Main_Frm(...)`。

但 DAQ 全局参数只在 `MTTfTest/Main_Frm.cs:264-265` 加载：

```csharp
ClsGlobal.DaqFrequency = double.Parse(ConfigOperation.SetOneItem("DaqFrequency"));
ClsGlobal.SamplesPerChannel = int.Parse(ConfigOperation.SetOneItem("SamplesPerChannel"));
```

`MTTfTest/ClsGlobe.cs:133-134` 的进程初始值却是：

```csharp
DaqFrequency = 0.0;
SamplesPerChannel = 0;
```

因此，全新的安全工作进程一定保留 `0.0/0`。这不是线程可见性或偶发配置读取失败，而是入口结构决定的必现结果。

### 5.2 P0 根因二：压力安全确认复用了整套校正/生产 DAQ 对象

安全工作进程在完成 DO/AO/程控电源断能动作后，于 `MTTfTest/WatchdogSafetyShutdownWorker.cs:95,131-168` 调用 `ConfirmPressureSafe`。

该方法创建 `PressureCalibrationHardware`；后者在 `MTTfTest/PressureCalibrationHardware.cs:43-48` 创建完整的 `TwoDeviceAiAcquirer`，并传入：

```csharp
ClsGlobal.DaqFrequency,
ClsGlobal.SamplesPerChannel
```

`IO.NI/TwoDeviceAiAcquirer.cs:1741-1752` 没有在边界处拒绝无效采样参数，而是在 `1848-1852` 才把 `_samplesPerChannel` 传给两个中值流滤波器。最终 `DataOperation/ClsDataFilter.cs:205-206` 对 `maximumSamplesPerBatch <= 0` 抛出现场完全一致的异常。

压力安全代理只需要：

- 再次确认 DO 全关；
- AO 归零；
- 程控电源关闭；
- 读取启用的压力通道并判断低于安全阈值且稳定保持。

它不需要生产运行中的双卡完整通道、控制滤波、Raw 发布、后台持久化、UI 发布和峰值证据链。复用完整采集器使最小安全路径继承了大量不必要的配置和生命周期依赖。

### 5.3 P0 根因三：安全配置快照缺少运行时 DAQ 参数

现场 `config-snapshot-manifest.json` 只包含：

- `AIConfig.xml`
- `AlarmConfig.xml`
- `AOConfig.xml`
- `DOConfig.xml`
- `PowerSupplyConfig.xml`
- `TestConfig.xml`
- `UiConfig.xml`

实际 `DaqFrequency=2000` 和 `SamplesPerChannel=20` 位于 `MTTfTest.exe.config` 的 appSettings；它既没有进入安全快照，也没有作为显式参数传给工作进程。快照哈希完整只能证明已复制的 XML 没被篡改，不能证明安全代理拥有运行所需的全部配置。

### 5.4 P0 根因四：同一恢复许可存在两个完成所有者

Sidecar 事件中，同一个 Permit Generation=1 出现两条旧进程退出证明：

- `Source=AutomaticTakeover`
- `Source=RelaunchAfterExitBegin`

源码也存在两条并行路径：

1. 自动接管事务调用 `RelaunchAfterProvenExitAndSafetyAsync`；
2. 应用退出监督完成后，`CompleteApplicationExitSupervision` 又调用 `BeginRelaunchAfterExit`。

两条路径随后都等待同一安全交接，并分别产生：

- `Outcome=Failed, SafetyWorkerExecutionFailed`
- `Outcome=MissingOrCorrupt, ClosingTombstoneMissingCorruptOrPermitMismatch`

这说明恢复协议没有把 `(SessionId, PermitGeneration, HandoffId)` 固化为唯一所有者事务。安全工作进程只启动了一次，但结果被两套监督流程消费。

### 5.5 P0 根因五：失败域和计数语义错误

`Watchdog.Protocol/WatchdogPolicy.cs:589-642` 会把未识别的软件错误归为 `UnhandledSoftwareStartup`，预算为 2；`Evaluate` 又规定同指纹、同稳定点的第二次失败立即进入 SafeIdle。

本次却有三个完全不同的失败域：

1. 安全代理执行失败；
2. 安全交接墓碑/许可一致性失败；
3. 恢复主程序启动失败。

现场只发生了前两类，第三类没有发生。耐久记录同时证明：

- `RelaunchProcessId=0`
- `LaunchExecutablePath=null`
- `LaunchAuthorityRevision=0`
- `RecoveryCommitGeneration=0`

因此 UI 的“恢复失败两次/主程序不会再启动”把“前置条件没有通过”错误呈现成“主程序启动两次失败”。增加总预算不会修复该语义错误。

### 5.6 P1 放大因素一：墙钟映射异常被升级为机械恢复

`IO.NI/WallClockStepDetector.cs:13-16` 的注释明确写着 DateTime 只用于诊断，控制和截止时间继续使用单调时钟；但 `TwoDeviceAiAcquirer.cs:3229-3247` 检测到墙钟跳变后，会发布 `DaqWallClockStep` 故障并丢弃批次。

`Controller/EpbManager.cs:5788-5821` 又明确要求 `DaqWallClockStep` 和 `DaqClockModelInvalid` 强制重建 DAQ。最终，一个 UTC 映射问题被放大为：整组暂停、断电、NI Task 重建、电源重新使能和机械启动定位。

本次墙钟跳变前后没有资源耗尽或队列堆积证据；因此“UTC 映射不连续”不应直接等价于“控制数据已失效/硬件必须重启”。

### 5.7 P1 放大因素二：时钟模型无效原因没有被完整记录

第二轮错误日志只记录最终：

- Dev1：`RateHz=2000.100005, SkewPpm=0.000, ResidualMs=-17.719`
- Dev2：`RateHz=2000.000000, SkewPpm=0.000, ResidualMs=-15.738`

当前 residual 硬阈值默认至少为 100 ms，因此这两次 Invalid 不是日志中最终 residual 数值直接越界造成。源码还有候选频率越界、拟合分母/分子无效、候选值非有限数等分支，但日志没有输出 `InvalidReason`、候选频率、候选 skew 和连续确认次数。

可以确定“两卡在第一轮重建后约 30 秒同步进入模型无效”，但不能从现有证据进一步区分是哪一种拟合无效分支。这是必须补齐的可观测性缺口。

### 5.8 P1 放大因素三：重入稳定观察窗口过短

第二轮 Dev1 从故障到：

- 首批新鲜数据：246 ms；
- 压力资格与持久化边界通过：355 ms；
- 进入 `Validating`：356 ms。

随后即进入 `PowerEnableThenMechanicalRelease`。约 5 秒后出现近 0.9 秒回调空窗并导致启动定位失败。恢复重入前没有同时要求：

- DAQ 回调持续稳定一段时间；
- Watchdog 管道健康；
- 当前没有 pending takeover；
- 时间模型/时间代次不再升级；
- 两卡恢复由一个批次级协调器统一提交。

### 5.9 P1 放大因素四：阻断后日志风暴

`ObserveApplicationExitIntent` 每次轮询到许可身份不匹配都会记录 `TakeoverExitPermitIdentityMismatch`。现场在约 5 分 20 秒内写入 1203 条相同事件。阻断状态已经耐久化后仍高频轮询，不会带来新决策，只会扩大磁盘写入和排障噪声。

### 5.10 发布可追溯性问题

`runtime-build-identity.json` 记录：

- `releasePackageVerified=false`
- `releasePackageCode=PackageManifestMissing`
- `gitCommit=unknown`
- `gitDirty=unknown`

这不是本次异常的直接根因，但安全接管属于必须在正式包中验证的 P0 功能。现场包来自 `D:\debug\...` 且缺少包清单，意味着发布门禁没有阻止一个从未通过真实独立进程测试的安全分支进入现场。

## 6. 已排除的方向

### 6.1 不是主机资源耗尽

00:05:07~00:05:17 的主机指标大致为：

- 进程 CPU 约 1%~11%；
- 系统 CPU 约 4%~15%；
- Working Set 约 218~224 MiB；
- 可用内存约 12 GiB；
- 磁盘队列 0；
- DAQ 控制、后台和 Raw 队列深度为 0。

没有 CPU、内存、磁盘或采集队列耗尽证据。

### 6.2 不是“安全工作进程重试次数太少”

该工作进程只执行了一次，但即使立即再执行也仍会从 `0/0` 全局参数开始并在相同构造器失败。只调大重试和熔断阈值属于无效修复。

### 6.3 不是两次恢复主程序启动失败

没有 `RecoveryProcessLaunched`，没有恢复进程 PID，也没有启动授权提交。Count=2 是许可/失败记账，不是两次进程启动事实。

### 6.4 没有证据表明已接收数据丢失

`application-exit.json` 给出 `PersistenceDrained=True` 和 `DataContinuityVerified=True`；恢复检查点仍为 `Armed=True, RestartPending=True`，保留正式圈余量和 RunId。可以判定本次已接收前缀已收口，但在修复版恢复前仍应按检查点和 SQLite 最终边界执行一次数据一致性复核。

## 7. “完全解决”的正确目标

无人值守不等于对所有故障无限重启。必须区分两类结果：

| 故障类别 | 无人值守目标行为 |
| --- | --- |
| 可恢复的软件/传输/时间映射故障 | 自动隔离故障、保持输出安全、恢复服务、校验数据边界并继续试验，不需要现场操作员。 |
| 无法证明物理安全的真实硬件故障，例如压力传感器和备用确认手段均不可用 | 保持 DO OFF、AO=0、程控电源 OFF；停止拉起可能重新上电的主程序；周期性低频复核并通过独立通道远程告警。不能为了“继续运行”绕过安全证明。 |

因此，本方案对本次软件缺陷的完成标准是：**所有可恢复的软件故障不再落入永久阻断；真正无法证明安全时，系统自行保持断能并告警，而不是静默卡在本机弹窗等待人处理。**

## 8. 必须实施的完整解决方案

### 8.1 P0-A：建立独立、最小、无 UI 依赖的安全代理

建议新增独立 x86 进程 `MTTFTest.SafetyAgent.exe`，不要继续把主 WinForms EXE 当作安全工作进程。安全代理只能依赖以下最小接口：

```text
IDigitalSafetyOutput   -> 全部 DO 建立 OFF 基线
IAnalogSafetyOutput    -> 全部 AO 归零
IPowerSafetyController -> 所有相关电源确认 OFF
ISafetyPressureProbe   -> 只读启用的压力通道并验证稳定低压
ISafetyReceiptStore    -> 分阶段耐久回执
```

禁止依赖：

- `Main_Frm`、任何 WinForms 控件或 UI Load 事件；
- `ClsGlobal`；
- 生产运行的 `TwoDeviceAiAcquirer`；
- Raw/SQLite 持久化发布器；
- 完整 EPB 控制器、峰值跟踪器和后台 UI 发布线程。

安全压力探针只创建需要的 NI AI 压力通道，使用构造参数中的显式采样率和批大小。其截止时间、稳定保持时间和重试间隔全部使用 `Stopwatch` 单调时钟，UTC 只写入审计字段。

### 8.2 P0-B：安全运行参数必须显式、不可变、可验证

新增 schema v2 的 `safety-runtime.json`，至少包含：

```json
{
  "sampleRateHz": 2000,
  "samplesPerChannel": 20,
  "pressureChannels": ["Pressure_1", "Pressure_2"],
  "releaseSafePressureBar": [5.0, 5.0],
  "pressureSampleMaxAgeMs": 250,
  "releaseStableMs": 100,
  "releaseTimeoutMs": 10000
}
```

要求：

1. 由主进程在建立交接前从已验证的有效配置生成，而不是从可变全局变量反推。
2. 纳入 `config-snapshot-manifest.json` 并绑定 HandoffId、Session、PermitGeneration、EXE SHA-256 和文件 SHA-256。
3. 安全代理启动后先完整校验，再打开任何硬件会话。
4. 边界校验至少包含 `sampleRateHz > 0`、`samplesPerChannel >= 1`、批周期处于允许范围、压力通道唯一且已启用、阈值为有限数。
5. `TwoDeviceAiAcquirer` 自身也必须在构造器第一行校验采样率和批大小，抛出领域错误 `DaqRuntimeConfigInvalid`，不能把无效值拖到滤波器才暴露。

紧急热修可先在 `Program.Main` 的安全分支前显式读取并验证 appSettings，再通过构造参数传递；但这只是阻止当前异常的最低限度补丁，**不能替代独立最小安全代理和快照 v2**。

### 8.3 P0-C：安全回执必须分阶段耐久化

当前工作进程只在全部成功后一次性写 Completed，异常时无法区分已经完成了哪些安全动作。改为每个不可逆阶段写穿：

1. `WorkerStarted`
2. `DoOffConfirmed`
3. `AoZeroConfirmed`
4. `PowerOffConfirmed`
5. `PressureSafeConfirmed`
6. `Completed`

每阶段包含：

- Session/Handoff/Permit 精确身份；
- 进程 PID 和启动时间；
- 单调耗时与 UTC 审计时间；
- 使用的配置清单哈希；
- 硬件通道及确认结果；
- Revision 和前一阶段哈希。

这样即使压力探针失败，也能明确证明“输出已断能，但压力尚未独立验证”，Sidecar 可以在不重新上电的前提下只重试压力探针。

### 8.4 P0-D：每个恢复许可只能有一个耐久协调器

以 `(SessionId, PermitGeneration, PermitId)` 为幂等键建立唯一 `RecoveryReplacementTransaction`。状态建议为：

```text
Approved
  → OldProcessExitProven
  → SafetyAgentRunning
  → SafetyCompleted
  → MainLaunchIntent
  → MainStarted
  → Attached
  → CheckpointCommitted
```

规则：

1. 自动接管和应用退出监督只向同一事务提交观察结果，不能各自启动 relaunch loop。
2. 一个状态只能由 CAS/耐久事务向前推进；重复事件返回 `AlreadyApplied`，不增加失败计数。
3. `SafetyWorkerExecutionFailed` 后不得再次把同一事实转换为 `MissingOrCorrupt` 并重复阻断。
4. 墓碑、application-exit receipt、安全回执和 relaunch permit 的身份更新在同一临界事务内完成，或通过明确的两阶段提交恢复。
5. `TakeoverExitPermitIdentityMismatch` 只在状态或身份首次变化时记录；持续不变最多每 30 秒汇总一次。进入 CircuitOpen 后停止无意义的高频许可轮询。

### 8.5 P0-E：拆分失败域、预算和 UI 文案

至少拆成以下计数器：

| 失败域 | 示例码 | 是否消耗主程序启动预算 |
| --- | --- | --- |
| SafetyAgent | `SafetyAgentConfigInvalid`、`SafetyPressureProbeFailed`、`SafetyAgentProcessCrash` | 否 |
| EvidenceBinding | `ClosingTombstonePermitMismatch`、`SafetyReceiptHashMismatch` | 否 |
| MainLaunch | `MainProcessStartFailed`、`RecoveryAttachTimeout`、`CheckpointCommitFailed` | 是 |
| HardwareUnavailable | `PressureSensorUnavailable`、`DaqDeviceUnavailable` | 否；保持安全并告警 |

对应策略：

- 确定性配置错误：发布/启动预检必须提前拦截；现场遇到时保持断能并发送 P0 告警，不循环启动主程序。
- 安全代理瞬态进程/IO 错误：在输出保持 OFF 的条件下按 1、5、15、30 秒退避重试，成功后继续原 Permit；次数不计入 MainLaunch。
- 主程序启动错误：只有真正执行过 `Process.Start` 且取得/未取得精确 PID 结果后才计数。
- UI 分别显示“安全代理失败”“证据一致性失败”“主程序启动失败”，不能再统一显示 `UnhandledSoftwareStartup`。

### 8.6 P0-F：分离单调控制时间轴与 UTC 展示时间轴

建议把 DAQ 时间拆为：

1. **控制/排序时间轴**：`Stopwatch` + 样本序号，严格单调，用于新鲜度、控制截止、圈边界顺序和恢复期限。
2. **UTC 映射时间轴**：`EpochId + AnchorUtc + AnchorMonotonic + SampleIndex`，用于日志、导出和跨系统对时。

检测到墙钟跳变时：

- 写入 `WallClockEpochChanged` 事件；
- 关闭旧 UTC epoch，创建新 epoch；
- 最多隔离映射不确定的一个批次；
- 不改变控制样本序号，不重建健康 NI Task，不执行机械重入；
- 只有真实回调年龄、控制序号或硬件读任务同时失败时，才升级为 DAQ 硬恢复。

必须修改现有“`DaqWallClockStep` 一律 `RequiresDaqTaskRecreate=true`”策略。墙钟事件可以触发时间映射修复，但不能单独触发整组电源和机械动作。

### 8.7 P0-G：真实 DAQ 恢复的重入门槛

当确实需要重建 NI Task 时，在允许 `PowerEnableThenMechanicalRelease` 前同时满足：

- 控制回调在单调时钟上持续新鲜，且无新的 gap/stale 事件；
- 两卡的恢复批次身份一致并由一个批次级协调器提交；
- Watchdog 管道已连续健康，最近心跳和 Stop/PowerOff ack 均在期限内；
- 没有 pending takeover 或退出许可；
- 持久化截止已闭合；
- 电机、电源、压力的 OFF 证据仍有效。

初始建议用 5 秒连续稳定窗口做现场标定起点，而不是当前约 356 ms；最终数值应由故障注入和现场 NI 实测确定。恢复期间主进程要发布单调的 `RecoveryLease/ProgressStage`，Sidecar 识别“安全恢复正在推进”，避免把耗时但有进展的操作误判为 `PowerOffUnconfirmedTimeout`。

### 8.8 P1：补齐诊断与外部无人值守告警

时钟模型日志新增：

- `InvalidReason`
- `CandidateRateHz`
- `CandidateSkewPpm`
- `EstimatorWindowSec`
- `OutOfRangeConfirmations`
- `ResidualConfirmations`
- `EpochId`

Windows 侧诊断包新增导出：

- System 日志中 W32Time/Kernel-General 时间变化事件；
- `Microsoft-Windows-Time-Service/Operational`；
- 当前时间服务配置和最近同步源。

Sidecar 新增独立 `IUnattendedAlarmSink`。至少具备不依赖主 WinForms 进程的现场声光/Windows 事件记录，并按现场条件配置企业消息、短信或监控平台 webhook。真正无法证明安全时，系统可以保持断能，但不能只在本机显示弹窗。

### 8.9 P1：发布门禁

正式包必须满足：

- `PackageVerified=True`
- Git Commit 可追溯且工作区干净
- EXE、SafetyAgent、配置和厂商依赖均有清单/哈希
- 安全代理 fresh-process 测试通过
- 独立接管实机演练通过
- 禁止从 `debug` 目录直接作为现场正式包运行

任何缺少安全代理、`safety-runtime.json` 或清单绑定的包都不得启动无人值守正式试验。

## 10. 必须补充的自动化与实机测试

### 10.1 本次异常的精确回归测试

1. 在全新进程中使用真实参数启动 `--watchdog-safety-shutdown`，明确不创建 `Main_Frm`；断言不读取任何 `ClsGlobal`，并可用 fake hardware 完成全部安全阶段。
2. 把 `ClsGlobal.DaqFrequency/SamplesPerChannel` 强制保持 `0/0`；SafetyAgent 仍应从绑定快照取得 `2000/20` 并成功。
3. 删除或篡改 `safety-runtime.json`；断言在打开硬件前以 `SafetyAgentConfigInvalid` 失败，不得归类为 `UnhandledSoftwareStartup`。
4. 在压力探针第一次启动时注入瞬态进程崩溃；断言保持输出 OFF、只重试 SafetyAgent、不增加 MainLaunchCount，第二次成功后继续原 Permit。
5. 同一个安全失败回执被自动接管和应用退出监督同时观察；断言只提交一次状态转换、只记录一次失败、不产生 `MissingOrCorrupt` 二次事件。

### 10.2 时间跳变测试

分别注入：

- 墙钟 `+1.5 s`
- 墙钟 `-1.5 s`
- 连续小步校时
- 恢复期间再次改时

断言：

- 单调控制时间和样本序号连续；
- 输出不因单独墙钟事件发生断电/重上电；
- 生成新的 UTC Epoch 和清晰审计记录；
- 不出现 `DaqWallClockStep → 全组机械重入`；
- Watchdog 所有硬期限不被 DateTime 跳变拉长或缩短。

### 10.3 看门狗状态机测试

1. 在 `Approved`、`OldProcessExitProven`、`SafetyAgentRunning`、`SafetyCompleted`、`MainStarted` 各阶段分别强杀相关进程并重启 Sidecar，验证从耐久状态幂等续跑。
2. AutomaticTakeover 与 ApplicationExit 同时到达；断言只有一个 `RecoveryReplacementTransaction` 所有者。
3. 墓碑写入成功但 application-exit receipt 延迟，反向场景也测试；断言不会生成第二个 Permit 或重复计数。
4. Permit/Handoff 身份真实不一致时继续 fail-closed，但事件限频，5 分钟内同一摘要不超过 11 条（首次 1 条 + 每 30 秒汇总）。

### 10.4 真实 DAQ/硬件测试

1. 运行态断开并恢复一张 NI 卡；确认整组先安全断能，DAQ 稳定窗口通过后再机械重入。
2. 在恢复重入时制造 1 秒回调空窗；确认立即回滚 OFF，Watchdog 能识别恢复进度，不出现并发双接管。
3. 主程序运行中强杀；SafetyAgent 必须在旧 PID 退出证明后完成 DO OFF、AO=0、电源 OFF 和压力安全，随后自动拉起主程序并从检查点续测。
4. 压力传感器真实不可用；不得拉起可能重新上电的主程序，必须保持断能并触发外部告警。

### 10.5 耐久验收

- 先执行 24 小时故障注入；通过后执行 72 小时无人值守运行。
- 周期性注入墙钟调整、管道断连、Sidecar 重启、主程序强杀、DAQ Task 重建和程控电源响应延迟。
- 验收期间不得出现：
  - 可恢复软件故障落入永久阻断；
  - 未证明安全即启动主程序；
  - 重复 Permit/重复失败计数；
  - 已接收 Raw/SQLite 前缀丢失；
  - 需要现场点击弹窗才能继续的可恢复故障。

## 14. 最终判定

本次不可自恢复不是“运行时间长后偶然卡死”，而是以下三层缺陷叠加：

1. 墙钟异常被过度升级为两轮整组 DAQ/机械恢复；

**P0 的直接阻断点已经由现场 PDB 调用栈和当前源码一一对应确认，不需要再以“可能是硬件”继续试错。**

要达到真正的无人值守，不能只给 `SamplesPerChannel` 填一个默认值，也不能只把 Count 从 2 改为 8。必须落地：独立最小安全代理、完整不可变配置、分阶段回执、单一恢复事务、失败域分离、单调控制时间轴和正式发布门禁。完成第 10、11 节验收后，才可以认为本次问题被完全解决。
