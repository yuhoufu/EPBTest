# V2.13.0.39 安全关闭交接阻断根因分析与整改方案

## 1. 结论先行

| 项目 | 结论 |
| --- | --- |
| 问题定性 | **软件问题**，为人工停止、启动取消和 Watchdog 关闭交接之间的并发时序缺陷，不是卡钳或液压硬件未断能导致的关闭阻塞。 |

## 3. 四层“安全终态”的区分

本次问题之所以容易误判，是因为程序内部同时存在四种不同的“已完成”：

| 层级 | 含义 | 本次状态 |
| --- | --- | --- |
| 设备物理安全 | 电机 DO 关闭、程控电源关闭、液压释压 | **已完成** |
| 数据耐久边界 | 已接收 Raw/SQLite 前缀全部持久化，队列和在途项归零 | **已完成** |
| Watchdog 传输终态 | 管道断开、工作者退出、日志 flush/dispose | **已完成** |
| 应用退出授权 | 耐久墓碑达到 Terminal，或 Sidecar 接受安全交接，UI 收到 `CanExit=true` | **未完成** |

因此，现场看到的并不是“硬件还在运行导致关不掉”，而是“硬件和数据已收口，但软件授权证据没有闭环”。

## 5. 证据链

### 5.1 硬件断能已完成

`log/run.log` 提供了直接证据：

- 所有当时运行卡钳的 DO 关闭命令均返回 `Result=True`。
- 4 个电源组在 7 ms 内均记录为已关闭。
- 两路液压执行 `DO=Off, AO=0`，随后压力值均小于安全阈值。
- 关闭窗口准备阶段又执行了一次 AO 归零和全部 DO 关闭。

这组证据排除了“某只卡钳未停止，所以程序不允许退出”的解释。

### 5.2 主 DAQ/SQLite 持久化已闭合

14:41:28.025 的 DAQ 状态已显示两设备队列深度为 0，`Accepted=Published=Persisted`。最终停止回执为：

| 设备 | 最终边界 | Published/Persisted | Depth/InFlight | 结果 |
| --- | ---: | ---: | ---: | --- |
| Dev1 | 4581 | 4581/4581 | 0/0 | `Recovered`, `Closed=True` |
| Dev2 | 4582 | 4582/4582 | 0/0 | `Recovered`, `Closed=True` |

因此，对于主 Raw/SQLite 采集链，本次封存数据没有显示最后一批已接收数据丢失。

14:41:31.974 另有一条“程控电源遥测清理线程未在退出窗口内完成”的警告。该流是辅助遥测封存，不是本次 `CanExit=false` 的直接阻断条件，但也说明不应将外部杀进程作为无风险操作。

Watchdog 客户端最终回执明确表示：

## 6. 源码级根因

### 6.1 根因一：批量启动取消分支提前关闭 Watchdog

`MTTfTest/FrmEpbMainMonitor.cs:2598-2612` 在 `StartBatchSynchronizedWithResultAsync` 被取消后会：

1. 调用 `NotifyRunStopped(...BatchStartCancelled)`；
2. 紧接着调用 `ShutdownWatchdogSessionAndReleaseUiAsync("BatchStartCancelled")`。

但本次取消本身是由人工 StopAll 引起。此时人工停止事务还在发布最终设备/数据结果，启动协程却先将 Watchdog 管道和 Sidecar 关闭。

这是第一个时序错误：**“批量启动取消”只应向统一停止协调器报告状态，不应独立销毁 Watchdog 会话。**

### 6.2 根因二：进度墓碑把“Completed”误当成“逻辑已静默”

`MTTfTest/WatchdogRuntime.cs:2933-2974` 用 `StopSafetyProgressSnapshot` 更新墓碑时：

- `progress.PhysicalSafe` 只写入 `MotorsOff=True` 和 `PowerOff=True`，**没有写入 `PressureSafe=True`**；
- 只要 `progress.Stage >= Completed`，就直接写入 `LogicalQuiescent=True`，没有使用最终 `StopSafetyResult.LogicalQuiescenceConfirmed`。

这会先生成一个“阶段已完成，但安全字段不完整”的 v4 墓碑。本次最终文件正是这种状态：`SafetyStage=LogicalQuiescent`，但 `PressureSafe=False`。

### 6.3 根因三：最终结果纠正可能被“阶段不得回退”规则拒绝，且异常被静默吞掉

`MTTfTest/WatchdogRuntime.cs:2977-3012` 随后尝试用完整 `StopSafetyResult` 纠正墓碑。但：

- 若最终结果的 `LogicalQuiescenceConfirmed=False`，正确安全阶段应回到 `DataDrained` 或 `PhysicalSafe`；
- `WatchdogClosingTombstoneStore.WriteThrough` 明确禁止 `EffectiveSafetyStage` 回退；
- 进度事件已经提前把阶段提升为 `LogicalQuiescent`，因此最终结果的纠正写入可能被判定为回退而拒绝；
- 该方法最外层使用 `catch { return false; }`，没有将失败原因写入日志。

**高置信推断：** 本次 v4 墓碑的字段组合、停止结果“要求重启”、人工停止凭证发布失败，与上述回退被拒绝路径完全一致。由于异常被吞掉，无法从封存日志中还原具体异常文本，但可以确认最终结果未进入耐久墓碑。

### 6.4 根因四：关闭顺序颠倒，先 detach，后请求退出授权

关闭判定本身也存在口径冲突：`Controller/ChannelRuntimeState.cs:1353` 中的 `CanCloseApplication` 只要求电机关闭、电源关闭和持久化边界完成；`MTTfTest/WatchdogRuntime.cs:2915-2917` 中的墓碑终态还要求压力安全和逻辑静默。这使监控窗口可以接受一份 `CanClose=True` 凭证，而 Watchdog 对同一份凭证拒绝终态化。两者需要分别定义“可退出进程”与“可在进程内再启动”，不能继续隐式混用。

`MTTfTest/WatchdogRuntime.ShutdownRetentionCoordinator.cs:417-427` 要求以下条件同时成立才返回终态：

- Pipeline 已终止；
- Engine 为精确终态；
- Journal 已 flush/dispose；
- Closing 墓碑已持久化为终态。

本次前三项均成立，第四项不成立。但程序仍将 Engine、Pipeline 和 Sidecar 拆除，留下一个无法继续完成墓碑的半关闭状态。

`session manifest` 同时把该会话记为 `ExpectedApplicationExit / RuntimeShutdown`，而 WinForms 实际并未退出。这是两套终态语义不一致：Watchdog 传输认为应用即将退出，UI 却在等待 Watchdog 交接证明。

### 6.5 根因五：重试缺少可继续完成交接的存活所有者

`MTTfTest/FrmEpbMainMonitor.cs:3440-3497` 在当前停止结果不允许进程内重启时，会请求 Sidecar 安全交接，并等待 5 秒。但 Sidecar 已在 14:41:33 退出，因此不可能再接受该请求。

`MTTfTest/Main_Frm.WatchdogUi.cs:376-386` 在任一监控窗体没有返回 `CanExit=true` 时，会主动取消关闭，并将标题改为“安全交接尚未完成，可重试关闭”。

重试时的诊断日志显示 `ContextReferenceExact=False`，说明 Engine detach 后旧 context 已不是当前内存引用。需要注意，Shutdown Retention Coordinator 的最终终态计算主要使用 Session Lease、Engine 回执和耐久墓碑，`ContextReferenceExact` 在这条警告中是诊断字段，不应单独解读为唯一阻断条件。本次真正无法恢复的组合是：墓碑未终态、运行时已拆除、Sidecar 已退出，且 UI 没有可复用的耐久退出回执。

所以本次不是操作员需要多等几秒，而是程序已进入逻辑上无法自行达到终态的活锁。

## 7. 为什么不是卡钳问题

本次关闭阻塞是全局的退出授权问题，与某一卡钳的电流、行程或通信无关，理由如下：

1. 停止命令已对所有运行通道成功执行 DO Off。
2. 程控电源四组均有关闭日志。
3. 液压两路都有低于阈值的释压实测值。
4. 数据队列已排空，没有某个通道持久化卡住的证据。
5. 最终阻断日志指向 `ContextReferenceExact=False` 和 `TombstoneState=Closing`，而非设备未断能。

不应把这次关闭困难归责于 7 号卡钳或其他卡钳。卡钳的独立运行故障可以另行分析，但它不是本次关闭活锁的原因。

## 8. 解决方案

### 8.1 P0：统一关闭事务所有权

**目标：一次停止只能有一个 Watchdog 关闭所有者。**

- `OperationCanceledException / BatchStartCancelled` 分支不再直接调用 `ShutdownWatchdogSessionAndReleaseUiAsync`。
- 该分支只发布“启动已取消”状态，然后加入当前 `StopSessionReceipt` / `StopSafetyTransactionId` 代表的同一收口事务。
- Watchdog 会话只能在最终 `StopSafetyResult` 耐久化成功、UI 资源准备完成后由唯一协调器关闭。
- 人工停止、应用关闭、启动回滚只能复用同一个幂等任务，不得各自发起 Engine shutdown。

### 8.2 P0：用最终结果一次性发布安全墓碑

- `StopSafetyProgressSnapshot` 只用于 UI 进度和中间观测，不得把 `Stage=Completed` 合成为 `LogicalQuiescent=True`。
- `PhysicalSafe` 不得只隐式表示电机/电源关闭；压力证据应来自明确字段，且支持 `Unknown/False/True` 三态，避免默认 `false` 被误当成已确认不安全。
- 在 Watchdog detach 之前，用最终 `StopSafetyResult` 一次写入 MotorsOff、PowerOff、PressureSafe、PersistenceDrained、LogicalQuiescent、DataContinuityVerified 及完整身份。
- 耐久结构的单调性应基于 `ResultRevision` 和证据类型，不能因中间进度过度提升而阻止最终真值纠正。
- 删除 `catch { return false; }` 式静默失败；至少写入 SessionId、Generation、Lease、StopSafetyTransactionId、前后 StateVersion 和异常文本。

### 8.3 P0：先耐久终态，后拆除传输

建议将正常关闭顺序固定为：

1. 撤销新的执行授权，冻结 Session/Run/Transaction 身份。
2. 完成 DO Off、电源 Off、AO=0 和压力确认。
3. 闭合 Raw/SQLite 已接收前缀。
4. 采集最终逻辑静默证据。
5. 将结构化的最终停止回执写入耐久存储。
6. 将墓碑写为可用于退出授权的终态，或完成 Sidecar 交接。
7. UI 拿到不可变的 `ApplicationCloseReceipt`。
8. 最后关闭 Pipeline、Journal、Engine 和 Sidecar，销毁窗口。

任何分支都不得在第 5-7 步之前执行第 8 步。

### 8.4 P0：分离“禁止进程内再启动”与“禁止退出进程”

`CanRestartInProcess=False` 的意义是当前进程不能再开始试验，不应推导出“当前进程不能退出”。

建议定义两个独立凭证：

```text
CanRestartInProcess = 设备安全
                      AND 数据边界完成
                      AND 逻辑完全静默
                      AND 无诊断级污染

CanExitApplication = 设备断能证据已耐久化
                     AND 已接收数据前缀已闭合
                     AND UI/硬件回调已隔离
                     AND (关闭终态已持久化 OR Sidecar已接管)
```

数据连续性异常可以禁止进程内重启并要求导出诊断，但在“已接收前缀持久化完成”后，不应将进程永久卡住。

### 8.5 P0：重试必须基于耐久身份，而非对象引用

- 重试键应为 `(SessionId, SessionGeneration, SessionLease, StopSafetyTransactionId)`。
- `ReferenceEquals(context, currentContext)` 只可用于运行期优化或诊断，不得作为 detach 后的退出必要条件。
- 如果当前 Engine 为空，但耐久身份与最终回执完全匹配，应直接复用耐久回执放行。
- 只有 SessionId/Generation/Lease/TransactionId 中任一真正不匹配时，才应 fail-closed。
- 每次点击关闭都应加入同一个幂等事务，不得重置身份或创建新的交接请求。

### 8.6 P1：给关闭 UI 增加有界、可操作的失败路径

用户不应再需要 Process Explorer。建议的 UI 行为：

- 显示真实阶段：“正在断能”、“正在确认压力”、“正在保存最后数据”、“正在完成 Watchdog 交接”。
- 使用确定性阶段进度，不使用会不断循环的伪进度条。
- 物理安全或持久化未确认时，保持窗口并显示具体阻断项，提供“重试安全关闭”和“导出诊断”。
- 物理安全和已接收数据前缀都已耐久确认，但只剩交接记账异常时，进入“降级但有审计的退出”：写入事故标记、导出小型诊断包，然后由程序自行退出。
- 超过软时限后不能无限等待。建议设备/数据正常收口目标不超过 10 秒，交接异常硬时限不超过 20 秒；超时后必须给出明确结果和处置按钮。
- “等待 Watchdog 重启”只能在实际存在已批准 relaunch permit 时显示；人工停止 Close Fence 已抑制重启时必须显示“请关闭后重新启动”。

## 10. 必须补充的回归测试

### 10.1 核心竞态用例

1. 在批量启动/自学习阶段点击停止，触发 `OperationCanceledException`；断言只有一个 Watchdog shutdown owner。
2. 令 StopSafety 返回物理安全、持久化完成、但 `RequiresProcessRestart=True`；断言程序可退出，且不允许进程内重启。
3. 先发布 `Stage=Completed`，再发布 `LogicalQuiescenceConfirmed=False`的最终结果；断言最终结果能正确覆盖中间进度，不会被“阶段回退”拒绝。
4. 压力实测安全，但进度快照未带压力布尔值；断言墓碑不会把 Unknown 写成 False，最终回执能写入 True。
5. 管道在 UI 授权前已终止，当前内存上下文为空；断言完全匹配的耐久身份仍可授权退出。
6. 耐久 SessionId/Generation/Lease/TransactionId 任一不匹配；断言仍然 fail-closed，不能被降级退出绕过。

### 10.2 幂等与故障注入

1. 连续点击三次关闭，断言始终复用同一个 StopSafetyTransactionId 和交接回执。
2. 在墓碑写入、Journal flush、Journal dispose、Engine detach 各阶段分别注入异常，断言记录具体失败阶段，且能从耐久回执幂等恢复。
3. Sidecar 在交接前退出，但主程序有完整物理/数据证据；断言进入可审计退出，而非无限等待。
4. 程控电源遥测清理延迟；断言封存待处理段，但不阻塞已安全的核心退出。

### 10.3 端到端验收用例

1. 使用与现场一致的 6 通道自学习启动，在启动过程点击停止，再关闭程序。
2. 记录从点击关闭到进程退出的时间，正常设备/存储条件下应小于 10 秒。
3. 验证墓碑在 Pipeline detach 前已达到可退出终态。
4. 验证主进程、Sidecar、工作者和厂商 SDK 句柄都退出，无残留进程。
5. 重新启动软件，验证新 Session 能正常连接、不复用旧 Lease，并能正常开始试验。

## 11. 验收标准

修复版本必须同时满足：

- 操作员只需一次点击关闭，不需要任务管理器或 Process Explorer。
- 正常条件下，安全关闭并退出进程不超过 10 秒。
- 设备或数据真正未安全时，程序继续 fail-closed，并明确显示未满足的证据项。
- 只剩 Watchdog 记账/交接异常时，程序在硬时限内完成诊断封存并自行退出，不无限等待。
- 关闭墓碑、Watchdog manifest、UI `ApplicationCloseReceipt` 三者对同一 Session/Generation/Lease 的终态表达一致。
- 关键写入失败不得被静默吞掉，必须能从封存包直接定位。
- 现场包必须 `PackageApproved=True`，并携带可核对的 Git Commit、EXE SHA-256 和配置 SHA-256。

## 14. 最终判定

本次 V2.13.0.39 关闭困难的根因是：

> 人工停止在批量启动/自学习阶段触发了启动取消，启动取消分支在最终停止证据耐久化之前提前关闭 Watchdog；同时，进度墓碑提前提升了安全阶段，使最终结果无法完整固化。随后 UI 仍在等待旧会话的耐久终态或已退出 Sidecar 给出交接回执，最终形成关闭活锁。

**这是确定的软件缺陷，应在下一个现场版本中按 P0 修复，不应继续让操作员依赖 Process Explorer 完成正常关闭。**
