# V2.13.0.15 强杀后 V2.13.0.25 启动即停根因分析与修复方案

## 技术结论

本次故障不是封盘数据库损坏、旧进程占用硬件端口或程控电源未释放导致，而是两代程序的两个问题串联形成：

1. **V2.13.0.15 的人工停止入口先执行了可能阻塞的 UI、Watchdog 和检查点操作，真正的 `StopAllAsync` 没有及时进入。** 08:13:12 UI 已记录“停止命令已接收”，但 35 秒后程序仍在启动新圈；操作员只能强杀进程。
2. **强杀发生在不同通道所处机械阶段不一致时。** EPB4/EPB11 已接近夹紧位置，EPB5/EPB12 仍处于正向行程，导致下一版启动定位时 4/11 很快取得高负载证据，而 5/12 在 5 秒边界只达到约 12 A，需要走一次正常的软件瞬态重试。
3. **V2.13.0.25 的启动定位重试事务存在确定的生命周期缺陷。** 重试 worker 结束时通道仍为 `Recovering`，通用恢复收口器因此按失效安全规则把通道发布为 `StartBlocked`。下一次重试尝试正向上电时，被 `ChannelRuntimeAllowsEnergization` 拒绝并报出 `ChannelExecutionPermitMissing ... State=StartBlocked`；三次零时长失败后整批停止。

因此：

- 强杀是本次故障的**触发条件**，不是 V2.13.0.25 启动即停的充分根因。
- V2.13.0.25 启动即停的**直接软件根因**是启动定位恢复事务没有完成 `Recovering → Starting` 的受控重入。
- V2.13.0.15 的停止按钮无响应问题，在当前 V2.13.0.25 源码中已经通过“先启动 `StopAllAsync`，再异步处理 Watchdog/检查点/UI”修正，但仍需现场验收。
- 当前 V2.13.0.25 不应继续用于 4/5/11/12 全通道正式试验；应先修复重试重入并发布新的候选版本。

## 2.13.0.15 为什么“停止后按钮无法点击”

### 事实证据

V2.13.0.15 的 `BtnStop_Click` 顺序为：

1. 先修改 12 个通道的 UI `Checked` 状态；
2. 记录“已接收停止命令”；
3. 同步执行 `UnattendedRecoveryCoordinator.Disarm`；
4. 同步执行 `WatchdogRuntime.NotifyManualStop`；
5. 同步清理恢复检查点；
6. 最后才调用 `_epb.StopAllAsync(...)`。

封盘日志只有第 2 步的 UI 记录，没有出现相应的 StopAll 授权撤销与安全停机链；与此同时，08:13:15、08:13:30、08:13:45 仍持续创建新周期。

### 根因判定

人工停止入口在建立硬件停止栅栏前执行了多个可能阻塞的同步操作。按钮被主动禁用或事件处理仍未返回，所以操作员看到“停止已点击，但界面按钮无法继续操作”；后台周期调度也未被 StopAll 撤销。

无法仅凭封盘日志精确区分究竟阻塞在 `Disarm`、Watchdog 管道还是检查点持久化，因为这些调用之间缺少逐步 admission 日志；但可以确定阻塞点位于“停止命令 UI 日志之后、`StopAllAsync` admission 之前”。

### 当前源码状态

提交 `51fd7e1`（`fix(shutdown): make hardware release and manual stop ownership deterministic`）已调整顺序：当前 `MTTfTest/FrmEpbMainMonitor.cs` 先调用 `StopAllAsync`，再后台通知 Watchdog、清理检查点和取消批次。这解决了本次旧版停止入口的结构性问题。

## 2.13.0.25 为什么“一启动就报错并停止”

### 第一次定位未通过是可恢复现场状态

启动安全基线和电源/DAQ 预检全部通过。EPB4、EPB11 在约 0.24 秒内达到 15 A 左右，而 EPB5、EPB12 在 5 秒时分别为 12.216 A、12.423 A。

结合强杀前最后一圈：

- EPB4/EPB11 已执行到高负载断电附近；
- EPB5/EPB12 刚开始正向动作约 2–3 秒，尚未完成该圈；

可以合理推断，强杀留下了不一致的机械行程位置。V2.13.0.25 的启动定位本来就是用于重新建立统一机械起点；5/12 第一次触及 5 秒进展边界后进入一次安全 OFF + 重试，是符合设计意图的可恢复路径。

这项推断不代表 5/12 存在硬件故障。日志中没有开路、过流、DAQ 失活、电源输出不稳或 DO 写失败的双证据。

### 直接代码根因：恢复事务没有重入 Starting

`Controller/EpbManager.cs` 的定位循环在软件瞬态后调用：

```text
RunStartupPositioningRetryIncidentAsync(...)
```

`Controller/EpbManager.StartupPositioning.cs` 中该方法执行了：

```text
发布 Recovering
→ 确认 OFF
→ 延时退避
→ CompleteAfterTerminal(
     CommitRecoveryIncidentStateForRelease(...))
```

问题是 worker 完成后没有先发布 `Starting`。通用收口器 `CommitRecoveryIncidentStateForRelease` 明确规定：如果当前状态仍是 `Recovering`，就调用 `PublishRecoverySafeTerminal`，失效安全地发布 `StartBlocked`。

下一次 `StartupPositioningAsync` 尝试执行正向命令时，`DoControlTrace.EnsureChannelExecutionPermit` 发现 `StartBlocked` 不允许上电，于是抛出：

```text
ChannelExecutionPermitMissing Channel=5 State=StartBlocked
Reason=StartupPositioningAsync
```

异常名称容易误导：本次并不是授权 generation 必然失效，而是运行状态已经被错误收口为 `StartBlocked`；`EnsureChannelExecutionPermit` 对“permit 失效”和“状态不允许上电”统一使用了同一种异常类型。

### 为什么日志显示“三次失败”

- 第 1 次是 EPB5/12 的真实 5 秒进展边界未通过；
- 第 2、3 次是在 `StartBlocked` 状态下立即拒绝上电，峰值捕获刚创建就被取消，电流回到约 0.02/0.03 A；
- 因此“三次失败”不等于三次真实机械尝试，也不能作为硬件损坏证据。

该缺陷由提交 `935b65d`（2026-08-25，`fix(epb): close rapid-load and watchdog recovery safety loop`）引入，包含在 V2.13.0.21 及之后版本，也包含 V2.13.0.25。

## 解决方案

### 立即处置

1. 暂停使用现有 V2.13.0.25 进行 4/5/11/12 全通道正式试验。
2. 不要通过删除 `index.db`、清空恢复检查点、手工把 `StartBlocked` 改成 `Running` 或反复点击启动来规避；这些操作不能修复确定性的状态机问题，还会破坏取证或绕过安全门禁。
3. 在维修/调试规程允许的情况下，先确认全部电源输出 OFF、DO 全关、AO 归零、液压已释压，再按批准的机械维护流程确认 5/12 已安全释放。
4. 如必须先验证其他功能，只能在风险评估和现场负责人批准后，临时选择本次首轮定位成功的 EPB4/EPB11 做非正式、有人值守验证；这不能替代全通道验收。
5. 不建议直接回退 V2.13.0.15：它存在本次已经复现的停止入口阻塞。V2.13.0.21–V2.13.0.25 又包含本报告定位的重试重入缺陷。应发布修复后的新候选版本，而不是在两类已知缺陷间切换。

### 永久代码修复

在 `RunStartupPositioningRetryIncidentAsync` 的 worker 成功完成 OFF 确认和退避后，必须在释放恢复合同前完成一次带身份校验的启动重入：

```text
Recovering
  → 验证 RunId / RunEpoch / RecoveryOwner / channel / cancellation
  → 验证原执行 permit 仍为 current、通道仍 Enabled、未进入 Stop/Restart
  → 发布 Starting（CorrelationId 使用当前 recovery contract）
  → CommitRecoveryIncidentStateForRelease
```

实现约束：

- **不得无条件调用 `AuthorizeChannelExecution`。** Runner 已持有本批次原 permit；重新授权会递增 generation，使现有 Runner 的 permit 反而过期，也可能把人工停止后的通道错误复活。
- 只有原 permit 仍有效、RunId/RunEpoch 与恢复合同一致、批次未取消、没有 Stop 栅栏、没有 `RequiresProcessRestart` 时，才允许 `Recovering → Starting`。
- 任一校验失败都保持 OFF，并按现有失效安全规则进入 `StartBlocked`，不能重新上电。
- `RunStartupPositioningRetryIncidentAsync` 中“检测到已经是 Recovering 就只 OFF + Delay + return”的快捷分支也必须使用同一重入门禁，或改为等待当前合同完成；不能再次遗留 `Recovering`。
- 建议把异常细分为 `ExecutionPermitStale` 与 `RuntimeStateDisallowsEnergization`，避免以后继续被 `ChannelExecutionPermitMissing` 的名称误导。

### V2.13.0.15 停止链的验收补强

虽然当前源码已经将 `StopAllAsync` 前移，仍应新增/保留以下门禁：

- 从 UI 记录“停止命令已接收”到 StopAll admission 日志不超过 100 ms；
- StopAll admission 必须先于 Watchdog 管道、检查点 flush、复选框事件和其他外部 I/O；
- admission 后不得再出现新一代 `HydraulicQualificationStarted`、Runner 创建或 Forward/Reverse 上电；
- UI 不得无限等待；达到有界超时后明确显示由 Watchdog 接管，并保持所有启动入口关闭；
- StopAll 的物理安全确认与 UI 按钮是否恢复必须分别记录，避免“按钮恢复”被误当成“物理断能完成”。

## 必须新增的回归测试

1. **启动定位可恢复重试**：第 1 次返回 `ForwardLoadRiseNotStarted`，恢复 worker 完成后状态必须为 `Starting`，原 permit 仍 current，第 2 次可以真实执行 Forward。
2. **禁止零时长伪重试**：第 2 次尝试必须产生真实上电命令或明确的终止原因；不得在 `StartBlocked` 下累计 attempt。
3. **退避期间人工停止**：人工停止撤销 permit 后，恢复合同不得发布 `Starting`，必须保持 OFF 并安全终止。
4. **退避期间批次取消/代际变化**：旧 recovery contract 不得重入新批次。
5. **多通道隔离**：5/12 的可恢复重试不得把已成功定位的 4/11 终态化或撤销授权。
6. **恢复合同完整性**：任何 `Recovering` worker 成功返回前，必须已发布非 `Recovering` 的受控重入状态；否则测试失败。
7. **人工停止 admission 顺序**：模拟 Watchdog/检查点永久阻塞，`StopAllAsync` 仍必须先开始并撤销所有执行授权。

## 现场验收标准

### 场景复现

在安全工装和有人监护下，人工构造与本次相近的机械位置差异：部分通道接近夹紧，部分通道位于较长空行程中。禁止通过强杀生产进程来构造场景。

### 通过条件

- 冷启动仍必须先完成 Power OFF、DO ALL OFF、AO ZERO。
- EPB5/12 第一次触及进展边界后，日志显示 `Recovering → Starting`，而不是 `Recovering → StartBlocked`。
- 第二次定位必须真正执行 Forward，不能出现“峰值捕获创建后立即取消”的零时长伪重试。
- 不再出现：

  ```text
  ChannelExecutionPermitMissing ... State=StartBlocked ... StartupPositioningAsync
  ```

- 若第二/第三次取得真实硬件故障双证据，应只隔离故障通道或对应硬件组；若无双证据，应按软件瞬态策略继续有界恢复。
- 启动成功后至少连续运行 100 圈，4/5/11/12 均有正式圈持久化，数据库无永久 gap。
- 人工停止后 100 ms 内出现 StopAll admission；其后不再创建新圈，最终具备 DO/AO/压力/电流与落盘收口证据。
- 独立 Watchdog 在正常启动成功后就绪；在受控故障注入时能够接管，但不能因为同一确定性重入缺陷无限重启。

## 限制与仍需确认的问题

- 应用内日志无法记录强杀的精确时刻；本报告只能把它界定在最后日志与封盘目录创建之间。
- 没有对 5/12 的机械位置进行独立传感器测量；“强杀造成位置差异”是由最后动作阶段和下一版启动电流共同支持的高可信推断，不是直接测量。
- 当前只完成了根因分析和修复设计，没有修改生产代码，也没有运行修复后现场试验。
- 发布新候选时必须补齐发布包 manifest；否则即使功能修复，运行窗口仍会标记为非受控包。

## 建议发布结论

现有 V2.13.0.25：**不通过全通道正式试验准入**。

建议版本动作：

1. 修复启动定位恢复事务的受控重入；
2. 增加上述回归测试；
3. 生成带 manifest 和校验文件的受控发布包；
4. 完成机械位置差异场景、100 圈连续运行、人工停止和 Watchdog 接管验收；
5. 全部门禁通过后再发布下一候选版本。
