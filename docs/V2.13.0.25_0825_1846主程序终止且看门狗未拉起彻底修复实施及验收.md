# V2.13.0.25 主程序终止且看门狗未拉起彻底修复实施及验收

## 1. 文档信息

- 问题版本：`V2.13.0.23`
- 修复版本：`V2.13.0.25`
- 实施日期：`2026-08-26`
- 根因分析：[`V2.13.0.23_0825_1846主程序终止且看门狗未拉起根因分析与修复方案.md`](./V2.13.0.23_0825_1846主程序终止且看门狗未拉起根因分析与修复方案.md)

## 2. 修复结论

本次已针对封存数据中确认的软件故障链完成闭环修复，而不是仅调整超时参数或增加重试：

1. 主程序并非自行崩溃，而是在旧的断电待确认状态被错误延续后，由看门狗按 `PowerOffUnconfirmedTimeout` 执行终止。
2. 首次恢复虽然已完成业务提交，但严格拉起授权仍停留在旧运行上下文的 `Attached` 状态；第二次接管时无法生成可消费的 `Approved` 许可，因此出现“主程序已终止、看门狗仍在、但没有重新拉起”的结果。
3. `StopAll` 原先在安全动作前等待运行资源冻结，可能让定时器、执行器、恢复上下文或液压锁占用两秒安全窗口。
4. 异步回调从共享字典中的 `CancellationTokenSource` 再读取 `.Token`，与停止流程的取消和释放存在竞态，可触发 `ObjectDisposedException`。

V2.13.0.25 已分别修复上述状态机、时序与资源生命周期问题，并新增回归测试覆盖“首次恢复提交后再次故障”的完整场景。

## 3. 根因与修复映射

| 故障链 | 原行为 | V2.13.0.25 修复 | 验证重点 |
| --- | --- | --- | --- |
| 恢复提交与严格授权上下文混用 | 已恢复的新运行上下文无法替换旧失败上下文，严格授权停留在 `Attached` | 冻结并保留最近一次失败证据；恢复提交允许写入新的 RunId、RunEpoch、阶段和进度；活动授权状态仍强校验上下文一致性 | 首次恢复提交后第二次故障能生成下一代 `Approved` 许可 |
| 先杀进程、后确认拉起许可 | 无可消费许可时旧进程已经被终止 | 接管事务调整为先持久化并回读 `Approved` 许可，再进入进程终止阶段 | 没有许可时中止接管并保留旧进程；有许可时许可 generation 与终止、拉起一致 |
| DAQ 恢复后的上电被误报为待断电 | 截止完成后的验证/重入上电仍可能携带旧 `PowerDisablePending` 和时间戳 | 仅截止完成前的恢复上下文可投影待断电；截止后的正常上电不再沿用旧断电计时 | 恢复后 `PowerDisablePending=False`，旧 `PowerDisableSince` 被清除 |
| StopAll 安全动作被资源冻结阻塞 | Freeze 阶段等待运行资源退出，可能挤占立即断电窗口 | StopAll 入口同步安装禁止上电栅栏并撤销执行许可；Freeze 只做非阻塞生产者冻结；资源清理移到 DO OFF 和电源禁用提交之后 | 停止入口立即禁止新上电，优先提交 DO OFF/PSU disable |

## 4. 关键实现

### 4.1 严格拉起授权状态机

- `DurableRelaunchAuthorityRecord` 增加最近失败证据的冻结字段：RunId、RunEpoch、恢复阶段、进度令牌、进程来源和设备/通道组。
- `ApplyFailure` 固化失败现场；`CommitCommitted` 在保存恢复后新上下文前为旧记录补齐冻结证据。
- `Committed` 状态允许当前上下文切换到恢复后的新运行；`Approved`、`LaunchIntent`、`Started`、`Attached` 等活动状态仍必须与冻结失败证据严格一致，避免放宽防篡改校验。
- 新故障到达时，旧 `Attached` 不再被误判为“已经存在待执行拉起”；系统原子生成下一代 `Approved`，并清除上一代 PID、启动意图和提交代次等身份字段。
- `RunEpoch` 已贯穿失败报告、拉起请求、许可记录和恢复提交。

### 4.2 恢复提交闭环

- 主程序在同一个心跳捕获临界区内取得 RunId、RunEpoch、恢复阶段、进度令牌和提交 generation，防止跨时刻字段拼接。
- 看门狗从心跳、命名管道提交或持久化标记收到恢复提交时，统一经过严格授权提交入口。
- 只有严格授权成功进入 `Committed` 后，才清理恢复日志；持久化标记还要求最近心跳已携带同代或更新的提交 generation 及完整运行上下文。
- 重复提交按幂等方式识别；普通提交拒绝不会被直接升级为永久阻断，只有明确的严格授权阻断/证据不足才进入阻断处理。

### 4.3 拉起许可先于进程终止

接管事务阶段调整为：

`StopRequested → DumpCapture → RelaunchPermit → ProcessTermination → Relaunching`

看门狗必须先生成、持久化并回读验证当前 generation 的 `Approved` 许可，之后才允许终止旧进程。若许可不存在、状态不可消费或上下文不匹配，则记录接管中止事件并保留旧进程，不再制造“已杀死但无法拉起”的不可恢复窗口。

### 4.4 断电状态语义

- DAQ 恢复上下文只有在 `CutoffCompleted` 之前，才能贡献待断电分组和待断电起始时间。
- 截止完成后的验证、重入或业务要求上电属于正常恢复动作，不再投影为旧的 `PowerDisablePending`。
- 仅对仍带电且缺少完整恢复上下文的孤儿通道保留兜底待断电投影。

### 4.5 StopAll 与 CTS 生命周期

- `StopAllAsync` 在等待共享任务锁之前同步设置 `_energizationRevoked` 并撤销全部通道执行许可，立即阻断新的上电动作。
- Freeze 阶段只暂停定时器、冻结循环证据并取消 CTS，不等待 Timer/Runner/液压资源退出。
- Timer、Runner 和液压映射清理移至立即安全动作提交之后。
- 停止和暂停 CTS 更新接口直接返回创建时捕获的 `CancellationToken`；所有异步回调只使用该 token 值。

## 5. 版本与兼容性

- 程序及看门狗相关程序集版本统一升级为 `2.13.0.25`。
- 看门狗线协议仍为 Protocol v3，严格授权仍为 schema 4 / format 2。
- 新增持久化字段为兼容性扩展；旧 format-2 `Attached` 记录在恢复提交时会补齐冻结失败证据，无需人为改写历史记录。
- 部署时必须使用同一次构建产生的主程序、看门狗、客户端和协议程序集，不得混用旧 DLL。

1. 将同一次 V2.13.0.25 构建生成的主程序、看门狗、客户端和协议程序集整体部署，确认各组件版本均为 `2.13.0.25`。

4. 检查恢复后心跳：正常上电时 `PowerDisablePending=False`，旧 `PowerDisableSince` 已清除。
5. 检查恢复提交：严格授权状态进入 `Committed`，记录的是恢复后的 RunId、RunEpoch、阶段、进度令牌和 commit generation。
6. 在受控台架上再次触发接管，确认先出现下一代 `Approved` 许可，再出现旧进程终止；新 PID 随后进入 `Started/Attached`。
7. 执行人工停止，确认调用入口立即禁止新上电，DO OFF 和 PSU disable 优先提交，日志中无 `ObjectDisposedException`。
8. 完成不少于原故障运行时长的连续耐久观察，确认主程序、看门狗和试验状态一致。
