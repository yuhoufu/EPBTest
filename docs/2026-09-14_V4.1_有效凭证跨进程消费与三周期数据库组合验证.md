# V4.1 有效凭证跨进程消费与三周期数据库组合验证

## 目的与边界

此前分别验证了恢复状态事务、数据库三条正式记录要求和任务拉起，缺少一次测试中把有效凭证交给真实子进程，再观察该进程提交数据库记录的组合验证。本次新增 `TicketDatabaseSimulationTests`，纳入 IndependentRecovery.ProcessTests 默认运行。

本次没有修改生产恢复逻辑，也没有完成生产 SYSTEM 服务到主程序试验控制的整体恢复验收。

| 环节 | 本次执行方式 |
|---|---|
| 旧控制进程 | 虚构身份，只用于状态夹具；未向操作系统提交终止操作 |
| 停机、电源 OFF、DO/AO/压力阶段 | 明确模拟回执，原因标注 SIMULATED: NO HARDWARE EXECUTED |
| 新进程 | 真实测试子进程，由 native Job 管理，记录 PID/启动时间 |
| 启动授权 | 实际持久状态协议签发、派发、消费一次性凭证；使用测试 exe 的实际 SHA-256 |
| 批次交接 | 实际 CommitReplacementRun，新 PID 绑定并将 RunEpoch 从 1 推进到 2 |
| 机械动作 | 未运行控制器或硬件；测试把模拟圈写成 mechanical_completed 记录 |
| 数据库 | 实际 SQLite 数据库、事务提交和生产证据读取器；不是 JSON 伪造查询结果 |
| 生产恢复成功状态 | 未设置为 Verified；仅验证数据库证据与跨进程消费，不冒充服务验收 |

## 八项检查

1. 新批次 Controller 的 PID、启动时间与实际 native 子进程一致，RunEpoch=2。
2. 各目标只有两条新正式记录时，7、8、9 仍全部处于证据未完成集合。
3. 第三条正式记录提交后，7、8、9 满足三记录证据要求。
4. 暂停通道 4、永久隔离通道 5、已完成通道 12 的机械完成记录数不变。
5. 第三次提交被读取验证时，新进程仍存活；不把单纯存活当成功条件。
6. 完成验证后，子进程收到结束信号并以 0 退出。
7. 第二个真实子进程重放相同已消费凭证，被拒绝并返回 23。
8. 重放拒绝后，数据库记录边界和机械完成计数均不变。

数据库以六个通道各一条 cycle_number=100 的基线记录开始；仅 7、8、9 新增 101、102、103。测试不重置旧数据；每次只创建新的 `ticket-db-simulation-<GUID>` 目录，并要求测试标记文件。测试子入口不加入生产主程序或安装包。

双向等待各自有 10 秒期限；消费进程由 25 秒、256 MiB native Job 约束，重放进程限 5 秒。子进程在恢复执行前记录归属，父进程记录自己的身份。标记文件用于控制测试暂停点，不是生产恢复凭证或硬件安全证明。

- 默认独立恢复测试退出码 0：进程 20/20、状态 172/172、新组合测试 8/8；`Codex/v41-ticket-db-full.log`。
- 专项命令 `IndependentRecovery.ProcessTests.exe --ticket-database-simulation <证据根目录>` 退出码 0，输出 JSON 为 passed=8、sessionId=1、hardware=SIMULATED_NO_HARDWARE、database=REAL_SQLITE_COMMITS；`Codex/v41-ticket-db-cli.log`。
- 主测试夹具：`Codex/v41-tests/ticket-db-simulation-f785c81f0b8f4a1b8a805c650ecd2a73`，保留数据库、持久状态、归属记录和同步标记。
- 精确身份复核确认父测试进程 PID 18528、消费进程 PID 51608、重放进程 PID 55268 均退出；`Codex/v41-ticket-db-cleanup.json`。

本轮只修改测试工程并增加 SQLite/已有 FallbackGuard 引用，未重复运行未改动的控制、写盘和电源全量测试。本轮未连接 jxcq 或 WJ-EPB，未创建远程会话。

将组合测试移到 jxcq 的实际交互会话，随后接入生产独立执行器的完整检测、接管和启动流程。真实主程序的自学习、控制动作、计数继续、正式数据持续落盘、监督重新绑定，以及故障注入矩阵和安装回滚仍未关闭。此测试不能替代上述事项，也不能替代电源、液压和继电器台架验收。
