# V2.13.0.27 0827-1326 故障根因分析与稳定运行整改方案

## 1. 结论先行

本次停机不是“4、5、11、12 四个通道同时发生硬件故障”，也不是 CPU、内存、磁盘或落盘队列耗尽。首发事件是一次约 **134 ms 的 DAQ 回调短空窗**；在软件作出硬切断决定时，Dev1 回调已经恢复到 **1.4 ms**，队列无积压、无丢样。V2.13.0.27 仍使用硬编码的 `DaqSampleStale>100ms`，把已自行恢复的短抖动判成硬故障，随后又被多层恢复逻辑连续放大，最终看门狗在第一次进程重启前就永久阻断。

完整放大链如下：

> 134 ms DAQ 短空窗  
> → 100 ms 硬编码切断 EPB4 当前周期  
> → EPB4 未进入下一公共液压槽，但仍被静态列为必到成员  
> → H1 等待 EPB4 满 15 秒后超时  
> → 正式阶段恢复被错误标记成 Startup 恢复  
> → 活跃恢复任务在 1.33 秒后被误判为“孤儿”  
> → 进程内恢复启动，但固定 30 秒边界在学习过程中撤销上电授权  
> → 4/5/11/12 因软件主动断电而全部“学习失败”  
> → 看门狗杀掉旧进程，准备第 2 次恢复  
> → 当前 RunId 已被前序清场置空，看门狗以 `FrozenExcludedChannelsRunIdentityMissing` 永久阻断重启  
> → 人工重启软件

因此，本次最终未自恢复的直接原因是两个确定的软件缺陷：

1. **恢复任务误判**：日志已经明确记录 `TaskCovered=True`，软件仍产生 `OrphanRecoveryOwnerOrTaskMissing` 并执行终态清场。
2. **看门狗恢复意图冻结过晚**：历史上存在完整有效的 RunId、通道集合和进程身份，但看门狗只使用清场后的最后一帧空 RunId，第一次重启就永久开路；当时仅 `ConsecutiveFailures=1`，配置上限为 8，并非重试耗尽。

整改方向不应继续增加互锁层数，而应采用“力大砖飞、局部故障局部消化”的可用性策略：

- 瞬态空窗只记告警或跳过一次动作，不启动恢复风暴；
- 单设备持续异常只暂停受影响组，健康组继续运行；
- 有活跃任务、有材料进展就不得判为孤儿或超时；
- 运行身份在正常心跳阶段提前固化，清场后的空值不能抹掉恢复依据；
- DAQ 暂时不可见时，允许“DO 已 OFF + 新鲜电源电流为 0 A”作为冗余断电证据；
- 只有输出状态无法证明安全、进程确实失活或恢复长期无进展时，才升级到整进程重启。

## 4. 首发事件为何属于可容忍的瞬态空窗

### 4.1 判定时数据已经恢复

首条硬切断日志同时给出了两组相互矛盾的语义：

```text
DAQ_LIVENESS ... CallbackAge=134.2ms
DAQ_FRESHNESS_SAFETY_CUTOFF ... Original=DaqSampleStale>100ms
CallbackAge=1.4ms ControlEnqueueAge=1.3ms ControlProcessedAge=1.3ms
```

前者说明过去出现过一个 134.2 ms 的 gap；后者说明作出切断决定时，新回调和控制处理已经恢复到 1～2 ms。当前实现没有做“恢复后再确认”，而是看到一次历史越线就继续执行硬故障动作。

### 4.2 没有资源耗尽或数据管线堵塞证据

封盘日志显示：

- DAQ produced、processed、persisted 数量持续追平；
- 队列深度为 0，没有积压；
- 未发现对应的数据不连续或落盘失败；
- 主机 CPU、系统 CPU、内存和磁盘队列正常；
- Dev1/Dev2 在同一时段都出现过约 130 ms 的 callback gap，更符合 Windows 调度、NI 驱动批次或短时系统抖动。

因此，134 ms 空窗值得记录和统计，但不足以证明 DAQ 任务已经失活，更不应触发整批软件重建。

### 4.3 配置的分层阈值被 100 ms 硬编码绕过

`MTTfTest/App.config` 已经配置：

```text
DaqLivenessWarnThresholdMs    = 100
DaqLivenessSuspectThresholdMs = 1000
DaqLivenessTripThresholdMs    = 2000
```

但 `Controller/Adaptive/EpbAdaptiveControl.cs` 仍在 100 ms 直接返回：

```csharp
return Fault(decision, "DaqSampleStale>100ms");
```

`EpbManager` 和 freshness snapshot 还有多处字面量 `100`。结果是配置上虽然存在 Warn/Suspect/Trip 三层，实际控制层在 Warn 阈值就硬故障，后两层失去意义。

## 5. 停机根因分解

### 5.1 根因 A：公共液压槽采用静态必到成员，缺席没有闭环

EPB4 当前周期被中止后，其正式定时器没有进入下一共享液压槽。其他通道创建该槽时，软件仍按“所有已启用分配”静态捕获参与者，把 EPB4 列为必到成员。EPB5 已到达却只能等待，最终满 15 秒报：

```text
HydraulicBarrierTimeout ... Phase=PreRelease Slot=2 Timeout=15000ms Pending=[4]
```

问题不在于屏障有超时，而在于系统没有表达“EPB4 本槽已跳过/已滚到下一槽”。一个通道跳过一次动作，拖死同液压组并触发恢复，是不符合持续运行目标的。

### 5.2 根因 B：恢复 key 丢失原阶段，正式恢复被伪装成 Startup

`Controller/EpbManager.BatchStart.cs` 在创建恢复代次时，把 key 的阶段统一改成：

```csharp
HydraulicPhaseKind.Recovery
```

随后 `RunHydraulicRecoveryAttemptIncidentAsync` 又根据 `key.PhaseKind` 推导 owner 和 target。`Recovery` 不属于 Learning、Qualification、Formal 三种分支，最终落入默认值：

```text
RecoveryOwnerKind.BatchStartup
RecoveryTargetPhase.Startup
```

但这次故障真实发生在 Formal 阶段。原始阶段信息在创建恢复 key 时已经丢失，后续运行时健康检查看到的恢复身份必然错误。

### 5.3 根因 C：活跃任务被 1 秒孤儿规则误杀

`Controller/EpbManager.TimerRuntimeHealth.cs` 在恢复超过 1000 ms 后调用 `HasRecoveryExecutionCoverage`。事件日志明确写出：

```text
Owner=; TaskCovered=True
```

也就是说恢复 task registry 已经证明工作任务存在，却仍被判为 `OrphanRecoveryOwnerOrTaskMissing`。原因是覆盖判断先要求 owner 合法，并按错误的 `BatchStartup/Startup` 身份走不同分支；另外诊断中的 `Owner=` 又来自另一套液压 owner 存储，造成“任务存在但显示无 owner”的矛盾。

这不是合理的失效安全，而是恢复身份模型不一致导致的确定性误报。

### 5.4 根因 D：固定 30 秒边界在有进展时反杀恢复

进程内恢复执行了 StopAll、清场和完整学习。完整学习本来就可能超过 30 秒，但当前实现不看阶段进展，固定在 30 秒撤销整个进程的上电授权。电源被软件主动关闭后，各通道在学习过程中出现：

- `InfrastructureTransitionOpenCircuit`；
- `PowerPermitMissing`；
- `LearningFailed`；
- “全部选中通道均在学习阶段被隔离”。

因此，四通道学习失败是 30 秒边界制造的派生故障，不是四套机构同时损坏。

### 5.5 根因 E：看门狗在清场后才冻结恢复意图

看门狗历史心跳中存在可用身份：

- 12:38:33：RunId=`68cc4b...`，RunEpoch=1，通道 4/5/11/12；
- 12:40:02 接管请求时：仍有有效的进程身份和恢复上下文；
- 12:40:17 dump/终止前最后心跳：RunId 已被同进程清场置空，RunEpoch=7。

`MTTFTest.Watchdog/WatchdogHost.cs` 当前只在需要恢复时从 `LastHeartbeat` 冻结排除通道意图，并硬要求 `RunId` 非空。于是已知的历史有效运行被一帧正常清场后的空 RunId 覆盖，返回：

```text
FrozenExcludedChannelsRunIdentityMissing
```

重启计数当时仅为 1，上限为 8。永久阻断不是因为多次拉起失败，而是恢复证据保存时机错误。

### 5.6 次生问题：DAQ 不可见时忽略了新鲜的 0 A 电源证据

人工重启后 12:54 又发生一次 Dev1 约 1193.2 ms 的真实回调空窗。软件最终自动恢复，但过程暴露了另一处过度互锁：

```text
OffCurrentUnverifiableDaqStale AgeMs=1145.0
PowerGroupIOut=0.000A PowerTelemetryAge=58.5ms Output=True
```

此时 DAQ 电流样本确实陈旧，但电源遥测只有 58.5 ms，组电流为 0.000 A，DO OFF 命令也成功。当前代码只把电源证据拼到日志里，仍无条件触发整个电源组联锁。随后又在电源被自己关闭时反复尝试启动定位，产生 `ExpectedOutputDisabled`、permit missing 和多层重试风暴。

该事件最后在 12:55:02 恢复 4/5，并原子加入公共槽 56；之后继续稳定运行。这证明局部自恢复路径基本可行，但应减少不必要的断电、重试和等待。

## 6. 稳定运行整改方案

### 6.1 P0：统一 DAQ 新鲜度策略，100 ms 不再硬故障

建议增加“可用性优先”现场配置，并让所有控制层只读取同一份配置，不允许再出现 `>100ms` 字面量：

| 级别 | 建议初值 | 动作 |
|---|---:|---|
| Observe/Warn | 250 ms | 未带电时只记录 gap 并限频告警；带电时立即 DO OFF、只作废当前动作，不启动恢复风暴 |
| Group pause/requalify | 1500 ms | 连续无回调才暂停受影响设备关联组；健康组继续，数据恢复后自动重新资格 |
| DAQ task rebuild | 5000 ms | 持续无回调或 NI 明确报错时，仅重建受影响 DAQ 任务和关联组 |
| Process recovery | 180 s 无材料进展，或进程失活 | 才交给独立看门狗重启进程 |

具体规则：

1. 越过阈值后，在做升级动作前重新读取当前 callback age、processed age 和 generation。
2. 如果当前数据已经恢复，例如本次从 134.2 ms 恢复到 1.4 ms：未带电时只记录瞬态；带电时最多关闭并作废该次电机动作，不启动设备/液压/整批恢复。
3. Warn/Suspect/Trip 要求连续 2～3 次监督轮询或持续时间成立，单个历史峰值不得直接跨级。
4. 保留电机绝对最大上电时间、DO OFF 高优先级通道和真实过流硬保护；放宽的是软件瞬态判据，不是带电安全底线。
5. 将阈值写入日志和 checkpoint，便于确认现场实际生效值。

如果现场希望先更激进地追求连续运行，可先采用 `250 / 1500 / 5000 ms`。运行数据积累后再收敛，而不是继续以 100 ms 作为硬故障线。

### 6.2 P0：公共槽改成“实际到达 + 明确跳过”的动态成员模型

目标是坏一次只丢一次动作，不拖死同组：

1. 公共槽参与者以“已经完成该槽 Admission 的通道”为准，不再直接把全部已启用通道作为永久必到成员。
2. 设置 200～500 ms 的槽 admission 窗口；窗口关闭后，晚到通道自动滚到下一公共槽。
3. 通道当前周期被 DAQ cutoff、取消或恢复接管时，必须向当前槽提交 `SkippedForSlot` tombstone，屏障立即减少待到成员。
4. 通道重新加入时，原子地基于组公共槽重置 phase slot，不能继续使用已经漂移的本地 cycle index。
5. 在所有输出已 OFF、压力状态安全时，BarrierTimeout 只记调度异常并进入下一槽，不升级 SystemFault。

### 6.3 P0：恢复身份必须保存原始阶段

不要再从 `HydraulicPhaseKind.Recovery` 反推 owner。建议在恢复事务中显式携带：

- `SourcePhaseKind`；
- `RecoveryOwnerKind`；
- `RecoveryTargetPhase`；
- `RunId/RunEpoch`；
- `IncidentId/TaskId`。

Formal 屏障恢复必须是：

```text
OwnerKind=HydraulicGroupRecovery
TargetPhase=Formal
```

Learning、Qualification、Startup 分别显式赋值，不能使用兜底分支猜测。

### 6.4 P0：孤儿判定改为多证据、带宽限

当前 1000 ms 太短，并且把 owner、task、progress 三类证据混为一体。建议：

1. 只要 task registry 中存在匹配 RunEpoch/IncidentId 的活跃任务，就认为有覆盖；`TaskCovered=True` 绝不能再产出 Orphan。
2. 只有“owner 不存在 + task 不存在 + progress token 长时间不变化”同时成立，才判孤儿。
3. 孤儿宽限至少 10 秒；重型液压/学习 worker 采用其阶段 deadline。
4. owner 存储统一为单一事实来源，日志同时输出 OwnerKind、TargetPhase、OwnerId、TaskId、IncidentId 和最后进展时间。
5. 第一次不一致只自修复 owner 映射；连续两次仍无任务、无进展才升级。

### 6.5 P0：30 秒固定边界改成“材料进展续租”

进程内恢复不能在自己正在成功推进时被墙钟杀死：

- StopAll、清场、DAQ 重建、学习完成一个通道、qualification 完成、正式定时器重建都应刷新 progress token 和阶段 lease；
- 每阶段使用独立超时，例如 StopAll 30 秒、DAQ 重建 60 秒、学习按通道数给 2～3 分钟；
- 只在连续 60 秒无材料进展或总时长超过 3～5 分钟时升级进程重启；
- 外部接管前先取消当前 worker 并等待安全交接，不得在学习动作中途直接撤销 permit，随后再把 permit missing 计为学习失败。

### 6.6 P0：看门狗提前冻结“最后一个已验证活动运行”

恢复意图不应等故障发生后才从最后一帧猜。建议：

1. 在每个 `InitialProcess` 且 RunId 非空的正常心跳中，持续更新并持久化 `LastVerifiedActiveRun`。
2. 一旦进入 Armed 正式运行，冻结：RunId、RunEpoch、PID、进程启动时间、已选通道、已排除通道、恢复资格通道、配置/程序 hash。
3. 后续 Idle/StopAll 心跳中的空 RunId 只表示生命周期过渡，不得覆盖该快照。
4. 外部接管前，在主进程清空 RunId 之前同步写一次 recovery boundary checkpoint。
5. 恢复证据优先级：已冻结快照 → 最后有效活动心跳 → Armed checkpoint mirror → 当前心跳。
6. 如果输出已经验证 OFF，且已选/排除通道能由多个持久证据无歧义重建，应允许重启；只有证据互相冲突、hash 不一致、输出不能证明安全时才永久阻断。
7. `ConsecutiveFailures=1/8` 不得仅因预期的空 RunId 直接开永久 circuit。

仍应保留 PID/启动时间/exe hash 校验，防止把旧会话或错误程序拉起。要放宽的是“过渡状态空 RunId”这一已知正常现象。

### 6.7 P0：采用冗余断电证明，避免无意义电源组联锁

DAQ 电流不可见时，按以下证据矩阵判断：

| DO OFF | DAQ 电流 | 电源遥测 | 动作 |
|---|---|---|---|
| 成功 | 新鲜且低于阈值 | 任意 | 确认断电，继续恢复 |
| 成功 | 陈旧 | 新鲜且组电流 ≤ 0.5 A | 以冗余证据确认断电，不触发电源组联锁 |
| 失败 | 任意 | 任意 | 立即关闭关联电源组 |
| 成功 | 陈旧 | 也陈旧/无数据 | 关闭关联电源组 |
| 成功 | 陈旧 | 新鲜但电流仍高 | 关闭关联电源组并报警 |

0.5 A 初值应配置化，并结合电源精度和组内待机电流验证。此次 `0.000 A / 58.5 ms` 明显属于可安全继续局部恢复的情形。

此外，`ExpectedOutputDisabled` 应作为“等待唯一电源恢复 owner”的状态，不能计入启动定位失败次数；同一组只允许一个恢复 worker，其他请求合并，避免组级 3 次 × 通道级 3 次的嵌套重试风暴。

### 6.8 P1：故障升级矩阵统一为局部优先

| 故障 | 最大影响范围 | 默认动作 |
|---|---|---|
| < 1.5 s 瞬态回调空窗且已恢复 | 单动作/单周期 | DO OFF（若带电）、作废本次、下一槽继续 |
| 1.5～5 s 单设备无回调 | 关联 DAQ/液压/电源组 | 受影响组暂停并重建，其他组继续 |
| NI 明确任务错误或 > 5 s 无回调 | 关联设备组 | 重建 NI task，重新资格确认后自动加入 |
| 局部恢复有持续进展 | 局部组 | 续租，不升级 |
| 局部恢复 60 s 无进展或多次重建失败 | 整进程 | 看门狗安全重启 |
| 输出无法确认 OFF、身份/hash 证据冲突 | 全局 | 安全停机，人工介入 |

核心原则：**瞬态问题不能跨过“单周期 → 单通道 → 单组 → 单设备 → 整进程”逐级升级链；每一级都必须有独立、持续、可复现的升级证据。**

### 6.9 P1：降低告警噪声并改正 UI 语义

- 对 near-target plateau、轻微 overshoot、单次 callback gap 做按通道/原因限频和聚合统计；
- 同一个 incident 不重复生成多条不同 fingerprint；
- UI 必须区分“正在退避、下一次会重启”和“恢复已永久阻断”；
- 一旦 `RelaunchState=Blocked`，停止显示“预计 N 秒后继续”，改为显示具体 DetailCode 和自动采用过的回退证据；
- `Owner=` 不允许为空却同时显示 `TaskCovered=True`，应输出真实 owner/task 关联状态。

## 7. 建议实施顺序

建议下一个现场版本按以下顺序一次落地，不再只补单个 if：

### 第一批：先解决“误报后必停”

1. 修正恢复 SourcePhase/OwnerKind/TargetPhase；
2. `TaskCovered=True` 直接视为有效覆盖，孤儿判定增加 progress 和 10 秒宽限；
3. 看门狗提前固化最后有效 RunId/通道意图，并增加 checkpoint fallback；
4. 30 秒固定边界改为阶段进展续租；
5. 公共槽加入 `SkippedForSlot` 和下一槽原子重入。

### 第二批：把 DAQ 瞬态变成可消化事件

1. 去掉所有 100 ms 硬编码；
2. 启用 `250/1500/5000 ms` 可用性配置；
3. 增加恢复后复查和连续样本/持续时间判据；
4. 引入 DO + 电源 0 A 冗余断电证明；
5. 合并电源恢复请求，消除嵌套重试。

### 第三批：现场稳定性验收

完成故障注入、8 小时预跑和 24 小时四通道连续运行。达标前不宣称“已稳定”。

## 8. 必须补充的回归与故障注入

1. **134 ms 双设备短 gap 重放**：不得产生 SystemFault、BarrierTimeout、进程内恢复或进程重启；四通道继续。
2. **1.2 s Dev1 gap**：只作废受影响动作，H2/EPB11/12 不暂停；4/5 自动重新资格并加入，不能整进程重启。
3. **5 s Dev1 无回调**：只重建 Dev1 和受影响组；健康组持续运行。
4. **通道在槽前被取消**：必须生成 `SkippedForSlot`，同组其他通道不得等待 15 秒。
5. **Formal 液压恢复任务运行超过 1 秒**：OwnerKind/TargetPhase 保持 Formal，绝不报 Orphan。
6. **task 活跃但辅助 owner 映射暂时缺失**：自动修复映射，不能终态清场。
7. **进程内恢复超过 30 秒但持续有进展**：不得外部接管；progress lease 正常续期。
8. **清场先把当前 RunId 置空**：看门狗必须使用最后有效活动快照或 Armed checkpoint 自动拉起。
9. **首次拉起证据需要 fallback**：重启计数仍为 1/8 时不得永久开路。
10. **DAQ 陈旧 + DO OFF 成功 + 电源 0 A 新鲜**：不得触发电源组失效安全联锁。
11. **DAQ 与电源遥测同时陈旧**：必须关闭关联电源组，证明硬安全仍有效。
12. **运行中单通道长期故障**：隔离该通道，其他通道持续运行；恢复后可按公共槽重新加入。
13. **24 小时四通道运行**：允许出现被统计的瞬态 gap，但不得需要人工重启、不得全通道学习隔离、不得出现 `RecoveryBlocked`。

验收日志必须能够回答：故障在哪一级被消化、为什么升级、哪个 owner/task 正在工作、最后一次材料进展是什么、为何允许或拒绝重启。

## 9. 现场临时运行建议

在上述代码整改完成前，不建议仅通过继续增大重试次数来掩盖问题，因为当前故障会在错误身份、固定 30 秒和空 RunId 三处确定性失败，重试只会重复清场。

如果必须继续用 V2.13.0.27 运行：

- 保留现有 DO OFF 和绝对最大上电时间；
- 避免把 100 ms Warn 继续用作硬故障阈值；如能通过受控配置覆盖，至少把硬 cutoff 提到 1000～1500 ms，并先做带电空窗注入验证；
- 看门狗窗口出现后不要仅依据倒计时判断会自动拉起，应查看 Relaunch 是否已经 Blocked；
- 完整保留 WatchdogSessions、Recovery、log 和 dump；
- 这只能降低触发频率，不能修复恢复身份和 RunId 冻结缺陷，不能作为最终解决方案。

## 10. 最终判定

V2.13.0.27 本次失败的本质是：**软件把一个已恢复的短 DAQ 空窗当成硬故障，并在恢复链中连续制造新的软件故障，最后由看门狗自己的证据保存缺陷阻断重启。**

需要保留的硬底线只有：

- 电机绝对最大上电时间；
- DO OFF 高优先级执行；
- DO 失败、真实电流不降、DAQ 与电源证据同时不可用时关闭电源组；
- 程序/hash/进程身份冲突时拒绝错误拉起。

除此之外，应优先“跳过一次、暂停一组、自动重建、自动重入”，而不是“一次 100 ms 抖动就逐级升级到整批停机”。完成本文件 P0 项并通过故障注入与 24 小时连续运行后，才能认为程序达到了无人值守稳定运行要求。
