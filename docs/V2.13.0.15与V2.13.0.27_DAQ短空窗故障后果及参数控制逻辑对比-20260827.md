## 1. 结论先行

### 1.1 对问题的直接回答

同样需要先区分“同一个直接触发条件”和“同一条最终失效链”。

1. **相同的直接根因在 V2.13.0.15 中仍然存在。**  
   V2.13.0.15 和 V2.13.0.27 都把 `DAQ 样本年龄 > 100 ms` 作为硬编码的循环安全切断条件。达到条件后，当前通道都会立即关电机并中止当前循环。因此，V2.13.0.15 并没有从根本上解决 100 ms 短空窗被当成故障的问题。

2. **但 V2.13.0.15 不会必然得到 V2.13.0.27 本次完全相同的最终结果。**  
   V2.13.0.27 本次最终失效需要后续多个新增机制共同参与：机械重新确认、跨液压组全局正式槽、恢复所有者/目标阶段误判、恢复任务被 FailSafe 终止、全通道学习隔离、Watchdog 冻结排除通道时丢失 RunId。V2.13.0.15 不具备其中数个关键机制，尤其不存在 `FrozenExcludedChannelsRunIdentityMissing` 这条拒绝重启路径。

3. **如果在 V2.13.0.15 上出现与本次相近的约 134 ms、且很快恢复的 DAQ 空窗，最可能结果是：**  
   当前循环被中止，随后在下一次 15 秒正式周期继续运行，不进入全局进程恢复。V2.13.0.15 的现场记录中，已经发生过更严重的 251.9 ms / 236.9 ms 双通道空窗，系统仍在下一正式槽恢复四通道运行。

4. **V2.13.0.15 也不能称为稳定版本。**  
   当空窗更长、叠加旧的电源组紧急停机锁存状态时，V2.13.0.15 会表现为局部液压组长期暂停且没有有效恢复所有者。2026-08-26 15:00 的现场事件中，EPB4/5 直到人工“批量暂停—继续”后才恢复。因此不能把回退 V2.13.0.15 当作最终解决方案。

5. **两版的主要差别不是配置阈值，而是控制逻辑。**  
   已比对的 `App.config` 151 个键完全一致；DAQ 的 20/100/1000/2000 ms 分级参数、15 秒周期、液压阈值、屏障超时、30 秒进程内恢复等待等关键参数也相同。V2.13.0.27 的失稳主要来自新增控制链之间的状态不一致，而不是现场把某个配置值调得更严格。

### 1.2 一句话判断

> V2.13.0.15 遇到同一类 DAQ 短空窗也会误切当前循环，但通常不会走成 V2.13.0.27 本次的全局自恢复阻断；它只是“故障停在更早、更局部的一层”，并不代表根因已经消失或具备长期无人值守稳定性。

## 3. “同样的根因”在两版中的结果矩阵

| 故障阶段 | V2.13.0.15 | V2.13.0.27 | 是否相同 |
|---|---|---|---|
| DAQ 样本年龄超过 100 ms | 立即关当前通道电机，中止当前循环 | 立即关当前通道电机，中止当前循环 | **相同** |
| 使用新鲜电源电流 0 A 证明已经断能 | 记录了电流，但仍无条件申请电气组紧急停机 | 同样记录电流但仍申请紧急停机 | **相同缺陷** |
| DAQ 恢复后的重新加入 | 新鲜度恢复后可较快重新参加本液压组下一周期 | 必须额外通过持续新鲜和机械释放重新确认 | **不同** |
| 正式周期调度 | 两个液压组各自定时、各自获取液压租约 | 新增跨两个液压组的全局正式槽和统一电机锚点 | **不同** |
| 某通道在快照后没有进入屏障 | 也存在静态参与者快照风险，但现场 8 次切断未形成屏障超时 | 重新确认使 EPB4 错过已经包含自己的槽，造成 H1 等待并超时 | **V27 更易放大** |
| 恢复阶段所有者判定 | 有所有者字符串时仍可能被判 `TaskCovered=False`，但动作通常是局部组重置 | 新增类型化所有者后，将 Formal 恢复误判成 BatchStartup；即使任务存在，也被判无有效覆盖 | **不同的误判** |
| 孤儿恢复动作 | 周期性报警并启动受影响组 Stop→Start | 错误组合落入 `FailSafeTerminal`，终止真实恢复任务并转全局 SystemFault | **V27 后果更重** |
| 进程内恢复 30 秒等待 | 固定 30 秒 | 固定 30 秒 | **相同** |
| 全通道学习隔离 | 现场同类事件没有进入该层；理论上进入 30 秒恢复后仍有风险 | 本次确实在恢复代际切换时把四通道全部学习隔离 | **本次仅 V27 实际触发** |
| Watchdog 冻结排除通道和 RunId 校验 | 没有冻结意图和 RunId 非空强校验 | 有严格冻结和 RunId 强校验，本次报 `FrozenExcludedChannelsRunIdentityMissing` | **V15 无此代码路径** |
| 最终现场结果 | 可局部自恢复，也可能局部组长期暂停等待人工操作 | 本次全局自恢复被阻断，最终人工重启软件 | **不相同** |

由此可见，V2.13.0.27 本次不是“134 ms 空窗单独导致程序无法重启”，而是短空窗依次击中了多个新增但尚未闭环的状态机接口。

### 4.2 与 V2.13.0.27 本次最接近的反证：12:49 事件

12:49 时，V2.13.0.15 同时出现了 251.9 ms 和 236.9 ms 的样本陈旧，明显大于 V2.13.0.27 本次首个约 134 ms 的短空窗：

- EPB5、EPB12 当前循环被中止；
- Dev2 随后记录约 239.6 ms 的 DAQ gap；
- 12:49:30～12:49:32，两个液压组重新进入正式周期；
- EPB4、EPB5、EPB11、EPB12 随后都产生了终态循环结果；
- 没有发生 `HydraulicBarrierTimeout`；
- 没有进入全局进程恢复；
- 没有退出程序，也不需要人工重启。

这组现场证据强烈支持：**若把 V2.13.0.27 本次最初的短空窗原样放到 V2.13.0.15，V15 大概率只损失当前循环，然后继续运行。**

### 4.3 12:56：V2.13.0.15 可以局部自恢复，但不是无条件

12:56 事件表面上也是 110～126 ms 触发，随后确认实际 DAQ 空窗约 1169.5 ms。V2.13.0.15 对 H1 的处理过程为：

1. EPB4/5 中止循环并请求电气组断能；
2. 两通道进入暂停/恢复状态；
3. 旧的覆盖检测持续报告 orphan；
4. 调度器仍执行受影响组重置；
5. 约 9 秒后 EPB4/5 报 `AffectedGroupResetRecovered`；
6. 两通道原子重新加入正式槽，继续运行。

这一事件说明 V15 的局部组重置有实际恢复能力；也说明它的恢复健康判定本身已经存在缺陷——日志中明明有 `GROUP-RESET...` 所有者，仍被报告 `TaskCovered=False`。

### 4.4 15:00：V2.13.0.15 同样会失去持续运行能力

15:00 时，Dev1 实际空窗约 1966 ms，Dev2 约 848.5 ms。日志同时显示：

- 电源电流为新鲜的 `0.000 A`；
- 电源输出状态仍为 `Output=True`；
- 系统仍持有 09:51 遗留的 `EmergencyPowerGroupLatch`；
- 新请求没有成功选出新的恢复所有者；
- EPB4/5 长期停留在暂停状态，EPB11/12 继续运行。

操作人员单通道继续无效，直到 15:05 执行一次“批量暂停—继续”，EPB4/5 才在约 1 秒后恢复。之后每个通道继续完成约 376 个成功循环，直到正常结束。

这表明：

- 硬件不是永久故障；
- V15 避免了本次 V27 的全局退出，但可能把故障固化为局部组永久暂停；
- V15 的“没有触发全局自动重启”不能等同于“稳定运行”；
- 回退 V15 只会改变故障形态，不会消除根因。

## 6. 控制逻辑差异

### 6.1 两版共有的 100 ms 硬切断

V2.13.0.15 和 V2.13.0.27 的 `EpbAdaptiveControl` 都直接判断：

```text
DaqSampleAge > 100 ms  =>  DaqSampleStale>100ms
```

上层收到 recoverable fault 后立即执行 Motor Off 并中止当前循环。问题在于：系统虽然配置了 Warn=100 ms、Suspect=1000 ms、Trip=2000 ms 三档，却在真正的动作执行器中绕过分级策略，把 Warn 值直接当成硬截止。

因此两版都存在“短暂调度抖动/DAQ 空窗被放大为控制故障”的共同根因。

### 6.2 V2.13.0.27 新增机械重新确认，使通道更容易错过下一槽

V2.13.0.15 在 DAQ 恢复新鲜后，可以较快重新参加后续正式周期。

V2.13.0.27 在每次 DAQ freshness cutoff 后新增了 `RequireDaqMechanicalRequalification`，重新加入前需要完成：

1. DAQ 连续新鲜约 500 ms；
2. 电源准备状态确认；
3. 电机/机构释放确认；
4. 清除重新确认标记。

安全意图本身合理，但它和正式槽参与者快照没有形成原子协议。本次现场中，H1 正式槽快照已经包含 EPB4/5，EPB4 却仍在重新确认，没有进入屏障；H1 随后等待 EPB4 直到屏障超时。

### 6.3 V2.13.0.27 从“分组独立周期”改成“跨液压组全局正式槽”

V2.13.0.15：

- H1、H2 各自计算下一个正式槽；
- 各自获取本组液压租约；
- 一组异常通常不阻断另一组当前周期。

V2.13.0.27：

- 新增全局正式参与者快照；
- H1、H2 进入同一个全局液压槽；
- 使用统一电机锚点；
- 一个组未完成屏障时，健康组也会跳过/等待同一个全局槽。

这提高了同步性，但扩大了故障域：一个通道的短空窗可以从单通道扩散到液压组，再扩散到整批正式周期。

两版的参与者快照都缺少明确的 `SkippedForSlot`/退出墓碑协议，理论上都可能等待“快照里有、实际不会到达”的成员；但 V15 现场 8 次 cutoff 没有出现屏障超时，而 V27 新增的重新确认和全局槽使这个潜在问题真正被触发。

### 6.4 恢复所有者模型：V15 判断粗糙，V27 类型更强但映射错误

V2.13.0.15 的问题：

- 是否有恢复覆盖，优先只看任务注册表；
- 即使 `_recoveryOwnership` 中存在 `GROUP-RESET...` 所有者，只要任务表没匹配到，仍返回 `TaskCovered=False`；
- 实际现场反复产生 orphan 错误日志；
- 但孤儿动作仍倾向执行“受影响组 Stop→Start”，所以 12:56 最终恢复成功。

V2.13.0.27 的变化：

- 新增 `RecoveryOwnerKind`、`RecoveryTargetPhase` 和恢复事故协调器；
- 恢复任务在任务表中可能已经存在，即 `TaskCovered=True`；
- 但失败键的阶段先被覆盖为 `Recovery`，随后又被错误推断成 `BatchStartup/Startup`；
- 实际故障发生在 Formal 阶段，类型化所有者和目标阶段由此不一致；
- 动作选择器没有把这种组合降级为局部组重置，而是落入 `FailSafeTerminal`；
- 结果是把真实存在的恢复任务终止，并把整批状态升级为 `SystemFault`。

可以概括为：

> V15 是“有 owner 但看不见 task”，V27 是“看得见 task 但 owner/target 身份映射错误”；V15 多报警后重置局部组，V27 则把误判升级为全局终止。

### 6.5 两版都没有利用“已经可靠断能”抑制重复恢复

两版都会读取电源输出电流用于日志和判断，但当 DAQ 样本陈旧时，仍无条件申请电气组紧急停机。

V15 和 V27 现场都出现过以下组合：

- 数字输出关断动作已经成功；
- 电源遥测新鲜；
- 电流为 `0.000 A`；
- 系统仍继续堆叠 EmergencyPowerGroupLatch 和恢复请求。

这使一次已经完成的安全动作继续污染后续所有权状态。对于“力大砖飞、持续运行”的目标，应当把“确认断能”作为终止重复升级的充分证据，而不是只记录不用。

### 6.6 固定 30 秒进程内恢复在两版中相同

V2.13.0.15 和 V2.13.0.27 都使用固定 30 秒等待进程内恢复。

V15 的 8 次现场 cutoff 没有走到这一层，因此没有暴露本次结果；V27 因为前面的 FailSafeTerminal 进入该层，30 秒到期后切换恢复代际，恰好中断仍在执行的学习流程，最终把四个已选通道全部学习隔离。

所以 30 秒风险不是 V27 新增，只是 V27 的前置控制链第一次把系统稳定地送进了这个风险点。

### 6.7 Watchdog：V15 更宽松，但当次监督实际上已失活

V2.13.0.15 Watchdog 会从最后心跳直接计算排除通道，然后尝试重启：

- 不要求非空 RunId；
- 没有冻结排除通道意图；
- 不存在 `FrozenExcludedChannelsRunIdentityMissing`；
- 因而不可能出现 V27 本次完全相同的最终 DetailCode。

但 V15 当次会话只更新到启动后不久：

- Session：`session-0ada3ac0a79a448a98efc71408dbd640.json`
- 最后心跳序号约 14；
- 最后阶段仍停留在 Learning；
- 主程序实际上继续运行到 16:40。

这说明 V15 的主程序—Watchdog 通信/监督很早就已经停滞。它没有在后续事故中拉起进程，不能证明 V15 的恢复策略更好，只能说明当次 Watchdog 没有持续掌握真实状态。

V15 的宽松策略还可能带来另一类错误：使用陈旧心跳或污染后的排除通道列表启动新进程，甚至把所有通道都排除。V27 引入持久化会话和严格身份校验是正确方向，但本次冻结时机晚于运行身份清理，又没有可靠回退，因此从“可能带错参数重启”变成了“明确拒绝重启”。

## 7. 将本次约 134 ms 根因放到 V2.13.0.15 的反事实路径

在假定 DAQ 只短暂陈旧约 134 ms、随后恢复，且没有再叠加 1 秒以上长空窗的情况下，V15 最可能按以下顺序运行：

```text
DAQ 样本年龄超过 100 ms
        ↓
当前通道 Motor Off
        ↓
中止当前循环，记录 DaqSampleStale>100ms
        ↓
DAQ 样本恢复新鲜
        ↓
无需执行 V27 新增的机械重新确认
        ↓
通道参加本液压组下一次独立正式槽
        ↓
继续 15 秒周期运行
```

因此不会自然出现以下 V27 专属链条：

```text
重新确认导致槽成员缺席
→ 全局液压屏障超时
→ Recovery 被误映射为 BatchStartup
→ 真实恢复任务被 FailSafeTerminal 误杀
→ 30 秒恢复代际切换
→ 全通道学习隔离
→ 清理 RunId
→ Watchdog 冻结排除通道时发现 RunId 缺失
→ 拒绝重启
```

但如果“同样的根因”是指更宽泛的 DAQ 不连续，而不是严格限定为 134 ms，则 V15 仍有两种可能结果：

- 空窗扩展到约 1 秒：触发局部组重置，可能在数秒内恢复；
- 空窗叠加旧紧急停机锁存/所有者状态：受影响组可能长期暂停，需要人工批量暂停—继续。

## 8. 对稳定版本方案的启示

### 8.1 不建议直接回退 V2.13.0.15

V15 的可取之处是故障域较小、短空窗后重新加入更直接；但它同时存在：

- 同样的 100 ms 硬切断；
- 恢复任务覆盖误判；
- EmergencyPowerGroupLatch 残留；
- 局部组可以永久暂停；
- 固定 30 秒恢复风险；
- Watchdog 心跳早停；
- 人工停止流程曾出现阻塞风险。

直接回退只会把“全局退出”换成“局部假死或无人监管”，不符合持续运行目标。

### 8.2 应保留 V27 的安全能力，但把故障升级链改成“宽进严出”

建议以 V2.13.0.27 为基线修复，而不是撤销全部新增机制：

1. **100 ms 只做短周期保护，不做系统级故障升级。**  
   允许立即 Motor Off 和中止当前循环，但 100 ms 内不得触发组重置、全局恢复或进程重启；持续空窗达到 Suspect/Trip 阈值后再逐级升级。

2. **真正使用 100/1000/2000 ms 分级。**  
   - 100 ms：通道级当前循环保护，自动重试；
   - 1000 ms：局部组暂停/重新确认；
   - 2000 ms：DAQ 重启或局部组重置；
   - 只有重复失败或硬件断能无法确认时，才进入进程级恢复。

3. **确认断能后立即封顶，不重复堆叠故障。**  
   当 DO Off 成功且新鲜 PSU 电流 `<0.1 A` 时，确认电气安全已经达成，清理重复 latch/request，只保留诊断记录和自动重试。

4. **正式槽参与者必须有原子加入/退出协议。**  
   重新确认中的通道不能先进入槽快照；如果快照后退出，必须写入 `SkippedForSlot`/tombstone，使屏障立即收敛。屏障超时应跳过本槽并进入下一槽，不能直接升级全局 SystemFault。

5. **Formal 恢复不得通过临时 `Recovery` 阶段反推为 Startup。**  
   在创建恢复事故时一次性保存 `OriginalPhase=Formal`、目标组、代际和任务 ID；后续健康检查只使用该不可变上下文。

6. **任务存在且持续报告进度时，不得被 orphan 清理器终止。**  
   `TaskCovered` 与 owner/target 一致性应分开诊断。身份字段异常时先修复/接管元数据，不能直接杀掉仍在工作的恢复任务。

7. **30 秒改为进度看门狗，不是绝对截止。**  
   有新鲜心跳、阶段推进或硬件状态改善时自动续期；只有完全无进展且超过硬上限才切换代际。旧代际退出要与新代际学习隔离解耦。

8. **Watchdog 在清理前冻结完整重启上下文。**  
   RunId、选中通道、允许排除通道、配置哈希和恢复原因必须在主程序清理状态前持久化；RunId 缺失时优先使用已验证的持久会话身份，不能因为一个晚到的空字段直接拒绝重启。

9. **禁止“全部已选通道都被排除”后静默重启。**  
   这种情况应先尝试清除仅由恢复代际产生的临时隔离，再按原选择通道启动；只有明确的永久硬件故障通道才能进入冻结排除列表。

### 8.3 “力大砖飞”的正确落点

目标不是取消 Motor Off 等电气保护，而是限制误升级：

> 短空窗可以损失一个循环，但不能损失一个液压组；局部恢复失败可以损失一个组，但不能因为元数据不一致杀死有效恢复任务；进程恢复可以重启软件，但不能因为 RunId 在清理阶段变空而放弃重启。

这能同时保住硬件安全底线和长时间无人值守能力。

## 9. 必须补充的回归场景

| 场景 | 期望结果 |
|---|---|
| 单通道 80 ms DAQ 空窗 | 不切断，不影响正式槽 |
| 单通道 120～300 ms 空窗 | 最多中止当前循环；下一槽自动参加 |
| 两个 DAQ 设备同时 120～300 ms 空窗 | 不触发全局恢复；两个液压组下一槽继续 |
| 800～1500 ms 空窗 | 只暂停/重新确认受影响组；健康组持续运行 |
| 超过 2000 ms 空窗 | 允许 DAQ 或局部组重置；恢复后自动重入 |
| DO Off 成功且 PSU 新鲜电流为 0 A | 不重复申请电气组紧急停机，不污染 owner/latch |
| 正式槽快照后某成员进入重新确认 | 该成员明确 `SkippedForSlot`，屏障立即收敛 |
| `Phase=Recovery` 但原始阶段为 Formal | 恢复目标保持 Formal，不得映射为 BatchStartup |
| 恢复任务存在但 owner 元数据暂时不一致 | 记录并修复元数据，不终止活动任务 |
| 30 秒时任务仍有进展 | 自动续期，不切换恢复代际 |
| 学习过程中发生恢复代际切换 | 不把所有已选通道永久学习隔离 |
| 主程序清理后 RunId 为空 | Watchdog 使用清理前持久化身份完成重启 |
| 冻结排除列表包含全部已选通道 | 清理临时隔离并保留至少一个可运行通道；禁止空跑 |
| Watchdog 管道/心跳停止更新 | 独立检测监督链失活并自建新会话，不依赖主程序继续报告 |

通过标准不应只看“没有崩溃”，而应至少连续运行 24～72 小时，并确认：

- 注入短空窗后只损失预期的当前循环；
- 没有 `HydraulicBarrierTimeout` 放大；
- 没有活动恢复任务被 orphan 清理器误杀；
- 没有通道因一次瞬态故障永久暂停；
- 进程级故障后 Watchdog 能在无人工操作下恢复到原运行集合；
- 故障日志能够明确区分“通道保护、局部组恢复、进程恢复、Watchdog 重启”四个层级。

## 10. 最终判断

| 问题 | 判断 |
|---|---|
| V15 是否存在同一个 100 ms 直接根因？ | **是** |
| V15 是否会中止当前循环？ | **是** |
| 约 134 ms 空窗是否大概率让 V15 无法继续？ | **否；现场更严重短空窗后已继续运行** |
| V15 是否会出现 V27 本次完全相同的最终链路？ | **不会；缺少多项 V27 新增机制和最终 DetailCode** |
| V15 是否足够稳定，可直接回退？ | **否；会出现局部组长期暂停和 Watchdog 监督失活** |
| 两版差异主要来自参数吗？ | **否；关键参数基本一致，差异主要在控制状态机** |
| 推荐方向 | **以 V27 为基线，保留安全动作，拆断误升级链并强化自动续跑** |

最终建议不是选择“V15 或 V27 哪个问题更少”，而是把 V15 的局部故障隔离和快速重入特点，与 V27 的持久恢复、身份校验能力正确组合起来，并补齐槽成员退出、恢复所有者、断能证据和 Watchdog 冻结时序四个闭环。
