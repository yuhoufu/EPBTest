# V2.13.0.15 长稳运行 EPB4/5 自行暂停未恢复与 V2.13.0.25 复发风险分析

> 分析日期：2026-08-26  
> 现场封盘：`D:\EPB_Data\10358-029a_V2.13.0.15_0826_1640`  
> 现场程序：V2.13.0.15，PID 7888，RunId `f4f203ee6b574d25946ba1a4a476b3f9`  
> 对比版本：当前仓库 HEAD `dd7fc83`，程序集版本 V2.13.0.25  
> 文档性质：根因分析、V2.13.0.25 复发风险判定、修复与验收方案；**本次未修改生产代码**

## 技术结论

**V2.13.0.25 仍存在与本次相同或高度相似的“安全暂停后不自动恢复”风险，当前不能判定为已经解决。**

更准确地说：

1. EPB4/5 的自行暂停是程序在 Dev1 DAQ 回调中断时执行的**正确失效安全动作**，不是卡钳机械卡死或过流报警。15:00:24 前后 Dev1 回调最终形成约 **1.966 秒**空窗，程序在样本超过 100ms 时先关闭 EPB4/5 DO，并关闭电源组 2。
2. 真正缺陷发生在断电之后。09:51 的较早事故已建立电源组 2 联锁 `a773be...`；虽然 EPB4/5 在 09:51:56 自动清场并恢复运行，但联锁对象没有在该成功终态被清除。12:56 和 15:00 的新事故仍被当作同一个旧事故的第 4～9 次重复请求。
3. 15:00 的新请求虽重新执行了安全断电，却没有重新建立恢复 owner。DAQ 回调在 15:00:26 恢复后，EPB4/5 的 Timer 已停在 `Paused`，但没有任何任务负责重新上电、机械释放复核和共同节拍重入，所以不会自行恢复。
4. EPB4/5 的单通道 RUN/STOP 恢复在 15:04:37 和 15:05:02 均被程序拒绝，因为系统安全暂停没有写入“人工安全暂停”时间戳；现有入口仍只接受人工优雅暂停产生的 `_channelPausedUtc`。
5. 操作员执行“暂停全部卡钳→继续试验”后，批次暂停流程补齐人工暂停边界，继续流程重新接管电源并重建 EPB4/5 Timer，故在 15:05:23 恢复。之后 EPB4/5 各新增 **376 个正式圈终态**，直至 16:39 正常运行，排除了卡钳 4/5 的持续性机械或电气硬故障。

V2.13.0.25 已增加执行许可栅栏、恢复 owner 和 DAQ 后机械复核，安全性优于 V2.13.0.15；但是：

- `EmergencyPowerGroupLatch` 在 V2.13.0.15 与当前 V2.13.0.25 之间**没有代码差异**；
- 受影响组 `AffectedGroupResetRecovered` 成功路径仍未清除所属电源组的 emergency latch；
- 重复请求仍由 `ShouldPublishNonDaqFault` 一次性门禁决定是否启动电源恢复，未检查“旧 latch 尚在、恢复 owner 已不存在”的不变量；
- 单通道恢复仍要求 `_channelPausedUtc + Timer + Runner` 三项同时存在，现场报错逻辑原样保留。

因此，本问题的发布判定是：**代码级复发路径未关闭，V2.13.0.25 不应仅凭版本升级直接投入无人值守长稳试验。**

## 3. 根因链

### 3.1 直接触发：DAQ 回调短时中断

当天日志共记录 8 次 `DAQ_FRESHNESS_SAFETY_CUTOFF`：

| 时间 | 设备/通道 | 截止时 CallbackAge |
|---|---|---:|
| 09:51:48 | Dev1 / EPB5 | 112.0ms |
| 12:49:24 | Dev1 / EPB5 | 251.9ms |
| 12:49:24 | Dev2 / EPB12 | 236.9ms |
| 12:56:02 | Dev1 / EPB5 | 110.6ms |
| 12:56:02 | Dev1 / EPB4 | 126.4ms |
| 15:00:24 | Dev1 / EPB4 | 110.2ms |
| 15:00:24 | Dev1 / EPB5 | 110.9ms |
| 15:00:25 | Dev2 / EPB12 | 110.0ms |

15:00 最终观测到 Dev1 1.966 秒、Dev2 0.848 秒回调空窗。两个 DAQ 设备在相近时段都受影响，更像采集/调度链的公共短暂停顿，不支持“只有 EPB4 或 EPB5 卡钳本体异常”。

V2.13.0.15 的策略是：样本超过 100ms 时立即关闭当前电机并作废本圈，但只有独立存活监督连续达到门槛才重建 DAQ。日志明确写出：

```text
Action=MotorOffAndAbortCurrentCycle;
DaqRestart=false;
EscalationOwner=DaqLivenessSupervisor
```

该快速切断策略本身正确；问题是回调恢复后没有一条必达事务负责把“已安全暂停的正式通道”重新纳入运行。

### 3.2 第一根因：成功的受影响组清场没有清除电源联锁

电源组联锁对象由 [EmergencyPowerGroupLatch.cs](../Controller/EmergencyPowerGroupLatch.cs#L34) 保存。每个组只有一个活动 Entry，其中包括：

- 原始 CorrelationId；
- StartedUtc；
- RequestCount；
- `NonDaqFaultPublished` 一次性标志。

V2.13.0.15 到当前 V2.13.0.25 之间，该文件没有任何差异。

正常电源自愈或完整 DAQ 恢复成功时，会在 [EpbManager.cs](../Controller/EpbManager.cs#L6765)、[EpbManager.cs](../Controller/EpbManager.cs#L9494) 清除 latch；但更高层 [ExecuteAffectedGroupResetAsync](../Controller/EpbManager.RecoveryCoordination.cs#L1346) 在 `AffectedGroupResetRecovered` 成功并重新加入通道后，只记录成功并释放恢复 lease，**没有清除涉及的电源组 latch**。

09:51 的现场顺序正好命中该遗漏：电源恢复先移交，高层清场后成功重入，于是通道恢复了，电源组 2 的旧 latch 却一直留在内存中。

### 3.3 第二根因：重复安全请求重新断电，但不重新选恢复 owner

[RequestElectricalGroupEmergencyShutdown](../Controller/EpbManager.cs#L11386) 仍采用以下门禁：

1. 注册或复用电源组 latch；
2. 每次请求都重新执行 DO OFF 和电源 OFF；
3. 只有 `registration.ShouldPublishNonDaqFault=true` 时才发布故障并调用 `BeginPowerSupplySoftwareRecovery`。

`ShouldPublishNonDaqFault` 在同一 latch 生命周期内只会成功一次。09:51 已经消费该标志，15:00 的第 6～9 次请求只能重复安全断电，不能重新建立恢复任务。

代码没有在该分支检查：

```text
latch 存在
AND 当前没有 Power/DAQ/Group recovery owner
AND 通道 Timer 因 ElectricalGroupEmergency 停在 Paused
```

这是本次“安全动作完成，但无人负责恢复”的核心不变量缺口。

### 3.4 第三根因：DAQ 派生判定依赖预先存在的事故 latch

[EpbManager.cs](../Controller/EpbManager.cs#L11403) 将联锁归类为 DAQ 派生，需要同时满足：

```text
reason 包含 OffCurrentUnverifiableDaqStale
AND _daqIncidentLatch.TryGet(...) 成功
```

本次 100ms 快速截止明确选择 `DaqRestart=false`；通道断电后，独立存活监督只记录 `ObservedUnenergizedGap`，且日志为 `RecoveryActive=false`。因此没有可供 `TryGet` 的活动 DAQ 事故，最终明明由陈旧 DAQ 样本触发，却被记录成 `DaqDerived=False`。

这使本应由 DAQ 截止事务完成的“新鲜度复核→电源复核→机械释放→共同节拍重入”，退化成一次普通电源联锁；而普通电源联锁又被旧 latch 去重，故恢复链完全断开。

### 3.5 为什么单通道恢复失败、批次暂停再继续却成功

[ResumePausedChannelAsync](../Controller/EpbManager.PauseResume.cs#L408) 在 V2.13.0.15 与当前 V2.13.0.25 中使用相同准入条件：

```csharp
if (!_channelPausedUtc.TryGetValue(channel, out _) ||
    !_timers.TryGetValue(channel, out var timer) ||
    !_runners.ContainsKey(channel))
    throw new InvalidOperationException(
        $"EPB[{channel}] 不处于可恢复的安全暂停状态。");
```

`_channelPausedUtc` 只由人工单通道优雅暂停或批次优雅暂停写入。`ElectricalGroupEmergency` 只暂停 Timer，不写人工暂停时间戳，所以 EPB4/5 界面虽然显示“暂停”，单通道继续入口仍必然拒绝。

批次暂停流程会对 4/5/11/12 重新完成全断能、持久化边界并统一写入暂停时间戳；随后批次继续入口重新做 DAQ、电源、机械和共同节拍预检，并替换旧 Timer。因此操作员的“暂停全部→继续”能够恢复。

## 4. V2.13.0.25 是否已经解决

### 4.1 版本差异判定

| 控制点 | V2.13.0.25 状态 | 对本问题的作用 |
|---|---|---|
| 100ms DAQ 陈旧样本立即断电 | 保留 | 正确安全行为，仍会出现“自行暂停”表象 |
| DAQ 截止后的机械重新资格确认 | 已增加 `RequireDaqMechanicalRequalification` | 防止未经机械复核直接重新上电，提升安全性 |
| 通道执行许可与恢复 owner | 已显著加强 | 降低旧任务串圈、无 owner 的 `Recovering` 被覆盖等风险 |
| emergency latch 数据结构 | 与 V2.13.0.15 完全相同 | 旧关联仍可无限残留 |
| `AffectedGroupResetRecovered` 后清 latch | 仍缺失 | 本次 09:51→15:00 的前置条件仍可形成 |
| 重复联锁但 owner 缺失时重新选主 | 仍缺失 | 新事故仍可能只断电、不恢复 |
| DAQ 陈旧原因无事故上下文时补建恢复事务 | 仍缺失 | `DaqDerived=False` 路径仍存在 |
| 系统安全暂停的单通道恢复 | 准入条件未变 | 仍会报“不处于可恢复的安全暂停状态” |
| 批次暂停→继续 | 仍可重建 Timer | 仍是目前现场可用的人工恢复手段 |

### 4.2 最终回答

**会有复发风险，而且是代码结构上尚未关闭的高置信风险。**

并不是每一次 100ms DAQ 抖动都会卡住：如果已经建立有效 DAQ 恢复事务，或电源恢复 owner 能正常完成并清 latch，程序可以自动续测。但只要出现以下组合，V2.13.0.25 仍可能重现：

```text
较早一次联锁由更高层 AffectedGroupReset 成功恢复
→ 电源组 emergency latch 残留
→ 后续 DAQ 回调空窗发生在通道带电/断电确认窗口
→ 新请求复用旧 latch 且不再发布恢复 fault
→ Timer 因安全联锁进入 Paused
→ 没有恢复 owner，单通道继续又因缺少人工暂停时间戳被拒绝
```

V2.13.0.25 的新增保护可能使失效更安全，但不会自动补齐缺失的恢复所有权。因此不能将“安全停住”误写成“问题已解决”。

此外，V2.13.0.25 还存在独立的启动定位重试 `Recovering → StartBlocked` 问题，详见 [V2.13.0.15 强杀后 V2.13.0.25 启动即停根因分析与修复方案](./V2.13.0.15强杀后V2.13.0.25启动即停根因分析与修复方案-20260826.md)。两个问题都关闭前，不建议把 V2.13.0.25 作为无人值守正式版本。

## 5. 正式修复方案

### P0-1：让 emergency latch 具备完整终态，而不是永久去重标志

在所有能够代表事故恢复终态的出口统一清理所属电源组 latch：

- `DaqRecovery Terminal`；
- `PowerSupplySelfHealed`；
- `AffectedGroupResetRecovered`；
- 恢复所有权移交后的继任 owner 成功终态；
- 批次 Stop/新 RunEpoch 建立前的安全清场。

建议将 latch 与 `RunId + RunEpoch + CorrelationId + RecoveryOwnerId` 绑定，禁止跨事故、跨运行复用；终态清理必须有审计日志：

```text
EmergencyPowerGroupLatchReleased
Group=2
CorrelationId=...
Terminal=AffectedGroupResetRecovered
Owner=...
```

### P0-2：重复请求必须检查恢复 owner 是否真实存在

不能把“故障已经发布过”当成“恢复仍有人负责”。注册重复请求后增加原子不变量检查：

```text
if latch active
and no current recovery owner/task covers this group
and any enabled member is Paused/Recovering due to this incident
then re-elect/adopt a recovery owner
```

若旧事故已有成功终态但 latch 未清，应原子替换为新关联号并将 `RequestCount` 重置为 1；若旧事故尚未终态但 owner 丢失，应沿用原关联号执行 owner adoption，避免同时创建两个恢复事务。

### P0-3：100ms 快速截止也必须拥有“无需重建 DAQ”的恢复事务

当 `DaqFreshnessSafetyCutoff` 已导致电机关闭或断电电流无法确认时，应立即建立 DAQ 派生恢复上下文，不能要求 `_daqIncidentLatch` 预先存在：

- 回调仍陈旧：重建 DAQ；
- 回调已经恢复：`restartDaq=false`，但仍执行新鲜批次确认、持久化截止、电源复核、机械释放和共同节拍重入；
- 任一安全条件不满足：保持断能并升级有界恢复，不允许静默停在普通 `Paused`。

### P0-4：区分“人工暂停”和“系统安全暂停”的恢复凭证

不要简单放宽 `_channelPausedUtc` 检查，也不要仅凭 `timer.IsPaused` 就重新上电。应增加独立的系统暂停凭证，例如：

```text
SystemSafePauseReceipt
- RunId / RunEpoch
- Channel / ElectricalGroup
- CorrelationId
- MotorOffConfirmed
- PressureSafeConfirmed
- PersistenceBoundary
- DaqFreshGeneration
- RecoveryOwner / Terminal
```

单通道按钮发现系统暂停凭证时，应路由到“电气组/液压组安全恢复”入口，而不是走人工单通道 Resume；恢复前必须重新验证 DAQ、电源、压力和机械释放。

### P0-5：补充“Paused 无 owner”运行时不变量

当前监督重点覆盖 `Recovering`，本次却最终停在普通 `Paused`。增加定时检查：

```text
Timer.IsPaused
AND Timer.Reason starts with ElectricalGroupEmergency
AND no manual pause receipt
AND no recovery owner/task
AND age > bounded threshold
```

命中后应自动进入受影响组恢复；若连续有界重试失败，再交由 Watchdog 回收整批，不能无限等待，也不能自动忽略。

### P1：补齐 DAQ 回调空窗的底层诊断

在下一版记录下列同一单调时间轴证据，以定位 1～2 秒空窗来源：

- NI Task 状态、回调线程 ID、最后一次 `BeginRead/EndRead/Rearm`；
- .NET GC 暂停时间、线程池饥饿、进程挂起时间；
- Windows DPC/ISR、设备重置/总线错误和 NI 驱动事件；
- 两设备是否同一时刻停止回调；
- 主线程/UI/远程会话事件只作为相关性证据，不直接定性。

底层原因未定不影响 P0：软件必须保证任何可恢复 DAQ 空窗都不会留下无 owner 的永久暂停。

## 6. 修复前的现场处置

在新版本完成故障注入验收前：

1. 不建议让 V2.13.0.25 无人值守长稳运行。
2. 若出现“部分卡钳暂停、其他卡钳继续运行”，先确认暂停通道电流为 0、电源组已 OFF、压力已安全，保留日志和截图。
3. 不要反复点击单通道 RUN/STOP；当前系统安全暂停没有人工恢复凭证，重复点击不会建立恢复 owner。
4. 在硬件断能状态可信时，使用本次已经验证有效的“暂停全部→等待全部安全暂停→继续试验”。继续预检失败时不得强制上电，应停止并封盘。
5. 若批次暂停不能完成、断电/压力状态无法确认，或出现永久数据连续性空洞，应执行安全停止，不再尝试同进程恢复。

这只是临时运维绕行，不是软件修复。

## 7. 验收门禁

### 7.1 必须新增的自动化测试

1. `AffectedGroupResetRecoveredClearsEmergencyLatch`：高层清场成功后，相关电源组 latch 必须不存在。
2. `StaleEmergencyLatchWithoutOwnerReelectsRecovery`：构造旧 latch、删除 owner，再触发新故障，必须建立且仅建立一个恢复 owner。
3. `DaqFreshnessCutoffCreatesRecoveryWithoutRestartWhenFreshAgain`：回调恢复后不重建 DAQ，但必须完成机械复核和共同槽重入。
4. `SystemSafePauseCannotUseUnsafeManualResume`：系统暂停不能绕过安全预检；UI 必须路由到组级恢复。
5. `ElectricalEmergencyPausedWithoutOwnerIsDetected`：无 owner 超时必须自动恢复或有界升级，不能永久停留。
6. `NewIncidentAfterRecoveredTerminalGetsNewCorrelation`：上一事故终态后，新事故必须 `RequestCount=1` 且使用新关联号。

### 7.2 现场故障注入

对 Dev1 在 EPB4/5 不同动作阶段分别注入 120ms、300ms、1s、2s 回调空窗，每档至少 100 次，并覆盖：

- 正向上电；
- 反向释放；
- DO OFF 后断电电流确认窗口；
- 较早一次液压/电源恢复发生所有权移交之后；
- 人工批次暂停或恢复预检并发窗口。

每次必须同时满足：

- 100ms 门槛后及时断电，迟到 DO 完成不能重新上电；
- 当前圈只封存一次且不计正式完成；
- 回调恢复后只有一个恢复 owner；
- latch 在终态清除，新事故使用新关联号；
- DAQ、电源、压力、机械释放全部通过后才从未来完整公共槽重入；
- 10 秒内自动恢复，或在明确失败原因下有界升级；
- 不允许出现普通 `Paused + no owner + no manual receipt`；
- 单通道按钮不再显示无解释的“不可恢复安全暂停”。

### 7.3 长稳放行

修复版至少完成一次 24 小时 4/5/11/12 全通道长稳运行，并检查：

- 零个残留 emergency latch；
- 零个恢复 owner/task 不匹配；
- 零个超过门槛的 `ElectricalGroupEmergency Paused` 无 owner 状态；
- 所有注入事故均有唯一 CorrelationId、确定终态和完整审计链；
- 人工暂停、继续和停止均能在界面与 Watchdog 中闭环。
