## 3. 代码改动

### 3.1 DAQ `DoOffConfirmed` 重复阶段推进

涉及文件：

- `Controller/EpbManager.DaqRecoveryState.cs`
- `Controller/EpbManager.cs`

`AdvanceDaqRecoveryStage` 增加默认关闭的 `allowAlreadyCommitted`。只有调用方显式允许，且目标阶段为 `DoOffConfirmed`，同时满足以下三项时才直接幂等成功：

1. Controller phase gate 已为 `DoOffConfirmed`；
2. Controller 已发布进度已为 `DoOffConfirmed`；
3. 当前 `DaqRecoveryTransaction.Phase` 已为 `DoOffConfirmed`。

该返回不会重复发布 checkpoint、不会增加 `ProgressVersion`。正常 DAQ 恢复和自维护两处确认入口启用此模式。`PowerOffSubmitted` 等其他阶段、跳级、回退、SafeIdle、Terminal 和事务不一致仍按原严格规则拒绝。

### 3.2 ForceRelease 后旧液压 scope 精确退役

涉及文件：

- `Controller/EpbManager.BatchStart.cs`
- `Controller/EpbManager.cs`
- `Controller/HydraulicGroupCoordinator.cs`

每次恢复自愈的 `ForceReleaseAsync` 生成包含异常类型、尝试号、旧代次 Key 和唯一 Token 的精确 reason，并将同一 reason 传入新 Recovery 代次建立路径。

新增的旧 scope 退役只在以下条件全部成立时生效：

- 目标 scope 属于同一液压组；
- scope 尚未关闭；
- 对应旧 generation 已退出活动表；
- lease completion 已完成且为 faulted；
- base exception 为 `OperationCanceledException`；
- 异常文本与本次 `HydraulicForceRelease Reason=<精确 reason>` 完全一致；
- 管理器在调用前再次确认该通道 DO OFF。

仅恢复代次进入前和 scope 替换两处使用该路径。原因不匹配、组不匹配、活动 lease、其他异常或 ForceRelease/压力确认失败均不会被吞掉。

### 3.3 Recovery worker 保留真实终态原因

涉及文件：

- `Controller/RecoveryIncidentCoordinator.cs`

worker 同步异常、异步异常或返回空 Task 时，安全终态改为发布：

```text
RecoveryWorkerFailed:<BaseExceptionType>
```

详情包含 base exception message、IncidentId 和完整 Scope（run、epoch、owner、target、resource）。终态仍然提交并释放 owner，worker Task 继续 faulted，不允许失败通道复活。

### 3.4 硬件安全等待不再触发进程风暴

涉及文件：

- `MTTFTest.Watchdog/WatchdogHost.cs`
- `MTTFTest.Watchdog/WatchdogHostStopMonitor.cs`

只有以下证据同时成立时，`hardwareSafeIdle` 才为真：

- 当前恢复进程身份与 Journal 的 PID/start ticks 完全匹配；
- 进程存活，心跳年龄小于 5 秒；
- 未撤销会话、未人工停止、尚未进入接管；
- `RecoveryProcessSource` 为恢复进程；
- `HardwareUnavailable=true`；
- phase 精确为 `SafeIdleHardwareUnavailable`；
- `EnergizedChannelCount=0`；
- hardware fingerprint 非空；
- probe attempt 和 next probe UTC 均有效。

该状态只抑制“非活动 StopAll 的历史粘滞终态”再次派发重启。活动 StopAll、进程死亡、心跳超时、重新带电、证据缺失或人工停止仍保留原接管路径及单次派发门。

### 3.5 冻结恢复通道意图

涉及文件：

- `MTTFTest.Watchdog/WatchdogHost.cs`

Watchdog Journal 在 schema 4 内增加可选的冻结投影字段：冻结标志、排序去重的 `FrozenExcludedChannels`、来源 PID/start ticks、RunId 和 RunEpoch。wire protocol 与耐久授权记录格式不变。

首次接管只允许从身份匹配且 `RecoveryProcessSource=InitialProcess` 的主进程心跳计算：

```text
人工禁用通道 + 已完成通道 + 永久报警通道
```

空集合也必须通过冻结标志明确持久化。冻结结果必须在首个 launch intent 前同步写入 Journal；持久化失败会阻断恢复启动并进入耐久安全终态。后续恢复子进程即使把 1–12 全部报告为 disabled，也只能继续使用已冻结集合。Sidecar 重启从 Journal 恢复该集合；非法、重复、越界或来源身份不完整的冻结证据，以及已进入恢复代次却缺失冻结证据，均 fail closed。

每代实际使用的集合仍通过现有 `--exclude-channels` 写入 durable `LaunchArguments`，没有建立第二套授权协议。

### 4.3 Recovery

- 同步异常、异步异常和空 Task 均发布 `RecoveryWorkerFailed:*`；
- 终态详情包含 Incident 和 Scope；
- 不再出现 `RecoveryTerminalPublisherMissing`；
- 终态仍覆盖全部合同通道并释放 registry lease。

### 4.4 Watchdog 安全等待

- 完整证据的硬件安全等待不派发非活动 Stop 粘滞终态；
- 活动 StopAll 即使传入安全等待标志仍派发；
- 进程死亡和心跳超时仍派发；
- 重新带电、人工停止或硬件指纹缺失不能被识别为安全等待；
- 接管派发保持 once-only。

### 4.5 通道冻结

- 初始主进程集合排序去重并同步持久化；
- 空集合可冻结；
- 同步持久化失败阻断 launch intent；
- JSON 序列化/Sidecar 重载保留冻结身份和集合；
- 恢复子进程报告 1–12 全禁用不能污染原集合；
- 非法、重复、越界集合 fail closed；
- 恢复子进程来源或 Started 状态下缺失冻结证据 fail closed。

### 5.3 第二次独立复核（2026-08-27）

本次没有仅复用首次验收结论，而是按代码路径、失败边界、持久化重启和完整测试重新检查。未发现需要追加的源代码修正，结论如下：

- DAQ 幂等入口只存在于正常恢复和自维护两处，并且都位于真实 DO OFF 确认之后；只有 Controller gate、已发布进度和当前事务三方同为 `DoOffConfirmed` 才返回幂等成功，不增加版本，也不能放行跳级、回退、SafeIdle、Terminal 或事务阶段不一致；
- 液压旧 scope 的退役仍要求 DO OFF，同液压组、旧代次已退出、lease 已完成且 fault 为本次精确 `HydraulicForceRelease` 原因；`ForceReleaseAsync` 的释放输出或安全压力确认失败时，生产调用点不会携带完成原因进入退役分支；
- Recovery worker 的同步异常、异步异常和空 Task 都先提交 `RecoveryWorkerFailed:<BaseExceptionType>` 安全终态，终态未被权威状态观察时仍走原有强制 OFF 和 fail-closed 复核，owner 不会由失败通道复活；
- `SafeIdleHardwareUnavailable` 只抑制已非活动的 StopAll 粘滞终态。当前恢复进程死亡、心跳达到 5 秒、重新带电、活动 StopAll、人工停止、会话撤权或身份/探测证据不完整时均不能获得该抑制；普通 Watchdog 恢复策略在硬件预检失败时也不会因空恢复候选集合制造第二条重启路径；
- 冻结通道集合只从首个已验证 InitialProcess 心跳生成，并在首个 launch intent 前同步持久化；恢复子进程不能重写集合，Sidecar 重载继续使用原集合，非法或缺失证据保持 fail closed；正常新试验由 `StartSessionAsync` 创建新的 GUID Session，不会跨试验继承上一会话的冻结集合；
- 第二次重新执行 Debug x86、三个完整测试套件、Release Any CPU、8 个产物版本核对和 `git diff --check`，结果与 5.2 相同：`600/600`、`55/55`、`17/17`、两种构建均 0 error、版本均为 `2.13.0.27`、diff check 0 error；
- 首次尝试构建时普通 PowerShell 未加载 Visual Studio Developer 环境，因 `msbuild` 不在 PATH 而未启动编译；改用已安装 MSBuild 的绝对路径后完成上述全部验收。该项属于验收宿主环境，不是软件失败。

因此，V2.13.0.27 的软件因果链和回归边界再次确认关闭；“已修复到位”在当前文档中仍只表示软件静态/自动化验收通过，不等同于现场硬件长稳完成。
