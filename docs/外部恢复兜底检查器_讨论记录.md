## 第一轮：提出独立分钟级监督与重启续测

### 用户

当前已经有windows的任务计划程序分钟级的去监督程序，
我在想能否有一个独立的分钟级的任务计划程序去监督程序，当发现程序退出、或者长时间卡钳异常不能恢复，去停止杀掉所有进程，重新拉起程序，运行试验？

### 助手

**可以，而且适合作为“进程内自恢复也失效时”的最后一道兜底。** 你想解决的是：程序退出了能重新启动；程序虽然还在，但试验长时间没有进展，也能由外部接管恢复。

建议做成：**独立的分钟级监督任务＋有条件的整套软件重建＋试验恢复验证。** 不要仅根据“进程存在”判断正常，也不要发现超时就无条件杀掉所有相关进程、立即重新通电试验。

**1．分钟级任务怎样判断需要接管**

监督程序每分钟启动一次，检查完就退出，将连续异常次数和恢复阶段保存到磁盘。

| 检查结果 | 应采取的动作 |
|---|---|
| 主程序退出，之前处于允许无人值守恢复的试验状态 | 发起恢复 |
| 主程序存在，但业务进度超过该阶段允许的时间没有变化 | 连续确认后，发起恢复 |
| 程序正在自恢复，且恢复阶段持续推进 | 继续观察 |
| 程序一直声称“正在恢复”，但阶段超过期限没有推进 | 外部接管，升级到进程重建 |
| 用户主动停止、暂停，或者试验正常完成 | 不自动恢复试验 |
| 急停、明确硬件故障、安全条件未满足 | 保持停止，记录原因并报警 |

这里最关键的是：**监督“试验有没有真正推进”，而不只是“心跳还在不在”。**

例如记录最后有效采样时间、控制动作完成时间、试验周期编号、数据落盘进度，以及当前恢复阶段和进入时间。长时间保压等正常等待，需要按阶段设置期限，不能统一认定“两分钟没变化就是卡死”。

同时，**一次读不到状态文件只能说明状态未知，不能直接认定卡死。**

**2．确实卡死之后，可以强制结束进程，但要按顺序**

建议恢复流程为：

1. **取得唯一恢复权。** 与现有看门狗、升级维护任务互斥，避免两边同时杀进程、启动程序。
2. **保存恢复意图和故障现场。** 记录试验身份、最后可靠检查点、异常原因；日志或转储采集必须有时间上限。
3. **进入安全停止流程。** 优先请求停止输出、断能，并确认设备安全状态。
4. **限定时间等待退出。** 超时后，强制结束明确属于本次试验实例的主程序和必要子进程。
5. **按依赖关系重新启动。** 校验配置、设备连接和检查点，完成必要的重新学习与恢复准备，再恢复试验。
6. **验证恢复结果。** 只有采样、控制和试验进度重新推进，才能记为恢复成功；出现窗口或启动进程不算成功。

需要注意：Windows 强制终止进程不会执行正常的退出清理，也不会自动终止其所有子进程。因此，**“进程已经杀掉”不能证明输出已经关闭或数据已经保存。** [Microsoft 进程终止说明](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process)

如果卡死进程占着设备句柄，必须先结束它才能重新接管设备，可以设计这条强制恢复路径；但必须有独立的断能保障，重新启动后也必须重新确认安全条件，不能直接继续输出。

**3．你说的“杀掉所有进程”，建议改成“重建本次试验的软件进程组”**

这个范围应通过程序路径、PID、启动时间和本次运行标识确定，避免误杀其他实例。

尤其不要同时杀掉正在负责断能、安全确认和恢复授权的组件。确实需要连这些组件一起重启时，应先完成职责交接，并保证恢复状态已经持久化。

**独立监督的价值，就是主程序彻底卡住后仍然能执行；如果监督者也跟着一起被杀，恢复链条就断了。**

**4．现有分钟级任务怎么安排更合理**

**优先扩展现有外部监督能力，不必再增加一个拥有独立杀进程权限的看门狗。**

如果现有任务只检查监督服务是否存活，可以增加“业务进度是否超期、恢复流程是否卡住”的检查；也可以新增一个独立检查任务，但最终交给同一个恢复协调者执行重启。

任务计划建议采用 `IgnoreNew`，防止上次检查未结束时重叠执行；检查程序本身要有执行期限，恢复状态跨次保存。Windows 任务计划明确支持这种实例策略。[Microsoft 多实例策略说明](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-multipleinstancespolicy-settingstype-element)

此外应保留重启次数限制、退避等待，以及“主动停止后不再自动续测”的持久化标志，防止无限重启或用户刚停止就被拉起来。

**我的建议是实施这层兜底，不需要为它引入大型开源框架。** Windows 任务计划程序已经能提供独立运行的基础，真正需要补齐的是业务停滞判定、唯一恢复权、安全重建和恢复后的进度确认。

它能覆盖软件退出、死锁和恢复流程卡住；如果你说的“卡钳异常”是物理卡滞或设备故障，重启软件不能被当作故障已消除。分钟级监督负责恢复可用性，设备的实时安全保护仍应由更快且独立的机制承担。

## 第二轮：如何实现这一层

### 用户

如果要加上这一层，该如何实现，思路？

### 助手

**建议增加一个“外部恢复兜底检查器”：Windows 每分钟启动它一次，检查试验是否停滞，以及现有恢复机制是否仍在推进；确认恢复失效后，接管并重建程序运行环境。**

对于你的 EPB 项目，核心是补上两项能力：**判断“恢复已经卡住”，以及在原恢复组件失效时仍能完成接管。** 以下是建议设计，不代表当前版本已经实现。

**1．独立运行，但与现有恢复机制共享规则**

可以新增一个轻量的独立程序，例如：

`MTTFTest.RecoveryGuard.exe`

由独立的 Windows 任务计划每分钟执行一次。它不引用主界面、不初始化 NI、不直接参与日常试验控制，只负责检查和必要时接管。

建议职责如下：

| 层级 | 职责 |
|---|---|
| 主程序内部自恢复 | 处理局部采样、控制和任务异常 |
| 现有外部看门狗 | 处理主程序退出、失联，以及常规重启 |
| 新增分钟级兜底检查器 | 处理前两层未能恢复、恢复流程长期停滞、相关进程缺失 |

**正常情况下，新检查器只观察。** 只有超过约定期限、且没有实际恢复进展时，才取得恢复权。

现有分钟级任务与新检查器涉及同一组件的重启动作，应使用同一套互斥和恢复状态，避免互相干扰。

**2．先建立一份“能否续测”和一份“实际进度”记录**

不能只检查进程，也不能只检查日志有没有更新。建议分开保存：

| 记录 | 主要内容 | 用途 |
|---|---|---|
| 续测意图 | 运行标识、项目路径、是否允许自动恢复、人工停止/暂停、是否完成 | 判断退出后该不该恢复 |
| 业务进度 | 有效采样位置、控制步骤序号、各活动通道周期、持久化位置 | 判断试验是否真正推进 |
| 恢复进度 | 恢复事务编号、当前阶段、阶段进入时间、最后实际进展、阶段期限 | 判断自恢复是否卡住 |
| 进程身份 | PID、进程启动时间、程序路径、所属运行标识 | 精确识别需要处理的实例 |

其中：

- **续测意图必须持久化**，不能随着主程序退出一起丢失。
- **人工停止、正常退出、试验完成，要先可靠撤销续测意图。**
- 定时写一次“我还活着”，只能证明发布状态的线程还活着；业务进度必须由实际完成的工作更新。
- 对你的 12 通道系统，应检查**本次参与试验的通道和压力组**，避免一个通道仍在运行就掩盖其他通道停滞。
- 状态写入采用原子替换、保留备份；读取失败先重试，不能立刻判定需要强杀。

**3．用“阶段期限”判断卡死，不用一个统一超时**

例如：

| 当前状态 | 判断方法 |
|---|---|
| 正式试验 | 活动通道的采样、控制和周期是否按预期推进 |
| 正常保压或等待 | 是否超过该步骤允许的等待时间 |
| 程序启动、设备初始化、重新学习 | 是否超过对应阶段期限 |
| 自动恢复中 | 阶段是否推进，以及整个恢复是否超过总期限 |
| 人工暂停或试验完成 | 不因没有业务进度而触发续测 |

**恢复阶段有期限，整个恢复过程也要有总期限。** 否则可能在“初始化→失败→重试”之间不断循环，每次刷新时间，看起来一直在恢复，实际几个小时都没有继续试验。

分钟级扫描可以连续确认异常，避免一次短暂抖动触发重启。具体阈值应依据现有恢复流程的合理最长耗时设置，而不是直接固定为一分钟。

**4．接管必须有明确顺序，并允许原协调者已经卡死**

建议把接管做成可持久化的状态流程：

**确认停滞 → 取得恢复权 → 安全停止 → 清理旧实例 → 重新启动 → 校验续测条件 → 验证实际进展。**

关键实现点：

- **优先请求现有恢复协调者处理**，给它一个有限的响应和执行期限。
- 如果它不响应，或者接受请求后仍不推进，检查器可以升级接管，不能永远等待它批准。
- 接管时生成新的恢复代次；旧实例恢复响应后，不得继续执行之前的启动或控制命令。
- 结束进程前重新核对 PID、启动时间和路径，只处理属于本次运行的实例。
- 不同时结束负责断能、安全确认的组件；需要重建这些组件时，先完成职责交接。
- 重启通过现有的交互会话启动链路进入用户桌面，并防止主程序重复启动。

**仅靠一个互斥锁还不够。** 如果持锁进程卡死，外部接管仍会受阻。因此还需要恢复所有者身份、有效期限，以及接管后拒绝旧命令的机制。

对于设备控制，旧实例必须确认失去控制能力，新实例才能重新取得设备控制权。

**5．“重新运行试验”必须从可靠检查点恢复**

重新启动后，建议依次确认：

1. 本次试验仍然允许自动续测，没有新的人工停止或急停。
2. 旧实例已经退出，设备处于可确认的安全状态。
3. 配置、项目身份和已保存数据一致。
4. 从最后可靠检查点恢复；中断中的不完整周期明确标记，不计为完成。
5. 完成必要的设备初始化和重新学习。
6. 采样、控制步骤及持久化位置重新推进，才确认恢复成功。

**不要为了自动续测而清空故障标志、伪造数据已保存，或绕过安全确认。** 软件性故障可以在冷却后继续尝试；急停和未解除的硬件故障保持断能，并显示具体阻塞原因。

**6．检查任务本身也要能中断后继续**

每分钟启动一次，不意味着整套恢复必须一分钟完成。

检查器每次执行有时间上限，采用单实例运行；跨分钟的恢复通过持久化状态继续。例如本次已完成旧进程清理，下次应检查启动结果，而不是重新从强杀开始。

此外，重启次数和冷却时间也需要持久化，避免检查器每次启动都把计数清零。每次决策记录：

> 哪个通道或阶段停滞、停滞多久、谁接管、结束了哪个实例、为何允许或阻止续测、最终是否恢复进展。

这能直接回答你之前遇到的“明明有分钟级任务，为什么没有重新拉起”。

**实施上，我建议分三步：**

1. **先做只观察模式**：采集实际进度，记录“如果启用接管，此时会重启”，用现场运行验证误判。
2. **再启用异常退出后的补拉起**：先覆盖进程已退出、续测意图仍有效的明确场景。
3. **最后启用停滞后的强制重建**：验证主程序卡死、恢复组件卡死、旧实例迟到响应、人工停止与接管同时发生等场景。

这样新增的这一层才有独立兜底能力，同时不会把现有系统变成几个看门狗互相重启。**最先应该落地的是统一的进度记录和接管规则，随后才是“杀进程、拉程序”的执行代码。**

## 第三轮：与已有程序解耦

### 用户

这个外部恢复兜底检查器能否彻底和已有的程序解耦，避免互相影响，给出合适的方案

### 助手

**可以做到独立部署、独立运行，并尽量隔离故障；但要可靠地自动续测，就必须保留少量状态交互。**

对你的项目，我推荐：**独立检查器＋只读状态文件＋接管时的启动互斥。** 检查器不参与日常试验控制，也不依赖原看门狗批准接管。

以下是建议方案，尚未实施。

**1．先明确“解耦”到什么程度**

| 解耦目标 | 能否实现 | 建议 |
|---|---|---|
| 独立 EXE、独立目录、独立升级 | 可以 | 实现 |
| 不引用主程序、控制器、看门狗的 DLL | 可以 | 实现 |
| 主程序或看门狗卡死，不影响检查器执行 | 可以隔离多数进程级故障 | 实现 |
| 检查器退出、升级，不中断正常试验 | 可以设计实现 | 作为验收条件 |
| 完全不读取任何业务状态，还能识别人工停止、正常等待、异常停滞 | 无法可靠做到 | 保留最小状态契约 |
| 两套机制都能杀进程、拉起程序，却完全不协调 | 无法保证不冲突 | 必须有接管边界 |

例如，“用户正常关闭”和“程序崩溃退出”，从外部看到的都可能是**进程不存在**。没有可靠记录，检查器只能猜测。

同一台电脑上的两个程序也仍共享 Windows、磁盘和资源，不能隔离操作系统卡死或整机断电。

**2．部署完全独立，去掉现有 DLL 依赖**

我刚核对了仓库：现有健康检查脚本通过 `Add-Type` 加载安装目录中的 `MTTFTest.Watchdog.Protocol.dll`，再探测监督服务。因此，检查脚本与被检查程序存在文件和版本依赖。[现有检查脚本](https://github.com/yuhoufu/EPBTest/blob/codex/i0046-v2.17.2.0/Tools/Test-MTTFTest-RecoveryHealth.ps1)

新方案建议：

| 项目 | 建议设计 |
|---|---|
| 程序 | `MTTFTest.RecoveryGuard.exe` |
| 安装位置 | 独立于主程序的 `Current` 版本目录 |
| 依赖 | Windows 接口和自身运行库，不加载业务 DLL、NI 驱动 |
| 配置 | 独立配置监控对象、允许操作的进程和超时 |
| 运行记录 | 独立保存观察记录、重启次数、冷却时间、接管事务 |
| 升级 | 与主程序分别升级，通过状态格式版本保持兼容 |

这样，主程序换包或某个业务 DLL 损坏，不会直接导致检查器无法启动。

**3．正常运行时，只单向读取，不互相等待**

主程序向外发布一份很小的状态快照，检查器只读：

| 状态类别 | 最少需要的信息 |
|---|---|
| 运行身份 | 本次运行标识、进程身份 |
| 续测意图 | 允许恢复、人工停止、暂停、完成 |
| 业务进度 | 活动通道的采样、控制和持久化进度 |
| 当前阶段 | 正式试验、保压、学习、恢复等，以及阶段期限 |

**不需要把内部所有恢复状态机、错误码和对象结构暴露出去。** 检查器只关心“是否应该运行、是否正在推进、允许等待多久”。

为避免检查器反过来影响试验：

- 状态发布不在采样和控制线程中同步写盘，采用有界后台发布。
- 文件采用原子替换；检查器短暂读取后立即关闭。
- 检查器不打开试验数据库做长时间查询，不扫描大量日志。
- 状态发布异常有明确记录，但不能把异常直接传播到控制线程。
- 文件损坏、格式不兼容或一次读取失败，判为“信息不足”，不能立即强杀。

**续测意图要比普通进度快照更严格。** 人工停止必须可靠撤销恢复授权；检查器每次启动、续测前都重新核对，不能长期沿用缓存中的“允许恢复”。

**4．真正需要协调的地方，缩小到“谁有权重建程序”**

这里建议保留一个很小的接管协议：

> 正常情况下，现有恢复机制负责处理。外部检查器确认超过恢复期限后，取得独占重建权；重建期间，其他机制不得另行拉起实例。

检查器不必依赖旧看门狗回应。具体顺序如下：

1. **持久化接管事务**：记录运行标识、接管原因、恢复代次、准备处理的进程。
2. **建立启动禁入窗口**：现有看门狗、分钟级任务和其他自动启动入口暂时禁止创建新实例；断能和停止动作仍然允许。
3. **重新核对状态**：确认试验没有恢复进展，也没有新发生的人工停止或维护操作。
4. **执行安全停止和旧实例清理**：必要时强制终止确切属于该运行的进程；确认旧实例退出、设备安全后才允许下一步。
5. **启动唯一的新实例**：通过规定入口启动，仍由试验程序验证检查点和续测条件。
6. **确认业务恢复后交还控制权**。

**仅创建一个锁文件是不够的。所有能自动拉起程序的入口，都必须遵守它。** 已经在进行中的启动也要纳入互斥，避免“检查时没有进程，下一刻两边都启动”。

这就是必须保留的少量耦合：**统一进程重建的所有权，不共享整套恢复实现。**

接管记录也不能简单设置“超时自动删除”。检查器如果执行到一半退出，下次应根据事务继续核对和收尾，避免旧实例还没清干净就恢复其他启动入口。

另外，现有 `maintenance-inhibit.json` 属于安装维护流程。建议为外部接管建立单独、明确的记录，维护禁止始终优先；不要直接复用或自动清除安装维护标志。[现有安装维护逻辑](https://github.com/yuhoufu/EPBTest/blob/codex/i0046-v2.17.2.0/Tools/Install-MTTFTest-Unattended.ps1)

**5．分钟级调度与恢复执行分开考虑**

建议任务计划每分钟运行检查器，采用 `IgnoreNew` 防止自身重叠，并为单次执行设置期限。跨分钟的恢复依靠持久化事务继续，而不是要求所有操作一分钟内结束。[Windows 多实例策略](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-multipleinstancespolicy-settingstype-element)

同时注意你的主程序是桌面应用：

- 检查器可以用 SYSTEM 身份检查服务和管理进程。
- 主界面应通过指定用户的交互会话入口启动。
- 没有合适用户会话时，记录“等待会话”，不能把后台启动了一个进程当作恢复成功。

Windows 服务运行于 Session 0，不能直接按普通桌面程序方式与用户交互。[Microsoft 交互服务说明](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)

**6．如果坚持“主程序一行不改”**

可以先做**纯外部观察版**：检查进程、窗口响应、现有数据进度和事件日志，输出异常报告。已有状态文件如果足够可靠，也可以通过外部适配器读取，但仍然存在文件格式依赖。

要直接开启“判定卡死→强杀→自动续测”，则必须证明现有接口已经能够提供续测意图、安全条件和启动互斥。否则，零改动方案无法可靠区分人工停止，也无法保证不与原看门狗冲突。

**我的推荐是：代码和部署充分独立，只保留“只读状态＋独占接管”两处稳定接口。** 验收时重点验证三件事：检查器被结束时试验照常运行；原恢复组件全部失去响应时它仍能接管；人工停止与接管同时发生时绝不自动续测。

## 第四轮：状态快照的时效性与旧试验禁止误恢复

### 用户

主程序向外发布一份很小的状态快照 ，很合理；但必须也得有时效性，不能前一个试验很久之前的状态终止，然后台架一直歇着没做，又给恢复起来；

### 助手

**对，这个约束必须加：旧状态不能成为重新启动试验的依据。** 尤其是台架闲置、电脑重启、检查器重新安装后，不能读到以前的“运行中”就自动恢复。

这里要分开管理 **“状态是否新鲜”** 和 **“是否仍有续测授权”**。

**1．停止、完成记录不能简单按时间失效**

| 状态 | 处理规则 |
|---|---|
| 人工停止、正常退出、试验完成 | 撤销本次续测授权，持续有效 |
| 人工暂停 | 保持暂停，不能由外部检查器自动续测 |
| 正在运行，快照持续更新 | 正常监督 |
| 快照停止更新、进程退出或业务停滞 | 根据近期有效授权，判断是否接管 |
| 很久以前的“运行中”，没有近期监督记录 | 不自动恢复，需要重新确认续测 |

**终止记录的含义是“这次试验已经不允许继续”，不能过几小时就被当作过期记录忽略。** 再次开始试验必须产生新的运行标识和授权。

**2．快照至少增加这些字段**

以下是建议字段：

| 字段 | 用途 |
|---|---|
| `RunId` | 每次新启动试验生成唯一标识，区分前后两次试验 |
| `IntentVersion` | 启动、停止、暂停等操作发生时递增，防止旧状态覆盖新决定 |
| `DesiredState` | 应运行、暂停、停止、完成 |
| `PublishedUtc`、`Sequence` | 判断快照是否新鲜、是否持续更新 |
| `LastBusinessProgressUtc` | 判断采样、控制和数据是否真正推进 |
| `RecoveryAdmissionUntilUtc` | 允许外部检查器**首次接管恢复**的截止时间 |

检查器还保存自己的“最后一次确认该试验有效运行”的记录，不能每次启动都仅凭磁盘上的一份文件重新建立信任。

**3．给首次接管设期限，给已经接管的恢复保留连续性**

这里有一个容易设计错的地方：

**快照过期，可能正是程序崩溃的表现。不能规定“快照一过期就绝不恢复”，否则兜底检查器会失去作用。**

建议采用两阶段规则：

- **尚未接管：** 必须是近期仍有授权的本次试验，且处于允许首次接管的时间窗口内。
- **已经接管：** 检查器持久化恢复事务，可以按限频和冷却策略继续尝试，不依赖已经退出的主程序继续刷新快照。

例如，可先将“快照每 10 秒更新、超过 2 分钟视为失联候选、首次接管窗口 15 分钟”作为讨论参数，最终结合你的正常恢复耗时确定。**这些是拟议值，不是当前版本配置。**

如果检查器和主程序都停了很久，第二天才重新运行检查器，即使残留文件写着“运行中”，也已经不能首次接管。

已经接管后，如果检查器自身也长时间失联，再启动时同样需要检查监督连续性，不能靠一个旧的“恢复中”事务无限期续上。

**4．你的典型场景应这样处理**

| 场景 | 结果 |
|---|---|
| 昨天试验完成，今天台架空闲 | 不启动，完成状态持续生效 |
| 昨天人工停止，旧备份还写着运行中 | 以更新的停止决定为准，不启动 |
| 正常试验突然崩溃，下一分钟检查发现 | 授权有效且在接管窗口内，可以恢复 |
| 检查器停用一天后重新启用 | 不根据旧运行快照自动续测 |
| 已经接管，重启限频进入冷却 | 保留恢复事务，满足条件后继续尝试 |
| 恢复过程中用户点击停止 | 立即撤销授权，后续重启和续测均取消 |

实现时，**停止决定要作为可靠的终止记录保留；读不到最新记录或主备记录冲突时，不能退回旧的“允许运行”。** 在启动新进程、尤其是重新允许设备输出之前，都要再次核对授权版本。

这样保留了“近期异常退出后自动恢复”的能力，也明确禁止“台架闲置很久，被旧状态重新唤起试验”。
